매크로 — 선언적·절차적

2026-06-25 약 8분 분량 Rust 시리즈
이 편에서 배우는 것 Rust 매크로는 컴파일 시점에 코드를 생성하는 메타프로그래밍 도구다. macro_rules!로 쓰는 선언적 매크로의 패턴 매칭 문법을 익히고, 매크로가 변수 이름을 더럽히지 않게 막는 위생(hygiene) 개념을 이해한다. 이어서 #[derive]로 대표되는 절차적 매크로가 무엇이고 선언적 매크로와 어떻게 다른지 살펴본다. 마지막으로 함수로 충분한 일에 매크로를 남용하지 않도록 선택 기준을 정리한다.

매크로란 무엇인가

Rust의 매크로는 코드를 입력으로 받아 코드를 출력하는 코드다. 함수가 실행 시점에 값을 다루는 것과 달리, 매크로는 컴파일 시점에 토큰을 받아 그 자리에 새로운 코드를 펼쳐 넣는다. 이렇게 펼쳐 넣는 과정을 매크로 확장(expansion)이라 부른다.

이미 익숙한 println!, vec!, assert_eq! 같은 것들이 모두 매크로다. 이름 뒤의 !가 매크로 호출 표시다. 함수로는 못 하는 일을 하기 때문에 매크로로 만들어졌다. 예를 들어 println!은 인자 개수가 가변이고 포맷 문자열을 컴파일 시점에 검사한다. 일반 함수는 인자 개수가 고정이라 이런 일을 못 한다.

C++ 경험자를 위한 첫 대조 C++의 #define은 전처리기가 순수 텍스트를 치환한다 — 타입도, 스코프도, 괄호도 모른다. 그래서 #define SQ(x) x*x에 SQ(a+b)를 넣으면 a+b*a+b로 깨진다. Rust 매크로는 텍스트가 아니라 토큰 트리 단위로 동작하고, 추상 구문 트리(AST)가 만들어지기 전 단계에서 구조를 보존한 채 확장된다. 전처리기 매크로의 고전적 함정 대부분이 설계 단계에서 사라진다.

선언적 매크로 — macro_rules!

가장 많이 쓰는 매크로는 macro_rules!로 정의하는 선언적 매크로다. match 식과 비슷하게 패턴 → 펼칠 코드 규칙을 나열한다. 다만 매칭 대상이 값이 아니라 Rust 코드 조각(토큰)이라는 점이 다르다.

가장 단순한 형태

인자가 없는 매크로부터 본다. 호출하면 규칙 오른쪽의 코드가 그 자리에 그대로 들어간다.

macro_rules! greet {
    () => {
        println!("Hello, macro!");
    };
}

fn main() {
    greet!(); // println!("Hello, macro!"); 로 확장된다
}

조각 지정자로 입력 받기

매크로는 입력 토큰을 조각 지정자(fragment specifier)로 잡아낸다. $x:expr는 "식 하나를 잡아 $x로 부른다"는 뜻이다. 자주 쓰는 지정자로 expr(식), ty(타입), ident(식별자), literal(리터럴), tt(토큰 트리) 등이 있다.

macro_rules! square {
    (// $x로 식 하나를 잡는다
     $x:expr) => {
        $x * $x
    };
}

fn main() {
    let n = 5;
    let result = square!(n + 1); // (n + 1) * (n + 1) = 36, 텍스트 치환이 아니라 식 단위라 안전하다
    assert_eq!(result, 36);
}

여기서 핵심은 $x가 식 전체를 하나의 단위로 잡는다는 점이다. C의 텍스트 매크로라면 n + 1 * n + 1로 깨지지만, expr 조각은 n + 1을 하나로 묶어 두므로 곱셈이 식 전체에 걸린다.

반복 — 가변 인자 다루기

매크로의 진짜 쓸모는 반복에서 나온다. $( ... )* 문법으로 0개 이상의 입력을 받아 코드를 여러 번 펼친다. 표준 라이브러리의 vec!를 직접 만들어 보면 구조가 잘 보인다.

macro_rules! my_vec {
    // $( $x:expr ),* : 쉼표로 구분된 식들을 0개 이상 잡는다
    ( $( $x:expr ),* $(,)? ) => {
        {
            let mut temp = Vec::new();
            $(
                temp.push($x); // 잡힌 식마다 push 한 줄씩 펼쳐진다
            )*
            temp
        }
    };
}

fn main() {
    let v = my_vec![1, 2, 3];
    assert_eq!(v, vec![1, 2, 3]);
}

$( temp.push($x); )*는 잡아 둔 각 식마다 push 한 줄을 펼친다. my_vec![1, 2, 3]이면 push(1); push(2); push(3); 세 줄로 확장된다. 끝의 $(,)?는 마지막 원소 뒤 쉼표(trailing comma)를 선택적으로 허용한다.

블록으로 감싸 값을 돌려준다 위 예제는 규칙 본문을 { ... } 블록으로 감쌌다. 블록의 마지막 식(temp)이 블록의 값이 되므로, my_vec!를 식처럼 써서 결과를 변수에 바로 받을 수 있다. 매크로가 펼쳐질 자리에 어떤 종류의 코드(식·문장·아이템)가 와야 하는지 늘 의식하면 확장 결과가 예측 가능해진다.

위생 — 매크로가 깨끗한 이유

매크로가 내부에서 임시 변수를 만들면, 그 이름이 호출한 쪽의 변수와 충돌할까 걱정된다. C 매크로에서는 실제로 큰 문제다. 하지만 Rust 매크로는 위생적(hygienic)이라 이 충돌이 기본적으로 일어나지 않는다.

위생이란, 매크로가 만든 식별자와 호출 측의 식별자를 컴파일러가 서로 다른 것으로 구분해 다루는 성질이다. 매크로 안에서 쓴 temp는 호출자가 쓴 temp와 이름만 같을 뿐 별개로 취급된다.

macro_rules! make_temp {
    () => {
        let temp = 99; // 매크로 내부의 temp
    };
}

fn main() {
    let temp = 1;       // 호출자의 temp
    make_temp!();        // 내부 temp는 위생 처리되어 별개다
    assert_eq!(temp, 1); // 호출자의 temp는 1 그대로 — 오염되지 않는다
}

매크로가 temp = 99를 선언했지만, 호출자의 temp는 여전히 1이다. 두 temp는 서로 다른 문맥(syntax context)에 속하므로 컴파일러가 충돌시키지 않는다. 덕분에 매크로 작성자는 호출자가 어떤 변수 이름을 쓸지 신경 쓰지 않아도 된다.

C++ 전처리기와의 결정적 차이 C/C++ 전처리기 매크로에는 위생이 없다. 매크로가 내부에서 int temp;를 선언하면 호출 지점의 같은 이름 변수와 그대로 충돌한다. 그래서 C 매크로 관용구는 __temp_unlikely_name__처럼 충돌을 피하려 일부러 괴상한 이름을 쓰거나, do { ... } while(0) 같은 방어 패턴에 의존한다. Rust는 이 문제 자체를 언어 차원에서 없앴다 — 텍스트 치환이 아니라 문맥을 가진 토큰을 다루기 때문이다.

절차적 매크로 개요

선언적 매크로가 "패턴 → 코드" 규칙으로 충분하지 않을 때, 절차적 매크로(procedural macro)를 쓴다. 절차적 매크로는 입력 토큰 스트림을 받아 Rust 코드로 직접 처리한 뒤 새 토큰 스트림을 돌려주는 함수다. 패턴 매칭이 아니라 임의의 로직으로 코드를 생성하므로 훨씬 강력하다.

절차적 매크로는 별도 크레이트(proc-macro = true)에 정의해야 하고, 보통 syn(파싱)과 quote(코드 생성) 크레이트를 함께 쓴다. 세 종류가 있다.

DERIVE 구조체·열거형에 트레잇 구현을 자동 생성 #[derive(MyTrait)]

가장 흔히 만나는 형태다. #[derive(Debug, Clone)]처럼 타입 정의 위에 붙이면, 그 타입에 대한 트레잇 구현 코드가 자동으로 생성된다. 보일러플레이트를 손으로 쓰지 않게 해 준다.

쓸 때: 여러 타입에 같은 형태의 트레잇 구현을 반복 생성해야 할 때(직렬화·비교·기본값 등).

ATTRIBUTE 임의의 아이템에 붙이는 사용자 정의 속성 #[route(GET, "/")]

함수·구조체 등에 새 속성을 정의해 붙인다. 붙은 아이템을 입력으로 받아 변형하거나 코드를 추가한다. 웹 프레임워크의 라우팅 속성이 대표 예다.

쓸 때: 기존 정의에 메타데이터를 달거나, 정의를 감싸 코드를 주입할 때.

FUNCTION-LIKE 함수 호출처럼 보이는 매크로 sql!(SELECT ...)

macro_rules!처럼 name!(...) 형태로 호출되지만, 내부는 절차적 코드다. 임의의 토큰을 받아 절차적으로 처리한다 — 예를 들어 매크로 안에 적은 SQL을 컴파일 시점에 검증한다.

쓸 때: 입력을 본격적으로 파싱·검증해야 해서 선언적 패턴으로는 부족할 때.

호출하는 쪽 코드는 다음처럼 단순하다. 복잡한 생성 로직은 매크로를 제공하는 크레이트 안에 숨어 있다.

// 표준 라이브러리의 derive 매크로 사용 예 — 별도 의존성 없이 동작한다
#[derive(Debug, Clone, PartialEq)]
struct Point {
    x: i32,
    y: i32,
}

fn main() {
    let p = Point { x: 1, y: 2 };
    let q = p.clone();           // Clone 구현이 자동 생성됨
    assert_eq!(p, q);            // PartialEq 구현이 자동 생성됨
    println!("{:?}", p);         // Debug 구현이 자동 생성됨 → Point { x: 1, y: 2 }
}

Debug, Clone, PartialEq 구현을 손으로 쓰면 수십 줄이지만, derive 한 줄로 끝난다. 이것이 절차적 매크로가 줄여 주는 보일러플레이트의 실제 모습이다.

언제 매크로를 쓰는가

매크로는 강력하지만 비용도 있다. 정의가 읽기 어렵고, 확장된 코드가 눈에 보이지 않아 디버깅이 까다로우며, 컴파일 오류 메시지가 멀리 떨어진 곳을 가리키기도 한다. 그래서 함수나 제네릭으로 되는 일은 그쪽을 먼저 고른다.

상황먼저 고려이유
같은 로직을 여러 타입에 적용제네릭 + 트레잇타입 검사를 온전히 받고 가독성이 높다
값을 받아 값을 돌려줌함수매크로의 복잡도가 필요 없다
가변 인자 / 컴파일 시점 문법 검사선언적 매크로함수로는 불가능한 영역이다
타입 정의에서 코드 자동 생성절차적 매크로(derive 등)보일러플레이트 제거에 적합하다
  • 함수가 먼저다 — 인자 개수가 고정이고 값만 다룬다면 함수로 충분하다. 매크로는 함수로 표현할 수 없는 일에 남겨 둔다.
  • 가변 인자·DSL은 선언적 매크로 — vec!처럼 개수가 가변이거나, 작은 도메인 문법을 만들 때 macro_rules!가 알맞다.
  • 타입 기반 자동 생성은 절차적 매크로 — 타입 정의를 보고 트레잇 구현을 찍어 내는 일은 derive 매크로의 영역이다.
  • 남용 주의 — 매크로는 한 번 쓰면 읽는 사람의 인지 비용이 오래 남는다. 정말 매크로여야 하는지 매번 되묻는다.
매크로는 추상화의 마지막 수단에 가깝다 매크로로 무엇이든 만들 수 있다는 점이 곧 함정이 된다. 타입 시스템의 도움을 우회하기 쉽고, 확장 결과가 코드에 드러나지 않아 협업 비용을 키운다. "이건 함수·제네릭·트레잇으로 정말 안 되나?"를 먼저 답하고, 그래도 안 될 때 매크로를 꺼내는 순서를 권한다.
