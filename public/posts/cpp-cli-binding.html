왜 C++/CLI인가

이미징 라이브러리는 두 세계로 나뉜다. 핵심 이미지 처리 로직은 C++로 짠다. 성능이 필요하고, OpenCV를 쓰고, 나중에 CUDA 커널까지 붙여야 하기 때문이다. 반면 UI는 C# WPF로 만든다. 데이터 바인딩, MVVM, XAML 같은 생산성 도구가 데스크톱 UI에서는 압도적으로 편하다.

문제는 이 둘이 서로 다른 런타임 위에서 돈다는 점이다. C++는 네이티브 머신 코드, C#는 .NET CLR 위의 관리 코드. 그래서 둘을 잇는 다리가 필요하다. C# UI가 C++ 코어의 함수를 호출하고, C++ 코어가 만든 이미지를 C#가 화면에 그릴 수 있어야 한다.

다리를 놓는 방법은 여러 가지가 있다. 짧게 비교한다.

방식장점단점적합한 경우
P/Invoke간단, C API만 있으면 됨복잡한 객체 전달 어려움, 수동 마샬링함수 몇 개만 호출하는 평탄한 C API
C++/CLI객체 그대로 래핑, 타입 안전, 디버깅 한 번에Windows 전용, 빌드 복잡풍부한 C++ 객체 모델을 .NET에 노출
SWIG다중 언어 자동 생성생성 코드 제어 어려움, 학습 곡선여러 언어 바인딩을 동시에
gRPC / IPC프로세스/언어 완전 분리, 크로스 플랫폼직렬화 오버헤드, 대용량 이미지 전송 느림분산 환경, 서비스 분리

ImagingLib처럼 Image, ImageProcessor 같은 C++ 객체를 C# ViewModel에서 자연스럽게 쓰고 싶다면, 같은 프로세스 안에서 객체를 그대로 래핑할 수 있는 C++/CLI가 가장 잘 맞는다.

C++/CLI란

C++/CLI는 Microsoft가 만든 .NET 언어다. 핵심 특징은 같은 소스 파일 안에서 네이티브 C++와 관리(managed) 코드를 섞어 쓸 수 있다는 점이다. 한쪽에서는 std::vector를 쓰고, 바로 아래 줄에서 .NET System::String을 쓸 수 있다.

이게 가능한 이유는 /clr 컴파일 옵션 덕분이다. 이 옵션을 켜면 컴파일러가 네이티브 코드와 .NET IL을 모두 생성할 수 있게 된다. C++/CLI 프로젝트는 결과적으로 .NET 어셈블리(DLL)가 되지만, 그 안에 네이티브 코드를 품을 수 있다.

바인딩 계층은 얇게 유지한다 C++/CLI는 "가장 얇은 바인딩 계층"을 만드는 용도다. 비즈니스 로직을 여기 두면 안 된다. 로직은 네이티브 코어에 두고, C++/CLI는 호출을 그대로 전달하는 통로 역할만 한다. 두꺼워질수록 디버깅이 지옥이 된다.

세 가지 코드 영역

C++/CLI 프로젝트를 이해하려면 코드를 세 영역으로 나눠 봐야 한다.

영역메모리 관리설명
native (네이티브 C++)수동 (delete) 또는 스마트 포인터기존 코어 라이브러리. ImagingLib::ImageProcessor 같은 클래스. C++/CLI는 이 코드를 그대로 가져다 쓴다.
managed (ref class).NET GC가 자동 관리ref class로 선언된 타입. C#에서 일반 클래스처럼 보인다. GC 힙에 할당된다.
C++/CLI wrapper둘을 잇는 코드managed ref class 안에 native 포인터를 들고, 메서드 호출을 네이티브로 전달한다.

핵심은 wrapper가 managed 타입이면서 내부에 native 포인터를 보유한다는 구조다. C#는 wrapper만 보고, wrapper가 네이티브 코어를 대신 호출한다.

ref class 기본

관리 클래스는 ref class 키워드로 선언한다. 다음은 ImagingLib의 ImageProcessor를 래핑하는 최소 형태다.

public ref class ImageProcessorWrapper
{
public:
    ImageProcessorWrapper();
    ~ImageProcessorWrapper();   // Dispose 패턴 (C#의 Dispose)
    !ImageProcessorWrapper();   // finalizer (GC 안전망)
    void ApplyBlur(int kernelSize);

private:
    ImagingLib::ImageProcessor* m_native;  // 네이티브 포인터 보유
};

새로 등장한 문법들을 정리한다.

문법의미C# 대응
ref classGC 힙에 할당되는 관리 클래스class
value class값 타입 (스택 또는 인라인 할당)struct
^ (handle)관리 객체를 가리키는 참조참조 타입 변수
gcnew관리 객체를 GC 힙에 생성new
%handle에 대한 추적 참조ref 비슷
// 관리 객체 생성과 사용
ImageProcessorWrapper^ proc = gcnew ImageProcessorWrapper();
proc->ApplyBlur(5);

// 네이티브 객체는 여전히 new / 스마트 포인터
ImagingLib::ImageProcessor* native = new ImagingLib::ImageProcessor();

생성자에서는 네이티브 객체를 만들어 포인터를 들고, 나머지 메서드는 그 포인터로 네이티브 함수를 호출하면 된다.

ImageProcessorWrapper::ImageProcessorWrapper()
{
    m_native = new ImagingLib::ImageProcessor();
}

void ImageProcessorWrapper::ApplyBlur(int kernelSize)
{
    // 호출을 네이티브로 그대로 전달한다.
    m_native->ApplyGaussianBlur(kernelSize);
}

수명 관리 — Dispose 패턴이 핵심

여기가 C++/CLI에서 가장 중요한 부분이다. .NET GC는 네이티브 메모리를 전혀 모른다. wrapper 객체가 GC에 의해 수거돼도, 내부의 네이티브 포인터(m_native)는 그대로 누수된다. 그래서 네이티브 메모리는 직접 해제해야 한다.

C++/CLI는 이를 위해 두 가지 특수 멤버를 제공한다.

멤버역할호출 시점
~Class() 소멸자C#의 Dispose()로 컴파일됨. IDisposable 자동 구현delete 또는 C# using 종료, 명시적 Dispose()
!Class() finalizerDispose를 깜빡했을 때를 위한 안전망GC가 객체를 수거할 때 (시점 비결정적)
ImageProcessorWrapper::~ImageProcessorWrapper()
{
    // 결정론적 해제 — Dispose 또는 using 종료 시 호출된다.
    this->!ImageProcessorWrapper();  // finalizer에 위임
}

ImageProcessorWrapper::!ImageProcessorWrapper()
{
    // 안전망 — GC가 마지막에 호출한다.
    if (m_native != nullptr)
    {
        delete m_native;
        m_native = nullptr;
    }
}

소멸자가 finalizer를 호출하도록 위임하면, 해제 코드를 한 곳에만 두면서 두 경로 모두를 커버할 수 있다. C# 쪽에서는 using 블록으로 결정론적으로 해제한다.

// C# 쪽 사용 — using으로 즉시 해제
using (var proc = new ImageProcessorWrapper())
{
    proc.ApplyBlur(5);
}  // 블록 종료 시 Dispose() 호출 → 네이티브 메모리 해제
Dispose를 빠뜨리면 네이티브 메모리가 샌다 finalizer가 안전망 역할을 하긴 하지만, GC가 언제 객체를 수거할지는 아무도 모른다. 이미지 버퍼처럼 큰 네이티브 메모리를 들고 있는 객체라면, Dispose를 빠뜨린 채 finalizer만 믿으면 메모리가 한참 동안 안 풀린다. C# 쪽에서는 항상 using을 쓴다.

마샬링 — 타입 변환

마샬링은 관리 타입과 네이티브 타입 사이를 변환하는 작업이다. 기본 타입은 자동으로 처리되지만, 문자열과 배열은 손이 간다.

관리 타입네이티브 타입변환 방법
int, double, boolint, double, bool자동 (그대로 전달)
System::String^std::string / const char*msclr::interop::marshal_as
array<Byte>^uint8_t*pin_ptr로 고정 후 포인터 획득

문자열 변환

msclr/marshal_cppstd.h를 포함하면 marshal_as로 양방향 변환이 된다.

#include <msclr/marshal_cppstd.h>

void ImageProcessorWrapper::LoadFile(System::String^ path)
{
    // 관리 String → std::string
    std::string nativePath = msclr::interop::marshal_as<std::string>(path);
    m_native->LoadFromFile(nativePath);
}

배열과 pin_ptr

배열을 네이티브로 넘길 때는 pin_ptr이 등장한다. GC는 평소에 객체를 메모리 안에서 자유롭게 이동시킨다. 그런데 네이티브 코드가 배열의 포인터를 들고 작업하는 동안 GC가 그 배열을 옮겨버리면, 포인터는 엉뚱한 곳을 가리키게 된다. pin_ptr은 GC가 해당 객체를 이동하지 못하도록 고정한다.

void ProcessManaged(array<Byte>^ data)
{
    // p가 살아있는 동안 data는 메모리에 고정된다.
    pin_ptr<Byte> p = &data[0];
    NativeProcess(p, data->Length);
}  // 스코프 종료 → 고정 해제, GC가 다시 이동 가능
pin_ptr 스코프를 벗어난 포인터는 dangling이다 pin_ptr이 살아있는 스코프 동안에만 고정이 유지된다. 고정된 포인터를 멤버 변수에 저장해 두거나, 비동기 작업에 넘긴 뒤 스코프를 빠져나가면, GC가 객체를 이동시켜 포인터가 무효가 된다. 그 포인터를 다시 쓰면 메모리 손상이다. pin은 짧고 동기적인 구간에서만 쓴다.

예외 변환

네이티브 C++ 예외와 .NET 예외는 서로 다른 메커니즘이다. 네이티브 std::exception이 그대로 C# catch로 잡히지 않는다. 그래서 wrapper의 경계에서 try/catch로 받아 .NET 예외로 변환해야 한다.

ImagingLib의 코어 함수는 ErrorCode를 반환한다. wrapper에서는 이 ErrorCode를 검사해 실패면 .NET 예외를 던지거나, 그대로 enum으로 노출하는 식으로 처리한다.

void ImageProcessorWrapper::ApplyBlur(int kernelSize)
{
    try
    {
        ImagingLib::ErrorCode ec = m_native->ApplyGaussianBlur(kernelSize);
        if (ec != ImagingLib::ErrorCode::Ok)
        {
            // 네이티브 ErrorCode → .NET 예외로 변환
            throw gcnew System::InvalidOperationException(
                "ApplyBlur failed: " + (int)ec);
        }
    }
    catch (const std::exception& e)
    {
        // 네이티브 예외 → .NET 예외로 변환
        throw gcnew System::Exception(
            msclr::interop::marshal_as<System::String^>(e.what()));
    }
}
경계에서 한 번만 변환한다 예외 변환은 wrapper 메서드 안에서만 한다. 네이티브 예외가 C++/CLI 경계를 넘어 C#까지 그대로 새어 나가면, 호출 스택과 메시지가 깨진 상태로 잡혀 디버깅이 어렵다.

이미지 데이터 전달 (ImagingLib 컨텍스트)

이미징 라이브러리에서 가장 자주 하는 일은 C++ Image를 C# 화면에 띄우는 것이다. WPF에서는 보통 BitmapSource 또는 WriteableBitmap으로 변환한다.

전략은 두 가지다.

전략장점단점
복사 (픽셀 버퍼를 .NET 쪽으로 복사)안전 — 네이티브 수명과 무관매 프레임 복사 비용
공유 (네이티브 버퍼를 직접 참조)빠름 — 복사 없음네이티브 버퍼 수명을 직접 관리해야 함

실시간 라이브 뷰처럼 성능이 중요하면, WriteableBitmap의 BackBuffer를 네이티브에 넘겨 직접 채우게 하는 방식이 효율적이다. BackBuffer를 pin한 뒤 네이티브 코드가 그 메모리에 픽셀을 써넣는다.

void ImageWrapper::CopyToBitmap(System::Windows::Media::Imaging::WriteableBitmap^ bmp)
{
    bmp->Lock();
    try
    {
        // BackBuffer는 IntPtr — 네이티브가 직접 채운다.
        uint8_t* dst = static_cast<uint8_t*>(bmp->BackBuffer.ToPointer());
        m_native->CopyPixelsTo(dst, bmp->BackBufferStride, bmp->PixelHeight);
        bmp->AddDirtyRect(System::Windows::Int32Rect(0, 0,
            bmp->PixelWidth, bmp->PixelHeight));
    }
    finally
    {
        bmp->Unlock();
    }
}
한 장짜리는 복사, 스트림은 공유 파일에서 한 번 불러와 보여주는 정적 이미지는 그냥 복사하면 안전하고 충분하다. 카메라 라이브 뷰처럼 초당 수십 프레임이 흐르는 경우에만 BackBuffer 직접 쓰기 같은 공유 전략을 고려한다.

콜백 — C# delegate와 C++ 함수 포인터

네이티브 코어가 진행률이나 에러를 알려줘야 할 때 콜백이 필요하다. 네이티브 코어는 C++ 함수 포인터를 받고, C# UI는 delegate를 쓴다. 이 둘을 잇는 것이 Marshal::GetFunctionPointerForDelegate다. delegate를 네이티브가 호출할 수 있는 함수 포인터로 변환해 준다.

// C#에서 전달받을 delegate 타입
public delegate void ProgressCallback(int percent);

ref class ImageProcessorWrapper
{
private:
    ProgressCallback^ m_callback;  // delegate 참조를 멤버로 유지!

public:
    void SetProgressHandler(ProgressCallback^ cb)
    {
        m_callback = cb;  // GC되지 않도록 참조 보관
        System::IntPtr fp =
            System::Runtime::InteropServices::Marshal::GetFunctionPointerForDelegate(cb);
        // 네이티브 함수 포인터 타입으로 캐스팅해 코어에 등록
        m_native->RegisterCallback(
            static_cast<void(*)(int)>(fp.ToPointer()));
    }
};
delegate 참조를 유지하지 않으면 콜백 시 크래시한다 GetFunctionPointerForDelegate로 얻은 함수 포인터는 delegate 객체가 살아있어야만 유효하다. delegate를 멤버 변수 등으로 붙잡아 두지 않으면 GC가 수거해 버리고, 네이티브 코어가 나중에 그 함수 포인터를 호출하는 순간 죽은 메모리를 실행하게 된다. delegate는 콜백이 등록된 동안 반드시 참조를 살려 둔다.

빌드 구성

솔루션은 세 프로젝트로 구성된다. 각각 빌드 설정이 다르다.

프로젝트산출물빌드 설정
NativeCore.lib (정적 라이브러리)일반 네이티브 빌드 (/clr 끔)
CliBridge.dll (.NET 어셈블리)/clr 켬, NativeCore 링크
CSharpApp.exe (WPF 앱)일반 C# 빌드, CliBridge 참조

의존 방향은 NativeCore.lib → CliBridge.dll → CSharpApp.exe 한 줄로 흐른다. C# 앱은 CliBridge만 참조하면 되고, 네이티브 코어는 직접 보이지 않는다.

아키텍처와 런타임을 일치시킨다 세 프로젝트의 플랫폼은 모두 x64로 통일한다. 하나라도 x86이거나 AnyCPU로 섞이면 로드 시점에 BadImageFormatException이 난다. C/C++ 런타임 라이브러리 설정(MD/MDd)도 디버그·릴리스 간에 일치시켜야 한다.

C++/CLI의 한계와 미래

C++/CLI는 강력하지만 제약도 분명하다.

  • Windows 전용 — CLR과 네이티브 코드를 한 어셈블리에 섞는 구조 자체가 Windows에 묶여 있다. Linux/macOS로는 못 간다.
  • .NET Core / .NET 5+ 지원이 제한적 — .NET Framework 시절보다 지원 범위가 좁다. .NET 5 이후로 C++/CLI 컴파일은 가능하지만 여전히 Windows 한정이고, 일부 기능에 제약이 있다.
  • 빌드 복잡도 — /clr 프로젝트는 컴파일이 느리고, 네이티브와 관리 코드가 섞이면서 에러 메시지가 난해해진다.

만약 크로스 플랫폼이 목표라면 C++/CLI는 답이 아니다. 그때는 네이티브 코어를 평탄한 C API로 노출하고 P/Invoke로 호출하거나, 아예 별도 프로세스로 분리해 IPC로 통신하는 쪽을 고려한다. ImagingLib는 현재 Windows 데스크톱 + WPF가 명확한 타깃이므로 C++/CLI가 합리적인 선택이다.

흔한 함정

C++/CLI에서 반복적으로 밟는 지뢰들을 모았다.

함정결과대응
Dispose 누락네이티브 메모리 누수C#에서 항상 using, 소멸자에서 네이티브 delete
pin_ptr 스코프 밖 포인터 사용GC 이동으로 dangling, 메모리 손상pin은 짧고 동기적인 구간에서만
delegate 참조 미유지콜백 호출 시 크래시delegate를 멤버로 붙잡아 수명 유지
ref class에 네이티브 멤버를 값으로 보유컴파일 에러 (불가능)네이티브 멤버는 반드시 포인터로 보유
헤더에 네이티브/관리 코드 혼재컴파일 복잡도·시간 폭증관리 인터페이스와 네이티브 헤더를 분리
ref class는 네이티브 객체를 값으로 품을 수 없다 ref class는 GC 힙에 올라가는데, 네이티브 객체는 GC가 관리하지 못한다. 그래서 ImagingLib::ImageProcessor m_native;처럼 값으로 멤버를 두면 컴파일 자체가 안 된다. 반드시 ImagingLib::ImageProcessor* m_native; 포인터로 들고, 생성자에서 만들고 소멸자/finalizer에서 delete한다.
헤더 분리는 빌드 속도를 살린다 네이티브 헤더와 관리 코드를 한 헤더에 섞으면, 그 헤더를 포함하는 모든 곳이 /clr 컴파일을 강제당한다. 관리 타입 선언은 wrapper 헤더에만, 네이티브 헤더는 .cpp에서만 포함하는 식으로 경계를 명확히 긋는다.
