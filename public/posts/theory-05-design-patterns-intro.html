디자인 패턴이란 무엇인가

디자인 패턴(Design Pattern)은 소프트웨어 설계에서 자주 마주치는 문제에 대한, 검증된 해법의 템플릿이다. 핵심은 "템플릿"이라는 단어다. 패턴은 복사해서 붙여 넣는 코드 조각이 아니라, 특정 상황에서 객체와 클래스를 어떻게 배치할지에 대한 구조의 청사진이다.

같은 패턴이라도 언어가 다르고 도메인이 다르면 구현 코드는 전혀 다르게 나온다. 그래서 패턴은 "코드"가 아니라 "설계 어휘(design vocabulary)"로 이해하는 편이 정확하다. 두 개발자가 "여기는 Strategy로 가자"라고 말하면, 한 문장으로 클래스 구조·확장 지점·의도가 전달된다. 패턴이 없다면 같은 내용을 설명하는 데 화이트보드 한 장이 필요하다.

패턴 = 문제 + 해법 + 결과 모든 패턴 기술서는 세 가지를 함께 적는다. 어떤 문제 상황인가, 어떤 해법 구조를 쓰는가, 그 결과 어떤 트레이드오프가 생기는가. 해법만 외우고 문제와 결과를 빼먹으면 패턴을 잘못 쓰게 된다.

패턴의 역사 — 건축에서 소프트웨어로

"패턴"이라는 개념은 소프트웨어가 아니라 건축에서 왔다. 건축가 Christopher Alexander는 1977년 저서 A Pattern Language에서, 좋은 건물과 도시에는 반복되는 설계 규칙이 있다고 정리했다. 예를 들어 "사람이 머무는 공간에는 양쪽에서 빛이 들어와야 한다" 같은 규칙에 이름을 붙이고, 각 규칙을 문제·해법·맥락으로 기술했다.

이 아이디어를 소프트웨어로 가져온 것이 1994년 출간된 Design Patterns: Elements of Reusable Object-Oriented Software다. 저자 네 명(Erich Gamma, Richard Helm, Ralph Johnson, John Vlissides)을 흔히 GoF(Gang of Four)라고 부른다. 이 책은 객체지향 설계에서 반복적으로 나타나는 23개의 패턴을 체계적으로 정리했고, 이후 디자인 패턴 논의의 공통 기준이 되었다.

GoF 패턴은 "발명"이 아니라 "발견"이다 GoF는 패턴을 새로 만든 것이 아니라, 당시 잘 작성된 객체지향 코드에서 반복적으로 나타나던 구조를 추출해 이름을 붙였다. 패턴은 현장의 경험을 정리한 결과물이다.

GoF 23패턴의 3분류

GoF는 23개 패턴을 목적에 따라 세 갈래로 나눴다. 무엇을 다루는 패턴인가를 기준으로 한다.

GoF 23패턴의 3분류 맵 — 생성 5종, 구조 7종, 행위 11종

생성 패턴 (Creational)

객체를 어떻게 만드느냐를 다룬다. new를 직접 호출하면 코드가 구체 클래스에 묶인다. 생성 패턴은 생성 과정을 별도의 책임으로 분리해, 무엇을 만들지·어떻게 조립할지를 유연하게 바꿀 수 있게 한다. Singleton은 인스턴스를 하나로 제한하고, Factory Method와 Abstract Factory는 생성할 클래스를 런타임에 결정하며, Builder는 복잡한 객체를 단계적으로 조립하고, Prototype은 기존 객체를 복제한다. 자세한 내용은 6편에서 다룬다.

구조 패턴 (Structural)

객체와 클래스를 어떻게 조합하느냐를 다룬다. 더 큰 구조를 만들면서도 각 부분을 독립적으로 유지하는 것이 목표다. Adapter는 호환되지 않는 인터페이스를 맞춰 주고, Decorator는 기능을 동적으로 덧붙이며, Facade는 복잡한 서브시스템에 단순한 창구를 제공하고, Proxy는 실제 객체에 대한 대리 접근을 만든다. Composite·Bridge·Flyweight도 여기 속한다. 자세한 내용은 7편에서 다룬다.

행위 패턴 (Behavioral)

객체들이 책임을 어떻게 나누고 어떻게 상호작용하느냐를 다룬다. 가장 수가 많은 분류다. Strategy는 알고리즘을 교체 가능하게 만들고, Observer는 상태 변화를 구독자에게 전파하며, Command는 요청을 객체로 캡슐화하고, State는 상태에 따라 동작을 바꾼다. Template Method·Iterator·Visitor·Mediator 등도 포함된다. 자세한 내용은 8편에서 다룬다.

분류다루는 것대표 패턴
생성 (Creational)객체 생성 방식Singleton, Factory Method, Abstract Factory, Builder, Prototype
구조 (Structural)객체·클래스 조합Adapter, Decorator, Facade, Proxy, Composite, Bridge, Flyweight
행위 (Behavioral)객체 간 책임·상호작용Strategy, Observer, Command, State, Template Method, Iterator, Visitor, Mediator, Memento, Chain of Responsibility, Interpreter

패턴이 주는 것

패턴을 배우는 실질적인 이득은 세 가지다.

공통 어휘 — 팀 소통

가장 큰 가치다. "이 클래스는 Observer로 구독자에게 알린다"라는 한 문장이, 긴 설명 없이 구조와 의도를 전달한다. 코드 리뷰·설계 회의·문서에서 패턴 이름은 압축된 소통 단위로 작동한다. 팀이 같은 어휘를 공유하면 설계 논의의 속도가 달라진다.

검증된 해법

패턴은 수많은 프로젝트에서 다듬어진 구조다. 처음 마주치는 문제라도 패턴을 알면 바닥부터 고민하지 않아도 된다. 함정과 트레이드오프까지 이미 문서화되어 있어, 같은 실수를 반복할 가능성이 줄어든다.

설계 유연성

대부분의 패턴은 "변하는 부분"과 "변하지 않는 부분"을 분리한다. 이 경계가 잘 잡히면 요구사항이 바뀌어도 영향 범위가 좁아진다. 패턴은 결국 변화를 흡수하는 지점을 미리 설계에 심어 두는 도구다.

언제 쓰고 언제 쓰지 말아야 하나

패턴의 가치를 인정하더라도, 더 중요한 질문은 "언제 쓰지 말아야 하나"다. 패턴은 실제로 문제가 있을 때만 쓴다. 아직 존재하지 않는 변화를 대비해 패턴을 먼저 까는 것은 거의 항상 손해다.

함정 1 — 패턴을 위한 패턴 (over-engineering) 값 하나만 바뀌는 자리에 Strategy를 넣고, 인스턴스가 하나뿐이라는 이유만으로 Singleton을 만들고, 한 곳에서만 쓰는 객체에 Factory를 두는 식이다. 패턴은 공짜가 아니다. 클래스 수가 늘고 호출 흐름이 간접화되어, 코드를 처음 읽는 사람이 추적해야 할 단계가 길어진다. 변화가 실제로 일어나지 않으면 이 비용은 그냥 손실이다.
함정 2 — 패턴 중독 (pattern addiction) 패턴을 막 배운 시기에 흔히 빠지는 함정이다. 모든 문제를 패턴으로 풀려 하고, 단순한 if 분기로 충분한 자리에 State를 끌어온다. 패턴을 많이 쓴 코드가 좋은 코드라는 착각이 원인이다. 좋은 설계의 기준은 패턴 개수가 아니라, 문제를 가장 단순하게 푸는 것이다. 패턴이 보이지 않는 코드가 더 나은 경우도 많다.

판단 기준은 간단하다. 지금 겪고 있는 구체적인 고통이 있는가. 같은 코드를 반복 수정하고 있는가, 분기가 통제 불능으로 늘어나는가, 확장할 때마다 기존 코드를 건드리는가. 이런 신호가 있을 때 그 신호에 맞는 패턴을 골라 쓴다. 신호가 없으면 가장 단순한 코드를 유지하고, 필요해질 때 리팩토링으로 패턴을 도입한다. 패턴은 설계의 출발점이 아니라 리팩토링의 목적지인 경우가 더 많다.

패턴 vs 원칙 vs 관용구

설계를 이야기할 때 자주 섞여 쓰이는 세 가지 개념이 있다. 추상화 수준이 서로 다르다.

구분무엇인가추상화 수준예시
원칙 (Principle)좋은 설계가 따라야 할 일반 지침가장 추상적 · 언어 무관SOLID, DRY, KISS
패턴 (Pattern)반복되는 문제에 대한 구조적 해법 템플릿중간 · 대체로 언어 무관Strategy, Observer, Factory
관용구 (Idiom)특정 언어에서 굳어진 관용적 해법가장 구체적 · 언어 종속C++ RAII, Pimpl, copy-and-swap

원칙은 "왜"에 가깝다. SOLID의 OCP(개방-폐쇄 원칙)는 "확장에는 열려 있고 수정에는 닫혀 있어야 한다"는 방향만 제시할 뿐, 구체적인 클래스 구조를 정해 주지 않는다. 패턴은 그 원칙을 만족시키는 구체적인 "어떻게"다. Strategy 패턴은 OCP를 실제 코드 구조로 실현하는 한 가지 방법이다. 관용구는 한 발 더 내려가, 특정 언어의 문법과 메모리 모델에 맞춰 굳어진 해법이다.

C++의 RAII가 대표적인 관용구다. "자원의 수명을 객체의 수명에 묶는다"는 이 기법은 C++의 소멸자 보장이 있기에 성립한다. 가비지 컬렉터가 있는 언어에는 그대로 옮겨지지 않는다. GoF 패턴이 여러 언어에서 통하는 것과 달리, 관용구는 언어를 떠나면 의미가 사라진다.

// 관용구(idiom): C++ RAII — 소멸자가 자원 해제를 보장한다.
class FileHandle
{
public:
    explicit FileHandle(const std::string& path)
        : m_file(std::fopen(path.c_str(), "rb"))
    {
    }

    ~FileHandle()  // 스코프를 벗어나면 자동 호출
    {
        if (m_file)
        {
            std::fclose(m_file);
        }
    }

private:
    std::FILE* m_file;
};

// 이 구조는 "패턴"이 아니라 C++의 수명 모델에 묶인 "관용구"다.

패턴은 만능이 아니다

GoF 책이 1994년에 나왔다는 점을 기억해야 한다. 당시 주류 언어는 C++와 초기 자바였고, 함수는 일급 시민이 아니었다. 그래서 "동작 하나를 객체로 감싸 교체 가능하게 만든다"는 작업에 별도의 클래스 계층이 필요했다. 그것이 Strategy 패턴이 클래스 위주로 기술된 이유다.

오늘날 C++는 람다와 std::function을 제공한다. 함수를 값처럼 전달할 수 있게 되자, Strategy의 많은 사례는 별도 클래스 없이 함수 객체 하나로 끝난다. 즉 언어가 발전하면 일부 패턴은 언어 기능으로 흡수된다. Iterator는 range-based for로, Command의 단순한 경우는 람다로 녹아든다.

// 1994년식 Strategy — 별도 클래스 계층
struct ICompareStrategy
{
    virtual ~ICompareStrategy() = default;
    virtual bool Less(int a, int b) const = 0;
};

// 현대 C++ — 함수가 일급 시민이므로 패턴이 언어 기능에 흡수된다.
std::function<bool(int, int)> compare = [](int a, int b) { return a < b; };
std::sort(v.begin(), v.end(), compare);  // 클래스 없이 전략 교체
패턴은 정적인 정답이 아니다 패턴은 특정 시대·특정 언어의 제약 위에서 정리된 해법이다. 제약이 바뀌면 해법도 바뀐다. 패턴의 이름과 구조를 외우는 것보다, 그 패턴이 풀려던 문제를 이해하는 것이 오래간다. 문제는 남지만, 해법의 모양은 언어와 함께 변한다.

산업 SW 관점에서 본 패턴

패턴은 억지로 끼워 넣는 것이 아니라, 문제 구조가 분명한 곳에서 자연스럽게 드러난다. 데이터 플로우 기반의 이미징 SDK를 예로 들면 패턴이 등장하는 지점이 또렷하다.

설계 요소드러나는 패턴이유
IProcessBlock 인터페이스Strategy블러·임계화·엣지 등 처리 알고리즘을 교체 가능한 단위로 다룬다
블록 팩토리Factory Method블록 이름(문자열)으로 구체 블록 객체를 생성해, 생성 코드와 사용 코드를 분리한다
데이터 플로우 실행Observer / Command한 블록의 출력 변화가 연결된 블록으로 전파되고, 각 실행 단위는 객체로 캡슐화된다
// IProcessBlock — Strategy 패턴이 자연스럽게 드러나는 지점.
// 처리 블록은 모두 같은 인터페이스를 따르고, 알고리즘만 교체된다.
class IProcessBlock
{
public:
    virtual ~IProcessBlock() = default;

    // Process the input image and produce an output image.
    virtual ErrorCode Process(const Image& input, Image& output) = 0;
};

// 블록 팩토리 — Factory 패턴. 생성 책임을 한 곳으로 모은다.
std::unique_ptr<IProcessBlock> CreateBlock(const std::string& blockType);

여기서 중요한 점은, 설계자가 "Strategy를 쓰자"라고 먼저 결정한 것이 아니라는 것이다. "처리 블록은 종류가 늘어나고 런타임에 교체되어야 한다"는 요구사항이 먼저 있었고, 그 요구를 정직하게 풀다 보니 결과 구조가 Strategy의 모양이 된 것이다. 패턴 이름은 그 구조를 사후에 부르는 라벨일 뿐이다. 이것이 패턴을 쓰는 올바른 순서다.

흔한 오해

오해 1 — 패턴을 많이 쓰면 좋은 코드다

반대인 경우가 더 많다. 패턴은 간접화 비용을 동반한다. 문제가 없는 곳에 패턴을 쓰면 코드는 읽기 어려워지기만 한다. 좋은 코드의 기준은 패턴 개수가 아니라, 문제를 가장 단순하게 푸는 것이다.

오해 2 — 패턴 이름을 외우는 것이 목적이다

23개 패턴의 이름과 클래스 다이어그램을 암기해도, 어떤 문제에 어떤 패턴이 맞는지 모르면 쓸모가 없다. 외워야 할 것은 이름이 아니라 "이 패턴은 어떤 고통을 해결하는가"다. 문제 인식이 먼저고 패턴 이름은 나중이다.

오해 3 — 모든 곳에 패턴을 적용해야 한다

대부분의 코드는 패턴 없이 직선적으로 작성되어야 한다. 패턴은 변화가 예상되거나 이미 고통이 발생한 일부 지점에만 들어간다. 전체 코드베이스를 패턴으로 도배하면, 정작 패턴이 필요한 핵심 지점이 묻혀 버린다.

정리 — 패턴은 어휘이자 도구다 패턴은 검증된 설계 어휘이고, 팀 소통과 유연성을 준다. 하지만 만능이 아니고, 문제가 있을 때만 쓰는 도구다. 다음 6·7·8편에서 생성·구조·행위 패턴을 하나씩 코드로 살펴보되, 항상 "이 패턴이 푸는 문제는 무엇인가"를 먼저 묻는다.
