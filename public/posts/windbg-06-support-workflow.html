왜 "워크플로"가 필요한가

크래시 하나를 분석하는 기술은 1~5편에서 다뤘다. 그런데 실무에서 막히는 지점은 분석 기술 자체가 아니다. "고객사에서 받은 덤프가 내 심볼과 안 맞는다", "재현이 안 된다", "릴리스 빌드라 콜스택이 깨진다" 같은 운영 문제다.

머신비전 SDK는 고객사의 PC, OS 버전, 카메라 드라이버, 다른 벤더 SDK와 섞여 돌아간다. 내 개발 PC에서 재현되는 경우는 오히려 드물다. 그래서 덤프 하나로 끝까지 분석할 수 있는 체계를 미리 갖춰 두는 것이 핵심이다. 이 글은 그 체계를 정리한다.

분석은 빌드 시점에 결정된다 덤프가 와도 그 빌드의 .pdb가 없으면 콜스택을 못 읽는다. 즉 기술지원 성공 여부는 장애가 나기 한참 전, 릴리스를 빌드하던 그 순간에 이미 절반이 결정된다. 심볼 아카이빙(3절)이 이 시리즈에서 가장 중요한 실무 포인트다.

고객사 덤프 수집 SOP

장애가 접수되면 "덤프 파일 하나"만 받아서는 부족하다. 분석에 필요한 정보를 한 번에 받는 표준 절차를 만들어 두면 왕복을 줄인다.

무엇을 받아야 하는가

항목이유
크래시 덤프(.dmp)분석의 본체. full dump 권장(힙·핸들 정보 포함)
SDK / 제품 정확한 버전해당 빌드의 pdb를 찾기 위해 (예: 1.4.2 build 3033)
OS 버전·비트수Windows 10/11, x64/x86 — 심볼·동작 차이
재현 절차 / 발생 빈도매번? 가끔? 특정 조작 후? — 분석 범위를 좁힌다
제품 로그 파일크래시 직전 동작 추적 (spdlog 등)
카메라·그래버·드라이버 정보외부 모듈 충돌 가능성 확인
고객사에 보낼 한 장 가이드 고객사 담당자는 개발자가 아닌 경우가 많다. "작업 관리자에서 덤프 만드는 법" 또는 "WER 로컬 덤프 레지스트리 설정(1편 참조)"을 캡처와 함께 한 장으로 만들어 두면, 매 장애마다 설명을 반복하지 않아도 된다.

제품에 덤프 생성을 내장하기

가장 확실한 방법은 제품이 스스로 크래시 시 덤프를 남기게 하는 것이다. 최상위 예외 핸들러를 등록해 두면 고객사 설정에 의존하지 않는다.

// 프로세스 시작 시 1회 등록
SetUnhandledExceptionFilter(MyCrashHandler);

LONG WINAPI MyCrashHandler(EXCEPTION_POINTERS* ep)
{
    // MiniDumpWriteDump로 덤프 저장 (dbghelp.dll)
    HANDLE hFile = CreateFileW(L"crash.dmp", GENERIC_WRITE, 0,
                               nullptr, CREATE_ALWAYS, 0, nullptr);
    MINIDUMP_EXCEPTION_INFORMATION mei{};
    mei.ThreadId          = GetCurrentThreadId();
    mei.ExceptionPointers = ep;
    mei.ClientPointers    = FALSE;

    MiniDumpWriteDump(GetCurrentProcess(), GetCurrentProcessId(),
                      hFile,
                      MiniDumpWithFullMemory,   // 정보량 ↔ 크기 트레이드오프
                      &mei, nullptr, nullptr);
    CloseHandle(hFile);
    return EXCEPTION_EXECUTE_HANDLER;
}

MiniDumpWithFullMemory는 파일이 크지만 힙까지 담아 분석이 쉽다. 용량이 부담이면 MiniDumpNormal + MiniDumpWithIndirectlyReferencedMemory 조합으로 줄인다. 덤프 종류 트레이드오프는 1편에서 다뤘다.

빌드별 심볼 아카이빙

이 시리즈를 통틀어 가장 실무적으로 중요한 절이다. 고객사 덤프를 분석하려면 그 덤프를 만든 바로 그 빌드의 .pdb가 있어야 한다. 빌드할 때마다 pdb를 버리면, 나중에 어떤 덤프도 제대로 못 읽는다.

pdb는 빌드마다 고유하다

같은 소스라도 다시 빌드하면 pdb의 시그니처(GUID + Age)가 달라진다. WinDbg는 덤프 안에 기록된 모듈의 시그니처와 정확히 일치하는 pdb만 로드한다. "비슷한 버전" pdb는 안 통한다. 그래서 릴리스로 내보낸 모든 빌드의 pdb를 영구 보관해야 한다.

사내 심볼 서버 (symstore)

pdb를 버전 폴더에 수동으로 모으는 것도 되지만, 규모가 커지면 심볼 서버가 답이다. Debugging Tools for Windows의 symstore.exe로 빌드 산출물의 pdb를 시그니처 기준으로 저장한다.

:: 빌드 직후 CI에서 실행 — pdb(와 exe/dll)를 심볼 서버에 적재
symstore add /r /f "build\out\*.*" ^
  /s "\\fileserver\symbols" ^
  /t "ImagingSDK" /v "1.4.2.3033"

분석 PC의 심볼 경로에 사내 서버를 Microsoft 심볼 서버보다 앞에 둔다. WinDbg가 덤프의 시그니처로 알아서 맞는 pdb를 찾아온다.

.sympath srv*\\fileserver\symbols;srv*C:\symbols*https://msdl.microsoft.com/download/symbols
.reload /f
소스 인덱싱까지 하면 금상첨화 pdb에 소스 버전 정보(소스 인덱싱)나 소스 서버를 연동하면, WinDbg가 그 빌드 시점의 소스까지 자동으로 띄워 준다. 빌드와 소스 커밋을 묶어 두는 것이 핵심이다 — 덤프의 콜스택 줄 번호가 어느 커밋의 코드인지 바로 확인된다.

재현되지 않는 버그 대응

"고객사에서만 나고 우리 쪽에선 재현이 안 된다." 기술지원에서 가장 흔하고 가장 까다로운 상황이다. 덤프와 로그만으로 좁혀야 한다.

덤프 하나를 끝까지 짜낸다

  • 예외 컨텍스트 — .ecxr 후 kb로 정확한 크래시 콜스택 (3편)
  • 전체 스레드 — ~*kb로 다른 스레드가 무엇을 하고 있었는지 (5편)
  • 모듈 목록 — lm으로 예상 못 한 외부 DLL(후킹 툴, 백신, 다른 SDK) 주입 여부
  • 지역 변수·인자 — full dump면 dv, dt로 크래시 당시 값 추적

로그를 분석 친화적으로 설계한다

재현 안 되는 버그는 결국 로그가 말해 준다. 평소 제품 로그를 분석에 유리하게 설계해 두는 것이 사후 대응을 좌우한다.

  • 크래시 직전 N줄을 항상 남기도록 충분한 로그 레벨/롤링 정책
  • 스레드 ID·타임스탬프를 모든 줄에 — 덤프의 스레드와 로그를 대조
  • 주요 상태 전이(버퍼 할당/해제, 카메라 grab 시작/종료)를 기록

조건부 덤프로 함정을 놓는다

특정 예외가 날 때만 덤프를 뜨게 하면, 가끔 나는 버그도 잡을 수 있다. ProcDump을 고객사에 띄워 두는 방식이다(1편).

:: 1차·2차 예외 발생 시마다 full dump, 무한 대기
procdump -ma -e 1 -f "" ImagingApp.exe C:\dumps

:: CPU가 일정 시간 이상 100% 유지되면 덤프 (행/무한루프 추적)
procdump -ma -c 90 -s 10 ImagingApp.exe C:\dumps

릴리스 빌드 디버깅의 한계

고객사에 나가는 건 최적화된 릴리스 빌드다. 디버그 빌드처럼 깔끔하게 안 읽힌다.

릴리스도 반드시 pdb를 만든다

가장 중요한 전제. Visual Studio에서 릴리스 구성도 디버그 정보를 생성하게 둔다.

  • 컴파일러: /Zi (또는 /Z7) — 디버그 정보 생성
  • 링커: /DEBUG + /OPT:REF /OPT:ICF — pdb는 만들되 최적화는 유지

이렇게 해도 실행 성능은 그대로다. pdb는 별도 파일이라 배포본에 안 섞인다. 단지 빌드 산출물로 보관(아카이빙)만 하면 된다.

최적화가 만드는 한계

증상원인대응
콜스택에 함수가 빠짐인라인 확장/Ob0로 핫픽스 빌드 또는 인라인 감안하고 해석
지역 변수 값이 안 보임레지스터로 최적화레지스터(r)·인접 메모리에서 유추
콜스택 줄 번호가 살짝 어긋남명령어 재배치전후 줄을 함께 의심
Frame Pointer Omission/Oy 최적화pdb의 FPO 데이터로 WinDbg가 보정(심볼 필수)
심볼만 맞으면 릴리스도 충분히 읽힌다 최적화 한계가 있어도, 정확한 pdb만 있으면 !analyze -v와 kb로 원인 함수까지 가는 경우가 대부분이다. 결국 다시 심볼 아카이빙(3절)으로 귀결된다.

장애 대응 체크리스트

접수부터 회신까지의 흐름을 한 장으로 정리한다. 이 시리즈 전체가 이 체크리스트의 각 단계에 대응한다.

기술지원 워크플로

① 접수 — 덤프 + 정확한 버전 + OS + 재현 절차 + 로그 + 드라이버 정보 수집(2절 SOP)
② 환경 구성 — 해당 빌드의 pdb를 심볼 서버에서 확보, 소스는 같은 커밋으로 체크아웃(3절)
③ 1차 분석 — !analyze -v → 예외 코드·폴트 모듈 확인(3편)
④ 유형 판별 — 단순 크래시 / 힙 손상(4편) / 데드락·행(5편) 분기
⑤ 심화 분석 — 콜스택·전체 스레드·힙 블록·락 소유자 추적
⑥ 로그 대조 — 스레드 ID·타임스탬프로 덤프와 로그 매칭, 직전 동작 확인
⑦ 결론·회신 — 원인 함수/조건 특정 → 임시 회피책 + 수정 버전 일정 안내
⑧ 재발 방지 — 같은 유형을 막을 어서션·검증 코드, 필요 시 조건부 덤프 함정 추가

시리즈를 마치며 덤프 분석은 "크래시가 난 다음"의 기술처럼 보이지만, 실제로는 릴리스를 빌드하는 순간(pdb 아카이빙)부터 로그를 설계하는 평소 습관까지 모두 포함하는 예방·대응 체계다. 1~5편의 분석 기술에 이 워크플로를 더하면, 고객사 어디에서 크래시가 나도 덤프 하나로 추적할 수 있다.
