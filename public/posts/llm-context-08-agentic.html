정적 프롬프트에서 동적 컨텍스트로

에이전트의 한 스텝은 대략 이렇게 돈다: 모델이 도구를 호출 → 도구가 결과를 반환 → 그 결과가 컨텍스트에 추가됨 → 모델이 다음을 판단. 이 루프가 수십 번 돌면 컨텍스트에는 지시 + 원래 질문 + 수많은 도구 호출과 그 결과 + 중간 추론이 켜켜이 쌓인다.

그래서 에이전트의 컨텍스트 엔지니어링은 "매 스텝 모델에게 보낼 컨텍스트를 동적으로 조립하는 것"이 된다. 무엇을 남기고, 무엇을 요약하고, 무엇을 버릴지를 매번 결정해야 한다. 이것이 최근 "프롬프트 엔지니어링"보다 "컨텍스트 엔지니어링"이라는 말이 쓰이는 핵심 이유다.

컨텍스트가 망가지는 4가지 방식

긴 컨텍스트는 단지 비쌀 뿐 아니라 품질을 떨어뜨린다. 대표적 실패 유형이 정리돼 있다(Drew Breunig 등).

실패무엇
Poisoning(오염)한 번 들어간 환각·오류가 컨텍스트에 남아 이후 판단을 계속 오염시킴
Distraction(산만)컨텍스트가 너무 길어 모델이 핵심보다 곁가지에 끌려감
Confusion(혼동)관련 없는 정보·도구가 많아 모델이 무엇을 쓸지 헷갈림
Clash(충돌)컨텍스트 안의 정보끼리 모순돼 모델이 잘못된 쪽을 따름

핵심 교훈: 컨텍스트는 쌓을수록 좋은 게 아니라, 관리하지 않으면 독이 된다. 특히 poisoning은 무섭다 — 에이전트가 초반에 한 번 잘못된 사실을 "기억"하면, 그 뒤 모든 스텝이 오염된 전제 위에서 돌아간다.

멀티턴 메모리 관리

대화·작업이 길어질 때 이력을 어떻게 들고 갈지가 메모리 문제다.

  • 단기 메모리: 최근 N턴은 원문 그대로 유지(최신 맥락은 중요).
  • 요약 메모리: 오래된 턴은 요약본으로 대체(7편 압축). 단 무엇을 남길지 기준 필요.
  • 장기 메모리(외부화): 컨텍스트 밖 저장소(벡터DB·파일·노트)에 사실을 적고, 필요할 때만 검색해 다시 불러온다. 컨텍스트를 "작업 기억"으로, 외부를 "장기 기억"으로 분리하는 발상.
  • 구조화된 메모(scratch note): 에이전트가 진행 상황·결정·미해결 항목을 별도 메모로 유지하고, 매 스텝 그 메모를 컨텍스트에 넣는다. 긴 작업에서 "지금 어디까지 했는지"를 잃지 않게 한다.

도구 결과 관리

에이전트 컨텍스트를 가장 빠르게 폭파시키는 건 도구 출력이다. 검색 한 번에 문서 수천 토큰, 파일 읽기 한 번에 수만 토큰이 들어온다. 그대로 쌓으면 몇 스텝 만에 윈도우가 찬다.

  • 요약 후 저장: 큰 도구 결과는 핵심만 추려 컨텍스트에 넣고, 원본은 외부에 둔 뒤 참조(ID·경로)만 남긴다.
  • 오래된 결과 정리(pruning): 이미 활용이 끝난 과거 도구 출력은 컨텍스트에서 덜어낸다(접거나, 요약으로 치환).
  • 관련 없는 도구 숨기기: 사용 가능한 도구가 수십 개면 그 정의만으로도 컨텍스트를 먹고 confusion을 일으킨다. 현재 단계에 필요한 도구만 노출한다.
  • 실패 결과 처리: 도구 에러·빈 결과도 컨텍스트에 남으면 잡음이다. 간결한 신호로 요약한다.

컨텍스트 격리와 서브에이전트

한 컨텍스트에 모든 걸 담으려 하면 distraction·confusion이 누적된다. 대안은 컨텍스트를 나누는 것이다.

  • 서브에이전트: 하위 작업을 별도 에이전트(별도 컨텍스트)에 위임하고, 그 결과 요약만 부모 컨텍스트로 가져온다. 하위 작업의 잡다한 중간 과정이 부모를 오염시키지 않는다.
  • 관심사 분리: 검색 담당, 코드 작성 담당, 검증 담당을 각자 깨끗한 컨텍스트에서 돌린다. 각 컨텍스트가 작고 집중돼 품질이 올라간다.
  • 트레이드오프: 격리하면 에이전트 간 정보 공유가 줄어든다. "무엇을 요약해 넘길지"의 인터페이스 설계가 새 과제가 된다.
핵심 발상 "하나의 거대한 컨텍스트"보다 "여러 개의 작고 깨끗한 컨텍스트 + 요약된 인터페이스"가 대체로 낫다. 사람 조직이 일을 나누고 보고로 합치는 것과 같다.

동적 컨텍스트 조립

정리하면, 에이전트의 매 스텝은 다음을 동적으로 조립하는 일이다.

이번 스텝 컨텍스트 =
    시스템 지시(고정·캐시)
  + 핵심 작업 목표 / 진행 메모
  + 관련 있는 장기 기억(검색해서)
  + 최근 대화·도구 결과(원문)
  + 오래된 것(요약본)
  + 지금 단계에 필요한 도구만

이 조립을 매 스텝 갱신하는 것이 에이전트 컨텍스트 엔지니어링이다. 평가도 중요하다 — 컨텍스트 변화가 성능을 올렸는지 내렸는지 측정해야 한다(needle test, 작업 성공률, 토큰당 성능). 감으로 "더 넣으면 낫겠지"는 대개 틀린다.

정리

핵심 요약 ① 에이전트 컨텍스트는 매 스텝 동적으로 조립·관리하는 대상이다. ② 컨텍스트는 4가지로 망가진다 — poisoning·distraction·confusion·clash. ③ 메모리는 단기 원문 / 오래된 요약 / 장기 외부화로 계층화. ④ 도구 출력은 요약·정리·관련 도구만 노출. ⑤ 거대한 단일 컨텍스트보다 작고 깨끗한 컨텍스트 여러 개(서브에이전트)가 낫다. ⑥ 컨텍스트 변경은 감이 아니라 측정으로 검증한다.

이로써 컨텍스트 엔지니어링 시리즈는 물리학(6)·구성 기법(7)·에이전트 관리(8)로 마무리된다. 디코딩 5편과 함께 보면 "모델 출력을 어떻게 뽑고, 모델에 무엇을 넣을지"의 양면을 모두 다룬 셈이다.
