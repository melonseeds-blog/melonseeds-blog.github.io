CLAUDE.md 잘 쓰는 법 — 의도·제약·Do NOT와 디렉터리 스코프

CLAUDE.md란 무엇이고 왜 필요한가

CLAUDE.md는 프로젝트 맥락을 Claude에 알려 주는 Markdown 파일이다. 세션이 시작될 때 자동으로 읽혀 대화 내내 배경 지식으로 깔린다. 즉 매 대화에서 "우리 프로젝트는 이런 규칙으로 돌아간다"를 다시 설명하지 않아도 되게 해 주는 상시 지시서다.

핵심은 코드만 봐서는 알기 어려운 것을 담는다는 데 있다. 코드에는 "무엇이 어떻게 구현됐나"는 있어도, "왜 이렇게 했나", "무엇은 하면 안 되나", "우리 팀은 어떤 관례를 따르나" 같은 정보는 거의 남지 않는다. 이런 의도·금지 사항·관례가 CLAUDE.md의 자리다.

있고 없고의 차이는 실제 동작으로 나타난다. CLAUDE.md가 없으면 Claude는 일반적인 관행으로 추측하고, 그 추측이 팀 규칙과 어긋나면 매번 되돌리는 왕복이 생긴다. 잘 적힌 CLAUDE.md가 있으면 처음부터 규칙에 맞는 방향으로 움직인다. 예를 들어 "직접 new/delete 금지, 스마트 포인터 사용" 한 줄이 있으면 생성되는 코드의 메모리 관리 방식 자체가 달라진다.

담을 것 vs 담지 말 것 담을 것 — 빌드·실행 명령, 코딩 컨벤션, 아키텍처 의도, 금지 사항, 자주 겪는 함정. 담지 말 것 — 코드를 보면 바로 아는 사실의 장황한 재설명, 한 번 쓰고 말 일회성 지시. CLAUDE.md는 매 세션 로드되므로 길수록 부담이다. 짧고 밀도 높게 쓴다.

/init으로 초안을 만들고 검수한다

맨손으로 시작할 필요는 없다. 프로젝트 루트에서 /init을 실행하면 Claude가 코드베이스를 훑어 CLAUDE.md 초안을 만들어 준다. 디렉터리 구성, 빌드 방법, 눈에 띄는 규칙 등을 자동으로 정리해 준다.

다만 초안을 그대로 두면 대개 "구조 설명서"에 그친다. 자동 생성물은 디렉터리를 나열하고 무슨 파일이 있는지 적는 데 강하지만, 그건 코드를 보면 알 수 있는 정보다. 진짜 가치는 코드에 없는 것 — 의도·제약·관례 — 을 사람이 보완하는 데서 나온다.

검수할 때 이 질문들로 초안을 훑으면 보완할 지점이 보인다.

  • 의도 — 왜 이 구조·이 라이브러리를 골랐나? 다음 사람이 무심코 바꾸면 안 되는 결정이 있나?
  • 제약 — 반드시 지켜야 하는 규칙(에러 처리 방식, 네이밍, 의존성 경계)이 명시됐나?
  • 관례 — 커밋 메시지 형식, 브랜치 전략, 테스트 위치 같은 팀 약속이 들어갔나?
  • 함정 — 새로 온 사람이 꼭 한 번은 밟는 문제가 미리 적혀 있나?

즉 /init은 빈 종이를 채워 주는 도구이지 완성본을 주는 도구가 아니다. 자동 생성 → 사람이 의도·제약 중심으로 압축·보완, 이 두 단계로 본다.

금지 사항은 "Do NOT"로 명확하게

규칙 중에서도 하면 안 되는 것은 특히 명시적으로 적는 게 좋다. "이 프로젝트에서는 이러이러한 상황이 있어서 가급적 저렇게 하지 않는 편이 좋고…"처럼 길게 풀어 쓰는 것보다, 짧고 단정한 규칙 한 줄이 더 잘 지켜진다.

효과적인 형태는 대문자 Do NOT 또는 MUST 같은 강한 지시어를 앞세워, 한 줄에 한 규칙을 적는 것이다.

# 권장 — 명시적이고 짧다
- Do NOT use raw new/delete. Use smart pointers.
- Do NOT expose OpenCV types in the public API. Use wrappers only.
- MUST return ErrorCode from all action functions.

# 지양 — 길고 모호해서 지켜지기 어렵다
- 메모리 관리를 할 때는 상황에 따라 여러 방법이 있지만
  가능하면 직접 할당·해제보다는 스마트 포인터를 쓰는 편이
  대체로 더 안전하다고 볼 수 있다.

차이는 "제안"이냐 "규칙"이냐다. 모호하게 서술하면 상황에 따라 무시될 여지가 생기지만, Do NOT ... 형태의 단정한 규칙은 경계가 분명해 위반 여부를 판단하기 쉽다. 한국어로 배경을 길게 덧붙이는 것보다, 규칙은 규칙으로 짧게 못 박고 필요하면 이유를 한 줄 덧붙이는 편이 낫다.

규칙에는 이유를 한 줄만 금지 규칙에 이유가 필요하면 짧게 한 줄로 붙인다. 예: Do NOT edit files under generated/. They are overwritten by the build. 이유가 있으면 규칙을 이해하고 유사 상황에도 적용하기 쉬워진다. 다만 이유가 규칙보다 길어지면 본말이 뒤집힌다.

디렉터리 스코프 — 폴더별 규칙

CLAUDE.md는 루트에 하나만 두는 파일이 아니다. 특정 디렉터리에도 둘 수 있고, 그 안에서 작업할 때 함께 참고된다. 프로젝트가 성격이 다른 여러 영역으로 나뉘어 있으면 규칙도 영역별로 분리하는 게 자연스럽다.

(root)/CLAUDE.md              # 프로젝트 전체 공통 규칙
(root)/src/components/CLAUDE.md   # 컴포넌트 폴더 전용 규칙
(root)/tests/CLAUDE.md        # 테스트 폴더 전용 규칙

이렇게 두면 루트에는 프로젝트 전반에 걸치는 큰 규칙(언어 표준, 커밋 형식, 아키텍처 의도)을 두고, 하위 폴더에는 그 영역에만 해당하는 세부 규칙을 둘 수 있다. 예를 들어 컴포넌트 폴더에는 "새 컴포넌트는 이 패턴을 따른다", 테스트 폴더에는 "테스트는 이 프레임워크로 이 위치에 둔다" 같은, 그 폴더에서만 의미 있는 규칙을 적는다.

이점은 두 가지다. 첫째, 루트 CLAUDE.md가 온갖 세부 규칙으로 비대해지는 걸 막는다. 둘째, 각 폴더의 규칙이 해당 폴더 작업에 맞게 국소화돼 관련성이 높아진다. 규칙은 그것이 적용되는 코드 가까이 두는 편이 관리하기 쉽다.

환경 이슈도 컨텍스트다 규칙만이 아니라 실제 환경 문제도 CLAUDE.md에 적어 두면 반복 사고를 막는다. 예를 들어 특정 빌드 설정에서 한글 주석이 깨진다면 "이 프로젝트는 소스를 UTF-8로 저장하고, MSVC에서는 /utf-8 옵션을 쓴다" 같은 실무 규칙을 적어 둔다. 빌드 경로에 한글이 들어가면 특정 도구가 실패한다든가, 특정 파일에는 BOM을 넣으면 안 된다든가 하는 함정도 마찬가지다. 사람이 매번 되짚어야 알던 것을 파일이 대신 기억한다.

작업 전에 CLAUDE.md를 읽고 확인하게 하는 습관

CLAUDE.md가 자동 로드된다 해도, 규모가 큰 작업을 시작할 때는 "작업 전에 관련 규칙을 다시 확인하고 시작한다"를 습관으로 두면 어긋남이 줄어든다. 규칙 자체에 이런 지시를 심어 둘 수도 있다.

- Before editing any file, re-read the rules in this CLAUDE.md.
- MUST read existing code before modifying it.

특히 하위 폴더 규칙이 여러 개일 때, 해당 폴더에서 작업을 시작하기 전 그 폴더의 CLAUDE.md를 확인하도록 유도하면 국소 규칙이 실제로 지켜진다.

프롬프트 · CLAUDE.md · Skill 구분

맥락과 규칙을 전달하는 방법은 하나가 아니다. 상황에 따라 세 가지를 나눠 쓰면 각자의 강점이 산다.

수단무엇에 맞나수명로드 방식
일반 프롬프트지금 이 작업에만 필요한 일회성 지시그 대화 한정직접 입력
CLAUDE.md항상 깔려 있어야 할 배경·규칙프로젝트 상시세션 시작 시 자동
Skill반복되는 절차·작업 순서필요할 때마다모델이 판단해 자동

구분 기준은 간단하다.

  • 일회성이면 프롬프트. "이번만 이렇게 해 줘"는 굳이 파일로 만들 필요가 없다.
  • 항상 필요한 배경·규칙이면 CLAUDE.md. 매 세션 반복 설명하던 맥락은 여기로 옮긴다.
  • 반복되는 절차면 Skill. 여러 단계로 이뤄진 정해진 작업 순서(예: 특정 형식의 문서 만들기, 정해진 배포 절차)는 스킬로 묶어 두면 그때그때 자동으로 따른다.

셋은 배타적이지 않다. CLAUDE.md에 상시 규칙을 깔아 두고, 반복 절차는 Skill로 두고, 그 위에서 개별 지시는 프롬프트로 준다. 다만 "매번 다시 설명하는 것"은 CLAUDE.md나 Skill로 옮길 신호라는 점만 기억하면 된다.

CLAUDE.md에 절차를 다 밀어 넣지 않는다 여러 단계짜리 반복 작업 절차까지 CLAUDE.md에 전부 적으면 파일이 비대해지고, 매 세션 그 내용을 모두 짊어지게 된다. 상시 필요한 "배경·규칙"과 필요할 때만 부르는 "절차"를 구분해, 절차성이 강한 것은 Skill로 분리하는 편이 낫다.

정리와 주의

  • 담을 것은 코드에 없는 것 — 의도·제약·관례·함정. 구조 나열이 아니라 이것들이 CLAUDE.md의 본체다.
  • 초안은 /init, 완성은 사람 — 자동 생성물을 의도·제약 중심으로 압축·보완한다.
  • 금지는 Do NOT로 — 길게 서술하기보다 짧고 단정한 규칙 한 줄로. 이유는 한 줄만 덧붙인다.
  • 규칙은 코드 가까이 — 루트 하나로 몰지 말고 디렉터리별로 국소화한다.
  • 수단을 나눠 쓴다 — 일회성은 프롬프트, 상시 배경·규칙은 CLAUDE.md, 반복 절차는 Skill.
  • 세부는 공식 문서로 — 파일 이름·경로·로드 규칙은 버전에 따라 바뀐다. 이 글의 원칙을 뼈대로 두고 정확한 사양은 문서에서 확인한다.
