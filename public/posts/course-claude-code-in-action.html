강의 개요

"Claude Code in Action"은 분량 1시간, 15차시, 퀴즈 1개의 Intermediate 강의다. 101이 "이게 무엇이고 어떻게 시작하는가"였다면, in Action은 "이미 진행 중인 프로젝트에 어떻게 끼워 넣고 자동화하는가"에 집중한다. 따라서 101 또는 Claude Code를 며칠이라도 써 본 경험이 사실상 전제 조건이다.

강의는 5개 섹션으로 구성된다.

  1. What is Claude Code? (3 lectures) — 코딩 어시스턴트의 정의와 실제 동작 시연
  2. Getting hands on (4 lectures) — 셋업부터 변경 적용까지
  3. Controlling context & Customization (3 lectures) — Custom command·MCP·GitHub
  4. Hooks and the SDK (5 lectures) — Hooks의 정의·구현·함정·예시
  5. Assessment & Conclusion (퀴즈 + 정리)
101과 in Action의 차이 같은 도구지만 시점이 다르다. 101은 "도구가 무엇인가"의 정적 설명, in Action은 "도구로 무엇을 만드는가"의 동적 시연이다. Hooks 섹션이 5차시에 달하는 게 가장 큰 특징이다.

What is Claude Code?

L1소개 (Introduction)

강의 자체의 도입부. 강사 소개, 학습 결과, 코스를 어떤 순서로 따라가야 하는지를 안내한다. 101보다 빠른 페이스로 진행됨이 예고된다.

L2코딩 어시스턴트란 (What is a coding assistant?)

"자동완성"과 "에이전트"의 차이를 분명히 한다. 자동완성은 한 줄을 채우고, 에이전트는 의도를 받아 여러 파일을 편집하고 명령을 실행하고 결과를 검증한다. Claude Code는 후자다.

L3실제 동작 시연 (Claude Code in action)

강사가 실제 코드베이스에서 Claude Code를 돌리는 데모다. 한 작업을 처음부터 끝까지 보여 줌으로써 이후 차시의 추상 개념들이 어떤 자리에 들어가는지 미리 감을 잡게 한다.

Getting hands on

L4Claude Code 셋업 (Claude Code setup)

설치·인증·IDE 통합을 다룬다. 101이 npm 설치 한 줄에 멈춘다면, 여기서는 VS Code·JetBrains 확장 연결, 셸 alias, 권한 모드(--allow/--ask/--auto)의 의미까지 다룬다.

L5프로젝트 셋업 (Project setup)

프로젝트에 처음 Claude Code를 들이는 절차다. CLAUDE.md 작성, .claude/ 디렉터리 구조, settings.json의 위치(프로젝트·로컬·사용자 글로벌)와 우선순위를 정리한다.

L6컨텍스트 부여 (Adding context)

가장 자주 쓰는 기법들이 한꺼번에 나온다. @로 파일 참조, #로 이슈 참조, 디렉터리 단위 참조, 그리고 "왜 모든 걸 다 컨텍스트에 넣으면 안 되는가"의 근거를 설명한다.

L7변경 적용 (Making changes)

실제 코드 변경을 시킬 때의 패턴이다. 계획 모드로 먼저 받기, diff 단위로 확인하기, 큰 변경은 작은 PR로 쪼개기. 강의는 "한 세션에서 너무 많은 일을 하지 말 것"을 반복해서 강조한다.

변경의 단위 = 리뷰의 단위 Claude Code가 한 번에 만든 변경은 사람이 한 번에 리뷰할 수 있는 크기여야 한다. 그 이상으로 가면 결국 검증 못 하고 머지하게 되고, 그게 회사 코드에 들어가는 가장 흔한 사고 원인이다.

Controlling context & Customization

L8Custom commands (Custom commands)

슬래시 명령(/my-command)을 직접 정의한다. .claude/commands/에 Markdown 파일을 두면 그게 곧 명령이 된다. "팀이 자주 쓰는 절차"를 명령화하는 것이 이 메커니즘의 본래 의도다.

L9MCP 서버 (MCP servers with Claude Code)

이미 만들어진 MCP 서버를 붙이는 방법과, 간단한 MCP 서버를 직접 만드는 방법을 함께 다룬다. Slack·DB·내부 API 같은 외부 시스템을 표준 인터페이스로 연결할 수 있다.

L10GitHub 통합 (GitHub integration)

gh CLI를 통한 PR/Issue 자동화, GitHub Actions에서의 Claude Code 활용 등을 다룬다. "사람이 본 코드만 머지된다"는 원칙을 유지하면서 어떻게 자동화 폭을 늘릴 수 있는지가 핵심 화두다.

Hooks and the SDK

강의에서 가장 비중이 큰 섹션이다. 5차시를 통째로 쓴다. Hooks는 settings.json에 정의되고, 라이프사이클 이벤트(PreToolUse·PostToolUse·Stop 등)에서 임의 스크립트를 실행하게 한다.

L11Hooks 소개 (Introducing hooks)

Hooks가 무엇이고 왜 필요한지부터 시작한다. "모델에게 매번 부탁할 수 없는 결정적 동작"을 자동화하는 자리라고 정리된다. 예: 위험한 명령 차단, 자동 포매팅, 변경 발생 시 알림.

L12Hook 정의 (Defining hooks)

settings.json의 hooks 키 안에 어떤 이벤트에 어떤 명령을 묶을지를 적는다. matcher로 특정 도구·특정 패턴에만 발동하도록 좁힐 수 있다. 메모리/스킬과는 별개의 메커니즘이라는 점이 강조된다.

L13Hook 구현 (Implementing a hook)

실제 셸 스크립트를 작성해 본다. 입력은 환경 변수·stdin으로 들어오고, 결정은 exit code와 stdout으로 돌려준다. 예시는 "Bash 도구 호출에서 rm -rf / 비슷한 패턴이 보이면 차단"이다.

L14Hook 함정 (Gotchas around hooks)

강의에서 가장 실용적인 차시 중 하나다. 자주 나오는 사고는 (1) Hook이 무한 루프를 도는 것, (2) Hook이 너무 느려 세션 전체가 느려지는 것, (3) Hook의 종료 코드 의미를 잘못 이해해 차단이 동작하지 않는 것이다. 모두 디버깅이 어렵다.

L15유용한 Hook 예시 (Useful hooks examples)

실전 예시 모음이다. 자동 포매터·테스트 트리거·금지 명령 차단·작업 완료 알림·민감 파일 접근 로깅 같은 패턴이 등장한다. 자기 환경에 맞게 골라 베끼면 된다.

Hook은 모델이 모르는 자동화 Hook이 실행되는 사실 자체를 모델이 항상 정확히 인식하지는 않는다. 따라서 Hook의 의도와 결과는 사용자 문서(README, CLAUDE.md)에도 반드시 명시해 두는 게 좋다. 안 그러면 본인이 두 달 뒤 자기가 만든 Hook을 디버깅하지 못한다.

Quiz와 마무리

마지막에 코스 전체 내용을 다루는 객관식 퀴즈가 한 번 있다. 분량은 짧고, 통과 여부가 어딘가에 기록되지는 않는다. 핵심 개념(컨텍스트 윈도우·Hook 라이프사이클·MCP의 역할)을 자기 말로 답해 보는 자가 점검 도구로 쓰면 좋다.

실무 적용 포인트

권장 학습 순서

본 블로그의 다른 글들과 합쳐 권장 순서는 다음과 같다.

  1. Claude Code 소개로 도구의 위치 파악
  2. 101로 개념과 기본 워크플로 체득
  3. Subagents & Skills로 확장 메커니즘 학습
  4. 본 글(in Action)로 Hooks·MCP·GitHub 통합까지 흡수
  5. 실전 활용 가이드와 플러그인 모음으로 정착

Hook은 차단부터, 자동화는 나중에

처음 Hook을 도입할 때는 "위험한 명령 차단"부터 시작하는 게 안전하다. 자동 포매팅·자동 커밋 같은 변경형 Hook은 안 익숙할 때 사고를 키운다. 차단형 Hook을 먼저 깔아 두고, 일주일 정도 무사히 돌아가면 변경형을 추가한다.

MCP는 기존 서버부터

처음부터 MCP 서버를 직접 작성하지 않는다. 공식·커뮤니티에서 제공하는 서버 중 자기 워크플로에 가까운 걸 먼저 붙여 본다. 직접 작성은 그 다음 단계다.

GitHub 자동화는 좁게

GitHub Actions에서 Claude Code를 돌리면 강력하지만, 잘못된 자동화는 회사 코드에 손상을 줄 수 있다. 처음에는 "PR에 라벨 붙이기"·"이슈 요약" 같은 읽기 전용 자동화부터 시작한다.

한계와 더 알아볼 것

  • 퀴즈가 가볍다 — 자가 점검용으로는 충분하지만 인증 가치는 없다. 실제 학습은 자기 프로젝트에서 검증해야 한다.
  • SDK 깊이가 얕다 — 차시 제목에는 SDK가 들어 있지만 실제 분량은 Hooks 쪽이 압도적이다. SDK로 자체 도구를 만드는 시나리오는 공식 문서로 보충해야 한다.
  • 버전 의존성 — settings.json의 키와 Hook 이벤트 이름은 업데이트로 바뀔 수 있다. 강의 시점과 현재 시점의 차이가 의심되면 공식 문서로 검증한다.
마무리 in Action까지 다 들었다면 Claude Code의 표면적 기능은 거의 다 본 셈이다. 이후 학습은 "내 프로젝트에서 어디가 진짜 자동화할 가치가 있는가"를 한 주에 하나씩 찾아 적용하는 방식으로 가는 게 훨씬 빠르다.
