unsafe Rust와 FFI 기초

2026-06-25 약 8분 분량 Rust 시리즈
이 편에서 배우는 것 unsafe가 실제로 푸는 것은 무엇이고(raw 포인터 역참조·extern 함수 호출 등), 무엇은 여전히 막혀 있는지 구분한다. unsafe 블록을 안전한 함수 시그니처로 감싸 호출자에게는 안전한 API만 노출하는 방법을 익힌다. 끝으로 extern "C"로 C 함수를 부르고 Rust 함수를 C에 내보내는 FFI의 기본 골격을 본다. C++ 경험자가 "Rust는 이 경계를 이렇게 다르게 다룬다"를 체감하는 게 목표다.

왜 unsafe가 필요한가

Rust의 기본 컴파일러는 메모리 안전을 정적으로 보장한다. 댕글링 포인터, 데이터 레이스, 해제 후 사용 같은 부류가 컴파일 단계에서 걸러진다. 그런데 이 보장은 컴파일러가 증명할 수 있는 범위 안에서만 작동한다. 운영체제 API를 직접 부르거나, C 라이브러리와 연동하거나, 하드웨어 레지스터를 다루는 일은 컴파일러가 정적으로 검증할 수 없다.

unsafe는 이 지점에서 "이 부분은 내가 직접 불변식을 책임진다"고 컴파일러에 선언하는 키워드다. 안전 검사를 통째로 끄는 스위치가 아니라, 몇 가지 추가 연산을 한정된 영역에서만 허용하는 표식이다. 핵심은 이 영역을 작게 격리하고, 그 바깥에는 안전한 인터페이스만 드러내는 것이다.

C++과 이렇게 다르다 — 기본값이 반대다 C++은 코드 전체가 사실상 "unsafe"다. 포인터 역참조, 형 변환, 수명 관리가 어디서든 가능하고 그만큼 어디서든 미정의 동작이 샐 수 있다. Rust는 기본이 안전하고, 위험한 연산은 unsafe로 표시한 영역에만 모인다. 그래서 메모리 버그를 추적할 때 C++은 코드 전체가 용의자지만, Rust는 unsafe 블록부터 들여다보면 된다. 감사 대상의 크기가 다르다.

unsafe가 푸는 다섯 가지

unsafe 블록 안에서만 추가로 허용되는 연산은 다섯 가지로 정해져 있다. 그 외의 일반 규칙(빌림 검사·타입 검사)은 그대로 적용된다.

  • raw 포인터(*const T, *mut T) 역참조
  • unsafe 함수·메서드 호출(extern 함수 포함)
  • 가변 static 변수 접근·수정
  • unsafe 트레이트 구현
  • union 필드 접근

raw 포인터는 unsafe 없이도 만들 수 있다. 막혀 있는 건 오직 역참조다. 아래 코드에서 포인터 생성은 안전한 코드, 역참조만 unsafe 블록에 들어간다.

fn main() {
    let mut value = 42;

    // 참조로부터 raw 포인터 만들기 — 여기까지는 안전한 코드다
    let const_ptr: *const i32 = &value;
    let mut_ptr: *mut i32 = &mut value;

    // 역참조는 unsafe 블록 안에서만 허용된다
    unsafe {
        println!("읽기: {}", *const_ptr);
        *mut_ptr += 1;
        println!("쓰기 후: {}", *mut_ptr);
    }
}

여기서 중요한 오해를 짚는다. unsafe는 빌림 검사기를 끄지 않는다. 아래 코드는 unsafe 블록 안에 있어도 컴파일되지 않는다. 같은 값에 대한 가변 참조와 불변 참조를 동시에 살아 있게 두는 일은 여전히 금지된다.

fn main() {
    let mut value = 10;

    let shared = &value;        // 불변 참조
    let exclusive = &mut value; // 같은 값의 가변 참조 — 컴파일 에러

    // unsafe로 감싸도 빌림 규칙 위반은 그대로 막힌다
    unsafe {
        println!("{} {}", shared, *exclusive);
    }
}

즉 unsafe가 위임하는 책임은 "위에 적힌 다섯 연산이 메모리 안전 불변식을 깨지 않도록 직접 보장하라"는 것에 한정된다. 일반 안전 규칙은 그대로 강제된다.

안전한 추상화로 감싸기

실무에서 unsafe를 다루는 핵심 기법은 안전한 함수 시그니처 뒤에 가두기다. 함수 내부에 unsafe 블록이 있어도, 그 함수가 어떤 인자를 받든 메모리 안전을 깨지 않는다면 함수 자체는 unsafe로 표시할 필요가 없다. 호출자는 평범한 안전 함수로 쓴다.

표준 라이브러리의 split_at_mut이 대표적이다. 하나의 가변 슬라이스를 두 개의 겹치지 않는 가변 슬라이스로 나누는데, 빌림 검사기만으로는 "두 조각이 안 겹친다"를 증명하지 못해 내부에서 raw 포인터를 쓴다. 단순화한 형태로 직접 구현해 본다.

use std::slice;

// 안전한 시그니처 — 호출자는 unsafe를 몰라도 된다
fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = values.len();
    let ptr = values.as_mut_ptr();

    assert!(mid <= len); // 불변식을 함수 안에서 강제한다

    unsafe {
        (
            slice::from_raw_parts_mut(ptr, mid),
            slice::from_raw_parts_mut(ptr.add(mid), len - mid),
        )
    }
}

fn main() {
    let mut data = [1, 2, 3, 4, 5, 6];
    let (left, right) = split_at_mut(&mut data, 3);

    left[0] = 10;
    right[0] = 40;

    println!("{:?}", data); // [10, 2, 3, 40, 5, 6]
}

이 함수가 안전한 이유는 내부의 불변식을 함수가 스스로 보장하기 때문이다. assert!(mid <= len)로 범위를 검사하고, 두 슬라이스가 같은 버퍼의 서로 다른 구간(0..mid와 mid..len)을 가리키므로 절대 겹치지 않는다. 어떤 인자가 들어와도 미정의 동작이 생기지 않으니 시그니처에 unsafe를 붙이지 않아도 된다.

경계의 위치가 설계의 핵심이다 좋은 unsafe 코드는 "위험 영역을 최소 면적으로 격리하고, 그 둘레에 안전한 계약을 두른 것"이다. unsafe 블록은 가능한 한 짧게, 그리고 그 블록이 의존하는 불변식을 함수가 책임지고 검증하게 만든다. 호출자에게는 위험이 새 나가지 않는다.

extern "C"로 FFI 시작하기

FFI(Foreign Function Interface)는 Rust가 다른 언어, 특히 C ABI를 따르는 코드와 함수를 주고받는 방법이다. 양방향 모두 extern "C"로 호출 규약을 명시한다. "C"는 C 언어의 ABI를 따른다는 표시다.

C 함수 호출하기

extern "C" 블록 안에 외부 함수의 시그니처를 선언한다. 다른 언어 함수의 동작은 Rust 컴파일러가 검증할 수 없으므로, 이 함수 호출은 본질적으로 unsafe다. 아래는 C 표준 라이브러리의 abs를 부르는 예다.

// C 표준 라이브러리의 함수 시그니처를 선언한다
extern "C" {
    fn abs(input: i32) -> i32;
}

fn main() {
    // 외부 함수 호출은 unsafe — 컴파일러가 내부를 검증할 수 없다
    unsafe {
        println!("abs(-7) = {}", abs(-7));
    }
}

Rust 함수를 C에 내보내기

반대 방향도 가능하다. Rust 함수를 C에서 부를 수 있게 내보내려면 extern "C"로 호출 규약을 맞추고, #[no_mangle]로 이름 맹글링을 꺼서 C 쪽이 기대하는 심볼 이름을 그대로 유지한다.

// C에서 'add_one'이라는 이름 그대로 호출할 수 있게 내보낸다
#[no_mangle]
pub extern "C" fn add_one(x: i32) -> i32 {
    x + 1
}

이 함수 본문 자체는 안전한 Rust다. unsafe가 필요한 쪽은 호출하는 C 코드이지, 내보내는 Rust 함수의 정의가 아니다.

C++과 이렇게 다르다 — 경계가 코드에 새겨진다 C++에서 C 라이브러리를 쓸 때 extern "C"는 이름 맹글링을 막는 링크 지시일 뿐, 호출부에 안전·불안전 구분이 따로 남지 않는다. Rust에서는 외부 함수 호출이 강제로 unsafe 블록에 들어가므로, 코드를 읽는 사람이 "여기서부터 컴파일러 보장이 끝난다"를 시각적으로 바로 안다. 신뢰 경계가 주석이 아니라 문법으로 표시된다.

정리와 주의

  • unsafe는 스위치가 아니다 — raw 포인터 역참조, extern·unsafe 함수 호출, 가변 static 접근, unsafe 트레이트 구현, union 접근. 딱 이 다섯 가지만 추가로 연다.
  • 빌림 검사기는 살아 있다 — unsafe 안에서도 소유권·빌림 규칙은 그대로 강제된다. 끄는 것이 아니다.
  • 작게 격리하고 안전하게 감싼다 — 위험 영역을 최소화하고, 불변식을 함수가 책임지면 호출자에게는 안전한 API만 노출된다.
  • FFI는 unsafe의 대표 무대 — extern "C"로 C 함수를 부르고, #[no_mangle] + extern "C"로 Rust 함수를 내보낸다.
  • 경계가 문법으로 드러난다 — C++과 달리 "보장이 끝나는 지점"이 unsafe 키워드로 명시되어, 감사할 면적이 작다.
