MVVM이란?

MVVM(Model-View-ViewModel)은 UI 코드를 세 개의 계층으로 분리해 관심사를 나누는 아키텍처 패턴이다. Microsoft가 WPF를 출시하며 데이터 바인딩과 함께 정착시켰고, 오늘날 WPF·UWP·Xamarin·.NET MAUI의 사실상 표준이 됐다.

핵심 아이디어는 간단하다. UI(View)는 화면 표시만 담당하고, 상태와 명령(ViewModel)은 별도 객체가 들고 있으며, 도메인 데이터(Model)는 그 어떤 UI 개념도 모른다. View와 ViewModel은 데이터 바인딩으로 느슨하게 연결된다.

MVC·MVP와의 차이 MVC의 Controller, MVP의 Presenter는 View를 직접 알고 호출한다. MVVM의 ViewModel은 View를 모른다. 바인딩 인프라가 그 간극을 메운다. 결과적으로 ViewModel을 UI 없이 단위 테스트할 수 있다.

각 계층의 책임

계층책임예시의존성
Model 도메인 데이터·비즈니스 로직. UI 개념 없음. InspectionResult, ImageProcessor, Repository 없음 (POCO)
View XAML로 작성한 UI. 레이아웃·시각 효과·애니메이션. InspectionWindow.xaml, Controls ViewModel을 DataContext로만 본다
ViewModel View가 표시·조작할 상태와 명령. 입력 검증·서식 변환. InspectionViewModel — IsRunning, Progress, StartCommand Model 참조. View는 모름.

Model 예시 — POCO

// Pure domain object. No UI dependency.
public class InspectionResult
{
    public int Id { get; set; }
    public DateTime Timestamp { get; set; }
    public bool IsPass { get; set; }
    public double Score { get; set; }
    public string DefectType { get; set; }
}

// Domain service — UI를 전혀 모른다.
public interface IInspectionService
{
    Task<InspectionResult> InspectAsync(byte[] image, CancellationToken ct);
}

View 예시 — XAML만

<Window x:Class="Vision.Views.InspectionWindow"

        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"

View의 코드 비하인드(.xaml.cs)는 거의 비어 있는 것이 이상적이다. UI 이벤트 처리는 모두 ViewModel의 명령으로 위임한다.

의존성 흐름

MVVM의 핵심은 단방향 의존성이다. View가 ViewModel을 알고, ViewModel이 Model을 안다. 역방향은 없다.

실선은 컴파일 타임 의존성을 나타낸다. 점선은 이벤트·바인딩 인프라를 통한 느슨한 알림이다. ViewModel은 View 타입을 참조하지 않는다. View의 변경은 ViewModel을 건드리지 않고 끝나야 한다.

INotifyPropertyChanged

VM의 속성이 바뀌었을 때 바인딩 엔진에 알리는 표준 인터페이스다. 7편 데이터 바인딩에서 다룬 내용을 MVVM 관점으로 다시 짚는다.

public class InspectionViewModel : INotifyPropertyChanged
{
    public event PropertyChangedEventHandler PropertyChanged;

    private string _statusText;
    public string StatusText
    {
        get => _statusText;
        set
        {
            if (_statusText == value) return;
            _statusText = value;
            PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(nameof(StatusText)));
        }
    }
}

이 보일러플레이트가 속성마다 반복된다. 속성 10개면 10번 같은 패턴이다. 이를 해결하기 위해 ObservableObject 기반 클래스를 쓴다.

ObservableObject — 보일러플레이트 제거

직접 구현

public abstract class ObservableObject : INotifyPropertyChanged
{
    public event PropertyChangedEventHandler PropertyChanged;

    // CallerMemberName으로 속성 이름 자동 전달.
    protected bool SetProperty<T>(ref T field, T value,
        [CallerMemberName] string propertyName = null)
    {
        if (EqualityComparer<T>.Default.Equals(field, value)) return false;
        field = value;
        PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(propertyName));
        return true;
    }

    protected void OnPropertyChanged([CallerMemberName] string propertyName = null)
        => PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(propertyName));
}

// 사용
public class InspectionViewModel : ObservableObject
{
    private string _statusText;
    public string StatusText
    {
        get => _statusText;
        set => SetProperty(ref _statusText, value);
    }

    private double _progress;
    public double Progress
    {
        get => _progress;
        set => SetProperty(ref _progress, value);
    }
}

CommunityToolkit.Mvvm — 소스 생성기

Microsoft가 유지하는 공식 MVVM 라이브러리다. [ObservableProperty] 어트리뷰트를 붙이면 컴파일 시 소스 생성기가 속성을 만들어준다. 코드가 극적으로 줄어든다.

using CommunityToolkit.Mvvm.ComponentModel;

public partial class InspectionViewModel : ObservableObject
{
    [ObservableProperty]
    private string _statusText;

    [ObservableProperty]
    private double _progress;

    [ObservableProperty]
    private bool _isRunning;
}
// 컴파일 후 StatusText, Progress, IsRunning 속성이 자동 생성된다.
// SetProperty 호출과 PropertyChanged 발생까지 전부 자동.
partial class 키워드 필수 소스 생성기가 같은 클래스에 코드를 추가하기 때문에 클래스 선언에 partial이 반드시 필요하다. 또한 필드명은 _camelCase 또는 m_camelCase 규칙을 따라야 자동으로 PascalCase 속성이 생성된다.

명령(Command)

8편에서 다룬 ICommand·RelayCommand를 MVVM 관점에서 다시 본다. VM은 메서드가 아니라 명령 객체를 노출한다. Button의 Click 이벤트 대신 Command 속성을 바인딩한다.

using CommunityToolkit.Mvvm.ComponentModel;
using CommunityToolkit.Mvvm.Input;

public partial class InspectionViewModel : ObservableObject
{
    private readonly IInspectionService _service;

    [ObservableProperty] private bool _isRunning;
    [ObservableProperty] private double _progress;

    public InspectionViewModel(IInspectionService service)
    {
        _service = service;
    }

    // [RelayCommand]가 StartCommand 속성을 자동 생성한다.
    [RelayCommand(CanExecute = nameof(CanStart))]
    private async Task StartAsync(CancellationToken ct)
    {
        IsRunning = true;
        try
        {
            var result = await _service.InspectAsync(GetCurrentImage(), ct);
            StatusText = result.IsPass ? "양품" : $"불량: {result.DefectType}";
        }
        finally
        {
            IsRunning = false;
        }
    }

    private bool CanStart() => !IsRunning;

    // IsRunning이 바뀌면 StartCommand의 CanExecute를 재평가한다.
    partial void OnIsRunningChanged(bool value) => StartCommand.NotifyCanExecuteChanged();
}

XAML에서는 단순히 바인딩한다.

<Button Content="검사 시작"
        Command="{Binding StartCommand}"
        IsEnabled="{Binding StartCommand.CanExecute}" />

VM 간 통신 — Messenger

여러 ViewModel이 서로 알아야 하는 상황이 생긴다. 검사 결과가 나오면 결과 목록 VM과 통계 VM이 동시에 갱신돼야 한다. VM끼리 직접 참조하면 결합도가 올라간다. 메신저(이벤트 집계자)를 두면 발행/구독 방식으로 느슨하게 연결된다.

using CommunityToolkit.Mvvm.Messaging;
using CommunityToolkit.Mvvm.Messaging.Messages;

// 메시지 정의 — 새 검사 결과 발생.
public class InspectionCompletedMessage : ValueChangedMessage<InspectionResult>
{
    public InspectionCompletedMessage(InspectionResult value) : base(value) { }
}

// 발행 측 (InspectionViewModel)
[RelayCommand]
private async Task StartAsync(CancellationToken ct)
{
    var result = await _service.InspectAsync(GetCurrentImage(), ct);
    WeakReferenceMessenger.Default.Send(new InspectionCompletedMessage(result));
}

// 구독 측 (HistoryViewModel)
public partial class HistoryViewModel : ObservableObject,
    IRecipient<InspectionCompletedMessage>
{
    public ObservableCollection<InspectionResult> Items { get; } = new();

    public HistoryViewModel()
    {
        WeakReferenceMessenger.Default.Register(this);
    }

    public void Receive(InspectionCompletedMessage message)
    {
        Items.Insert(0, message.Value);
    }
}
WeakReferenceMessenger 권장 WeakReferenceMessenger는 구독자를 약한 참조로 보관해 명시적 해제 없이도 메모리 누수를 막아준다. 강한 참조 버전은 ViewModel이 살아 있는 동안만 사용해야 한다.

DataTemplate으로 VM ↔ View 매핑

ContentControl에 ViewModel 인스턴스를 바인딩하고 DataTemplate으로 어떤 View로 그릴지 선언한다. 이렇게 하면 View의 코드 비하인드에서 View를 생성할 일이 없다.

<Window xmlns:vm="clr-namespace:Vision.ViewModels"
        xmlns:v="clr-namespace:Vision.Views">
    <Window.Resources>
        <!-- VM 타입 → View 매핑 -->
        <DataTemplate DataType="{x:Type vm:InspectionViewModel}">
            <v:InspectionView />
        </DataTemplate>
        <DataTemplate DataType="{x:Type vm:HistoryViewModel}">
            <v:HistoryView />
        </DataTemplate>
    </Window.Resources>

    <!-- CurrentPage가 어떤 VM이든 적절한 View로 자동 렌더 -->
    <ContentControl Content="{Binding CurrentPage}" />
</Window>

MainViewModel은 CurrentPage 속성에 InspectionViewModel 또는 HistoryViewModel을 넣기만 하면 된다. View 생성·전환은 WPF가 알아서 처리한다.

테스트 용이성

MVVM의 진짜 보상은 UI 없이 VM을 테스트할 수 있다는 점이다. xUnit·NUnit·MSTest 어떤 것으로든 일반 클래스처럼 단위 테스트가 가능하다.

public class InspectionViewModelTests
{
    [Fact]
    public async Task Start_SetsIsRunningDuringExecution()
    {
        // Arrange — 서비스를 Mock으로 대체.
        var mockService = new Mock<IInspectionService>();
        mockService.Setup(s => s.InspectAsync(It.IsAny<byte[]>(), It.IsAny<CancellationToken>()))
                   .ReturnsAsync(new InspectionResult { IsPass = true });

        var vm = new InspectionViewModel(mockService.Object);
        Assert.False(vm.IsRunning);

        // Act
        await vm.StartCommand.ExecuteAsync(null);

        // Assert — 완료 후 false로 복귀.
        Assert.False(vm.IsRunning);
        Assert.Equal("양품", vm.StatusText);
    }

    [Fact]
    public void StartCommand_CannotExecute_WhenRunning()
    {
        var vm = new InspectionViewModel(Mock.Of<IInspectionService>());
        vm.IsRunning = true;
        Assert.False(vm.StartCommand.CanExecute(null));
    }
}

이 테스트들은 WPF·XAML을 전혀 띄우지 않고 실행된다. CI 빌드 서버에서도 동작한다.

산업 비전 UI 예제 — InspectionViewModel

실전 비전 검사기 UI의 ViewModel을 만들어본다. 이미지·검사 결과·진행률·시작/정지 명령을 노출하고, View는 바인딩만 한다.

using System.Collections.ObjectModel;
using CommunityToolkit.Mvvm.ComponentModel;
using CommunityToolkit.Mvvm.Input;

public partial class InspectionViewModel : ObservableObject
{
    private readonly IInspectionService _service;
    private readonly ICameraService _camera;
    private CancellationTokenSource _cts;

    [ObservableProperty] private BitmapSource _currentImage;
    [ObservableProperty] private string _statusText = "대기";
    [ObservableProperty] private double _progress;
    [ObservableProperty] private bool _isRunning;
    [ObservableProperty] private int _passCount;
    [ObservableProperty] private int _failCount;

    public ObservableCollection<InspectionResult> RecentResults { get; } = new();

    public InspectionViewModel(IInspectionService service, ICameraService camera)
    {
        _service = service;
        _camera = camera;
    }

    [RelayCommand(CanExecute = nameof(CanStart))]
    private async Task StartAsync()
    {
        _cts = new CancellationTokenSource();
        IsRunning = true;
        StatusText = "검사 중...";
        try
        {
            int total = 100;
            for (int i = 0; i < total && !_cts.IsCancellationRequested; i++)
            {
                var frame = await _camera.GrabAsync(_cts.Token);
                CurrentImage = frame.ToBitmapSource();
                var result = await _service.InspectAsync(frame.Raw, _cts.Token);

                if (result.IsPass) PassCount++;
                else FailCount++;

                RecentResults.Insert(0, result);
                if (RecentResults.Count > 50) RecentResults.RemoveAt(50);

                Progress = (i + 1) * 100.0 / total;
            }
            StatusText = "완료";
        }
        catch (OperationCanceledException)
        {
            StatusText = "취소됨";
        }
        finally
        {
            IsRunning = false;
            StopCommand.NotifyCanExecuteChanged();
        }
    }

    [RelayCommand(CanExecute = nameof(CanStop))]
    private void Stop() => _cts?.Cancel();

    private bool CanStart() => !IsRunning;
    private bool CanStop() => IsRunning;

    partial void OnIsRunningChanged(bool value)
    {
        StartCommand.NotifyCanExecuteChanged();
        StopCommand.NotifyCanExecuteChanged();
    }
}

C++/CLI로 비전 코어 연결

위 예제의 IInspectionService·ICameraService는 인터페이스다. 실제 구현은 C++로 만든 비전 코어 라이브러리를 호출해야 한다. C++/CLI가 그 다리 역할을 한다.

// C# 인터페이스
public interface IInspectionService
{
    Task<InspectionResult> InspectAsync(byte[] image, CancellationToken ct);
}

// C++/CLI 어셈블리가 노출하는 클래스 (개념적)
// namespace ImagingLib::Clr {
//     public ref class InspectionEngine {
//     public:
//         InspectionResultDto^ Inspect(array<Byte>^ image);
//     };
// }

public class NativeInspectionService : IInspectionService
{
    private readonly ImagingLib.Clr.InspectionEngine _engine = new();

    public Task<InspectionResult> InspectAsync(byte[] image, CancellationToken ct)
    {
        // 무거운 작업은 백그라운드로.
        return Task.Run(() =>
        {
            var dto = _engine.Inspect(image);
            return new InspectionResult
            {
                IsPass = dto.IsPass,
                Score = dto.Score,
                DefectType = dto.DefectType,
                Timestamp = DateTime.Now
            };
        }, ct);
    }
}

ViewModel은 인터페이스만 안다. 네이티브 엔진이 바뀌어도 VM은 영향 받지 않는다. 12편에서 C++/CLI 브리지 구현을 본격적으로 다룬다.

흔한 함정

함정 1 — VM에 UI 타입 노출

VM이 Visibility·Brush·Window를 알면 테스트가 깨진다 VM은 System.Windows나 System.Windows.Controls를 참조하면 안 된다. UI 결정은 컨버터·트리거·DataTrigger로 한다. 
// 나쁜 예 — VM이 Visibility를 다룬다.
public Visibility ErrorVisibility => HasError ? Visibility.Visible : Visibility.Collapsed;

// 좋은 예 — VM은 의미 있는 bool만 노출.
public bool HasError { get; set; }
<!-- View에서 BooleanToVisibilityConverter 사용 -->
<Window.Resources>
    <BooleanToVisibilityConverter x:Key="BoolToVis"/>
</Window.Resources>
<TextBlock Text="오류 발생!"
           Visibility="{Binding HasError, Converter={StaticResource BoolToVis}}"/>

함정 2 — God ViewModel (SRP 위반)

VM 하나가 1,000줄을 넘으면 분해 신호 화면 전체를 하나의 VM이 들고 있으면 테스트와 유지보수가 어려워진다. 자식 VM으로 분리해 컴포지션으로 묶자. 
// 나쁜 예 — MainViewModel이 모든 것을 갖고 있다.
public partial class MainViewModel : ObservableObject
{
    [ObservableProperty] private BitmapSource _image;
    [ObservableProperty] private InspectionResult _result;
    [ObservableProperty] private CameraSettings _cameraSettings;
    [ObservableProperty] private ObservableCollection<LogEntry> _logs;
    // ... 50개 속성, 30개 명령
}

// 좋은 예 — 자식 VM으로 컴포지션.
public partial class MainViewModel : ObservableObject
{
    public InspectionViewModel Inspection { get; }
    public CameraSettingsViewModel CameraSettings { get; }
    public LogViewModel Log { get; }

    public MainViewModel(InspectionViewModel inspection,
                          CameraSettingsViewModel cameraSettings,
                          LogViewModel log)
    {
        Inspection = inspection;
        CameraSettings = cameraSettings;
        Log = log;
    }
}

함정 3 — 코드 비하인드 남용

.xaml.cs에 비즈니스 로직을 두면 MVVM이 깨진다 Button_Click 핸들러에서 데이터를 조작하면 VM이 우회된다. Command로 옮긴다. 단, 순수 UI 로직(애니메이션 시작, 포커스 이동, 컨트롤 직접 조작)은 코드 비하인드에 둬도 된다.

함정 4 — MVVM 라이브러리 과사용

작은 앱에 Prism은 과하다 도구 윈도우 하나짜리 앱에 모듈·Region·DI 컨테이너를 들이면 진입 비용만 커진다. 규모에 맞는 도구를 고른다 — 소형은 CommunityToolkit.Mvvm, 대형 모듈식 앱만 Prism.

함정 5 — async void 명령

// 나쁜 예 — 예외가 잡히지 않고 앱이 죽는다.
public ICommand StartCommand => new RelayCommand(async () => await StartAsync());

// 좋은 예 — AsyncRelayCommand가 Task를 추적한다.
[RelayCommand]
private async Task StartAsync() { /* ... */ }

CommunityToolkit의 [RelayCommand]는 Task 반환 메서드를 보면 자동으로 AsyncRelayCommand를 생성한다. 예외도 명령 객체가 추적한다.
