Sampling — 서버가 모델을 부른다

왜 필요한가

일반적인 도구 호출은 한 방향이다 — 모델이 도구를 부르고, 도구가 결과를 돌려준다. 그런데 서버가 작업하는 도중에 "이 텍스트를 요약해 줘"처럼 LLM의 도움이 필요해질 때가 있다. 이를 위한 메커니즘이 Sampling이다.

"How MCP servers can request language model calls through clients."

중요한 건 서버가 직접 모델 API에 접근하지 않는다는 점이다. 클라이언트를 경유해서 요청하므로 다음 이점이 있다.

  • API 키 분리 — 서버는 모델 키를 가지지 않는다. 보안 경계가 명확하다.
  • 사용자 승인 — 클라이언트가 "서버가 LLM을 부르려 한다"를 사용자에게 확인할 수 있다.
  • 모델 선택 자유도 — 어떤 모델을 쓸지는 호스트가 정한다.

Sampling Walkthrough — 흐름도

Server                       Client                    Model
  |                            |                         |
  |-- sampling/createMessage -->|                         |
  |   (messages, max_tokens)   |                         |
  |                            |-- user approval? -------|
  |                            |-- model API call ------>|
  |                            |<------- response -------|
  |<----- result ---------------|                         |

사용 사례

  • 대형 PDF를 도구가 페이지별로 잘라 요약을 의뢰
  • 코드 분석 서버가 함수마다 자연어 설명을 LLM에 요청
  • 비전 검사 서버가 결함 마스크를 받아 "결함 설명문" 생성을 위임
Sampling을 안 써도 될 때 결정론적 변환(파싱·합산·필터링)으로 풀리는 일에는 Sampling을 쓰지 않는다. 호출비용·지연·확률성 셋 다 비용이 크다.

Log & Progress Notifications

장시간 작업의 침묵 문제

도구가 5분 동안 무언가를 하고 있을 때, 클라이언트는 "이게 죽었나? 살았나?" 알 길이 없다. Notification은 응답을 기대하지 않는 단방향 메시지로 진행 상황을 흘려보낸다.

종류용도메서드
Log notificationinfo/warn/error 수준 메시지notifications/message
Progress notification0.0~1.0 비율 또는 단계 진행notifications/progress

구현 패턴

도구가 ctx(컨텍스트) 인자를 받아, ctx.info()·ctx.report_progress()를 호출하는 방식이다.

@mcp.tool()
async def run_long_job(ctx: Context) -> str:
    """Run a long pipeline with progress reports."""
    for i, step in enumerate(steps):
        await ctx.info(f"Processing {step.name}")
        await ctx.report_progress(i / len(steps))
        step.run()
    return "done"
UX 관점에서의 차이 Notification이 있으면 클라이언트는 "검사 3/10 진행 중"처럼 진행 표시를 그릴 수 있다. 사용자는 모델 출력만 기다리는 것이 아니라 작업이 진짜로 돌아가는 걸 본다.

Roots — 파일 접근 경계

개념

Roots는 클라이언트가 서버에게 "여기까지만 봐도 돼"라고 알려주는 디렉터리 화이트리스트다. 파일 시스템 서버처럼 광범위한 접근이 가능한 서버에 보안 경계를 친다.

"Permission-based file access with security boundaries."
  • 호스트(예: 에디터)는 현재 워크스페이스 폴더만 Root로 알려준다.
  • 서버는 roots/list를 호출해 허용된 경로를 받는다.
  • 워크스페이스가 바뀌면 roots/list_changed 알림으로 갱신된다.

구현 시 주의

Roots를 지키는 책임은 서버에 있다. 클라이언트가 경로를 알려줘도 서버가 무시하면 의미가 없다. 서버 코드에서 모든 파일 접근 전에 경로가 Root 안에 있는지 검사해야 한다.

경로 정규화 함정 ../나 심볼릭 링크로 Root를 우회할 수 있다. Path.resolve() 후 Root와의 부모-자식 관계를 확인해야 한다.

JSON 메시지 타입 — 양방향 통신

MCP는 JSON-RPC 2.0 기반이다. 강의는 메시지 종류를 셋으로 정리한다.

타입응답 기대id 필드예시
Request예있음tools/call, resources/read
Result / Error—요청 id와 매칭tools/call 응답
Notification아니오 (단방향)없음notifications/progress

양방향성

흔히 "클라이언트가 요청, 서버가 응답"이라고 생각하지만 MCP는 그렇지 않다. 서버도 클라이언트에 요청을 보낼 수 있다 (Sampling이 그 예). 양쪽 모두 Request도 보내고 Notification도 보낸다.

// Server -> Client (Sampling 요청 예시)
{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "sampling/createMessage",
  "params": { "messages": [...], "maxTokens": 1000 }
}

Transports — STDIO vs Streamable HTTP

STDIO Transport

표준 입출력으로 통신하는 방식이다. 클라이언트가 서버 프로세스를 자식으로 띄우고 stdin/stdout으로 JSON 메시지를 주고받는다.

  • 장점 — 설정 간단, 로컬 보안 우수, 네트워크 노출 없음
  • 단점 — 원격 사용 불가, 한 클라이언트 = 한 서버 프로세스
  • 적합 — 데스크톱 통합, 개발/로컬 도구

Streamable HTTP Transport

HTTP POST + Server-Sent Events(SSE)를 결합한 새로운 전송 방식이다. 기존 SSE 단독 전송보다 단순화됐다.

방향채널설명
Client → ServerHTTP POSTJSON 메시지 본문으로 전송
Server → ClientSSE 스트림장기 연결로 알림/응답 푸시
  • 장점 — 원격 서버 가능, 표준 인프라(프록시·LB) 활용
  • 단점 — 인증·세션 관리 복잡, 방화벽 정책 필요
  • 적합 — 사내 호스팅 서버, 멀티 사용자 공유 서비스

어느 것을 고를까

요건권장
로컬 도구, 단일 사용자STDIO
원격 접근, 다중 사용자Streamable HTTP
CI/CD 봇처럼 무상태Streamable HTTP (stateless)
장기 세션 유지 필요Streamable HTTP (stateful)

State와 StreamableHTTP

무상태 vs 유상태

HTTP 기반 서버는 두 가지 모드로 운영할 수 있다.

구분StatelessStateful
세션 유지없음 — 매 요청 독립세션 ID로 유지
확장수평 확장 쉬움 (로드 밸런서 친화)스티키 세션 필요
SSE 알림제한적장기 연결로 자유롭게 푸시
Sampling어려움자연스럽게 지원
선택 기준 단발성 도구(검색·계산)면 stateless로 시작한다. Notification·Sampling·장기 작업이 필요하면 stateful이 자연스럽다. 둘을 섞을 수도 있지만 운영 복잡도가 올라간다.

적용 포인트 — 비전 검사 파이프라인에 적용

산업용 이미징 SDK에서의 활용

Notifications — 100장의 이미지를 배치 검사할 때 진행률을 클라이언트로 흘려보낸다. 사용자는 어느 단계에서 멈췄는지, 어떤 이미지에서 경고가 나왔는지 즉시 본다.
Sampling — 결함 영역의 마스크 + 메타데이터를 서버가 받아서 자연어 결함 분류 라벨링을 LLM에 위임한다. 키는 클라이언트가 관리한다.
Roots — 검사 이미지 폴더를 Root로 제한해서 LLM이 회사 전체 파일 시스템을 탐색하지 못하게 한다.
Streamable HTTP (stateful) — 현장 PC와 검사 서버가 LAN으로 연결될 때, 한 세션 동안 카메라 상태·검사 컨텍스트를 유지한다.

권장 아키텍처 스케치

[WPF Viewer]  --stdio-->  [Local MCP Server]
     |                          |
     |                          +-- run_flow(name)        # Tool
     |                          +-- flow://current        # Resource
     |                          +-- /diagnose-defect       # Prompt
     |                          +-- progress notifications
     |                          +-- sampling/createMessage

한계와 운영 고려사항

  • 버전 호환성 — 클라이언트와 서버 SDK 버전이 달라지면 새 기능(Sampling, Roots 등)이 동작하지 않을 수 있다. 핸드셰이크 시 capability를 협상한다.
  • 비용 — Sampling은 토큰을 소비한다. 서버가 무절제하게 부르면 사용자 비용이 폭증한다. 호출 횟수 제한 정책이 필요하다.
  • 관측성 — Streamable HTTP에서 SSE 끊김·재연결 처리는 직접 구현해야 한다. 로그 표준화가 중요하다.
  • 보안 — Roots만으로는 부족하다. 인증(토큰), 권한(스코프), 감사 로그까지 함께 설계한다.
"심화 기능 = 만능"이 아니다 Sampling·Notifications·Roots는 강력하지만 그만큼 디버깅 표면적이 늘어난다. 입문 강의에서 다룬 stdio + tools 조합으로 풀리는 문제라면 굳이 복잡한 전송·양방향을 도입하지 않는 게 낫다.
