책 개요

The Missing README: A Guide for the New Software Engineer

저자Chris Riccomini, Dmitriy Ryaboy

개발자 온보딩 가이드(원제 The Missing README)는 제목 그대로 "있어야 하는데 아무도 안 준 설명서"를 표방하는 책이다. 컴퓨터공학 수업이나 부트캠프는 알고리즘과 문법은 가르치지만, 정작 회사에 들어가서 마주치는 현실 — 남이 짠 거대한 코드베이스, 코드 리뷰, 배포, 장애 대응, 동료와 일하는 법 — 은 알려주지 않는다. 이 책은 그 빈칸을 채운다.

저자 Chris Riccomini는 PayPal·LinkedIn·WePay를 거치며 Apache Samza를 만든 엔지니어이고, Dmitriy Ryaboy는 Cloudera·Twitter를 거치며 Apache Parquet 제작에 참여한 엔지니어다. 둘 다 대형 테크 기업에서 신입을 오래 멘토링해 온 경험을 책에 녹였다.

대상은 명확하다. 막 현업에 들어선 신입 개발자, 그리고 신입을 받아 멘토링해야 하는 선임이다. 코드를 짜는 법이 아니라 "회사에서 개발자로 일하는 법"을 다룬다.

왜 이 책인가

개발 실력과 "회사에서 잘 일하는 것"은 다른 문제다. 알고리즘 문제를 잘 풀어도, 수십만 줄짜리 레거시 코드 앞에서 어디부터 봐야 할지, 첫 코드 리뷰에서 깨졌을 때 어떻게 받아들여야 할지, 새벽에 장애 알림을 받으면 뭘 해야 할지는 아무도 안 알려준다. 신입이 가장 막막해하는 건 대부분 이런 "코드 바깥의 일"이다.

이 책의 가치는 그 막막함을 구체적인 행동 지침으로 바꿔준다는 데 있다. 추상적인 "열심히 해라"가 아니라, "첫 주에는 이렇게, 코드 리뷰는 이렇게, 배포는 이렇게"라는 식의 실용적 조언이 이어진다.

제목의 의미 소프트웨어 프로젝트의 README는 "이걸 어떻게 쓰는지"를 알려주는 첫 문서다. 신입 개발자에게는 "회사 생활을 어떻게 하는지" 알려주는 README가 없다 — 그 빠진(missing) README를 쓴 책이라는 뜻이다.

책의 구성

책은 크게 "들어가기 → 일하기 → 함께하기"의 흐름으로 전개된다. 처음 출근부터 시작해 코드를 다루는 실무, 그리고 팀·조직과 협업하는 단계로 넓어진다.

부다루는 내용
시작하기첫 출근, 멘토·동료와 관계 맺기, 기대치 조율, 도구 환경 세팅
코드 다루기남의 코드베이스 적응, 기술부채 관리, 프로덕션급 코드 작성, 의존성 관리
엔지니어링 실무테스트, 코드 리뷰, 안전한 배포, 진화 가능한 아키텍처 설계, 온콜·장애 대응
함께 일하기커뮤니케이션, 회의, 프로젝트 진행, 커리어 성장과 평가

핵심 내용 몇 가지

남의 코드베이스에 적응하기

신입이 가장 먼저 겪는 충격은 "이 거대한 코드를 다 이해해야 하나"라는 압박이다. 책은 전부 이해하려 하지 말고, 지금 맡은 작업에 필요한 만큼만 좁게 파고들라고 조언한다. 작은 변경부터 시작해 코드베이스와 빌드·배포 흐름에 익숙해지는 게 먼저다.

코드 리뷰를 대하는 자세

첫 코드 리뷰에서 지적을 잔뜩 받으면 자존심이 상한다. 책은 리뷰가 "사람"이 아니라 "코드"를 향한다는 점을 강조한다. 받는 쪽은 방어적으로 굴지 않고, 하는 쪽은 친절하고 구체적으로 — 양쪽의 태도를 모두 다룬다.

기술부채와 프로덕션 코드

학교 과제 코드와 프로덕션 코드는 다르다. 동작하는 것을 넘어, 남이 읽고·고치고·운영할 수 있어야 한다. 에러 처리, 로깅, 모니터링, 테스트 — "돌아가는 코드"와 "운영되는 코드"의 차이를 짚는다.

배포와 온콜·장애 대응

안전한 배포 전략, 그리고 새벽에 울리는 장애 알림(온콜)에 어떻게 대응하는지까지 다룬다. 신입 시절 가장 두려운 순간을 "절차와 침착함"으로 바꾸는 법을 알려준다.

인상 깊은 점

대부분의 기술서가 "무엇을 만드는가"에 집중하는 데 비해, 이 책은 "조직 안에서 어떻게 살아남고 성장하는가"를 정면으로 다룬다. 커뮤니케이션, 기대치 조율, 시간 관리, 멘토 활용 같은 "소프트 스킬"을 추상적 훈계가 아니라 구체적 행동으로 풀어낸 점이 좋았다.

특히 "완벽하게 이해하고 시작하려 하지 말라", "질문하는 것을 두려워하지 말되 먼저 스스로 찾아보라" 같은 균형 잡힌 조언이 현실적이다. 신입의 흔한 두 극단(아무것도 안 묻기 / 다 물어보기) 사이를 잘 짚는다.

핵심 교훈

신입 시절 알았으면 좋았을 것 ① 코드베이스를 전부 이해하려 하지 말고 작업에 필요한 만큼만 좁게 판다. ② 코드 리뷰의 지적은 코드를 향한 것이지 나를 향한 게 아니다. ③ "돌아가는 코드"가 아니라 "운영되는 코드"를 짠다. ④ 막히면 적당한 시점에 도움을 청하는 것도 실력이다.

누구에게 / 어떻게 읽나

막 현업에 들어온 신입이라면 입사 첫 달에 읽으면 가장 효과가 크다. 닥칠 일을 미리 지도로 받아두는 셈이다. 신입을 멘토링하는 선임이라면, 내가 암묵적으로 알고 있던 것을 어떻게 말로 전달할지 정리하는 데 도움이 된다.

처음부터 끝까지 정독해도 좋지만, 목차를 훑어두고 그 상황이 닥칠 때마다 해당 장을 다시 펴 보는 "레퍼런스" 식 독서도 잘 맞는 책이다.

이 블로그와의 연결

이 책이 다루는 "운영되는 코드"와 "장애 대응"은 본 블로그의 다른 글과도 맞닿아 있다. 코드 품질·설계 측면은 프로그래밍 이론 시리즈와, 장애·디버깅 측면은 Windows 크래시 덤프 분석 시리즈와 함께 보면 "신입이 알아야 할 실무"의 그림이 더 선명해진다.

한 줄 평

"학교가 안 가르쳐 준 '회사에서 개발자로 사는 법'을 한 권에 담은 책." 코드를 잘 짜는 것과 현업에서 잘 일하는 것이 다르다는 걸 일찍 알려주는, 신입에게 특히 고마운 안내서다.
