빌드 시스템과 패키지 매니저가 푸는 문제

C++ 프로젝트가 커지면 두 가지 골치 아픈 문제가 생긴다. 하나는 "이 소스들을 어떻게 바이너리로 만드는가", 다른 하나는 "OpenCV 같은 외부 라이브러리를 어떻게 가져오는가"다. 이 둘은 서로 다른 도구가 해결한다.

도구푸는 문제본 프로젝트
빌드 시스템소스 → 바이너리. 플랫폼/IDE에 독립적인 빌드 정의CMake
패키지 매니저외부 라이브러리 설치 / 버전 관리vcpkg

CMake는 컴파일러를 직접 호출하지 않는다. 대신 CMakeLists.txt라는 빌드 정의를 읽어서 Visual Studio 솔루션이나 Makefile 같은 실제 빌드 파일을 생성한다. 같은 정의 하나로 윈도우에서는 VS, 리눅스에서는 Make로 빌드할 수 있다.

vcpkg는 OpenCV, spdlog, gtest 같은 의존성을 소스에서 받아 컴파일하고 설치해 준다. 둘의 통합은 단순하다 — vcpkg가 라이브러리를 깔고, CMake의 find_package()가 그것을 찾아 쓴다. 이 글은 그 연결을 처음부터 끝까지 다룬다.

CMake 기본 개념

CMake의 빌드는 세 단계로 흐른다.

단계하는 일
configureCMakeLists.txt를 읽고 컴파일러 / 환경을 탐지
generate실제 빌드 파일(VS 솔루션, Makefile 등) 생성
build생성된 빌드 파일로 컴파일 / 링크

중요한 원칙은 out-of-source 빌드다. 빌드 산출물은 소스 디렉터리가 아니라 별도의 build/ 디렉터리에 모은다. 소스와 산출물이 섞이지 않아서 깨끗하고, build/ 폴더만 지우면 처음부터 다시 빌드할 수 있다.

# 프로젝트 루트에서
cmake -B build -S .      # configure + generate (build/ 디렉터리에)
cmake --build build      # build

그리고 모던 CMake에서 가장 중요한 사고방식 — 모든 것은 target이다. 라이브러리도 target, 실행 파일도 target. include 경로, 컴파일 옵션, 링크할 라이브러리는 전부 "어떤 target에 붙는 속성"으로 다룬다. 이 관점을 잡으면 나머지가 자연스럽게 따라온다.

최소 CMakeLists.txt

cmake_minimum_required(VERSION 3.21)
project(ImagingLibrary VERSION 0.1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_library(core
    core/src/Image.cpp
    core/src/ImageProcessor.cpp
)
target_include_directories(core PUBLIC core/include)

add_library(core ...)가 core라는 target을 만들고, target_include_directories가 그 target에 include 경로를 붙인다. 실행 파일은 add_executable(...)로 만든다. 구조는 동일하다.

target 기반 빌드 — 모던 CMake의 핵심

target에 속성을 붙이는 명령은 한 묶음으로 외워두면 좋다.

명령붙이는 속성
target_link_libraries링크할 라이브러리 (다른 target 포함)
target_include_directories헤더 검색 경로
target_compile_features요구 언어 표준 (예: cxx_std_17)
target_compile_definitions전처리기 매크로 정의

PUBLIC / PRIVATE / INTERFACE

이 세 키워드는 속성이 어디까지 전파되는가를 정한다. 모던 CMake를 제대로 쓰려면 반드시 이해해야 하는 부분이다.

키워드이 target이 target을 쓰는 쪽예시
PRIVATE적용전파 안 됨구현에만 쓰는 내부 의존성
INTERFACE적용 안 됨전파됨헤더 전용 라이브러리
PUBLIC적용전파됨공개 헤더에 노출되는 의존성

판단 기준은 단순하다. 어떤 의존성이 core의 공개 헤더(.h)에 등장하면 그것을 쓰는 쪽도 알아야 하니 PUBLIC. .cpp 안에서만 쓰면 PRIVATE. 예를 들어 OpenCV 타입이 Image.h에 노출된다면 PUBLIC, 로깅용 spdlog가 구현 파일에서만 쓰인다면 PRIVATE다.

target 기반으로 사고하라 "core가 무엇을 필요로 하는가"를 core target에 직접 선언하면, core를 링크하는 쪽은 그 의존성을 신경 쓸 필요가 없다. 의존성이 target을 따라 자동으로 흐르는 것 — 이게 모던 CMake의 전부다.
전역 명령은 안티패턴이다 include_directories()나 link_libraries()처럼 target 없이 쓰는 전역 명령은 피한다. 모든 target에 무차별 적용되어 "이 target이 정확히 무엇에 의존하는가"를 추적할 수 없게 된다.

여러 모듈로 구성하기

ImagingLibrary는 core 라이브러리, measurement 솔루션, 테스트로 나뉜다. 각 디렉터리가 자기 CMakeLists.txt를 갖고, 루트의 CMakeLists.txt가 add_subdirectory()로 묶는다.

ImagingLibrary/
  CMakeLists.txt               # 루트 - 전체를 묶음
  core/CMakeLists.txt          # core 라이브러리
  solutions/measurement/CMakeLists.txt
  tests/CMakeLists.txt         # gtest 테스트
# 루트 CMakeLists.txt
cmake_minimum_required(VERSION 3.21)
project(ImagingLibrary VERSION 0.1.0 LANGUAGES CXX)

add_subdirectory(core)
add_subdirectory(solutions/measurement)
add_subdirectory(tests)
# solutions/measurement/CMakeLists.txt
add_library(measurement
    src/EdgeDistance.cpp
)
target_include_directories(measurement PUBLIC include)

# measurement는 core에 의존한다
target_link_libraries(measurement PUBLIC core)

target_link_libraries(measurement PUBLIC core) 한 줄이면 끝이다. measurement는 core의 include 경로와 의존성을 자동으로 물려받는다. 따로 target_include_directories로 core의 헤더 경로를 다시 적어줄 필요가 없다 — core target이 PUBLIC으로 선언해 둔 것이 그대로 전파되기 때문이다.

vcpkg와 manifest mode

vcpkg는 Microsoft가 만든 C++ 패키지 매니저다. 동작 방식이 두 가지 있다.

모드의존성 선언 위치특징
classic mode없음 (vcpkg install 수동 실행)전역 설치, 프로젝트 간 공유, 버전 추적 어려움
manifest mode프로젝트의 vcpkg.json프로젝트별 격리, 버전 선언적 관리 (권장)

manifest mode는 프로젝트 루트에 vcpkg.json 파일을 두고 거기에 의존성을 적어두는 방식이다. configure 시점에 CMake가 그 파일을 읽어 필요한 라이브러리를 자동으로 설치한다. 프로젝트마다 독립적이고, 파일 하나로 의존성 전체가 기술되니 새 팀원도 클론 후 빌드만 하면 된다.

vcpkg.json 작성

{
  "name": "imaging-library",
  "version": "0.1.0",
  "dependencies": [
    {
      "name": "opencv4",
      "version>=": "4.10.0",
      "features": ["contrib"]
    },
    "spdlog",
    "gtest"
  ],
  "builtin-baseline": "abc1234567890def...",
  "overrides": [
    { "name": "spdlog", "version": "1.14.1" }
  ]
}
필드의미
dependencies필요한 패키지 목록. 문자열 또는 객체로 적는다
features패키지의 선택적 기능 활성화 (예: opencv4의 contrib)
version>=최소 버전 요구
builtin-baselinevcpkg 레지스트리의 특정 커밋. 버전 고정의 기준점
overrides특정 패키지를 지정한 버전으로 강제
baseline을 반드시 고정하라 builtin-baseline이 없으면 빌드하는 시점의 최신 레지스트리를 따라가서 사람마다, 날짜마다 다른 버전이 깔린다. baseline 커밋을 박아두면 재현 가능한 빌드(reproducible build)가 보장된다.

CMake + vcpkg 통합

둘을 잇는 핵심은 toolchain file 하나다. vcpkg에는 vcpkg.cmake라는 toolchain 파일이 들어 있다. 이것을 CMake의 CMAKE_TOOLCHAIN_FILE 변수로 지정하면, configure 시점에 vcpkg가 끼어들어 vcpkg.json의 의존성을 설치하고, find_package()가 그 설치본을 찾도록 경로를 설정한다.

cmake -B build -S . \
  -DCMAKE_TOOLCHAIN_FILE=C:/vcpkg/scripts/buildsystems/vcpkg.cmake

이 한 줄을 매번 치는 건 번거롭고 실수도 잦다. 그래서 뒤에서 다룰 CMakePresets.json에 toolchain 경로를 한 번 박아두는 것이 권장된다.

find_package로 target 연결

toolchain이 지정되면 find_package가 vcpkg 설치본을 찾는다. 찾은 라이브러리는 target 형태로 제공되므로 target_link_libraries로 그냥 붙이면 된다.

find_package(OpenCV CONFIG REQUIRED)
find_package(spdlog CONFIG REQUIRED)

target_link_libraries(core
    PUBLIC  opencv_core opencv_imgproc
    PRIVATE spdlog::spdlog
)

OpenCV 타입이 core의 공개 헤더에 노출되므로 opencv_*는 PUBLIC, spdlog는 구현 파일에서만 쓰이므로 PRIVATE다. CONFIG 키워드는 패키지가 제공하는 CMake 설정 파일을 쓰라는 의미로, vcpkg 패키지는 대부분 이 방식을 지원한다.

find_package가 못 찾으면 toolchain 미지정을 의심하라 "Could not find package" 에러의 가장 흔한 원인은 CMAKE_TOOLCHAIN_FILE을 빠뜨린 것이다. vcpkg.json이 있어도 toolchain을 지정하지 않으면 CMake는 vcpkg의 존재 자체를 모른다.

CMakePresets.json과 VS2022

CMakePresets.json은 빌드 설정을 파일로 고정하는 표준 방식이다. toolchain 경로, generator, 빌드 디렉터리, 캐시 변수를 한 곳에 정의해 두면 팀원 모두가 똑같은 설정으로 빌드한다.

{
  "version": 3,
  "configurePresets": [
    {
      "name": "default",
      "generator": "Visual Studio 17 2022",
      "binaryDir": "${sourceDir}/build",
      "cacheVariables": {
        "CMAKE_TOOLCHAIN_FILE": "C:/vcpkg/scripts/buildsystems/vcpkg.cmake"
      }
    }
  ],
  "buildPresets": [
    { "name": "default", "configurePreset": "default" }
  ]
}
cmake --preset default          # configure
cmake --build --preset default  # build
CMakePresets.json은 커밋하라 toolchain 경로와 generator를 preset에 박아두면 명령줄 인자를 외울 필요가 없고, CI도 같은 preset을 그대로 쓴다. 빌드 환경의 단일 진실 공급원(single source of truth)이 된다.

VS2022 통합

VS2022는 CMake 프로젝트를 솔루션 변환 없이 직접 연다. CMakeLists.txt가 있는 폴더를 "폴더 열기"로 열면 된다. CMakePresets.json은 자동으로 인식되어 상단 드롭다운에서 preset을 고를 수 있고, vcpkg는 VS에 통합되어 있어 별도 설정 없이 manifest mode가 동작한다.

테스트 통합

CMake에는 CTest라는 테스트 러너가 내장되어 있다. enable_testing()으로 켜고, gtest 기반이면 gtest_discover_tests()가 테스트 케이스를 자동으로 등록해 준다.

# tests/CMakeLists.txt
find_package(GTest CONFIG REQUIRED)
enable_testing()

add_executable(core_tests core_tests/ImageProcessorTest.cpp)
target_link_libraries(core_tests PRIVATE core GTest::gtest_main)

include(GoogleTest)
gtest_discover_tests(core_tests)
ctest --preset default        # 또는 build 디렉터리에서 ctest

이렇게 해두면 CI 파이프라인에서도 ctest 한 줄로 전체 테스트가 돌아간다. 본 프로젝트의 GitLab CI Phase 2(빌드 + 테스트 자동 실행)가 정확히 이 구조를 전제로 한다.

흔한 함정

전역 include_directories 남용 target 없이 전역으로 경로를 뿌리면 어느 target이 무엇에 의존하는지 추적이 불가능해진다. 항상 target_include_directories를 쓴다.
find_package가 못 찾음 대부분 CMAKE_TOOLCHAIN_FILE 미지정이 원인이다. preset에 toolchain을 박아두면 이 실수가 사라진다.
classic mode와 manifest mode 혼용 둘을 섞으면 어느 쪽 라이브러리가 링크되는지 예측 불가능해진다. manifest mode를 쓰기로 했으면 전역 vcpkg install은 쓰지 않는다.
baseline 미고정 builtin-baseline이 없으면 빌드할 때마다 다른 버전이 깔릴 수 있다. 재현 가능한 빌드를 위해 반드시 고정한다.
build 디렉터리를 커밋 build/는 생성물이다. 절대 커밋하지 않는다. .gitignore에 반드시 추가한다.
CMAKE_CXX_STANDARD를 전역으로만 설정 전역 set(CMAKE_CXX_STANDARD 17)도 동작은 하지만, 모던하게는 target별로 target_compile_features(core PUBLIC cxx_std_17)를 쓰는 것이 권장된다. 표준 요구가 target을 따라 전파되기 때문이다.

시리즈를 닫으며

이 글로 C++ 시리즈 24편이 끝난다. STL의 컨테이너와 알고리즘에서 출발해, 모던 C++의 스마트 포인터와 이동 의미론, 동시성, 산업 현장 적용을 거쳐, 마지막은 그 코드를 실제로 빌드하고 의존성을 관리하는 인프라까지 왔다.

문법을 아는 것과 프로젝트를 굴리는 것은 다른 일이다. 24편을 통해 그 간극이 조금이나마 좁혀졌다면 시리즈의 목적은 이룬 셈이다.
