복잡도를 왜 따지는가

복잡도(complexity)는 입력 크기가 커질 때 알고리즘이 얼마나 더 느려지는가, 얼마나 더 많은 메모리를 쓰는가를 나타내는 척도다. 핵심은 "얼마나 느린가"의 절대값이 아니라 "입력이 커질 때 어떻게 변하는가"의 증가 경향이다.

같은 알고리즘이라도 CPU 클럭, 컴파일러 최적화, 캐시 상태에 따라 실행 시간이 달라진다. 측정값은 환경에 종속적이므로 알고리즘 자체를 평가하는 기준이 될 수 없다. 그래서 우리는 "입력 크기 n에 대해 연산 횟수가 어떤 함수로 증가하는가"라는, 환경에 독립적인 추상적 척도를 쓴다.

측정값이 아니라 증가 경향

아래 두 함수는 같은 일(배열에서 특정 값 찾기)을 한다. 하나는 정렬되지 않은 배열을 처음부터 훑고, 하나는 정렬된 배열을 이분 탐색한다.

// 선형 탐색 — 최악의 경우 n번 비교
int LinearSearch(const std::vector<int>& data, int target)
{
    for (int i = 0; i < static_cast<int>(data.size()); ++i)
    {
        if (data[i] == target)
        {
            return i;
        }
    }
    return -1;
}

// 이분 탐색 — 정렬된 배열에서 매 단계 범위를 절반으로 줄임
int BinarySearch(const std::vector<int>& sorted, int target)
{
    int low = 0;
    int high = static_cast<int>(sorted.size()) - 1;
    while (low <= high)
    {
        int mid = low + (high - low) / 2;
        if (sorted[mid] == target)      { return mid; }
        else if (sorted[mid] < target)  { low = mid + 1; }
        else                            { high = mid - 1; }
    }
    return -1;
}

n이 100일 때는 둘의 차이가 미미하다. 하지만 n이 10억이면 선형 탐색은 최악의 경우 10억 번 비교하고, 이분 탐색은 약 30번이면 끝난다. 입력이 커질수록 벌어지는 이 격차가 복잡도가 말하려는 전부다. 작은 입력에서의 1~2배 차이가 아니라, 큰 입력에서의 수억 배 차이가 알고리즘의 운명을 가른다.

복잡도는 "알고리즘의 체급"이다 복잡도를 따진다는 것은 스톱워치로 시간을 재는 일이 아니다. "이 알고리즘은 입력이 두 배가 되면 일이 몇 배로 늘어나는 종류인가?"를 묻는 일이다. 체급이 다르면, 상대의 코드를 아무리 최적화해도 입력이 커지면 결국 진다.

Big-O 표기

Big-O 표기법은 입력 크기 n이 충분히 커질 때, 알고리즘의 연산 횟수가 증가하는 비율의 상한(upper bound)을 나타낸다. 보통 "최악의 경우 이보다 빠르게 증가하지는 않는다"는 보장으로 읽는다.

f(n) = O(g(n))  ⇔  어떤 상수 c > 0, n₀ ≥ 0 이 존재하여 모든 n ≥ n₀ 에서 f(n) ≤ c · g(n) n이 충분히 커지면 f(n)은 g(n)의 상수배를 절대 넘지 않는다 — 즉 g(n)이 증가율의 천장이다

상수와 낮은 차수 항을 버리는 이유

어떤 함수의 연산 횟수가 3n² + 5n + 100 이라고 하자. Big-O는 이것을 O(n²)으로 단순화한다. 두 가지를 버린다.

  • 상수 계수 — 3n²의 3을 버린다. 상수 계수는 하드웨어와 구현에 따라 달라지는 값이라 알고리즘의 본질이 아니다.
  • 낮은 차수 항 — 5n과 100을 버린다. n이 커지면 n² 항이 압도적으로 커져 나머지는 무시할 만해진다.

예를 들어 n = 1,000이면 3n²은 300만, 5n은 5천, 100은 100이다. n² 항이 전체의 99.8%를 차지한다. n이 더 커지면 이 비중은 100%에 수렴한다. Big-O는 "큰 입력에서 결국 무엇이 지배하는가"만 본다.

// 연산 횟수: 1(초기화) + 3n(루프) + 2(반환부) = 3n + 3  ->  O(n)
int SumArray(const std::vector<int>& data)
{
    int sum = 0;                                    // 상수 작업
    for (size_t i = 0; i < data.size(); ++i)        // n번 반복
    {
        sum += data[i];                             // 반복마다 상수 작업
    }
    return sum;                                     // 상수 작업
}

// 연산 횟수: n + n*n = n + n^2  ->  O(n^2) (낮은 차수 n은 버려짐)
void PrintPairs(const std::vector<int>& data)
{
    for (size_t i = 0; i < data.size(); ++i)        // 바깥 루프 n번
    {
        for (size_t j = 0; j < data.size(); ++j)    // 안쪽 루프 n번
        {
            // i, j 조합 출력 — 총 n*n번 실행
        }
    }
}
상수를 버린다고 상수가 안 중요한 건 아니다 Big-O가 상수를 버리는 것은 증가 경향을 비교하기 위한 추상화일 뿐이다. 같은 O(n)이라도 한 쪽의 상수 계수가 다른 쪽의 100배라면 실제로는 100배 느리다. 상수는 "이론적 분류"에서 무시될 뿐, "실제 성능"에서는 결정적일 수 있다. 이 간극은 8장에서 다시 다룬다.

주요 복잡도 등급

실무에서 마주치는 복잡도는 대부분 몇 가지 정해진 등급으로 분류된다. 좋은 것부터 나쁜 것 순으로 정리한다.

복잡도 등급별 증가 곡선 — n이 커질수록 등급 간 격차가 폭발적으로 벌어진다

O(1) — 상수 시간

입력 크기와 무관하게 항상 일정한 연산을 한다. 배열 인덱스 접근, 해시 테이블 조회, 스택의 push/pop이 여기 속한다.

// 입력 크기와 무관 — 항상 한 번의 접근
int GetFirst(const std::vector<int>& data)
{
    return data[0];   // n이 10이든 10억이든 동일
}

O(log n) — 로그 시간

매 단계마다 처리할 범위를 일정 비율(보통 절반)로 줄인다. 이분 탐색, 균형 이진 탐색 트리 연산이 대표적이다. n이 두 배가 되어도 연산은 한 번만 늘어난다.

// 매 반복마다 탐색 범위가 절반 -> log2(n)번이면 끝
int CountHalvings(int n)
{
    int steps = 0;
    while (n > 1)
    {
        n /= 2;       // 범위를 절반으로
        ++steps;
    }
    return steps;     // n=1024 -> 10, n=1048576 -> 20
}

O(n) — 선형 시간

입력의 모든 원소를 상수 횟수만큼 훑는다. 배열 합산, 최댓값 찾기, 선형 탐색이 여기 속한다. 입력이 두 배가 되면 시간도 두 배가 된다.

// 모든 원소를 한 번씩 확인 -> O(n)
int FindMax(const std::vector<int>& data)
{
    int maxValue = data[0];
    for (size_t i = 1; i < data.size(); ++i)
    {
        if (data[i] > maxValue)
        {
            maxValue = data[i];
        }
    }
    return maxValue;
}

O(n log n) — 선형 로그 시간

비교 기반 정렬의 이론적 하한이다. 병합 정렬, 힙 정렬, 평균적인 퀵 정렬이 여기 속한다. "n개를 log n번 훑는다"는 형태로 자주 나타난다.

// 표준 라이브러리 정렬 — 평균 O(n log n)
void SortAscending(std::vector<int>& data)
{
    std::sort(data.begin(), data.end());   // 내부적으로 introsort
}

O(n²) — 이차 시간

중첩 반복문으로 모든 원소 쌍을 확인한다. 버블 정렬, 삽입 정렬, 단순한 중복 검사가 여기 속한다. 입력이 두 배가 되면 시간은 네 배가 된다.

// 모든 쌍을 비교 -> n*(n-1)/2 ~ O(n^2)
bool HasDuplicate(const std::vector<int>& data)
{
    for (size_t i = 0; i < data.size(); ++i)
    {
        for (size_t j = i + 1; j < data.size(); ++j)
        {
            if (data[i] == data[j])
            {
                return true;
            }
        }
    }
    return false;
}

O(2ⁿ), O(n!) — 지수·팩토리얼 시간

입력이 하나 늘 때마다 일이 두 배(2ⁿ) 또는 그 이상(n!)으로 폭증한다. 모든 부분집합 탐색, 분기 한정 없는 외판원 문제 완전 탐색이 여기 속한다. n이 조금만 커져도 사실상 계산이 불가능하다.

// 메모이제이션 없는 재귀 피보나치 — O(2^n)
// fib(n)이 fib(n-1)과 fib(n-2)를 각각 다시 호출하며 호출 트리가 지수적으로 분기
long long FibNaive(int n)
{
    if (n <= 1)
    {
        return n;
    }
    return FibNaive(n - 1) + FibNaive(n - 2);   // 한 번 호출이 두 번 호출로
}

최선·평균·최악

같은 알고리즘이라도 입력의 상태에 따라 연산 횟수가 달라진다. 그래서 복잡도는 세 가지 경우로 나눠 본다.

  • 최선의 경우(best case) — 알고리즘이 가장 운이 좋은 입력. 보통 큰 의미가 없다.
  • 평균의 경우(average case) — 무작위 입력에 대한 기댓값. 실무 성능 예측에 가장 유용하다.
  • 최악의 경우(worst case) — 가장 불리한 입력. Big-O가 기본적으로 보장하는 값이며, 실시간 시스템에서 가장 중요하다.

퀵 정렬 — 같은 알고리즘, 다른 복잡도

퀵 정렬은 피벗(pivot)을 골라 그보다 작은 값과 큰 값으로 분할하는 과정을 재귀적으로 반복한다. 피벗이 매번 중앙값에 가까우면 분할이 균형 잡혀 O(n log n)이지만, 피벗이 매번 최솟값이나 최댓값이면 한쪽으로만 분할되어 O(n²)으로 퇴화한다.

// 퀵 정렬 — 피벗 선택에 따라 복잡도가 갈린다
void QuickSort(std::vector<int>& data, int low, int high)
{
    if (low >= high)
    {
        return;
    }
    int pivot = data[high];   // 마지막 원소를 피벗으로 (단순한 선택)
    int i = low - 1;
    for (int j = low; j < high; ++j)
    {
        if (data[j] < pivot)
        {
            ++i;
            std::swap(data[i], data[j]);
        }
    }
    std::swap(data[i + 1], data[high]);
    int p = i + 1;

    QuickSort(data, low, p - 1);    // 왼쪽 부분
    QuickSort(data, p + 1, high);   // 오른쪽 부분
}
경우복잡도발생 조건
최선O(n log n)피벗이 매번 중앙값 — 분할이 완벽히 균형
평균O(n log n)무작위 입력 — 분할이 대체로 균형
최악O(n²)이미 정렬된 배열 + 끝 원소 피벗 — 분할이 1:n-1로 치우침

아이러니하게도 위 코드에서 이미 정렬된 배열이 최악의 입력이다. 그래서 실무 구현은 무작위 피벗이나 "median-of-three" 같은 기법으로 최악 케이스를 회피한다. C++ 표준 라이브러리의 std::sort는 퀵 정렬이 퇴화 조짐을 보이면 힙 정렬로 전환하는 introsort를 써서 최악에도 O(n log n)을 보장한다.

어느 경우를 봐야 하는가 일반 응용에서는 평균이 현실적인 예측치다. 하지만 실시간 검사 장비처럼 "한 프레임을 반드시 N ms 안에 처리"해야 하는 시스템에서는 최악이 곧 설계 기준이다. 평균이 빨라도 최악이 마감을 넘기면 그 알고리즘은 못 쓴다.

공간 복잡도

공간 복잡도(space complexity)는 입력 크기가 커질 때 알고리즘이 사용하는 추가 메모리의 증가율이다. 시간 복잡도와 똑같이 Big-O로 표기한다. 보통 입력 자체가 차지하는 공간은 제외하고, 알고리즘이 별도로 쓰는 메모리만 센다.

// 공간 O(1) — 입력 크기와 무관하게 변수 몇 개만 사용
int SumInPlace(const std::vector<int>& data)
{
    int sum = 0;                              // 추가 메모리: 상수
    for (int v : data)
    {
        sum += v;
    }
    return sum;
}

// 공간 O(n) — 입력 크기에 비례하는 새 배열을 만듦
std::vector<int> DoubledCopy(const std::vector<int>& data)
{
    std::vector<int> result;
    result.reserve(data.size());              // 추가 메모리: n에 비례
    for (int v : data)
    {
        result.push_back(v * 2);
    }
    return result;
}

재귀의 숨은 공간 비용

재귀 함수는 호출될 때마다 스택 프레임을 쌓는다. 따라서 재귀 깊이만큼 호출 스택 메모리를 소모한다. 코드에 새 배열이 보이지 않아도 공간을 쓰고 있는 것이다.

// 시간 O(n), 공간 O(n) — 재귀 깊이 n만큼 스택 프레임이 쌓인다
long long FactorialRecursive(int n)
{
    if (n <= 1)
    {
        return 1;
    }
    return n * FactorialRecursive(n - 1);   // n번 중첩 호출
}

// 시간 O(n), 공간 O(1) — 반복으로 바꾸면 스택을 쓰지 않는다
long long FactorialIterative(int n)
{
    long long result = 1;
    for (int i = 2; i <= n; ++i)
    {
        result *= i;
    }
    return result;
}

시간-공간 트레이드오프

많은 알고리즘에서 시간과 공간은 맞바꿀 수 있다. 메모리를 더 쓰면 시간을 줄이고, 메모리를 아끼면 시간을 더 쓴다. 메모이제이션이 대표적이다 — 계산 결과를 저장해두면 같은 계산을 반복하지 않아도 된다.

// 메모이제이션 피보나치 — 공간 O(n)을 써서 시간을 O(2^n)에서 O(n)으로
long long FibMemo(int n, std::vector<long long>& cache)
{
    if (n <= 1)
    {
        return n;
    }
    if (cache[n] != -1)
    {
        return cache[n];          // 이미 계산했으면 즉시 반환
    }
    cache[n] = FibMemo(n - 1, cache) + FibMemo(n - 2, cache);
    return cache[n];
}
트레이드오프는 "공짜 점심이 없다"는 뜻이 아니다 시간-공간 트레이드오프는 종종 압도적으로 이득이다. 피보나치 메모이제이션은 O(n)의 작은 메모리를 써서 O(2ⁿ)를 O(n)으로 바꾼다. 다만 임베디드 장비처럼 메모리가 빠듯한 환경에서는 그 작은 O(n)조차 부담일 수 있으므로, 트레이드오프의 방향은 항상 환경이 결정한다.

복잡도 분석 방법

코드를 보고 복잡도를 읽어내는 데는 몇 가지 규칙이 있다. 대부분의 코드는 이 규칙의 조합으로 분석된다.

반복문 — 횟수의 곱

순차적인 코드 블록은 복잡도를 더하고, 중첩된 반복문은 복잡도를 곱한다. 더한 결과에서는 가장 큰 항만 남긴다.

void AnalyzeMe(const std::vector<int>& data)
{
    int n = static_cast<int>(data.size());

    for (int i = 0; i < n; ++i) { /* ... */ }       // O(n)

    for (int i = 0; i < n; ++i)                     // 바깥 n번
    {
        for (int j = 0; j < n; ++j) { /* ... */ }   // 안쪽 n번  ->  n*n
    }
    // 전체: O(n) + O(n^2) = O(n^2)  (큰 항만 남김)
}

주의할 점은 안쪽 루프가 항상 n번 도는 것은 아니라는 것이다. 안쪽 루프의 반복 횟수가 바깥 인덱스에 의존하면 합을 직접 계산해야 한다.

// 안쪽 루프가 j = i 부터 시작 -> 총 반복: n + (n-1) + ... + 1 = n(n+1)/2
void TriangularLoop(int n)
{
    for (int i = 0; i < n; ++i)
    {
        for (int j = i; j < n; ++j) { /* ... */ }   // 평균 n/2번
    }
    // n(n+1)/2 -> 상수와 낮은 차수를 버리면 O(n^2)
}

재귀 — 점화식

재귀 함수의 복잡도는 점화식(recurrence relation)으로 표현한다. "이 문제를 푸는 비용 T(n)은, 더 작은 문제를 푸는 비용 + 그 외 작업"의 형태다.

T(n) = T(n-1) + O(1) FactorialRecursive: n번 호출하며 매번 상수 작업 → T(n) = O(n)
T(n) = 2 · T(n-1) + O(1) FibNaive: 한 번 호출이 두 번 호출로 분기 → T(n) = O(2ⁿ)

분할정복 — 마스터 정리

분할정복 알고리즘은 문제를 a개의 부분 문제로 쪼개고, 각 부분 문제의 크기는 n/b이며, 쪼개고 합치는 데 O(nᵈ)이 든다. 이 형태의 점화식은 마스터 정리(master theorem)로 한 번에 풀 수 있다.

T(n) = a · T(n/b) + O(nᵈ) logba 와 d 의 대소를 비교해 세 경우로 결과가 갈린다
조건결과해석
d < logbaT(n) = O(nlogba)부분 문제 개수가 지배
d = logbaT(n) = O(nᵈ log n)분할 비용과 균형
d > logbaT(n) = O(nᵈ)분할/합치는 비용이 지배

예를 들어 병합 정렬은 문제를 2개로 쪼개고(a = 2), 크기는 절반이고(b = 2), 합치는 데 O(n)이 든다(d = 1). log₂2 = 1 = d이므로 두 번째 경우에 해당하여 T(n) = O(n log n)이다. 이분 탐색은 부분 문제가 1개(a = 1), 크기 절반(b = 2), 분할 비용 O(1)(d = 0)이며 log₂1 = 0 = d로 T(n) = O(log n)이 된다.

// 병합 정렬 — a=2, b=2, 합치기 O(n)  ->  마스터 정리로 O(n log n)
void MergeSort(std::vector<int>& data, int left, int right)
{
    if (left >= right)
    {
        return;
    }
    int mid = left + (right - left) / 2;
    MergeSort(data, left, mid);        // T(n/2) — 왼쪽 절반
    MergeSort(data, mid + 1, right);   // T(n/2) — 오른쪽 절반
    Merge(data, left, mid, right);     // O(n) — 두 절반을 병합
}

Big-O / Big-Ω / Big-Θ

Big-O는 상한만 말한다. 하지만 알고리즘의 증가율을 정확히 묘사하려면 하한과 정확한 경계도 필요하다. 세 가지 표기가 한 세트로 쓰인다.

표기이름의미읽는 법
O(g(n))Big-O증가율의 상한"아무리 나빠도 이보다 빠르게 늘지 않는다"
Ω(g(n))Big-Omega증가율의 하한"아무리 좋아도 이보다 느리게 늘지 않는다"
Θ(g(n))Big-Theta상한 = 하한, 정확한 경계"상한과 하한이 같다 — 딱 이 비율로 늘어난다"
f(n) = Θ(g(n))  ⇔  f(n) = O(g(n))  그리고  f(n) = Ω(g(n)) 상한과 하한이 같은 함수로 묶일 때만 Theta가 성립한다

예를 들어 FindMax는 항상 모든 원소를 정확히 한 번씩 본다. 최선이든 최악이든 n번이므로 상한도 O(n), 하한도 Ω(n), 따라서 Θ(n)이라고 정확하게 말할 수 있다. 반면 선형 탐색은 최선이 O(1)(첫 원소가 정답), 최악이 O(n)이라 단일 Θ로 묶이지 않는다 — 그래서 보통 "최악의 경우 O(n)"이라고만 말한다.

실무에서 Big-O가 사실상 Big-Θ로 쓰이는 이유 엄밀히 말하면 O(n) 알고리즘을 O(n²)이라 불러도 (상한이니까) 틀린 말은 아니다. 하지만 관용적으로 사람들은 Big-O를 "가장 빡빡한 상한(tight bound)"의 뜻으로 쓴다. 즉 실무의 "이 알고리즘은 O(n log n)이다"는 사실상 "Θ(n log n)이다"를 의미한다.

실무에서의 복잡도

Big-O는 강력한 도구지만, 그것만 보고 알고리즘을 고르면 실패한다. 이론과 실제 사이에는 분명한 간극이 있다.

n이 작으면 O(n²)도 충분하다

Big-O는 "n이 충분히 클 때"의 이야기다. n이 작으면 더 나쁜 등급이 오히려 빠를 수 있다. 그래서 실무 정렬 라이브러리는 부분 배열이 작아지면 삽입 정렬로 전환한다 — 작은 입력에서는 O(n²) 삽입 정렬이 O(n log n) 병합 정렬보다 상수 인자가 작아 더 빠르기 때문이다.

// 실무 패턴 — 작은 구간은 삽입 정렬, 큰 구간만 분할정복
constexpr int kSmallThreshold = 16;

void HybridSort(std::vector<int>& data, int left, int right)
{
    if (right - left < kSmallThreshold)
    {
        InsertionSort(data, left, right);   // 작을 땐 O(n^2)이 더 빠름
        return;
    }
    int mid = left + (right - left) / 2;
    HybridSort(data, left, mid);
    HybridSort(data, mid + 1, right);
    Merge(data, left, mid, right);
}

상수 인자와 캐시 효율

Big-O는 상수 계수를 버리지만, 현실에서는 그 상수가 성능을 결정하는 일이 흔하다. 특히 캐시 효율은 Big-O 표기에 전혀 나타나지 않는다. 같은 O(n)이라도 메모리를 순차적으로 접근하는 코드와 무작위로 접근하는 코드는 캐시 적중률 차이로 수십 배까지 벌어진다.

// 둘 다 O(n*m) — 하지만 캐시 동작이 다르다
void RowMajor(std::vector<std::vector<int>>& m)
{
    for (size_t i = 0; i < m.size(); ++i)
        for (size_t j = 0; j < m[i].size(); ++j)
            m[i][j] += 1;          // 메모리 순차 접근 — 캐시 친화적
}

void ColumnMajor(std::vector<std::vector<int>>& m)
{
    for (size_t j = 0; j < m[0].size(); ++j)
        for (size_t i = 0; i < m.size(); ++i)
            m[i][j] += 1;          // 메모리 건너뛰며 접근 — 캐시 미스 빈발
}
// 같은 Big-O, 같은 연산 수. 하지만 RowMajor가 실측으로 몇 배 빠르다.
Big-O는 "n 크기"와 "상수"라는 두 함정을 숨긴다 Big-O만 보고 "이게 더 빠르다"고 단정하면 안 된다. (1) 실제 n이 작으면 등급 비교가 무의미하다. (2) 같은 등급 안에서는 상수 인자와 캐시 동작이 실제 속도를 가른다. 알고리즘을 고를 때는 Big-O로 후보를 좁히고, 실측으로 결정하는 것이 옳은 순서다.

복잡도와 자료구조 선택

복잡도 분석의 가장 실용적인 쓰임새는 자료구조 선택이다. 자료구조마다 같은 연산이라도 복잡도가 다르고, "어떤 연산을 자주 하는가"가 어떤 자료구조를 써야 하는가를 결정한다.

자료구조임의 접근탐색맨 끝 삽입중간 삽입
동적 배열 (vector)O(1)O(n)O(1) 분할상환O(n)
연결 리스트 (list)O(n)O(n)O(1)O(1) (위치를 알 때)
해시 테이블 (unordered_map)—O(1) 평균O(1) 평균—
균형 트리 (map)—O(log n)O(log n)O(log n)

예를 들어 "키로 값을 자주 조회한다"면 O(1) 평균인 unordered_map이, "항상 정렬된 순서로 순회해야 한다"면 O(log n)이지만 순서를 유지하는 map이 적합하다. "중간에 자주 삽입/삭제한다"면 vector의 O(n)보다 list의 O(1)이 유리하다 — 단, 캐시 효율 때문에 실제로는 작은 데이터에서 vector가 이기는 경우도 많다(8장 참고).

다음 편 예고 — 자료구조 각 자료구조가 왜 그런 복잡도를 갖는지, 내부 구조가 어떻게 연산 비용을 결정하는지는 다음 편 "자료구조"에서 본격적으로 다룬다. 복잡도는 자료구조를 이해하기 위한 언어이고, 자료구조는 복잡도가 실제로 적용되는 무대다.

산업 SW 관점

산업용 이미징 SW에서 복잡도는 추상적인 개념이 아니라 처리 시간 예산으로 직결된다. 이미지 처리의 입력 크기는 보통 픽셀 수 N이다. 2000×2000 이미지면 N = 4,000,000이다.

대부분의 픽셀 단위 필터(블러, 임계화, 산술 연산)는 모든 픽셀을 한 번씩 훑으므로 O(N)이다. 커널 크기 k×k의 컨볼루션은 픽셀마다 k²번 연산하므로 O(N · k²)이다. 여기서 N은 고정이고 k가 변수가 된다.

// 픽셀 단위 임계화 — 모든 픽셀을 한 번씩 -> O(N)
ErrorCode ApplyThreshold(Image& image, int thresholdValue)
{
    if (image.IsEmpty())
    {
        return ErrorCode::InvalidImage;
    }
    const int pixelCount = image.GetWidth() * image.GetHeight();
    for (int i = 0; i < pixelCount; ++i)        // N번 반복
    {
        unsigned char& p = image.At(i);
        p = (p >= thresholdValue) ? 255 : 0;    // 픽셀당 상수 작업
    }
    return ErrorCode::Ok;
}

실시간 검사의 복잡도 예산

라인 속도 60 FPS로 도는 검사 장비는 한 프레임을 16.6 ms 안에 처리해야 한다. 이 마감 시간이 곧 복잡도 예산이다. 만약 어떤 알고리즘이 O(N²)이라면, N = 400만일 때 16조 번의 연산이 필요해 예산을 수천 배 초과한다 — 그 알고리즘은 실시간 파이프라인에 들어갈 수 없다.

처리 단계복잡도2000×2000 기준 연산 수
픽셀 임계화 / 산술O(N)~4 × 10⁶
5×5 컨볼루션O(N · k²)~10⁸
연결 요소 분석 (blob)O(N · α(N)) ~ O(N)~4 × 10⁶
순진한 전역 템플릿 매칭O(N · M)이미지×템플릿 — 예산 초과 위험

그래서 산업 SW에서 복잡도 분석은 "이 알고리즘을 쓸 수 있는가"를 판단하는 1차 관문이다. O(N · M) 템플릿 매칭은 이미지 피라미드(coarse-to-fine)로 탐색 공간을 줄이거나, 주파수 영역 변환으로 복잡도 등급 자체를 낮춰야 실시간 예산에 들어온다.

흔한 오해

오해 1 — Big-O가 낮으면 항상 빠르다

Big-O는 증가 경향이지 실제 속도가 아니다. O(n log n) 알고리즘이 O(n²) 알고리즘보다 항상 빠른 것은 아니다 — n이 작거나, 상수 인자가 크게 차이 나면 얼마든지 역전된다. Big-O는 "n이 무한히 커질 때"의 약속일 뿐, 당신의 실제 n에서의 약속이 아니다.

오해 2 — O(1)은 항상 빠르다

O(1)은 "입력 크기와 무관하게 일정하다"는 뜻이지 "빠르다"는 뜻이 아니다. 상수 시간이 1나노초일 수도, 1초일 수도 있다. 무거운 해시 함수 한 번의 호출도 O(1)이고, 단순한 배열 접근도 O(1)이지만 둘의 실제 비용은 다르다. O(1)인 디스크 읽기가 O(n)인 메모리 순회보다 느릴 수도 있다.

오해 3 — 최악의 경우만 보면 된다

최악의 경우는 중요하지만, 그것만 보면 좋은 알고리즘을 놓친다. 해시 테이블의 최악은 O(n)이지만 평균은 O(1)이고, 현실의 거의 모든 입력에서 평균처럼 동작한다. 퀵 정렬의 최악은 O(n²)이지만 평균 O(n log n)에 상수 인자가 작아 실무에서 가장 빠른 정렬 중 하나다. 최악·평균·최선을 함께 보고, 자신의 입력 분포가 어디에 가까운지를 판단해야 한다.

오해 4 — 복잡도가 낮을수록 무조건 좋은 코드다

복잡도를 낮추려다 코드가 읽기 어려워지고 메모리를 과하게 쓰면, 그것이 항상 이득은 아니다. n이 항상 10 이하인 곳을 O(n²)에서 O(n log n)으로 바꾸는 것은 의미 없는 최적화다. 복잡도 개선은 그 코드가 실제 병목일 때, 실제 n이 클 때 가치가 있다. "측정하기 전에 최적화하지 말라"는 격언은 복잡도에도 그대로 적용된다.

// n이 항상 작다면(예: 설정 항목 4~8개) 이 O(n^2) 코드는 고칠 이유가 없다
// 가독성이 높고, 실측 시간도 무시할 수준이다
for (const auto& a : configItems)
{
    for (const auto& b : configItems)
    {
        checkConflict(a, b);   // n이 작으면 O(n^2)도 충분히 빠르다
    }
}
