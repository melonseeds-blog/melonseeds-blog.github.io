MCP 기초 — 왜 새로운 프로토콜인가

Welcome / Introducing MCP

강의 초반은 동기 설명에 시간을 충분히 쓴다. LLM이 강력해질수록 외부 데이터·도구를 가져다 붙이는 일이 늘어나는데, 통합 코드를 매번 새로 짜다 보면 다음 문제가 반복된다.

  • N×M 폭발 — 모델 N개와 도구 M개가 곱셈으로 통합 코드가 늘어난다.
  • 스키마 불일치 — 같은 "파일 읽기"여도 앱마다 함수 시그니처가 다르다.
  • 권한·라이프사이클 — 도구 등록/해지, 인증, 에러 전파가 표준화되지 않는다.

MCP는 이 셋을 한 번에 푼다. "같은 규격으로 도구를 노출하면 어떤 호스트에서도 동작한다"는 게 핵심 가치다. Anthropic은 강의에서 이를 "USB-C for AI tools" 비유로 설명한다.

"MCP delegates tool management to specialized servers."

아키텍처 — Host / Client / Server

MCP는 세 역할로 구성된다.

역할설명예시
Host사용자가 보는 앱. 모델 호출의 주체.Claude Desktop, IDE, 챗봇 UI
Client호스트 내부에서 서버와 1:1로 대화하는 컴포넌트서버별 stdio 연결 객체
Server도구·자원·프롬프트를 제공하는 외부 프로세스파일 시스템 서버, GitHub 서버, 사내 DB 서버

핵심은 "도구 관리 책임을 서버에 위임"하는 것이다. 호스트는 모델·UI에만 집중하고, 서버는 자기가 잘 아는 도메인 기능을 노출한다.

Overview of MCP Clients

강의는 클라이언트 측면을 먼저 짚는다. 이미 시중에 나와있는 MCP 지원 클라이언트(Claude Desktop, Cursor, Continue 등)가 어떻게 서버 목록을 들고와 도구를 자동 노출하는지 보여준다. 사용자가 따로 함수 시그니처를 외울 필요가 없다.

서버 실습 — Python SDK로 직접 만들기

Project Setup

가상환경을 만들고 mcp 패키지를 설치한다. 강의에서는 문서 관리(document management) 시나리오를 예제로 쓴다 — 메모/문서를 읽고 쓰는 작은 도메인이다.

python -m venv .venv
.venv\Scripts\activate
pip install "mcp[cli]"

Defining Tools with Decorators

Python SDK는 데코레이터 기반이다. 함수에 @mcp.tool()을 붙이면 자동으로 입력 스키마가 생성되고, 도구 목록에 노출된다.

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("docs-server")

@mcp.tool()
def list_documents() -> list[str]:
    """List all documents in the workspace."""
    return [...]

@mcp.tool()
def read_document(name: str) -> str:
    """Read the content of a document by name."""
    return ...

if __name__ == "__main__":
    mcp.run()

강의에서 강조하는 포인트가 두 가지다.

  • 독스트링이 곧 설명서 — 모델이 도구를 선택할 때 참고하는 텍스트다. 영어로 명료하게 작성한다.
  • 타입 힌트가 스키마 — SDK가 Python 타입 힌트를 JSON Schema로 변환한다. int, str, list[str] 같은 단순 타입을 우선 쓴다.

MCP Inspector — 서버 디버깅

Inspector는 MCP 팀이 제공하는 GUI 디버거다. 서버를 띄우고 도구·자원·프롬프트가 잘 노출되는지, 호출 결과가 무엇인지 눈으로 확인할 수 있다.

npx @modelcontextprotocol/inspector python server.py

강의에서 권장하는 흐름은 단순하다. "서버를 짜자마자 Inspector부터 띄운다." 모델에 붙이기 전에 사람이 먼저 확인하는 것이다. 머신비전에서 ROI 시각화 없이 알고리즘 디버깅을 못 하는 것과 같은 이치다.

Inspector 활용 팁 도구 호출 결과가 LLM 친화적으로 보이는지 미리 확인한다. 너무 긴 JSON은 모델이 읽기 힘들고, 너무 짧은 문자열은 컨텍스트가 부족해 추론이 어긋난다.

클라이언트 연결 — 호스트, 클라이언트, 서버

Implementing a Client

이 챕터에서 강의는 클라이언트를 직접 짠다. Claude Desktop을 쓰는 것이 가장 빠른 길이지만, 내부 동작을 이해하려면 한 번 직접 구현해 보는 게 좋다.

  • 서버 프로세스를 stdio로 띄운다 (자식 프로세스 + 표준 입출력).
  • JSON-RPC 메시지로 initialize 핸드셰이크를 한다.
  • tools/list, resources/list, prompts/list로 노출된 항목을 받는다.
  • 모델 응답에 도구 호출 의도가 있으면 tools/call로 전달하고 결과를 다시 모델에 넣는다.

메시지 흐름 한눈에 보기

Host (Claude)            Client                MCP Server
   |  user prompt          |                     |
   |-------------------->  |                     |
   |                       |---- tools/list ---->|
   |                       |<--- tool schema ----|
   |<-- assistant turn ----|                     |
   |  (tool_use intent)    |                     |
   |-------------------->  |---- tools/call ---->|
   |                       |<---- result --------|
   |<--- tool_result ------|                     |

세 가지 프리미티브 — Tools · Resources · Prompts

MCP의 진짜 핵심은 "세 종류의 노출 단위"를 구분한다는 점이다. 함수 호출만 있던 시절보다 한 단계 더 올라간다.

프리미티브의미호출 주체예시
Tools모델이 부르는 액션 (사이드 이펙트 가능)모델 (자동 호출)send_email, run_query
Resources읽기 전용 데이터 (URI로 식별)호스트/사용자 (모델은 참조)file://, db://table/123
Prompts재사용 가능한 워크플로 템플릿사용자 (슬래시 명령처럼)/review-pr, /summarize-doc

Defining / Accessing Resources

Resources는 URI 스킴 + MIME 타입으로 정의한다. 강의는 docs:// 같은 커스텀 스킴을 만들어 문서를 노출한다.

@mcp.resource("docs://{name}")
def get_doc(name: str) -> str:
    """Return the document body as plain text."""
    return load(name)

Tool과의 결정적 차이는 "사이드 이펙트 없음"이다. Resource는 GET처럼 동작해야 한다. 데이터 노출이 목적이지, 무언가를 바꾸려면 Tool로 분리한다.

Defining / Integrating Prompts

Prompts는 사용자가 직접 고르는 워크플로다. 슬래시 명령처럼 클라이언트 UI에 노출되며, 인자를 받아 완성된 대화 시퀀스를 생성한다.

@mcp.prompt()
def review_doc(name: str) -> str:
    """Produce a structured review of the given document."""
    return f"Please review the document '{name}' for..."

Tools가 "모델이 결정하는 것"이라면 Prompts는 "사람이 결정하는 것"이다. 정형 워크플로를 한 줄로 실행하고 싶을 때 적합하다.

어느 프리미티브를 쓸까 부수효과가 있으면 Tool, 데이터 조회만이면 Resource, 사람이 자주 반복하는 흐름이면 Prompt다. 같은 기능을 세 가지 방식으로 동시에 노출하는 것도 가능하지만, 권장하지 않는다 — 모델이 혼란스러워한다.

적용 포인트 — 머신비전 워크플로에 붙이기

이 강의는 일반 문서 도메인을 예제로 쓰지만, 산업용 이미징 SDK 관점에서 어디에 붙일지 그려보면 다음과 같다.

머신비전 통합 시나리오

Tools — run_inspection(image_path), capture_frame(camera_id), save_flow(json) 같은 액션을 노출하면, Claude가 사용자의 자연어를 받아 검사 파이프라인을 직접 실행할 수 있다.
Resources — image://camera/0/last, flow://current처럼 카메라 라이브 프레임과 현재 데이터플로 그래프를 읽기 전용 자원으로 노출한다.
Prompts — /diagnose-defect, /explain-flow 같은 슬래시 명령으로 자주 묻는 검사·분석 흐름을 미리 정의한다.

데이터플로 에디터에 어떻게 녹일까

WPF 블록 에디터에 MCP 서버를 두면, 사용자가 자연어로 "이 단계 다음에 가우시안 블러를 넣어줘"라고 했을 때 Claude가 직접 블록을 추가하는 그림이 가능하다. 핵심은 "에디터 상태를 Resource로 노출하고, 블록 추가/연결/삭제를 Tool로 노출"하는 것이다.

한계와 다음 단계

입문 강의가 다루지 않는 영역도 분명히 있다. 이는 후속 강의("Advanced Topics")의 주제와 정확히 맞물린다.

  • Sampling — 서버가 거꾸로 모델을 호출하는 양방향 흐름은 입문에서 다루지 않는다.
  • Notifications / Progress — 장시간 작업에서 진행률을 보고하는 메커니즘이 빠져 있다.
  • Transports — stdio 외에 HTTP / SSE / Streamable HTTP의 트레이드오프는 심화 강의로 미뤄진다.
  • Roots — 파일 접근 권한 경계를 정의하는 보안 메커니즘은 별도로 다룬다.
주의 — "도구가 많으면 좋다"는 함정 강의에서도 짧게 짚지만, 노출 도구가 많을수록 모델이 잘못된 선택을 할 가능성도 올라간다. 한 서버에 도구를 무더기로 넣기보다 도메인별로 서버를 쪼개는 편이 디버깅에 유리하다.
