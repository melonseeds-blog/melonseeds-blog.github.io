Agent Team 설계 — 역할 분리로 문서 자동화 (Release Assistant 예시)

2026-06-25 약 8분 분량 도구/환경 설정

왜 하나가 아니라 "팀"인가

복합 업무를 에이전트 하나에 통째로 맡기면 세 가지가 걸린다. 컨텍스트 윈도우가 빠르게 차고, 서로 다른 성격의 작업(분석·작성·검토)이 한 흐름에 뒤섞이며, 스스로 쓴 것을 스스로 검토하는 자기 채점의 한계가 남는다.

역할을 나눈 "팀" 설계는 이 셋을 각각 푼다. 병렬 처리로 서로 독립적인 작업을 동시에 돌려 속도를 올리고, 상호 검토로 작성자와 검토자를 분리해 품질을 높이며, 컨텍스트 분리로 각 에이전트가 자기 일에 필요한 것만 들고 있게 한다. 핵심은 사람 조직과 같다 — 한 사람이 다 하는 것보다, 좁은 역할을 잘하는 사람들이 나눠 맡고 서로 확인할 때 결과가 좋아진다.

여기서 각 역할은 별도 컨텍스트를 가진 서브에이전트로 구현한다. 메인 에이전트는 팀을 지휘하는 오케스트레이터가 되고, 각 서브에이전트는 자기 몫만 처리한 뒤 요약 결과만 돌려준다.

Release Assistant 예시

릴리스마다 사람이 손으로 쓰던 문서 묶음을 자동화하는 팀을 생각해 본다. 릴리스 한 번에 보통 릴리스 노트, API 문서 갱신, 마이그레이션 가이드, QA 체크리스트가 함께 필요하다. 이걸 한 에이전트가 순차로 쓰면 느리고, 뒤로 갈수록 앞의 맥락이 흐려진다. 대신 아래 흐름으로 나눈다.

  • 1 코드 분석 Agent — 이번 릴리스의 변경(커밋·diff·이슈)을 읽어, 무엇이 추가·변경·제거됐는지 구조화된 요약을 만든다. 이 요약이 이후 모든 문서의 공통 입력이 된다.
  • 2 분배 — 오케스트레이터가 그 분석 결과를 각 문서 작성 Agent에 나눠 전달한다. 각 작성 Agent는 자기 문서에 필요한 부분만 받는다.
  • 3 문서 작성 Agent들 (병렬) — Release Note / API 문서 / Migration Guide / QA Checklist를 각각 담당하는 네 Agent가 동시에 작성한다. 서로 독립적이라 병렬로 돌아가 시간이 크게 줄어든다.
  • 4 문서 리뷰 Agent — 완성된 문서들을 다시 코드를 기준으로 대조해, 실제 변경과 어긋나거나 빠진 항목이 없는지 정합성을 검토한다. 작성자와 검토자가 분리돼 자기 채점의 한계를 넘는다.

흐름을 개념적으로만 옮기면 다음과 같다. 실제 API·명령은 버전에 따라 다르니 형태만 참고한다.

# 오케스트레이터의 개념적 흐름 (의사코드)
analysis = run_agent("code-analyzer", input=diff_of_release)

# 분석 하나를 여러 작성 Agent에 병렬로 분배
docs = run_parallel([
    ("release-note-writer",   analysis),
    ("api-doc-writer",        analysis),
    ("migration-guide-writer",analysis),
    ("qa-checklist-writer",   analysis),
])

# 코드(analysis)를 기준으로 문서 정합성 검토
report = run_agent("doc-reviewer", input={
    "source_of_truth": analysis,
    "documents": docs,
})
왜 분석을 먼저 한 번만 하나 네 작성 Agent가 각자 코드를 처음부터 다시 읽으면, 같은 일을 네 번 하고 해석이 조금씩 어긋난다. 분석 Agent가 한 번 만든 구조화 요약을 공유 입력으로 두면, 모든 문서가 같은 사실에서 출발해 서로 모순되지 않는다.

좋은 Agent 설계 원칙

팀이 잘 굴러가려면 각 구성원의 정의가 좋아야 한다. 반복해서 효과를 본 원칙은 아래 세 가지다.

원칙뜻왜 중요한가
좁은 책임한 Agent는 한 가지만 잘하게 한다. "문서 다 써"가 아니라 "릴리스 노트만 쓴다".역할이 좁을수록 프롬프트가 명확해지고, 병렬·교체·재사용이 쉬워진다.
명확한 출력 형식결과의 구조를 미리 못박는다(정해진 섹션·필드·Markdown 틀).다음 Agent가 그 출력을 입력으로 받으므로, 형식이 흔들리면 파이프라인이 깨진다.
실패 보고못 하겠으면 지어내지 말고 "무엇이 부족한지"를 보고하게 한다.조용한 환각보다 명시적 실패가 낫다. 오케스트레이터가 재시도·보완을 판단할 수 있다.

이 원칙들은 서로 맞물린다. 책임이 좁아야 출력 형식을 못박기 쉽고, 출력이 정형화돼야 실패도 정형화된 형태로 보고된다. 정리하면 다음과 같다.

  • 한 가지만 — 역할·도구·권한을 그 일에 필요한 최소로 좁힌다.
  • 계약을 정한다 — 입력이 무엇이고 출력이 어떤 형태인지를 에이전트 정의에 명시한다.
  • 모르면 모른다고 — 근거가 부족하면 채워 넣지 말고 부족분을 되돌려준다.
  • 부작용을 격리한다 — 파일 쓰기·외부 호출은 담당 Agent에만 허용해 예측 가능성을 지킨다.

오케스트레이션 — 단일 기준과 교차 검증

여러 문서가 병렬로 나오면 필연적으로 "서로 안 맞는" 위험이 생긴다. 릴리스 노트는 새 파라미터를 언급하는데 API 문서엔 빠지는 식이다. 이를 막는 설계 원칙이 단일 기준(source of truth)이다.

이 파이프라인에서 단일 기준은 문서가 아니라 코드(그리고 코드에서 뽑은 분석 결과)다. 모든 문서는 코드에서 파생되고, 마지막 리뷰 Agent는 문서끼리 비교하는 게 아니라 문서를 코드에 대조한다. 기준이 하나이므로, 세 문서가 서로를 참조하며 오차가 누적되는 상황을 피한다.

교차 검증의 방향 검토를 "문서 A vs 문서 B"로 하면 둘 다 틀렸을 때 통과해 버린다. "각 문서 vs 코드"로 하면 기준이 흔들리지 않는다. 리뷰 Agent에는 항상 기준이 되는 사실(분석 결과)과 검증 대상(문서)을 함께 넘겨, 어긋난 지점을 목록으로 되돌려받는다.

오케스트레이터의 역할도 정리된다. 스스로 문서를 쓰지 않고, (1) 분석을 한 번 돌리고, (2) 결과를 분배해 병렬 작성을 띄우고, (3) 리뷰 결과를 받아 통과·재작성을 판단한다. 지휘에 집중하므로 메인 컨텍스트가 문서 초안으로 가득 차지 않는다.

다른 팀 구성으로 일반화

같은 골격 — 분석 → 병렬 실행 → 기준 대비 검토 — 은 릴리스 문서에만 쓰이지 않는다. 역할 이름만 바꾸면 여러 업무에 그대로 옮겨 간다.

문서 기반 개발팀요구/스펙 분석 Agent구현 · 테스트 작성 · 예제 작성 Agent스펙 문서
알고리즘 개발팀문제·데이터 분석 Agent후보 구현 · 벤치마크 · 시각화 Agent정답 기준·성능 지표

공통점은 뚜렷하다. 먼저 흩어진 입력을 한 번 정제해 공통 입력을 만들고, 서로 독립적인 산출물을 병렬로 뽑고, 마지막에 흔들리지 않는 기준에 대조한다. 도메인이 달라도 이 세 박자는 유지된다.

팀이 항상 정답은 아니다 작은 일까지 여러 Agent로 쪼개면 위임·조율 오버헤드가 이득을 넘어선다. 산출물이 서로 독립적이지 않거나, 단일 기준을 정의하기 어렵거나, 그냥 한 흐름에서 끝나는 일이라면 굳이 팀으로 만들 필요가 없다. 팀 설계는 "병렬로 나눌 만하고, 검토가 품질을 실제로 끌어올릴 때" 값을 한다.

정리와 주의

  • 한 문장 요약 — 복합 업무는 좁은 역할의 서브에이전트로 나눠, 병렬로 처리하고 코드 같은 단일 기준에 대조하면 품질과 속도가 함께 오른다.
  • 세 박자 — 분석으로 공통 입력을 만들고 → 독립 산출물을 병렬로 뽑고 → 흔들리지 않는 기준에 교차 검증한다.
  • 구성원 원칙 — 좁은 책임, 명확한 출력 형식, 실패 보고. 이 셋이 파이프라인의 안정성을 만든다.
  • 과설계 경계 — 병렬로 나눌 만하고 검토가 실제로 값을 할 때만 팀으로 만든다. 작은 일엔 하나가 낫다.
  • 세부는 공식 문서로 — 서브에이전트 정의·호출 방식은 버전에 따라 바뀐다. 구조를 뼈대로 두고 정확한 사양은 문서에서 확인한다.
