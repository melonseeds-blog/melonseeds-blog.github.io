세 가지 전달 방식 비교

이더넷에서 패킷을 보내는 방식은 크게 세 가지다.

방식수신자스위치 동작주요 용도
유니캐스트 특정 1대 MAC 주소 학습 후 해당 포트로만 전달 일반적인 카메라 → PC 영상 전송
브로드캐스트 같은 서브넷 전체 모든 포트로 복사해서 전달 ARP, DHCP, GigE Vision 장치 탐색
멀티캐스트 그룹에 가입한 장치 기본은 모든 포트, IGMP Snooping이 있으면 가입 포트만 한 카메라 영상을 여러 PC가 동시에 받는 경우

멀티캐스트를 쓰는 이유

카메라 한 대의 영상을 여러 PC가 동시에 받아야 할 때 유니캐스트로는 카메라가 PC 수만큼 같은 데이터를 반복 전송해야 한다. 멀티캐스트에서는 카메라가 한 번만 보내고, 스위치(또는 NIC)가 복사를 담당하므로 카메라 쪽 대역폭이 절약된다.

Master와 Monitor GigE Vision에서 카메라를 제어하는 PC를 Master, 영상만 받아 보는 PC를 Monitor라 부름. Master가 촬영 파라미터를 설정하고 Grab를 시작하면, Monitor는 같은 멀티캐스트 그룹에 가입해 영상 패킷을 받음. Monitor는 카메라를 제어하지 않음.

PC의 멀티캐스트 수신 원리

IGMP 그룹 가입

멀티캐스트 주소는 224.0.0.0 ~ 239.255.255.255 범위다. PC가 이 중 특정 그룹의 패킷을 받으려면 OS에 그룹 가입 신호를 보내야 한다. 소켓 프로그래밍에서는 IP_ADD_MEMBERSHIP 옵션으로 가입한다.

/* 소켓에 멀티캐스트 그룹 가입 — C 예시 */ struct ip_mreq mreq; mreq.imr_multiaddr.s_addr = inet_addr("239.1.2.3"); // 그룹 주소 mreq.imr_interface.s_addr = htonl(INADDR_ANY); // 수신 NIC setsockopt(sock, IPPROTO_IP, IP_ADD_MEMBERSHIP, &mreq, sizeof(mreq));

가입하면 OS가 NIC에 해당 멀티캐스트 MAC 주소를 받도록 설정하고, 스위치에는 IGMP Join 메시지를 보낸다.

NIC의 멀티캐스트 MAC 필터

멀티캐스트 MAC 주소(01:00:5E:xx:xx:xx)는 IPv4 멀티캐스트 그룹 주소의 하위 23비트를 그대로 사용한다. 예를 들어 239.1.2.3의 MAC은 01:00:5E:01:02:03이다.

NIC 내부에는 이 MAC 주소들을 담은 해시 테이블이 있다. 그런데 일부 NIC는 32가지 이하의 버킷만 두고 해시 충돌을 허용한다. 가입하지 않은 그룹 주소가 우연히 이미 가입한 그룹과 같은 해시 버킷에 들어가면, 그 그룹의 패킷까지 NIC가 통과시킨다.

"어떤 PC에서는 되고 어떤 PC에서는 안 되는" 현상의 원인 NIC 드라이버마다 해시 알고리즘이 다르기 때문에, 같은 네트워크 구성이어도 특정 PC에서만 가입하지 않은 멀티캐스트 영상이 수신되거나, 반대로 수신이 안 되는 경우가 나타남. NIC 모델과 드라이버 버전을 확인해야 함.

htonl 순서 주의

그룹 주소를 소켓 API에 넘길 때는 네트워크 바이트 순서(빅엔디언)로 변환해야 한다. inet_addr()은 자동으로 변환해 주지만, 주소를 정수로 직접 계산한 뒤 넘길 때 htonl()을 빠뜨리면 엉뚱한 그룹에 가입된다. 가입 자체는 성공으로 보이지만 영상을 전혀 받지 못하며, 오류 메시지도 없어 원인을 찾기 어려운 실수 중 하나다.

스위치의 멀티캐스트 처리 방식

일반(비관리형) 스위치

멀티캐스트 MAC 주소(01:00:5E:...)는 스위치의 MAC 테이블에 학습되지 않는다. 따라서 일반 스위치는 멀티캐스트 패킷을 브로드캐스트처럼 모든 포트로 복사해 보낸다. 가입하지 않은 PC의 NIC에도 패킷이 도달하고, NIC가 버리거나(필터 적중 시) CPU로 올려보낸다(해시 충돌 시).

그림 1 — 일반 스위치는 멀티캐스트를 모든 포트로 전달. 미가입 PC3에도 패킷이 도달함.

관리형 스위치 + IGMP Snooping

IGMP Snooping이 켜진 관리형 스위치는 PC가 보내는 IGMP Join/Leave 메시지를 "들여다보며(snooping)" 어느 포트가 어느 그룹에 가입했는지 기록한다. 이후 해당 그룹의 멀티캐스트 패킷이 들어오면, 가입한 포트로만 전달한다.

그림 2 — IGMP Snooping이 있는 관리형 스위치는 가입한 PC1·PC2 포트로만 전달하고, 미가입 PC3 포트는 차단함.

IGMP Querier

IGMP Snooping이 관리하는 그룹 가입 정보는 영원히 유지되지 않는다. PC가 Leave 메시지를 보내거나, 일정 시간이 지나도 확인이 없으면 스위치가 해당 포트를 그룹에서 제거한다. 스위치가 주기적으로 "아직 이 그룹이 필요한가?"를 확인하려면 IGMP 질의(Query)를 보낼 주체가 있어야 한다.

일반적인 네트워크에서는 라우터가 Querier 역할을 한다. 하지만 카메라와 PC만 연결된 독립 망(라우터 없음)에서는 스위치의 IGMP Querier 기능을 켜야 한다. 이걸 빠뜨리면 초기에는 정상이었다가 시간이 지나면서 그룹이 제거되어 영상이 끊기는 증상이 나타난다.

PTP 동기화 패킷과 IGMP Snooping 일부 카메라는 정밀한 시간 동기화를 위해 PTP(IEEE 1588) 프로토콜을 사용한다. PTP 이벤트 메시지는 멀티캐스트(224.0.1.129)로 전송되는데, 카메라나 PC가 이 그룹에 IGMP Join을 보내지 않는 경우가 있다. IGMP Snooping이 켜진 스위치에서는 Join이 없으면 포트에 전달하지 않으므로 PTP 동기화가 되지 않는다. Basler의 공개 자료(참고 자료 참조)에서도 이 문제를 다루고 있다. 해결 방법은 해당 멀티캐스트 주소를 스위치의 정적 그룹에 등록하거나, PTP 포트에 한해 Snooping을 우회(flood)하도록 설정하는 것이다.

멀티캐스트와 유니캐스트 혼용 구성의 문제

한 스위치에 멀티캐스트 카메라(여러 PC가 받는)와 유니캐스트 카메라(PC 1대가 받는)를 함께 연결했을 때 어떤 문제가 생기는지 단계적으로 살펴본다.

일반 스위치에서의 대역폭 충돌

일반 스위치는 멀티캐스트를 모든 포트로 복사한다. 즉, 유니캐스트 카메라만 받는 PC의 포트에도 멀티캐스트 영상이 그대로 전달된다. 그 포트가 받는 실제 트래픽은 두 가지의 합이다.

그림 3 — 일반 스위치에서 멀티캐스트(800 Mbps)와 유니캐스트(200 Mbps)를 함께 받는 포트. 1G 한도(실제 유효 대역폭 약 940 Mbps)를 초과해 패킷 손실이 발생함.

계산 예

카메라 영상 대역폭은 다음 식으로 구한다.

대역폭(Mbps) = 가로 × 세로 × 비트수(bit) × fps ÷ 1,000,000 예) 1920 × 1200 × 8 bit × 60 fps = 1,105,920,000 bps ≈ 1106 Mbps → 1G 포트에서는 이미 한도 초과 → fps를 50으로 낮추면 ≈ 922 Mbps (패킷 오버헤드 포함 시 여전히 위험)

1500바이트 패킷 기준으로 1G 이더넷에서 실제 영상에 쓸 수 있는 대역폭은 패킷 간 최소 간격(IFG) 등의 오버헤드를 제외하면 약 940 Mbps다. 멀티캐스트 영상이 800 Mbps이고 유니캐스트 영상이 200 Mbps라면, 합산 1000 Mbps는 이 한도를 넘는다.

순간 버스트 문제

평균 대역폭이 1G 이하여도 카메라가 패킷 간격 설정 없이 한 프레임을 한꺼번에 보내면(burst), 짧은 시간 동안 2.5G 이상의 속도로 트래픽이 몰릴 수 있다. 스위치 내부 버퍼가 넘치면 패킷이 버려지고 영상이 끊긴다.

증상 카메라를 직접 PC에 연결하면 정상이다. 그런데 같은 스위치에 멀티캐스트 카메라와 유니캐스트 카메라를 함께 연결하고 멀티캐스트 Grab를 시작하는 순간, 유니캐스트 카메라의 영상이 끊기거나 패킷 손실 오류가 발생함.

방법 비용/난이도 설명 및 주의사항

PC에 NIC가 2개 이상 있어야 함.

비관리형 스위치에서는 불가.

경로 위 모든 장비(NIC, 스위치, 카메라)가 같은 MTU로 설정해야 함. 크기가 맞지 않으면 단편화(fragmentation)가 발생해 오히려 나빠짐.

패킷 간격 조정 낮음 (카메라 설정) 카메라가 한 프레임을 보낼 때 패킷 사이에 간격을 두도록 설정해 스위치 버퍼 포화를 완화함.
순간 버스트를 줄이는 효과가 있으나, 근본적인 대역폭 문제는 해결되지 않음.
해상도·fps 감소 낮음 (소프트웨어) 영상 대역폭 자체를 줄여 1G 한도 내로 맞춤. ROI(관심 영역) 설정이나 바이닝(binning)도 방법 중 하나.

Windows에서 확인하는 방법

그룹 가입 여부 확인

# 이 NIC가 어느 멀티캐스트 그룹에 가입했는지 목록 표시 PS> netsh interface ipv4 show joins 인터페이스 이름: Ethernet 주소 그룹 --------- ---------------------- ... 239.1.2.3 <-- 카메라 멀티캐스트 그룹 ... 224.0.0.1 <-- All Hosts (항상 가입됨)

멀티캐스트 수신 패킷 수 확인

# 1초 간격으로 수신 멀티캐스트 패킷 카운터 변화 확인 PS> Get-NetAdapterStatistics -Name "Ethernet" | Select ReceivedMulticastPackets ReceivedMulticastPackets ------------------------ 42183 # Grab 중에 숫자가 계속 늘어나면 멀티캐스트 수신 중

점보 프레임 설정 확인

# NIC 드라이버 고급 속성에서 Jumbo Packet 값 확인 PS> Get-NetAdapterAdvancedProperty -Name "Ethernet" -DisplayName "Jumbo Packet" DisplayName DisplayValue RegistryKeyword RegistryValue ----------- ------------ --------------- ------------- Jumbo Packet 9014 Bytes *JumboPacket 9014

스위치 종류 구분 방법

  • 웹 설정 화면 유무 — 브라우저에서 스위치 IP로 접속했을 때 관리 화면이 나타나면 관리형
  • 제품 사양표 — "Managed" 또는 "Smart Managed" 표기와 "IGMP Snooping" 지원 여부 확인
  • 콘솔 포트 — CLI 접속용 RJ-45 또는 USB 포트가 있으면 관리형인 경우가 많음
  • 가격대 — 비관리형은 같은 포트 수 기준으로 관리형보다 크게 저렴한 경향이 있음

설치 전 체크리스트

  • 멀티캐스트 그룹 주소(224.x.x.x ~ 239.x.x.x)를 카메라·SDK에 어떻게 설정하는지 확인했는가
  • PC 측 소프트웨어가 IP_ADD_MEMBERSHIP으로 해당 그룹에 가입하는지 확인했는가
  • 영상 대역폭(가로 × 세로 × 비트수 × fps)이 스위치 포트 속도의 80% 이하인가
  • 유니캐스트와 멀티캐스트를 같은 스위치에 혼용하는 경우, IGMP Snooping 지원 여부를 확인했는가
  • 라우터가 없는 독립 망이라면 스위치의 IGMP Querier를 켰는가
  • 점보 프레임을 사용한다면 경로의 모든 장비(카메라·스위치·NIC)를 같은 MTU로 설정했는가
  • 카메라가 PTP 동기화를 사용하고 IGMP Snooping이 켜져 있다면, PTP 멀티캐스트 주소(224.0.1.129)를 정적 그룹으로 등록했는가
  • Windows에서 netsh interface ipv4 show joins로 그룹 가입을 확인했는가
