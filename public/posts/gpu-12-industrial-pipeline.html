전체 검사 파이프라인 — GPU의 자리

산업 검사 시스템은 카메라가 영상을 잡는 순간부터 OK/NG 판정 신호가 나갈 때까지 정해진 택트 타임 안에 모든 작업을 끝내야 한다. GPU는 이 흐름 중 일부 단계를 가속하기 위해 들어간다. 그러나 호스트와 디바이스 사이 데이터 복사 비용, 동기화 비용, 메모리 할당 비용을 통합 단계에서 통제하지 못하면 단일 단계 가속의 이득이 모두 사라진다.

GPU에 모든 단계를 올릴 필요는 없다 Contour 추출, blob 계측, 로직 판정 등은 CPU가 더 빠르거나 비슷한 경우가 많다. 데이터를 GPU에 올렸다 내리는 비용을 항상 함께 계산해야 한다.

메모리 흐름 최적화 — 카메라 버퍼와 핀드 메모리

카메라 SDK는 일반적으로 내부 링버퍼에 프레임을 채우고 콜백으로 포인터를 넘긴다. 이 포인터는 보통 페이지블 메모리다. 페이지블 메모리에서 GPU로 복사하면 드라이버가 내부 staging 버퍼를 거치게 되어 처리량이 떨어진다. 따라서 카메라가 직접 핀드 메모리 버퍼에 영상을 채우게 하는 것이 이상적이다.

핀드 메모리 풀 설계

매 프레임 cudaMallocHost를 호출하면 수 밀리초가 소모된다. 시작 시 N개를 미리 잡아 풀로 돌리는 것이 정석이다.

// Pinned host buffer pool for camera frames.
class PinnedBufferPool
{
public:
    ErrorCode Initialize(size_t bufferSize, size_t bufferCount)
    {
        m_bufferSize = bufferSize;
        m_buffers.reserve(bufferCount);
        for (size_t i = 0; i < bufferCount; ++i)
        {
            void* ptr = nullptr;
            cudaError_t err = cudaMallocHost(&ptr, bufferSize);
            if (err != cudaSuccess)
            {
                return ErrorCode::OutOfHostMemory;
            }
            m_buffers.push_back(ptr);
            m_free.push_back(ptr);
        }
        return ErrorCode::Ok;
    }

    // Acquire a free buffer. Returns nullptr if the pool is empty.
    void* Acquire()
    {
        std::lock_guard<std::mutex> lk(m_mtx);
        if (m_free.empty())
        {
            return nullptr;
        }
        void* p = m_free.back();
        m_free.pop_back();
        return p;
    }

    // Release a buffer back to the pool.
    void Release(void* ptr)
    {
        std::lock_guard<std::mutex> lk(m_mtx);
        m_free.push_back(ptr);
    }

    ~PinnedBufferPool()
    {
        for (void* p : m_buffers)
        {
            cudaFreeHost(p);
        }
    }

private:
    size_t m_bufferSize = 0;
    std::vector<void*> m_buffers;
    std::vector<void*> m_free;
    std::mutex m_mtx;
};
zero-copy가 가능한 경우 Jetson 같은 통합 메모리 시스템에서는 핀드 메모리를 GPU가 직접 매핑해 복사 없이 접근할 수 있다(cudaHostAllocMapped). 디스크리트 GPU에서는 PCIe 대역폭이 병목이라 zero-copy가 항상 빠른 것은 아니며, 접근 패턴이 코어레스드일 때만 유리하다.

스트림 파이프라이닝 — N·N+1·N+2의 중첩

5편에서 CUDA 스트림이 비동기 작업 큐임을 다뤘다. 산업 파이프라인의 핵심은 업로드·계산·다운로드를 서로 다른 프레임에 대해 동시에 진행하는 것이다. 디스크리트 GPU에는 보통 복사 엔진이 두 개(H2D, D2H) 있고 컴퓨트 엔진이 별도로 동작하므로, 잘 설계하면 세 단계를 모두 겹쳐 처리량을 약 3배까지 끌어올릴 수 있다.

// Triple-buffered pipeline with N rolling streams.
class GpuPipeline
{
public:
    static constexpr int kStages = 3;

    ErrorCode Initialize(size_t imageBytes)
    {
        for (int i = 0; i < kStages; ++i)
        {
            cudaStreamCreate(&m_streams[i]);
            cudaMallocHost(&m_hostBuf[i], imageBytes);
            cudaMalloc(&m_devIn[i],   imageBytes);
            cudaMalloc(&m_devOut[i],  imageBytes);
            cudaEventCreateWithFlags(&m_done[i], cudaEventDisableTiming);
        }
        return ErrorCode::Ok;
    }

    // Submit one frame. Returns immediately; the caller polls m_done[slot].
    ErrorCode Submit(const uint8_t* src, size_t bytes, int frameIndex)
    {
        const int slot = frameIndex % kStages;

        // Wait for the previous use of this slot to finish.
        cudaEventSynchronize(m_done[slot]);

        // Copy into the slot's pinned host buffer.
        std::memcpy(m_hostBuf[slot], src, bytes);

        cudaMemcpyAsync(m_devIn[slot], m_hostBuf[slot], bytes,
                        cudaMemcpyHostToDevice, m_streams[slot]);

        LaunchPreprocessKernel(m_devIn[slot], m_devOut[slot], m_streams[slot]);
        LaunchInference(m_devOut[slot], m_streams[slot]);

        cudaMemcpyAsync(m_hostBuf[slot], m_devOut[slot], bytes,
                        cudaMemcpyDeviceToHost, m_streams[slot]);

        cudaEventRecord(m_done[slot], m_streams[slot]);
        return ErrorCode::Ok;
    }

private:
    cudaStream_t m_streams[kStages]{};
    cudaEvent_t  m_done[kStages]{};
    void*        m_hostBuf[kStages]{};
    void*        m_devIn[kStages]{};
    void*        m_devOut[kStages]{};
};
동기화 누락은 잘못된 결과를 만든다 같은 슬롯을 두 프레임이 동시에 쓰면 이전 프레임의 다운로드가 끝나기 전 새 데이터가 덮어쓰일 수 있다. 슬롯 재사용 직전에 반드시 cudaEventSynchronize로 이전 사이클의 완료를 확인해야 한다.

여러 GPU 작업 동시 실행

같은 스트림 안의 커널은 발행 순서대로 직렬 실행된다. 서로 독립적인 전처리와 후처리를 동시에 진행하려면 별도 스트림으로 분리하고 필요한 지점에서 이벤트로 묶어야 한다.

// Two streams overlap: preprocess on streamA, postprocess of previous frame on streamB.
cudaStream_t streamA, streamB;
cudaStreamCreate(&streamA);
cudaStreamCreate(&streamB);

cudaEvent_t preDone;
cudaEventCreateWithFlags(&preDone, cudaEventDisableTiming);

for (int n = 0; n < frameCount; ++n)
{
    // streamA: upload + preprocess frame n.
    cudaMemcpyAsync(d_in, h_in, bytes, cudaMemcpyHostToDevice, streamA);
    LaunchPreprocess(d_in, d_pre, streamA);
    cudaEventRecord(preDone, streamA);

    // streamB: wait for preDone, then run inference + postprocess.
    // streamA can already start the next frame upload while B runs.
    cudaStreamWaitEvent(streamB, preDone, 0);
    LaunchInference(d_pre, d_out, streamB);
    LaunchPostprocess(d_out, d_final, streamB);
    cudaMemcpyAsync(h_out, d_final, bytes, cudaMemcpyDeviceToHost, streamB);
}

커널 자체가 작아 점유율이 낮다면 같은 스트림에 작은 커널을 한 번에 발행해 GPU의 컴퓨트 유닛을 채우는 것보다, 여러 스트림으로 분산해 하드웨어 큐를 동시에 사용하는 것이 더 빠른 경우가 있다. 이 부분은 8편의 Nsight Systems 타임라인으로 확인하는 것이 가장 정확하다.

메모리 재사용 — GpuMat·텐서 버퍼 풀

매 프레임 cudaMalloc·cudaFree는 절대 호출하지 않는다. 두 호출 모두 디바이스 전역 동기화를 유발하기 때문에 파이프라인의 모든 스트림이 잠시 멈춘다. 시작 시 풀을 잡고 슬롯 단위로 빌려 쓴다.

방식프레임당 비용지터권장
매 프레임 cudaMalloc/Free0.5~수 ms큼 (드라이버 GC)금지
풀 + 슬롯 재사용~0 µs매우 작음표준
cudaMallocAsync (스트림 풀)µs 단위드라이버가 관리CUDA 11.2+
// GpuMat pool keyed by shape.
class GpuMatPool
{
public:
    cv::cuda::GpuMat Acquire(int rows, int cols, int type)
    {
        const Key key{rows, cols, type};
        std::lock_guard<std::mutex> lk(m_mtx);
        auto& bucket = m_pool[key];
        if (!bucket.empty())
        {
            cv::cuda::GpuMat m = std::move(bucket.back());
            bucket.pop_back();
            return m;
        }
        return cv::cuda::GpuMat(rows, cols, type);  // first time only
    }

    void Release(cv::cuda::GpuMat& mat)
    {
        if (mat.empty()) return;
        const Key key{mat.rows, mat.cols, mat.type()};
        std::lock_guard<std::mutex> lk(m_mtx);
        m_pool[key].push_back(std::move(mat));
    }

private:
    struct Key
    {
        int rows, cols, type;
        bool operator==(const Key& o) const { return rows == o.rows && cols == o.cols && type == o.type; }
    };
    struct KeyHash
    {
        size_t operator()(const Key& k) const noexcept
        {
            return std::hash<long long>()(((long long)k.rows << 32) ^ ((long long)k.cols << 8) ^ k.type);
        }
    };
    std::unordered_map<Key, std::vector<cv::cuda::GpuMat>, KeyHash> m_pool;
    std::mutex m_mtx;
};
매 프레임 alloc/free는 가장 흔한 성능 함정이다 cv::cuda 함수는 출력 인자를 비워두면 내부적으로 할당한다. 출력 GpuMat을 미리 풀에서 받아 인자로 넘기는 패턴을 강제하지 않으면 라이브러리가 조용히 매 프레임 alloc/free를 한다.

실시간 보장 — 택트 타임과 워스트케이스

산업 검사에서는 평균 처리 시간이 빠른 것보다 워스트케이스가 택트 타임 안에 들어오는지가 더 중요하다. GPU는 점유율, 드라이버 컴파일, 메모리 가비지 컬렉션 등으로 종종 튀는 프레임을 만든다.

// Per-frame latency tracker.
class LatencyTracker
{
public:
    void Record(double ms)
    {
        m_samples.push_back(ms);
        if (m_samples.size() > m_window)
        {
            m_samples.pop_front();
        }
    }

    double P99() const
    {
        if (m_samples.empty()) return 0.0;
        std::vector<double> sorted(m_samples.begin(), m_samples.end());
        std::sort(sorted.begin(), sorted.end());
        const size_t idx = static_cast<size_t>(sorted.size() * 0.99);
        return sorted[std::min(idx, sorted.size() - 1)];
    }

    double Max() const
    {
        return m_samples.empty() ? 0.0 : *std::max_element(m_samples.begin(), m_samples.end());
    }

private:
    std::deque<double> m_samples;
    size_t m_window = 1000;
};

측정 시에는 첫 수십 프레임을 워밍업 구간으로 분리해 통계에서 제외한다. TensorRT 엔진 로딩, cuDNN 알고리즘 선택, 메모리 풀의 lazy fill이 모두 첫 프레임에서 발생한다.

NVIDIA driver의 Persistence Mode를 켜자 Linux에서는 nvidia-smi -pm 1로 켤 수 있다. 드라이버가 idle 시 컨텍스트를 내리는 것을 막아 첫 호출 지연을 줄인다. Windows에서는 TCC 모드 또는 데이터센터 GPU에서 유사한 효과가 있다.

CUDA 에러 처리와 디바이스 복구

CUDA 에러는 일반 함수의 실패와 다르다. 한 번 비동기 커널이 메모리 위반을 일으키면 해당 컨텍스트의 모든 후속 호출이 같은 에러를 반환한다. 디바이스가 sticky 상태에 빠진 것이다.

// CUDA error utility: separates sticky errors from recoverable ones.
ErrorCode CheckCudaError(const char* where)
{
    cudaError_t err = cudaGetLastError();
    if (err == cudaSuccess) return ErrorCode::Ok;

    spdlog::error("CUDA error at {}: {} ({})", where, cudaGetErrorString(err), static_cast<int>(err));

    // Sticky errors require device reset.
    if (err == cudaErrorIllegalAddress ||
        err == cudaErrorLaunchFailure  ||
        err == cudaErrorECCUncorrectable)
    {
        return ErrorCode::CudaDeviceCorrupted;
    }
    return ErrorCode::CudaError;
}

// Restart strategy when the device is corrupted.
ErrorCode ResetCudaDevice()
{
    cudaError_t err = cudaDeviceReset();
    if (err != cudaSuccess)
    {
        spdlog::critical("cudaDeviceReset failed: {}", cudaGetErrorString(err));
        return ErrorCode::CudaFatal;
    }
    spdlog::warn("CUDA device reset; reloading engines and pools.");
    return ErrorCode::Ok;
}

실전에서는 디바이스 reset 후 모든 디바이스 자원을 다시 만들어야 한다. 스트림, 이벤트, 메모리 풀, TensorRT 엔진, cuDNN 핸들이 모두 무효화된다. 따라서 자원 생성을 한 곳에 모아두고 reset과 재로딩을 한 흐름으로 묶는 설계가 필요하다.

ImagingLib 관점 통합 예

ImagingLib의 데이터플로우 에디터에서 GPU 블록을 자연스럽게 연결하려면, Image 컨테이너가 CPU/GPU 메모리 중 어디에 살고 있는지 추상화해야 한다. EnsureCpu()·EnsureGpu() 패턴이 핵심이다.

// Image container that hides CPU/GPU memory location.
class Image
{
public:
    // Make sure CPU side has valid data. Downloads from GPU if needed.
    ErrorCode EnsureCpu()
    {
        if (m_cpuValid) return ErrorCode::Ok;
        if (!m_gpuValid) return ErrorCode::EmptyImage;
        m_gpuMat.download(m_cpuMat);
        m_cpuValid = true;
        return ErrorCode::Ok;
    }

    // Make sure GPU side has valid data.
    ErrorCode EnsureGpu()
    {
        if (m_gpuValid) return ErrorCode::Ok;
        if (!m_cpuValid) return ErrorCode::EmptyImage;
        m_gpuMat.upload(m_cpuMat);
        m_gpuValid = true;
        return ErrorCode::Ok;
    }

    // After a CPU write the GPU copy is stale.
    void MarkCpuWritten() { m_cpuValid = true; m_gpuValid = false; }
    void MarkGpuWritten() { m_gpuValid = true; m_cpuValid = false; }

    const cv::Mat&            GetCpu() const { return m_cpuMat; }
    const cv::cuda::GpuMat&   GetGpu() const { return m_gpuMat; }

private:
    cv::Mat            m_cpuMat;
    cv::cuda::GpuMat   m_gpuMat;
    bool m_cpuValid = false;
    bool m_gpuValid = false;
};
// Block interface — every processing block speaks the same language.
class IProcessBlock
{
public:
    virtual ~IProcessBlock() = default;
    virtual ErrorCode Process(Image& input, Image& output) = 0;
    virtual bool PrefersGpu() const = 0;
};

// GPU preprocess block — declares it wants the GPU side.
class GpuPreprocessBlock : public IProcessBlock
{
public:
    ErrorCode Process(Image& input, Image& output) override
    {
        ErrorCode ec = input.EnsureGpu();
        if (ec != ErrorCode::Ok) return ec;

        cv::cuda::GpuMat& src = const_cast<cv::cuda::GpuMat&>(input.GetGpu());
        cv::cuda::GpuMat dst = m_pool.Acquire(src.rows, src.cols, src.type());

        cv::cuda::GaussianBlur(src, dst, cv::Size(5, 5), 1.2);

        output = Image::FromGpu(std::move(dst));
        output.MarkGpuWritten();
        return ErrorCode::Ok;
    }

    bool PrefersGpu() const override { return true; }

private:
    GpuMatPool m_pool;
};

실행 엔진은 연결된 블록 사이를 보면서 두 블록이 모두 GPU를 선호하면 호스트 복사를 생략하고, 한쪽이 CPU만 지원하면 그 직전 노드의 출력에서 EnsureCpu()를 호출한다. 데이터플로우 그래프 컴파일 단계에서 한 번 결정해두면 런타임 분기 비용도 사라진다.

다중 카메라·다중 GPU 확장

카메라 한 대에 한 스트림을 할당하는 것이 기본 구조다. 카메라가 늘면 스트림이 늘고, GPU가 여러 장이면 cudaSetDevice로 컨텍스트를 바꿔가며 각 카메라를 특정 디바이스에 고정한다.

// Per-camera worker bound to a specific GPU.
class CameraWorker
{
public:
    ErrorCode Initialize(int cameraIndex, int deviceIndex)
    {
        m_deviceIndex = deviceIndex;
        cudaSetDevice(m_deviceIndex);
        cudaStreamCreate(&m_stream);
        return m_pipeline.Initialize(kImageBytes);
    }

    void Run()
    {
        // Each worker thread must set its device once.
        cudaSetDevice(m_deviceIndex);
        while (m_running)
        {
            const Frame f = m_camera.WaitNextFrame();
            m_pipeline.Submit(f.data, f.bytes, f.index);
        }
    }

private:
    int m_deviceIndex = 0;
    cudaStream_t m_stream{};
    GpuPipeline m_pipeline;
    CameraHandle m_camera;
    std::atomic<bool> m_running{true};
};
스레드별로 cudaSetDevice를 한 번 호출하라 CUDA의 현재 디바이스는 스레드 로컬 상태다. 멀티스레드에서 작업을 분산할 때 새 스레드를 만들 때마다 시작 부분에서 명시적으로 디바이스를 지정해야 한다. 안 하면 기본값(0번)으로 흘러가 의도와 다른 GPU에서 실행된다.

테스트와 디버깅

GPU 코드는 일반 단위 테스트와 두 가지가 다르다. 첫째, 결정성이 약하다. 일부 알고리즘(예: atomic 기반 누적)은 같은 입력에도 부동소수 합 순서가 달라져 미세하게 다른 결과를 낼 수 있다. 둘째, CI 환경에 GPU가 없을 수 있다.

// GoogleTest helper: skip if no CUDA device is present.
#define REQUIRE_CUDA()                                              \
    do {                                                            \
        int count = 0;                                              \
        if (cudaGetDeviceCount(&count) != cudaSuccess || count == 0) {  \
            GTEST_SKIP() << "No CUDA device available";             \
        }                                                           \
    } while (0)

TEST(GpuBlur, MatchesCpuReference)
{
    REQUIRE_CUDA();

    cv::Mat src = cv::imread("test/lena.png", cv::IMREAD_GRAYSCALE);
    cv::Mat cpuRef;
    cv::GaussianBlur(src, cpuRef, cv::Size(5, 5), 1.2);

    cv::cuda::GpuMat gsrc(src), gdst;
    cv::cuda::GaussianBlur(gsrc, gdst, cv::Size(5, 5), 1.2);

    cv::Mat gpuOut;
    gdst.download(gpuOut);

    cv::Mat diff;
    cv::absdiff(cpuRef, gpuOut, diff);
    double maxDiff = 0;
    cv::minMaxLoc(diff, nullptr, &maxDiff);
    EXPECT_LE(maxDiff, 2.0);  // small numerical tolerance
}

디버깅 도구로는 compute-sanitizer(메모리 위반·레이스 검출), cuda-gdb(커널 라인 단위 디버깅), Nsight Compute(커널 프로파일링), Nsight Systems(스트림 타임라인)가 있다. 의심 가는 동작이 비동기 동기화 누락일 때는 CUDA_LAUNCH_BLOCKING=1 환경 변수로 모든 호출을 동기화시켜 재현하면 원인이 드러나는 경우가 많다.

시리즈 마무리

1편에서 GPU와 CPU의 구조적 차이를 살펴보는 것으로 시작해, 메모리 계층과 첫 커널을 거쳐 스트림·shared memory·warp까지 내려갔다. 8편에서 측정 도구를 익히고, 9·10편에서 OpenCV의 cv::cuda와 직접 작성한 이미지 커널을 비교했으며, 11편에서 TensorRT로 추론을 가속했다. 이번 12편은 그 모든 조각을 하나의 산업 검사 파이프라인으로 묶었다.

GPU는 마법이 아니다. 잘못 쓰면 CPU보다 느리고, 잘 쓰면 한 자릿수 이상 빠르다. 그 사이의 거리는 결국 메모리 흐름·동기화·할당을 얼마나 통제하느냐에 달려 있다. ImagingLib의 로드맵에서 GPU 파이프라인은 2년 차 이후 본격적으로 들어올 영역이지만, 1년 차 CPU 구현부터 EnsureCpu/EnsureGpu를 비롯한 추상화의 자리를 비워두면 옮겨붙이는 비용이 훨씬 작아진다. 이 시리즈는 C++ 시리즈가 다룬 인터페이스·메모리 모델, OpenCV 시리즈가 다룬 알고리즘, AI 시리즈가 다룬 모델 배포, 스마트 공장 시리즈가 다룬 검사 시스템과 한 점에서 만난다. 같은 문제를 다른 각도에서 바라본 결과이며, 실제 검사 장비 한 대가 동작하려면 이 네 흐름이 모두 필요하다.
