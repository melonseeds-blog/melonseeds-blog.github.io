AI 시대의 Git 레포 구성 가이드 — monorepo·polyrepo와 에이전트 친화 구조

레포 구성에 "정답"은 없다

레포 구성에서 가장 흔한 실수는 "대기업이 이렇게 하니까"를 따라 하는 것이다. 구글이 거대한 monorepo를 쓴다고 해서 2인 팀이 그래야 하는 건 아니다. 구성은 회사 규모·조직·도구가 만든 제약의 결과이지, 그 자체가 목표가 아니다.

그래서 "무엇이 정답인가"보다 "우리 상황에서 무엇이 마찰을 줄이나"를 본다. 판단의 축은 보통 세 가지다 — 팀 규모, 배포 결합도(함께 배포되나), 코드 공유 정도. 이 셋을 기준으로 아래 결정을 내려 간다.

monorepo vs polyrepo

첫 갈림길은 "레포를 하나로 묶을까, 여러 개로 나눌까"다.

  • Monorepo — 여러 프로젝트·서비스를 하나의 레포에 둔다. 코드 공유와 일관성, 한 번에 가로지르는(atomic) 변경에 강하다.
  • Polyrepo(멀티레포) — 프로젝트마다 레포를 따로 둔다. 팀 자율성, 독립 배포, 접근 제어에 강하다.
기준MonorepoPolyrepo
코드 공유쉬움(공통 타입·유틸 재사용)패키지/계약으로 분리
배포함께 자주 배포할 때 유리완전 독립 배포에 유리
일관성표준·정책 한 곳에서 강제레포별로 제각각 될 위험
규모 감각대략 50명 이하·강한 공유100명 이상·자율 팀
대가빌드 인프라(선택적 빌드) 투자 필요서비스 계약·소유 경계 정의 필요

현실의 다수 팀(대략 20~80명)은 하이브리드로 간다. 밀접한 서비스는 도메인별 monorepo로 묶고, 정말 독립적인 것만 별도 레포로 뺀다. 개인·소규모 프로젝트라면 고민할 것 없이 monorepo 하나로 시작해도 충분하다 — 나누는 건 나중에 필요할 때 해도 늦지 않다.

AI 협업이 더하는 변수 AI 코딩 에이전트를 쓴다면 monorepo가 한 가지 이점을 더 가진다 — 에이전트가 한 곳에서 전체 맥락을 읽을 수 있다는 점이다. 레포가 잘게 흩어져 있으면 에이전트가 봐야 할 컨텍스트도 흩어진다. 이게 최근 "AI 시대엔 monorepo가 유리하다"는 말이 나오는 배경이다(절대 규칙은 아니다).

업계·공식 권장 규약

레포를 몇 개로 나눌지와 별개로, "안에서 어떻게 일하나"에는 비교적 합의된 기본기가 있다.

브랜칭 전략 — 단순한 쪽이 이긴다

  • GitHub Flow — main + 짧은 기능 브랜치 + PR. 대부분의 팀에 충분하고 가장 단순하다. (GitHub 권장)
  • Trunk-Based Development — 아주 짧게 사는 브랜치를 자주 main에 합친다. CI/CD·배포 속도를 중시하는 팀의 표준으로, DORA 연구가 권하는 방향이다.
  • Git Flow — develop/release/hotfix까지 두는 복잡한 모델. 정기 릴리스·버전 관리가 엄격한 제품이 아니면 요즘은 과한 경우가 많다.
고민되면 대부분은 GitHub Flow로 시작하면 된다. "브랜치는 짧게 살리고, 자주 합친다"는 원칙만 지켜도 절반은 성공이다. 오래 사는 브랜치가 가장 큰 통합 비용을 만든다.

커밋 — Conventional Commits

커밋 메시지는 feat:, fix:, docs:, refactor: 같은 접두사를 붙이는 Conventional Commits 규약이 사실상 표준이다. 변경 로그 자동 생성·버전 자동화와 잘 맞는다. 명령형(imperative)으로, 제목은 짧게 쓴다.

레포 기본 골격

언어·프레임워크마다 다르지만, 루트에 있어야 할 "위생" 파일은 공통이다.

# 어떤 레포든 루트에 두면 좋은 것 README.md # 무엇·왜·어떻게 시작하는지(사람용 첫 관문) LICENSE # 라이선스(공개 레포면 필수) .gitignore # 추적 제외(빌드 산출물·비밀·로컬 설정) CONTRIBUTING.md # 기여·개발 절차(팀 레포) src/ tests/ docs/ # 코드·테스트·문서 분리
비밀은 절대 커밋하지 않는다 API 키·토큰·`.env`는 처음부터 `.gitignore`에 넣는다. 한 번 커밋되면 히스토리에 남아 지우기 까다롭다. 예시는 `.env.example`로 형식만 공유한다.

AI 협업 시대의 구조

여기서부터가 "지금 세대"의 핵심이다. 코드를 사람만 읽던 시절의 구조에, 에이전트가 읽을 한 겹이 더해졌다.

AGENTS.md — 기계를 위한 README

2026년 들어 AGENTS.md가 에이전트 지시 파일의 사실상 공통 규격으로 자리 잡았다. 레포 루트에 두는 마크다운 한 장으로, 빌드·테스트 명령, 코딩 컨벤션, 아키텍처 경계, 하지 말아야 할 것(가드레일)을 적는다. 주요 코딩 에이전트(Claude Code·OpenAI Codex·Cursor 등)들이 이를 읽도록 수렴하는 중이다.

# AGENTS.md 예시 골격 ## Project overview # 한두 줄 요약 ## Setup # 설치·실행 명령 ## Build & Test # 빌드·테스트 명령(에이전트가 바로 쓰게) ## Conventions # 네이밍·스타일·디렉토리 규칙 ## Guardrails # 금지 사항(예: main 직접 커밋 금지)
AGENTS.md vs CLAUDE.md vs .cursorrules 도구마다 읽는 파일이 다르다 — Claude Code는 CLAUDE.md, Codex는 AGENTS.md, Cursor는 .cursorrules 등. 하나만 유지한다면 AGENTS.md를 기본으로 두고, 특정 도구 전용 기능이 필요할 때만 그 도구 파일을 추가하는 게 권장된다. (Claude Code는 CLAUDE.md를 우선하므로, 이 둘을 같은 내용으로 두거나 한쪽이 다른 쪽을 가리키게 한다.)

계층적 컨텍스트 파일

큰 레포라면 루트 한 장으로 부족하다. 주요 도구는 중첩 컨텍스트 파일을 지원한다. 루트에 전체 규칙을 두고, src/api/AGENTS.md처럼 디렉토리별로 그 영역에만 적용되는 규칙을 둔다. 에이전트는 작업 중인 위치에 가까운 파일을 우선 참고한다 — monorepo에서 특히 유용하다.

에이전트 친화 구조의 원칙

  • 경계를 분명히 — 디렉토리·모듈 경계가 또렷할수록 에이전트가 영향 범위를 좁게 잡는다.
  • 문서를 코드 옆에 — README·AGENTS.md가 충실하면 에이전트의 추측이 줄고 정확도가 오른다.
  • 작은 단위 — 거대한 단일 파일보다 잘 쪼갠 모듈이 사람에게도 에이전트에게도 낫다.

에이전트와의 git 워크플로 규칙

에이전트가 커밋·PR을 만들기 시작하면 몇 가지 규칙을 명시해 두는 게 좋다. 여러 가이드가 공통으로 권하는 것은 다음과 같다.

  • 변경 전 항상 새 브랜치를 만든다(예: agent/<티켓>-<요약>). main에 직접 커밋하지 않는다.
  • PR을 작게 유지한다(예: 변경 수백 줄 이내). 리뷰 가능한 단위로 쪼갠다.
  • 커밋에 Co-Authored-By 트레일러로 에이전트 기여를 남긴다.
  • 기존 커밋 amend·force push 금지 — 히스토리를 안전하게 유지한다.

추천 출발 구성

"지금 막 시작하는데 감이 안 온다"면, 아래에서 출발해 필요할 때 확장하면 된다.

  1. monorepo 하나로 시작. 나누는 건 팀·서비스가 실제로 갈라질 때 한다. 처음부터 쪼개면 관리 비용만 늘어난다.
  2. GitHub Flow. main + 짧은 기능 브랜치 + PR. 브랜치는 짧게 살리고 자주 합친다.
  3. 위생 파일부터. README·.gitignore·LICENSE를 첫 커밋에 둔다. 비밀은 절대 커밋하지 않는다.
  4. AGENTS.md 추가. 빌드·테스트 명령과 컨벤션, 가드레일을 적는다. AI 협업을 한다면 이게 가장 가성비 높은 한 장이다.
  5. Conventional Commits. feat:/fix: 접두사로 히스토리를 읽기 쉽게.

정리

  • 구성은 제약의 결과다 — 팀 규모·배포 결합도·코드 공유로 정해진다. 대기업을 따라 하지 않는다.
  • 의심되면 단순하게 — monorepo 하나 + GitHub Flow + 위생 파일이면 대부분 충분하다. 확장은 나중에.
  • AI 한 겹을 더한다 — AGENTS.md(필요 시 CLAUDE.md)로 에이전트에게 규칙을 명시하고, 에이전트용 git 규칙(브랜치 분리·작은 PR)을 정해 둔다.
  • 세부는 공식 문서로 — 도구별 지원 파일·정확한 규약은 빠르게 바뀐다. 이 글의 골격을 뼈대로 두고 최신 문서를 확인한다.
