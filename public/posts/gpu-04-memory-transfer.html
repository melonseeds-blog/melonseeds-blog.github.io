왜 메모리 전송이 병목인가

GPU가 아무리 빠르게 연산해도, 데이터가 GPU 안에 들어가 있지 않으면 의미가 없다. 호스트 RAM과 GPU 전역 메모리 사이의 데이터 이동은 PCIe 버스를 통해 일어나고, 이 구간이 전체 파이프라인에서 가장 느린 구간이다.

Host ↔ PCIe ↔ GPU 전송 흐름 — 대역폭은 안쪽으로 갈수록 빨라진다
구간대표 대역폭비고
Host RAM (DDR5)~50 GB/sCPU 측 메모리
PCIe Gen4 x16~32 GB/s (이론), 실측 24~26가장 좁은 구간
PCIe Gen5 x16~64 GB/s최신 메인보드
GPU Global Memory500~1500 GB/sHBM3는 3 TB/s 이상
GPU Shared / L110 TB/s 이상SM on-chip
한 줄 요약 커널 실행 시간보다 cudaMemcpy 시간이 더 큰 경우가 흔하다. 전송을 줄이는 것이 GPU 최적화의 7할이다.

기본 API — cudaMalloc / cudaMemcpy

할당과 해제

GPU 전역 메모리는 cudaMalloc으로 잡고 cudaFree로 푼다. 반환은 항상 cudaError_t이므로 체크해야 한다.

#include <cuda_runtime.h>
#include <cstdio>

int main()
{
    const size_t n = 1024 * 1024;          // 1M elements
    const size_t bytes = n * sizeof(float);

    // Host 측 할당 — 일반 malloc/new
    float* hPtr = static_cast<float*>(malloc(bytes));

    // Device 측 할당
    float* dPtr = nullptr;
    cudaError_t err = cudaMalloc(&dPtr, bytes);
    if (err != cudaSuccess)
    {
        fprintf(stderr, "cudaMalloc failed: %s\n", cudaGetErrorString(err));
        return 1;
    }

    // ... 사용 ...

    cudaFree(dPtr);
    free(hPtr);
    return 0;
}

복사 방향

cudaMemcpy는 4가지 방향을 지정할 수 있다. 방향만 다르고 인자 순서는 (dst, src, bytes, kind)로 항상 같다.

// Host → Device : 입력 데이터 업로드
cudaMemcpy(dPtr, hPtr, bytes, cudaMemcpyHostToDevice);

// Device → Host : 결과 다운로드
cudaMemcpy(hPtr, dPtr, bytes, cudaMemcpyDeviceToHost);

// Device → Device : GPU 내부 복사 (PCIe 안 탐, 매우 빠름)
cudaMemcpy(dPtrB, dPtrA, bytes, cudaMemcpyDeviceToDevice);

// Host → Host : 거의 안 씀 (memcpy로 충분)
cudaMemcpy(hPtrB, hPtrA, bytes, cudaMemcpyHostToHost);

// 방향 자동 추론 (느림, 디버그용)
cudaMemcpy(dst, src, bytes, cudaMemcpyDefault);
Device→Device는 거의 공짜 같은 GPU 내부 복사는 PCIe를 타지 않고 GPU 메모리 대역폭(~1 TB/s)을 그대로 쓴다. 중간 결과를 호스트로 보냈다가 다시 올리는 코드는 즉시 의심해야 한다.

초기화 — cudaMemset

// GPU 메모리를 0으로 초기화 (byte 단위)
cudaMemset(dPtr, 0, bytes);

// 주의: float 1.0f로 채우지는 못한다. byte 패턴만 지정 가능.

2D / 3D 메모리와 Pitch

이미지처럼 2D 데이터를 다룰 때, 단순히 width * height * sizeof(T)로 잡으면 행 시작 주소가 정렬되지 않아 메모리 접근이 느려진다. CUDA는 cudaMallocPitch로 각 행을 정렬해 잡고, 실제 행 간격을 pitch(stride)로 알려준다.

const int kImageWidth  = 1920;
const int kImageHeight = 1080;

float* dImage = nullptr;
size_t pitch = 0;  // 한 행의 실제 byte 수 (보통 width*sizeof(T)보다 큼)

cudaMallocPitch(&dImage, &pitch,
                kImageWidth * sizeof(float),  // 논리적 행 크기
                kImageHeight);

printf("logical row = %zu bytes, pitch = %zu bytes\n",
       kImageWidth * sizeof(float), pitch);
// 예: logical row = 7680, pitch = 7680 또는 8192

전송도 pitch를 인지하는 cudaMemcpy2D를 쓴다.

// Host에 일반 배열 (pitch == width*sizeof(T))
float* hImage = static_cast<float*>(malloc(kImageWidth * kImageHeight * sizeof(float)));

cudaMemcpy2D(dImage, pitch,                          // dst, dst pitch
             hImage, kImageWidth * sizeof(float),    // src, src pitch
             kImageWidth * sizeof(float),            // 한 행 byte 수
             kImageHeight,                           // 행 수
             cudaMemcpyHostToDevice);

커널 안에서는 pitch를 이용해 행 주소를 계산한다.

__global__ void InvertKernel(float* image, size_t pitch, int width, int height)
{
    int x = blockIdx.x * blockDim.x + threadIdx.x;
    int y = blockIdx.y * blockDim.y + threadIdx.y;
    if (x >= width || y >= height) return;

    // pitch는 byte 단위 → char*로 캐스팅한 뒤 다시 float*로
    float* row = reinterpret_cast<float*>(reinterpret_cast<char*>(image) + y * pitch);
    row[x] = 1.0f - row[x];
}
pitch를 무시하고 width로 접근하지 말 것 image[y * width + x]로 접근하면 어떤 행은 맞고 어떤 행은 어긋난다. 이미지 가장자리에 줄무늬가 나타나면 거의 이 문제다.

3D 메모리

cudaPitchedPtr dVolume;
cudaExtent extent = make_cudaExtent(width * sizeof(float), height, depth);
cudaMalloc3D(&dVolume, extent);
// dVolume.ptr, dVolume.pitch, dVolume.xsize, dVolume.ysize 로 접근

핀드(Pinned) 메모리

일반 malloc으로 잡은 호스트 메모리는 pageable이다. OS가 페이지를 디스크로 스왑할 수 있어서, GPU가 DMA로 직접 읽을 수 없다. CUDA 런타임은 일단 임시 핀드 버퍼로 복사한 다음 PCIe로 보낸다. 즉, 한 번 더 복사한다.

핀드 메모리(page-locked memory)는 OS가 스왑하지 못하도록 고정한 호스트 메모리다. GPU가 DMA로 바로 읽고 쓸 수 있어 전송 속도가 빨라진다.

// 핀드 할당
float* hPinned = nullptr;
cudaMallocHost(&hPinned, bytes);   // 또는 cudaHostAlloc

// 사용은 일반 포인터와 동일
for (size_t i = 0; i < n; ++i) hPinned[i] = static_cast<float>(i);

cudaMemcpy(dPtr, hPinned, bytes, cudaMemcpyHostToDevice);

// 해제
cudaFreeHost(hPinned);

체감 — 간단 벤치

#include <cuda_runtime.h>
#include <cstdio>

double TransferMs(void* dst, void* src, size_t bytes, cudaMemcpyKind kind, int iter = 20)
{
    cudaEvent_t s, e;
    cudaEventCreate(&s); cudaEventCreate(&e);
    cudaEventRecord(s);
    for (int i = 0; i < iter; ++i) cudaMemcpy(dst, src, bytes, kind);
    cudaEventRecord(e); cudaEventSynchronize(e);
    float ms = 0.f; cudaEventElapsedTime(&ms, s, e);
    cudaEventDestroy(s); cudaEventDestroy(e);
    return ms / iter;
}

int main()
{
    const size_t bytes = 256 * 1024 * 1024;  // 256 MB
    float* dPtr; cudaMalloc(&dPtr, bytes);

    float* hPageable = static_cast<float*>(malloc(bytes));
    float* hPinned;  cudaMallocHost(&hPinned, bytes);

    printf("Pageable H2D: %.2f ms\n", TransferMs(dPtr, hPageable, bytes, cudaMemcpyHostToDevice));
    printf("Pinned   H2D: %.2f ms\n", TransferMs(dPtr, hPinned,   bytes, cudaMemcpyHostToDevice));

    cudaFree(dPtr); free(hPageable); cudaFreeHost(hPinned);
}

RTX 4090 + PCIe Gen4 환경에서 대략 다음과 같은 차이가 난다.

방식대역폭 (예시)비고

Pinned + 비동기 + 스트림~25 GB/s × 오버랩다음 편 주제
핀드 메모리를 너무 많이 잡으면 시스템이 느려진다 OS가 페이지를 스왑/이동하지 못하므로 가용 RAM이 줄어든다. 16 GB 시스템에서 8 GB를 핀드로 잡으면 다른 프로세스가 스왑으로 내몰린다. 꼭 필요한 grab 버퍼·전송 스테이징 버퍼에만 사용한다.

cudaHostAlloc — 플래그 버전

float* hp = nullptr;
cudaHostAlloc(&hp, bytes, cudaHostAllocDefault);
// 플래그 종류:
//   cudaHostAllocDefault         : 일반 핀드
//   cudaHostAllocPortable        : 모든 CUDA 컨텍스트에서 핀드로 보임
//   cudaHostAllocMapped          : Zero-Copy용 매핑
//   cudaHostAllocWriteCombined   : Write-Combined

Write-Combined 메모리

Write-Combined(WC)은 CPU 캐시를 우회하는 핀드 메모리다. CPU가 쓰기만 하고 절대 읽지 않을 때 유리하다. PCIe로 나가는 속도가 더 빨라지지만, CPU가 이 영역에서 한 번이라도 읽으면 굉장히 느려진다.

float* hWc = nullptr;
cudaHostAlloc(&hWc, bytes, cudaHostAllocWriteCombined);

// 좋은 사용: 입력 버퍼 채우고 GPU로 보내기만 함
for (size_t i = 0; i < n; ++i) hWc[i] = ProduceSample(i);
cudaMemcpy(dPtr, hWc, bytes, cudaMemcpyHostToDevice);

// 나쁜 사용: CPU 읽기 — 매우 느림!
// float v = hWc[0];   // ✗ 캐시 우회 → 메모리에서 직접 읽음
언제 쓰나 Host→Device 일방향 스트리밍 (예: 카메라 grab 후 GPU로 보내기만 하는 버퍼). Device→Host 결과 버퍼에는 절대 쓰지 말 것.

Zero-Copy 메모리

Zero-Copy는 호스트 메모리를 GPU 주소공간에 매핑해서, 커널이 PCIe를 통해 직접 읽거나 쓰는 방식이다. cudaMemcpy가 필요 없다는 게 장점이지만, GPU의 모든 접근이 PCIe를 타기 때문에 큰 데이터엔 매우 불리하다.

// Mapped host memory 할당
float* hMapped = nullptr;
cudaHostAlloc(&hMapped, bytes, cudaHostAllocMapped);

// 같은 메모리를 가리키는 device 포인터 얻기
float* dMapped = nullptr;
cudaHostGetDevicePointer(&dMapped, hMapped, 0);

// 커널이 dMapped를 직접 사용 — 명시적 복사 없음
MyKernel<<<grid, block>>>(dMapped, n);
cudaDeviceSynchronize();

// 결과를 host에서 읽기 (이미 같은 메모리)
printf("%f\n", hMapped[0]);

cudaFreeHost(hMapped);
특성Zero-Copy 적합일반 cudaMemcpy 적합
데이터 크기작음 (~수 MB 이하)큼
접근 패턴1회 순차 읽기/쓰기반복 접근
예시구성 파라미터, 룩업 테이블 일부이미지·텐서
큰 데이터에 Zero-Copy를 쓰지 말 것 각 메모리 접근이 PCIe를 탄다. 1920×1080 이미지를 zero-copy로 읽으며 처리하면 cudaMemcpy + 커널 조합보다 5~10배 느려진다.

Unified Memory (cudaMallocManaged)

Unified Memory는 호스트와 디바이스가 같은 포인터를 공유하는 가상 메모리다. CUDA 런타임이 페이지 폴트를 잡아 필요한 쪽으로 자동 마이그레이션한다. Pascal 세대(SM 6.0) 이상에서 페이지 폴트 기반 마이그레이션을 지원한다.

float* uPtr = nullptr;
cudaMallocManaged(&uPtr, bytes);

// Host에서 초기화 — 자동으로 host에 페이지 배치
for (size_t i = 0; i < n; ++i) uPtr[i] = static_cast<float>(i);

// Device에서 사용 — 접근 시 페이지가 GPU로 자동 마이그레이션
MyKernel<<<grid, block>>>(uPtr, n);
cudaDeviceSynchronize();

// Host에서 다시 읽기 — 페이지가 host로 돌아옴
printf("%f\n", uPtr[0]);

cudaFree(uPtr);

접근 패턴을 미리 알 수 있다면 cudaMemPrefetchAsync로 마이그레이션 시점을 앞당겨 페이지 폴트를 줄일 수 있다.

int device = 0;
cudaGetDevice(&device);

// GPU로 미리 보내기
cudaMemPrefetchAsync(uPtr, bytes, device);
MyKernel<<<grid, block>>>(uPtr, n);

// Host로 미리 가져오기
cudaMemPrefetchAsync(uPtr, bytes, cudaCpuDeviceId);
cudaDeviceSynchronize();

메모리 전송 최적화 패턴

1) 전송 횟수를 줄인다

여러 단계의 처리를 GPU에서 한 번에 끝내는 것이 가장 좋다.

// ✗ 나쁜 예 — 단계마다 host로 내림
cudaMemcpy(dA, hA, bytes, cudaMemcpyHostToDevice);
BlurKernel<<<...>>>(dA, dB);
cudaMemcpy(hB, dB, bytes, cudaMemcpyDeviceToHost);   // 불필요
cudaMemcpy(dB, hB, bytes, cudaMemcpyHostToDevice);   // 불필요
EdgeKernel<<<...>>>(dB, dC);
cudaMemcpy(hC, dC, bytes, cudaMemcpyDeviceToHost);

// ✓ 좋은 예 — 중간 결과는 GPU에 둠
cudaMemcpy(dA, hA, bytes, cudaMemcpyHostToDevice);
BlurKernel<<<...>>>(dA, dB);
EdgeKernel<<<...>>>(dB, dC);
cudaMemcpy(hC, dC, bytes, cudaMemcpyDeviceToHost);

2) 버퍼를 재사용한다

cudaMalloc/cudaFree는 비싸다. 처리할 때마다 할당하지 말고 풀(pool)을 만든다.

class GpuImageBuffer
{
public:
    ErrorCode Resize(int width, int height)
    {
        const size_t need = static_cast<size_t>(width) * height * sizeof(float);
        if (need <= m_capacity) { m_width = width; m_height = height; return ErrorCode::Ok; }

        if (m_ptr) cudaFree(m_ptr);
        cudaError_t e = cudaMalloc(&m_ptr, need);
        if (e != cudaSuccess) return ErrorCode::OutOfMemory;
        m_capacity = need;
        m_width = width; m_height = height;
        return ErrorCode::Ok;
    }
    ~GpuImageBuffer() { if (m_ptr) cudaFree(m_ptr); }

private:
    float* m_ptr      = nullptr;
    size_t m_capacity = 0;
    int    m_width    = 0;
    int    m_height   = 0;
};

3) 핀드 + 비동기 + 스트림 (예고)

핀드 메모리는 cudaMemcpyAsync의 전제 조건이다. 스트림을 활용하면 전송과 커널 실행을 겹쳐 PCIe 대기 시간을 숨길 수 있다. 자세한 내용은 5편에서 다룬다.

cudaStream_t s;
cudaStreamCreate(&s);

cudaMemcpyAsync(dPtr, hPinned, bytes, cudaMemcpyHostToDevice, s);
MyKernel<<<grid, block, 0, s>>>(dPtr, n);
cudaMemcpyAsync(hPinned, dPtr, bytes, cudaMemcpyDeviceToHost, s);

cudaStreamSynchronize(s);
cudaStreamDestroy(s);

산업 비전 적용 — 카메라 grab 버퍼

머신 비전 파이프라인에서 가장 효과 큰 최적화는 카메라 grab 버퍼 자체를 핀드 메모리로 잡는 것이다. Vieworks SDK든 GenICam이든, 사용자 버퍼 등록 API를 제공하면 거기에 cudaMallocHost로 잡은 버퍼를 넘긴다.

// Pinned ring buffer for camera grab
class PinnedRingBuffer
{
public:
    ErrorCode Initialize(int width, int height, int slotCount)
    {
        m_frameBytes = static_cast<size_t>(width) * height;  // Mono8 가정
        m_slotCount = slotCount;
        m_slots.resize(slotCount);

        for (int i = 0; i < slotCount; ++i)
        {
            // 카메라가 직접 쓰고, GPU가 빠르게 읽을 버퍼
            cudaError_t e = cudaHostAlloc(&m_slots[i], m_frameBytes,
                                          cudaHostAllocDefault);
            if (e != cudaSuccess) return ErrorCode::OutOfMemory;
        }
        return ErrorCode::Ok;
    }

    // 카메라 콜백에 슬롯 포인터 제공
    uint8_t* GetSlot(int index) const { return m_slots[index]; }

    ~PinnedRingBuffer()
    {
        for (auto* p : m_slots) if (p) cudaFreeHost(p);
    }

private:
    std::vector<uint8_t*> m_slots;
    size_t m_frameBytes = 0;
    int    m_slotCount  = 0;
};

전송은 비동기로 보내 다음 프레임 grab과 겹친다.

// 카메라 콜백 — 새 프레임이 슬롯 k에 들어왔다고 알려옴
void OnFrameReady(int k)

    cudaMemcpyAsync(m_dGpuFrame, m_ring.GetSlot(k),

    cudaMemcpyAsync(m_hResult, m_dResult, m_resultBytes,
                    cudaMemcpyDeviceToHost, m_stream);
    // CPU는 다음 grab을 기다리고, GPU는 이번 프레임을 처리한다.
}
실측 — 4K Mono8 (32 MB) 1프레임 Pageable로 받아 복사: ~3.0 ms / Pinned 직접 grab: ~1.3 ms / Pinned + 스트림 오버랩: 사실상 0 ms (커널과 겹침). 30 fps × 4K 라인에서 결정적인 차이다.

흔한 함정

너무 잦은 작은 전송

1 KB짜리 cudaMemcpy를 100번 호출하면, 100 KB를 한 번에 보내는 것보다 수십 배 느리다. 각 호출에는 고정 오버헤드(수 µs)가 있다. 작은 데이터를 모아 한 번에 보내자.

핀드 메모리 과다 사용

"빠르니까 다 핀드로" 는 위험 가용 시스템 RAM이 줄고, 다른 프로세스가 스왑으로 내몰린다. cudaHostAlloc이 어느 순간 cudaErrorMemoryAllocation을 돌려주기도 한다. 카메라 grab 슬롯·전송 스테이징처럼 빈번하게 PCIe를 타는 곳에만 사용한다.

pitch를 무시한 접근

2D 메모리를 image[y * width + x]로 접근하면 일부 행이 어긋난다. 반드시 pitch를 통해 행 주소를 구한다 (위 Pitch 섹션 참조).

Zero-Copy 남용

"cudaMemcpy 호출이 사라져서 좋다"는 이유로 큰 이미지에 Zero-Copy를 쓰면 모든 픽셀 접근이 PCIe를 탄다. 결과적으로 5~10배 느려진다. Zero-Copy는 작은 상수 데이터·룩업 테이블의 일부 접근 정도에만.

Managed Memory를 만능으로 보기

편하지만 페이지 폴트 비용이 누적되면 수동 cudaMemcpy보다 느려질 수 있다. 성능이 중요한 경로에서는 cudaMemPrefetchAsync로 마이그레이션 시점을 지정하거나, 아예 cudaMalloc으로 바꾸는 편이 낫다.

동기 vs 비동기 혼동

cudaMemcpy는 동기(완료까지 블록)지만, cudaMemcpyAsync는 호스트 측에서만 비동기다. 그리고 cudaMemcpyAsync는 핀드 메모리에서만 진짜로 비동기로 동작한다. pageable 메모리를 넘기면 내부에서 동기 복사로 폴백된다.

다음 편 예고 5편에서는 스트림과 비동기 실행을 다룬다. 핀드 메모리 + 멀티 스트림으로 전송과 커널을 어떻게 겹치는지, 그리고 이벤트로 동기화하는 방법까지.
