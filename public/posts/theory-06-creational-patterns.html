생성 패턴이란 무엇인가

생성 패턴(Creational Pattern)은 객체를 어떻게 만들 것인가를 다루는 패턴 묶음이다. GoF의 23패턴 중 Singleton·Factory Method·Abstract Factory·Builder·Prototype 다섯 개가 여기에 속한다. 공통 목적은 하나다 — 객체 생성 과정을 캡슐화하고, 사용하는 쪽이 구체 클래스 이름에 묶이지 않게 한다.

왜 생성 과정을 따로 다뤄야 하는가. new를 직접 쓰면 그 코드는 구체 클래스 이름을 소스에 박아 넣은(hard-coded) 상태가 된다. 이것이 강한 결합이다.

// 사용하는 쪽이 구체 클래스를 직접 안다 — 강한 결합
void RunInspection()
{
    GaussianBlurBlock* block = new GaussianBlurBlock();   // 구체 타입 박힘
    // ...
    delete block;   // 소유권 관리도 직접 떠안음
}

이 코드는 두 가지 문제를 안고 있다. 첫째, RunInspection은 GaussianBlurBlock이라는 구체 클래스를 알아야만 한다. 블록 종류를 바꾸려면 이 함수를 고쳐야 한다. 둘째, new/delete로 수명을 직접 관리한다. 예외가 던져지면 delete가 누락된다. 생성 패턴은 "무엇을 만들지 결정하는 책임"을 사용자에게서 떼어내, 한 곳에 모은다.

생성 패턴의 두 가지 캡슐화 생성 패턴은 두 가지를 동시에 숨긴다 — 어떤 구체 클래스를 만드는가, 그리고 어떻게 만드는가(인자 조합, 초기화 순서, 의존성 주입). 사용자는 "결과 객체"만 받고, 그 객체가 어떤 과정을 거쳐 나왔는지는 알 필요가 없다.

Singleton — 인스턴스를 하나로

Singleton은 어떤 클래스의 인스턴스가 프로그램 전체에서 오직 하나만 존재하도록 보장하고, 그 하나에 접근하는 전역 지점을 제공하는 패턴이다. 로거, 설정 관리자, 디바이스 드라이버 핸들처럼 "두 개가 있으면 곤란한" 자원에 쓴다.

Meyers Singleton — 함수 내 static

C++에서 가장 권장되는 구현은 Meyers Singleton이다. 함수 안의 static 지역 변수를 이용한다. 생성자를 private으로 막고, 복사/이동을 삭제해 외부에서 새 인스턴스를 만들 수 없게 한다.

// Meyers Singleton — 함수 내 static 지역 변수
class Logger
{
public:
    // 유일한 인스턴스에 접근하는 전역 지점
    static Logger& Instance()
    {
        static Logger s_instance;   // 최초 호출 시 한 번만 생성됨
        return s_instance;
    }

    void Info(const std::string& message);
    void Error(const std::string& message);

    // 복사와 이동을 막아 인스턴스가 둘이 되는 것을 차단
    Logger(const Logger&) = delete;
    Logger& operator=(const Logger&) = delete;

private:
    Logger() = default;    // 외부 생성 금지
    ~Logger() = default;

    std::string m_logFilePath;
};

// 사용
Logger::Instance().Info("inspection start");

이 방식의 장점은 지연 초기화(lazy initialization)다. Instance()가 처음 불릴 때 단 한 번 객체가 만들어진다. 한 번도 안 쓰이면 생성조차 되지 않는다.

멀티스레드 안전성

예전 C++에서는 두 스레드가 동시에 Instance()를 처음 호출하면 static 변수가 두 번 초기화되는 경쟁 조건이 있었다. C++11부터는 함수 내 static 지역 변수의 초기화가 스레드 안전하다고 표준이 보장한다. 한 스레드가 초기화 중이면 다른 스레드는 완료될 때까지 대기한다. 따라서 Meyers Singleton은 별도 락 없이도 안전하다.

직접 만든 "double-checked locking" Singleton은 피한다 C++11 이전 코드에서 흔히 보이는 포인터 + if (instance == nullptr) + 뮤텍스 패턴은, 메모리 모델을 잘못 다루면 미묘한 경쟁 조건을 남긴다. C++11 이후에는 Meyers Singleton이 같은 일을 표준 보장으로 더 안전하게 처리한다. 직접 락을 짜지 말 것.

Singleton의 위험 — 가장 남용되는 패턴

Singleton은 GoF 패턴 중 가장 쉽게 익히고, 가장 자주 오용된다. 본질적으로 Singleton은 전역 변수에 클래스 옷을 입힌 것이다. 전역 변수의 모든 문제를 그대로 물려받는다.

  • 숨은 의존성 — 어떤 함수가 Logger::Instance()를 부르면, 그 함수의 시그니처에는 Logger 의존성이 드러나지 않는다. 코드를 읽기 전엔 무엇에 의존하는지 알 수 없다.
  • 테스트의 어려움 — 전역 인스턴스는 테스트마다 가짜(mock)로 갈아끼우기 어렵다. 테스트 간 상태가 새어 나가 한 테스트가 다른 테스트를 오염시킨다.
  • 전역 상태 — 어디서든 접근 가능하다는 것은 어디서든 변경 가능하다는 뜻이다. 상태 변경 지점을 추적하기 어렵다.
  • 초기화/소멸 순서 — 여러 Singleton이 서로를 참조하면, 프로그램 종료 시 소멸 순서가 정의되지 않아 댕글링 참조가 생길 수 있다.
"Singleton으로 만들까?"의 답은 대개 "아니오"다 Singleton이 진짜 필요한 경우는 생각보다 드물다. "전역에서 편하게 접근하고 싶다"는 것은 Singleton의 이유가 아니라 증상이다. 대부분의 경우 객체를 한 번 만들어 필요한 곳에 인자로 전달(의존성 주입)하면 충분하다. 그러면 의존성이 시그니처에 드러나고, 테스트에서 가짜로 교체할 수 있다. Singleton은 "정말 하나여야만 하는 물리적 자원"에만 신중하게 쓴다.

Factory Method — 생성을 서브클래스에 위임

Factory Method는 객체를 생성하는 메서드를 정의하되, 어떤 구체 클래스를 만들지는 서브클래스가 결정하게 하는 패턴이다. 생성하는 코드와 사용하는 코드를 분리해, 사용하는 쪽은 추상 타입만 다룬다.

Creator는 추상 메서드만 선언하고, 어떤 구체 Product를 만들지는 ConcreteCreator가 결정한다

가장 흔한 변형은 매개변수화 팩토리다. 종류를 나타내는 인자를 받아, 그에 맞는 구체 객체를 만들어 추상 타입으로 돌려준다.

enum class FilterKind
{
    GaussianBlur,
    Median,
    Sobel
};

// 매개변수화 팩토리 — 어떤 구체 Filter를 만들지 런타임에 결정
class FilterFactory
{
public:
    // 종류를 받아 구체 Filter를 만들고 추상 타입으로 돌려준다
    static ErrorCode Create(FilterKind kind, std::unique_ptr<Filter>& outFilter)
    {
        switch (kind)
        {
        case FilterKind::GaussianBlur:
            outFilter = std::make_unique<GaussianBlurFilter>();
            return ErrorCode::Ok;
        case FilterKind::Median:
            outFilter = std::make_unique<MedianFilter>();
            return ErrorCode::Ok;
        case FilterKind::Sobel:
            outFilter = std::make_unique<SobelFilter>();
            return ErrorCode::Ok;
        default:
            return ErrorCode::InvalidParameter;
        }
    }
};

// 사용하는 쪽은 구체 타입을 전혀 모른다
std::unique_ptr<Filter> filter;
if (FilterFactory::Create(FilterKind::Median, filter) == ErrorCode::Ok)
{
    filter->Apply(image);   // 추상 인터페이스로만 다룸
}

이 구조의 핵심 가치는 구체 클래스 의존성의 격리다. GaussianBlurFilter를 안다는 사실이 FilterFactory 한 곳에만 갇힌다. 사용하는 코드 어디에도 구체 클래스 이름이 박히지 않는다. 게다가 new/delete 대신 unique_ptr로 소유권을 명확히 넘긴다.

Abstract Factory — 객체 family 생성

Abstract Factory는 서로 관련된 객체들의 family를 통째로 생성하는 패턴이다. Factory Method가 객체 하나의 생성을 다룬다면, Abstract Factory는 "함께 쓰여야 하는 객체 묶음"을 일관되게 만든다.

예를 들어 카메라 벤더마다 카메라·그래버·트리거 컨트롤러가 한 세트로 묶여 있고, 한 벤더의 카메라에 다른 벤더의 그래버를 섞으면 안 된다고 하자. Abstract Factory는 "벤더"라는 축으로 이 family를 묶는다.

// 추상 family 인터페이스
class IVisionDevice { public: virtual ~IVisionDevice() = default; };
class ICamera  : public IVisionDevice { /* ... */ };
class IGrabber : public IVisionDevice { /* ... */ };

// Abstract Factory — 한 family를 함께 만든다
class IDeviceFactory
{
public:
    virtual ~IDeviceFactory() = default;
    virtual std::unique_ptr<ICamera>  CreateCamera()  = 0;
    virtual std::unique_ptr<IGrabber> CreateGrabber() = 0;
};

// 구체 family 1 — Vieworks 세트
class VieworksDeviceFactory : public IDeviceFactory
{
public:
    std::unique_ptr<ICamera> CreateCamera() override
    {
        return std::make_unique<VieworksCamera>();
    }
    std::unique_ptr<IGrabber> CreateGrabber() override
    {
        return std::make_unique<VieworksGrabber>();
    }
};

// 사용하는 쪽은 한 factory로부터 일관된 세트만 받는다
ErrorCode SetupVision(IDeviceFactory& factory)
{
    auto camera  = factory.CreateCamera();
    auto grabber = factory.CreateGrabber();   // 같은 벤더 세트가 보장됨
    // 카메라와 그래버가 섞일 일이 없다
    return ErrorCode::Ok;
}

SetupVision은 어떤 factory를 받든 한 벤더 안에서 일관된 세트를 얻는다. Vieworks 카메라에 다른 벤더 그래버가 끼어들 수 없다. 이것이 Abstract Factory가 보장하는 family 일관성이다.

Builder — 복잡한 객체를 단계별로

Builder는 복잡한 객체를 단계별로 조립하는 패턴이다. 생성자 인자가 너무 많거나, 선택적 파라미터가 많아 생성자 오버로드가 폭발할 때 쓴다.

문제 — 텔레스코핑 생성자

검사 설정 객체에 파라미터가 여덟 개쯤 있다고 하자. 일부는 필수, 일부는 선택이다. 생성자로 풀면 인자 순서를 외워야 하고, 같은 타입 인자가 줄지어 있으면 실수로 자리를 바꿔도 컴파일은 통과한다.

// 안티 패턴 — 인자가 무엇을 뜻하는지 호출부만 봐서는 알 수 없다
InspectionConfig config(1920, 1080, 8, true, false, 200.0, 3, true);
//                       ^^^^  ^^^^  ^  ^^^^  ^^^^^  ^^^^^  ^  ^^^^
//                       이게 width? height? threshold? 누가 알겠는가

해법 — fluent interface로 조립

Builder는 각 파라미터를 이름 있는 메서드로 설정하고, 마지막에 Build()로 완성된 객체를 받는다. 각 setter가 자기 자신(*this)을 돌려주면 호출을 연쇄할 수 있다 — 이것이 fluent interface다.

class InspectionConfig
{
public:
    int    GetWidth() const     { return m_width; }
    int    GetHeight() const    { return m_height; }
    double GetThreshold() const { return m_threshold; }
    bool   IsSubpixelEnabled() const { return m_subpixel; }

private:
    // Builder만 InspectionConfig를 만들 수 있게 한다
    friend class InspectionConfigBuilder;
    InspectionConfig() = default;

    int    m_width    = 0;
    int    m_height   = 0;
    double m_threshold = 128.0;
    bool   m_subpixel  = false;
};

// Builder — 단계별로 조립하고 마지막에 Build로 완성
class InspectionConfigBuilder
{
public:
    // 각 setter가 자기 자신을 돌려줘 호출을 연쇄한다
    InspectionConfigBuilder& SetResolution(int width, int height)
    {
        m_config.m_width = width;
        m_config.m_height = height;
        return *this;
    }
    InspectionConfigBuilder& SetThreshold(double value)
    {
        m_config.m_threshold = value;
        return *this;
    }
    InspectionConfigBuilder& EnableSubpixel()
    {
        m_config.m_subpixel = true;
        return *this;
    }

    // 조립이 끝난 객체를 검증 후 돌려준다
    ErrorCode Build(InspectionConfig& outConfig)
    {
        if (m_config.m_width <= 0 || m_config.m_height <= 0)
        {
            return ErrorCode::InvalidParameter;
        }
        outConfig = m_config;
        return ErrorCode::Ok;
    }

private:
    InspectionConfig m_config;
};

// 사용 — 각 값이 무엇인지 호출부에서 바로 읽힌다
InspectionConfig config;
ErrorCode ec = InspectionConfigBuilder()
                   .SetResolution(1920, 1080)
                   .SetThreshold(200.0)
                   .EnableSubpixel()
                   .Build(config);

호출부가 곧 문서가 된다. SetResolution(1920, 1080)은 인자 순서를 외울 필요가 없다. 설정하지 않은 선택 파라미터는 클래스에 정의된 기본값을 그대로 쓴다. Build()는 조립이 끝난 시점에 한 번에 검증한다.

단순한 객체에 Builder를 쓰지 않는다 파라미터가 두세 개뿐이거나 모두 필수라면 Builder는 과한 장치다. 클래스 하나를 위해 Builder 클래스를 하나 더 만들어 코드량을 두 배로 늘릴 뿐이다. Builder는 "인자가 많고 + 상당수가 선택적이며 + 잘못 조합되기 쉬울 때" 가치가 있다. 그 조건이 아니면 평범한 생성자나 집합 초기화가 더 정직하다.

Prototype — 복제로 생성

Prototype은 새 객체를 클래스로부터 만드는 대신, 기존 객체를 복제(clone)해서 만드는 패턴이다. 객체 생성 비용이 크거나, 만들고 싶은 객체의 구체 타입을 컴파일 타임에 모를 때 유용하다.

핵심은 Clone()이라는 가상 메서드다. 각 구체 클래스가 "자기 자신의 복제본"을 만드는 법을 안다. 사용하는 쪽은 원본의 구체 타입을 몰라도 복제본을 얻을 수 있다.

// Prototype 인터페이스 — 자기 자신을 복제하는 법을 안다
class ProcessBlock
{
public:
    virtual ~ProcessBlock() = default;

    // 자기 자신의 복제본을 만들어 돌려준다
    virtual std::unique_ptr<ProcessBlock> Clone() const = 0;
    virtual ErrorCode Process(Image& image) = 0;
};

class BlurBlock : public ProcessBlock
{
public:
    std::unique_ptr<ProcessBlock> Clone() const override
    {
        // 복사 생성자를 이용해 자기 타입의 사본을 만든다
        return std::make_unique<BlurBlock>(*this);
    }
    ErrorCode Process(Image& image) override;

private:
    int m_kernelSize = 3;   // 복제 시 이 설정값도 함께 복사됨
};

// 사용 — 원본의 구체 타입을 몰라도 같은 설정의 사본을 얻는다
std::unique_ptr<ProcessBlock> CopyConfiguredBlock(const ProcessBlock& prototype)
{
    return prototype.Clone();   // BlurBlock인지 EdgeBlock인지 알 필요 없음
}

플로우 에디터에서 사용자가 이미 파라미터를 다 맞춰 둔 블록을 "복제"할 때 Prototype이 자연스럽게 들어맞는다. 새 블록을 클래스로부터 만들면 기본값으로 초기화되지만, Clone()은 현재 설정 상태까지 통째로 복사한다.

패턴 선택 가이드

다섯 패턴은 모두 "객체 생성"을 다루지만 해결하는 문제가 다르다. 어떤 상황에 무엇을 쓰는지 정리한다.

패턴목적이런 상황에 쓴다
Singleton 인스턴스를 정확히 하나로 보장 물리적으로 하나여야 하는 자원(드라이버 핸들 등). 단, 남용 주의 — 대개는 의존성 주입이 낫다
Factory Method 어떤 구체 클래스를 만들지 런타임 결정 종류가 런타임에 정해지고, 사용하는 쪽이 구체 타입을 몰라야 할 때
Abstract Factory 관련 객체 family를 일관되게 생성 함께 쓰여야 하는 객체 묶음이 있고, 섞이면 안 될 때(벤더별 디바이스 세트)
Builder 복잡한 객체를 단계별로 조립 생성자 인자가 많고, 선택적 파라미터가 많아 조합 실수가 잦을 때
Prototype 기존 객체를 복제해 생성 생성 비용이 크거나, 현재 상태를 그대로 가진 사본이 필요할 때
"무엇을 만들까"와 "어떻게 만들까"를 구분한다 Factory 계열(Factory Method·Abstract Factory)은 어떤 구체 클래스를 만들지를 다룬다. Builder는 어떻게 조립할지를 다룬다. Prototype은 무엇으로부터 만들지를 다룬다. 풀려는 문제가 "구체 타입 선택"인지 "조립 과정"인지 "복제"인지 먼저 가려내면, 패턴은 거의 자동으로 정해진다.

모던 C++와 생성 패턴

GoF 책은 1994년에 나왔다. 그때의 C++과 지금의 C++은 다르다. 모던 C++의 언어 기능은 일부 생성 패턴을 더 안전하게 만들고, 일부는 아예 더 가볍게 대체한다.

스마트 포인터 — 소유권을 명확히

예전 팩토리는 new로 만든 raw 포인터를 돌려줬다. 누가 delete할지 규약으로만 정해져 누수가 잦았다. 모던 C++에서 팩토리는 std::unique_ptr을 돌려준다. 반환 타입 자체가 "당신이 이 객체를 소유한다"는 계약을 표현한다. 내부 생성도 new 대신 std::make_unique를 쓴다.

람다 팩토리 — 클래스 없는 생성 전략

Factory Method를 위해 매번 Creator 클래스 계층을 만들 필요는 없다. 생성 동작을 std::function으로 받아 등록하면, 람다 하나가 곧 팩토리가 된다.

// 생성 함수를 값으로 다룬다 — 클래스 계층 없이도 팩토리가 된다
using FilterCreator = std::function<std::unique_ptr<Filter>()>;

std::unordered_map<std::string, FilterCreator> creators;

// 람다 하나가 곧 하나의 팩토리
creators["blur"]   = [] { return std::make_unique<GaussianBlurFilter>(); };
creators["median"] = [] { return std::make_unique<MedianFilter>(); };

// 이름으로 생성
auto it = creators.find("blur");
if (it != creators.end())
{
    std::unique_ptr<Filter> filter = it->second();
}
패턴은 "구조"이지 "클래스 개수"가 아니다 람다 팩토리도 여전히 Factory 패턴이다. 생성 책임을 분리해 한 곳에 모은다는 구조가 같기 때문이다. GoF가 그린 클래스 다이어그램을 글자 그대로 따를 필요는 없다. 언어가 더 가벼운 표현을 제공하면 그것을 쓰되, 패턴이 풀려던 문제는 그대로 풀어야 한다.

언어 기능이 대체하는 부분

일부 패턴은 모던 C++에서 언어 기능으로 간소화된다. Builder가 풀던 "선택적 파라미터" 문제 중 일부는 지명 초기화(designated initializers, C++20)나 기본 멤버 초기값으로 충분히 해결된다. Prototype의 Clone()도, 멤버가 모두 복사 가능하면 컴파일러가 만들어 주는 복사 생성자로 상당 부분 대체된다. 패턴을 도입하기 전에 "언어가 이미 해 주는 일인가?"를 먼저 확인한다.

산업 SW 관점

이미징 SDK 같은 시스템에서 생성 패턴은 추상적인 이론이 아니라 플러그인 구조의 실제 뼈대다. 두 지점에서 자연스럽게 등장한다.

BlockRegistry — Factory로 플러그인 블록 생성

데이터 플로우 에디터에서 모든 처리 블록은 IProcessBlock 인터페이스를 구현한다. 사용자가 에디터에서 "블러 블록 추가"를 누르면, 엔진은 "GaussianBlur"라는 문자열만 받아 해당 블록을 만들어야 한다 — 구체 클래스를 알지 못한 채로. 이를 람다 팩토리 + 레지스트리로 푼다.

// 블록 종류를 이름으로 등록하고 이름으로 생성하는 레지스트리
class BlockRegistry
{
public:
    using BlockCreator = std::function<std::unique_ptr<IProcessBlock>()>;

    // 블록 종류를 이름과 생성 함수로 등록한다
    ErrorCode Register(const std::string& typeName, BlockCreator creator)
    {
        if (typeName.empty() || m_creators.count(typeName) > 0)
        {
            return ErrorCode::InvalidParameter;
        }
        m_creators[typeName] = std::move(creator);
        return ErrorCode::Ok;
    }

    // 이름으로 블록을 생성한다 — 구체 타입은 레지스트리만 안다
    ErrorCode Create(const std::string& typeName,
                     std::unique_ptr<IProcessBlock>& outBlock) const
    {
        auto it = m_creators.find(typeName);
        if (it == m_creators.end())
        {
            return ErrorCode::NotFound;
        }
        outBlock = it->second();
        return ErrorCode::Ok;
    }

private:
    std::unordered_map<std::string, BlockCreator> m_creators;
};

// 시작 시 블록 종류를 등록한다
BlockRegistry registry;
registry.Register("GaussianBlur",
                  [] { return std::make_unique<GaussianBlurBlock>(); });
registry.Register("EdgeDetect",
                  [] { return std::make_unique<EdgeDetectBlock>(); });

// 에디터는 문자열만으로 블록을 만든다
std::unique_ptr<IProcessBlock> block;
registry.Create("GaussianBlur", block);

이 구조의 위력은 확장의 격리다. 새 블록을 추가하려면 IProcessBlock을 구현한 클래스 하나를 만들고 Register 한 줄을 더할 뿐이다. 에디터·엔진 코드는 한 줄도 바뀌지 않는다. 나아가 플러그인 DLL이 로드될 때 스스로 Register를 호출하게 하면, SDK를 다시 컴파일하지 않고도 블록을 추가할 수 있다.

검사 설정 — Builder로 복잡한 구성 조립

실제 검사 설정은 해상도·ROI·임계값·서브픽셀 여부·재시도 횟수·캘리브레이션 데이터 등 파라미터가 십수 개에 이른다. 대부분 선택적이고 기본값이 있다. 이런 구성 객체는 Builder로 조립할 때 호출부가 읽기 쉬워지고, Build() 시점에 "ROI가 이미지 범위를 벗어났는가" 같은 교차 검증을 한 번에 할 수 있다. 앞의 InspectionConfigBuilder 예제가 이 패턴의 축소판이다.

레지스트리를 Singleton으로 만들고 싶은 유혹 BlockRegistry를 "어디서나 접근하게" Singleton으로 만들고 싶어진다. 하지만 그 순간 앞서 본 Singleton의 모든 문제(테스트 격리 불가, 숨은 의존성)가 따라온다. 레지스트리는 애플리케이션 시작 시 한 번 만들어 필요한 곳에 인자로 전달하는 편이 거의 항상 낫다. "하나만 있으면 된다"와 "전역으로 접근해야 한다"는 다른 이야기다.

흔한 함정

함정 1 — Singleton 남용, 사실상 전역 변수

가장 흔하고 가장 비싼 함정이다. "전역에서 편하게 쓰자"는 이유로 Singleton을 도입하면, 클래스 옷을 입은 전역 변수가 코드 전체에 퍼진다. 의존성이 시그니처에 드러나지 않고, 테스트에서 가짜로 교체할 수 없으며, 상태 변경 지점을 추적할 수 없다. Singleton을 쓰기 전에 "이것을 인자로 넘기면 안 되는 이유가 무엇인가?"를 자문한다. 명확한 답이 없다면 Singleton이 아니라 의존성 주입을 쓴다.

함정 2 — 멀티스레드 Singleton 초기화 경쟁

C++11 이전 방식으로 Singleton을 직접 구현하면(포인터 + null 체크 + 수동 락), 메모리 모델을 잘못 다뤄 두 스레드가 동시에 인스턴스를 만들거나, 절반만 초기화된 객체를 보게 될 수 있다. 해법은 단순하다 — Meyers Singleton을 쓴다. C++11부터 함수 내 static 지역 변수 초기화는 표준이 스레드 안전성을 보장한다. 직접 락을 짜는 순간 그것이 버그의 출처가 된다.

"내가 짠 락은 맞다"는 가장 위험한 가정이다 멀티스레드 초기화 버그는 대부분의 실행에서 멀쩡히 동작하다가, 특정 타이밍·특정 하드웨어에서만 터진다. 재현이 어렵고 디버깅이 고통스럽다. 표준이 보장하는 Meyers Singleton을 두고 직접 락을 짤 이유는 거의 없다.

함정 3 — 단순 객체에 Builder 과용

패턴을 막 배운 시점에 흔히 빠진다. 멤버가 두 개뿐인 Point에까지 PointBuilder를 만든다. 이것은 코드를 명료하게 만들기는커녕, 클래스 수만 두 배로 늘리고 Point{x, y}면 끝날 일을 세 줄로 만든다. Builder는 "인자가 많고 + 선택적이고 + 잘못 조합되기 쉬울 때"의 도구다. 그 조건을 만족하지 않으면 평범한 생성자가 더 정직하다.

함정 4 — Factory가 거대해진다

매개변수화 팩토리의 switch문은 종류가 늘 때마다 길어진다. 종류가 수십 개가 되면 FilterFactory::Create는 거대한 분기 덩어리가 되고, 새 종류를 추가할 때마다 이 함수를 열어 고쳐야 한다 — 개방-폐쇄 원칙 위반이다. 해법은 앞서 본 레지스트리 방식이다. switch 대신 map<이름, 생성함수>에 등록하면, 새 종류 추가가 곧 Register 한 줄이 되고 팩토리 코드 자체는 닫혀 있게 된다.

// 함정 — switch가 끝없이 길어진다
std::unique_ptr<Filter> Create(FilterKind kind)
{
    switch (kind)
    {
    case FilterKind::GaussianBlur: return std::make_unique<GaussianBlurFilter>();
    case FilterKind::Median:       return std::make_unique<MedianFilter>();
    // ... 종류가 늘 때마다 이 함수를 계속 고쳐야 한다
    }
    return nullptr;
}

// 해법 — 등록 기반. 팩토리 코드는 닫혀 있고, 추가는 Register 한 줄
registry.Register("gaussian", [] { return std::make_unique<GaussianBlurFilter>(); });
