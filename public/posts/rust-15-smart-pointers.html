스마트 포인터 — Box·Rc·RefCell

2026-06-25 약 8분 분량 Rust 시리즈
이 편에서 배우는 것 스마트 포인터는 단순한 포인터가 아니라, 데이터를 가리키면서 동시에 추가 메타데이터와 동작을 들고 다니는 타입이다. 이 글에서는 힙에 값을 두는 Box<T>, 하나의 값을 여러 곳에서 공유 소유하는 Rc<T>, 불변 참조 뒤에서도 안쪽 값을 바꾸게 해 주는 RefCell<T>를 차례로 다룬다. 마지막에 이 셋을 합친 Rc<RefCell<T>> 관용 패턴까지 본다. C++의 unique_ptr·shared_ptr과 무엇이 같고 무엇이 다른지를 곳곳에서 대조한다.

왜 스마트 포인터인가

Rust의 기본 참조 &T·&mut T는 빌림(borrow)일 뿐 값을 소유하지 않는다. 컴파일 타임에 크기를 알 수 없는 값을 다루거나, 하나의 값을 여러 주인이 공유하거나, 불변으로 빌린 값의 안쪽만 바꾸고 싶을 때는 일반 참조로 풀리지 않는다. 이때 쓰는 것이 스마트 포인터다.

스마트 포인터는 포인터처럼 동작하지만 소유권과 추가 기능을 함께 들고 다니는 타입이다. 대부분 Deref 트레이트로 가리키는 값처럼 역참조되고, Drop 트레이트로 스코프를 벗어날 때 정리 동작을 수행한다. 표준 라이브러리의 핵심 셋이 Box<T>, Rc<T>, RefCell<T>다.

각각이 푸는 문제를 한 줄로 요약하면 이렇다.

  • Box<T> — 값을 스택이 아니라 힙에 두고, 단일 소유권으로 관리한다.
  • Rc<T> — 같은 값을 여러 소유자가 공유하되, 단일 스레드에서만 쓴다.
  • RefCell<T> — 불변 참조 뒤에서도 안쪽 값을 바꾼다. 빌림 규칙을 컴파일 타임이 아니라 런타임에 검사한다.

Box<T> — 힙에 값을 둔다

Box<T>는 가장 단순한 스마트 포인터다. 값을 힙에 할당하고, 스택에는 그 힙 주소를 가리키는 포인터만 남긴다. 소유자는 하나뿐이고, Box가 스코프를 벗어나면 힙의 값도 함께 해제된다.

fn main() {
    // 정수 5를 힙에 할당하고 b가 그 값을 소유한다
    let b = Box::new(5);
    println!("b = {}", b); // Deref 덕분에 값처럼 출력된다

    // b가 스코프를 벗어나면 힙의 5도 자동 해제된다
}

스택에 그냥 두면 될 정수를 굳이 박싱할 일은 드물다. Box가 진짜 필요한 대표 사례는 컴파일 타임에 크기를 알 수 없는 재귀 타입이다. 아래 연결 리스트는 Box 없이는 무한 크기가 되어 컴파일되지 않는다.

// 재귀적 타입: List는 자기 자신을 포함한다
enum List {
    // Box로 감싸 크기를 포인터 하나로 고정한다
    Cons(i32, Box<List>),
    Nil,
}

use List::{Cons, Nil};

fn main() {
    // 1 -> 2 -> 3 -> Nil 형태의 리스트
    let list = Cons(1, Box::new(Cons(2, Box::new(Cons(3, Box::new(Nil))))));

    // 첫 원소만 꺼내 본다
    if let Cons(head, _) = &list {
        println!("head = {}", head); // head = 1
    }
}

List 안에 List를 직접 넣으면 컴파일러가 크기를 무한히 계산하게 된다. Box<List>로 바꾸면 필드 크기가 "포인터 한 개"로 고정되므로 크기가 결정된다. 트레이트 객체(Box<dyn Trait>)로 크기가 다른 여러 타입을 한 컨테이너에 담을 때도 같은 원리가 쓰인다.

C++ 대조 — Box는 std::unique_ptr에 가깝다 Box<T>는 단일 소유 + 자동 해제라는 점에서 std::unique_ptr<T>에 대응한다. 다만 C++에서 unique_ptr은 비워질 수 있어 nullptr 검사가 필요하지만, Box<T>는 항상 유효한 값을 가리킨다 — "널일 수도 있는 박스"는 Option<Box<T>>로 타입에 명시한다. 또한 Box의 이동은 컴파일러가 강제하므로, 옮긴 뒤의 원본을 실수로 다시 쓰면 컴파일 에러가 난다.

Rc<T> — 공유 소유

값 하나를 여러 주인이 동시에 소유해야 할 때가 있다. 예컨대 그래프에서 한 노드를 여러 간선이 가리키는 경우다. 소유자가 정확히 하나여야 하는 Rust 기본 규칙으로는 표현할 수 없다. Rc<T>(Reference Counted)가 이를 푼다.

Rc::clone을 호출하면 데이터를 복제하지 않고 참조 카운트만 1 늘린다. 마지막 Rc가 사라져 카운트가 0이 되는 순간 데이터가 해제된다. Rc는 단일 스레드 전용이다.

use std::rc::Rc;

fn main() {
    // 문자열을 Rc로 감싸 공유 소유로 만든다
    let a = Rc::new(String::from("shared data"));
    println!("count after a = {}", Rc::strong_count(&a)); // 1

    // clone은 데이터를 복사하지 않고 카운트만 올린다
    let b = Rc::clone(&a);
    println!("count after b = {}", Rc::strong_count(&a)); // 2

    {
        let c = Rc::clone(&a);
        println!("count after c = {}", Rc::strong_count(&a)); // 3
        // 같은 데이터를 세 곳에서 읽을 수 있다
        println!("{}, {}, {}", a, b, c);
    } // c가 스코프를 벗어나며 카운트가 2로 줄어든다

    println!("count after scope = {}", Rc::strong_count(&a)); // 2
}

Rc::clone(&a)는 일부러 a.clone() 대신 쓴다. 깊은 복사가 아니라 "카운트만 증가하는 가벼운 연산"임을 코드에서 분명히 드러내기 위한 Rust 커뮤니티의 관례다.

핵심 차이는 두 가지다. 첫째, Rc는 단일 스레드 전용이고 스레드 간 공유에는 원자적 카운트를 쓰는 Arc<T>를 별도로 선택한다 — 비용과 안전성을 타입으로 구분한다. 둘째, Rc<T>가 주는 것은 불변 공유뿐이다. Rc를 통해서는 안쪽 값을 바꿀 수 없다. 여기서 RefCell이 필요해진다.

RefCell<T> — 내부 가변성

Rust의 빌림 규칙은 "불변 참조는 여럿, 가변 참조는 하나, 둘은 동시에 안 됨"을 컴파일 타임에 강제한다. 그런데 어떤 설계에서는 불변으로 보이는 값의 안쪽만 바꾸고 싶다. RefCell<T>는 이 빌림 검사를 컴파일 타임이 아니라 런타임으로 미룬다. 이를 내부 가변성(interior mutability)이라 한다.

borrow()는 불변 빌림을, borrow_mut()는 가변 빌림을 런타임에 요청한다. 규칙을 어기면 컴파일은 통과하지만 실행 중에 패닉이 난다.

use std::cell::RefCell;

fn main() {
    // value 자체는 불변(let)이지만 안쪽은 바꿀 수 있다
    let value = RefCell::new(5);

    // 가변 빌림을 얻어 안쪽 값을 수정한다
    *value.borrow_mut() += 10;

    // 불변 빌림으로 읽는다
    println!("value = {}", value.borrow()); // value = 15
}

다음은 빌림 규칙을 런타임에 어긴 예다. 가변 빌림이 살아 있는 동안 또 가변 빌림을 시도하면 패닉한다. 이런 코드는 작성하면 안 되지만, RefCell이 무엇을 검사하는지 보여 준다.

use std::cell::RefCell;

fn main() {
    let data = RefCell::new(vec![1, 2, 3]);

    // 가변 빌림을 변수로 잡아 둔다
    let mut first = data.borrow_mut();
    first.push(4);

    // first가 살아 있는 동안의 추가 빌림은 런타임 패닉을 부른다.
    // let second = data.borrow_mut(); // 실행 시 panic: already borrowed

    // first를 명시적으로 드롭하면 그 다음 빌림은 안전하다
    drop(first);
    println!("{:?}", data.borrow()); // [1, 2, 3, 4]
}
RefCell은 검사를 없애지 않는다 — 미룰 뿐이다 같은 빌림 규칙이 그대로 적용된다. 다만 위반을 컴파일 에러 대신 런타임 패닉으로 잡는다. 그만큼 안전망이 약해지므로, 컴파일 타임 빌림으로 풀 수 있으면 그쪽을 먼저 쓰고 RefCell은 꼭 필요한 곳에만 둔다.
C++ 대조 — RefCell에 직접 대응물은 없다 C++에는 빌림 규칙을 런타임에 강제하는 표준 타입이 없다. const 객체의 일부 멤버만 변경하려면 mutable 키워드를 쓰지만, 이는 동시 접근을 검사하지 않는다. RefCell의 진짜 가치는 "공유된 데이터를 안전하게 변경하되, 동시 가변 접근 같은 실수를 런타임에 확실히 잡아 준다"는 데 있다. C++에서 const를 우회해 값을 바꾸다 발생하던 미정의 동작 부류를, Rust는 명확한 패닉으로 바꿔 놓는다.

Rc<RefCell<T>> 패턴

이제 두 요구를 합친다 — 여러 곳에서 공유하면서, 그 값을 변경하고 싶다. Rc<T>는 공유를 주지만 불변이고, RefCell<T>는 변경을 주지만 공유가 안 된다. 둘을 겹친 Rc<RefCell<T>>가 단일 스레드에서 "공유되면서 변경 가능한" 데이터를 만드는 관용 패턴이다.

use std::cell::RefCell;
use std::rc::Rc;

fn main() {
    // 공유 가능(Rc)하면서 변경 가능(RefCell)한 카운터
    let shared = Rc::new(RefCell::new(0));

    // 같은 값을 가리키는 두 핸들을 만든다 (데이터 복사 아님)
    let owner_a = Rc::clone(&shared);
    let owner_b = Rc::clone(&shared);

    // 각 소유자가 안쪽 값을 변경한다
    *owner_a.borrow_mut() += 5;
    *owner_b.borrow_mut() += 7;

    // 셋 다 같은 데이터를 가리키므로 결과가 공유된다
    println!("value = {}", shared.borrow()); // value = 12
    println!("ref count = {}", Rc::strong_count(&shared)); // 3
}

읽는 순서는 안에서 바깥이다. RefCell<i32>로 "이 정수는 런타임 빌림으로 변경 가능"하게 만들고, 그것을 Rc<...>로 감싸 "여러 소유자가 공유"하게 한다. borrow_mut()로 얻은 가변 빌림은 한 문장 안에서 즉시 쓰고 끝나므로, 위 코드에서는 빌림이 겹치지 않아 패닉이 없다.

조합으로 의미를 만든다 Rust 표준 라이브러리는 "공유되며 변경 가능한 포인터" 같은 거대한 단일 타입을 주는 대신, 작은 빌딩 블록을 조합하게 한다. 단일 스레드면 Rc<RefCell<T>>, 멀티스레드면 Arc<Mutex<T>>처럼 필요한 보장만큼만 비용을 치른다. 조합 순서(Rc가 바깥, RefCell이 안)에 따라 가능한 동작이 달라지니, "무엇을 공유하고 무엇을 변경하는가"를 기준으로 층을 정한다.
순환 참조 주의 Rc<RefCell<T>>로 서로를 가리키는 구조(부모↔자식 등)를 만들면 참조 카운트가 0으로 떨어지지 않아 메모리가 누수될 수 있다. 한쪽 방향을 카운트를 올리지 않는 Weak<T>로 두어 순환을 끊는다 — C++에서 shared_ptr 순환을 weak_ptr로 끊는 것과 같은 발상이다.

정리와 선택 기준

세 스마트 포인터는 경쟁이 아니라 서로 다른 축을 책임진다. 무엇이 필요한지로 고른다.

타입해결하는 문제소유가변성검사 시점
Box<T>힙 할당, 재귀 타입, 트레이트 객체단일일반 규칙컴파일 타임
Rc<T>단일 스레드 공유 소유다중불변컴파일 타임
RefCell<T>불변 참조 뒤의 내부 가변성단일가변(내부)런타임
Rc<RefCell<T>>공유되며 변경 가능다중가변(내부)런타임
  • 한 문장 요약 — 힙이 필요하면 Box, 공유가 필요하면 Rc, 불변 뒤의 변경이 필요하면 RefCell, 둘 다면 Rc<RefCell<T>>다.
  • C++ 대응 — Box≈unique_ptr, Rc≈단일 스레드용 shared_ptr, Arc≈스레드 안전 shared_ptr. RefCell은 직접 대응물이 없는 Rust 고유의 런타임 빌림 검사다.
  • 먼저 컴파일 타임으로 — 런타임 검사(RefCell)는 안전망이 약하다. 일반 빌림이나 Box로 풀 수 있으면 그쪽을 먼저 쓴다.
  • 멀티스레드는 다른 타입으로 — Rc·RefCell은 단일 스레드 전용이다. 스레드 간에는 Arc·Mutex/RwLock을 쓴다.
