커널이 느린 두 가지 원인

커널이 느릴 때 원인은 크게 둘 중 하나다. 계산할 일이 너무 많아서 연산 장치가 바쁜 경우, 아니면 계산은 금방 끝나는데 데이터를 메모리에서 가져오고 내보내느라 기다리는 경우다. 앞의 것을 compute-bound, 뒤의 것을 memory-bound라고 부른다.

구분병목고치는 방향
compute-bound산술 연산 장치 (FP32, Tensor Core)연산 수 줄이기, 더 빠른 명령(Tensor Core, 낮은 정밀도), 분기 줄이기
memory-boundglobal memory 대역폭읽고 쓰는 바이트 수 줄이기, 접근 패턴 개선, 커널 합치기

어느 쪽인지 모르고 최적화하면 헛수고가 된다. memory-bound 커널의 곱셈을 아무리 줄여도 빨라지지 않는다. 영상 처리 커널은 대부분 memory-bound다. 픽셀 하나를 읽어 몇 번 계산하고 쓰는 일이 대부분이기 때문이다. 이 판단을 숫자로 하게 해 주는 도구가 Roofline 모델이다.

산술 강도 - 바이트당 연산 수

Roofline 모델의 핵심 값은 산술 강도(arithmetic intensity)다. 메모리에서 1바이트를 옮길 때마다 연산을 몇 번 하는지를 나타낸다.

산술 강도 = 연산 수(FLOP) ÷ 메모리 이동량(byte) 값이 크면 데이터 하나로 계산을 많이 하는 커널(compute 쪽), 작으면 데이터를 옮기기만 하고 계산은 거의 없는 커널(memory 쪽)이다.

영상 처리에서 흔한 커널로 직접 계산해 보면 다음과 같다. float 영상 기준이고, 캐시 재사용이 완벽하다고 가정해 이웃 픽셀을 한 번만 읽는 것으로 센다.

커널픽셀당 연산픽셀당 이동량산술 강도
두 영상 더하기 c = a + b1 FLOP읽기 8 + 쓰기 4 = 12 B약 0.08

Roofline 그림 읽기

GPU가 낼 수 있는 성능에는 두 개의 천장이 있다. 연산 장치의 최대 속도(수평선)와, 메모리 대역폭 × 산술 강도(기울어진 선)다. 실제로 낼 수 있는 성능은 둘 중 낮은 쪽이다. 두 선을 그리면 지붕 모양이 되어 Roofline이라는 이름이 붙었다.

Roofline 모델. 능선보다 왼쪽에 있는 커널은 메모리 대역폭이 한계를 정하고, 오른쪽에 있는 커널은 연산 속도가 한계를 정한다

두 선이 만나는 점을 능선(ridge point)이라고 하며, 그 위치는 "최대 연산 성능 ÷ 메모리 대역폭"이다. 예를 들어 FP32 30 TFLOPS, 메모리 900 GB/s인 GPU라면 능선은 약 33 FLOP/byte다. 산술 강도가 33보다 작은 커널은 아무리 연산을 최적화해도 메모리 속도를 넘을 수 없다. 위 표의 영상 처리 커널은 9×9 컨볼루션까지도 모두 능선 왼쪽, 즉 memory-bound다.

내 GPU의 능선 구하기 최대 FP32 성능은 "SM 수 × SM당 FP32 코어 수 × 2(FMA) × 클럭"으로, 메모리 대역폭은 "메모리 클럭 × 버스 폭 × 2(DDR) ÷ 8"로 계산하거나 제조사 사양표의 값을 쓴다. 정확한 값보다 자릿수가 중요하다. 대부분의 최신 GPU는 능선이 수십 FLOP/byte 정도다.

내 커널의 위치 측정

계산으로 짐작한 위치가 맞는지는 Nsight Compute(8편)로 확인한다. Roofline 차트 섹션을 켜면 커널이 그림의 어디에 찍히는지 바로 보여 준다.

# roofline chart + speed-of-light summary for one kernel
ncu --section SpeedOfLight --section SpeedOfLight_RooflineChart -k Blur3x3 ./my_app

# or everything (slow)
ncu --set full -k Blur3x3 -o blur_report ./my_app

Compute (SM) Throughput (%)연산 장치를 얼마나 바쁘게 쓰는가
둘 다 낮음 (예: 30% 미만)어느 한계에도 닿지 못한 상태. 점유율 부족, 동기화 대기, 실행 비용(17편)을 의심

코드 안에서 직접 재는 방법도 있다. memory-bound 커널은 유효 대역폭(실제로 옮긴 바이트 ÷ 걸린 시간)을 계산해 GPU 최대 대역폭과 비교하면 된다.

cudaEventRecord(t0, s);
AddImages<<<grid, block, 0, s>>>(d_a, d_b, d_c, n);
cudaEventRecord(t1, s);
cudaEventSynchronize(t1);

float ms = 0;
cudaEventElapsedTime(&ms, t0, t1);
double bytes = 3.0 * n * sizeof(float);            // read a, read b, write c
double gbps  = bytes / (ms * 1e-3) / 1e9;
printf("effective bandwidth %.1f GB/s\n", gbps);   // compare with the device peak

memory-bound 커널을 빠르게 하는 법

memory-bound 커널의 실행 시간은 거의 "옮기는 바이트 수 ÷ 대역폭"이다. 대역폭은 정해져 있으므로 할 수 있는 일은 옮기는 바이트를 줄이거나, 대역폭을 끝까지 쓰는 것뿐이다.

방법효과관련 편
메모리 결합(coalescing) 맞추기같은 바이트를 옮겨도 실제 트랜잭션 수가 줄어 대역폭을 끝까지 씀7편
벡터 로드 (float4, uchar4)명령 수가 줄고 한 번에 큰 단위로 읽음7편
작은 데이터 형식float 대신 8비트, 16비트로 저장하면 이동량이 1/4, 1/223편
shared memory 타일이웃 픽셀을 여러 번 읽는 대신 한 번 읽어 공유6편
커널 융합중간 결과를 global memory에 쓰고 다시 읽는 왕복을 없앰이 글

이 중 영상 처리 파이프라인에서 효과가 가장 큰 경우가 많은 것이 커널 융합이다.

커널 융합 - 원소별 연산 합치기

전처리 파이프라인이 "정규화 → 감마 보정 → 임계값 이진화" 세 단계라고 하자. 단계마다 커널을 하나씩 만들면 코드는 깔끔하지만, 각 커널이 영상 전체를 읽고 쓴다.

// three separate kernels: 3 reads + 3 writes of the whole image
__global__ void Normalize(const uint8_t* in, float* out, int n, float scale)
{ int i = blockIdx.x * blockDim.x + threadIdx.x; if (i < n) out[i] = in[i] * scale; }

__global__ void Gamma(const float* in, float* out, int n, float g)
{ int i = blockIdx.x * blockDim.x + threadIdx.x; if (i < n) out[i] = __powf(in[i], g); }

__global__ void Threshold(const float* in, uint8_t* out, int n, float th)
{ int i = blockIdx.x * blockDim.x + threadIdx.x; if (i < n) out[i] = in[i] > th ? 255 : 0; }

// fused: 1 read (uint8) + 1 write (uint8); intermediates stay in registers
__global__ void PreprocessFused(const uint8_t* in, uint8_t* out, int n,
                                float scale, float g, float th)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n)
    {
        float v = in[i] * scale;
        v = __powf(v, g);
        out[i] = v > th ? 255 : 0;
    }
}
방식픽셀당 global memory 이동500만 화소 영상 기준
커널 3개1 + 4 + 4 + 4 + 4 + 1 = 18 B약 90 MB
융합 커널 1개1 + 1 = 2 B약 10 MB

이동량이 9분의 1로 줄었다. memory-bound 커널이므로 실행 시간도 거의 그 비율로 줄고, 커널 실행 횟수도 3번에서 1번이 되어 실행 비용(17편)까지 준다. 중간 float 버퍼 두 개도 필요 없어져 GPU 메모리도 아낀다.

융합을 유지하면서 코드를 나누는 법

모든 단계를 커널 하나에 몰아 쓰면 재사용이 어렵다. 단계를 __device__ 함수(또는 함수 객체)로 만들고, 템플릿으로 조합하면 단계별 코드는 나눠 두면서 실행은 한 커널로 할 수 있다.

struct NormalizeOp { float scale; __device__ float operator()(float v) const { return v * scale; } };
struct GammaOp     { float g;     __device__ float operator()(float v) const { return __powf(v, g); } };
struct ThresholdOp { float th;    __device__ float operator()(float v) const { return v > th ? 255.f : 0.f; } };

// apply any chain of ops in one pass
template <typename Op1, typename Op2, typename Op3>
__global__ void Pointwise3(const uint8_t* in, uint8_t* out, int n, Op1 a, Op2 b, Op3 c)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = (uint8_t)c(b(a((float)in[i])));
}

Pointwise3<<<grid, block, 0, s>>>(d_in, d_out, n,
                                  NormalizeOp{1.f / 255.f}, GammaOp{0.8f}, ThresholdOp{0.5f});

컴파일러가 함수 객체 호출을 모두 인라인하므로, 손으로 합친 커널과 같은 코드가 나온다. Thrust의 transform_iterator(18편)도 같은 원리로 융합을 해 준다.

이웃 픽셀을 쓰는 단계의 융합

원소별 연산끼리는 쉽게 합쳐진다. 문제는 블러처럼 이웃 픽셀이 필요한 단계(스텐실)가 끼어 있을 때다. "정규화 → 3×3 블러 → 이진화"를 합치려면, 블러가 읽는 이웃 픽셀도 정규화된 값이어야 한다.

방법은 6편의 shared memory 타일에 정규화를 끼워 넣는 것이다. 타일을 global memory에서 읽어 올 때 바로 정규화해서 shared memory에 넣고, 블러는 shared memory에서 계산한 뒤, 이진화까지 해서 한 번만 쓴다.

#define TILE 16
#define R 1                                     // 3x3 blur radius

__global__ void NormBlurThreshold(const uint8_t* in, uint8_t* out, int w, int h,
                                  float scale, float th)
{
    __shared__ float tile[TILE + 2 * R][TILE + 2 * R];

    int x0 = blockIdx.x * TILE - R, y0 = blockIdx.y * TILE - R;
    // 1) load tile + halo, NORMALIZING on the way in (clamp at image borders)
    for (int ty = threadIdx.y; ty < TILE + 2 * R; ty += blockDim.y)
        for (int tx = threadIdx.x; tx < TILE + 2 * R; tx += blockDim.x)
        {
            int gx = min(max(x0 + tx, 0), w - 1);
            int gy = min(max(y0 + ty, 0), h - 1);
            tile[ty][tx] = in[gy * w + gx] * scale;
        }
    __syncthreads();

    // 2) blur from shared memory, 3) threshold, single write
    int x = blockIdx.x * TILE + threadIdx.x, y = blockIdx.y * TILE + threadIdx.y;
    if (x < w && y < h)
    {
        float s = 0.f;
        for (int dy = 0; dy <= 2 * R; ++dy)
            for (int dx = 0; dx <= 2 * R; ++dx)
                s += tile[threadIdx.y + dy][threadIdx.x + dx];
        out[y * w + x] = (s / 9.f) > th ? 255 : 0;
    }
}

dim3 block(TILE, TILE), grid((w + TILE - 1) / TILE, (h + TILE - 1) / TILE);
스텐실 두 개를 연달아 합칠 때 블러 뒤에 또 블러(또는 모폴로지)가 오면, 두 번째 단계가 필요한 halo가 첫 단계의 halo만큼 더 넓어진다. 타일 가장자리 픽셀은 이웃 블록과 중복 계산해야 해서, 합칠수록 중복 계산과 shared memory 사용량이 늘어난다. 보통 스텐실 한두 단계까지만 합치고, 그 이상은 커널을 나누는 편이 낫다.

흔한 함정

memory-bound 커널의 연산 최적화 나눗셈을 곱셈으로 바꾸고, 함수 호출을 줄여도 memory-bound 커널은 거의 빨라지지 않는다. 먼저 Roofline 위치를 확인하고, 그에 맞는 쪽을 고친다.
대역폭 계산에서 캐시 재사용 무시 3×3 블러를 "픽셀마다 9개 읽음"으로 계산하면 이동량을 크게 부풀려, 실제보다 대역폭을 많이 쓰는 것처럼 보인다. 이웃 픽셀은 캐시나 shared memory에서 재사용되므로 실제 global memory 이동량은 입력 1회, 출력 1회에 가깝다.
융합 후 결과 비교 합친 커널은 중간 값을 float 레지스터에 둔 채 다음 단계로 넘긴다. 단계별 커널이 중간에 8비트로 저장했다면 반올림 위치가 달라져 결과가 1 정도 다를 수 있다. 기준 결과와 비교할 때 이 차이를 허용 범위에 넣는다(23편).
