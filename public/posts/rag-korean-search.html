왜 검색이 필요한가

RAG(Retrieval-Augmented Generation)는 이름 그대로 검색으로 찾은 문서를 근거로 삼아 생성하는 방식이다. 여기서 흔히 뒤의 "생성"에만 눈이 가지만, 실제 품질을 좌우하는 건 앞의 "검색"이다.

문서가 방대한 환경 — 이를테면 하루에도 수만 건 규모로 문서가 쌓이는 곳 — 에서는 전체를 매번 모델의 컨텍스트에 통째로 넣는 방식이 성립하지 않는다. 컨텍스트 윈도우에 물리적으로 안 들어갈 뿐 아니라, 들어간다 해도 토큰 비용이 크고 관련 없는 문서가 신호를 흐린다. 그래서 질문에 관련된 소수의 문서만 골라 넣는 검색 시스템이 앞단에 필요하다.

이 글은 그 검색 시스템을 한국어 문서에 맞게 설계하는 관점을 정리한다. 핵심 순서는 하나다 — 좋은 검색기를 먼저 세우고, 그 결과만 AI가 참고하게 한다.

검색 프레임워크와 BM25

대량 문서 검색의 표준 도구는 역색인(inverted index) 기반 검색 엔진이다. 대표적으로 Elasticsearch나 OpenSearch가 있다. 역색인은 "어떤 단어가 어떤 문서에 들어 있는가"를 미리 뒤집어 색인해 두는 자료구조라, 수만~수억 건 규모에서도 키워드 검색이 빠르다.

BM25 — 키워드 검색의 표준 스코어링

Elasticsearch·OpenSearch가 검색 결과의 순위를 매길 때 기본으로 쓰는 알고리즘이 BM25다. 질의어가 문서에 얼마나 자주 나오는지(단어 빈도), 그 단어가 전체 문서에서 얼마나 희귀한지(문서 빈도의 역수), 문서 길이 보정을 종합해 관련도 점수를 낸다. 이런 방식의 키워드 검색을 sparse(희소) 검색이라 부른다 — 단어 단위의 일치를 본다는 뜻이다.

BM25는 별도 학습이 필요 없고, 질의어가 문서에 실제로 등장하는지를 직접 보기 때문에 정확한 용어 매칭에 강하다. 제품 코드·오류 메시지·고유명사처럼 표기가 정확히 일치해야 하는 검색에서 특히 잘 맞는다.

한국어 토크나이저가 핵심

키워드 검색은 문서와 질의를 토큰(token)으로 잘라 비교한다. 그래서 "어떻게 자르느냐"가 검색 품질을 직접 좌우한다. 그리고 이 지점이 한국어에서 가장 중요하다.

영어의 공백 분리 vs 한국어의 형태소

영어는 단어 사이가 공백으로 나뉘어, 공백만 기준으로 잘라도 대체로 토큰이 맞다. 반면 한국어는 조사·어미가 명사·어간에 붙는 교착어라 공백 기준으로는 제대로 잘리지 않는다. 예를 들어 "검색기를", "검색기가", "검색기로"는 표면 형태가 모두 달라, 공백 기준 토큰화로는 "검색기"라는 같은 핵심어를 하나로 묶지 못한다.

그래서 한국어에는 형태소 분석기(morphological analyzer)를 토크나이저로 쓴다. 형태소 단위로 잘라 "검색기 + 를", "검색기 + 가"처럼 어근과 조사를 분리하면, 세 표현이 모두 "검색기"로 색인돼 하나로 검색된다.

nori와 Kiwi

Elasticsearch·OpenSearch 환경에서 한국어 형태소 분석에 널리 쓰이는 선택지가 있다.

  • nori — Elasticsearch·OpenSearch에 공식 플러그인으로 제공되는 한국어 형태소 분석기다. 엔진에 바로 붙는다는 점에서 도입 문턱이 낮아, 공식 문서에서 한국어 분석기로 안내된다.
  • Kiwi — 별도의 한국어 형태소 분석기로, Elasticsearch·OpenSearch용 연동(analyzer 이름 예: ko_kiwi)도 제공된다. 분석 방식·사전 구성이 nori와 달라 결과가 다를 수 있다.

둘 중 무엇이 항상 낫다고 단정하긴 어렵다. 문서 도메인·용어 특성에 따라 결과가 갈리므로, 실제 문서로 검색 품질을 비교해 고르는 것이 맞다. 분명한 건, 토크나이저 선택이 한국어 검색 품질을 좌우하는 첫 번째 변수라는 점이다.

설정 스니펫 — nori analyzer

Elasticsearch 인덱스에 nori 분석기를 지정하는 형태는 대략 아래와 같다. 필드에 이 analyzer를 걸면 색인·검색 시 같은 방식으로 토큰화된다.

# nori 플러그인 설치 후 인덱스 생성 시 analyzer 지정

  "settings": {
    "analysis": {
      "analyzer": {
        "korean": {
          "type": "custom",

  },
  "mappings": {

    }
  }

설정 문법은 버전을 탄다 플러그인 설치 방식, analyzer/tokenizer 옵션 이름, 필드 매핑 문법은 엔진 버전에 따라 달라진다. 위 예시는 구조를 보여 주기 위한 뼈대이므로, 실제 적용 전에 사용하는 버전의 공식 문서에서 정확한 옵션을 확인한다.

하이브리드 검색과 RRF

BM25(키워드) 검색은 정확한 용어 매칭엔 강하지만, 표현이 다른데 의미가 같은 경우("자동차" ↔ "승용차")를 놓치기 쉽다. 반대로 임베딩(embedding) 기반 검색은 문장을 벡터로 바꿔 의미 유사도로 찾으므로 표현이 달라도 잡아내지만, 정확히 일치해야 하는 고유명사·코드에는 오히려 약할 수 있다. 이런 벡터 방식을 dense(밀집) 검색이라 한다.

sparse vs dense

구분BM25 (sparse)임베딩 (dense)
찾는 방식단어 단위 일치(역색인)의미 벡터의 유사도
강점정확한 용어·고유명사·코드 매칭표현이 달라도 의미로 매칭
약점동의어·의미 유사 표현에 약함정확한 표기 일치에 약할 수 있음
사전 준비토크나이저(한국어는 형태소)임베딩 모델로 벡터화
한국어 유의점형태소 분석기 선택이 결정적한국어에 맞는 임베딩 모델 필요

둘을 합치는 RRF

둘은 서로의 약점을 메운다. 그래서 2026년 시점의 실무 표준은 하이브리드 검색이다 — BM25(sparse)와 임베딩(dense)을 함께 돌리고, 각 결과 목록을 하나로 합친다. 합칠 때 널리 쓰이는 방법이 RRF(Reciprocal Rank Fusion)다.

RRF는 두 검색 결과의 점수 척도를 직접 비교하지 않고 각 목록에서의 순위(rank)만 이용한다. 각 문서에 대해 목록별 순위의 역수를 더해 최종 점수를 매기는 방식이라, 서로 스케일이 다른 BM25 점수와 벡터 유사도를 무리 없이 통합한다. 결과적으로 키워드의 정확성과 의미의 유사성을 동시에 반영한 순위가 나온다.

# RRF 점수: 문서 d가 각 검색 결과에서 가진 순위 r의 역수 합
# k는 순위 편차를 완충하는 상수(구현마다 기본값이 있음)
score(d) = sum over each result list:  1 / (k + rank(d))

# 예 — 어떤 문서가 BM25에서 2위, 벡터 검색에서 5위라면
#   1/(k+2) + 1/(k+5) 로 합산해 최종 순위를 매긴다
BM25만으로 시작해도 된다 하이브리드가 표준이라고 처음부터 임베딩 파이프라인까지 다 세울 필요는 없다. 한국어 문서라면 먼저 형태소 토크나이저 + BM25로 검색 품질의 바닥을 확보하고, 동의어·의미 검색이 부족하다고 느낄 때 dense를 더해 RRF로 합치는 순서가 현실적이다. 검색 개선의 대부분은 토크나이저를 제대로 맞추는 데서 나온다.

Agent 연계와 지식 연결

검색기가 준비되면, AI 연계의 핵심 원칙은 단순하다 — 검색기를 먼저 돌려 관련 문서를 찾고, 그 결과만 Agent가 참고하게 한다. 전체 문서를 넣지 않고, 질문마다 검색으로 좁힌 소수의 문서만 근거로 준다. 이것이 RAG의 실제 동작 방식이다.

Agent에 주는 지시 예시

검색기를 도구로 붙였다면, Agent에게는 "검색기를 먼저 쓰라"는 방향을 지시로 못 박아 둔다. 예를 들면 이런 식이다.

# Agent 지시 예시
질문에 답하기 전에, 한국어 토크나이저를 사용한 BM25 기반
검색기로 관련 문서를 먼저 찾아 참고해줘.
검색된 문서에 근거가 없으면 모른다고 답하고,
근거 문서의 출처를 함께 밝혀줘.

이렇게 하면 Agent는 답을 지어내기 전에 검색을 먼저 돌리고, 검색된 문서라는 확인 가능한 근거 위에서만 답하게 된다. 근거 출처를 함께 밝히게 두면 사람이 검증하기도 쉬워진다.

(선택) 문서 간 관계를 잇는 지식 연결

문서가 서로 참조하거나 상하 관계로 얽혀 있는 대규모 환경에서는, 개별 문서를 따로 검색하는 것만으로는 부족할 때가 있다. 이런 경우 문서·개념 사이의 관계를 그래프나 온톨로지로 관리해, "이 문서와 연결된 문서까지" 함께 가져오는 접근을 쓰기도 한다. 이른바 대규모 지식 연결이다.

다만 이는 도입·유지 비용이 큰 선택지다. 대부분의 경우는 앞서 다룬 형태소 토크나이저 + 하이브리드 검색으로 충분하며, 관계 기반 탐색이 실제로 필요하다고 확인된 뒤에 지식 그래프를 얹는 순서가 안전하다.

정리와 주의

  • 문제의 본질 — 방대한 문서를 매번 통째로 넣을 수 없으므로, 질문에 관련된 문서만 골라 넣는 검색이 RAG의 앞단으로 필요하다.
  • 기반 — 역색인 기반 엔진(Elasticsearch·OpenSearch)과 그 기본 스코어링인 BM25가 키워드(sparse) 검색의 표준이다.
  • 한국어의 핵심 — 형태소 토크나이저(nori·Kiwi) 선택이 검색 품질을 좌우한다. 여기에 가장 먼저 투자한다.
  • 2026년 표준 — BM25(sparse) + 임베딩(dense)을 RRF로 합치는 하이브리드가 표준이다. 다만 BM25부터 시작해도 된다.
  • 연계 원칙 — 검색을 먼저 돌려 관련 문서만 Agent에 근거로 준다. 세부 문법·플러그인 사양은 버전에 따라 바뀌니 공식 문서로 확인한다.
