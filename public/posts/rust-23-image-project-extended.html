번외편 — 이미지 처리 프로젝트 확장

2026-08-03 약 12분 분량 Rust 시리즈
이 편에서 하는 것 22편(작은 프로젝트 — 이미지 처리 맛보기)에서 만든 그레이스케일 변환기를 확장한다. 지난 편 끝에 남겨 둔 숙제 — 필터 추가, 에러 처리 다듬기, 테스트 작성 — 를 실제로 해 보고, 여기에 rayon으로 픽셀 루프를 병렬화하는 것까지 더한다. 22편을 먼저 읽었다면 자연스럽게 이어지고, 안 읽었어도 각 절이 독립적으로 읽히도록 썼다.

왜 확장하나

22편은 "끝까지 도는 작은 프로그램 하나"를 목표로 일부러 짧게 끝냈다. expect로 에러를 단순화했고, 필터는 그레이스케일 하나뿐이었고, 테스트도 없었다. 실무 도구로 다듬으려면 딱 그 세 가지를 손봐야 한다. 이번 편은 그 작업을 그대로 따라가며, 마지막에는 시리즈에서 다루지 않았던 병렬 처리까지 살짝 맛본다.

기준이 되는 22편의 to_grayscale 함수를 그대로 가져온다 — 입력을 &RgbImage로 빌리고, 새 GrayImage를 소유권째 반환하는 패턴이다. 이번에 추가하는 필터들도 전부 이 패턴을 그대로 따른다.

필터 모음 만들기

그레이스케일 버퍼(GrayImage)를 입력으로 받아 새 버퍼를 돌려주는 필터 세 개를 추가한다. 반전, 밝기 조절, 임계값 이진화다. 셋 다 픽셀 하나에만 의존하는 점 연산(point operation)이라 구조가 거의 같다.

use image::{GrayImage, Luma};

// 반전 — 255에서 빼면 밝고 어두움이 뒤집힌다.
fn invert(src: &GrayImage) -> GrayImage {
    let (width, height) = src.dimensions();
    let mut out = GrayImage::new(width, height);
    for y in 0..height {
        for x in 0..width {
            let v = src.get_pixel(x, y).0[0];
            out.put_pixel(x, y, Luma([255 - v]));
        }
    }
    out
}

// 밝기 조절 — offset을 더하되 0~255를 벗어나지 않게 saturating 연산을 쓴다.
fn adjust_brightness(src: &GrayImage, offset: i16) -> GrayImage {
    let (width, height) = src.dimensions();
    let mut out = GrayImage::new(width, height);
    for y in 0..height {
        for x in 0..width {
            let v = src.get_pixel(x, y).0[0] as i16;
            let adjusted = (v + offset).clamp(0, 255) as u8;
            out.put_pixel(x, y, Luma([adjusted]));
        }
    }
    out
}

// 임계값 이진화 — cutoff 이상이면 흰색, 아니면 검은색.
fn threshold(src: &GrayImage, cutoff: u8) -> GrayImage {
    let (width, height) = src.dimensions();
    let mut out = GrayImage::new(width, height);
    for y in 0..height {
        for x in 0..width {
            let v = src.get_pixel(x, y).0[0];
            let bin = if v >= cutoff { 255 } else { 0 };
            out.put_pixel(x, y, Luma([bin]));
        }
    }
    out
}

adjust_brightness에서 u8 대신 i16으로 올려 계산한 점이 핵심이다. u8끼리 더하면 255를 넘을 때 패닉(디버그 빌드) 또는 랩어라운드(릴리즈 빌드)가 나므로, 넉넉한 타입으로 계산하고 clamp로 범위를 강제한 뒤 u8로 되돌린다.

C++ 대조 — 오버플로 처리 C++에서 uchar 연산의 오버플로는 조용히 랩어라운드된다(정의된 동작이지만 원하는 결과는 아닐 때가 많다). OpenCV의 cv::saturate_cast<uchar>가 이 문제를 감춰 준다. Rust는 그 역할을 as 캐스팅과 clamp를 조합해 직접 명시한다 — 자동으로 안전해지진 않지만, 어디서 값이 잘릴 수 있는지 코드에 그대로 드러난다.

에러 처리 다듬기

22편은 expect로 실패 시 그냥 패닉하게 두었다. 도구답게 다듬으려면 main이 Result를 반환하게 하고, 실패를 값으로 전파해야 한다. 12편(에러 처리 심화)에서 다룬 ?가 여기서 실전으로 쓰인다.

use image::{ImageReader, GrayImage};
use std::error::Error;

fn main() -> Result<(), Box<dyn Error>> {
    // 각 단계가 실패하면 즉시 함수를 빠져나가며 에러를 위로 전달한다.
    let img = ImageReader::open("input.png")?.decode()?;
    let rgb = img.to_rgb8();

    let gray = to_grayscale(&rgb);       // 22편 함수
    let inverted = invert(&gray);
    let bin = threshold(&gray, 128);

    gray.save("out_gray.png")?;
    inverted.save("out_invert.png")?;
    bin.save("out_threshold.png")?;

    println!("3개 파일을 저장했다");
    Ok(())
}

Box<dyn Error>는 "Error 트레이트를 구현한 아무 타입이나"를 뜻하는 트레이트 객체다. image의 디코딩 에러, 파일 I/O 에러처럼 서로 다른 에러 타입이 섞여도 ? 한 줄로 처리할 수 있다. 다만 호출자 입장에서 "정확히 어떤 에러였는지" 구분하기는 어렵다.

더 다듬고 싶다면 에러 종류를 구분해서 다뤄야 하는 라이브러리 코드라면 12편에서 본 thiserror로 직접 에러 타입(예: enum ImgToolError { Io(...), Decode(...) })을 정의하는 편이 낫다. 반대로 최종 실행 파일이라 "실패하면 메시지 찍고 끝"이면 anyhow::Result가 Box<dyn Error>보다 에러 메시지 출력이 편하다. 지금 예제 같은 작은 CLI 도구에는 Box<dyn Error> 정도로 충분하다.

테스트 작성

필터를 &GrayImage -> GrayImage 순수 함수로 뽑아 둔 덕분에, 파일 I/O 없이 작은 이미지를 코드로 만들어 테스트할 수 있다. Rust는 #[test] 속성과 cargo test만으로 별도 프레임워크 없이 테스트가 된다.

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn invert_flips_extremes() {
        let mut img = GrayImage::new(2, 1);
        img.put_pixel(0, 0, Luma([0]));
        img.put_pixel(1, 0, Luma([255]));

        let result = invert(&img);

        assert_eq!(result.get_pixel(0, 0).0[0], 255);
        assert_eq!(result.get_pixel(1, 0).0[0], 0);
    }

    #[test]
    fn threshold_splits_at_cutoff() {
        let mut img = GrayImage::new(2, 1);
        img.put_pixel(0, 0, Luma([100]));
        img.put_pixel(1, 0, Luma([200]));

        let result = threshold(&img, 128);

        assert_eq!(result.get_pixel(0, 0).0[0], 0);   // 100 < 128
        assert_eq!(result.get_pixel(1, 0).0[0], 255);  // 200 >= 128
    }
}

mod tests를 같은 파일 안에 두고 use super::*;로 바깥 함수를 그대로 끌어다 쓰는 게 Rust의 관례다(13편에서 다룬 모듈 시스템의 연장선이다). cargo test를 실행하면 이 모듈의 테스트만 골라 컴파일·실행한다 — 릴리즈 바이너리에는 포함되지 않는다.

rayon으로 병렬화

지금까지의 필터는 픽셀마다 이전 픽셀과 무관하게 독립적으로 계산된다. 이렇게 작업 단위끼리 서로 의존이 없어 병렬화하기 쉬운 경우를 "embarrassingly parallel"이라고 부른다. 이런 작업은 rayon 크레이트로 스레드 풀에 그대로 뿌릴 수 있다. 16편(동시성)에서 다룬 Send/Sync가 여기서 컴파일러의 안전판 역할을 한다.

# Cargo.toml에 추가
cargo add rayon
use image::GrayImage;
use rayon::prelude::*;

// 원시 픽셀 버퍼(&[u8])를 순회하며 병렬로 매핑한다.
fn threshold_parallel(src: &GrayImage, cutoff: u8) -> GrayImage {
    let (width, height) = src.dimensions();

    let out_pixels: Vec<u8> = src
        .as_raw()                              // &Vec<u8> — 원시 그레이 버퍼
        .par_iter()                             // rayon의 병렬 이터레이터
        .map(|&v| if v >= cutoff { 255 } else { 0 })
        .collect();

    GrayImage::from_raw(width, height, out_pixels)
        .expect("입력과 같은 크기이므로 항상 성공한다")
}

바뀐 부분은 .iter()가 .par_iter()로 바뀐 게 전부다. rayon이 내부적으로 코어 수만큼 작업을 나눠 스레드 풀에서 처리하고 결과를 순서대로 모아 준다. 함수 시그니처와 호출부는 순차 버전과 동일하다 — threshold_parallel(&gray, 128)처럼 그대로 쓴다.

왜 이 예제가 안전한가 각 픽셀 계산이 다른 픽셀의 결과에 의존하지 않고(순수 함수), 클로저가 캡처하는 값(cutoff)도 Copy인 u8이라 데이터 경쟁 소지 자체가 없다. 만약 클로저가 여러 스레드에서 공유 가변 상태를 건드리려 하면, 그 타입이 Send/Sync를 만족하지 않는 한 컴파일이 거부된다. "일단 돌려보고 경쟁 조건을 디버거로 잡는" 대신 "컴파일러가 애초에 막는" 쪽이다.
C++ 대조 — 병렬 루프 C++에서 같은 걸 하려면 OpenMP #pragma omp parallel for나 std::for_each + std::execution::par를 쓴다. 문법은 비슷하게 간단하지만, 캡처한 변수가 스레드 안전한지는 개발자가 직접 보장해야 한다 — 실수로 공유 변수를 캡처해도 컴파일은 되고, 데이터 경쟁은 런타임에(운이 나쁘면 가끔씩만) 드러난다. rayon은 그 보장을 타입 시스템으로 옮겨 컴파일 타임에 확인한다.

마무리

22편의 작은 변환기가 이번 편을 거치며 필터 세 개, Result 기반 에러 처리, 테스트, 그리고 병렬화까지 갖췄다. 각 단계에서 바뀐 코드량은 크지 않았다는 점이 눈여겨볼 만하다 — 순수 함수로 필터를 뽑아 둔 22편의 설계가 테스트와 병렬화를 둘 다 거의 공짜로 만들어 줬다.

  • 더 해볼 것 — 커맨드라인 인자로 필터 종류·경로를 받고 싶다면 clap 크레이트가 표준적인 선택이다.
  • 더 해볼 것 — 이미지가 커지면 rayon 도입 전후로 std::time::Instant로 직접 시간을 재 보면 병렬화 효과를 체감할 수 있다.
  • 시리즈 전체를 돌아보면 — 입문부터 여기까지, 소유권·빌림이라는 하나의 규칙이 메모리 관리·동시성·에러 처리 전반에 반복해서 등장했다. 처음엔 제약처럼 느껴지던 규칙이, 이 번외편처럼 "그냥 바꿔도 안전하다"는 확신으로 돌아오는 경험이 Rust를 계속 쓰게 만드는 이유다.
