C++에는 형 변환 방법이 다섯 가지 있다. C에서 물려받은 (T)x 형태 하나와, 목적별로 나눈 C++ 캐스트 네 개(static_cast, dynamic_cast, const_cast, reinterpret_cast)다. 26편 MFC 글의 DYNAMIC_DOWNCAST와 RTTI도 이 중 하나와 연결된다. 이 글은 네 가지가 각각 무엇을 하는지, 언제 무엇을 골라야 하는지 정리한다.

C 스타일 캐스트의 문제

(T)x는 쓰기 편하지만, 컴파일러가 아래 순서로 되는 것 하나를 조용히 골라 적용한다.

순서시도하는 변환
1const_cast
2static_cast
3static_cast + const_cast
4reinterpret_cast
5reinterpret_cast + const_cast

그래서 같은 (T)x가 상황에 따라 안전한 숫자 변환이 되기도 하고, 메모리를 아무렇게나 다시 해석하는 위험한 변환이 되기도 한다. 코드만 봐서는 어느 쪽인지 알 수 없다. 헤더 하나를 빠뜨려 클래스 선언이 안 보이면, 원래 static_cast였던 변환이 경고 없이 reinterpret_cast로 바뀌는 일도 생긴다.

문제C++ 캐스트로 바꾸면
무슨 변환인지 코드에 안 드러남이름에 의도가 드러남
위험한 변환이 섞여도 컴파일 오류가 없음그 캐스트로 안 되는 변환은 컴파일 오류
코드에서 찾기 어려움 (괄호는 어디에나 있음)reinterpret_cast로 검색하면 위험한 곳이 모두 나옴

static_cast - 컴파일 시점에 정해지는 변환

가장 자주 쓰는 캐스트다. 컴파일러가 타입 관계를 알고 있는 "정상적인" 변환을 한다. 실행 중에 검사는 하지 않는다.

// 1) numbers
int   sum = 7, count = 2;
double avg = static_cast<double>(sum) / count;      // 3.5, not 3
int   px  = static_cast<int>(12.9f);                // 12 (truncation toward zero)
uint8_t v = static_cast<uint8_t>(300);              // 44: wraps, no clamping

// 2) enum <-> int
enum class PixelFormat { Mono8 = 0, Mono12 = 1 };
int code = static_cast<int>(PixelFormat::Mono12);   // 1
auto fmt = static_cast<PixelFormat>(code);

// 3) void* -> real type (callback user data)
void OnFrame(void* user)
{
    auto* self = static_cast<Inspector*>(user);
    self->Process();
}

// 4) up/down the class hierarchy WITHOUT a runtime check
Shape*  s = new Circle();
Circle* c = static_cast<Circle*>(s);                // ok only because s really is a Circle
쓰는 곳예
숫자 형식 사이 변환int ↔ double, float → uint8_t
enum ↔ 정수enum class 값을 정수로 저장하거나 읽을 때
void* → 원래 타입C 콜백의 사용자 데이터 포인터
부모 ↔ 자식 포인터 (검사 없음)실제 타입을 확실히 알 때만
explicit 생성자, 변환 연산자 호출static_cast<std::string>(path)
틀린 다운캐스트는 검사되지 않음 static_cast<Circle*>(s)에서 s가 실제로는 Rect라도 컴파일도 되고 실행 중 오류도 나지 않는다. 그 포인터로 Circle 멤버를 쓰는 순간 정의되지 않은 동작이 된다. 실제 타입이 확실하지 않으면 dynamic_cast를 쓴다.

dynamic_cast - 실행 중에 확인하는 변환

부모 포인터가 실제로 어떤 자식 객체를 가리키는지 실행 중에 확인하고 변환한다. 26편 MFC 글에서 본 RTTI(실행 중 타입 정보)를 사용하므로, 가상 함수가 하나 이상 있는 클래스(다형적 클래스)에서만 쓸 수 있다.

struct Shape  { virtual ~Shape() = default; };
struct Circle : Shape { double r = 1; };
struct Rect   : Shape { double w = 1, h = 1; };

void Describe(Shape* s)
{
    // pointer form: nullptr if s is not a Circle (or derived from Circle)
    if (auto* c = dynamic_cast<Circle*>(s))
        printf("circle r=%f\n", c->r);
    else if (auto* r = dynamic_cast<Rect*>(s))
        printf("rect %fx%f\n", r->w, r->h);
}

void MustBeCircle(Shape& s)
{
    // reference form: throws std::bad_cast on failure (a reference cannot be null)
    Circle& c = dynamic_cast<Circle&>(s);
}
형태실패하면
포인터 dynamic_cast<T*>(p)nullptr 반환
참조 dynamic_cast<T&>(r)std::bad_cast 예외
가상 함수가 없는 클래스에 사용컴파일 오류

dynamic_cast는 vtable 옆에 붙은 타입 정보를 따라 상속 관계를 확인한다. 동작 원리는 28편 vtable 글에서 다룬다. 비용은 상속 깊이와 구현에 따라 달라지지만, 일반 함수 호출보다 훨씬 비싸다.

dynamic_cast가 자주 보이면 설계를 다시 보기 if (dynamic_cast<A*>) ... else if (dynamic_cast<B*>) ...가 여러 곳에 있다면, 새 자식 클래스를 추가할 때마다 이 분기를 모두 고쳐야 한다. 타입마다 다른 동작은 가상 함수(s->Describe())로 옮기는 편이 낫다. dynamic_cast는 플러그인처럼 외부에서 들어온 객체가 추가 기능(인터페이스)을 지원하는지 물어볼 때 쓰기 좋다. 
// good use: ask whether an object ALSO supports an optional interface
struct ICamera      { virtual ~ICamera() = default; virtual Frame Grab() = 0; };
struct ITriggerable { virtual ~ITriggerable() = default; virtual void SoftTrigger() = 0; };

void Capture(ICamera* cam)
{
    if (auto* t = dynamic_cast<ITriggerable*>(cam))   // cross cast between unrelated bases
        t->SoftTrigger();
    Frame f = cam->Grab();
}

const_cast - const 떼고 붙이기

const(와 volatile)만 떼거나 붙인다. 다른 변환은 하지 않는다.

// legitimate: an old C API that takes char* but never modifies the string
extern "C" int LegacyOpenDevice(char* name);   // documented as read-only

int Open(const std::string& name)
{
    return LegacyOpenDevice(const_cast<char*>(name.c_str()));   // safe only because it never writes
}

// UNDEFINED BEHAVIOR: writing to an object that was created const
const int limit = 10;
int* p = const_cast<int*>(&limit);
*p = 20;                         // may crash, may be ignored, may "work" - never do this
상황결과
원래 const가 아닌 객체를 const 참조로 받았다가 const를 떼고 수정정의된 동작
처음부터 const로 만든 객체를 const를 떼고 수정정의되지 않은 동작
수정하지 않는 옛 API에 넘기려고 const를 뗌안전 (그 API가 정말로 안 쓸 때만)
캐시 값 갱신에는 mutable const 멤버 함수 안에서 계산 결과를 저장해 두고 싶어 const_cast<Foo*>(this)를 쓰는 코드가 있다. 이런 경우에는 그 멤버를 mutable로 선언하는 것이 맞다. 의도가 선언에 드러나고 캐스트가 필요 없다.

reinterpret_cast - 비트를 다른 타입으로 다시 읽기

메모리의 비트는 그대로 두고 다른 타입으로 다시 해석한다. 관계없는 포인터 사이 변환, 포인터와 정수 사이 변환에 쓴다. 가장 위험한 캐스트이고, 결과가 컴파일러와 플랫폼에 따라 달라질 수 있다.

// 1) raw byte buffer from a driver -> 16-bit pixels
std::vector<uint8_t> raw = ReadFrameBytes();          // Mono12 stored in 2 bytes per pixel
auto* pixels = reinterpret_cast<const uint16_t*>(raw.data());
// valid only if raw.data() is 2-byte aligned and the bytes really are uint16 values

// 2) pointer <-> integer (e.g. alignment check, handles)
uintptr_t addr = reinterpret_cast<uintptr_t>(raw.data());
bool aligned16 = (addr % 16) == 0;

// 3) viewing ANY object as bytes is allowed (char / unsigned char / std::byte)
float f = 1.0f;
auto* bytes = reinterpret_cast<const unsigned char*>(&f);   // ok to read bytes[0..3]

엄격한 별칭 규칙과 비트 복사

C++에는 "어떤 타입의 객체를 관계없는 다른 타입의 포인터로 읽으면 안 된다"는 규칙(strict aliasing)이 있다. 예를 들어 float의 비트를 정수로 보려고 *reinterpret_cast<uint32_t*>(&f)를 쓰면 규칙 위반이고, 최적화 빌드에서 엉뚱한 값이 나올 수 있다. 바이트 단위(char, unsigned char, std::byte)로 읽는 것만 예외로 허용된다.

float f = 1.0f;

// WRONG: violates strict aliasing
uint32_t bad = *reinterpret_cast<uint32_t*>(&f);

// OK: copy the bits (compilers turn this into a single move)
uint32_t ok1;
std::memcpy(&ok1, &f, sizeof f);

// OK, C++20: std::bit_cast
#include <bit>
uint32_t ok2 = std::bit_cast<uint32_t>(f);     // 0x3F800000
정렬 조건 uint8_t 버퍼의 홀수 주소를 uint16_t*나 float*로 바꿔 읽으면, x86에서는 대개 느려지기만 하지만 ARM 등 다른 CPU나 SIMD 명령에서는 오류가 날 수 있다. 카메라 SDK가 준 버퍼라도 헤더 크기 때문에 영상 시작 위치가 어긋나는 경우가 있으므로, 바꾸기 전에 주소 정렬을 확인하거나 memcpy로 정렬된 버퍼에 복사한다.

다중 상속에서 static_cast와 reinterpret_cast의 차이

두 캐스트의 차이가 가장 극적으로 드러나는 경우다. 부모가 여러 개인 클래스에서 두 번째 부모로 변환할 때, static_cast는 포인터 값을 고쳐 그 부모 부분을 가리키게 하지만, reinterpret_cast는 주소를 그대로 둔다.

struct A { int a = 1; };
struct B { int b = 2; };
struct C : A, B { int c = 3; };

C obj;
B* p1 = static_cast<B*>(&obj);        // adjusted: points at the B part inside obj
B* p2 = reinterpret_cast<B*>(&obj);   // NOT adjusted: points at the A part

printf("%p %p %p\n", (void*)&obj, (void*)p1, (void*)p2);
printf("%d %d\n", p1->b, p2->b);      // 2, and 1 (reading A::a as if it were B::b)
다중 상속에서 두 번째 부모로 바꿀 때 static_cast는 주소를 옮기고, reinterpret_cast는 옮기지 않는다 (오프셋은 int 4바이트 기준 예)

C 스타일 캐스트 (B*)&obj는 클래스 선언이 보이면 static_cast로 동작해 맞는 결과가 나온다. 그런데 선언이 안 보이는 파일(전방 선언만 있는 경우)에서는 reinterpret_cast로 동작해 위 그림의 잘못된 결과가 나온다. 같은 코드가 include 하나에 따라 다르게 동작하는 셈이라, C 스타일 캐스트를 피해야 하는 대표적인 이유다.

흔한 함정

경고를 없애려고 C 스타일 캐스트 추가 컴파일러가 "형 변환할 수 없음"이라고 하는 곳에 (T)를 붙여 오류를 없애면, 대부분 reinterpret_cast가 되어 문제를 실행 시점으로 미룰 뿐이다. 오류가 나면 타입 관계부터 다시 본다.
dynamic_cast 결과를 확인하지 않음 포인터 형태의 dynamic_cast는 실패하면 nullptr를 돌려준다. 확인 없이 바로 쓰면 널 포인터 접근으로 죽는다. 실패하면 안 되는 상황이면 참조 형태를 써서 예외로 드러나게 한다.
float → 작은 정수에서 범위 확인 없음 static_cast<uint8_t>(300.0f)처럼 범위를 넘는 float를 정수로 바꾸는 것은 정의되지 않은 동작이다. 영상 값을 8비트로 바꿀 때는 먼저 0~255로 자른 뒤 변환한다(GPU 23편).
