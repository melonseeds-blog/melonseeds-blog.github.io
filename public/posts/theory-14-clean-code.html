클린 코드란?

클린 코드(clean code)는 읽기 쉽고 이해하기 쉬운 코드다. 동작이 같더라도, 다른 사람이 — 그리고 6개월 뒤의 자신이 — 빠르게 읽고 안전하게 고칠 수 있는 코드가 깨끗한 코드다. 클린 코드의 반대는 "동작은 하지만 손대기 두려운 코드"다.

핵심 전제는 단순하다. 코드는 쓰는 시간보다 읽는 시간이 훨씬 길다. 한 번 작성한 코드는 수십, 수백 번 다시 읽힌다. 버그를 찾을 때, 기능을 추가할 때, 리뷰할 때 매번 읽는다. 그러므로 "빨리 쓰는 코드"보다 "빨리 읽히는 코드"가 결국 더 빠르다. 작성 시점에 몇 분 더 들여 이름을 고르고 함수를 나누면, 이후 수백 번의 읽기에서 그 비용을 회수한다.

깨끗하지 않은 코드의 비용

지저분한 코드는 시간이 지날수록 이자가 붙는다. 작은 무질서가 쌓이면 코드를 읽는 데 드는 시간이 늘고, 읽기 어려우면 고치기 어렵고, 고치기 어려우면 또 다른 무질서가 생긴다. 이 악순환을 기술 부채(technical debt)라 부른다. 클린 코드는 거창한 재설계가 아니라, 이 부채가 쌓이지 않게 매 순간 조금씩 갚는 습관이다.

클린 코드는 취향이 아니다 "읽기 좋다"는 주관적으로 들리지만, 클린 코드의 원칙은 대부분 측정 가능한 효과로 이어진다. 좋은 이름은 검색 시간을 줄이고, 작은 함수는 버그의 범위를 좁히고, 중복 제거는 수정 누락을 막는다. 미적 취향이 아니라 유지보수 비용의 문제다.

네이밍

이름 짓기는 클린 코드의 출발점이자 가장 자주 마주치는 결정이다. 변수, 함수, 클래스 — 코드를 읽는다는 것은 결국 이름을 읽는 것이다. 이름이 의도를 드러내면 주석이 거의 필요 없고, 이름이 거짓말을 하면 코드 전체가 거짓말을 한다.

의도가 드러나는 이름

좋은 이름은 "이것이 무엇이고 왜 존재하며 어떻게 쓰이는지"에 답한다. d, tmp, data2, flag 같은 이름은 아무것도 말해 주지 않는다. 읽는 사람이 코드를 거슬러 올라가 의미를 추론해야 한다.

// 나쁜 코드 — 이름이 의도를 숨긴다
ErrorCode proc(Image& img, int d, bool flag)
{
    int tmp = img.GetWidth() * d;
    if (flag)
    {
        // d가 뭐지? flag는 뭘 켜는 거지? 코드를 다 읽어야 안다
    }
    auto data2 = compute(tmp);
    return ErrorCode::Ok;
}

// 좋은 코드 — 이름이 의도를 말한다
ErrorCode ResizeImage(Image& image, int scaleFactor, bool keepAspectRatio)
{
    int scaledWidth = image.GetWidth() * scaleFactor;
    if (keepAspectRatio)
    {
        // 무엇을 하는 코드인지 이름만 봐도 안다
    }
    auto resizedBuffer = compute(scaledWidth);
    return ErrorCode::Ok;
}

발음 가능한 이름, 검색 가능한 이름

이름은 발음 가능해야 한다. m_grbImgBuf는 동료와 대화할 때 "엠 그르브 아이엠지 버프"라고 읽을 수 없다. m_grabbedImageBuffer는 그냥 말로 읽힌다. 사람은 코드를 머릿속에서 소리 내어 읽기 때문에, 발음할 수 없는 이름은 인지 부담을 키운다.

또한 이름은 검색 가능해야 한다. 코드 전체에서 7을 검색하면 수백 개가 걸리지만, kMaxRetryCount를 검색하면 정확히 그것만 나온다. 한 글자 변수나 매직 넘버는 검색이 불가능한 상수다.

// 나쁜 코드 — 발음 불가, 검색 불가
for (int i = 0; i < 7; i++)
{
    if (st[i] == 3) { rty++; }
}

// 좋은 코드 — 발음 가능하고 검색 가능하다
for (int channelIndex = 0; channelIndex < kChannelCount; channelIndex++)
{
    if (sensorStatus[channelIndex] == SensorState::Error)
    {
        retryCount++;
    }
}

매직 넘버를 명명 상수로

코드에 박혀 있는 숫자 리터럴은 매직 넘버(magic number)다. 그 숫자가 무엇을 뜻하는지, 왜 그 값인지 코드만 봐서는 알 수 없다. 같은 의미의 숫자가 여러 곳에 흩어지면 하나를 고칠 때 나머지를 놓치기 쉽다. 의미 있는 이름의 상수로 바꾸면 의도가 드러나고 수정 지점이 한 곳으로 모인다.

// 나쁜 코드 — 65535, 0.299 ... 가 무엇인지 알 수 없다
if (pixelValue > 65535) { pixelValue = 65535; }
double luma = 0.299 * r + 0.587 * g + 0.114 * b;

// 좋은 코드 — 명명 상수가 의미를 설명한다
constexpr int kMax16BitValue = 65535;
constexpr double kLumaWeightRed   = 0.299;
constexpr double kLumaWeightGreen = 0.587;
constexpr double kLumaWeightBlue  = 0.114;

if (pixelValue > kMax16BitValue) { pixelValue = kMax16BitValue; }
double luma = kLumaWeightRed * r + kLumaWeightGreen * g + kLumaWeightBlue * b;

일관성

같은 개념에는 같은 단어를 쓴다. 어떤 곳은 GetImage(), 다른 곳은 FetchPicture(), 또 다른 곳은 RetrieveFrame()이라면, 읽는 사람은 셋이 같은 일인지 다른 일인지 매번 확인해야 한다. 조회는 Get, 생성은 Create, 변환은 Convert — 한번 정한 어휘를 코드베이스 전체에서 일관되게 쓴다.

나쁜 이름좋은 이름이유
delapsedDays한 글자는 의미가 없다
tmpscaledWidth임시 변수도 역할이 있다
data2filteredImage숫자 접미사는 차이를 설명하지 않는다
flagisStreaming무엇의 참/거짓인지 드러나야 한다

함수 — 작게, 한 가지만

함수에 관한 첫 번째 규칙은 "작아야 한다"이고, 두 번째 규칙은 "더 작아야 한다"이다. 함수가 작으면 한눈에 들어오고, 한눈에 들어오면 이해와 검증이 쉽다.

한 가지만 한다

함수는 한 가지 일만 해야 한다. "한 가지"의 기준은 명료하다 — 함수 이름이 설명하는 그 일만 하고, 그 일을 잘하면 된다. 함수 이름에 And가 들어간다면(LoadAndValidateAndSave), 그것은 여러 가지 일을 하고 있다는 신호다.

한 함수는 한 추상화 수준

하나의 함수 안에서는 비슷한 추상화 수준의 문장만 모인다. 고수준 개념(파이프라인 실행)과 저수준 세부(픽셀 비트 시프트)가 한 함수에 섞이면, 읽는 사람의 시선이 위아래로 출렁인다.

// 나쁜 코드 — 추상화 수준이 뒤섞임. 고수준 흐름과 저수준 비트 연산이 한 함수에
ErrorCode ProcessFrame(Image& image)
{
    if (image.IsEmpty()) { return ErrorCode::NullImage; }

    // 고수준: 노이즈 제거
    ApplyMedianFilter(image, 3);

    // 갑자기 저수준: 픽셀 단위 비트 연산
    unsigned char* p = image.GetRawData();
    for (int i = 0; i < image.GetWidth() * image.GetHeight(); i++)
    {
        p[i] = (p[i] >> 4) | (p[i] << 4);
    }

    // 다시 고수준: 결과 저장
    SaveResult(image);
    return ErrorCode::Ok;
}

// 좋은 코드 — 한 추상화 수준. 저수준 세부는 이름 있는 함수 뒤로 숨김
ErrorCode ProcessFrame(Image& image)
{
    if (image.IsEmpty()) { return ErrorCode::NullImage; }

    ApplyMedianFilter(image, kDenoiseKernelSize);
    SwapPixelNibbles(image);   // 저수준 비트 연산은 이름 뒤로
    SaveResult(image);
    return ErrorCode::Ok;
}

인자 수를 줄인다

인자가 적을수록 함수는 이해하기 쉽다. 0개가 가장 이상적이고, 1~2개가 좋고, 3개는 신중해야 하며, 그 이상은 거의 항상 묶을 수 있는 개념이 흩어진 것이다. 인자가 많으면 호출하는 쪽에서 순서를 외워야 하고, 테스트할 조합도 폭발한다. 관련된 인자는 구조체로 묶는다.

// 나쁜 코드 — 인자 7개. 호출 시 순서를 외워야 한다
ErrorCode DrawRoi(Image& image, int x, int y, int width, int height,
                  int r, int g, int b);

// 좋은 코드 — 관련 인자를 구조체로 묶는다
struct Rect
{
    int x;
    int y;
    int width;
    int height;
};

struct Color
{
    int r;
    int g;
    int b;
};

ErrorCode DrawRoi(Image& image, const Rect& roi, const Color& lineColor);

플래그 인자를 지양한다

bool 플래그 인자는 함수가 두 가지 일을 한다고 큰 소리로 알리는 신호다. Save(image, true)를 호출하는 쪽에서는 true가 무엇인지 알 수 없다. 함수를 두 개로 나누면 이름이 의도를 설명한다.

// 나쁜 코드 — true가 무슨 뜻인지 호출부만 봐서는 알 수 없다
ErrorCode Save(const Image& image, bool asCompressed);
Save(result, true);   // true? 무엇이 true인가?

// 좋은 코드 — 함수를 나누면 이름이 설명한다
ErrorCode SaveAsRaw(const Image& image);
ErrorCode SaveAsCompressed(const Image& image);
SaveAsCompressed(result);   // 의도가 분명하다

부수 효과를 없앤다

부수 효과(side effect)는 함수가 이름이 약속하지 않은 일을 몰래 하는 것이다. CheckImageValid()가 검사만 할 것 같은데 내부에서 이미지를 수정한다면, 그 함수를 쓰는 모든 코드가 잠재적 버그가 된다. 함수는 이름이 약속한 일만 하고, 약속하지 않은 상태는 건드리지 않는다.

// 나쁜 코드 — 이름은 검사인데 몰래 m_buffer를 초기화한다 (부수 효과)
bool CheckImageValid(const Image& image)
{
    if (image.IsEmpty()) { return false; }
    m_buffer.clear();   // 이름이 약속하지 않은 일!
    return true;
}

// 좋은 코드 — 검사는 검사만. 초기화가 필요하면 호출부가 명시적으로
bool IsImageValid(const Image& image) const
{
    return !image.IsEmpty();
}

함수 추출

긴 함수를 깨끗하게 만드는 가장 강력한 도구는 함수 추출(extract function)이다. 의미 있는 코드 블록을 잘라내 이름 있는 함수로 만들면, 원래 함수는 "무엇을 하는지"의 목록이 되고 "어떻게 하는지"는 각 함수 안으로 숨는다.

주석이 필요한 블록은 함수로 추출

"이 블록은 ~를 한다"라고 주석을 달고 싶어지는 순간, 그 블록은 함수로 추출할 후보다. 주석 대신 함수 이름이 그 설명을 대신하면, 설명과 코드가 분리될 일이 없다.

// 나쁜 코드 — 한 함수에 모든 단계. 주석으로 블록을 구분하고 있다
ErrorCode InspectPart(const Image& input, InspectResult& outResult)
{
    Image working = input.Clone();

    // 전처리: 노이즈 제거하고 대비 보정
    ApplyMedianFilter(working, 3);
    NormalizeContrast(working);
    ApplyGaussianBlur(working, 5);

    // 엣지 검출하고 윤곽선 추출
    Image edges;
    DetectEdges(working, edges);
    std::vector<Contour> contours;
    ExtractContours(edges, contours);

    // 각 윤곽선의 면적을 재서 불량 판정
    for (const auto& contour : contours)
    {
        double area = 0.0;
        ComputeContourArea(contour, area);
        if (area < kMinValidArea) { outResult.defects++; }
    }
    return ErrorCode::Ok;
}

// 좋은 코드 — 주석이 가리키던 블록을 각각 함수로 추출
ErrorCode InspectPart(const Image& input, InspectResult& outResult)
{
    Image working = input.Clone();

    Preprocess(working);
    std::vector<Contour> contours = FindContours(working);
    outResult.defects = CountDefectiveContours(contours);
    return ErrorCode::Ok;
}

추출된 InspectPart는 이제 검사 절차의 요약처럼 읽힌다 — 전처리하고, 윤곽선을 찾고, 불량을 센다. 각 단계의 세부가 궁금하면 해당 함수로 내려가면 된다. 이것이 함수 추출이 만드는 계층적 가독성이다.

주석으로 구분되던 블록을 이름 있는 함수로 추출하면, 원래 함수는 절차의 요약이 된다
추출의 기준은 "이름을 붙일 수 있는가" 코드 블록에 의미 있는 이름을 붙일 수 있다면 추출할 가치가 있다. 이름이 잘 떠오르지 않는다면, 그 블록이 사실 여러 일을 하고 있거나 경계가 잘못 잡힌 것이다. 좋은 이름이 떠오를 때까지 경계를 다시 본다.

주석

주석에 관한 가장 중요한 사실은 "주석은 코드의 실패를 보완한다"는 것이다. 코드 자체로 의도를 표현할 수 있다면 그것이 항상 낫다. 주석은 코드와 함께 갱신되지 않으면 거짓말이 되기 때문이다. 그래도 코드로 표현할 수 없는 것 — 왜 이렇게 했는지, 어떤 함정이 있는지 — 은 주석으로 남긴다.

좋은 주석 — 왜·의도·경고·TODO

좋은 주석은 코드가 말할 수 없는 것을 말한다. 왜 이 알고리즘을 선택했는지, 왜 직관과 다른 값을 쓰는지, 이 코드를 건드릴 때 무엇을 조심해야 하는지. 이런 정보는 코드 어디에도 적혀 있지 않다.

// 좋은 주석 — 왜 이 값인지 설명한다 (코드만 봐서는 알 수 없는 것)
// Vieworks 그래버는 라인당 64바이트 정렬을 요구한다. 정렬을 깨면 DMA 전송이 실패한다.
constexpr int kLineAlignment = 64;

// 좋은 주석 — 경고
// 이 함수는 m_imageLock을 이미 잡은 상태에서 호출해야 한다. 직접 호출 금지.
void flushBufferLocked();

// 좋은 주석 — TODO (할 일을 명시적으로 남긴다)
// TODO(claude05): Mono12 packed 포맷은 아직 미지원. 4.2 릴리스에서 추가.
ErrorCode DecodePixelFormat(PixelFormat format);

나쁜 주석 — 코드 반복·거짓말·주석 처리된 코드

나쁜 주석은 코드를 그대로 한국어로 옮긴 것, 코드와 어긋나 거짓말을 하는 것, 그리고 지우지 않고 남겨 둔 주석 처리된 코드다. 특히 주석 처리된 코드는 "혹시 필요할까 봐" 남기지만, 버전 관리 시스템이 그 역할을 한다 — 그냥 지운다.

// 나쁜 주석 — 코드를 그대로 반복한다 (아무 정보도 더하지 않음)
// width를 1 증가시킨다
width++;

// 나쁜 주석 — 거짓말. 코드는 바뀌었는데 주석은 안 바뀌었다
// 커널 크기를 3으로 설정한다
int kernelSize = 7;

// 나쁜 주석 — 주석 처리된 코드. 버전 관리가 있으니 그냥 지운다
// ApplyOldBlur(image, 5);
// NormalizeLegacy(image);
ApplyGaussianBlur(image, kBlurKernelSize);

포맷팅

포맷팅은 사소해 보이지만 가독성에 직접 영향을 준다. 일관된 들여쓰기, 적절한 공백, 의미 있는 줄바꿈은 코드의 구조를 눈에 보이게 만든다. 핵심은 "무엇이 옳은가"가 아니라 "팀 전체가 같은 규칙을 따르는가"다.

관련 코드는 가까이

서로 관련된 코드는 세로로 가깝게 둔다. 변수는 처음 쓰이는 곳 근처에서 선언하고, 함께 호출되는 함수는 붙여 둔다. 관련 없는 코드 사이에는 빈 줄로 간격을 둬서 "여기서 생각의 단위가 바뀐다"를 시각적으로 표시한다.

// 나쁜 코드 — 들여쓰기 불일치, 공백 없음, 변수 선언이 사용처와 멀다
ErrorCode Calibrate(Camera& cam){
int retry=0;double offset=0.0;Image ref;
  cam.Connect();
    cam.SetExposure(1000.0);
cam.Capture(ref);
offset=ComputeOffset(ref);
  return ErrorCode::Ok;}

// 좋은 코드 — 일관된 들여쓰기, 의미 단위로 빈 줄, 선언은 사용처 근처
ErrorCode Calibrate(Camera& cam)
{
    cam.Connect();
    cam.SetExposure(kCalibrationExposureUs);

    Image referenceImage;
    cam.Capture(referenceImage);

    double offset = ComputeOffset(referenceImage);
    ApplyOffset(cam, offset);

    return ErrorCode::Ok;
}
포맷팅은 도구에 맡긴다 들여쓰기와 공백 규칙은 사람이 매번 신경 쓸 일이 아니다. clang-format 같은 자동 포맷터에 규칙을 한 번 정의하고 저장 시 자동 적용하면, 포맷 논쟁이 사라지고 리뷰는 내용에만 집중할 수 있다.

에러 처리

에러 처리는 중요하지만, 그것이 코드의 논리를 가려서는 안 된다. 정상 흐름과 에러 처리가 뒤엉키면 둘 다 읽기 어려워진다. 에러 처리도 "한 가지 일"이라는 원칙을 따른다 — 에러를 처리하는 함수는 에러만 처리한다.

예외 vs 에러 코드

예외와 에러 코드는 각각의 자리가 있다. 예외는 정상 흐름과 에러 흐름을 코드 상에서 분리해 주지만, 호출 규약이 시그니처에 드러나지 않는다. 에러 코드는 명시적이고 호출부가 반드시 확인하게 만들지만, 정상 흐름에 검사 코드가 섞인다. 이 프로젝트는 API 경계에서 ErrorCode 반환을 규약으로 삼는다 — 내부에서 예외를 쓰더라도 경계에서 잡아 ErrorCode로 변환한다.

null 반환·전달을 지양한다

함수가 nullptr을 반환하면, 호출하는 모든 곳이 null 검사를 해야 하고, 한 곳이라도 빠뜨리면 크래시다. null을 인자로 전달하는 것은 더 나쁘다. 가능하면 빈 객체, 에러 코드, 또는 명시적인 옵셔널 타입으로 "값이 없음"을 표현한다.

// 나쁜 코드 — null 반환. 호출부가 검사를 빠뜨리면 크래시
Image* FindTemplate(const Image& source)
{
    if (source.IsEmpty()) { return nullptr; }   // 호출부가 검사할까?
    // ...
}

// 나쁜 코드 — 정상 흐름과 에러 검사가 뒤엉킨다
ErrorCode Run()
{
    Image* t = FindTemplate(src);
    if (t != nullptr)
    {
        if (Match(t) == ErrorCode::Ok)
        {
            if (Save(t) == ErrorCode::Ok) { /* ... */ }
        }
    }
}

// 좋은 코드 — out 파라미터 + ErrorCode, 이른 반환으로 흐름을 평탄하게
ErrorCode FindTemplate(const Image& source, Image& outTemplate)
{
    if (source.IsEmpty()) { return ErrorCode::NullImage; }
    // ...
    return ErrorCode::Ok;
}

ErrorCode Run()
{
    Image found;
    if (FindTemplate(src, found) != ErrorCode::Ok) { return ErrorCode::NotFound; }
    if (Match(found) != ErrorCode::Ok)             { return ErrorCode::MatchFailed; }
    if (Save(found) != ErrorCode::Ok)              { return ErrorCode::SaveFailed; }
    return ErrorCode::Ok;
}

두 번째 좋은 예시에서 쓴 기법이 이른 반환(early return)이다. 에러 조건을 먼저 걸러 내고 함수를 빠져나가면, 정상 흐름은 들여쓰기 없이 평탄하게 이어진다. 중첩된 if 피라미드가 사라진다.

DRY 원칙

DRY(Don't Repeat Yourself)는 "모든 지식은 시스템 안에서 단 하나의 명확한 표현을 가져야 한다"는 원칙이다. 같은 로직이 여러 곳에 복사되어 있으면, 그것을 고칠 때 모든 사본을 찾아 똑같이 고쳐야 한다. 하나라도 놓치면 버그다.

중복 제거

// 나쁜 코드 — 같은 클램핑 로직이 세 번 복사됨. 범위가 바뀌면 세 곳을 고쳐야
void AdjustBrightness(Image& image, int delta)
{
    // ... r = r + delta; if (r < 0) r = 0; if (r > 255) r = 255;
    // ... g = g + delta; if (g < 0) g = 0; if (g > 255) g = 255;
    // ... b = b + delta; if (b < 0) b = 0; if (b > 255) b = 255;
}

// 좋은 코드 — 클램핑 지식을 한 곳에 모은다
int ClampToByte(int value)
{
    if (value < kMinByteValue) { return kMinByteValue; }
    if (value > kMaxByteValue) { return kMaxByteValue; }
    return value;
}

{
    // ... r = ClampToByte(r + delta);
    // ... g = ClampToByte(g + delta);
    // ... b = ClampToByte(b + delta);

과한 추상화 경계

그러나 DRY를 맹목적으로 적용하면 반대 방향의 함정에 빠진다. 우연히 비슷해 보이는 코드를 무리하게 하나로 합치면, 나중에 둘이 서로 다르게 변해야 할 때 억지로 만든 추상화가 짐이 된다. 진짜 중복(같은 지식의 반복)과 우연한 유사(지금만 비슷한 코드)를 구별해야 한다.

성급한 추상화는 중복보다 비쌀 수 있다 "코드가 두 번 비슷하다"는 이유만으로 즉시 공통 함수로 합치지 않는다. 세 번째 사례가 나타날 때까지 기다리면, 무엇이 진짜 공통이고 무엇이 다른지가 분명해진다. 잘못 만든 추상화를 되돌리는 비용은, 중복을 잠시 두는 비용보다 크다. "중복이 잘못된 추상화보다 싸다(duplication is cheaper than the wrong abstraction)"는 격언을 기억한다.

보이스카웃 규칙

보이스카웃에는 "캠프장을 처음 왔을 때보다 깨끗하게 두고 떠나라"는 규칙이 있다. 코드에도 그대로 적용된다 — 코드를 체크아웃했을 때보다 조금 더 깨끗하게 만들어 체크인한다.

핵심은 점진적이라는 점이다. 거대한 리팩토링 프로젝트를 따로 잡을 필요가 없다. 버그를 고치러 어떤 파일을 열었다면, 그 김에 모호한 변수 이름 하나를 고치고, 매직 넘버 하나를 상수로 빼고, 죽은 주석 한 줄을 지운다. 작은 개선이 매번 쌓이면 코드베이스는 시간이 지날수록 나빠지는 대신 좋아진다.

한 번에 조금씩, 그러나 매번 보이스카웃 규칙의 힘은 빈도에 있다. 한 번에 큰 개선을 하는 것이 아니라, 코드를 만질 때마다 작은 개선을 빠뜨리지 않는 것이다. 단, 개선과 기능 변경은 커밋을 분리한다 — 리뷰어가 무엇이 동작 변경이고 무엇이 정리인지 구분할 수 있어야 한다.

코드 리뷰와 클린 코드

클린 코드는 개인의 습관이지만, 코드베이스의 청결은 팀 차원의 합의로만 유지된다. 코드 리뷰는 그 합의가 작동하는 자리다. 리뷰는 단순히 버그를 잡는 절차가 아니라, "이 코드를 나 말고 다른 사람도 읽을 수 있는가"를 확인하는 절차다.

리뷰에서 클린 코드 관점으로 던질 질문은 일정하다. 이름이 의도를 드러내는가? 함수가 한 가지만 하는가? 주석이 코드의 실패를 변명하고 있지는 않은가? 중복이 있는가? 이 질문들을 팀이 공유하면 리뷰가 취향 다툼이 아니라 공통 기준의 적용이 된다.

리뷰의 대상은 코드이지 사람이 아니다 클린 코드 리뷰가 효과를 내려면 지적이 개인 공격으로 느껴지지 않아야 한다. "이 이름은 의도가 안 드러난다"는 코드에 대한 관찰이지 작성자에 대한 평가가 아니다. 팀이 코딩 컨벤션 문서를 공유하면, 리뷰 코멘트는 "내 취향"이 아니라 "우리 합의"를 가리키게 된다.

산업 SW 관점

산업용 이미징 SDK처럼 수년에 걸쳐 유지보수되고 여러 사람이 손대는 코드베이스에서, 클린 코드는 선택이 아니라 생존 조건이다. 그래서 이 프로젝트는 클린 코드의 원칙을 코딩 컨벤션으로 명문화한다.

코딩 컨벤션 — 네이밍 규칙과 ErrorCode 패턴

네이밍 규칙(PascalCase 메서드, m_ 멤버, k 접두 상수), Allman 중괄호, ErrorCode 반환 패턴은 모두 "팀 전체가 같은 규칙을 따른다"는 클린 코드 원칙의 구체적 실현이다. 컨벤션이 있으면 어떤 파일을 열어도 익숙한 구조가 보이고, 새 사람이 합류해도 코드의 모양을 다시 배울 필요가 없다.

// 컨벤션을 따른 코드 — 어느 파일을 열어도 같은 모양
class ImageProcessor
{
public:
    // 공개 API는 PascalCase, 처리 함수는 ErrorCode 반환
    ErrorCode ApplyMedianFilter(Image& image, int kernelSize);

    // 단순 getter는 값을 직접 반환
    int GetProcessedCount() const { return m_processedCount; }

private:
    // private 메서드는 camelCase
    bool validateKernelSize(int kernelSize) const;

    // 멤버는 m_ 접두
    int m_processedCount = 0;
};

ErrorCode ImageProcessor::ApplyMedianFilter(Image& image, int kernelSize)
{
    // 입력 검사 — 이른 반환으로 흐름을 평탄하게
    if (image.IsEmpty())             { return ErrorCode::NullImage; }
    if (!validateKernelSize(kernelSize)) { return ErrorCode::InvalidParameter; }

    // ... 처리 ...
    m_processedCount++;
    return ErrorCode::Ok;
}

검사 로직의 가독성

머신 비전의 검사 로직은 특히 가독성이 중요하다. 불량 판정 기준은 시간이 지나며 계속 조정되고, 그때마다 엔지니어가 코드를 읽고 고쳐야 한다. 판정 조건이 매직 넘버와 익명 변수로 쓰여 있으면, 조정할 때마다 코드를 해독하는 데 시간을 쓴다. 판정 기준을 이름 있는 상수와 의도가 드러나는 함수로 표현하면, 검사 로직 자체가 사양서처럼 읽힌다.

// 나쁜 코드 — 판정 기준이 매직 넘버. 기준을 조정하려면 코드를 해독해야
bool judge(double a, double w)
{
    return a > 1500.0 && a < 4000.0 && w < 0.15;
}

// 좋은 코드 — 판정 기준이 이름으로 드러난다. 검사 사양처럼 읽힌다
constexpr double kMinValidArea   = 1500.0;
constexpr double kMaxValidArea   = 4000.0;
constexpr double kMaxWidthVariation = 0.15;

bool IsPartWithinSpec(const Measurement& measurement)
{
    bool areaInRange     = measurement.area > kMinValidArea
                        && measurement.area < kMaxValidArea;
    bool widthStable     = measurement.widthVariation < kMaxWidthVariation;
    return areaInRange && widthStable;
}

흔한 함정

함정 1 — 주석으로 나쁜 코드를 변명

가장 흔한 함정은 이해하기 어려운 코드 위에 긴 주석을 달고 "설명했으니 됐다"고 넘어가는 것이다. 주석은 나쁜 코드를 좋은 코드로 만들지 못한다. // 아래는 픽셀 평균을 구하는 복잡한 로직이라고 쓸 시간에, 그 로직을 ComputePixelMean()으로 추출하는 것이 정답이다. 주석이 길어진다면 그것은 코드가 자기 설명을 못 한다는 신호이지, 주석이 부족하다는 신호가 아니다.

"주석을 달면 되지"는 리팩토링의 회피다 나쁜 코드에 주석을 다는 것은 문제를 해결하는 것이 아니라 문제에 라벨을 붙이는 것이다. 주석을 쓰고 싶어질 때마다 먼저 물어야 한다 — "이 주석이 필요 없도록 코드를 고칠 수 있는가?" 대부분의 경우 답은 "그렇다"이고, 이름 변경이나 함수 추출이면 충분하다.

함정 2 — 과한 약어

calcImgHistEq(), m_tmpBufPtr, procRslt 같은 약어 범벅은 타이핑을 몇 글자 줄이지만 읽기를 평생 어렵게 만든다. 현대 IDE는 자동 완성을 제공하므로 긴 이름의 타이핑 비용은 거의 없다. CalculateHistogramEqualization()이 길어 보여도, 그것을 읽는 수백 번의 미래가 짓는 비용에 비하면 무료다. 약어는 누구나 아는 것(id, url, roi)만 허용한다.

함정 3 — 거대 함수

스크롤을 여러 번 해야 끝이 보이는 함수는 그 자체로 위험 신호다. 거대 함수는 보통 여러 책임이 한 곳에 뭉친 결과이고, 그 안의 지역 변수들이 함수 전체에 걸쳐 얽혀 있어 일부만 떼어 내기도 어렵다. 함수가 한 화면을 넘어가기 시작하면, 추출할 블록이 있는지 먼저 살핀다. 거대 함수는 한 번에 다 고치려 하지 말고, 보이스카웃 규칙으로 만질 때마다 한 조각씩 떼어 낸다.

함정 4 — 클린 코드를 핑계로 한 과한 추상화

마지막 함정은 클린 코드 자체를 오해하는 데서 온다. "추상화는 좋은 것"이라는 믿음이 지나치면, 한 번만 쓰이는 코드에 인터페이스를 만들고, 두 줄짜리 함수를 다섯 개의 작은 함수로 쪼개고, 모든 것을 설정 가능하게 만든다. 이렇게 만든 코드는 "깨끗해 보이지만" 실제로는 한 가지 동작을 이해하기 위해 열 개의 파일을 오가야 한다. 이것은 클린 코드가 아니라 과잉 설계(over-engineering)다.

추상화는 공짜가 아니다 — 간접 비용을 치른다 모든 추상화 계층은 "이름 하나를 더 이해해야 한다"는 인지 비용을 더한다. 추상화는 그 비용보다 큰 가치(중복 제거, 변경 격리, 진짜 다형성)가 있을 때만 정당하다. "나중에 필요할지도 모른다"는 추측만으로 만든 추상화는 대개 그 나중이 오지 않고, 코드만 복잡하게 남긴다. 클린 코드의 목표는 추상화의 양을 늘리는 것이 아니라 읽기 쉬움을 늘리는 것이다. 단순한 코드가 읽기 쉽다면, 단순한 것이 깨끗한 것이다.
