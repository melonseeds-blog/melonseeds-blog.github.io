테스트와 빌드 — cargo test·워크스페이스

왜 테스트가 cargo에 내장인가

Rust에서는 테스트를 위해 별도의 프레임워크를 고르고 빌드 스크립트에 연결하는 단계가 없다. 컴파일러가 테스트 어트리뷰트를 알고, cargo가 테스트 러너를 품고 있다. 새 프로젝트를 만들면 그 자리에서 바로 테스트를 쓸 수 있다.

이 차이는 단순한 편의 이상이다. 표준이 하나로 정해져 있으니 어느 프로젝트를 열어도 테스트 구조가 같고, 라이브러리를 받아 쓸 때도 그 라이브러리의 테스트를 같은 명령으로 돌릴 수 있다. "테스트는 처음부터 일급 시민"이라는 설계가 도구 전반에 깔려 있다.

C++과 이렇게 다르다 — 테스트 셋업 C++에서는 보통 CMake에 GoogleTest를 FetchContent나 vcpkg로 끌어와 add_executable·target_link_libraries·add_test를 손으로 엮고, 그제서야 ctest로 돌린다. 테스트 프레임워크 선택(gtest·Catch2·doctest…)부터 사람마다 갈린다. Rust는 그 모든 결정과 배선이 cargo test 한 줄로 사라진다 — 프레임워크도, 러너도 기본 제공이다.

단위 테스트 — #[test]와 #[cfg(test)]

단위 테스트는 보통 테스트하려는 코드와 같은 파일에 둔다. 관례는 파일 맨 아래에 tests 모듈을 만들고 거기에 테스트 함수를 모으는 것이다. 함수에 #[test]를 붙이면 그 함수가 테스트 대상이 된다.

// src/lib.rs
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}

// #[cfg(test)]: 이 모듈은 `cargo test`로 빌드할 때만 컴파일된다.
// 일반 빌드(`cargo build`)에는 포함되지 않아 산출물이 가벼워진다.
#[cfg(test)]
mod tests {
    // 바깥 모듈의 항목을 끌어온다.
    use super::*;

    #[test]
    fn adds_two_positive_numbers() {
        assert_eq!(add(2, 3), 5);
    }

    #[test]
    fn adds_with_negative() {
        assert_eq!(add(-4, 1), -3);
    }
}

여기서 두 어트리뷰트의 역할이 다르다. #[test]는 "이 함수는 테스트다"라고 표시하고, #[cfg(test)]는 "이 모듈 전체를 테스트 빌드에서만 컴파일하라"는 조건부 컴파일 지시다. 덕분에 테스트 코드는 배포 산출물에 들어가지 않는다.

assert 매크로와 실패 표현

검증에는 assert!(불리언이 참인지), assert_eq!(두 값이 같은지), assert_ne!(다른지)를 쓴다. assert_eq!는 실패하면 좌·우 값을 함께 출력해 주어 디버깅이 편하다. 실패를 직접 표현해야 할 때는 panic!을 쓰거나, 테스트 함수가 Result를 반환하게 만들 수도 있다.

pub fn divide(a: i32, b: i32) -> Result<i32, String> {
    if b == 0 {
        return Err(String::from("division by zero"));
    }
    Ok(a / b)
}

#[cfg(test)]
mod tests {
    use super::*;

    // 테스트가 Result를 반환하면 `?`로 에러를 그대로 전파할 수 있다.
    #[test]
    fn divides_evenly() -> Result<(), String> {
        let q = divide(10, 2)?;
        assert_eq!(q, 5);
        Ok(())
    }

    // #[should_panic]: 이 테스트는 패닉이 나야 통과한다.
    // expected로 패닉 메시지 일부를 함께 검사한다.
    #[test]
    #[should_panic(expected = "out of range")]
    fn rejects_bad_index() {
        let v = vec![1, 2, 3];
        if 9 >= v.len() {
            panic!("index 9 is out of range");
        }
    }
}

테스트 함수가 Err를 반환하면 그 테스트는 실패로 처리된다. 그래서 ? 연산자로 중간 단계의 에러를 자연스럽게 흘려보내면서도 검증 흐름을 깔끔하게 유지할 수 있다.

통합 테스트 — tests/ 디렉터리

단위 테스트가 모듈 내부까지 들여다본다면, 통합 테스트는 외부 사용자처럼 크레이트를 쓴다. 프로젝트 루트에 tests/ 디렉터리를 만들면, 그 안의 각 .rs 파일이 독립된 크레이트로 컴파일되어 우리 라이브러리를 마치 남의 의존성처럼 use로 가져온다.

// tests/integration_add.rs
// 크레이트 이름이 `my_calc`라고 가정한다(Cargo.toml의 name).
// 통합 테스트는 공개(pub) API에만 접근할 수 있다.
use my_calc::add;

#[test]
fn public_api_adds_correctly() {
    // 내부 구현이 아니라 외부에 노출된 함수만 검증한다.
    assert_eq!(add(40, 2), 42);
}

핵심 제약은 통합 테스트가 pub으로 공개된 항목만 볼 수 있다는 점이다. 이것이 오히려 장점이 된다 — 실제 사용자가 마주할 표면, 즉 공개 API의 계약을 그대로 검증하게 되기 때문이다. 내부 헬퍼는 단위 테스트로, 외부 계약은 통합 테스트로 나누는 구분이 자연스럽게 생긴다.

tests/ 안의 공용 헬퍼는 서브모듈로 여러 통합 테스트 파일이 공유할 보조 코드는 tests/common/mod.rs에 둔다. tests/common.rs가 아니라 common/mod.rs 형태로 두는 이유는, 그래야 그 파일이 독립 테스트 크레이트로 따로 컴파일되지 않고 단순 헬퍼 모듈로만 취급되기 때문이다.

cargo test 실행하기

cargo test는 단위 테스트·통합 테스트·문서 테스트를 한 번에 빌드하고 실행한다. 기본적으로 테스트들은 병렬로 돌기 때문에, 공유 상태에 의존하는 테스트는 서로 간섭하지 않게 작성해야 한다.

명령하는 일
cargo test모든 테스트를 빌드하고 실행
cargo test adds이름에 adds가 들어간 테스트만 실행
cargo test -- --nocapture테스트 안의 println! 출력을 숨기지 않음
cargo test -- --test-threads=1병렬을 끄고 순차 실행
cargo test --release릴리스 최적화 빌드로 테스트

-- 뒤의 인자는 cargo가 아니라 테스트 바이너리에 전달된다. 그래서 --nocapture나 --test-threads 같은 옵션은 -- 다음에 와야 한다. 기본적으로 통과한 테스트의 표준 출력은 가려지므로, 디버깅 중 로그를 보려면 --nocapture를 쓴다.

오래 걸리는 테스트는 ignore로 분리 무겁고 평소엔 건너뛰고 싶은 테스트에는 #[ignore]를 붙인다. 평소 cargo test에서는 제외되고, 필요할 때 cargo test -- --ignored로만 따로 돌릴 수 있다.

워크스페이스와 crates.io 배포

프로젝트가 커지면 하나의 크레이트로는 부족해진다. 워크스페이스는 여러 크레이트를 한 빌드 단위로 묶어, Cargo.lock과 target/ 출력 디렉터리를 공유하게 한다. 루트의 Cargo.toml에 멤버를 나열한다.

# 워크스페이스 루트의 Cargo.toml
[workspace]
resolver = "2"
members = [
    "core",       # 라이브러리 크레이트
    "cli",        # core에 의존하는 실행 파일 크레이트
]

이제 cli 크레이트는 같은 워크스페이스의 core를 경로로 의존할 수 있다. 멤버 간 의존은 path로 가리킨다.

# cli/Cargo.toml
[package]
name = "my-cli"
version = "0.1.0"
edition = "2021"

[dependencies]
# 같은 워크스페이스 안의 다른 멤버를 상대 경로로 가져온다.
core = { path = "../core" }

워크스페이스 루트에서 cargo build나 cargo test를 돌리면 모든 멤버가 함께 빌드·테스트된다. 특정 크레이트만 다루려면 cargo test -p core처럼 -p로 패키지를 지정한다. 의존성 버전이 워크스페이스 전체에서 하나의 Cargo.lock으로 잠기므로, 멤버마다 버전이 어긋나는 문제가 줄어든다.

crates.io 배포 개요

라이브러리를 공개 등록소인 crates.io에 올리는 흐름은 대략 이렇다. 세부는 버전에 따라 바뀔 수 있으니 큰 순서만 본다.

  1. 계정·토큰 준비. crates.io에 로그인해 발급한 토큰으로 cargo login을 한 번 실행한다.
  2. 메타데이터 채우기. 해당 크레이트의 Cargo.toml에 name·version·license·description 등 공개에 필요한 필드를 적는다.
  3. 사전 점검. cargo publish --dry-run으로 실제 업로드 없이 패키징과 빌드를 검증한다.
  4. 게시. cargo publish로 해당 크레이트를 올린다. 워크스페이스라도 게시는 크레이트 단위라, 멤버마다 따로 실행한다.
게시는 되돌릴 수 없다 crates.io에 한 번 올린 버전은 삭제할 수 없고, cargo yank로 "새 의존에 쓰이지 않게" 막는 것만 가능하다(이미 그 버전을 쓰던 프로젝트는 계속 받을 수 있다). 그래서 --dry-run으로 미리 확인하는 단계가 중요하다.

여기까지가 Rust의 테스트와 빌드 골격이다. 핵심은 하나다 — 테스트·빌드·의존성·배포가 cargo라는 단일 도구로 통합돼 있어, 별도 배선 없이 처음부터 표준 흐름을 탄다. C++에서 도구 조합에 쏟던 결정 비용이 여기서는 대부분 사라진다.
