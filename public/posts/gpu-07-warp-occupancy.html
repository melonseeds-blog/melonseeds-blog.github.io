Warp — GPU의 실행 단위

커널을 짤 때는 스레드 하나를 단위로 생각하지만, GPU 하드웨어가 실제로 묶어서 실행하는 단위는 warp다. NVIDIA GPU에서 warp는 항상 32개 스레드로 구성되고, 한 warp의 모든 스레드는 같은 명령을 동시에 실행한다. 이 모델을 SIMT(Single Instruction, Multiple Thread)라고 부른다.

하나의 Block은 32-thread warp 여러 개로 쪼개진다. 한 warp의 32 lane은 같은 명령을 동시에 처리한다.

이 사실에서 두 가지 실용적인 결과가 따라온다. 첫째, 블록 크기는 32의 배수로 잡는다. 예를 들어 블록 크기를 100으로 두면 마지막 warp의 28개 lane이 쓸모없이 비어 있어 자원이 낭비된다. 둘째, 같은 warp 안의 스레드들은 같은 명령을 함께 수행하므로, 분기와 메모리 접근을 warp 단위로 생각해야 한다.

// blockDim.x는 32의 배수로 — warp가 꽉 차게
const int kThreadsPerBlock = 256;   // good: 32 * 8
// const int kBad = 100;            // bad: 마지막 warp 28 lane 낭비

// 커널 안에서 lane id와 warp id를 구할 때
__device__ int laneId() { return threadIdx.x & 31; }      // 0..31
__device__ int warpId() { return threadIdx.x >> 5; }      // tid / 32
SIMT vs SIMD SIMD는 CPU의 AVX/SSE처럼 한 명령으로 여러 데이터를 처리하는 모델이다. SIMT는 같은 명령을 여러 thread가 처리하되, 각 lane이 자기 레지스터·자기 주소를 갖는다. 프로그래머 입장에서는 thread 한 개로 짜고, 하드웨어가 warp 단위로 묶어 실행한다.

Warp Divergence

같은 warp 안의 스레드가 if-else로 서로 다른 경로를 타면 어떻게 될까? 하드웨어는 한 번에 한 명령만 처리할 수 있으므로, 두 분기를 차례대로 실행하고 그 사이에 해당 경로를 타지 않는 lane은 마스킹되어 놀게 된다. 이를 warp divergence라고 부른다.

warp 안에서 분기가 갈리면 양쪽을 순차 실행한다. warp 경계로 분기를 정렬하면 페널티가 사라진다.

나쁜 예 — thread id 단위 분기

// Bad: 같은 warp 안에서 갈라진다
__global__ void divergentKernel(float* data, int n)
{
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    if (tid >= n) return;

    if (tid % 2 == 0)            // 짝/홀로 갈림 → 한 warp 안에 두 경로 공존
    {
        data[tid] = sqrtf(data[tid]);
    }
    else
    {
        data[tid] = data[tid] * data[tid];
    }
}

좋은 예 — warp 단위 분기 또는 분기 제거

// Good 1: warp 단위로 분기 — 같은 warp는 같은 경로
__global__ void warpAlignedKernel(float* data, int n)
{
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    if (tid >= n) return;

    int warpIdInBlock = threadIdx.x >> 5;   // tid / 32
    if ((warpIdInBlock & 1) == 0)            // 짝수 warp / 홀수 warp
        data[tid] = sqrtf(data[tid]);
    else
        data[tid] = data[tid] * data[tid];
}

// Good 2: 분기 자체를 산술로 — 분기 제거(branchless)
__global__ void branchlessKernel(float* data, int n)
{
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    if (tid >= n) return;

    float v = data[tid];
    float a = sqrtf(v);
    float b = v * v;
    int even = ((tid & 1) == 0);            // 0 또는 1
    data[tid] = even * a + (1 - even) * b;  // 양쪽 다 계산하되 선택
}
함정: 짧은 if는 컴파일러가 predication으로 처리 몇 줄짜리 분기는 NVCC가 predicate 명령으로 변환해 divergence 비용이 거의 없다. 문제는 분기 안에 긴 코드, 메모리 접근, 함수 호출이 들어갈 때다. 짧은 분기까지 branchless로 바꾸려고 코드를 일그러뜨릴 필요는 없다 — 프로파일러로 측정하고 결정한다.

루프 divergence

루프 횟수가 thread마다 다르면 가장 오래 도는 lane이 끝날 때까지 warp 전체가 기다린다.

// 각 thread의 work 양이 다르면 가장 긴 lane이 warp를 잡고 있음
__global__ void unbalancedLoop(int* counts, float* out, int n)
{
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    if (tid >= n) return;

    float sum = 0.0f;
    for (int i = 0; i < counts[tid]; ++i)   // counts[tid]가 천차만별이면 idle 발생
    {
        sum += sinf((float)i);
    }
    out[tid] = sum;
}
// 해결: 작업 정렬·재분배. 비슷한 크기끼리 같은 warp에 모으기.

Occupancy(점유율)

한 SM(Streaming Multiprocessor)은 동시에 여러 warp를 갖고 있다가 메모리 대기 등으로 어떤 warp가 멈추면 다른 warp로 즉시 전환한다. Occupancy는 SM에서 실제 활성화된 warp 수를 그 SM이 지원하는 최대 warp 수로 나눈 비율이다.

Occupancy = Active Warps per SM ÷ Max Warps per SM

점유율이 높을수록 SM이 메모리 레이턴시를 다른 warp 실행으로 숨길 수 있는 여유가 커진다. 메모리 바운드(memory-bound) 커널에서는 점유율이 중요한 변수다. 하지만 점유율이 100%여야만 빠른 건 아니다. 컴퓨트 바운드(compute-bound) 커널이거나 ILP(Instruction-Level Parallelism)가 충분하면 점유율 50%만으로도 최고 성능이 나온다.

레이턴시 숨기기(Latency Hiding) 한 warp가 global memory를 기다리는 동안(수백 cycle) 스케줄러는 다른 ready warp를 골라 실행한다. SM에 동시에 머무는 warp가 많을수록 이 전환 풀이 커지고, 결과적으로 메모리 대기가 노출되지 않는다.

Occupancy의 제약

SM이 한 번에 품을 수 있는 thread/block 수는 정해져 있다. 그리고 그 한계는 보통 세 자원 중 가장 빠듯한 것에 의해 결정된다.

제약 요소한계 (Ampere/Ada 기준 예시)커널이 쓰는 만큼 줄어듦
레지스터(Register file)64K regs / SMthread당 reg 사용 × warp 수 ≤ 64K
Shared memory최대 100~228 KB / SM (아키텍처별)block당 shared mem × 활성 block 수 ≤ 한계
Block 수32 blocks / SM (Ampere)block이 너무 작으면 block 수 한계에 걸림
Warp 수48~64 warps / SM이 값이 점유율 분모

가장 흔히 보는 제약은 레지스터 사용량이다. 변수 많고 함수 인라이닝이 많은 커널은 thread당 64~128개씩 레지스터를 잡아먹고, 그러면 동시에 띄울 수 있는 warp가 줄어 점유율이 떨어진다.

// nvcc -Xptxas -v 로 컴파일하면 자원 사용량이 출력된다
// ptxas info    : Used 42 registers, 12288 bytes smem, 384 bytes cmem[0]

// 1) 컴파일 시 thread당 레지스터 상한을 강제
//    nvcc --maxrregcount=32 ...

// 2) 커널별로 상한 — launch bounds
__global__ __launch_bounds__(256, 4)    // blockDim 256, SM당 최소 4 block
void myKernel(float* out, const float* in, int n)
{
    // 컴파일러가 이 제약을 만족하도록 레지스터를 줄임
    // ...
}
register spilling 주의 --maxrregcount로 레지스터를 강제로 줄이면 점유율은 올라가지만, 부족한 변수는 local memory(=global memory)로 흘러나간다(spill). 메모리 대역폭을 잡아먹어 오히려 느려질 수 있다. ptxas 출력에서 X bytes stack frame이 0이 아니면 spill 발생 신호다.

Occupancy Calculator와 API

CUDA Toolkit에 들어 있던 Excel 기반 Occupancy Calculator는 NVIDIA가 deprecate했고, 지금은 두 가지 권장 경로가 있다 — Nsight Compute의 occupancy 섹션과, 커널 launch 직전에 호출하는 런타임 API다.

cudaOccupancyMaxActiveBlocksPerMultiprocessor

#include <cuda_runtime.h>
#include <cstdio>

__global__ void myKernel(float* x, int n) { /* ... */ }

void inspectOccupancy()
{
    int device = 0;
    cudaDeviceProp prop{};
    cudaGetDeviceProperties(&prop, device);

    int blockSize = 256;
    int numBlocksPerSm = 0;
    cudaOccupancyMaxActiveBlocksPerMultiprocessor(
        &numBlocksPerSm,            // out
        myKernel,                   // 커널 함수 포인터
        blockSize,                  // blockDim
        0);                         // dynamic shared mem (bytes)

    int activeWarps  = numBlocksPerSm * (blockSize / 32);
    int maxWarps     = prop.maxThreadsPerMultiProcessor / 32;
    float occupancy  = (float)activeWarps / (float)maxWarps;

    printf("blocks/SM=%d, occupancy=%.2f\n", numBlocksPerSm, occupancy);
}

cudaOccupancyMaxPotentialBlockSize — 추천 블록 크기

// 점유율이 최대가 되는 block size를 자동으로 추천받는다
int minGridSize = 0;
int suggestedBlockSize = 0;
cudaOccupancyMaxPotentialBlockSize(
    &minGridSize,
    &suggestedBlockSize,
    myKernel,
    0,          // dynamic shared mem
    0);         // blockSizeLimit (0 = 제한 없음)

int gridSize = (n + suggestedBlockSize - 1) / suggestedBlockSize;
myKernel<<<gridSize, suggestedBlockSize>>>(x, n);
예시 출력 (RTX 3090, blockSize=256)
blocks/SM=6, occupancy=1.00 suggestedBlockSize=512, minGridSize=82
점유율은 목표가 아니라 진단 지표다 점유율을 100%로 만드는 것보다, 우선 메모리 결합·shared memory 활용·divergence를 잡는 게 보통 더 큰 이득이다. 점유율은 그다음에 본다. "왜 안 빠른가" 디버깅 단서로 쓸 것.

메모리 결합(Coalescing)

global memory는 32-byte / 128-byte 캐시 라인 단위로 트랜잭션이 일어난다. warp의 32 thread가 어떤 주소를 읽느냐에 따라 메모리 컨트롤러가 요구하는 트랜잭션 수가 달라진다. 32 thread가 연속된 128 byte 영역을 읽으면 한 번의 트랜잭션으로 처리되고, 이 상태를 coalesced(결합됨)라고 부른다.

결합 접근은 한 번의 트랜잭션으로 끝나고, 비결합 접근은 여러 트랜잭션으로 쪼개진다.
접근 패턴warp가 읽는 모양트랜잭션 수대역폭 효율
Coalesced — stride 1a[tid]1 (128B)100%
Misaligneda[tid + 1]2약 50%
Strided — stride 2a[tid * 2]2약 50%
Strided — stride 32a[tid * 32]32약 3%
Randoma[idx[tid]]최악 32매우 낮음

결합 접근 패턴

1D — thread id가 가장 안쪽 인덱스

// Good — coalesced
__global__ void vecAdd(const float* a, const float* b, float* c, int n)
{
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    if (tid < n)
    {
        c[tid] = a[tid] + b[tid];   // warp가 연속된 32 float을 읽음 → 1 transaction
    }
}

2D 이미지 — row-major에서 x가 가장 안쪽

이미지는 보통 row-major(행 우선)로 저장된다 — 같은 행의 픽셀들이 메모리에서 인접하다. 따라서 threadIdx.x가 열(x) 인덱스를 담당해야 결합이 된다.

// 이미지가 width × height, row-major (pitch 무시한 단순 예)
// img[y * width + x]

// Good — 같은 warp의 32 thread가 같은 행의 연속된 32 픽셀을 읽음
__global__ void blurGood(const uint8_t* in, uint8_t* out, int width, int height)
{
    int x = blockIdx.x * blockDim.x + threadIdx.x;   // x ← threadIdx.x
    int y = blockIdx.y * blockDim.y + threadIdx.y;
    if (x >= width || y >= height) return;

    int idx = y * width + x;
    out[idx] = in[idx];           // warp 32 thread → 같은 row, 32 pixel 연속
}

// Bad — x와 y를 바꿔 잡으면 stride = width 가 된다
__global__ void blurBad(const uint8_t* in, uint8_t* out, int width, int height)
{
    int x = blockIdx.y * blockDim.y + threadIdx.y;   // 뒤집힘
    int y = blockIdx.x * blockDim.x + threadIdx.x;
    if (x >= width || y >= height) return;

    int idx = y * width + x;
    out[idx] = in[idx];           // warp가 width만큼 떨어진 32 pixel을 읽음 → 결합 깨짐
}
pitch 정렬을 위해 cudaMallocPitch를 쓴다 2D 이미지를 cudaMallocPitch로 할당하면 각 row가 128 byte 경계에 정렬되어 결합이 깨지지 않는다. 단순 cudaMalloc(width * height)은 width가 128의 배수가 아니면 다음 행 시작이 어긋난다.

전치(Transpose) — 읽기와 쓰기 중 한쪽은 깨진다

행렬 전치는 결합 문제의 교과서 예제다. naive 버전은 읽기 또는 쓰기 중 하나가 stride=width가 되어 깨진다. shared memory를 거쳐서 둘 다 결합되게 만든다.

// Bad — 쓰기가 stride=width 로 깨진다
__global__ void transposeNaive(const float* in, float* out, int w, int h)
{
    int x = blockIdx.x * blockDim.x + threadIdx.x;
    int y = blockIdx.y * blockDim.y + threadIdx.y;
    if (x < w && y < h)
    {
        out[x * h + y] = in[y * w + x];   // 쓰기 비결합
    }
}

// Good — shared memory 타일을 거쳐 양쪽 모두 결합
constexpr int kTile = 32;
__global__ void transposeTiled(const float* in, float* out, int w, int h)
{
    __shared__ float tile[kTile][kTile + 1];   // +1: bank conflict 방지

    int x = blockIdx.x * kTile + threadIdx.x;
    int y = blockIdx.y * kTile + threadIdx.y;

    if (x < w && y < h)
        tile[threadIdx.y][threadIdx.x] = in[y * w + x];   // 결합된 읽기

    __syncthreads();

    int xt = blockIdx.y * kTile + threadIdx.x;            // 전치된 좌표
    int yt = blockIdx.x * kTile + threadIdx.y;

    if (xt < h && yt < w)
        out[yt * h + xt] = tile[threadIdx.x][threadIdx.y]; // 결합된 쓰기
}

AoS vs SoA

같은 데이터를 어떻게 묶느냐가 결합에 직접 영향을 준다. CPU에서는 캐시 친화적이라 자주 쓰던 AoS(Array of Structs)가 GPU에서는 결합을 깨는 패턴이 된다.

AoS는 컴포넌트가 인터리브되어 stride가 커지고, SoA는 각 컴포넌트가 연속이라 결합이 자연스럽다.
// Bad — AoS
struct Particle { float x, y, z, mass; };

__global__ void updateAoS(Particle* p, int n, float dt)
{
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    if (tid >= n) return;
    p[tid].x += p[tid].y * dt;     // warp가 stride=16 byte로 접근 → 비결합
}

// Good — SoA
struct ParticleSoA
{
    float* x;     // 길이 N
    float* y;
    float* z;
    float* mass;
};

__global__ void updateSoA(ParticleSoA p, int n, float dt)
{
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    if (tid >= n) return;
    p.x[tid] += p.y[tid] * dt;     // 두 배열 모두 stride 1 → 결합
}
혼합 전략 — AoSoA 구조체 안에 길이 32짜리 작은 배열을 두는 "AoSoA"(Array of Struct of Arrays)도 자주 쓴다. CPU 친화성과 GPU 결합을 절충할 때 유용하다.

정렬과 벡터 로드

결합은 주소가 정렬되어 있을 때 가장 잘 동작한다. cudaMalloc은 256 byte 정렬을 보장하므로 시작 주소는 걱정하지 않아도 된다. 문제는 그 안에서 offset이나 구조체 멤버가 어긋날 때다.

// 1) 자연 정렬 — 16 byte 단위로 한 번에 로드
//    float4는 16-byte aligned 타입, 하드웨어가 1 instruction으로 가져온다
__global__ void copyFloat4(const float4* in, float4* out, int n4)
{
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    if (tid < n4)
    {
        out[tid] = in[tid];      // 128-bit load/store, throughput 4배
    }
}

// 호출 — 길이를 4의 배수로 맞춰 reinterpret_cast
int n = 1 << 20;
float4* d_in  = reinterpret_cast<float4*>(d_in_raw);
float4* d_out = reinterpret_cast<float4*>(d_out_raw);
copyFloat4<<<(n/4 + 255) / 256, 256>>>(d_in, d_out, n / 4);

// 2) 사용자 구조체 강제 정렬
struct __align__(16) Vec3
{
    float x, y, z;     // 12 byte + 4 byte pad → 16-byte aligned
};
벡터 로드의 이득 float4·int4 로드는 LDG.128 명령으로 컴파일되어 명령 수를 1/4로 줄인다. 대역폭이 아니라 명령 발행이 병목인 커널에서 차이가 크다. 단, 데이터 개수가 4의 배수가 아니면 꼬리 처리 코드가 따로 필요하다.
