구조 패턴이란 무엇인가

구조 패턴(Structural Pattern)은 클래스와 객체를 조합해 더 큰 구조를 만들되, 그 구조가 유연하고 효율적으로 유지되도록 하는 패턴이다. GoF 23패턴 중 7개가 여기에 속하며, 6편의 생성 패턴이 "객체를 어떻게 만드느냐"를 다뤘다면 구조 패턴은 "만든 객체들을 어떻게 엮느냐"를 다룬다.

핵심 도구는 두 가지다. 상속으로 인터페이스나 구현을 합치거나, 합성(composition)으로 객체를 다른 객체 안에 품어 기능을 위임한다. GoF 책 자체가 "상속보다 합성"을 권하며, 실제로 구조 패턴 대부분은 합성을 중심에 둔다. 객체를 멤버로 들고 그 객체에 일을 넘기는 구조 — 이 단순한 골격 위에서 Adapter·Decorator·Facade·Proxy가 각자 다른 의도로 갈라진다.

구조는 비슷해도 의도가 패턴을 가른다 구조 패턴은 클래스 다이어그램만 보면 서로 닮았다. "다른 객체를 멤버로 들고 같은 인터페이스를 노출한다"는 골격을 여럿이 공유한다. 그래서 이 글은 코드 구조보다 왜 그 구조를 쓰는가, 즉 의도를 반복해서 강조한다.

Adapter — 인터페이스를 맞춘다

Adapter 패턴은 호환되지 않는 두 인터페이스 사이에 변환 계층을 끼워, 한쪽이 기대하는 형태로 다른 쪽을 감싸는 패턴이다. 전원 콘센트의 모양이 달라 끼울 수 없을 때 쓰는 여행용 어댑터와 정확히 같은 발상이다.

현실에서 Adapter가 필요한 순간은 거의 정해져 있다. 레거시 코드나 서드파티 라이브러리를 통합할 때다. 우리 코드는 IImageSource라는 인터페이스를 기대하는데, 들여온 라이브러리는 전혀 다른 메서드 이름과 시그니처를 가진다. 라이브러리 소스를 고칠 수는 없으므로, 그 사이에 어댑터를 둔다.

객체 어댑터 — 합성으로 감싼다

객체 어댑터(object adapter)는 적응 대상(adaptee)을 멤버로 들고, 우리 인터페이스 호출을 그 멤버의 메서드 호출로 변환한다. 합성 기반이므로 가장 널리 쓰인다.

// 우리 코드가 기대하는 인터페이스 (target)
class IImageSource
{
public:
    virtual ~IImageSource() = default;
    virtual ErrorCode Grab(Image& outImage) = 0;
    virtual bool IsConnected() const = 0;
};

// 서드파티 라이브러리 — 우리가 고칠 수 없는 코드 (adaptee)
class VendorCameraSdk
{
public:
    int  vendor_open();
    int  vendor_read_frame(unsigned char* buffer, int* len);
    void vendor_close();
};

// 객체 어댑터 — adaptee를 멤버로 들고 호출을 변환한다
class VendorCameraAdapter : public IImageSource
{
public:
    explicit VendorCameraAdapter(std::unique_ptr<VendorCameraSdk> sdk)
        : m_sdk(std::move(sdk))
    {
    }

    ErrorCode Grab(Image& outImage) override
    {
        // 우리 인터페이스 호출 -> 벤더 SDK 호출로 변환
        int length = 0;
        if (m_sdk->vendor_read_frame(outImage.MutableData(), &length) != 0)
        {
            return ErrorCode::DeviceError;
        }
        return ErrorCode::Ok;
    }

    bool IsConnected() const override
    {
        return m_isOpen;
    }

private:
    std::unique_ptr<VendorCameraSdk> m_sdk;   // adaptee를 합성으로 보유
    bool m_isOpen = false;
};

클래스 어댑터 — 상속으로 잇는다

클래스 어댑터(class adapter)는 target 인터페이스와 adaptee를 동시에 상속(C++의 다중 상속)해, 한 클래스 안에서 두 세계를 잇는다. adaptee의 protected 멤버에 접근할 수 있다는 장점이 있지만, 상속이 주는 강한 결합과 다중 상속의 복잡성 때문에 객체 어댑터보다 덜 권장된다.

// 클래스 어댑터 — target과 adaptee를 다중 상속한다
class VendorCameraClassAdapter
    : public IImageSource
    , private VendorCameraSdk   // adaptee를 private 상속
{
public:
    ErrorCode Grab(Image& outImage) override
    {
        int length = 0;
        // 상속받은 멤버 함수를 직접 호출한다
        if (vendor_read_frame(outImage.MutableData(), &length) != 0)
        {
            return ErrorCode::DeviceError;
        }
        return ErrorCode::Ok;
    }

    bool IsConnected() const override { return true; }
};
구분객체 어댑터클래스 어댑터
방식adaptee를 멤버로 합성target + adaptee 다중 상속
결합도느슨함 — 공개 인터페이스에만 의존강함 — adaptee 내부에 의존
런타임 교체가능 — 멤버를 바꿔 끼울 수 있음불가 — 컴파일 타임에 고정
권장도일반적 선택특수한 경우에만
Adapter는 "감싸기만" 한다 좋은 어댑터는 변환 외에 새 기능을 더하지 않는다. 호출 이름을 바꾸고, 자료형을 변환하고, 에러 코드를 우리 체계로 옮길 뿐이다. 어댑터 안에 비즈니스 로직이 들어가기 시작하면, 그것은 더 이상 어댑터가 아니라 정체불명의 중간 계층이 된다.

Decorator — 책임을 동적으로 더한다

Decorator 패턴은 객체에 런타임에 새로운 책임을 덧붙이는 패턴이다. 핵심은 상속이 아니라 합성으로 기능을 확장한다는 점이다. 데코레이터는 원본 객체와 같은 인터페이스를 구현하면서, 내부에 그 인터페이스 타입의 객체를 하나 품는다. 자기 일을 한 뒤 품은 객체에게 나머지를 위임한다.

상속으로 기능을 확장하면 조합마다 클래스가 폭발한다. "블러 + 샤픈", "블러 + 샤픈 + 감마보정"마다 별도 클래스를 만들 수는 없다. 데코레이터는 같은 인터페이스를 구현하므로 데코레이터가 데코레이터를 감쌀 수 있고, 이렇게 데코레이터 체인이 만들어진다.

데코레이터 체인 — 모두 같은 인터페이스라 서로를 감쌀 수 있다
// 공통 인터페이스 — 원본과 데코레이터가 모두 구현한다
class IImageFilter
{
public:
    virtual ~IImageFilter() = default;
    virtual ErrorCode Apply(Image& image) = 0;
};

// 핵심 객체 — 아무 장식도 없는 기본 구현
class RawImageFilter : public IImageFilter
{
public:
    ErrorCode Apply(Image& image) override
    {
        return ErrorCode::Ok;   // 원본 그대로 통과
    }
};

// 데코레이터 베이스 — 같은 인터페이스를 구현하고, 같은 인터페이스를 품는다
class FilterDecorator : public IImageFilter
{
public:
    explicit FilterDecorator(std::unique_ptr<IImageFilter> inner)
        : m_inner(std::move(inner))
    {
    }

protected:
    std::unique_ptr<IImageFilter> m_inner;   // 감싼 대상에게 위임한다
};

// 구체 데코레이터 1 — 블러 책임을 더한다
class BlurDecorator : public FilterDecorator
{
public:
    using FilterDecorator::FilterDecorator;

    ErrorCode Apply(Image& image) override
    {
        ErrorCode ec = m_inner->Apply(image);   // 먼저 안쪽에 위임
        if (ec != ErrorCode::Ok)
        {
            return ec;
        }
        return applyGaussianBlur(image);        // 그 다음 자기 책임 수행
    }

private:
    ErrorCode applyGaussianBlur(Image& image);
};

// 구체 데코레이터 2 — 샤픈 책임을 더한다
class SharpenDecorator : public FilterDecorator
{
public:
    using FilterDecorator::FilterDecorator;

    ErrorCode Apply(Image& image) override
    {
        ErrorCode ec = m_inner->Apply(image);
        if (ec != ErrorCode::Ok)
        {
            return ec;
        }
        return applyUnsharpMask(image);
    }

private:
    ErrorCode applyUnsharpMask(Image& image);
};

사용하는 쪽은 데코레이터를 양파처럼 겹쳐 체인을 조립한다. 조립은 런타임에 일어나므로, 사용자가 고른 옵션에 따라 필터 구성을 그때그때 다르게 만들 수 있다.

// 런타임에 체인을 조립한다 — 상속이라면 불가능한 유연성
std::unique_ptr<IImageFilter> filter = std::make_unique<RawImageFilter>();
filter = std::make_unique<BlurDecorator>(std::move(filter));
filter = std::make_unique<SharpenDecorator>(std::move(filter));

// 한 번의 Apply 호출이 체인 전체를 타고 흐른다
filter->Apply(image);   // Raw -> Blur -> Sharpen 순서로 실행
filter->Apply(image) 실행 흐름
SharpenDecorator::Apply 진입 BlurDecorator::Apply 진입 RawImageFilter::Apply 실행 (원본 통과) BlurDecorator 가우시안 블러 적용 SharpenDecorator 언샤프 마스크 적용
Decorator는 "상속의 조합 폭발"을 푸는 답이다 기능 N개를 상속으로 조합하면 클래스가 최대 2^N개로 늘어난다. 데코레이터는 N개의 데코레이터 클래스만으로 모든 조합을 런타임에 만들어 낸다. "기능을 자유롭게 켜고 끄고 싶다"는 요구가 보이면 Decorator를 떠올린다.

Facade — 복잡함에 단순한 창구를

Facade 패턴은 여러 클래스로 이뤄진 복잡한 서브시스템 앞에 단순한 통합 인터페이스 하나를 세우는 패턴이다. Facade는 프랑스어로 건물의 "정면"을 뜻한다. 건물 내부가 아무리 복잡해도 사람은 정문으로만 드나든다.

이미지 검사 시스템을 생각해 보자. 한 번 검사하려면 카메라 초기화, 프레임 획득, 전처리 필터, 측정 알고리즘, 판정 로직, 결과 로깅까지 예닐곱 개의 객체를 순서대로 다뤄야 한다. 이 모든 절차를 호출하는 쪽이 직접 알아야 한다면, 서브시스템의 내부 구조가 사용자 코드에 그대로 새어 나온다. Facade는 이 절차를 RunInspection() 한 메서드 뒤로 감춘다.

// 복잡한 서브시스템 — 여러 클래스가 협력한다
class CameraController { /* ... */ };
class PreprocessPipeline { /* ... */ };
class MeasurementEngine { /* ... */ };
class JudgementUnit { /* ... */ };
class ResultLogger { /* ... */ };

// Facade — 서브시스템 전체에 단순한 창구 하나를 제공한다
class InspectionFacade
{
public:
    // 호출하는 쪽은 이 메서드 하나만 알면 된다
    ErrorCode RunInspection(InspectionResult& outResult)
    {
        Image frame;
        if (m_camera.Capture(frame) != ErrorCode::Ok)
        {
            return ErrorCode::DeviceError;
        }

        m_preprocess.Run(frame);                  // 전처리
        MeasurementData data;
        m_measurement.Measure(frame, data);       // 측정
        outResult = m_judgement.Judge(data);      // 판정
        m_logger.Write(outResult);                // 로깅
        return ErrorCode::Ok;
    }

private:
    CameraController   m_camera;
    PreprocessPipeline m_preprocess;
    MeasurementEngine  m_measurement;
    JudgementUnit      m_judgement;
    ResultLogger       m_logger;
};
// 사용하는 쪽 — 서브시스템의 내부 구조를 전혀 몰라도 된다
InspectionFacade inspection;
InspectionResult result;
if (inspection.RunInspection(result) == ErrorCode::Ok)
{
    // 결과만 사용한다
}

중요한 점은 Facade가 서브시스템을 숨기는 것이지 봉인하는 것이 아니라는 것이다. 일반적인 작업은 Facade로 처리하되, 세밀한 제어가 필요한 고급 사용자는 여전히 MeasurementEngine을 직접 다룰 수 있어야 한다. Facade는 "쉬운 길"을 제공할 뿐, "유일한 길"을 강제하지 않는다.

Facade가 God Object로 자라는 것을 경계할 것 Facade는 편리해서 자꾸 메서드가 늘어난다. 처음엔 RunInspection() 하나였다가, 어느새 카메라 설정·필터 파라미터·로그 경로까지 전부 Facade를 거치게 된다. 그러면 Facade는 "단순한 창구"가 아니라 모든 것을 아는 거대 객체(God Object)가 되어, 서브시스템의 모든 변경이 Facade를 건드리게 된다. Facade는 흔한 사용 시나리오만 담아야 한다. 새 메서드를 더하기 전에 "이건 정말 흔한 작업인가, 아니면 고급 사용자가 직접 해야 할 일인가"를 물어야 한다.

Proxy — 대리자를 둔다

Proxy 패턴은 어떤 객체에 대한 접근을 대리자(proxy)를 통해 통제하는 패턴이다. 프록시는 실제 객체(real subject)와 같은 인터페이스를 구현하므로, 사용하는 쪽은 자기가 프록시를 쓰는지 실제 객체를 쓰는지 구분하지 못한다. 그 사이에서 프록시는 접근을 가로채 무언가를 한다 — 무엇을 하느냐에 따라 종류가 갈린다.

종류하는 일대표 용도
가상 프록시 (Virtual)실제 객체 생성을 실제로 필요할 때까지 미룬다대용량 리소스 지연 로딩
보호 프록시 (Protection)호출자의 권한을 검사한 뒤 통과시킨다접근 제어, 권한 관리
원격 프록시 (Remote)다른 프로세스·머신의 객체를 로컬처럼 보이게 한다네트워크 통신, RPC
캐싱 프록시 (Caching)비싼 연산 결과를 저장해 재사용한다반복 호출 비용 절감

가상 프록시 — 지연 로딩

가장 흔히 쓰이는 형태다. 고해상도 이미지나 GPU 메모리처럼 생성 비용이 큰 객체는, 정작 한 번도 안 쓰일 수도 있다. 가상 프록시는 실제 객체를 미리 만들지 않고, 처음 접근하는 순간에 만든다.

// 공통 인터페이스 — 프록시와 실제 객체가 모두 구현한다
class IImageData
{
public:
    virtual ~IImageData() = default;
    virtual const unsigned char* GetPixels() = 0;
    virtual int GetWidth() const = 0;
};

// 실제 객체 — 생성 비용이 크다 (디스크에서 대용량 이미지 로드)
class HighResImage : public IImageData
{
public:
    explicit HighResImage(const std::string& path)
    {
        loadFromDisk(path);   // 무겁다
    }

    const unsigned char* GetPixels() override { return m_pixels.data(); }
    int GetWidth() const override { return m_width; }

private:
    void loadFromDisk(const std::string& path);
    std::vector<unsigned char> m_pixels;
    int m_width = 0;
};

// 가상 프록시 — 실제 객체 생성을 첫 접근까지 미룬다
class HighResImageProxy : public IImageData
{
public:
    explicit HighResImageProxy(std::string path)
        : m_path(std::move(path))
    {
    }

    const unsigned char* GetPixels() override
    {
        ensureLoaded();                  // 필요한 순간에만 생성
        return m_real->GetPixels();
    }

    int GetWidth() const override
    {
        // 폭만 필요하면 메타데이터로 답할 수도 있다
        return m_cachedWidth;
    }

private:
    void ensureLoaded()
    {
        if (!m_real)
        {
            m_real = std::make_unique<HighResImage>(m_path);   // 지연 생성
        }
    }

    std::string m_path;
    int m_cachedWidth = 0;
    std::unique_ptr<HighResImage> m_real;   // 처음엔 nullptr
};

보호 프록시 — 권한 검사

보호 프록시는 실제 객체에 접근하기 전에 호출자의 권한을 확인한다. 실제 객체는 권한 개념을 전혀 모르고, 그 책임은 온전히 프록시에 격리된다.

// 보호 프록시 — 권한을 검사한 뒤에만 실제 객체에 위임한다
class CameraConfigProxy : public ICameraConfig
{
public:
    CameraConfigProxy(std::shared_ptr<ICameraConfig> real, UserRole role)
        : m_real(std::move(real))
        , m_role(role)
    {
    }

    ErrorCode SetExposure(double microseconds) override
    {
        if (m_role != UserRole::Engineer)
        {
            return ErrorCode::PermissionDenied;   // 권한 없으면 차단
        }
        return m_real->SetExposure(microseconds);  // 통과 시에만 위임
    }

private:
    std::shared_ptr<ICameraConfig> m_real;
    UserRole m_role;
};
Proxy의 공통점 — 사용자는 차이를 모른다 네 종류의 프록시는 하는 일이 다르지만 한 가지를 공유한다. 사용하는 쪽이 인터페이스만 보고 코딩하므로, 실제 객체가 프록시로 바뀌어도 호출 코드는 한 줄도 변하지 않는다. 이 "투명한 대체 가능성"이 Proxy를 강력하게 만드는 동시에, 뒤에서 다룰 디버깅 함정의 원인이 되기도 한다.

Composite — 부분과 전체를 같게

Composite 패턴은 객체들을 트리 구조로 구성해 부분-전체 계층을 표현하고, 개별 객체(leaf)와 복합 객체(composite)를 같은 인터페이스로 다루게 하는 패턴이다. 파일 시스템이 전형적인 예다. 파일 하나도, 수많은 파일을 담은 폴더도, 모두 "크기를 계산할 수 있는 것"으로 똑같이 취급된다.

이미징 SDK의 처리 그래프도 같은 구조다. 단일 필터 블록 하나와, 여러 블록을 묶은 블록 그룹을 동일하게 "실행 가능한 처리 단위"로 다룰 수 있으면, 그룹 안에 그룹을 중첩하는 일도 자연스럽게 풀린다.

Composite 트리 — BlockGroup 안에 BlockGroup을 중첩해도 Run() 호출법은 같다
// 공통 인터페이스 — leaf와 composite가 모두 구현한다
class IProcessNode
{
public:
    virtual ~IProcessNode() = default;
    virtual ErrorCode Run(Image& image) = 0;
};

// Leaf — 더 쪼갤 수 없는 개별 처리 단위
class BlurBlock : public IProcessNode
{
public:
    ErrorCode Run(Image& image) override
    {
        return applyBlur(image);
    }

private:
    ErrorCode applyBlur(Image& image);
};

// Composite — 자식을 담고, 자식들에게 재귀적으로 위임한다
class BlockGroup : public IProcessNode
{
public:
    void AddChild(std::unique_ptr<IProcessNode> child)
    {
        m_children.push_back(std::move(child));
    }

    ErrorCode Run(Image& image) override
    {
        // leaf든 composite든 구분 없이 같은 방식으로 호출한다
        for (const auto& child : m_children)
        {
            ErrorCode ec = child->Run(image);
            if (ec != ErrorCode::Ok)
            {
                return ec;
            }
        }
        return ErrorCode::Ok;
    }

private:
    std::vector<std::unique_ptr<IProcessNode>> m_children;
};

BlockGroup::Run이 자식을 호출할 때 그 자식이 단일 블록인지 또 다른 그룹인지 신경 쓰지 않는다는 점이 핵심이다. 트리가 아무리 깊어져도 클라이언트 코드는 루트 노드의 Run() 한 번만 호출하면 된다.

Bridge — 추상과 구현을 분리

Bridge 패턴은 추상(abstraction)과 구현(implementation)을 별개의 클래스 계층으로 분리해, 둘이 독립적으로 확장될 수 있게 하는 패턴이다. 한 계층에서 두 축의 변화를 모두 상속으로 처리하려 하면, 클래스 수가 두 축의 곱으로 폭발한다.

예를 들어 도형(원·사각형)이라는 축과, 렌더링 방식(CPU·GPU)이라는 축이 있다고 하자. 상속만 쓰면 CpuCircle, GpuCircle, CpuRectangle, GpuRectangle... 2×2가 필요하고, 축이 늘면 더 심해진다. Bridge는 "렌더링 방식" 축을 별도 인터페이스로 떼어 내, 도형이 그것을 합성으로 들고 위임하게 만든다.

// 구현 계층 — "어떻게 그리는가" 축
class IRenderer
{
public:
    virtual ~IRenderer() = default;
    virtual void DrawCircle(double x, double y, double radius) = 0;
};

class CpuRenderer : public IRenderer { /* ... */ };
class GpuRenderer : public IRenderer { /* ... */ };

// 추상 계층 — "무엇을 그리는가" 축. 구현 계층을 합성으로 들고 있다 (= 다리)
class Shape
{
public:
    explicit Shape(std::shared_ptr<IRenderer> renderer)
        : m_renderer(std::move(renderer))
    {
    }
    virtual ~Shape() = default;
    virtual void Draw() = 0;

protected:
    std::shared_ptr<IRenderer> m_renderer;   // 이 멤버가 두 계층을 잇는 "다리"
};

// 추상 계층의 확장 — 렌더러 종류와 무관하게 추가된다
class Circle : public Shape
{
public:
    Circle(std::shared_ptr<IRenderer> renderer, double r)
        : Shape(std::move(renderer)), m_radius(r)
    {
    }

    void Draw() override
    {
        m_renderer->DrawCircle(0.0, 0.0, m_radius);   // 구현 계층에 위임
    }

private:
    double m_radius;
};

이제 새 도형을 추가해도 렌더러 계층은 건드리지 않고, 새 렌더러(예: CudaRenderer)를 추가해도 도형 계층은 그대로다. 두 축이 독립적으로 자란다. Decorator·Proxy가 "같은 인터페이스를 감싸는" 구조라면, Bridge는 "서로 다른 두 계층을 잇는" 구조라는 점이 다르다.

Adapter vs Decorator vs Proxy

이 세 패턴은 클래스 다이어그램이 거의 같다. 셋 다 다른 객체를 멤버로 들고, 같은(또는 비슷한) 인터페이스를 노출하며, 호출을 그 객체로 위임한다. 그래서 코드만 보면 구분이 안 된다. 차이는 오직 의도에 있다.

패턴의도 — 무엇을 위해인터페이스핵심 질문
Adapter호환되지 않는 인터페이스를 맞춘다감싼 대상과 다르다 (변환)"인터페이스가 안 맞는가?"
Decorator객체에 책임을 더한다감싼 대상과 같다 (기능 추가)"기능을 덧붙이고 싶은가?"
Proxy객체에 대한 접근을 통제한다감싼 대상과 같다 (접근 제어)"접근을 가로채야 하는가?"
Facade복잡한 서브시스템을 단순화한다서브시스템과 전혀 새롭다"창구가 하나 필요한가?"

정리하면 이렇다. Adapter는 인터페이스를 바꾼다 — 기능은 그대로 두고 모양만 맞춘다. Decorator는 인터페이스를 유지하면서 기능을 더한다 — 같은 타입인데 일을 더 한다. Proxy도 인터페이스를 유지하지만 기능을 더하지 않는다 — 단지 실제 객체로 가는 길목을 지킨다. 같은 골격이라도 "왜 감쌌는가"를 물으면 셋은 분명히 갈라진다.

Decorator와 Proxy의 미세한 차이 둘 다 같은 인터페이스를 감싼다. 차이는 관계다. Decorator는 보통 클라이언트가 직접 체인을 조립하고, 여러 개를 겹칠 것을 전제한다. Proxy는 보통 실제 객체를 프록시 스스로 관리하며(생성·수명 포함), 하나만 둔다. "내가 겹쳐 쌓는가" vs "그것이 뒤에서 알아서 관리하는가"로 보면 구분이 쉽다.

산업 SW 관점

구조 패턴은 산업용 이미징 SDK에서 억지로 끼우는 장식이 아니라, 문제 구조가 분명한 곳에서 자연스럽게 드러난다. 네 패턴이 각각 어디에 들어맞는지 보면 의도가 더 또렷해진다.

설계 지점드러나는 패턴이유
카메라 SDK 통일AdapterVieworks·Basler·FLIR 등 제조사별로 API가 제각각이다. 어댑터로 IImageSource 하나로 통일한다
이미지 처리 필터 체인Decorator블러·샤픈·감마보정을 사용자가 자유롭게 켜고 끄며 체인으로 조립한다
검사 시스템 진입점Facade카메라·전처리·측정·판정·로깅을 RunInspection() 하나 뒤로 감춘다
GPU 메모리 지연 로딩Proxy이미지를 GPU에 올리는 비용이 크므로, GPU 연산이 처음 필요한 순간까지 업로드를 미룬다

특히 카메라 SDK Adapter는 산업 SW의 거의 모든 프로젝트에서 등장한다. 제조사별 SDK는 API 이름도, 에러 처리 방식도, 픽셀 버퍼 레이아웃도 다르다. 이것을 코드 곳곳에서 if (vendor == Basler) ...로 분기하면 새 카메라를 지원할 때마다 전체 코드가 흔들린다. 각 제조사 SDK를 어댑터로 감싸 IImageSource로 통일하면, 상위 코드는 어떤 카메라인지 영영 몰라도 된다.

// GPU 메모리 지연 로딩 — 가상 프록시가 자연스럽게 드러나는 지점.
// EnsureGpu()가 처음 호출될 때만 실제 업로드가 일어난다.
class GpuImageProxy : public IGpuImage
{
public:
    explicit GpuImageProxy(const Image& cpuImage)
        : m_cpuImage(cpuImage)
    {
    }

    ErrorCode EnsureGpu() override
    {
        if (!m_uploaded)
        {
            ErrorCode ec = uploadToGpu(m_cpuImage);   // 첫 접근에만 업로드
            if (ec != ErrorCode::Ok)
            {
                return ec;
            }
            m_uploaded = true;
        }
        return ErrorCode::Ok;
    }

private:
    ErrorCode uploadToGpu(const Image& image);
    Image m_cpuImage;
    bool m_uploaded = false;
};

여기서도 순서가 중요하다. 설계자가 "Proxy를 쓰자"라고 먼저 결정한 게 아니다. "GPU 업로드는 비싸고, 안 쓰일 수도 있다"는 요구가 먼저 있었고, 그것을 정직하게 풀다 보니 결과가 가상 프록시의 모양이 된 것이다. 패턴 이름은 그 구조에 붙는 사후 라벨일 뿐이다.

흔한 함정

함정 1 — Adapter와 Decorator를 혼동한다

가장 흔한 혼동이다. 둘 다 객체를 감싸지만 목적이 정반대 방향이다. Adapter는 인터페이스를 바꾸되 기능은 그대로 두고, Decorator는 인터페이스를 유지하되 기능을 더한다. 어댑터를 만들면서 슬그머니 새 기능을 끼워 넣으면, 그것은 어댑터도 데코레이터도 아닌 정체불명의 클래스가 된다. 감싸는 클래스를 만들 때는 먼저 물어야 한다 — "나는 모양을 맞추는가, 일을 더하는가?"

함정 2 — Facade가 God Object가 된다

Facade는 편리해서 메서드가 계속 붙는다. 단순한 창구로 시작했다가, 결국 서브시스템의 모든 기능이 Facade를 거치게 되면, 서브시스템의 어떤 변경이든 Facade를 건드려야 한다. Facade는 흔한 시나리오만 담고, 고급 제어는 서브시스템 클래스를 직접 열어 두는 것이 맞다. Facade의 메서드 개수가 계속 늘고 있다면 경고 신호다.

패턴 혼동과 God Object는 "의도를 잊었을 때" 생긴다 함정 1과 2는 뿌리가 같다. 패턴을 구조(클래스 다이어그램)로만 외우고 의도를 잊으면, Adapter에 기능을 더하고 Facade에 모든 것을 몰아넣게 된다. 패턴을 쓸 때마다 "이 패턴이 풀려던 문제가 무엇인가"를 다시 확인하면 두 함정은 대부분 피할 수 있다.

함정 3 — Proxy 남용으로 디버깅이 어려워진다

Proxy의 강점인 "투명한 대체 가능성"이 그대로 약점이 된다. 호출 코드가 자기가 프록시를 쓰는지 실제 객체를 쓰는지 모르므로, 버그가 났을 때 호출 한 줄이 실제로는 권한 검사·지연 로딩·캐시 조회·네트워크 왕복을 거칠 수 있다. 프록시를 여러 겹 쌓으면 스택 트레이스가 프록시 계층으로 뒤덮여, 정작 실제 객체에서 무슨 일이 일어나는지 보이지 않는다. Proxy는 정말 필요한 한 겹만 두고, 어떤 종류의 프록시인지 이름에 분명히 드러내야 한다.

함정 4 — 데코레이터 체인이 너무 깊어진다

데코레이터는 자유롭게 겹칠 수 있어서, 거꾸로 너무 깊게 겹쳐지기 쉽다. 체인이 열 겹을 넘어가면 Apply() 한 번이 어떤 순서로 무엇을 거치는지 추적하기 어렵고, 같은 데코레이터가 실수로 두 번 들어가도 알아채기 힘들다. 또 순서 의존성도 함정이다 — "블러 후 샤픈"과 "샤픈 후 블러"는 결과가 다른데, 체인 조립 코드만 봐서는 의도한 순서인지 알기 어렵다. 데코레이터가 서너 겹을 넘기 시작하면, 그 조합을 의미 있는 이름의 클래스로 묶거나 빌더로 조립 과정을 명시하는 편이 낫다.

정리 — 구조 패턴은 "조합의 기술"이다 구조 패턴은 객체를 엮어 큰 구조를 만드는 도구다. Adapter는 모양을 맞추고, Decorator는 기능을 더하고, Facade는 복잡함을 감추고, Proxy는 접근을 지키고, Composite는 트리를 같게 다루고, Bridge는 두 축을 분리한다. 구조가 닮았어도 의도가 다르다는 점, 그리고 모든 패턴은 문제가 있을 때만 쓴다는 점 — 이 두 가지를 기억하면 된다. 다음 8편에서는 행위 패턴을 다룬다.
