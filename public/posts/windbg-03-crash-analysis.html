1편에서 덤프를 받고, 2편에서 WinDbg와 심볼을 맞췄다. 이제 본론이다. 덤프를 열고 "왜 죽었는가"를 짚어낸다. 핵심은 두 가지다. 어떤 종류의 사고였는지(예외 코드), 그리고 사고 직전에 어떤 경로로 거기까지 왔는지(콜스택). 이 둘을 읽으면 대부분의 크래시는 윤곽이 잡힌다.

!analyze -v 읽는 법

!analyze -v는 출력이 길다. 처음 보면 압도되지만, 실제로 집중해서 봐야 할 줄은 몇 개뿐이다. 아래는 전형적인 출력을 핵심만 추린 예시다.

0:000> !analyze -v
*******************************************************************************
*                        Exception Analysis                                   *
*******************************************************************************

EXCEPTION_CODE: (NTSTATUS) 0xc0000005 - ... 0x... 명령이 0x... 메모리를 참조했습니다.

FAULTING_IP:
VisionCore!ImageBuffer::At+2a
00007ff8`9c2e567a 0fb60401        movzx   eax,byte ptr [rax+rax]

EXCEPTION_RECORD:  (.exr -1)
ExceptionAddress: 00007ff89c2e567a (VisionCore!ImageBuffer::At+0x000000000000002a)
   ExceptionCode: c0000005 (Access violation)
  ExceptionFlags: 00000000
NumberParameters: 2
   Parameter[0]: 0000000000000000   <- 읽기(0) 시도
   Parameter[1]: 0000000000000000   <- 접근하려던 주소 = 0 (널!)

PROCESS_NAME:  MyVisionApp.exe

STACK_TEXT:
00 VisionCore!ImageBuffer::At+0x2a
01 VisionCore!GaussianFilter::Apply+0x1f4
02 VisionCore!ProcessBlock::Execute+0x88
03 HostApp!Pipeline::Run+0x143
04 HostApp!main+0x66

MODULE_NAME: VisionCore
IMAGE_NAME:  VisionCore.dll
FAILURE_BUCKET_ID: NULL_POINTER_READ_c0000005_VisionCore.dll!ImageBuffer::At

이 출력에서 반드시 확인하는 네 가지는 다음과 같다.

필드의미이 예시에서
EXCEPTION_CODE사고의 종류0xc0000005 — Access Violation
FAULTING_IP크래시가 난 기계 명령 위치ImageBuffer::At 함수 내부
STACK_TEXT그 지점까지 온 호출 경로Pipeline → Execute → Apply → At
MODULE_NAME의심 모듈VisionCore (우리 모듈!)
FAILURE_BUCKET_ID는 요약 한 줄이다 맨 아래 FAILURE_BUCKET_ID는 WinDbg가 위 정보를 한 줄로 압축한 분류 키다. 위 예시의 NULL_POINTER_READ_c0000005_VisionCore.dll!ImageBuffer::At만 봐도 "VisionCore의 ImageBuffer::At에서 널 포인터 읽기로 죽었다"가 그대로 읽힌다. 여러 덤프를 같은 버킷으로 묶어 "동일 원인인지" 판단할 때도 유용하다.
!analyze의 MODULE_NAME을 맹신하지 않는다 !analyze -v는 휴리스틱으로 "범인"을 추정한다. 그런데 진짜 원인은 우리 모듈인데 크래시는 시스템 DLL 안에서 났거나, 반대로 시스템 모듈이 지목됐지만 실제로는 우리가 넘긴 잘못된 인자가 원인인 경우도 많다. !analyze의 결론은 출발점으로 삼고, 콜스택을 직접 읽어 검증한다.

콜스택 읽기 — k 계열 명령

콜스택(call stack)은 "지금 이 함수에 오기까지 거쳐 온 호출 경로"다. 크래시 분석의 중심이며, k 계열 명령으로 본다. 접미사에 따라 정보량이 달라진다.

k / kb / kn / kp 차이

명령보여 주는 것쓰는 상황
k기본 콜스택 (Child-SP, RetAddr, Call Site)전체 흐름을 빠르게 훑을 때
kb위 + 인자 앞 3개(스택 기준)넘어온 값을 가늠할 때
kn위 + 프레임 번호특정 프레임으로 이동(.frame)하기 전
kp완전한 함수 인자(이름·값)private pdb가 있을 때 정밀 분석
kv위 + 호출 규약·FPO 정보스택이 의심스러울 때
x64에서 kb 인자는 참고만 kb가 보여 주는 인자는 x86 시절 스택 전달 방식을 전제로 한다. x64는 앞쪽 인자를 레지스터로 전달하므로, kb의 인자 3개가 실제 호출 인자와 다를 수 있다. x64에서 인자를 정확히 보려면 private pdb를 갖춘 상태에서 kp를 쓰거나, .frame으로 해당 프레임에 들어가 dv로 확인한다.

스택 프레임 해석

kn 출력의 한 줄을 뜯어보면 콜스택 읽는 법이 잡힌다.

0:000> kn
 # Child-SP          RetAddr           Call Site
00 000000ab`12dff8a0 00007ff8`9c2e1abc VisionCore!ImageBuffer::At+0x2a
01 000000ab`12dff8e0 00007ff8`9c2e0d44 VisionCore!GaussianFilter::Apply+0x1f4
02 000000ab`12dff920 00007ff8`9c2dffaa VisionCore!ProcessBlock::Execute+0x88
03 000000ab`12dff990 00007ff7`aabb1234 HostApp!Pipeline::Run+0x143
04 000000ab`12dffa10 00007ff7`aabb0066 HostApp!main+0x66
  • 맨 위(프레임 00)가 크래시가 난 지점이다. 여기서는 ImageBuffer::At 함수 내부 +0x2a 위치다.
  • 아래로 내려갈수록 "그 함수를 부른 쪽"이다. main → Pipeline::Run → Execute → Apply → At 순으로 호출이 흘렀고, 가장 깊은 At에서 터졌다.
  • 모듈!함수+0x오프셋 형식에서 오프셋은 함수 시작점부터의 거리다. 줄번호까지 보려면 private pdb가 필요하다.
  • Child-SP는 그 프레임의 스택 포인터, RetAddr은 그 함수가 끝나면 돌아갈 주소다.
읽는 방향 — 위에서 아래로 "왜"를 묻는다 맨 위 프레임이 "무엇이 터졌나"이고, 한 줄씩 내려가며 "누가 그걸 불렀나 → 왜 그런 인자로 불렀나"를 추적한다. 크래시는 At에서 났지만, 원인은 그 위 어딘가(예: Apply가 잘못된 좌표를 넘겼다)에 있는 경우가 대부분이다. 그래서 맨 위만 보고 끝내지 않는다.

주요 예외 패턴

예외 코드만 봐도 사고 유형이 절반은 좁혀진다. 현장에서 자주 만나는 세 가지를 정리한다.

0xC0000005
Access Violation
접근 권한 없는 메모리 참조. 널 포인터, 해제된 메모리, 범위 밖 인덱스가 주범이다.
0xC00000FD
Stack Overflow
스택 가드 페이지 침범. 거의 무한 재귀 또는 과도한 스택 할당이 원인이다.
0xE06D7363
C++ Exception
C++ throw가 처리되지 않음. 매직 넘버 'msc'에서 유래한 코드다.

Access Violation (0xC0000005)

가장 흔한 크래시다. 허용되지 않은 메모리를 건드렸을 때 발생한다. !analyze -v의 EXCEPTION_RECORD에 담긴 두 파라미터가 결정적 단서다.

  • Parameter[0] — 접근 유형. 0=읽기, 1=쓰기, 8=실행(DEP 위반)을 뜻한다.
  • Parameter[1] — 접근하려던 주소.

이 두 값으로 원인 유형을 좁힌다.

  • 주소가 0 또는 그 근처(0x00000008 등) → 널 포인터 역참조일 가능성이 높다. 객체 포인터가 null인 채로 멤버에 접근한 경우다.
  • 접근 유형이 쓰기(1)이고 주소가 그럴듯한 큰 값 → 버퍼 경계를 넘어 범위 밖 쓰기(out-of-bounds write)일 수 있다.
  • 주소가 한때 유효했을 법한 값인데 지금은 죽어 있음 → 해제 후 사용(use-after-free)이나 댕글링 포인터를 의심한다.

Stack Overflow (0xC00000FD)

스택을 다 써 버려 가드 페이지를 침범하면 발생한다. 현장에서는 대부분 무한 재귀가 원인이다. 콜스택을 보면 진단이 즉각적이다 — 같은 함수들이 끝없이 반복되기 때문이다.

0:000> k
 # Call Site
00 VisionCore!ContourNode::Traverse+0x33
01 VisionCore!ContourNode::Traverse+0x33
02 VisionCore!ContourNode::Traverse+0x33
03 VisionCore!ContourNode::Traverse+0x33
...
(동일 프레임이 수천 줄 반복)

이런 패턴이 보이면 종료 조건이 빠진 재귀를 의심한다. 콜스택이 너무 길어 잘리면 kn 200처럼 프레임 수를 지정해 본다.

C++ 예외 (0xE06D7363)

코드 0xE06D7363은 C++ throw로 던져진 예외가 끝까지 처리되지 않아 프로세스가 종료된 경우다. 끝의 6D7363이 ASCII로 'msc'(Microsoft C++)라서 외워 두면 바로 알아본다. 이 경우 콜스택의 위쪽에 RaiseException, _CxxThrowException 같은 런타임 함수가 보이고, 그 아래로 실제 throw를 일으킨 우리 함수가 나온다.

어떤 예외가 던져졌나 C++ 예외 덤프에서는 던져진 예외 객체의 타입을 확인하는 것이 핵심이다. .exr -1로 예외 레코드를 보고, 콜스택 아래쪽의 우리 함수를 짚으면 "어떤 검사 단계에서 무슨 예외를 던졌는지"가 드러난다. 우리 SDK가 내부 예외를 API 경계에서 ErrorCode로 변환하도록 설계돼 있다면, 이 크래시는 그 경계가 뚫렸다는 신호이기도 하다.

콜스택에서 내 코드 찾기

콜스택에는 우리 모듈과 시스템 DLL이 뒤섞여 나온다. 분석의 요령은 그 사이에서 "우리 코드"를 빠르게 식별하는 것이다.

lm / lmvm — 모듈 식별과 버전 확인

lm은 로드된 모듈 목록을, lmvm <모듈>은 특정 모듈의 상세 정보를 보여 준다. 우리 모듈의 버전이 덤프와 일치하는지 확인하는 핵심 명령이다.

:: 로드된 모듈 목록 — 심볼 상태도 함께 표시
0:000> lm

:: 우리 모듈 상세 — 경로, 타임스탬프, 버전, pdb 매칭
0:000> lmvm VisionCore
    Image path: C:\Program Files\MyVision\VisionCore.dll
    Image name: VisionCore.dll
    Timestamp:  ...
    File version:     1.4.2.0
    Symbol file: C:\ProductSymbols\VisionCore.pdb
    Loaded symbol image file: VisionCore.dll

시스템 모듈은 익숙해지면 한눈에 걸러진다. ntdll, kernel32, kernelbase, ucrtbase, vcruntime140, msvcp140 등은 Windows·런타임 모듈이다. 콜스택에서 이들을 제외하고 남는 VisionCore, HostApp 같은 이름이 우리가 봐야 할 코드다.

.ecxr / r / dv — 사고 현장으로 이동

덤프를 열면 디버거의 현재 컨텍스트가 예외 지점이 아닐 수 있다. .ecxr로 예외가 발생한 바로 그 컨텍스트로 이동한 뒤 콜스택과 레지스터, 지역 변수를 본다.

:: 예외 컨텍스트 레코드로 이동 (사고 현장으로 점프)
0:000> .ecxr

:: 그 시점의 레지스터 — rax 등에서 문제 포인터를 추적
0:000> r

:: n번 프레임으로 들어간 뒤 지역 변수 확인 (private pdb 필요)
0:000> .frame 1
0:000> dv
            this = 0x000001f2`33aa0090
        srcImage = 0x000001f2`33aa0100
       kernelSize = 5
            width = 2448
           height = 0          <- 의심스러운 값!

dv(display variables)는 private pdb가 있어야 지역 변수를 이름과 값으로 보여 준다. 위처럼 height = 0 같은 값이 잡히면, 콜스택만으로는 안 보이던 "왜"의 실마리가 풀린다. 변수의 타입 구조를 더 파고들 때는 dt(display type)를 함께 쓴다.

dv가 안 보이면 풀 덤프 + private pdb를 확인 dv로 지역 변수가 안 나오거나 <value unavailable>로 뜬다면, 미니덤프라 메모리가 없거나(1편 참고) private pdb가 아닌 export 심볼만 잡힌 상태(2편 참고)다. 변수 값까지 봐야 하는 분석에서 1·2편의 준비가 그대로 효력을 발휘한다.

머신비전 실전 시나리오

지금까지의 명령을 하나의 가상 사례로 엮어 본다. 고객사 제보는 이랬다고 하자. "특정 카메라로 라인 검사 중 가끔 프로그램이 그냥 꺼진다. 항상은 아니고 어쩌다 한 번." WER LocalDumps로 풀 덤프를 받아 열었다.

1단계 — !analyze -v로 큰 그림

예외 코드는 0xC0000005(Access Violation), 접근 유형은 쓰기(Parameter[0]=1), 의심 모듈은 VisionCore였다. 콜스택은 다음과 같았다.

0:000> .ecxr
0:000> kn
 # Call Site
00 VisionCore!ImageBuffer::SetPixel+0x41
01 VisionCore!ThresholdFilter::Apply+0x2da
02 VisionCore!ProcessBlock::Execute+0x88
03 HostApp!InspectionPipeline::RunFrame+0x1c7
04 HostApp!CameraGrabThread::OnFrame+0x95

2단계 — 콜스택 해석

맨 위는 ImageBuffer::SetPixel, 쓰기 도중 크래시. 호출 경로는 카메라 프레임 콜백(OnFrame)에서 시작해 검사 파이프라인을 거쳐 ThresholdFilter가 픽셀을 쓰다가 터졌다. "쓰기 + 범위 밖 주소"는 버퍼 경계를 넘은 쓰기의 전형이다.

3단계 — dv로 변수 확인

풀 덤프라 지역 변수를 볼 수 있었다. ThresholdFilter::Apply 프레임으로 들어가 dv를 실행했다.

0:000> .frame 1
0:000> dv
        this = 0x000001f2`33aa0090
    srcImage = 0x000001f2`33aa0100
       width = 2448
      height = 2050        <- 버퍼가 가정한 높이
      stride = 2448
          y = 2049
          x = 0
0:000> dt VisionCore!ImageBuffer 0x000001f2`33aa0100
   +0x010 m_width  : 0n2448
   +0x014 m_height : 0n2048   <- 실제 버퍼 높이!

여기서 모순이 드러난다. 필터는 height = 2050을 전제로 루프를 돌았는데, 실제 ImageBuffer의 m_height는 2048이었다. 2048 높이로 잡힌 버퍼에 y = 2049 행을 쓰려다 경계를 넘어 Access Violation이 난 것이다.

4단계 — 결론과 재현 조건

"가끔만" 죽는 이유도 설명된다. 대부분의 프레임은 높이가 일치하지만, 특정 트리거 타이밍에서 이전 해상도 설정값(2050)으로 필터가 돌고 버퍼는 새 해상도(2048)로 재할당된 한 프레임에서만 어긋난다. 즉 카메라 해상도 변경과 버퍼 재할당 사이의 경합(race)이 의심된다. 분석 결과를 다음처럼 정리해 개발팀과 고객에게 전달한다.

  • 증상 — 라인 검사 중 간헐적 크래시
  • 직접 원인 — ImageBuffer::SetPixel에서 범위 밖 쓰기(0xC0000005, write)
  • 근본 원인 — 필터가 사용한 높이(2050)와 버퍼 실제 높이(2048) 불일치, 해상도 변경 시점의 경합 추정
  • 재현 조건 — 해상도 변경 직후 첫 프레임
  • 조치 방향 — 필터 진입 시 버퍼의 실제 m_width/m_height로 경계 검증, 해상도 변경과 버퍼 재할당의 동기화
덤프가 "재현 없는 재현"을 만든다 개발 PC에서 한 번도 재현 못 한 문제였지만, 풀 덤프 하나로 버퍼의 실제 멤버 값까지 확인해 근본 원인을 좁혔다. 이것이 덤프 분석의 힘이다. 콜스택으로 "어디서"를, 변수 값으로 "왜"를 메우면, 현장에 가지 않고도 원인에 도달한다.

정리와 시리즈 마무리

세 편에 걸친 흐름을 다시 한 줄로 잇는다.

  • 1편 — 사용자 모드 덤프를 이해하고, WER LocalDumps·ProcDump로 현장에서 받아온다. 제품 버전을 함께 받는다.
  • 2편 — WinDbg를 설치하고, OS 심볼은 공개 서버로, 우리 모듈은 버전별 pdb로 맞춘다.
  • 3편(이 글) — !analyze -v로 예외 코드·콜스택을 읽고, k/lmvm/.ecxr/dv로 우리 코드의 원인을 짚는다.

실무에서 가장 중요한 습관은 단순하다. "예외 코드로 유형을 좁히고, 콜스택으로 위치를 찾고, 변수 값으로 이유를 메운다." 이 순서를 지키면 대부분의 크래시는 원인까지 추적된다. 그리고 그 출발점은 늘 좋은 덤프와 맞는 심볼이라는 것을, 1·2편이 받쳐 준다.

다음 단계 여기까지가 "크래시 원인 분석"의 기본기다. 한 걸음 더 들어가면 힙 손상(!heap, PageHeap)과 데드락·행(멀티스레드 추적) 분석이 기다린다. 같은 트러블슈팅 시리즈에서 이어 다룬다. 우선은 이 세 편의 흐름을 실제 덤프 하나로 처음부터 끝까지 따라 해 보는 것을 권한다.
