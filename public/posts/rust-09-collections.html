컬렉션 — Vec·String·HashMap

2026-06-25 약 8분 분량 Rust 시리즈
이 편에서 배우는 것 Rust의 표준 컬렉션 셋 — 가변 길이 배열 Vec<T>, 소유권 있는 문자열 String과 빌린 문자열 슬라이스 &str, 키-값 저장소 HashMap<K, V> — 을 다룬다. 단순히 API를 나열하지 않고, 이 컬렉션들이 소유권·빌림 규칙과 어떻게 맞물리는지를 중심에 둔다. C++의 std::vector·std::string·std::unordered_map을 알고 있다는 전제로, 무엇이 같고 무엇이 더해졌는지 짚는다.

Vec<T> — 가변 길이 배열

Vec<T>는 같은 타입 T의 값을 힙에 연속으로 저장하는 가변 길이 배열이다. C++의 std::vector<T>와 메모리 레이아웃·성능 특성이 사실상 같다 — 끝에 추가하는 push는 분할상환 O(1)이고, 용량이 모자라면 더 큰 버퍼로 재할당한다.

fn main() {
    // 빈 벡터를 만들고 타입을 추론하게 한다
    let mut numbers: Vec<i32> = Vec::new();
    numbers.push(10);
    numbers.push(20);
    numbers.push(30);

    // vec! 매크로로 초기값과 함께 만들 수도 있다
    let primes = vec![2, 3, 5, 7, 11];

    // 인덱싱은 범위를 벗어나면 패닉, get은 Option을 돌려준다
    println!("첫 소수: {}", primes[0]);
    match primes.get(99) {
        Some(v) => println!("값: {}", v),
        None => println!("범위를 벗어남"),
    }

    println!("길이: {}, 합계: {}", numbers.len(), numbers.iter().sum::<i32>());
}

핵심 차이는 안전성이다. primes[99]처럼 범위를 벗어난 인덱싱은 정의되지 않은 동작이 아니라 패닉으로 즉시 멈춘다. 경계를 직접 다루고 싶으면 get이 Option<&T>를 돌려주므로, 없는 경우를 match나 if let으로 명시적으로 처리한다.

C++과 이렇게 다르다 — 인덱싱 std::vector에서 v[99]는 범위를 검사하지 않아 정의되지 않은 동작이고, 검사하려면 v.at(99)로 예외를 받는다. Rust는 v[99]가 항상 경계를 검사해 패닉으로 멈추고, 예외 대신 v.get(99)가 Option을 돌려준다. "조용한 손상" 대신 "즉시 중단" 또는 "명시적 None"이 기본값이다.

String과 &str

Rust의 문자열은 둘로 나뉜다. String은 힙에 데이터를 소유한 가변 문자열이고, &str(문자열 슬라이스)은 어딘가에 있는 UTF-8 바이트를 빌려서 가리키는 읽기 전용 뷰다. 문자열 리터럴 "hello"의 타입은 &str이며 바이너리에 박혀 있다.

fn main() {
    // String: 소유하는 가변 문자열
    let mut greeting = String::from("안녕");
    greeting.push_str(", 세상"); // &str를 이어 붙인다
    greeting.push('!');           // 문자 하나를 붙인다

    // &str: 빌린 뷰. String은 &str로 자동 변환된다(deref coercion)
    let view: &str = &greeting;
    println!("길이(바이트): {}", view.len());

    // 함수 인자는 &str로 받는 게 관례 — String과 리터럴 둘 다 받는다
    print_upper(&greeting);  // String -> &str
    print_upper("리터럴");    // &str 그대로
}

// &str로 받으면 호출자가 소유권을 넘길 필요가 없다
fn print_upper(s: &str) {
    println!("{}", s.to_uppercase());
}

실무 관례는 분명하다. 함수가 문자열을 읽기만 한다면 인자는 &str로 받는다. 그러면 호출하는 쪽은 String이든 리터럴이든 그대로 빌려줄 수 있고, 소유권을 넘기지 않아도 된다. 반환하거나 보관할 문자열을 새로 만들어야 할 때만 String을 쓴다.

한 가지 주의할 점은 len()이 글자 수가 아니라 UTF-8 바이트 수를 돌려준다는 것이다. "안녕"은 6바이트다. 문자 단위로 다루려면 chars()로 반복한다.

fn main() {
    let word = "café";
    println!("바이트 수: {}", word.len());          // 5 (é는 2바이트)
    println!("문자 수: {}", word.chars().count());  // 4

    for c in word.chars() {
        print!("[{}]", c);  // [c][a][f][é]
    }
    println!();
}

HashMap<K, V>

HashMap<K, V>는 키 K를 값 V에 대응시키는 해시 기반 저장소다. C++의 std::unordered_map과 같은 역할이며, 표준 라이브러리에 들어 있지만 프렐류드(prelude)에는 없어 use std::collections::HashMap;로 가져와야 한다.

use std::collections::HashMap;

fn main() {
    let mut scores: HashMap<String, i32> = HashMap::new();
    scores.insert(String::from("blue"), 10);
    scores.insert(String::from("red"), 50);

    // get은 Option<&V>를 돌려준다 — 없는 키를 안전하게 다룬다
    if let Some(score) = scores.get("blue") {
        println!("blue: {}", score);
    }

    // entry: 키가 없을 때만 기본값을 넣고, 가변 참조를 돌려준다
    let count = scores.entry(String::from("green")).or_insert(0);
    *count += 1; // green이 없었으면 0을 넣고 1로 만든다

    for (team, score) in &scores {
        println!("{}: {}", team, score);
    }
}

가장 자주 쓰는 패턴은 entry(...).or_insert(...)다. "키가 있으면 그 값을, 없으면 기본값을 넣고 그 값을" 가변 참조로 돌려주므로, 조회·삽입·갱신을 한 번에 처리한다. 단어 빈도 세기 같은 작업에 특히 깔끔하다.

use std::collections::HashMap;

fn main() {
    let text = "the cat the dog the bird";
    let mut counts: HashMap<&str, i32> = HashMap::new();

    // split_whitespace는 &str 슬라이스들을 돌려준다
    for word in text.split_whitespace() {
        *counts.entry(word).or_insert(0) += 1;
    }

    // the: 3, cat: 1, dog: 1, bird: 1 (순서는 보장되지 않음)
    println!("{:?}", counts);
}
순회 순서는 보장되지 않는다 std::unordered_map과 마찬가지로 HashMap의 반복 순서는 정해져 있지 않다. 게다가 Rust 표준 HashMap은 기본적으로 해시 시드를 무작위화하므로, 같은 프로그램이라도 실행마다 순서가 달라질 수 있다. 정렬된 키 순회가 필요하면 BTreeMap을 쓴다.

컬렉션과 소유권

여기가 C++ 경험자가 가장 새롭게 느끼는 지점이다. 컬렉션에 값을 넣는 순간, 그 값의 소유권이 어떻게 되는지를 컴파일러가 추적한다.

넣으면 이동(move)한다

String처럼 Copy가 아닌 값을 컬렉션에 넣으면 소유권이 컬렉션으로 이동한다. 이동 후 원래 변수는 더 이상 쓸 수 없고, 이를 어기면 컴파일 자체가 막힌다.

fn main() {
    let name = String::from("Horus");
    let mut list: Vec<String> = Vec::new();

    list.push(name); // name의 소유권이 list로 이동

    // println!("{}", name); // 컴파일 오류: name은 이미 이동됨
    println!("{}", list[0]); // 이렇게 컬렉션을 통해 접근한다
}

반면 i32·f64·bool처럼 Copy 트레잇을 구현한 작은 값은 넣을 때 복사되므로 원본을 계속 쓸 수 있다. 이 구분은 "스택에 통째로 들어가는 값이냐, 힙 자원을 소유하느냐"로 기억하면 된다.

C++과 이렇게 다르다 — 넣은 뒤의 변수 C++에서 vec.push_back(std::move(name))를 하면 name은 "유효하지만 미지정 상태"로 남아 실수로 다시 써도 컴파일은 통과한다. Rust는 이동된 name을 다시 쓰는 코드를 컴파일 단계에서 거부한다. use-after-move 류의 버그가 런타임이 아니라 빌드에서 걸러진다.

빌리면 함께 잠긴다

컬렉션을 빌리는 동안에는 그 컬렉션을 동시에 변경할 수 없다. 예를 들어 Vec를 &로 빌려 어떤 요소를 가리키는 중에 push를 하면, 재할당으로 그 참조가 무효가 될 수 있으므로 컴파일러가 막는다.

fn main() {
    let mut v = vec![1, 2, 3];

    let first = &v[0]; // v를 불변으로 빌림
    println!("첫 값: {}", first); // 빌림이 여기서 끝난다

    v.push(4); // 빌림이 끝난 뒤이므로 OK
    println!("{:?}", v);
}

위 코드는 first를 마지막으로 쓴 직후 빌림이 끝나므로 push가 허용된다. 만약 first를 push 뒤에서 다시 썼다면, 그 사이 push 때문에 v를 동시에 변경하는 셈이 되어 컴파일이 거부된다. C++의 "push_back 후 기존 반복자/포인터 무효화"가 런타임 함정이었다면, Rust는 같은 문제를 컴파일 타임 규칙으로 바꿔 놓은 것이다.

반복 처리

Rust는 컬렉션을 반복하는 세 가지 방식을 소유권 기준으로 명확히 나눈다. 어느 것을 고르느냐가 곧 "원소를 빌릴지, 가변으로 빌릴지, 소유권을 가져갈지"를 결정한다.

형태각 원소 타입컬렉션은?쓸 때
for x in &v (iter)&T그대로 남음읽기만 할 때
for x in &mut v (iter_mut)&mut T그대로 남음제자리에서 수정
for x in v (into_iter)T소비됨(move)원소를 꺼내 가져갈 때
fn main() {
    let mut v = vec![1, 2, 3];

    // 1) 불변 빌림: 읽기만 한다. v는 그대로 남는다
    for x in &v {
        println!("읽기: {}", x); // x는 &i32
    }

    // 2) 가변 빌림: 제자리에서 두 배로 만든다
    for x in &mut v {
        *x *= 2; // x는 &mut i32, 역참조로 수정
    }
    println!("{:?}", v); // [2, 4, 6]

    // 3) 소유권 이동: v를 소비하며 합을 구한다
    let total: i32 = v.into_iter().sum();
    println!("합: {}", total); // 12
    // 이 시점 이후 v는 더 이상 쓸 수 없다(소비됨)
}

이터레이터는 어댑터와 조합하면 더 강력해진다. map·filter·collect를 엮어 새 컬렉션을 만드는 방식은 선언적이면서도 보통 수동 루프만큼 효율적이다(이터레이터가 게으르게 평가되고 최적화에서 풀어 헤쳐지기 때문이다).

fn main() {
    let nums = vec![1, 2, 3, 4, 5, 6];

    // 짝수만 골라 제곱한 새 Vec를 만든다
    let even_squares: Vec<i32> = nums
        .iter()                  // &i32 들의 이터레이터
        .filter(|&&n| n % 2 == 0) // 짝수만 통과
        .map(|&n| n * n)         // 제곱
        .collect();              // Vec<i32>로 모음

    println!("{:?}", even_squares); // [4, 16, 36]
}

collect()는 타입 추론으로 무엇을 만들지 결정한다. 위에서는 좌변의 Vec<i32> 표기가 그 단서다. HashMap이나 String으로도 모을 수 있어, 컬렉션 사이 변환의 공통 출구 역할을 한다.

고르는 한 줄 기준 반복할 때 "원소를 읽기만 하면 &v, 제자리에서 고치면 &mut v, 꺼내 가져가면 v". 이 세 가지를 소유권으로 구분하는 습관이 곧 빌림 검사기와 싸우지 않는 길이다. 의심스러우면 가장 약한 권한인 불변 빌림(&v)부터 시작한다.
