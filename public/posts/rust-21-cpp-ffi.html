C++/C 연동 — FFI 실전

2026-06-25 약 8분 분량 Rust 시리즈
이 편에서 배우는 것 Rust의 FFI는 새 ABI를 만드는 게 아니라, C가 이미 깔아 둔 평탄한 ABI 위에 올라타는 일이다. 이 편에서는 extern "C" 경계와 #[no_mangle]로 함수를 노출하는 법, #[repr(C)]로 구조체 레이아웃을 맞추는 법, bindgen·cbindgen으로 헤더를 자동 생성하는 흐름, 그리고 기존 C++ 코드베이스에 Rust를 점진적으로 끼워 넣는 전략을 다룬다. C++ 경험자가 C++/CLI와 무엇이 다른지 대조하며 읽으면 빠르다.

왜 FFI인가 — C ABI라는 공용어

Rust로 새 프로젝트를 통째로 짜는 경우는 드물다. 대개는 검증된 C/C++ 자산이 이미 있고, 그 일부만 Rust로 바꾸거나 반대로 C에서 Rust 루틴을 호출하고 싶다. 이때 두 언어를 잇는 접착제가 FFI(Foreign Function Interface)다.

핵심은 Rust와 C++가 직접 대화하지 않는다는 점이다. 둘 다 C ABI라는 평탄하고 안정적인 호출 규약 위에서 만난다. C ABI는 이름 맹글링이 없고, 데이터 레이아웃이 단순하며, 사실상 모든 플랫폼이 표준으로 합의한 바닥이다. Rust는 자체 ABI를 안정화하지 않았지만, C ABI를 따르는 함수와 타입은 명시적으로 노출할 수 있다.

C++/CLI와 무엇이 다른가 C++ 진영에서 .NET과 네이티브를 잇던 C++/CLI는 /clr로 컴파일된 관리(managed) 런타임이라는 무거운 다리를 놓는다. 반면 Rust FFI는 런타임도, GC도, 마샬링 계층도 없다. 그냥 같은 프로세스 안에서 C 함수 하나를 호출하는 것과 동일한 비용이다. "다리를 놓는다"가 아니라 "이미 깔린 C ABI라는 바닥에 같이 선다"에 가깝다.

extern "C"와 #[no_mangle] — 경계 만들기

FFI 경계는 두 방향이 있다. Rust가 C 함수를 부르는 쪽과, Rust가 함수를 C에 내보내는 쪽이다.

C 함수를 Rust에서 부르기

C 라이브러리의 함수를 쓰려면 extern "C" 블록에 시그니처를 선언한다. 선언만으로는 정의가 없으므로, 이 호출은 항상 unsafe 안에서 한다. 컴파일러가 외부 함수의 계약을 검증할 수 없기 때문이다.

// C 표준 라이브러리의 abs를 직접 선언해서 부른다.
unsafe extern "C" {
    fn abs(input: i32) -> i32;
}

fn main() {
    // 외부 함수 호출은 컴파일러가 안전을 보장할 수 없으므로 unsafe.
    let value = unsafe { abs(-42) };
    println!("abs(-42) = {value}");
}

Rust 함수를 C에 내보내기

반대로 Rust 함수를 C가 부르게 하려면 두 가지가 필요하다. extern "C"로 C 호출 규약을 지정하고, #[no_mangle]로 이름 맹글링을 꺼서 심볼 이름을 그대로 유지한다. 맹글링을 끄지 않으면 링커가 함수를 못 찾는다.

// C에서 add_one(int) 으로 그대로 호출 가능한 심볼을 만든다.
#[no_mangle]
pub extern "C" fn add_one(value: i32) -> i32 {
    value + 1
}

// 패닉이 FFI 경계를 넘으면 정의되지 않은 동작이다.
// 경계 함수 안에서는 패닉 가능성을 직접 막거나 catch_unwind로 감싼다.
#[no_mangle]
pub extern "C" fn safe_divide(a: i32, b: i32) -> i32 {
    if b == 0 {
        return 0; // 패닉 대신 호출자가 약속한 기본값을 돌려준다.
    }
    a / b
}
패닉은 경계를 넘으면 안 된다 Rust 패닉이 extern "C" 경계를 넘어 C 쪽으로 풀려 나가는 것은 정의되지 않은 동작이다. 경계 함수는 패닉할 수 있는 코드를 std::panic::catch_unwind로 감싸거나, 애초에 패닉하지 않도록 작성해 오류를 반환값(예: -1이나 널 포인터)으로 표현한다.

repr(C)와 포인터 — 데이터 전달

함수 시그니처가 정수뿐이면 쉽지만, 구조체나 문자열이 끼면 메모리 레이아웃을 맞춰야 한다. Rust의 기본 구조체 레이아웃은 컴파일러가 자유롭게 재배치할 수 있어 C와 호환되지 않는다. #[repr(C)]를 붙이면 필드 순서와 정렬이 C 규칙을 따라, 양쪽이 같은 바이트 배치를 본다.

use std::os::raw::c_double;

// repr(C)로 C 구조체와 동일한 메모리 레이아웃을 보장한다.
#[repr(C)]
pub struct Point {
    pub x: c_double,
    pub y: c_double,
}

// 구조체를 값으로 받고 새 값을 돌려준다. 소유권 문제가 없다.
#[no_mangle]
pub extern "C" fn point_midpoint(a: Point, b: Point) -> Point {
    Point {
        x: (a.x + b.x) / 2.0,
        y: (a.y + b.y) / 2.0,
    }
}

문자열과 포인터 — 널 종료와 수명

문자열은 가장 까다롭다. Rust의 String/&str은 길이를 따로 갖지만, C 문자열은 널(\0) 종료에 의존한다. 경계에서는 std::ffi::CStr(C→Rust 읽기)와 CString(Rust→C 생성)을 쓴다. C에서 받은 포인터는 반드시 널 검사를 한 뒤 다룬다.

use std::ffi::CStr;
use std::os::raw::c_char;

// C가 넘긴 널 종료 문자열의 길이를 센다.
// 포인터를 역참조하므로 함수 전체가 unsafe 계약을 진다.
#[no_mangle]
pub unsafe extern "C" fn c_strlen(ptr: *const c_char) -> usize {
    if ptr.is_null() {
        return 0; // 널 포인터는 역참조하지 않고 0을 돌려준다.
    }
    // 호출자가 유효한 널 종료 문자열을 줬다고 약속한 경우에만 안전하다.
    let c_str = CStr::from_ptr(ptr);
    c_str.to_bytes().len()
}

여기서 빌림 규칙을 위반하지 않는 게 중요하다. CStr::from_ptr가 돌려주는 &CStr은 원본 포인터가 가리키는 메모리를 빌릴 뿐 소유하지 않는다. 따라서 C 쪽이 그 메모리를 해제하기 전까지만 유효하며, Rust 함수가 반환되면 빌림도 끝난다. 반대로 Rust가 CString으로 만든 문자열을 C에 넘겨주면, 그 메모리는 Rust가 소유하므로 나중에 Rust가 다시 회수해 해제해야 한다.

bindgen과 cbindgen — 헤더 자동화

경계가 함수 몇 개면 손으로 선언해도 되지만, 헤더가 수백 줄이면 비현실적이다. 두 도구가 양방향을 자동화한다.

BINDGEN C 헤더 → Rust 선언 자동 생성 build.rs + bindgen

기존 C/C++ 라이브러리의 .h 헤더를 읽어 그에 대응하는 Rust extern "C" 선언과 #[repr(C)] 구조체를 자동으로 뽑아낸다. C 자산을 Rust에서 소비할 때 쓴다.

방향: C/C++ → Rust. 큰 외부 라이브러리를 Rust에서 호출할 때.

CBINDGEN Rust 코드 → C 헤더 자동 생성 cbindgen.toml

반대로 #[no_mangle] extern "C" 함수와 #[repr(C)] 타입이 든 Rust 크레이트를 분석해 C/C++가 #include할 .h 헤더를 생성한다. Rust로 짠 라이브러리를 C++에 제공할 때 쓴다.

방향: Rust → C/C++. Rust 라이브러리를 기존 C++ 빌드에 노출할 때.

아래는 build.rs에서 bindgen으로 C 헤더 바인딩을 생성하는 전형적인 골격이다. 빌드 시점에 wrapper.h를 읽어 bindings.rs를 만들고, 본문에서 include!로 끌어 쓴다.

// build.rs — 빌드 스크립트에서 bindgen 실행.
fn main() {
    // 링크할 C 라이브러리를 카고에 알린다.
    println!("cargo:rustc-link-lib=mylib");

    let bindings = bindgen::Builder::default()
        .header("wrapper.h")          // 대상 C 헤더
        .generate()
        .expect("failed to generate bindings");

    // 생성된 Rust 선언을 OUT_DIR에 기록한다.
    let out = std::path::PathBuf::from(std::env::var("OUT_DIR").unwrap());
    bindings
        .write_to_file(out.join("bindings.rs"))
        .expect("failed to write bindings");
}
C++/CLI 래퍼와 대비 C++/CLI에서는 네이티브 타입을 관리 타입으로 손으로 마샬링하는 래퍼 클래스를 직접 짰다. bindgen/cbindgen은 그 손작업을 빌드 파이프라인의 코드 생성으로 대체한다. 마샬링 비용이 사라지는 대신, 양쪽 타입이 같은 메모리 레이아웃을 공유한다는 계약을 개발자가 #[repr(C)]로 보증해야 한다.

기존 C++ 코드 잇기 — 점진 도입

FFI의 진짜 가치는 전면 재작성 없이 코드베이스 일부만 Rust로 옮길 수 있다는 점이다. C++/CLI가 .NET 경계 하나를 통째로 그어야 했다면, C ABI 기반 FFI는 함수 단위로 야금야금 도입할 수 있다.

불투명 핸들로 객체 수명 넘기기

Rust 객체를 C++가 들고 다니게 하려면, 내부 구조를 노출하지 않고 void* 같은 불투명 핸들로만 넘긴다. Rust는 Box::into_raw로 힙 객체의 소유권을 포인터로 내보내고, 나중에 Box::from_raw로 도로 가져와 해제한다. 생성과 해제를 짝지어 노출하는 게 핵심이다.

// C++가 들고 다닐 카운터 객체. 내부는 숨긴다.
pub struct Counter {
    value: i64,
}

// 생성: 힙에 만들고 소유권을 raw 포인터로 넘긴다.
#[no_mangle]
pub extern "C" fn counter_new() -> *mut Counter {
    Box::into_raw(Box::new(Counter { value: 0 }))
}

// 사용: 핸들을 빌려 값을 1 올린다.
#[no_mangle]
pub extern "C" fn counter_increment(handle: *mut Counter) {
    if handle.is_null() {
        return;
    }
    // 호출자가 유효한 핸들을 줬다는 계약 아래 가변 참조를 빌린다.
    let counter = unsafe { &mut *handle };
    counter.value += 1;
}

// 해제: 소유권을 Box로 되찾아 드롭시킨다. 생성과 반드시 짝짓는다.
#[no_mangle]
pub extern "C" fn counter_free(handle: *mut Counter) {
    if handle.is_null() {
        return;
    }
    // from_raw로 소유권 회수 → 스코프 끝에서 메모리 해제.
    unsafe { drop(Box::from_raw(handle)); }
}

이 패턴에서 빌림 규칙은 그대로 지켜진다. counter_increment는 핸들을 빌려 가변 참조를 잠깐 만들 뿐 소유권을 가져가지 않으므로, 같은 핸들을 이후에 다시 쓸 수 있다. 소유권을 실제로 회수하는 건 counter_free 하나뿐이고, 그 뒤로 그 핸들을 다시 쓰면 안 된다는 계약을 C++ 쪽이 지켜야 한다.

순수 C ABI가 부담되면 cxx를 고려한다 손으로 unsafe 경계를 관리하기 부담스러운 C++ 상호운용이라면, cxx 크레이트처럼 안전한 양방향 브리지를 코드 생성으로 제공하는 도구를 검토할 만하다. 이 글은 그 바닥에 깔린 C ABI 메커니즘을 다뤘고, 상위 도구들도 결국 같은 경계 위에서 동작한다.

정리와 주의

  • C ABI가 공용 바닥 — Rust와 C++는 직접 말하지 않고 평탄한 C ABI 위에서 만난다. extern "C" + #[no_mangle]이 그 입구다.
  • 레이아웃은 명시로 맞춘다 — 구조체는 #[repr(C)]로 C와 동일 배치를 보장하고, 문자열은 CStr/CString으로 널 종료를 다룬다.
  • 소유권 경계를 분명히 — 누가 메모리를 소유하고 누가 해제하는지 함수 쌍(new/free)으로 못 박는다. 빌림은 함수 반환과 함께 끝난다.
  • 패닉을 가두라 — 패닉이 경계를 넘으면 UB다. 오류는 반환값으로 표현하거나 catch_unwind로 감싼다.
  • 자동화로 규모를 감당 — 헤더가 커지면 bindgen(C→Rust)·cbindgen(Rust→C)으로 선언 생성을 맡긴다.
  • 점진 도입이 강점 — C++/CLI식 전면 경계 대신, 함수 단위로 Rust를 끼워 넣어 기존 코드를 살리며 옮길 수 있다.
