GPU 버그가 찾기 어려운 이유

CPU 프로그램의 버그는 대개 디버거로 멈춰서 변수를 보면 찾을 수 있다. GPU 커널은 사정이 다르다.

특징디버깅에 미치는 영향
스레드 수만 개가 동시에 실행"어느 스레드"에서 문제가 났는지부터 찾아야 함
커널 실행은 비동기오류가 실제로 난 곳이 아니라 한참 뒤의 API 호출에서 보고됨
배열 범위를 넘어도 바로 죽지 않음다른 버퍼를 조용히 덮어써서 엉뚱한 곳에서 증상이 나타남
실행 순서가 매번 다름race condition은 가끔만 틀리고, 디버거를 붙이면 사라지기도 함
디버그 빌드는 최적화가 꺼짐릴리스에서만 나는 버그가 디버그 빌드에서는 재현되지 않음

그래서 GPU 디버깅은 "디버거로 한 줄씩 보기"보다 오류 검사 습관 + 자동 검사 도구 + CPU 기준 결과와 비교를 먼저 쓴다. 디버거는 원인 범위를 좁힌 뒤에 꺼낸다.

1단계 - 모든 호출의 오류 검사

가장 기본이면서 가장 자주 빠뜨리는 단계다. CUDA API는 오류를 예외가 아니라 반환값으로 알린다. 반환값을 버리면 오류가 조용히 묻힌다.

#define CUDA_CHECK(call)                                                        \
    do {                                                                        \
        cudaError_t err__ = (call);                                             \
        if (err__ != cudaSuccess) {                                             \
            fprintf(stderr, "CUDA error %s (%d) at %s:%d\n  %s\n",              \
                    cudaGetErrorName(err__), (int)err__, __FILE__, __LINE__,    \
                    cudaGetErrorString(err__));                                 \
            std::abort();                                                       \
        }                                                                       \
    } while (0)

// kernel launches return nothing: check in two steps
#define KERNEL_CHECK()                                                          \
    do {                                                                        \
        CUDA_CHECK(cudaGetLastError());            /* bad launch config */      \
        if (g_debugSync) CUDA_CHECK(cudaDeviceSynchronize()); /* errors inside the kernel */ \
    } while (0)

CUDA_CHECK(cudaMalloc(&d_buf, bytes));
MyKernel<<<grid, block, 0, stream>>>(d_buf, n);
KERNEL_CHECK();

커널 오류는 두 종류다.

종류예잡는 방법
실행 설정 오류블록당 스레드 1025개, shared memory 한도 초과실행 직후 cudaGetLastError()
실행 중 오류범위 밖 접근(illegal address), 장치 assert 실패동기화 후에야 보임. 그 전까지는 다음 API 호출이 대신 오류를 받음
되돌릴 수 없는 오류 (sticky error) cudaErrorIllegalAddress, cudaErrorLaunchFailure, cudaErrorAssert 같은 실행 중 오류가 나면 CUDA context 전체가 망가진다. 이후 모든 CUDA 호출이 같은 오류를 돌려주며, 복구하려면 cudaDeviceReset()이나 프로세스 재시작이 필요하다. 12편의 디바이스 복구 설계가 필요한 이유다. "아무 API나 계속 실패한다"면 그보다 앞에서 난 첫 오류를 찾아야 한다.
CUDA_LAUNCH_BLOCKING=1 환경 변수 CUDA_LAUNCH_BLOCKING=1을 설정하고 실행하면 모든 커널 실행이 동기로 바뀐다. 오류가 실제로 난 커널 바로 다음 호출에서 보고되므로 "어느 커널이 문제인지"를 빠르게 좁힐 수 있다. 성능은 떨어지므로 디버깅할 때만 쓴다.

2단계 - compute-sanitizer

compute-sanitizer는 CUDA Toolkit에 들어 있는 자동 검사 도구다. 프로그램을 다시 빌드하지 않고 실행 파일 앞에 붙여서 돌리면 된다. 예전의 cuda-memcheck를 대신하는 도구로, cuda-memcheck는 CUDA 12에서 제거되었다.

# default tool = memcheck
compute-sanitizer ./my_app

# choose a tool explicitly
compute-sanitizer --tool memcheck  --leak-check full ./my_app
compute-sanitizer --tool racecheck ./my_app
compute-sanitizer --tool initcheck ./my_app
compute-sanitizer --tool synccheck ./my_app

# Windows
compute-sanitizer.exe --tool memcheck my_app.exe
도구찾는 버그대표 증상
memcheckglobal, shared, local 메모리 범위 밖 접근, 정렬 오류, 메모리 누수(--leak-check full), API 오류illegal address, 다른 버퍼 값이 깨짐
racecheckshared memory의 race condition (동기화 없이 같은 주소를 읽고 쓰기)결과가 실행마다 가끔 다름
initcheck초기화하지 않은 global memory 읽기첫 프레임만 이상하거나, 실행마다 다른 쓰레기 값
synccheck잘못된 동기화 (분기 안의 __syncthreads(), 잘못된 mask의 __syncwarp)커널 멈춤, 정의되지 않은 결과

출력 읽는 법

13편 리덕션 커널에서 범위 검사를 빠뜨렸다고 하자. memcheck는 대략 다음과 같은 보고를 낸다.

========= Invalid __global__ read of size 4 bytes
=========     at Reduce4(const float *, float *, int)+0x1b0 in reduce.cu:42
=========     by thread (255,0,0) in block (4095,0,0)
=========     Address 0x7f3a2c400000 is out of bounds
=========     and is 1 bytes after the nearest allocation at 0x7f3a2bc00000 of size 8388608 bytes
줄알려 주는 것
Invalid __global__ read of size 4global memory에서 4바이트(float 하나) 읽기가 잘못됨
at ... reduce.cu:42커널 이름과 소스 줄 번호 (아래 -lineinfo 필요)
by thread (255,0,0) in block (4095,0,0)문제를 일으킨 스레드와 블록 좌표. 마지막 블록의 마지막 스레드이므로 경계 처리 문제임을 짐작
1 bytes after the nearest allocation할당 영역 바로 뒤를 읽음. 전형적인 "끝 하나 넘김" (off-by-one)
줄 번호를 보려면 -lineinfo nvcc에 -lineinfo를 주면 최적화는 그대로 두고 소스 줄 정보만 넣는다. 릴리스 빌드에 넣어도 성능 영향이 거의 없으므로, sanitizer와 Nsight Compute(8편)를 위해 기본으로 켜 두는 것이 좋다. 디버거로 한 줄씩 실행하려면 -G가 필요한데, 이것은 최적화를 끈다.

실행 팁

상황방법
너무 느림 (수십 배 이상 느려짐)작은 입력(작은 영상, 프레임 몇 장)으로 실행. 문제가 되는 커널만 검사하려면 --kernel-name kns=Reduce처럼 커널 이름으로 걸러냄
오류가 너무 많이 나옴첫 오류만 보고 고친 뒤 다시 실행. 첫 오류가 뒤의 오류를 연쇄로 만드는 경우가 많음
CI에서 자동 검사--error-exitcode 1로 오류가 있으면 실패 코드를 돌려주게 해서 테스트 단계에 넣음
라이브러리 내부 경고가 섞임내 코드의 커널만 필터링해서 실행

3단계 - 커널 안의 printf와 assert

커널 안에서도 printf를 쓸 수 있다. 수만 스레드가 모두 찍으면 읽을 수 없으므로 조건으로 대상을 좁힌다.

__global__ void Debayer(const unsigned short* raw, float3* rgb, int w, int h)
{
    int x = blockIdx.x * blockDim.x + threadIdx.x;
    int y = blockIdx.y * blockDim.y + threadIdx.y;

    // only one suspicious pixel
    if (x == 1023 && y == 767)
        printf("raw=%u at (%d,%d), block (%d,%d) thread (%d,%d)\n",
               raw[y * w + x], x, y, blockIdx.x, blockIdx.y, threadIdx.x, threadIdx.y);

    // device assert: stops the kernel with cudaErrorAssert (removed when NDEBUG is defined)
    assert(x < w + 32 && y < h + 32);
    ...
}
항목내용
출력 시점커널 안에서 바로 찍히지 않고 버퍼에 모였다가 동기화 시점(cudaDeviceSynchronize 등)에 출력됨
버퍼 크기기본 1MB 정도. 넘치면 뒤쪽 출력이 사라짐. cudaDeviceSetLimit(cudaLimitPrintfFifoSize, bytes)로 키움
출력 순서스레드 사이 순서는 보장되지 않음
성능printf가 있으면 커널이 느려지고 레지스터 사용도 늘어남. 확인 후 반드시 제거
assert#include <cassert> 후 사용. 실패하면 파일, 줄, 스레드 좌표를 출력하고 context가 망가짐(sticky)

4단계 - 디버거로 한 줄씩 보기

범위가 좁혀졌는데도 원인이 안 보이면 디버거를 쓴다. GPU 디버거는 스레드 하나를 골라서 그 스레드 시점으로 변수를 보는 방식이다.

Windows - Nsight Visual Studio Edition

Windows에서 Visual Studio를 쓴다면 Nsight Visual Studio Edition이 CUDA Toolkit 설치 시 함께 들어간다.

순서할 일
1CUDA 프로젝트 속성에서 Device → Generate GPU Debug Information을 "예"로 (-G)
2커널 코드 줄에 중단점 설정
3메뉴 Extensions → Nsight → Start CUDA Debugging (Next-Gen)으로 실행 (일반 F5 디버깅은 CPU 코드만 멈춤)
4중단점에서 멈추면 Locals 창에 현재 스레드의 변수, Warp Info 창에 워프와 lane 상태가 나옴
5특정 스레드를 보려면 Warp Info에서 lane을 선택하거나 조건부 중단점 사용

리눅스 - cuda-gdb

리눅스에서는 gdb를 확장한 cuda-gdb를 쓴다. gdb 명령은 그대로 쓰고, GPU 스레드를 고르는 cuda 명령이 추가된다.

nvcc -g -G -o app app.cu          # host and device debug info
cuda-gdb ./app

(cuda-gdb) break Reduce4           # stop when the kernel starts
(cuda-gdb) run
(cuda-gdb) info cuda kernels       # running kernels
(cuda-gdb) cuda block (4095,0,0) thread (255,0,0)   # switch focus to one thread
(cuda-gdb) print i                 # variables as seen by that thread
(cuda-gdb) print s[0]@8            # 8 elements of a shared array
(cuda-gdb) next                    # step (the whole warp moves together)
(cuda-gdb) info cuda threads       # where every thread is
-G로 빌드하면 버그가 사라질 수 있음 -G는 장치 코드 최적화를 끄고 레지스터 사용, 명령 순서가 크게 바뀐다. race condition이나 경계 조건 버그는 타이밍이 달라져서 디버그 빌드에서 재현되지 않을 수 있다. 이런 경우에는 디버거 대신 racecheck와 printf, CPU 기준 비교로 좁혀 간다.

Windows의 TDR - 커널이 2초를 넘으면

Windows에서 화면 출력에 쓰이는 GPU(WDDM 모드)는 커널 하나가 오래(기본 약 2초) 응답하지 않으면 운영체제가 GPU가 멈췄다고 보고 드라이버를 재시작한다. 이것을 TDR(Timeout Detection and Recovery)이라고 한다. 화면이 잠깐 깜빡이고 "디스플레이 드라이버가 응답을 중지했다가 복구되었습니다" 알림이 뜨며, 프로그램은 cudaErrorLaunchTimeout 같은 오류를 받는다.

원인대책
디버그 빌드(-G)나 sanitizer로 커널이 수십 배 느려짐디버깅할 때는 입력을 작게. 디버깅 전용 PC라면 TDR 시간 연장 (레지스트리 TdrDelay, Nsight Monitor 설정)
커널 하나가 원래 오래 걸림커널을 여러 번으로 나눠 실행
무한 루프, 동기화 교착버그. synccheck, printf로 원인 확인
계산 전용 GPU화면 출력이 없는 데이터센터용 GPU는 TCC 모드로 전환하면 TDR 대상에서 빠짐 (지원 GPU만)
장비 PC라면 레지스트리 변경에 주의 TDR 시간을 늘리면 GPU가 실제로 멈췄을 때 화면도 그만큼 오래 멈춘다. 생산 장비에서는 TDR을 늘리기보다 커널이 짧게 끝나도록 나누는 쪽이 맞다.

CPU 기준 구현과 비교하기

도구로 잡히지 않는 버그도 있다. 메모리 접근은 모두 올바른데 계산 결과가 틀린 경우다. 이때 가장 확실한 방법은 같은 계산을 하는 단순한 CPU 구현을 하나 만들어 두고 결과를 비교하는 것이다.

// compare GPU output with a slow but obviously correct CPU version
bool Compare(const std::vector<float>& gpu, const std::vector<float>& cpu,
             float absTol, float relTol, int width)
{
    int bad = 0;
    for (size_t i = 0; i < gpu.size(); ++i)
    {
        float diff = std::fabs(gpu[i] - cpu[i]);
        float tol  = absTol + relTol * std::fabs(cpu[i]);
        if (diff > tol && bad++ < 10)          // print only the first 10
            printf("mismatch at (%zu,%zu): gpu=%g cpu=%g\n", i % width, i / width, gpu[i], cpu[i]);
    }
    printf("%d mismatches of %zu\n", bad, gpu.size());
    return bad == 0;
}
틀린 위치의 모양의심할 원인
영상 가장자리 몇 줄만 틀림경계 처리 (패딩, clamp 누락)
블록 크기 간격으로 격자 무늬블록 경계의 halo 처리, shared memory 타일 인덱스
오른쪽 끝 부분만 틀림pitch(행 간격)를 width로 착각
실행마다 틀린 위치가 바뀜race condition, 초기화하지 않은 메모리, atomic 누락
전체가 아주 조금씩 다름부동소수점 계산 순서 차이 (버그가 아닐 수 있음. 허용 오차 확인)

틀린 위치를 영상으로 저장해서 보면(차이 영상, 틀린 픽셀을 흰색으로) 위 패턴이 한눈에 보인다. 텍스트 로그보다 훨씬 빠르게 원인을 짐작할 수 있다.

증상별 도구 선택

증상먼저 쓸 도구
어떤 API든 계속 오류 (illegal address 등)CUDA_LAUNCH_BLOCKING=1로 문제 커널 찾기 → memcheck
결과가 실행마다 가끔 다름racecheck, initcheck
커널이 끝나지 않음synccheck, 디버거로 멈춘 위치 확인
결과가 항상 같은 위치에서 틀림CPU 기준 비교 + 차이 영상 → printf 또는 디버거
오래 돌리면 메모리가 부족해짐memcheck --leak-check full, Nsight Systems 메모리 사용량
느림버그가 아니라 성능 문제. Nsight Systems, Nsight Compute (8편)
Windows에서 화면 깜빡임 후 오류TDR. 커널 실행 시간 확인

흔한 함정

오류 보고 위치를 원인 위치로 착각 비동기 실행 때문에 오류는 원인 커널보다 나중의 API(cudaMemcpy 등)에서 보고된다. 오류가 난 줄만 들여다보면 원인을 찾을 수 없다.
릴리스 빌드에서 오류 검사를 모두 끔 cudaDeviceSynchronize를 곁들인 검사는 디버그용으로 끄더라도, API 반환값 검사와 cudaGetLastError는 릴리스에도 남겨 둔다. 비용이 거의 없고, 현장에서 난 오류의 첫 위치를 로그로 남길 수 있다.
sanitizer가 조용하면 버그가 없다는 뜻은 아님 sanitizer는 실행된 경로만 검사한다. 테스트 입력이 문제 경로(가장자리, 크기가 블록 배수가 아닌 영상)를 지나가지 않으면 잡지 못한다. 영상 크기를 블록 크기의 배수가 아닌 값(예: 1023×767)으로도 꼭 돌려 본다.
