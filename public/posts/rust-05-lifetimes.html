라이프타임(Lifetimes) 기초

2026-06-25 약 8분 분량 Rust 시리즈
이 편에서 배우는 것 라이프타임은 "참조가 가리키는 값이 살아 있는 범위"를 컴파일러가 추적하기 위한 장치다. 이 글에서는 라이프타임이 무엇이고 왜 필요한지, 함수 시그니처에 'a 같은 파라미터를 어떻게 적는지, 대부분의 경우 표기를 생략할 수 있게 해 주는 생략 규칙은 무엇인지를 본다. 마지막으로 C++의 댕글링 포인터·참조 문제를 Rust가 컴파일 타임에 어떻게 막는지까지 정리한다.

라이프타임이란 무엇인가

Rust의 모든 참조에는 라이프타임이 있다. 라이프타임은 그 참조가 유효한 코드 범위, 즉 참조가 가리키는 값이 살아 있는 구간을 뜻한다. 빌림 검사기(borrow checker)는 이 범위를 비교해서, 참조가 자기가 가리키는 값보다 오래 살아남는 일이 없는지 컴파일 타임에 검사한다.

대부분의 라이프타임은 타입처럼 추론되어 드러나지 않는다. 그래서 라이프타임을 평소에 의식하지 않다가, 컴파일러가 추론만으로는 안전을 보장할 수 없을 때 비로소 명시 표기를 요구한다. 다음은 빌림 검사기가 막아 주는 전형적인 예다.

fn main() {
    let r;                // r 선언, 아직 값 없음
    {
        let x = 5;
        r = &x;           // x를 빌림
    }                     // 여기서 x가 드롭됨
    // println!("{}", r); // 컴파일 에러: x보다 오래 사는 참조
}

안쪽 블록이 끝나면 x는 드롭되어 메모리에서 사라진다. 그런데 r은 바깥에 남아 사라진 x를 가리키게 된다. 이런 참조를 그대로 쓰면 해제된 메모리를 읽는 것이므로, Rust는 r의 라이프타임이 x의 라이프타임보다 길다는 사실을 보고 컴파일을 거부한다. 아래는 같은 의도를 안전하게 고친 버전이다.

fn main() {
    let x = 5;
    let r = &x;           // x와 r의 유효 범위가 일치
    println!("{}", r);    // OK: x는 여기까지 살아 있음
}

함수 시그니처의 라이프타임 표기

함수가 참조를 받아 참조를 돌려줄 때, 컴파일러는 반환된 참조가 어느 입력에서 빌려온 것인지 알아야 한다. 이를 알 수 없으면 명시적인 라이프타임 파라미터를 요구한다. 라이프타임 파라미터는 작은따옴표로 시작하는 이름('a)이며, 제네릭 타입 파라미터처럼 꺾쇠 안에 선언한다.

// 두 문자열 슬라이스 중 더 긴 쪽을 반환한다.
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() {
        x
    } else {
        y
    }
}

fn main() {
    let s1 = String::from("long string");
    let s2 = String::from("short");
    let result = longest(s1.as_str(), s2.as_str());
    println!("longest: {}", result);
}

<'a>는 "이 함수에는 'a라는 라이프타임이 있다"고 선언한 것이다. 그리고 x, y, 반환값에 모두 'a를 붙여, 반환되는 참조의 유효 범위는 x와 y 중 더 짧은 쪽에 맞춰진다고 컴파일러에게 알린다. 표기 자체가 라이프타임을 바꾸지는 않는다. 입력들 사이의 관계를 서술해서, 검사기가 호출 지점에서 안전을 따질 수 있게 해 줄 뿐이다.

구조체가 참조를 필드로 가질 때도 라이프타임을 적는다. 이렇게 하면 구조체 인스턴스가 자신이 빌린 참조보다 오래 살 수 없게 강제된다.

// 문장의 첫 단어를 빌려 들고 있는 구조체.
struct FirstWord<'a> {
    word: &'a str,
}

fn main() {
    let text = String::from("hello world");
    let first = text.split(' ').next().unwrap();
    let holder = FirstWord { word: first };
    println!("first word: {}", holder.word);
}

라이프타임 생략 규칙

참조를 다루는 함수마다 라이프타임을 일일이 적으면 번거롭다. 그래서 컴파일러는 흔한 패턴을 자동으로 채워 주는 라이프타임 생략 규칙(lifetime elision rules)을 가지고 있다. 이 규칙으로 라이프타임이 모두 결정되면 표기를 생략해도 된다. 규칙은 세 가지다.

  1. 입력 위치의 각 참조 파라미터는 저마다 별개의 라이프타임을 받는다.
  2. 입력 라이프타임이 정확히 하나뿐이면, 그 라이프타임이 모든 출력 참조에 부여된다.
  3. 메서드처럼 &self 또는 &mut self가 있으면, self의 라이프타임이 모든 출력 참조에 부여된다.

예를 들어 다음 함수는 참조 입력이 하나뿐이라 2번 규칙이 적용된다. 표기를 생략해도 컴파일러가 출력 라이프타임을 입력과 같게 채운다.

// 생략 표기: 입력 참조가 하나라 출력도 그 라이프타임을 따른다.
fn first_word(s: &str) -> &str {
    let bytes = s.as_bytes();
    for (i, &b) in bytes.iter().enumerate() {
        if b == b' ' {
            return &s[..i];
        }
    }
    s
}

// 위와 동치인 명시 표기.
fn first_word_explicit<'a>(s: &'a str) -> &'a str {
    let bytes = s.as_bytes();
    for (i, &b) in bytes.iter().enumerate() {
        if b == b' ' {
            return &s[..i];
        }
    }
    s
}

반면 앞서 본 longest는 참조 입력이 둘이고 self도 없어서, 어느 규칙으로도 출력 라이프타임이 정해지지 않는다. 그래서 longest는 'a를 직접 적어야 한다. 생략 규칙은 "흔하고 모호하지 않은 경우"만 처리하고, 모호하면 사람에게 표기를 넘기는 셈이다.

댕글링 방지 — C++과 무엇이 다른가

라이프타임의 실질적 목적은 단 하나, 댕글링 참조(dangling reference)를 컴파일 타임에 없애는 것이다. 댕글링이란 이미 해제된 메모리를 가리키는 참조를 말한다. 함수가 지역 변수를 빌려 반환하려고 하면 Rust는 거부한다.

// 컴파일 에러: 지역 변수 s를 빌려 반환할 수 없다.
// fn dangle() -> &String {
//     let s = String::from("hi");
//     &s  // s는 함수가 끝나면 드롭됨 -> 댕글링
// }

// 해결: 소유권을 넘겨 반환한다. 참조가 아니라 값을 돌려준다.
fn no_dangle() -> String {
    let s = String::from("hi");
    s                 // 소유권 이동, 안전
}

fn main() {
    let s = no_dangle();
    println!("{}", s);
}

C++ 경험자에게 가장 와닿는 지점이 여기다. C++에서 지역 변수의 주소나 참조를 반환하는 코드는 문법상 통과되고, 운이 나쁘면 실행 중에 정의되지 않은 동작으로 터진다. Rust는 같은 상황을 빌드 단계에서 막는다.

C++과 이렇게 다르다 C++에서 const int& f() { int x = 5; return x; }는 컴파일은 되지만 해제된 스택 변수를 가리키는 댕글링 참조를 만든다. 발견은 런타임(혹은 ASan 같은 도구)에 미뤄지고, 그마저 못 잡으면 미정의 동작이 된다. Rust에서 같은 코드는 컴파일 자체가 실패한다. 즉 댕글링 검사의 책임이 "개발자의 주의·런타임 도구"에서 "컴파일러"로 옮겨 간다.
상황C++Rust
지역 변수 참조 반환컴파일됨, 미정의 동작 위험컴파일 에러로 차단
가리키는 값보다 오래 사는 참조개발자가 직접 관리빌림 검사기가 라이프타임으로 검증
해제 후 사용(use-after-free)주로 런타임에 발견(ASan 등)대부분 컴파일 타임에 차단
검사 비용런타임 도구·리뷰에 의존런타임 오버헤드 없음

여기서 강조할 점은, 라이프타임 표기가 런타임 비용을 전혀 더하지 않는다는 것이다. 표기는 검사기에게 주는 정보일 뿐이며, 컴파일이 끝나면 사라진다. 안전성을 정적 분석으로 확보하기 때문에, 댕글링을 막으려고 가비지 컬렉터나 런타임 검사를 들일 필요가 없다.

정리

  • 라이프타임은 참조의 유효 범위 — 빌림 검사기가 참조가 가리키는 값보다 오래 사는지 비교해 검사한다.
  • 표기는 관계 서술 — 'a는 라이프타임을 바꾸지 않고, 입력과 출력 참조의 관계를 컴파일러에 알려 줄 뿐이다.
  • 생략 규칙으로 대부분 생략 — 입력 참조가 하나거나 메서드의 &self가 있으면 표기를 적지 않아도 된다. 모호할 때만 직접 적는다.
  • 댕글링을 컴파일 타임에 차단 — C++에서 런타임 위험으로 남는 해제 후 사용·지역 변수 참조 반환을 Rust는 빌드 단계에서 막는다. 그러면서 런타임 오버헤드는 없다.
