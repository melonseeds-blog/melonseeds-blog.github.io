학습과 배포의 간극

딥러닝 모델을 만드는 일과 그 모델을 현장에 올리는 일은 서로 다른 세계에서 일어난다. 학습은 Python 환경에서 PyTorch나 TensorFlow로 진행한다. GPU가 달린 워크스테이션, 주피터 노트북, 풍부한 라이브러리가 학습의 무대다. 그런데 배포의 무대는 전혀 다르다. C++로 짠 산업 검사 소프트웨어, 메모리가 빠듯한 엣지 디바이스, Python 인터프리터를 띄울 수 없는 임베디드 보드가 모델이 실제로 돌아야 하는 곳이다.

이 간극을 그냥 두면 문제가 생긴다. 학습에 쓴 프레임워크를 배포 환경까지 그대로 끌고 가야 하기 때문이다. C++ 검사 SW 안에 PyTorch 런타임을 통째로 넣는 것은 무겁고, 의존성이 얽히고, 버전 관리가 악몽이 된다. 학습 팀이 프레임워크를 바꾸면 배포 코드도 따라 바뀌어야 한다. 모델이 학습 프레임워크에 묶여 있는 한, 배포는 매번 그 프레임워크와 싸우는 일이 된다.

프레임워크 종속을 끊는다는 것

학습 프레임워크는 모델을 만들기 좋게 설계되어 있다. 자동 미분, 동적 그래프, 디버깅 도구가 다 들어 있어 무겁다. 하지만 배포 단계에서는 그 기능이 대부분 필요 없다. 학습이 끝난 모델은 입력을 받아 출력을 내놓기만 하면 된다.

그래서 필요한 것은 모델을 학습 프레임워크와 분리해, 추론에만 집중하는 가벼운 형태로 옮기는 다리다. 학습은 PyTorch로 하되, 그 결과물을 프레임워크에 묶이지 않는 중립 포맷으로 꺼내면 배포 환경은 학습이 무엇으로 이루어졌는지 알 필요가 없어진다. 그 다리가 바로 ONNX다.

ONNX란 무엇인가

ONNX는 Open Neural Network Exchange의 약자다. 이름 그대로 신경망을 주고받기 위한 열린 포맷이다. 특정 회사나 프레임워크의 소유물이 아니라, 여러 곳이 함께 정의한 공개 표준이다. ONNX 파일 하나에는 모델의 연산 구조와 학습된 가중치가 함께 담긴다.

비유하자면 ONNX는 모델의 공통어다. PyTorch가 한국어로, TensorFlow가 일본어로 모델을 표현한다면, ONNX는 둘 다 번역해 담을 수 있는 중립 언어다. 한쪽에서 ONNX로 옮겨 적으면, 그 언어를 읽을 줄 아는 어떤 런타임이든 모델을 실행할 수 있다. 학습 쪽과 배포 쪽이 직접 약속을 맞출 필요 없이, 둘 다 ONNX만 알면 된다.

ONNX는 "모델"이 아니라 "포맷"이다 ONNX는 새로운 모델 아키텍처가 아니다. 이미 학습된 CNN, ResNet, YOLO 같은 모델을 어떤 형식으로 저장하느냐에 대한 규약이다. .onnx 확장자를 가진 파일은 그 규약을 따라 직렬화된 모델이다. 따라서 ONNX로 바꾼다고 모델의 성능이 좋아지거나 나빠지지 않는다. 단지 더 많은 환경에서 읽을 수 있는 형태가 될 뿐이다.

ONNX는 어떻게 동작하는가

ONNX의 핵심 흐름은 단순하다. 학습 프레임워크에서 모델을 ONNX로 내보내고(export), 다양한 런타임이 그 ONNX를 읽어 추론한다. 학습은 PyTorch든 TensorFlow든 상관없고, 추론은 ONNX Runtime이든 OpenCV DNN이든 TensorRT든 상관없다. ONNX가 그 사이에서 허브 역할을 한다.

그림 1. ONNX는 학습 프레임워크와 추론 런타임 사이의 허브다 — 모든 프레임워크가 모든 런타임에 직접 다리를 놓는 대신, 모두가 ONNX 하나만 거치면 된다

ONNX 파일 안에는 두 가지가 들어 있다. 하나는 연산 그래프다. 합성곱, 활성화, 풀링 같은 연산들이 어떤 순서로 어떻게 연결되는지를 노드와 엣지로 표현한 구조다. 다른 하나는 가중치다. 학습으로 얻어진 각 연산의 파라미터 값이다. 그래프는 "무엇을 어떻게 계산하는가"를, 가중치는 "그 계산에 쓰는 값"을 담는다. 둘이 합쳐져야 모델이 완성된다.

연산자(operator)와 opset

ONNX 그래프의 노드 하나하나는 Conv, Relu, MaxPool 같은 표준 연산자다. ONNX는 이런 연산자들의 목록과 각각의 동작 규칙을 정의해 둔다. 이 연산자 집합의 버전이 opset(operator set)이다.

opset은 시간이 지나며 갱신된다. 새 연산자가 추가되고, 기존 연산자의 동작이 다듬어진다. 그래서 모델을 ONNX로 내보낼 때 "어떤 opset 버전으로 내보낼지"를 정해야 하고, 그 모델을 읽는 런타임도 그 opset을 지원해야 한다. opset 버전이 변환과 배포에서 자주 문제가 되는 이유가 여기에 있다.

ONNX 변환

학습이 끝난 모델을 ONNX로 옮기는 과정을 변환 또는 export라 한다. 프레임워크마다 방법이 다르지만, 가장 흔한 PyTorch의 경우 torch.onnx.export 한 줄로 시작한다.

PyTorch에서 내보내기

import torch

# 학습이 끝난 모델을 추론 모드로 전환한다
model = MyDefectClassifier()
model.load_state_dict(torch.load("best.pth"))
model.eval()

# export에 쓸 더미 입력 — 실제 추론 때와 같은 형태(NCHW)여야 한다
dummy_input = torch.randn(1, 3, 224, 224)

torch.onnx.export(
    model, dummy_input, "defect_model.onnx",
    input_names=["input"], output_names=["output"],
    opset_version=17,                       # 런타임이 지원하는 opset으로 맞춘다
    dynamic_axes={                            # 배치 크기를 가변으로 둔다
        "input":  {0: "batch"},
        "output": {0: "batch"},
    },
)

PyTorch의 export는 더미 입력을 한 번 흘려보내며 모델이 수행하는 연산을 따라 기록하는 방식(tracing)으로 동작한다. 그래서 더미 입력의 형태가 중요하다. 실제 추론에서 모델이 받을 입력과 같은 차원 구조여야 한다. TensorFlow 모델은 tf2onnx 같은 별도 변환 도구를 거쳐 ONNX로 옮긴다. 출발 프레임워크는 달라도 도착지는 같은 .onnx 파일이다.

변환 시 주의점

항목 무엇인가 주의할 점
opset 버전 변환에 사용할 연산자 집합의 버전 너무 높으면 배포 런타임이 지원하지 않고, 너무 낮으면 모델의 일부 연산이 표현되지 않는다. 배포 런타임 기준으로 맞춘다
동적 축 배치·해상도처럼 추론 때 바뀔 수 있는 차원 dynamic_axes에 지정하지 않으면 export 당시 더미 입력 크기로 고정된다. 가변 배치가 필요하면 반드시 지정한다
추론 모드 Dropout·BatchNorm의 학습/추론 동작 차이 export 전에 model.eval()을 호출하지 않으면 학습용 동작이 그래프에 박힌다
미지원 연산 ONNX 표준에 없는 커스텀 연산 특이한 레이어나 직접 짠 연산은 export가 실패하거나 잘못 변환될 수 있다. 변환 후 검증이 필수다
제어 흐름 입력 값에 따라 분기하는 if·loop tracing 방식은 한 번의 실행 경로만 기록한다. 데이터 의존적 분기는 그대로 옮겨지지 않을 수 있다
변환은 "되었다"가 아니라 "맞다"를 확인해야 한다 torch.onnx.export가 에러 없이 끝났다고 변환이 성공한 것은 아니다. tracing 과정에서 일부 연산이 다르게 기록되거나 동적 축이 누락되어도 파일은 멀쩡히 생성된다. 변환이 끝나면 같은 입력을 원본 모델과 ONNX 모델에 각각 넣어 출력이 일치하는지 반드시 비교한다. 이 검증을 건너뛰면 배포 후에야 문제를 발견하게 된다.

ONNX Runtime

ONNX 파일이 있어도 그것을 실행할 엔진이 없으면 그림의 떡이다. ONNX Runtime은 Microsoft가 만든 고성능 추론 엔진으로, ONNX 모델을 읽어 실제로 연산을 수행한다. 그래프를 최적화하고, 메모리를 관리하고, 대상 하드웨어에 맞춰 연산을 분배하는 일을 맡는다.

Execution Provider

ONNX Runtime의 핵심 개념은 Execution Provider(EP)다. EP는 "이 연산을 어떤 하드웨어/백엔드로 실행할 것인가"를 결정하는 플러그인이다. 같은 ONNX 모델을 코드 변경 거의 없이 CPU에서 돌리다가 GPU로 옮길 수 있는 것이 이 구조 덕분이다.

Execution Provider 대상 하드웨어 특징
CPU EP 일반 CPU 기본 제공. 별도 하드웨어 없이 어디서나 동작. 이식성이 가장 좋다
CUDA EP NVIDIA GPU GPU 병렬 연산으로 처리량을 크게 높인다. CUDA·cuDNN 설치 필요
TensorRT EP NVIDIA GPU TensorRT로 추가 최적화. 같은 GPU에서 CUDA EP보다 더 빠를 수 있다
DirectML EP Windows GPU 전반 DirectX 기반. NVIDIA가 아닌 GPU에서도 가속. Windows 산업 PC에 유용
OpenVINO EP Intel CPU·iGPU·VPU Intel 하드웨어에 특화된 최적화. 엣지 산업 PC에서 자주 쓰인다
NPU 계열 EP 전용 신경망 가속 칩 저전력 고성능. 지원 연산·자료형에 제약이 있다

추론 코드

ONNX Runtime은 Python과 C++ 양쪽에 API를 제공한다. 학습 검증은 Python으로, 산업 SW 통합은 C++로 같은 모델을 쓸 수 있다. 다음은 Python API로 추론하는 최소 예시다.

import onnxruntime as ort
import numpy as np

# 세션 생성 — EP는 우선순위 순서로 지정한다 (GPU 없으면 CPU로 폴백)
session = ort.InferenceSession(
    "defect_model.onnx",
    providers=["CUDAExecutionProvider", "CPUExecutionProvider"],
)

# 전처리 — 학습 때와 동일한 정규화·리사이즈여야 한다
img = preprocess(raw_image)          # (1, 3, 224, 224), float32, NCHW

# 추론 실행
outputs = session.run(
    ["output"],
    {"input": img.astype(np.float32)},
)
score = outputs[0]

# 후처리 — softmax, NMS 등도 학습 때 정의와 같아야 한다
result = postprocess(score)
EP는 우선순위 목록으로 준다 providers에 EP를 여러 개 나열하면 ONNX Runtime이 앞에서부터 사용 가능한 것을 고른다. GPU가 있는 장비에서는 CUDA EP가, 없는 장비에서는 CPU EP가 자동으로 선택된다. 덕분에 같은 배포 바이너리를 하드웨어가 다른 여러 현장에 그대로 뿌릴 수 있다. 다만 EP에 따라 지원하는 연산이 다를 수 있어, 실제 배포 장비에서 한 번은 검증해야 한다.

OpenCV DNN과의 관계

ONNX 모델을 읽을 수 있는 런타임은 ONNX Runtime만이 아니다. OpenCV의 DNN 모듈도 ONNX 모델을 직접 불러와 추론할 수 있다. 산업 비전 개발자에게 이것은 특별한 의미가 있다. 이미 전통 비전 처리를 OpenCV로 하고 있다면, 딥러닝 추론을 위해 별도의 런타임을 추가하지 않고도 같은 OpenCV 안에서 모델을 돌릴 수 있기 때문이다.

# OpenCV DNN으로 같은 ONNX 모델을 읽는다 (C++ / Python 공통 흐름)
net = cv2.dnn.readNetFromONNX("defect_model.onnx")

# blobFromImage가 리사이즈·정규화·NCHW 변환을 한 번에 처리한다
blob = cv2.dnn.blobFromImage(
    image, scalefactor=1/255.0, size=(224, 224), swapRB=True,
)
net.setInput(blob)
output = net.forward()

OpenCV DNN과 ONNX Runtime은 경쟁 관계라기보다 상황에 따라 고르는 선택지다. 전처리·후처리가 이미 OpenCV로 짜여 있고 모델이 비교적 표준적이면 OpenCV DNN이 통합 비용이 낮다. 반대로 다양한 EP, 최신 opset, 더 폭넓은 연산 지원이 필요하면 ONNX Runtime이 유리하다. 둘 다 같은 ONNX 파일을 입력으로 받는다는 점이 핵심이다 — 모델을 ONNX로 만들어 두면 두 길이 모두 열려 있다.

OpenCV DNN 실전은 다음 12편에서 자세히 다룬다 이 글에서는 "OpenCV DNN도 ONNX 모델을 읽는 런타임 중 하나"라는 관계만 잡아 두면 된다. blobFromImage로 전처리를 맞추는 법, 분류·검출·세그멘테이션 모델별 출력 해석, 백엔드와 타깃 설정 같은 실전 내용은 다음 편에서 본격적으로 풀어간다. 산업 검사 SW가 OpenCV 기반이라면 12편이 가장 직접적인 배포 경로가 된다.

배포 파이프라인

모델 하나를 현장에 올리기까지는 여러 단계를 거친다. 학습으로 끝나는 것이 아니라, 변환하고 검증하고 최적화하고 통합하고 나서야 양산에 들어간다. 이 흐름을 배포 파이프라인이라 부른다.

그림 2. 배포 파이프라인 — 학습 → ONNX 변환 → 검증 → 최적화 → 런타임 통합 → 양산. 검증이 실패하면 변환 단계로 되돌아간다

이 파이프라인에서 가장 자주 생략되는 단계가 검증이다. 변환이 에러 없이 끝나면 다음으로 넘어가고 싶은 유혹이 크다. 하지만 변환 전후 출력이 일치하는지 확인하지 않으면, 미세하게 어긋난 모델이 그대로 양산까지 흘러간다. 검증은 같은 입력 여러 개를 원본 모델과 ONNX 모델에 넣어 출력 차이가 허용 오차 안에 드는지 보는, 어렵지 않지만 반드시 거쳐야 하는 단계다.

최적화 단계는 10편에서 다룬 양자화·프루닝과 이어진다. ONNX로 변환한 뒤 양자화를 적용해 모델을 더 가볍게 만들거나, ONNX Runtime의 그래프 최적화를 켜는 식이다. 최적화는 선택 단계지만, 택트 타임이 빡빡한 산업 현장에서는 사실상 필수가 되는 경우가 많다.

배포 시 고려사항

모델 파일만 옮긴다고 배포가 끝나는 것이 아니다. 모델 주변을 둘러싼 여러 가지가 함께 옮겨져야 학습 때와 같은 결과가 나온다.

전처리와 후처리도 함께 옮겨야 한다

모델은 파이프라인의 가운데 토막일 뿐이다. 그 앞에는 전처리가, 뒤에는 후처리가 붙어 있다. 학습 때 입력 이미지를 리사이즈하고 0~1 또는 특정 평균·표준편차로 정규화했다면, 배포 환경에서도 똑같은 전처리를 거쳐야 한다. 출력 쪽도 마찬가지다. softmax, 경계 상자 디코딩, NMS 같은 후처리 정의가 학습 때와 어긋나면 모델은 멀쩡해도 최종 결과가 틀린다.

배포 체크리스트

점검 항목 확인 내용
전처리 일치 리사이즈 크기·보간 방식, 정규화 평균·표준편차, 채널 순서(RGB/BGR)가 학습과 동일한가

NCHW와 NHWC — 차원 순서

이미지 텐서는 보통 네 개의 차원을 가진다 — 배치(N), 채널(C), 높이(H), 너비(W). 문제는 이 차원을 어떤 순서로 배열하느냐가 환경마다 다르다는 것이다. PyTorch와 ONNX는 NCHW(채널이 앞)를 쓰고, TensorFlow는 흔히 NHWC(채널이 뒤)를 쓴다.

이 순서가 맞지 않으면 런타임이 입력을 잘못 해석한다. 에러가 나면 그나마 다행이고, 차원 크기가 우연히 맞아떨어지면 에러 없이 엉뚱한 결과를 낸다. 배포 시에는 모델이 기대하는 차원 순서를 명확히 알고, 전처리에서 그 형태로 맞춰 넣어야 한다.

산업 비전 관점

산업 비전에서 ONNX 배포는 추상적인 이야기가 아니라 매일 부딪히는 현실이다. 학습은 데이터 사이언티스트가 Python으로 하지만, 그 모델이 최종적으로 도는 곳은 C++로 짠 검사 소프트웨어다. ONNX는 이 둘을 잇는 표준 다리다.

C++ 검사 SW 통합

검사 SW는 카메라 입력, 전통 비전 처리, 판정 로직이 C++로 묶여 있다. ONNX 모델을 ONNX Runtime이나 OpenCV DNN의 C++ API로 불러 그 안에 딥러닝 추론 블록을 끼워 넣는다.

엣지 디바이스 배포

현장의 작은 박스에는 GPU가 없거나 임베디드 GPU·NPU만 있다. ONNX Runtime의 EP를 장비에 맞게 골라, 같은 모델 파일을 다양한 엣지 환경에 배포한다.

추론 속도와 택트 타임

라인은 정해진 주기(택트 타임) 안에 한 장을 처리해야 한다. 추론이 그 예산을 넘기면 모델이 아무리 정확해도 쓸 수 없다. EP 선택과 최적화가 정확도만큼 중요하다.

블록 에디터 통합

ImagingLib의 데이터 플로우 에디터에서 ONNX 추론은 하나의 블록이 된다. 전통 비전 블록과 같은 캔버스에서 연결되어 하이브리드 파이프라인을 이룬다.

ImagingLib에서 ONNX의 자리 이 블로그가 따라가는 산업 이미징 SDK ImagingLib에서 Deep Learning 솔루션의 추론 진입점이 ONNX다. 학습은 외부 프레임워크에서 하더라도, SDK 안으로 들어오는 모델은 ONNX 형태로 통일된다. 그러면 SDK는 학습이 무엇으로 이루어졌는지 신경 쓸 필요 없이, ONNX 추론 블록 하나만 잘 만들어 두면 어떤 모델이든 받아들일 수 있다. 프레임워크 종속을 끊는다는 ONNX의 가치가 SDK 설계 차원에서 그대로 드러나는 지점이다.

흔한 함정

ONNX 배포에서 사고는 대부분 정해진 몇 군데에서 난다. 미리 알아 두면 대부분 피할 수 있는 함정들이다.

함정 1 — 전처리 불일치로 정확도가 급락한다 가장 흔하고 가장 잡기 어려운 함정이다. 학습 때는 ImageNet 평균·표준편차로 정규화했는데 배포에서는 그냥 0~1로 나누거나, 학습은 RGB인데 OpenCV는 BGR로 읽거나, 리사이즈 보간 방식이 다른 경우다. 모델도 멀쩡하고 코드도 에러가 없는데 정확도만 떨어진다. 학습 코드의 전처리를 한 줄씩 그대로 옮겨 적고, 변환 전후 출력으로 검증해야 한다.
함정 2 — 변환 후 출력 검증을 생략한다 export가 에러 없이 끝났다는 사실에 안심하고 검증을 건너뛰는 경우다. tracing 과정에서 연산이 어긋나거나 동적 축이 누락되어도 파일은 정상적으로 생성된다. 같은 입력을 원본 모델과 ONNX 모델에 넣어 출력이 일치하는지 비교하는 단계를 파이프라인에 고정으로 넣어야 한다. 이 검증 없이는 어떤 배포도 신뢰할 수 없다.
함정 3 — opset 버전 미지원 연산 최신 opset으로 변환했더니 배포 런타임이 그 버전을 지원하지 않거나, 모델에 쓰인 특정 연산자가 런타임에 구현되어 있지 않은 경우다. 변환 단계에서 배포 런타임의 지원 범위를 먼저 확인하고, 그에 맞는 opset 버전으로 export해야 한다. 미지원 연산이 있다면 모델 구조를 바꾸거나 다른 런타임을 검토한다.
함정 4 — 동적 축 설정 누락 dynamic_axes를 지정하지 않으면 ONNX 모델은 export 당시 더미 입력의 크기로 차원이 고정된다. 배치 크기 1로 export한 모델에 배치 8을 넣으면 에러가 난다. 가변 배치나 가변 해상도가 필요하다면 변환 시점에 반드시 동적 축을 지정해야 한다.
함정 5 — NCHW와 NHWC 혼동 모델은 NCHW를 기대하는데 전처리에서 NHWC로 텐서를 만들어 넣는 경우다. 차원 크기가 우연히 맞으면 에러도 없이 엉뚱한 결과가 나와 원인을 찾기 어렵다. 모델이 기대하는 차원 순서를 명확히 확인하고 전처리에서 그 형태로 맞춰야 한다.
함정의 공통 해법은 "검증"이다 다섯 가지 함정을 들여다보면 해법이 하나로 모인다 — 변환 전후 출력을 같은 입력으로 비교하는 검증이다. 전처리가 어긋났든, opset이 안 맞든, 차원 순서가 틀렸든, 검증 단계에서 출력 불일치로 드러난다. 검증을 파이프라인의 필수 관문으로 만들어 두면 대부분의 배포 사고는 양산 전에 걸러진다. 다음 12편에서는 OpenCV DNN으로 ONNX 모델을 실제로 추론하는 구체적인 방법을 다룬다.
