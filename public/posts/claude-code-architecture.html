Claude Code를 구조로 이해하기 — 6가지 확장 메커니즘과 선택 기준

2026-06-25 약 12분 분량 도구/환경 설정
이 글의 목적 Claude Code의 확장 기능들(slash command·skill·subagent·hook·MCP·plugin)을 하나씩 따로 외우는 대신, "각각이 무엇을 더해 주는가"라는 한 장의 구조로 묶어 본다. 구조를 잡으면 새 기능이 나와도 어디에 끼우면 되는지 바로 보인다. 명령어·파일 경로는 버전에 따라 바뀔 수 있으니 세부는 공식 문서를 함께 확인한다.

왜 "구조로" 이해해야 하나

Claude Code를 처음 쓰면 기능 이름이 빠르게 늘어난다. slash command, skill, subagent, hook, MCP, plugin, 거기에 CLAUDE.md와 settings.json까지. 각각을 개별 튜토리얼로 따라 하면 동작은 시키지만, "이 일에는 무엇을 써야 하지?"라는 질문 앞에서는 매번 막힌다.

이 기능들은 서로 경쟁 관계가 아니다. 한 가지 공통 목적 — 모델의 기본 동작을 내 작업 방식에 맞게 확장하는 것 — 을 서로 다른 축에서 푸는 도구들이다. 그래서 외울 게 아니라 한 장의 구조로 묶어야 한다. 구조가 잡히면 선택이 빨라지고, 새 기능이 추가돼도 "아, 이건 트리거 축의 변형이구나"처럼 자리부터 보인다.

한 장으로 보는 멘탈 모델

"Claude를 확장한다"는 말은 결국 아래 네 가지 질문 중 하나에 답하는 것이다. 6개 기능은 이 네 질문에 대한 서로 다른 대답일 뿐이다.

확장의 축핵심 질문주로 쓰는 기능
지식·절차무엇을, 어떻게 하라고 가르칠까CLAUDE.md · Slash command · Skill
일손(컨텍스트)이 일을 어디서(누가) 처리하게 할까Subagent
연결바깥의 무엇에 닿게 할까MCP
자동 개입언제 자동으로 끼어들게 할까Hook

그리고 Plugin은 다섯 번째 축이 아니라, 위의 것들을 하나로 묶어 남에게 배포하는 포장지다. 이 그림을 머릿속에 두고 각 레이어를 본다.

6가지 확장 레이어

각 레이어를 정의 · 저장 위치 · 트리거 · 쓸 때 순으로 정리한다. 저장 위치의 ~/.claude/는 모든 프로젝트에 적용되는 개인 설정, .claude/는 해당 프로젝트(팀과 git으로 공유)다.

① Slash command — 내가 부르는 재사용 프롬프트

COMMAND 자주 쓰는 지시를 명령어로 등록 .claude/commands/이름.md

매번 길게 타이핑하던 지시를 Markdown 파일 한 장으로 저장해 두고 /이름으로 부른다. 파일 내용이 그대로 프롬프트로 펼쳐진다. 인자도 받을 수 있다.

트리거 — 사용자가 직접 /명령 입력 (명시적).

쓸 때: "이 정형 지시를 내가 원할 때 즉시 부르고 싶다" — 배포·릴리스 노트·정해진 리뷰 절차처럼 내가 시점을 정하는 작업.

② Skill — 모델이 알아서 따르는 절차 패키지

SKILL 절차·지식을 모듈로 묶어 자동 로드 .claude/skills/이름/SKILL.md

디렉터리 단위의 Markdown 패키지다. SKILL.md의 frontmatter에 "이 스킬은 언제 쓰는가"를 자연어로 적으면, 모델이 매 턴 그 설명을 읽고 지금 필요한지 스스로 판단해 적용한다. 보조 파일(스크립트·예시)을 함께 두고 필요할 때만 읽는 지연 로드 구조라 컨텍스트를 아낀다.

트리거 — 모델이 description을 보고 자동 (원하면 /스킬이름 명시 호출도 가능).

쓸 때: "같은 절차·규칙을 매번 다시 설명하고 있다" — 코딩 컨벤션, 반복 체크리스트, 특정 작업의 표준 순서.

③ Subagent — 분리된 컨텍스트에 위임

SUBAGENT 별도 컨텍스트를 가진 보조 에이전트 .claude/agents/이름.md

자기만의 컨텍스트 윈도우·도구 세트·시스템 프롬프트를 가진 별도 에이전트다. 메인 세션이 무거운 일을 통째로 떠안으면 윈도우가 빨리 차는데, subagent에 위임하면 그쪽에서 처리하고 메인은 요약 결과만 받는다. 함수 호출과 비슷한 추상이다.

트리거 — 모델이 작업과 description을 맞춰 자동 위임.

쓸 때: "메인에서 직접 하면 컨텍스트가 부담되는, 결과만 받으면 되는 일" — 대형 코드 리뷰, 광범위 조사, 여러 파일 일관성 검사. 작은 일에 남발하면 호출 오버헤드로 오히려 손해.

④ Hook — 정해진 시점에 자동 실행

HOOK 라이프사이클 이벤트에 거는 스크립트 .claude/settings.json 의 hooks

도구 실행 전후나 세션 시작 같은 정해진 시점에 셸 명령을 결정론적으로 실행한다. 모델의 판단에 맡기지 않고 "무조건" 돌게 만드는 게 핵심이라, 정책 강제와 자동화에 쓴다. 주요 이벤트로 PreToolUse(도구 실행 전, 차단 가능)·PostToolUse(실행 후)·UserPromptSubmit·Stop·SessionStart 등이 있다.

트리거 — 해당 이벤트가 발생하면 자동 (모델 판단 아님).

쓸 때: "이건 반드시·매번 일어나야 한다" — 파일 저장 후 자동 포맷/lint, 위험 명령 차단, 커밋 전 검사.

⑤ MCP — 바깥 도구·데이터에 연결

MCP 외부 시스템을 도구로 연결하는 프로토콜 .mcp.json

Model Context Protocol. 데이터베이스·이슈 트래커·브라우저·사내 API 같은 외부 시스템을 표준 방식으로 연결해, 모델이 그것들을 도구처럼 호출하게 한다. 연결 정보를 .mcp.json에 적어 두면 세션 시작 시 서버가 떠 모델이 필요할 때 호출한다.

트리거 — 모델이 필요하다고 판단할 때 자동 호출.

쓸 때: "Claude가 우리 DB/Slack/브라우저/사내 시스템에 직접 닿아야 한다" — 모델 자체엔 없는 외부 능력 추가.

⑥ Plugin — 위를 묶어 배포

PLUGIN command·skill·agent·hook·MCP를 한 패키지로 .claude-plugin/plugin.json

앞의 확장들을 하나의 설치 가능한 묶음으로 포장한 것이다. 매니페스트(plugin.json)에 메타데이터를 적고, 마켓플레이스나 git을 통해 팀·커뮤니티가 받아 쓴다. 플러그인 안의 스킬은 /플러그인이름:스킬이름처럼 네임스페이스가 붙는다.

트리거 — 설치 후, 안에 든 각 요소가 자기 방식대로 동작.

쓸 때: "내가 만든 확장 묶음을 팀 전체·여러 프로젝트에 일관되게 퍼뜨리고 싶다".
바탕에 깔리는 설정 계층 6개 레이어 밑에는 항상 CLAUDE.md(상시 적용되는 지시·맥락)와 settings.json(권한·환경 변수·훅·모델 선택), 그리고 자동 메모리가 깔려 있다. 같은 항목은 프로젝트(.claude) 설정이 개인(~/.claude) 설정을 덮어쓴다. 확장을 만들기 전에, 상시 지시는 CLAUDE.md로 두는 게 먼저다.

언제 무엇을 — 선택 기준

핵심 구분 축은 세 가지다. (1) 누가 트리거하나(내가 명시 / 모델이 자동 / 이벤트가 자동), (2) 컨텍스트가 분리되나, (3) 무엇을 더하나(지식 / 일손 / 연결 / 자동개입).

기능무엇을 더하나트리거컨텍스트전형적 용도
Slash command지식·절차사용자 명시 /cmd메인 안정형 지시 즉시 호출
Skill지식·절차모델 자동 / 명시메인 안(지연 로드)반복 절차·규칙 자동 적용
Subagent일손모델 자동분리됨무거운 위임(리뷰·조사)
Hook자동 개입이벤트 자동해당 없음정책 강제·자동화
MCP연결모델 자동해당 없음외부 도구·데이터 접근
Plugin(묶음 배포)설치—팀·커뮤니티 공유

막힐 때는 위에서부터 내려오며 답하면 대개 갈린다.

  1. 바깥 시스템(DB·Slack·브라우저·사내 API)에 닿아야 하나? → MCP
  2. 특정 시점에 반드시·매번 자동 실행돼야 하나(저장 후 lint, 위험 명령 차단)? → Hook
  3. 무겁고 분리해도 되는 일을 위임하고 결과만 받으면 되나? → Subagent
  4. 반복되는 절차·규칙을 모델이 알아서 따르게 하고 싶나? → Skill
  5. 정형 지시를 내가 원할 때 직접 부르고 싶나? → Slash command
  6. 위에서 만든 것들을 남에게 배포하나? → Plugin
경계가 겹칠 땐 "분리"와 "강제"로 가른다 Skill과 Subagent가 헷갈리면 컨텍스트 분리가 필요한지로 가른다 — 필요하면 Subagent, 아니면 Skill. Skill과 Hook이 헷갈리면 "모델 판단에 맡겨도 되나(Skill)" vs "무조건 돌아야 하나(Hook)"로 가른다. 이 둘은 배타적이지 않아 함께 합성할 수도 있다(예: Skill 안에서 특정 작업을 Subagent에 위임).

이게 Claude만의 구조인가

질문을 정확히 두 층으로 나누면 답이 분명해진다.

명시 명령(slash command류)은 발상이 보편적

"자주 쓰는 지시를 명령으로 등록해 재사용한다"는 발상 자체는 새롭지 않다. 여러 AI 코딩 도구가 각자의 이름과 UX로 비슷한 명령·규칙 개념을 제공한다. 표면은 달라도 메커니즘은 "사용자 입력 → 프롬프트로 확장 → 실행"으로 같다. 그래서 한 도구에서 익힌 감각이 다른 도구로 대체로 옮겨 간다.

Skill·MCP는 공개 표준으로 가고 있다

두 레이어는 Claude 안에 갇힌 기능이 아니라 도구 경계를 넘는 표준을 지향한다.

  • Agent Skills — Anthropic이 SKILL.md 형식을 공개 표준으로 내놓아, 한 번 작성한 스킬을 여러 도구·환경에서 재사용하는 방향을 잡았다. "절차를 한 번 가르쳐 두면 어디서든 쓴다"가 목표다.
  • MCP — 외부 도구 연결 프로토콜로, Anthropic이 처음 제안했지만 주요 AI 제공자와 도구들이 채택하면서 사실상 업계 공용 규격이 됐다. MCP 서버 하나를 만들면 이를 지원하는 여러 클라이언트에서 함께 쓸 수 있다.

정리하면, 이 구조는 "Claude만의 특이한 장치"가 아니라 에이전트형 AI 도구가 공통으로 수렴하고 있는 골격에 가깝다. 그래서 구조로 한 번 이해해 두면 투자가 특정 도구에 종속되지 않는다.

수치·채택 현황은 빠르게 바뀐다 "어떤 도구가 무엇을 지원한다", "표준 버전이 몇이다" 같은 구체 사실은 변동이 잦다. 이 글은 의도적으로 큰 흐름만 다뤘다. 최신 채택 현황·정확한 사양은 각 공식 문서에서 그때그때 확인하는 게 맞다.

구조 이해를 생산성으로

구조를 아는 것과 생산성이 오르는 것은 다르다. 둘을 잇는 건 "지금 내 마찰을 어느 레이어로 옮길까"라는 한 가지 습관이다. 권하는 출발 순서는 가벼운 것부터다.

CLAUDE.md → Skill → 나머지 순으로

  1. CLAUDE.md부터. 매 세션 반복하는 맥락(빌드 명령·코딩 규칙·금지 사항)을 여기 적는다. 진입 비용이 가장 낮고 효과가 즉시 난다.
  2. 반복 설명은 Skill로. "이 절차를 또 설명하고 있네" 싶은 게 보이면 그게 첫 스킬 후보다. Markdown 한 장이면 시작된다.
  3. 무거운 위임은 Subagent로. 메인 대화를 어지럽히는 대형 리뷰·조사를 떼어 낸다.
  4. 꼭 지켜야 할 규칙은 Hook으로. 사람·모델이 깜빡해도 강제되는 안전장치로 만든다.
  5. 외부 능력은 MCP, 공유는 Plugin. 팀에 퍼뜨릴 단계가 오면 묶는다.
"매번 다시 하는 것"이 다음 후보다 생산성 향상은 거창한 설계가 아니라, 반복되는 마찰을 발견해 알맞은 레이어로 옮기는 일의 누적이다. 같은 지시를 반복하면 Skill, 같은 위험을 반복 점검하면 Hook, 같은 외부 조회를 반복하면 MCP. 한편, 작은 일에 무거운 subagent나 과한 스킬을 남발하면 관리 비용만 늘어난다 — 마찰이 실제로 반복될 때 구조화한다.

정리와 주의

  • 한 문장 요약 — 확장이란 모델에 지식(command·skill)·일손(subagent)·연결(MCP)·자동개입(hook)을 더하는 것이고, plugin은 그것들의 포장지다.
  • 선택은 세 축으로 — 누가 트리거하나 / 컨텍스트가 분리되나 / 무엇을 더하나. 이 셋이면 대부분 갈린다.
  • 전이 가능한 투자 — Skill·MCP는 표준을 향하므로, 구조로 익힌 이해는 특정 도구에 묶이지 않는다.
  • 세부는 공식 문서로 — 파일 경로·명령어·이벤트 이름은 버전에 따라 바뀐다. 이 글의 구조를 뼈대로 두고 정확한 사양은 문서에서 확인한다.
