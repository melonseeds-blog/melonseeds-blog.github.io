강의 개요와 대상

Building with the Claude API는 Anthropic이 직접 제공하는 8시간 분량의 공식 강의다. 84개 차시와 10개 퀴즈로 구성되어 있고, Claude API를 처음 다루는 개발자가 한 사이클(요청 → 평가 → 도구/RAG → 에이전트)을 끝까지 경험할 수 있도록 설계되어 있다.

누구를 위한 강의인가

  • 백엔드/풀스택 엔지니어로 AI 기능을 제품에 붙이려는 사람
  • 챗봇, 가상 어시스턴트, 문서 분석 도구를 만들려는 사람
  • 이미 GPT API 같은 LLM API를 써본 사람이 Claude 특유의 패턴(시스템 프롬프트, 도구 사용, 캐싱)을 배우려는 경우
  • 전제: Python 기본 문법과 JSON 처리 정도는 알아야 한다

API 기초 — 요청, 멀티턴, 시스템 프롬프트

강의의 첫 큰 덩어리는 Claude API를 실제로 호출해보는 부분이다. SDK는 Python/TypeScript 둘 다 제공되고, 강의는 Python 기준이다.

인증과 첫 요청

API 키는 console.anthropic.com에서 발급하고, 환경변수 ANTHROPIC_API_KEY에 넣는 것이 표준 패턴이다. 키를 코드에 하드코딩하지 말라는 부분이 강의 초반에 강조된다.

from anthropic import Anthropic client = Anthropic() # 환경변수에서 자동 로드 response = client.messages.create( model="claude-opus-4-5", max_tokens=1024, messages=[{"role": "user", "content": "Hello"}], ) print(response.content[0].text)

멀티턴 대화의 핵심

Claude API는 상태를 저장하지 않는다(stateless). 대화를 이어가려면 클라이언트가 직접 이전 메시지 리스트를 통째로 다시 보내야 한다. 강의에서 가장 자주 반복되는 패턴이 이거다.

"메시지 리스트는 항상 user/assistant가 번갈아 나와야 한다." Messages must alternate between user and assistant.

이 규칙을 어기면 400 에러가 나기 때문에, 채팅 봇을 만들 때 직접 리스트를 관리하는 코드 패턴(append 후 다시 create 호출)이 필수다.

시스템 프롬프트

시스템 프롬프트는 messages에 넣지 않고 별도의 system 파라미터로 분리한다. 역할 정의, 톤, 출력 형식 같은 "대화 전체를 관통하는 규칙"을 여기에 둔다.

response = client.messages.create( model="claude-opus-4-5", max_tokens=1024, system="You are a helpful coding assistant. Always answer in Korean.", messages=[...] )

Temperature, 스트리밍, 구조화된 출력

  • Temperature: 0에 가까울수록 결정적, 1에 가까울수록 창의적. 강의는 분류·추출 작업은 0, 글쓰기는 0.7~1을 기본 권장한다.
  • 스트리밍: client.messages.stream(...)로 토큰 단위 수신. 챗봇 UX에 필수.
  • 구조화된 데이터: 강의는 JSON 출력 요구 시 도구 사용(Tool Use)을 통한 강제 스키마를 우선 권장한다. 단순히 "JSON으로 답하라" 프롬프트보다 훨씬 안정적이다.

프롬프트 평가 워크플로우

강의에서 가장 인상적인 모듈이다. "프롬프트를 짰다 → 잘 되는 것 같다 → 배포"라는 단계가 얼마나 위험한지를 보여주고, 대안으로 평가 주도 개발(eval-driven development)을 제시한다.

전형적인 평가 워크플로우

  1. 테스트 데이터셋 생성 — 실제 입력과 비슷한 케이스 30~100건
  2. 각 케이스에 대해 기대 결과(또는 합격 조건) 정의
  3. 현재 프롬프트로 일괄 실행 → 결과 수집
  4. 채점(모델 기반 or 코드 기반)
  5. 지표(정확도/리콜 등) 모니터링하며 프롬프트 개선

모델 기반 채점 vs 코드 기반 채점

구분모델 기반(LLM-as-judge)코드 기반
적합한 경우"답변이 친절한가" 같은 정성 평가"숫자가 42인가" 같은 정량 평가
장점유연, 자연어 기준 가능빠르고 결정적, 무료
단점비용/지연/판정 자체의 흔들림딱딱한 기준만 가능
실무 노트 강의에서 반복되는 메시지가 "프롬프트를 바꿀 때마다 eval을 돌려라"다. 한 번 만들어두면 모델 업그레이드(예: 4.6 → 4.7)했을 때도 회귀 테스트로 그대로 쓸 수 있다.

프롬프트 엔지니어링 5원칙

강의는 프롬프트 엔지니어링을 "마법"이 아니라 반복 가능한 기술로 본다. 다음 다섯 가지가 큰 줄기다.

  1. 명확하고 직접적으로(Be clear and direct) — 모호한 지시는 모호한 답을 부른다. "분석해줘" 대신 "다음 3개 항목을 표로 출력해줘"가 낫다.
  2. 구체적으로(Be specific) — 출력 형식, 길이, 제약을 명시한다.
  3. XML 태그로 구조화 — Claude는 <document>...</document> 같은 태그를 잘 인식한다. 입력 부분, 지시 부분, 예시 부분을 태그로 구분하면 효과가 크다.
  4. 예시 제공(Few-shot) — 정답 예시 2~3개만 보여줘도 출력 일관성이 크게 올라간다.
  5. Chain of thought 유도 — 어려운 추론은 "단계별로 생각하라"고 시키면 정확도가 오른다(또는 Extended thinking 사용).
# XML 태그 예시 prompt = """다음 문서를 요약해라. <document> {user_text} </document> 요약은 3문장 이내, 한국어로."""

도구 사용(Tool Use)

도구 사용은 강의에서 가장 비중이 큰 모듈 중 하나(12강 + 퀴즈)다. Claude가 외부 함수를 호출해 결과를 받아오는 메커니즘이다.

Tool Use의 4단계 흐름

  1. 클라이언트가 사용 가능한 도구 목록(JSON Schema)을 함께 보냄
  2. Claude가 필요하다고 판단하면 tool_use 블록 반환
  3. 클라이언트가 실제 함수를 실행해서 결과를 얻음
  4. tool_result 블록을 messages에 추가해서 다시 보냄 → Claude가 최종 답변 생성

도구 스키마 정의

tools = [{ "name": "get_weather", "description": "Get current weather for a city.", "input_schema": { "type": "object", "properties": { "city": {"type": "string"} }, "required": ["city"] } }]

Anthropic 제공 빌트인 도구

  • Text Editor Tool — Claude가 파일을 직접 읽고 수정한다. Claude Code의 기반.
  • Web Search Tool — 실시간 검색. 모델이 알 수 없는 최신 정보를 가져온다.
  • Code Execution Tool — 샌드박스에서 Python 실행. 계산/데이터 분석에 유용.
  • Computer Use — 스크린샷을 보고 마우스/키보드를 조작한다(별도 모듈).
구조화된 데이터 출력의 정석 강의는 "JSON으로 답해라" 식 프롬프트보다 도구 사용을 추천한다. 도구 스키마 자체가 강제 스키마 역할을 하기 때문에, 출력 검증 코드가 거의 필요 없다.

RAG와 검색 파이프라인

RAG(Retrieval Augmented Generation)는 Claude에게 외부 문서를 컨텍스트로 넣어주는 패턴이다. 강의는 단순 임베딩 검색에서 시작해 실전급 멀티 검색 파이프라인까지 단계적으로 쌓는다.

청킹 전략

긴 문서를 잘게 쪼개는 단계다. 너무 작으면 맥락이 사라지고, 너무 크면 검색이 둔해진다. 강의 권장은 다음과 같다.

  • 고정 토큰 청킹: 가장 단순, 토큰 500~1000
  • 문장/문단 단위: 자연스러운 경계
  • 의미 기반(semantic) 청킹: 임베딩 유사도로 경계 결정
  • 오버랩(겹침) 10~20% 권장

임베딩 검색과 BM25

벡터 검색만으로 충분하지 않다는 게 핵심 메시지다. 의미 검색(임베딩) + 키워드 검색(BM25)을 결합한 하이브리드가 거의 항상 더 낫다.

  • 임베딩: 의미 유사도. "강아지"로 "puppy" 찾기.
  • BM25: 정확 키워드. 제품명, 오류 코드처럼 토큰 자체가 중요한 경우.
  • 리랭킹(reranker): 두 결과를 합친 뒤 별도 모델로 재정렬.

Contextual Retrieval

Anthropic이 발표한 기법으로, 각 청크를 임베딩하기 전에 Claude로 "이 청크가 전체 문서 어느 부분인지" 한 문장 컨텍스트를 붙이는 방식이다. 검색 정확도가 크게 올라간다. 강의 후반에 실습 차시로 나온다.

Claude의 고급 기능

Extended Thinking

모델이 응답 전에 별도의 "사고 토큰"을 소비해 어려운 문제를 풀게 하는 기능이다. 수학, 코딩, 다단계 추론에서 정확도가 눈에 띄게 오른다. 단점은 지연과 비용이라, 모든 호출에 켜는 게 아니라 어려운 케이스에만 켠다.

이미지와 PDF 지원

  • 이미지: base64 또는 URL로 첨부. 차트, 다이어그램, 스크린샷 분석.
  • PDF: 직접 첨부 가능. 텍스트 추출은 모델이 알아서 한다.
  • Files API: 큰 파일을 사전 업로드 후 ID로 재사용 → 토큰/대역폭 절감.

Citations

문서 기반 답변 시 "어느 문장에서 인용했는지"를 자동으로 표시해주는 기능이다. 법률, 의료, 사내 지식 검색에서 환각(hallucination) 위험을 크게 줄인다.

프롬프트 캐싱

강의에서 가장 비용 절감 효과가 큰 기능으로 강조된다. 시스템 프롬프트나 긴 문서처럼 매 요청마다 반복되는 부분을 캐시해두면, 두 번째 요청부터는 그 부분의 토큰 비용이 약 1/10로 떨어진다.

"캐시는 비용보다 지연(latency)을 더 크게 줄인다." Caching reduces latency more than cost.
  • 캐시 가능한 블록: system, messages 초반, tools 정의
  • 최소 청크 크기: 1024 토큰(모델별 상이)
  • TTL: 5분(기본) / 1시간(연장형)

Model Context Protocol(MCP)

MCP는 Anthropic이 만든 도구/리소스/프롬프트를 표준화된 방식으로 제공하는 프로토콜이다. 강의 후반 1/4가 MCP에 할애된다.

왜 MCP가 필요한가

도구 사용(Tool Use)은 각 앱이 도구를 직접 정의하고 실행한다. 도구가 많아지고, 여러 앱이 같은 도구를 쓰게 되면 중복과 유지보수 부담이 폭발한다. MCP는 "도구 제공자(server) ↔ 도구 사용자(client)"를 분리해서 재사용 가능하게 한다.

MCP의 3가지 핵심 개념

  • Tools — 모델이 호출하는 함수(기존 Tool Use와 동일 개념, 서버 측에 정의)
  • Resources — 모델에게 제공할 파일/데이터(읽기 전용 컨텍스트)
  • Prompts — 재사용 가능한 프롬프트 템플릿

실습 흐름

  1. MCP 서버를 Python으로 작성 — 도구/리소스/프롬프트 정의
  2. mcp inspector로 동작 확인(GUI 디버거)
  3. 클라이언트(예: Claude Desktop, Claude Code)에 서버 등록
  4. 대화 중 자동으로 도구가 호출됨
실무 관점 사내 시스템(DB, 사내 API, 파일 서버)을 MCP 서버로 한 번 만들어두면, Claude Desktop이든 Claude Code든 다른 MCP 클라이언트든 모두 그 서버를 그대로 쓸 수 있다. 비전 SDK 프로젝트에서도 "내부 데이터셋 조회 MCP 서버"를 만들어두면 어시스턴트 활용도가 크게 올라간다.

에이전트와 워크플로우

강의의 마지막 큰 모듈이다. 단발 호출이 아닌, 여러 단계에 걸쳐 스스로 결정하면서 일을 처리하는 시스템을 다룬다.

워크플로우 패턴

  • Chaining(체이닝) — 출력 → 다음 입력. 번역 → 요약 → 톤 변환 같은 직렬 파이프라인.
  • Routing(라우팅) — 입력 종류에 따라 다른 프롬프트로 분기. "환불 문의 vs 기술 문의" 분류 후 각 전용 프롬프트로.
  • Parallelization(병렬화) — 같은 입력을 여러 관점에서 동시에 처리 후 합치기. 코드 리뷰에서 보안/성능/스타일을 동시에 검토.
  • Orchestrator-Worker — 상위 모델이 작업을 쪼개 하위 모델에게 분배.

워크플로우 vs 에이전트

구분워크플로우에이전트
흐름개발자가 미리 정의모델이 동적으로 결정
예측가능성높음낮음(자율적)
적합한 작업구조가 명확한 반복 업무탐색적/개방형 문제
예문서 요약 파이프라인Claude Code, Computer Use

Claude Code 셋업과 활용

강의는 Claude Code를 에이전트의 대표 사례로 다룬다. 터미널에서 claude 한 줄로 시작하고, 파일 읽기/쓰기/실행/git 조작을 자율적으로 수행한다. MCP 서버를 붙이면 회사 시스템과도 연결된다.

Anthropic의 권장: 단순한 것부터 강의 마지막에 강조되는 메시지가 "에이전트보다 워크플로우가 먼저"다. 동적 판단이 꼭 필요한 부분만 에이전트로 두고, 나머지는 명시적 워크플로우로 짜는 게 신뢰성/디버깅 모두 유리하다.

실무 적용 포인트

8시간짜리 강의를 끝까지 듣고 나면, Claude를 "그냥 채팅" 수준이 아니라 제품에 내장할 수 있는 컴포넌트로 볼 수 있게 된다. 비전 SDK 프로젝트 관점에서 정리한 적용 포인트는 다음과 같다.

eval-driven development Tool Use로 강제 스키마 하이브리드 RAG(임베딩+BM25) 프롬프트 캐싱으로 비용 절감 MCP로 내부 도구 표준화 워크플로우 우선, 에이전트는 신중히

1. 프롬프트 평가를 CI에 넣기

제품에 LLM이 들어가는 순간, 일반 단위 테스트로는 회귀를 못 잡는다. eval 데이터셋과 채점 코드를 GitLab CI에 묶어두면 모델 업그레이드/프롬프트 수정 시 안전망이 생긴다.

2. 구조화된 출력은 Tool Use로

측정 결과 추출, 검사 리포트 자동 생성 같은 작업에서 JSON 파싱 실패를 거의 없앨 수 있다. JSON Schema로 강제하기 때문에 후처리 코드가 단순해진다.

3. 사내 매뉴얼 RAG 구축 시

비전 SDK 매뉴얼, 카메라 사양서, 트러블슈팅 가이드 같은 문서는 검색 정확도가 중요하다. 임베딩만 쓰지 말고 BM25를 함께 두는 하이브리드 패턴, Contextual Retrieval을 적용하면 효과가 크다.

4. 캐싱은 시스템 프롬프트가 길어질 때 켜기

코드 어시스턴트나 도메인 특화 봇은 시스템 프롬프트가 수천 토큰을 넘어간다. 이때 캐싱이 필수다. 비용은 둘째치고 첫 토큰 지연이 눈에 띄게 줄어든다.

5. MCP 서버를 하나 만들어두기

사내 빌드 시스템, 테스트 결과 DB, 이미지 데이터셋 같은 자원을 MCP 서버로 노출하면 Claude Code, Claude Desktop, 사내 챗봇이 모두 같은 인터페이스를 쓸 수 있다.

한 줄 요약 Claude API를 "강력한 채팅 SDK"가 아니라 "평가, 도구, 검색, 프로토콜이 갖춰진 컴포넌트 플랫폼"으로 보는 시각을 얻게 해주는 강의다. 클라우드 배포 옵션은 Bedrock과 Vertex AI 통합 정리에서 이어진다.
