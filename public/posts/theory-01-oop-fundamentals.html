객체지향 프로그래밍이란?

객체지향 프로그래밍(Object-Oriented Programming, OOP)은 데이터와 그 데이터를 다루는 동작을 객체(object)라는 하나의 단위로 묶어 프로그램을 구성하는 패러다임이다. 현실 세계의 사물을 코드로 모델링하려는 시도에서 출발했다.

예를 들어 "카메라"라는 객체는 해상도·노출 시간 같은 데이터와 캡처·트리거 설정 같은 동작을 함께 가진다. 데이터와 동작이 흩어져 있지 않고 한 곳에 모여 있으므로, 그 객체를 다룰 때 어디를 봐야 하는지 명확하다.

절차지향과의 차이

절차지향은 데이터와 함수가 분리되어 있다. 데이터는 구조체에 담고, 함수는 그 구조체를 인자로 받아 처리한다. 기능 중심으로 생각하며, 프로그램은 "함수의 호출 흐름"으로 구성된다.

// 절차지향 — 데이터와 함수가 분리됨
struct Image
{
    unsigned char* data;
    int width;
    int height;
};

void applyBlur(Image* img, int kernelSize);   // 함수가 데이터를 받아 처리
void saveImage(Image* img, const char* path);

// 객체지향 — 데이터와 동작을 하나로 묶음
class Image
{
public:
    void ApplyBlur(int kernelSize);           // 객체가 스스로 동작
    void Save(const std::string& path);

private:
    std::vector<unsigned char> m_data;        // 데이터는 내부에 숨김
    int m_width;
    int m_height;
};

차이는 단순히 문법이 아니다. 절차지향에서는 Image 구조체의 내부 구조가 바뀌면 그것을 사용하는 모든 함수를 검토해야 한다. 객체지향에서는 데이터를 private로 숨기므로, 내부 구조 변경의 영향이 클래스 안으로 제한된다. 이 "변경 격리"가 OOP가 주는 가장 큰 실용적 이점이며, 아래 4대 특성이 모두 이를 떠받친다.

캡슐화 (Encapsulation)

캡슐화는 데이터와 그것을 다루는 메서드를 하나로 묶고, 외부에서 내부 구현에 직접 접근하지 못하도록 숨기는 것이다. 캡슐화는 두 가지를 동시에 의미한다 — 묶기(bundling)와 정보 은닉(information hiding).

접근 제어자

C++은 세 가지 접근 수준을 제공한다.

제어자접근 범위용도
public어디서나클래스가 제공하는 인터페이스
private같은 클래스 내부만구현 세부, 내부 상태
protected같은 클래스 + 파생 클래스상속 계층 안에서만 공유할 멤버
class Camera
{
public:
    // 외부에 노출하는 인터페이스
    ErrorCode SetExposure(double microseconds);
    double GetExposure() const;

private:
    // 내부 구현 — 외부는 존재 자체를 알 필요 없음
    double m_exposureUs;
    bool m_isStreaming;

    void validateExposureRange(double value);   // private 메서드
};

getter / setter의 진짜 목적

멤버 변수를 private로 막고 GetXxx() / SetXxx()를 여는 것은 캡슐화의 흔한 형태다. 하지만 핵심은 "접근 함수를 만드는 것"이 아니라 접근 지점을 통제하는 것이다. setter 안에서 값을 검증하거나, 단위를 변환하거나, 변경을 로깅할 수 있다.

// 단순 전달만 하는 setter — 캡슐화의 의미가 거의 없다
void SetExposure(double v) { m_exposureUs = v; }

// 통제하는 setter — 검증과 상태 보호를 담당한다
ErrorCode Camera::SetExposure(double microseconds)
{
    if (microseconds < kMinExposureUs || microseconds > kMaxExposureUs)
    {
        return ErrorCode::InvalidParameter;
    }
    m_exposureUs = microseconds;
    return ErrorCode::Ok;
}

정보 은닉이 주는 이점 — 변경 격리

내부 구현을 숨기면, 그 구현을 바꿔도 외부 코드는 영향을 받지 않는다. 위 Camera가 노출 시간을 마이크로초 대신 내부적으로 나노초로 저장하도록 바꿔도, public 인터페이스만 유지하면 호출하는 쪽 코드는 한 줄도 고칠 필요가 없다. 이것이 캡슐화가 제공하는 변경의 격리다.

모든 멤버에 getter/setter를 다는 것은 캡슐화가 아니다 private 멤버마다 기계적으로 Get/Set 쌍을 만들면, 사실상 모든 내부 상태가 외부에 노출된 것과 같다. 이것은 캡슐화가 아니라 구조체에 함수 껍데기를 씌운 것일 뿐이다. "이 값을 외부가 정말 바꿔야 하는가?"를 먼저 묻고, 필요한 것만 열어야 한다.

상속 (Inheritance)

상속은 기존 클래스(기반 클래스, base class)의 속성과 동작을 물려받아 새로운 클래스(파생 클래스, derived class)를 만드는 것이다. 공통된 부분을 기반 클래스에 모으고, 파생 클래스는 차이점만 추가하거나 재정의한다.

is-a 관계

상속은 "B는 A의 한 종류다(B is-a A)"가 성립할 때만 적절하다. AreaScanCamera는 Camera의 한 종류이므로 상속이 자연스럽다. 반면 Camera가 Lens를 가진다고 해서 Camera가 Lens를 상속하면 안 된다 — 이것은 "가진다(has-a)" 관계이며 합성(composition)으로 표현해야 한다.

// is-a 관계 — 상속이 적절하다
class Camera
{
public:
    virtual ErrorCode Capture(Image& outImage) = 0;
    double GetExposure() const { return m_exposureUs; }

protected:
    double m_exposureUs = 1000.0;
};

class AreaScanCamera : public Camera   // AreaScanCamera is-a Camera
{
public:
    ErrorCode Capture(Image& outImage) override;   // 차이점만 재정의
};

상속의 위험

상속은 강력하지만 대가가 있다. 파생 클래스는 기반 클래스의 protected 멤버와 구현 세부에 의존하게 되어 강한 결합(tight coupling)이 생긴다. 기반 클래스를 수정하면 모든 파생 클래스가 영향을 받으며, 때로는 컴파일은 되지만 동작이 미묘하게 깨진다. 이를 깨지기 쉬운 기반 클래스 문제(fragile base class problem)라 한다.

상속을 코드 재사용 수단으로만 쓰지 말 것 "이 클래스에 쓸 만한 메서드가 있으니 상속받자"는 동기는 위험하다. 상속은 영구적인 is-a 계약이며, 단순히 코드를 빌려 쓰는 수단이 아니다. 재사용만이 목적이라면 합성이 거의 항상 더 안전하다.

상속보다 합성

"상속보다 합성(composition over inheritance)"은 객체지향 설계의 핵심 격언이다. 합성은 다른 객체를 멤버로 가지고, 필요한 기능을 그 객체에 위임(delegate)한다. 결합이 느슨하고, 런타임에 구성을 바꿀 수 있으며, 기반 클래스의 변경에 휘둘리지 않는다.

// 상속 — Logger를 강하게 물려받음 (Camera is-a Logger? 어색하다)
class Camera : public Logger { /* ... */ };

// 합성 — Logger를 가지고 위임함
class Camera
{
public:
    ErrorCode Capture(Image& outImage)
    {
        m_logger.Info("capture start");   // 가진 객체에 위임
        // ...
        return ErrorCode::Ok;
    }

private:
    Logger m_logger;   // has-a 관계
};
비교상속 (Inheritance)합성 (Composition)
관계is-a (B는 A다)has-a (B는 A를 가진다)
결합도강함 — 기반 클래스 내부에 의존느슨함 — 공개 인터페이스에만 의존
유연성컴파일 타임에 고정런타임에 교체 가능
변경 영향기반 클래스 변경이 전파됨위임 대상 변경이 격리됨
적절한 경우진짜 is-a, 다형성이 필요할 때기능 재사용, 부분의 조합

다형성 (Polymorphism)

다형성은 같은 인터페이스로 서로 다른 동작을 수행하는 능력이다. 호출하는 쪽은 "무엇을 하라"고만 말하고, "어떻게 하는가"는 실제 객체가 결정한다.

런타임 다형성 — 가상 함수와 동적 디스패치

C++에서 런타임 다형성은 virtual 함수로 구현한다. 기반 클래스 포인터/참조로 파생 객체를 가리킬 때, 실제 타입에 맞는 함수가 실행 시점에 선택된다. 이것을 동적 디스패치(dynamic dispatch)라 한다.

class Filter
{
public:
    virtual ~Filter() = default;
    virtual ErrorCode Apply(Image& image) = 0;   // 순수 가상 함수
};

class GaussianBlur : public Filter
{
public:
    ErrorCode Apply(Image& image) override;      // 재정의 (overriding)
};

class MedianFilter : public Filter
{
public:
    ErrorCode Apply(Image& image) override;
};

// 호출하는 쪽은 구체 타입을 모른다
void RunPipeline(const std::vector<std::unique_ptr<Filter>>& filters, Image& image)
{
    for (const auto& filter : filters)
    {
        filter->Apply(image);   // 실제 타입에 맞는 Apply가 실행됨
    }
}
RunPipeline 실행 흐름
filters[0] -> GaussianBlur::Apply 실행 filters[1] -> MedianFilter::Apply 실행 filters[2] -> GaussianBlur::Apply 실행

RunPipeline은 새로운 필터 종류가 추가되어도 한 줄도 바뀌지 않는다. 새 필터는 Filter를 상속해 Apply만 구현하면 된다. 이것이 다형성이 주는 확장성이다.

컴파일 타임 다형성 — 템플릿과 오버로딩

다형성이 가상 함수만을 뜻하는 것은 아니다. C++은 함수 오버로딩과 템플릿으로 컴파일 타임 다형성도 제공한다. 타입에 따라 어떤 코드를 쓸지 컴파일 시점에 결정되므로 런타임 오버헤드가 없다.

// 오버로딩 — 같은 이름, 다른 매개변수
void Save(const Image& image, const std::string& path);
void Save(const PointCloud& cloud, const std::string& path);

// 템플릿 — 타입에 무관하게 같은 로직
template <typename T>
T Clamp(T value, T low, T high)
{
    return (value < low) ? low : (value > high) ? high : value;
}

int   a = Clamp(15, 0, 10);      // int 버전이 생성됨
double b = Clamp(1.5, 0.0, 1.0); // double 버전이 생성됨
런타임 vs 컴파일 타임 다형성 가상 함수는 유연하지만 vtable을 통한 간접 호출 비용이 있다. 템플릿은 빠르지만 코드가 타입마다 생성되고 컴파일 타임에 타입이 고정된다. 플러그인처럼 런타임에 종류가 결정되는 구조에는 가상 함수가, 성능이 중요한 수치 코드에는 템플릿이 적합하다.

추상화 (Abstraction)

추상화는 대상에서 본질적인 특징만 남기고 불필요한 세부를 숨기는 것이다. 캡슐화가 "구현을 숨긴다"는 메커니즘이라면, 추상화는 "무엇을 드러내고 무엇을 감출지 결정한다"는 설계 행위에 가깝다.

추상 클래스와 인터페이스

C++에는 별도의 interface 키워드가 없다. 대신 순수 가상 함수만 가진 클래스로 인터페이스를 표현한다. 추상 클래스는 "이런 동작을 제공해야 한다"는 계약만 정의하고, 구체적인 구현은 파생 클래스에 맡긴다.

// 인터페이스 — 순수 가상 함수만 가진 추상 클래스
class IImageSource
{
public:
    virtual ~IImageSource() = default;

    // "이미지를 한 장 가져온다"는 계약. 어떻게 가져오는지는 정의하지 않음
    virtual ErrorCode Grab(Image& outImage) = 0;
    virtual bool IsConnected() const = 0;
};

// 구현 1 — 파일에서 읽기
class FileImageSource : public IImageSource { /* ... */ };

// 구현 2 — 카메라에서 캡처
class CameraImageSource : public IImageSource { /* ... */ };

// 사용하는 쪽은 IImageSource만 알면 된다
ErrorCode ProcessNextFrame(IImageSource& source)
{
    Image frame;
    if (source.Grab(frame) != ErrorCode::Ok)
    {
        return ErrorCode::DeviceError;
    }
    // 파일인지 카메라인지 신경 쓰지 않는다
    return ErrorCode::Ok;
}

추상화 수준

좋은 설계는 일관된 추상화 수준을 유지한다. 하나의 함수나 클래스 안에서 고수준 개념(이미지 처리 파이프라인 실행)과 저수준 세부(메모리 정렬, 픽셀 비트 시프트)가 뒤섞이면 읽기 어렵다. 고수준은 고수준끼리, 저수준은 저수준끼리 모아 계층을 만든다.

추상화의 기준은 "사용자가 알아야 하는 것" 무엇을 숨길지 고민될 때는 "이 인터페이스를 쓰는 사람이 이것을 정말 알아야 하는가?"를 물으면 된다. 알 필요가 없다면 숨긴다. 추상화는 코드를 줄이는 기술이 아니라, 사용자의 인지 부담을 줄이는 기술이다.

네 특성의 관계

4대 특성은 따로 노는 개념이 아니라 서로 맞물려 작동한다. 캡슐화로 내부를 숨기고, 추상화로 드러낼 인터페이스를 정의하고, 상속으로 그 인터페이스를 이어받아, 다형성으로 다양한 구현을 같은 방식으로 다룬다.

캡슐화로 숨기고 → 추상화로 인터페이스를 정하고 → 상속으로 잇고 → 다형성으로 다룬다
특성핵심 질문제공하는 가치
캡슐화무엇을 감출 것인가?변경의 격리, 상태 보호
추상화무엇을 드러낼 것인가?인지 부담 감소, 계약 정의
상속무엇을 물려받을 것인가?공통 계약/구현의 공유
다형성다른 것을 어떻게 같게 다룰까?확장성, 호출부의 안정성

객체지향이 항상 답은 아니다

객체지향은 강력한 도구이지만 만능은 아니다. 문제의 성격에 따라 다른 패러다임이 더 명료할 수 있다.

함수형·절차적 접근이 나은 경우

상태 없이 입력을 받아 출력만 내는 순수 계산은 함수로 표현하는 편이 깔끔하다. 픽셀 변환, 좌표 계산, 통계 집계 같은 코드를 굳이 클래스로 감쌀 이유가 없다. 데이터 변환 파이프라인은 함수형 스타일이, 단순한 스크립트성 작업은 절차적 스타일이 더 읽기 쉽다.

// 굳이 클래스로 만들 이유가 없는 순수 계산
double ComputeMean(const std::vector<double>& values)
{
    if (values.empty())
    {
        return 0.0;
    }
    double sum = std::accumulate(values.begin(), values.end(), 0.0);
    return sum / static_cast<double>(values.size());
}

// 이것을 StatisticsCalculator 클래스로 감싸면 오히려 복잡해진다
"everything is a class"의 함정 모든 것을 클래스로 만들려는 강박은 흔한 과한 객체지향이다. StringUtils 같은 상태 없는 유틸리티 클래스, 메서드가 하나뿐인 Manager·Helper·Processor 클래스는 함수 하나로 충분한 일을 객체로 부풀린 결과인 경우가 많다. 클래스는 상태와 동작을 함께 가질 때 가치가 있다. 상태가 없다면 자유 함수가 더 정직하다.

산업 SW 관점

산업용 이미징 SDK 같은 시스템에서 4대 특성은 추상적인 이론이 아니라 플러그인 구조의 토대로 직결된다. 핵심은 인터페이스 설계다.

예를 들어 데이터 플로우 기반 블록 에디터에서 모든 처리 블록이 IProcessBlock이라는 인터페이스를 구현한다고 하자.

// 모든 처리 블록이 따르는 계약 (추상화)
class IProcessBlock
{
public:
    virtual ~IProcessBlock() = default;

    // 입력을 받아 처리하고 출력을 낸다 — 어떻게 처리하는지는 각 블록이 결정
    virtual ErrorCode Process(const BlockInput& input, BlockOutput& output) = 0;
    virtual std::string GetBlockName() const = 0;
};

// 엔진은 구체 블록을 전혀 모른 채 실행한다 (다형성)
ErrorCode FlowEngine::Run(const std::vector<std::shared_ptr<IProcessBlock>>& blocks)
{
    for (const auto& block : blocks)
    {
        BlockInput in = collectInput(block);
        BlockOutput out;
        ErrorCode ec = block->Process(in, out);   // 동적 디스패치
        if (ec != ErrorCode::Ok)
        {
            return ec;
        }
        storeOutput(block, out);
    }
    return ErrorCode::Ok;
}

이 구조의 가치는 분명하다. 추상화로 IProcessBlock 계약을 정의했기에, 블러·엣지·블롭 분석 같은 새 블록을 추가해도 FlowEngine은 바뀌지 않는다. 다형성 덕분에 엔진은 구체 타입을 몰라도 된다. 캡슐화로 각 블록의 내부 알고리즘이 외부와 격리된다. 결과적으로 새 블록을 플러그인처럼 끼워 넣을 수 있다 — 이것이 확장 가능한 SDK 설계의 출발점이다.

C++ 시리즈와 연결 인터페이스 설계와 플러그인 구조의 구체적인 C++ 구현은 별도 글에서 다룬다. 이 글에서는 4대 특성이 그 설계의 왜를 떠받친다는 점만 짚는다.

흔한 오해

오해 1 — 상속 = 코드 재사용

상속을 코드 재사용의 일차 수단으로 여기는 것은 가장 흔한 오해다. 상속은 재사용 도 제공하지만 그 본질은 is-a 계약과 다형성이다. 단지 메서드를 빌려 쓰고 싶을 뿐이라면, 강한 결합을 만드는 상속보다 합성이 거의 항상 낫다. "상속받을까?"라는 질문 앞에서는 먼저 "이것이 정말 is-a인가, 아니면 has-a인가?"를 물어야 한다.

오해 2 — getter/setter를 달면 캡슐화다

모든 멤버에 접근 함수를 다는 것은 캡슐화의 형태만 흉내 낸 것이다. 진짜 캡슐화는 "외부가 알 필요 없는 것을 숨기는 것"이지 "접근 함수를 통해 모든 것을 노출하는 것"이 아니다. setter가 단순 대입만 한다면, 그 멤버는 애초에 외부가 바꿔도 되는지부터 의심해야 한다.

오해 3 — 다형성은 그저 문법이다

다형성의 실질적 가치는 조건 분기(if-else / switch)의 제거에 있다. 타입에 따라 동작이 갈리는 if (type == A) ... else if (type == B) ... 구조는, 타입이 늘 때마다 모든 분기문을 찾아 수정해야 한다. 이를 다형성으로 바꾸면 새 타입은 새 클래스 추가만으로 끝나고 기존 코드는 닫혀 있다. 다형성을 쓰는데도 여전히 타입 분기 if-else가 남아 있다면, 다형성을 제대로 활용하지 못한 신호다.

// 안티 패턴 — 타입 분기. 필터가 늘 때마다 이 함수를 고쳐야 한다
ErrorCode ApplyFilter(Image& image, FilterType type)
{
    if (type == FilterType::GaussianBlur)      { /* 가우시안 로직 */ }
    else if (type == FilterType::Median)       { /* 미디언 로직 */ }
    else if (type == FilterType::Sobel)        { /* 소벨 로직 */ }
    // 새 필터 추가 = 또 else if ...
    return ErrorCode::Ok;
}

// 다형성 적용 — 분기가 사라지고, 새 필터는 새 클래스만 추가하면 된다
ErrorCode ApplyFilter(Image& image, Filter& filter)
{
    return filter.Apply(image);
}
