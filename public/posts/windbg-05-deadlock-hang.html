4편까지는 프로세스가 죽는 상황을 다뤘다. 크래시는 적어도 친절하다. 예외가 나고, WER이 덤프를 떠주고, 콜스택이 단서를 남긴다(1편). 그런데 현장에서 "프로그램이 죽지는 않는데 멈췄어요"라는 신고가 들어오면 이야기가 완전히 달라진다. 이번 편은 행(hang), 그중에서도 멀티스레드 비전 파이프라인의 데드락을 추적한다.

행과 크래시의 차이

크래시는 예외로 프로세스가 종료된다. 종료 순간 운영체제와 WER이 개입해 덤프를 자동으로 남긴다. 반면 행은 프로세스가 살아 있다. UI는 "응답 없음" 상태로 멈추고, 처리 스레드는 진행을 멈췄지만 프로세스 자체는 종료되지 않는다. 예외가 발생하지 않으니 자동 덤프도 없다.

여기서 행 분석의 첫 번째 원칙이 나온다. 멈춘 바로 그 순간에, 사람이 직접 덤프를 떠야 한다. 크래시처럼 사후에 떨어진 파일을 받는 게 아니라, 현장에서 멈춘 상태를 포착해야 한다.

행은 크게 두 부류로 나뉘고, 분석 접근이 서로 다르다.

  • 대기 행(blocking hang) — 스레드들이 무언가를 무한정 기다리며 잠들어 있다. CPU 사용률은 0%에 가깝다. 데드락이 대표적이다.
  • 폭주 행(spinning hang) — 한 스레드가 CPU를 100% 태우며 무한 루프나 busy-wait를 돈다. 멈춘 것처럼 보이지만 사실 미친 듯이 돌고 있다.
먼저 CPU 사용률부터 본다 행 신고를 받으면 작업 관리자에서 해당 프로세스의 CPU 사용률을 먼저 확인한다. 0%에 가까우면 대기 행(데드락 의심), 한 코어를 꽉 채우고 있으면 폭주 행이다. 이 한 가지만으로 분석 방향이 절반으로 좁혀진다.

행 상태 덤프 수집

멈춘 순간을 포착하는 방법은 두 가지다. 둘 다 full memory 덤프(-ma 상당)를 떠야 스레드와 락 상태가 온전히 담긴다.

작업 관리자

가장 간단한 방법이다. 작업 관리자 > 세부 정보 탭에서 대상 프로세스를 우클릭하고 "덤프 파일 만들기"를 누르면 %temp%에 full dump가 떨어진다. 별도 도구 설치가 필요 없어 고객 PC에서 바로 쓸 수 있다. 다만 한 번에 한 장만 뜨고, 시점을 정밀하게 고르기 어렵다.

procdump

Sysinternals의 procdump는 행 분석에 훨씬 유연하다. 특히 시차를 둔 연속 덤프를 뜰 수 있어, "정말 멈춘 것인지" 아니면 "아주 느리게 진행 중인지"를 구분할 수 있다.

:: 즉시 full memory 덤프 1장
procdump -ma MyVision.exe

:: 10초 간격으로 3장 (연속 캡처 → 스택 비교용)
procdump -ma -n 3 -s 10 MyVision.exe

:: 윈도우가 "응답 없음(hung)" 상태가 되면 자동 덤프
procdump -ma -h MyVision.exe

:: PID로 지정도 가능
procdump -ma 1234

-ma는 full memory, -n은 덤프 장수, -s는 간격(초), -h는 hung window 감지다. 행 분석에서 여러 시점의 덤프를 비교하는 것이 결정적이다. 두 덤프에서 같은 스레드들이 똑같은 위치에 멈춰 있으면 진짜 블로킹이거나 데드락이고, 콜스택이 조금씩 달라지면 멈춘 게 아니라 느리게 진행 중인 것이다.

최소 두 장, 가능하면 시차를 두고 행은 단일 덤프로 판단하면 오진하기 쉽다. "멈춤"과 "느림"은 한 장으로는 구별되지 않는다. procdump -ma -n 3 -s 10으로 10초 간격 3장을 떠서 스택이 고정인지 변하는지 확인하는 습관을 들인다.

전체 스레드 콜스택

크래시 분석은 "죽은 스레드 하나"의 콜스택을 본다. 행 분석은 정반대다. 모든 스레드가 각자 어디서 멈췄는지를 펼쳐 놓고, 서로의 관계를 읽어야 한다. WinDbg의 스레드 명령을 먼저 정리한다.

명령의미
~스레드 목록(인덱스, TID, 상태)
~<n>sn번 스레드로 컨텍스트 전환
~~[TID]sTID(16진)로 스레드 전환
k / kb현재 스레드 콜스택 (kb는 앞 인자 표시)
~*k모든 스레드의 콜스택
~*kb모든 스레드 콜스택 + 인자

행 분석의 출발점은 거의 항상 ~*kb다. 전체 스레드를 한 화면에 펼쳐 놓고, 같은 함수에서 멈춰 있는 스레드 무리를 스캔한다. 특히 여러 스레드가 동시에 WaitForSingleObject나 RtlEnterCriticalSection에 걸려 있으면, 같은 락을 두고 경합 중일 가능성이 높다.

0:000> ~*kb

.  0  Id: 1a2c.0b10   ChildEBP RetAddr  Args
       ntdll!NtWaitForSingleObject+0x14
       KERNELBASE!WaitForSingleObjectEx+0x8e
       MyVision!FrameQueue::pop+0x52        // process 스레드
       MyVision!ProcessThread::run+0xc1

   5  Id: 1a2c.0c44   ChildEBP RetAddr  Args
       ntdll!NtWaitForSingleObject+0x14
       ntdll!RtlpWaitOnCriticalSection+0x110
       ntdll!RtlEnterCriticalSection+0x142
       MyVision!FrameQueue::push+0x3a       // grab 스레드, 같은 큐 락 대기
       MyVision!GrabThread::run+0x88

위에서 5번 스레드는 RtlEnterCriticalSection에서 멈춰 있다. 크리티컬 섹션을 잡으려다 누군가에게 막혔다는 뜻이다. 0번은 WaitForSingleObjectEx에서 대기 중이다. 이 둘이 서로 얽혀 있는지가 다음 질문이다.

데드락 분석

데드락은 두(이상의) 스레드가 서로가 가진 자원을 기다리며 영원히 멈추는 상태다. 가장 단순한 형태는 이렇다.

스레드 A: 락1 보유 → 락2 를 기다림 ⏳
스레드 B: 락2 보유 → 락1 을 기다림 ⏳

A는 B가 락2를 놓길 기다리고, B는 A가 락1을 놓길 기다린다.
둘 다 영원히 양보하지 않는다 → 데드락 (사이클)

콜스택에서 찾을 신호

대기 스레드의 콜스택에는 무엇을 기다리는지가 드러난다. 네이티브 코드에서 자주 보는 패턴은 다음과 같다.

  • ntdll!NtWaitForSingleObject + KERNELBASE!WaitForSingleObjectEx — 이벤트·뮤텍스·세마포어 같은 커널 객체 대기.
  • ntdll!RtlpWaitOnCriticalSection + ntdll!RtlEnterCriticalSection — CRITICAL_SECTION 대기. 네이티브 데드락에서 가장 흔한 신호다.
  • ntdll!ZwWaitForAlertByThreadId 계열 — SRWLOCK이나 std::mutex 내부 구현에서 보일 수 있다.

추적 절차

데드락 확정은 "사이클"을 찾는 일이다. 순서대로 좁혀 들어간다.

  1. ~*kb로 대기 중인 스레드들을 추린다(RtlEnterCriticalSection, WaitForSingleObject 등에 걸린 스레드).
  2. 각 스레드가 무슨 락을 기다리는지 확인한다.
  3. 그 락의 소유자가 누구인지 추적한다(!locks / !critsec, 다음 절).
  4. 소유자가 또 다른 락을 기다리고, 그 락의 소유자가 다시 첫 스레드라면 사이클이 닫힌다 = 데드락 확정.
단순 대기는 데드락이 아니다 빈 큐에서 condition variable로 잠들어 있는 process 스레드는 그 자체로는 정상이다. 깨워줄 grab 스레드가 살아 있다면 곧 진행한다. 데드락은 반드시 사이클이 있어야 한다. "기다리는 스레드"를 봤다고 곧장 데드락이라 결론짓지 말고, 그 대기가 닫힌 고리의 일부인지 확인한다.

!locks와 !critsec

락 소유자를 손으로 추적하는 대신, WinDbg 확장이 한 번에 보여준다.

!locks

!locks는 프로세스의 모든 CRITICAL_SECTION을 훑어 상태와 소유 스레드를 나열한다. 경합 중인(대기자가 있는) 락을 빠르게 식별할 수 있다.

0:000> !locks

CritSec MyVision!g_queueLock+0 at 00007ff6`0a3c1240
LockCount          1
RecursionCount     1
OwningThread       0c44          // 이 락은 grab 스레드(TID 0c44)가 보유
EntryCount         0
ContentionCount    1

CritSec MyVision!g_poolLock+0 at 00007ff6`0a3c12a0
LockCount          1
RecursionCount     1
OwningThread       0b10          // 이 락은 process 스레드(TID 0b10)가 보유
ContentionCount    1

OwningThread가 핵심이다. 위에서 큐 락은 grab 스레드(0c44)가, 풀 락은 process 스레드(0b10)가 쥐고 있다. 그런데 앞서 ~*kb에서 grab 스레드는 큐 락이 아니라 다른 락을 기다리고 있었다. 두 스레드가 서로의 락을 기다린다면 사이클이다.

!critsec

특정 크리티컬 섹션 하나를 자세히 보려면 !critsec <address>를 쓴다. LockCount, OwningThread, LockSemaphore 등 상세 상태가 나온다. 소유자 TID를 얻으면 ~~[TID]s로 그 스레드로 전환해 지금 무엇을 하는지(또 다른 락을 기다리는지) 확인한다.

0:000> !critsec 00007ff6`0a3c1240
CritSec MyVision!g_queueLock+0 at 00007ff60a3c1240
LockCount          1
OwningThread       0c44

0:000> ~~[0c44]s        // 소유 스레드로 전환
0:005> k               // 소유자가 지금 뭘 하는지 → 또 다른 락 대기면 데드락
!locks는 CRITICAL_SECTION만 본다 !locks는 CRITICAL_SECTION을 대상으로 한다. SRWLOCK이나 std::mutex는 Windows에서 내부적으로 다른 동기화 기본형으로 구현될 수 있어 !locks 목록에 나오지 않을 수 있다. 그럴 때는 락 목록에 의존하지 말고, 각 스레드의 콜스택을 직접 읽어 무엇을 기다리는지 판단해야 한다.

CPU 폭주 vs 대기 행

대기 행이 아니라 폭주 행이면 락 추적은 헛수고다. 아무도 락을 기다리지 않고, 한 스레드가 그냥 미친 듯이 돌고 있기 때문이다. 둘을 가르는 명령이 !runaway다.

!runaway는 스레드별 누적 CPU 시간을 보여준다. 한 스레드의 사용자 모드 시간이 압도적으로 크면 그 스레드가 폭주 용의자다.

0:000> !runaway

 User Mode Time
  Thread       Time
   5:0c44      0 days 0:01:58.421     // 거의 2분간 CPU 독식 → 폭주 용의자
   0:0b10      0 days 0:00:00.015
   3:0d20      0 days 0:00:00.000

!runaway는 기본적으로 사용자 모드 시간을 보여주고, !runaway 7처럼 비트마스크를 주면 사용자 시간(1) · 커널 시간(2) · 경과 시간(4)을 함께 본다. 폭주 스레드를 찾으면 ~<n>s; k로 전환해 어느 루프에서 도는지 확인한다. 여기서도 두 덤프 비교가 유효하다. 같은 스레드가 두 덤프 모두에서 같은 구간을 돌고 있으면 무한 루프로 확정할 수 있다.

구분대기 행폭주 행
CPU 사용률0%에 가까움한 코어 100%
콜스택NtWaitFor*에 잠듦같은 루프 구간 반복
핵심 명령!locks, ~*kb!runaway
대표 원인데드락, 영원한 블로킹무한 루프, busy-wait

머신비전 실전 시나리오

4편과 같은 grab↔process 파이프라인을 다시 가져온다. 이번엔 수명 문제가 아니라 락 순서 문제다.

시나리오 1 — 큐·풀 락 순서 역전

증상

장시간 검사 중 가끔 화면이 멈추고 검사가 중단된다. 프로세스는 살아 있지만 CPU는 거의 0%. 재시작 전까지 회복되지 않는다.

원인

grab 스레드는 풀 락 → 큐 락 순서로 잡고, process 스레드는 큐 락 → 풀 락 순서로 잡는다. 평소엔 우연히 어긋나지 않다가, 특정 타이밍에 grab이 풀 락을, process가 큐 락을 동시에 쥐면 서로 상대의 락을 기다리며 사이클이 닫힌다.

추적

procdump -ma -n 2 -s 15로 두 장을 떴다. 두 덤프 모두 grab·process 스레드가 RtlEnterCriticalSection에서 동일하게 멈춰 있었다(진짜 데드락 확정). !locks로 보니 큐 락은 process가, 풀 락은 grab이 보유 중이었고, ~*kb에서 grab은 큐 락을, process는 풀 락을 기다리고 있었다. 사이클이 닫힌다. 근본 해결은 두 스레드의 락 획득 순서를 통일(lock ordering)하는 것이다.

grab : 풀 락 보유 → 큐 락 대기 (RtlEnterCriticalSection)
process: 큐 락 보유 → 풀 락 대기 (RtlEnterCriticalSection)
↳ !locks 소유자 + ~*kb 대기 대상이 교차 → 데드락

시나리오 2 — busy-wait 폭주

증상

검사가 멈춘 것처럼 보이는데, 작업 관리자에서 한 코어가 100%로 고정. 팬 소음이 커진다.

원인

process 스레드가 condition variable 대기 없이 while (queue.empty()) { }로 빈 큐를 계속 폴링한다. 큐가 한동안 비면 그 스레드가 CPU를 통째로 태운다.

추적

!runaway로 process 스레드의 사용자 시간이 압도적으로 큼을 확인했다. ~<n>s; k로 전환하니 빈 큐 폴링 루프에서 돌고 있었다. 대기 행이 아니라 폭주 행이므로 락 추적은 불필요했다. 해결은 busy-wait를 condition variable 기반 대기로 바꾸는 것이다.

예방은 락 순서와 RAII 락에서 시작한다 데드락의 큰 줄기는 "여러 락을 항상 같은 순서로 잡기"와 "락 범위를 최소화하기"로 막힌다. std::scoped_lock으로 여러 뮤텍스를 한 번에 잡으면 순서 역전 자체를 없앨 수 있다. 4편의 use-after-free와 마찬가지로, 멀티스레드 버그는 분석보다 설계에서 막는 비용이 훨씬 싸다.

이번 편 요약

행은 멈춘 순간 직접 덤프를 뜬다. ~*kb로 전체 스레드를 펼치고, !locks로 락 소유 사이클을 찾으면 데드락이, !runaway로 CPU 독식 스레드를 찾으면 폭주가 드러난다.

마지막 6편에서는 지금까지의 기법을 실제 기술지원 업무로 묶는다. 고객사 덤프를 무엇과 함께 받을지, 어떤 빌드의 심볼을 어떻게 보관할지, 재현되지 않는 버그에 어떻게 그물을 칠지 — 장애 접수부터 회신까지의 워크플로를 체크리스트로 정리한다.
