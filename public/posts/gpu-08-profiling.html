추측 대신 측정

최적화의 출발점은 항상 측정이다. 어디가 병목인지 모르면 최적화할 수도 없다. "이 커널이 느릴 것 같다"는 직관은 자주 틀린다. 실제로 측정해 보면 의외로 메모리 전송이 80% 차지하거나, 커널 시작 오버헤드가 본체보다 크거나, 동기화 지점에서 모든 스트림이 멈춰 있는 경우가 흔하다.

GPU 코드의 성능은 단순히 "빠르다/느리다"로 평가할 수 없다. 다음 질문에 답할 수 있어야 한다.

  • 커널이 실제로 GPU에서 몇 ms 동안 실행됐는가?
  • SM(Streaming Multiprocessor)이 얼마나 활용됐는가? (Occupancy)
  • 메모리 대역폭의 몇 %를 사용했는가?
  • warp 분기(divergence)가 얼마나 심한가?
  • 호스트-디바이스 전송이 커널 실행을 가리고 있는가?

이 모든 질문에 답하기 위한 도구가 프로파일러다. NVIDIA는 세대별로 도구를 갈아 끼워 왔으며, 현재(CUDA 12+)는 nvprof를 deprecated 처리하고 Nsight Systems(전체 흐름)와 Nsight Compute(커널 분석)로 일원화했다.

Donald Knuth의 격언 "Premature optimization is the root of all evil." — 그러나 후반부에는 "Yet we should not pass up our opportunities in that critical 3%"라는 단서가 붙는다. 그 3%를 찾는 도구가 프로파일러다.

CPU 측정의 한계와 비동기 실행

가장 흔한 실수는 std::chrono로 GPU 커널 시간을 재는 것이다. CUDA 커널 호출은 비동기(asynchronous)다. 호스트는 커널을 큐에 넣자마자 곧바로 다음 줄로 진행한다. 따라서 다음과 같이 측정하면 커널 실행 시간이 아니라 호출 오버헤드만 잡힌다.

#include <chrono>

// 잘못된 측정 — 커널이 끝나기 전에 시간이 찍힘
auto start = std::chrono::high_resolution_clock::now();
myKernel<<<grid, block>>>(d_data, n);
auto end = std::chrono::high_resolution_clock::now();

auto ms = std::chrono::duration<double, std::milli>(end - start).count();
std::cout << "Kernel time: " << ms << " ms\n";  // 거의 0에 가까운 값

해결책은 측정 전에 cudaDeviceSynchronize()로 GPU 작업이 모두 끝날 때까지 호스트를 블로킹하는 것이다.

// CPU 타이머로 측정하려면 동기화 필수
cudaDeviceSynchronize();  // 이전 작업 모두 끝낸 후 시작
auto start = std::chrono::high_resolution_clock::now();

myKernel<<<grid, block>>>(d_data, n);

cudaDeviceSynchronize();  // 커널 완료 대기
auto end = std::chrono::high_resolution_clock::now();

auto ms = std::chrono::duration<double, std::milli>(end - start).count();
cudaDeviceSynchronize는 측정 외 코드에서 남발하면 안 된다 동기화는 호스트-디바이스 병렬성을 깨뜨려 전체 성능을 떨어뜨린다. 프로파일링이 끝나면 반드시 제거하거나, #ifdef PROFILE로 가두자.

그러나 CPU 타이머는 호스트 클럭에 의존하고, 큐 잠재 시간·커널 실행·완료 신호까지 모두 묶여 잡힌다. 더 정확한 측정은 GPU 자체의 타임스탬프를 쓰는 CUDA Events다.

CUDA Events로 정밀 측정

cudaEvent_t는 스트림 큐에 끼워 넣는 타임스탬프 마커다. GPU가 마커를 처리하는 순간 기록되므로 호스트 오버헤드를 우회한다. 해상도는 약 0.5 마이크로초.

#include <cuda_runtime.h>
#include <iostream>

// CUDA Event 기반 커널 시간 측정.
float MeasureKernelMs(int n, float* d_data)
{
    cudaEvent_t startEvent;
    cudaEvent_t stopEvent;
    cudaEventCreate(&startEvent);
    cudaEventCreate(&stopEvent);

    // 워밍업 — 첫 실행은 컴파일·캐시 적재로 느리다.
    myKernel<<<(n + 255) / 256, 256>>>(d_data, n);
    cudaDeviceSynchronize();

    // 측정 시작 마커.
    cudaEventRecord(startEvent, 0);

    myKernel<<<(n + 255) / 256, 256>>>(d_data, n);

    // 측정 종료 마커.
    cudaEventRecord(stopEvent, 0);
    cudaEventSynchronize(stopEvent);  // stopEvent까지 완료 대기.

    float elapsedMs = 0.0f;
    cudaEventElapsedTime(&elapsedMs, startEvent, stopEvent);

    cudaEventDestroy(startEvent);
    cudaEventDestroy(stopEvent);
    return elapsedMs;
}

여러 번 평균 내기

일회성 측정은 신뢰할 수 없다. GPU 클럭 부스트, 캐시 상태, 다른 프로세스 간섭 때문에 편차가 크다. 최소 10~100회 반복하고 평균(또는 중앙값)을 쓴다.

constexpr int kWarmupRuns = 3;
constexpr int kMeasureRuns = 50;

// 워밍업.
for (int i = 0; i < kWarmupRuns; ++i)
{
    myKernel<<<grid, block>>>(d_data, n);
}
cudaDeviceSynchronize();

// 본 측정.
cudaEvent_t startEvent;
cudaEvent_t stopEvent;
cudaEventCreate(&startEvent);
cudaEventCreate(&stopEvent);

cudaEventRecord(startEvent, 0);
for (int i = 0; i < kMeasureRuns; ++i)
{
    myKernel<<<grid, block>>>(d_data, n);
}
cudaEventRecord(stopEvent, 0);
cudaEventSynchronize(stopEvent);

float totalMs = 0.0f;
cudaEventElapsedTime(&totalMs, startEvent, stopEvent);
float avgMs = totalMs / kMeasureRuns;

std::cout << "Average kernel time: " << avgMs << " ms\n";
RAII 래퍼로 감싸기 cudaEventCreate/cudaEventDestroy 쌍은 누락 위험이 있다. 작은 CudaTimer 클래스를 만들어 생성자에서 record, 소멸자에서 elapsed를 로깅하면 측정 코드가 깔끔해진다.

nvprof — legacy 커맨드라인 프로파일러

nvprof는 CUDA 5~10 시대의 표준 프로파일러였다. 별도 계측 코드 없이 실행 파일에 붙여 커널별 시간·메모리 처리량·SM 점유율을 출력했다. CUDA 11부터 deprecated이며 Volta 이후 일부 메트릭은 지원되지 않는다. 그러나 가볍고 빠른 1차 진단용으로 여전히 유용하다.

# 기본 커널 타이밍 요약.
nvprof ./my_cuda_app

# 메모리 전송 포함 자세히.
nvprof --print-gpu-trace ./my_cuda_app

# 특정 메트릭만.
nvprof --metrics achieved_occupancy,gld_efficiency,gst_efficiency ./my_cuda_app

# 결과를 파일로 (Visual Profiler에서 열기 가능).
nvprof -o profile.nvvp ./my_cuda_app
출력 예시 (요약)

Turing(SM 75) 이후는 Nsight 도구를 쓰자 nvprof는 Volta까지만 메트릭이 완전하며, Ampere(RTX 30 시리즈) 이후는 일부 기능이 동작하지 않는다. 새 프로젝트는 처음부터 Nsight Systems / Compute를 권장한다.

Nsight Systems — 시스템 타임라인

Nsight Systems(nsys)는 전체 시스템 레벨의 타임라인 프로파일러다. CPU 스레드, OS 호출, CUDA API 호출, 커널 실행, 메모리 전송, 스트림, NVTX 마커를 모두 같은 타임라인에 그린다. "어디서 시간이 새고 있는가?"를 한눈에 본다.

Nsight Systems 타임라인 예시 — CPU·메모리 전송·커널을 한 화면에서 본다
# 기본 프로파일링 (.nsys-rep 파일 생성).
nsys profile -o report ./my_cuda_app

# CUDA + NVTX + OS 런타임 API 추적.
nsys profile --trace=cuda,nvtx,osrt -o report ./my_cuda_app

# 특정 구간만 (NVTX 범위로).
nsys profile --capture-range=nvtx --nvtx-capture="MeasureRegion" \
             -o report ./my_cuda_app

# 콘솔에 요약 출력.
nsys stats report.nsys-rep

NVTX로 코드 구간 라벨링

NVTX(NVIDIA Tools Extension)로 코드에 색깔 있는 라벨을 박으면 타임라인에서 어떤 단계인지 한눈에 보인다.

#include <nvtx3/nvToolsExt.h>

void RunInspection(const Image& src)
{
    nvtxRangePush("Preprocess");
    Preprocess(src);
    nvtxRangePop();

    nvtxRangePush("Convolution");
    RunConvKernel(src);
    nvtxRangePop();

    nvtxRangePush("BlobAnalysis");
    RunBlobKernel(src);
    nvtxRangePop();
}

Nsight Compute — 커널 단위 깊이 분석

Nsight Compute(ncu)는 단일 커널을 현미경으로 들여다보는 도구다. SM 점유율, 메모리 처리량, warp 분기, 명령어 믹스, 캐시 히트율 등 수백 개의 메트릭을 수집한다. Nsight Systems가 "병목 커널을 찾는 도구"라면, Nsight Compute는 "찾은 커널을 왜 느린지 분석하는 도구"다.

# 전체 커널 기본 분석.
ncu -o profile ./my_cuda_app

# 특정 커널만 (이름·정규식).
ncu --kernel-name convKernel ./my_cuda_app
ncu --kernel-name regex:'conv.*' ./my_cuda_app

# 특정 메트릭만 (빠르고 가볍다).
ncu --metrics sm__warps_active.avg.pct_of_peak_sustained_active,\
              dram__throughput.avg.pct_of_peak_sustained_elapsed \
    ./my_cuda_app

# 커널의 N번째 호출만.
ncu --launch-skip 10 --launch-count 1 ./my_cuda_app

# 풀 메트릭 — 매우 느림(커널당 수십 번 재실행).
ncu --set full -o profile ./my_cuda_app
Nsight Compute는 커널을 여러 번 재실행한다 모든 메트릭을 한 번에 수집할 수 없어 커널을 메트릭 그룹별로 재실행한다. --set full은 같은 커널을 수십~수백 번 돌릴 수 있으므로, 큰 입력에서는 --launch-count 1로 1회만 수집하자.

주요 메트릭 읽기

수백 개 메트릭 중 실전에서 자주 보는 것은 6~7개다.

메트릭의미해석
Achieved OccupancySM 한 개당 활성 warp 비율낮으면(<30%) 블록 크기·레지스터·공유 메모리 조정
SM Active CyclesSM이 실제로 일한 사이클낮으면 GPU가 놀고 있음 — grid 부족 의심
Global Load Efficiency실제 / 요청 메모리 비율낮으면(<80%) 메모리 결합(coalescing) 깨짐
Global Store Efficiency쓰기 결합 비율스캐터 패턴 의심 — 인덱싱 점검
Branch Efficiency분기 후 같이 가는 warp 비율낮으면 warp divergence 심함
DRAM Throughput실제 / 이론 대역폭높으면(80%+) 메모리 바운드
Compute Throughput실제 / 이론 FLOPS높으면 연산 바운드

메모리 바운드 vs 연산 바운드 판별

Nsight Compute의 "Speed of Light" 섹션이 가장 먼저 봐야 할 곳이다. 두 막대(SM, Memory) 중 어느 쪽이 90%에 가까운지가 병목을 결정한다.

Speed-of-Light로 본 병목 분류 — 다음 최적화 방향이 결정된다

프로파일링 워크플로우

실무에서 권장하는 절차는 "넓게 보고 → 좁혀서 파고 → 다시 검증"이다.

표준 GPU 프로파일링 워크플로우 — 한 사이클 끝나면 새 병목이 위로 올라온다
  1. Nsight Systems로 전체 흐름 캡처 — 호스트 대기 시간, 전송 vs 커널 비율, 스트림 겹침 여부 확인
  2. 핫스팟 커널 선정 — 시간 점유율 상위 1~2개를 다음 분석 대상으로
  3. Nsight Compute로 해당 커널만 깊이 분석 — SoL → Occupancy → Memory Workload Analysis 순서
  4. 가설 → 수정 → 재측정 — 한 번에 한 가지만 바꾼다. 그래야 효과를 분리할 수 있다
  5. 다음 병목으로 이동 — 한 커널이 빨라지면 다른 곳이 새 병목이 된다

산업 비전 관점 — 사이클 타임 검증

산업 비전 시스템은 검사 사이클 타임이라는 절대 마감 시간이 있다. 컨베이어가 30 ms마다 한 장씩 보내면, 처리 파이프라인은 30 ms 안에 끝나야 한다. 평균 25 ms라도 99 percentile이 35 ms면 라인이 멈춘다.

따라서 GPU 프로파일링은 단순한 평균이 아니라 최악 케이스 분포까지 봐야 한다.

// 사이클 타임 분포 측정 — 평균뿐 아니라 max·p99까지.
#include <algorithm>
#include <vector>

constexpr int kRuns = 1000;
std::vector<float> samples;
samples.reserve(kRuns);

for (int i = 0; i < kRuns; ++i)
{
    cudaEvent_t s;
    cudaEvent_t e;
    cudaEventCreate(&s);
    cudaEventCreate(&e);
    cudaEventRecord(s, 0);

    RunInspectionPipeline(image);  // 검사 파이프라인 전체.

    cudaEventRecord(e, 0);
    cudaEventSynchronize(e);
    float ms = 0.0f;
    cudaEventElapsedTime(&ms, s, e);
    samples.push_back(ms);

    cudaEventDestroy(s);
    cudaEventDestroy(e);
}

std::sort(samples.begin(), samples.end());
float avg = std::accumulate(samples.begin(), samples.end(), 0.0f) / kRuns;
float p50 = samples[kRuns / 2];
float p99 = samples[kRuns * 99 / 100];
float max = samples.back();

std::cout << "avg=" << avg << " p50=" << p50
          << " p99=" << p99 << " max=" << max << " ms\n";
실제 카메라 트리거 환경에서 측정하자 벤치마크 환경(루프에서 같은 영상 반복)은 캐시가 너무 잘 듣는다. 실제 산업 현장의 트리거 간격·전송 부하·다른 프로세스 간섭까지 포함해야 의미 있는 사이클 타임이 나온다.

흔한 함정

함정 1 — 측정 없이 최적화

"여기가 느릴 것 같아"라는 직관으로 일주일 갈아엎고 보면 핵심 병목은 다른 곳이다. 단 10분의 프로파일링이 일주일을 절약한다.

함정 2 — 워밍업 누락

첫 커널 실행은 JIT 컴파일, 메모리 할당, 캐시 적재로 본 실행보다 10~100배 느리다. 첫 측정값은 버리거나 별도 표기한다.

워밍업은 최소 3회 커널 JIT, cuBLAS 핸들 생성, GPU 클럭 부스트 안정화에 시간이 걸린다. 3~5회 실행 후 측정 시작.

함정 3 — 동기화 누락

CPU 타이머로 잴 때 cudaDeviceSynchronize()를 잊으면 0에 가까운 시간이 나온다. 반대로 너무 자주 동기화하면 측정값이 진짜 성능보다 나빠진다.

함정 4 — 일회성 측정

같은 코드를 두 번 돌려도 5~10% 편차가 흔하다. 클럭 부스트, OS 스케줄링, 다른 GPU 작업이 영향을 준다. 최소 10회 반복하고 중앙값을 보자.

함정 5 — 디버그 빌드 프로파일링

-G(디바이스 디버그) 옵션은 모든 최적화를 끄고 레지스터 spill을 유발한다. 릴리스 빌드(-O3 -lineinfo)로 프로파일링하자. -lineinfo는 소스 매핑을 유지하면서 최적화는 살린다.

함정 6 — 입력 크기 한 가지만 보기

작은 입력에서는 커널 시작 오버헤드가 지배적이고, 큰 입력에서는 메모리 대역폭이 지배적이다. 최소 3가지 크기(작음·중간·실제)로 측정해야 스케일링을 본다.

함정 7 — 메모리 전송 무시

커널만 빠르게 만들었는데 전체는 그대로인 경우, HtoD/DtoH 전송이 진짜 병목인 경우가 많다. Nsight Systems 타임라인에서 빨간 막대(memcpy)가 얼마나 차지하는지 먼저 확인하자.

측정은 코드와 함께 살아 있어야 한다 한 번 측정하고 끝내지 말고, --metrics 옵션 몇 개를 CI에 넣어 회귀를 잡자. 어느 커밋부터 점유율이 떨어졌는지 추적하면 원인 파악이 훨씬 빠르다.
