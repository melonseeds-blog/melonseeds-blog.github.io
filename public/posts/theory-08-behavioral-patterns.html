행위 패턴이란?

행위 패턴(behavioral pattern)은 객체와 클래스 사이의 책임 분배와 상호작용·통신 방식을 다루는 디자인 패턴이다. 생성 패턴이 "객체를 어떻게 만드는가", 구조 패턴이 "객체를 어떻게 조립하는가"를 다룬다면, 행위 패턴은 "객체들이 어떻게 협력하며 일을 처리하는가"를 다룬다.

핵심 질문은 하나다 — 어떤 일을 누가 맡고, 객체들이 서로 어떻게 메시지를 주고받을 것인가. 행위 패턴은 이 협력 구조를 명시적으로 설계해, 한 객체의 변경이 다른 객체로 번지지 않도록 만든다.

이 글에서는 가장 자주 쓰이는 네 가지 — Strategy·Observer·Command·State — 를 중심으로 보고, 보조 패턴 세 가지를 간단히 짚는다.

Strategy — 알고리즘의 캡슐화

Strategy 패턴은 알고리즘을 각각 별도의 클래스로 캡슐화해, 런타임에 서로 교체할 수 있게 한다. 알고리즘을 사용하는 쪽(context)과 알고리즘 자체를 분리하는 것이 목적이다.

문제 — if-else 분기의 누적

이진화(thresholding) 방식이 여러 개라고 하자. 분기로 처리하면 방식이 늘 때마다 같은 함수를 계속 수정해야 한다.

// 안티 패턴 - 이진화 방식이 늘 때마다 이 함수를 고쳐야 한다
ErrorCode ApplyThreshold(Image& image, ThresholdType type)
{
    if (type == ThresholdType::Fixed)         { /* 고정 임계값 로직 */ }
    else if (type == ThresholdType::Otsu)     { /* Otsu 로직 */ }
    else if (type == ThresholdType::Adaptive) { /* 적응형 로직 */ }
    // 새 방식 추가 = 또 else if ...
    return ErrorCode::Ok;
}

해법 — 알고리즘을 인터페이스 뒤로

각 알고리즘을 IThresholdStrategy 인터페이스의 구현으로 만든다. context는 어떤 전략을 들고 있는지만 알면 되고, 분기는 사라진다.

// 전략 인터페이스 - 모든 이진화 알고리즘이 따르는 계약
class IThresholdStrategy
{
public:
    virtual ~IThresholdStrategy() = default;
    virtual ErrorCode Apply(Image& image) = 0;
};

// 구체 전략 1 - 고정 임계값
class FixedThreshold : public IThresholdStrategy
{
public:
    explicit FixedThreshold(int value) : m_value(value) {}

    ErrorCode Apply(Image& image) override
    {
        // 고정 임계값 이진화 수행
        return ErrorCode::Ok;
    }

private:
    int m_value;
};

// 구체 전략 2 - Otsu 자동 임계값
class OtsuThreshold : public IThresholdStrategy
{
public:
    ErrorCode Apply(Image& image) override
    {
        // Otsu 알고리즘으로 임계값을 계산해 이진화
        return ErrorCode::Ok;
    }
};

// Context - 전략을 들고 위임한다. 분기가 없다
class BinarizationBlock
{
public:
    void SetStrategy(std::unique_ptr<IThresholdStrategy> strategy)
    {
        m_strategy = std::move(strategy);
    }

    ErrorCode Process(Image& image)
    {
        if (m_strategy == nullptr)
        {
            return ErrorCode::InvalidState;
        }
        return m_strategy->Apply(image);   // 어떤 알고리즘인지 모른 채 위임
    }

private:
    std::unique_ptr<IThresholdStrategy> m_strategy;
};

새 이진화 방식이 필요하면 IThresholdStrategy를 구현하는 클래스를 하나 추가하면 끝이다. BinarizationBlock은 한 줄도 바뀌지 않는다 — 개방·폐쇄 원칙(OCP)이 그대로 적용된 형태다.

모던 C++ — std::function과 람다

전략이 상태 없이 동작 하나만 담는다면, 클래스 계층 대신 std::function으로 간소화할 수 있다. 호출 측에서 람다로 전략을 즉석에서 정의한다.

// 함수 객체 기반 전략 - 클래스 계층이 필요 없다
class BinarizationBlock
{
public:
    using ThresholdFn = std::function<ErrorCode(Image&)>;

    void SetStrategy(ThresholdFn strategy)
    {
        m_strategy = std::move(strategy);
    }

    ErrorCode Process(Image& image)
    {
        if (!m_strategy)
        {
            return ErrorCode::InvalidState;
        }
        return m_strategy(image);
    }

private:
    ThresholdFn m_strategy;
};

// 사용 - 람다로 전략을 즉석에서 주입
BinarizationBlock block;
block.SetStrategy([](Image& img) -> ErrorCode
{
    // 고정 임계값 이진화
    return ErrorCode::Ok;
});
클래스 전략 vs 함수 전략 전략이 자체 상태(파라미터)나 수명 관리가 필요하면 클래스가 낫다. 동작 하나만 갈아끼우는 단순한 경우라면 std::function + 람다가 보일러플레이트를 크게 줄인다. 둘 다 Strategy 패턴의 정신은 동일하다.

Observer — 발행·구독

Observer 패턴은 한 객체(subject)의 상태가 변할 때, 그 변화를 구독하는 여러 객체(observer)에게 자동으로 통보한다. 발행·구독(publish-subscribe) 구조의 기본형이며, 이벤트 시스템·GUI·데이터 플로우의 토대다.

Observer는 Subject를 구독하고(subscribe), Subject는 상태 변화 시 모든 Observer에게 통보한다(notify)

기본 구현

Subject는 observer 목록을 들고, 상태가 바뀌면 전부 순회하며 통보한다. Subject는 observer가 무엇을 하는지 전혀 모른다 — 그저 OnNotify를 호출할 뿐이다.

// Observer 인터페이스
class IInspectionObserver
{
public:
    virtual ~IInspectionObserver() = default;
    virtual void OnInspectionDone(const InspectionResult& result) = 0;
};

// Subject - observer를 관리하고 통보한다
class InspectionSubject
{
public:
    void Subscribe(IInspectionObserver* observer)
    {
        m_observers.push_back(observer);
    }

    void Unsubscribe(IInspectionObserver* observer)
    {
        m_observers.erase(
            std::remove(m_observers.begin(), m_observers.end(), observer),
            m_observers.end());
    }

protected:
    // 상태 변화가 일어나면 모든 observer에게 통보한다
    void notifyAll(const InspectionResult& result)
    {
        for (IInspectionObserver* observer : m_observers)
        {
            observer->OnInspectionDone(result);
        }
    }

private:
    std::vector<IInspectionObserver*> m_observers;
};

// 구체 observer - 각자 다른 반응을 한다
class ResultLogger : public IInspectionObserver
{
public:
    void OnInspectionDone(const InspectionResult& result) override
    {
        // 검사 결과를 로그에 기록
    }
};

새 반응을 추가하고 싶으면 IInspectionObserver 구현을 하나 더 만들어 Subscribe하면 된다. InspectionSubject는 수정할 필요가 없다. 발행자와 구독자가 서로의 구체 타입을 모르므로 결합도가 매우 낮다.

위험 — 메모리 누수와 댕글링 포인터

Observer 패턴의 가장 흔한 사고는 구독 해제 누락이다. observer가 파괴됐는데 Unsubscribe를 호출하지 않으면, Subject는 이미 죽은 객체의 포인터를 들고 있다가 통보 시점에 그것을 역참조한다 — 댕글링 포인터 접근이다.

구독 해제 누락 = 메모리 누수 또는 크래시 raw 포인터로 observer를 들고 있으면, observer 소멸 시 반드시 Unsubscribe를 호출해야 한다. 이를 놓치면 Subject가 죽은 객체를 통보하다 크래시한다. 반대로 Subject가 observer의 수명을 shared_ptr로 붙들고 있으면, observer가 영원히 해제되지 않는 누수가 생긴다. 안전한 해법은 std::weak_ptr로 observer를 들고, 통보 직전 lock()으로 살아있는지 확인하는 것이다. 
// 안전한 구현 - weak_ptr로 들고, 죽은 observer는 자동으로 건너뛴다
class InspectionSubject
{
public:
    void Subscribe(const std::shared_ptr<IInspectionObserver>& observer)
    {
        m_observers.push_back(observer);   // weak_ptr로 저장됨
    }

protected:
    void notifyAll(const InspectionResult& result)
    {
        // 죽은 observer를 정리하면서 통보한다
        for (auto it = m_observers.begin(); it != m_observers.end(); )
        {
            if (std::shared_ptr<IInspectionObserver> obs = it->lock())
            {
                obs->OnInspectionDone(result);
                ++it;
            }
            else
            {
                it = m_observers.erase(it);   // 이미 소멸된 observer 제거
            }
        }
    }

private:
    std::vector<std::weak_ptr<IInspectionObserver>> m_observers;
};

Command — 요청의 객체화

Command 패턴은 "어떤 동작을 수행하라"는 요청 자체를 객체로 캡슐화한다. 요청이 객체가 되면 그것을 변수에 담고, 큐에 쌓고, 로그로 남기고, 거꾸로 되돌릴 수 있다. 실행 취소(undo)·작업 큐잉·매크로의 기반이다.

기본 구현 — Execute와 Undo

모든 명령은 Execute와 Undo를 가진 인터페이스를 구현한다. 명령은 자신을 되돌리는 데 필요한 정보를 스스로 들고 있다.

// 명령 인터페이스 - 실행과 취소를 모두 정의
class ICommand
{
public:
    virtual ~ICommand() = default;
    virtual ErrorCode Execute() = 0;
    virtual ErrorCode Undo() = 0;
};

// 구체 명령 - 이미지에 회전을 적용
class RotateCommand : public ICommand
{
public:
    RotateCommand(Image& target, double degrees)
        : m_target(target), m_degrees(degrees) {}

    ErrorCode Execute() override
    {
        // m_target을 m_degrees 만큼 회전
        return ErrorCode::Ok;
    }

    ErrorCode Undo() override
    {
        // 반대 방향으로 회전해 원래대로 복구
        return ErrorCode::Ok;
    }

private:
    Image& m_target;
    double m_degrees;
};

Invoker — 실행 이력과 undo 스택

명령을 실행하는 쪽(invoker)은 실행한 명령을 스택에 쌓아 둔다. undo 요청이 오면 스택 맨 위 명령의 Undo를 호출한다. invoker는 명령이 구체적으로 무슨 일을 하는지 전혀 모른다.

// Invoker - 명령을 실행하고 이력을 관리한다
class CommandInvoker
{
public:
    ErrorCode Run(std::unique_ptr<ICommand> command)
    {
        ErrorCode ec = command->Execute();
        if (ec == ErrorCode::Ok)
        {
            m_history.push(std::move(command));   // 실행 이력에 보관
        }
        return ec;
    }

    ErrorCode UndoLast()
    {
        if (m_history.empty())
        {
            return ErrorCode::InvalidState;
        }
        ErrorCode ec = m_history.top()->Undo();
        m_history.pop();
        return ec;
    }

private:
    std::stack<std::unique_ptr<ICommand>> m_history;
};
CommandInvoker 동작 흐름
Run(RotateCommand 90) -> Execute / history: [Rotate90] Run(BlurCommand 5) -> Execute / history: [Rotate90, Blur5] UndoLast() -> Blur5.Undo / history: [Rotate90] UndoLast() -> Rotate90.Undo / history: []

요청을 객체로 만든 덕분에 얻는 것이 많다. 명령을 큐에 쌓으면 작업 큐가 되고, 실행 전후를 기록하면 감사 로그가 되며, 명령 리스트를 묶으면 매크로가 된다. 모두 "요청이 일급 객체"이기에 가능하다.

State — 상태에 따른 행동

State 패턴은 객체의 내부 상태에 따라 행동이 달라질 때, 각 상태를 별도의 클래스로 표현한다. 객체는 현재 상태 객체에 행동을 위임하고, 상태 객체가 다음 상태로의 전이를 결정한다. 거대한 switch문을 상태 클래스들로 분해하는 것이 핵심이다.

문제 — 상태 분기의 폭발

카메라가 Idle → Ready → Capturing 상태를 오간다고 하자. 상태 enum과 switch로 처리하면, 모든 동작 함수마다 같은 switch가 반복되고 상태가 늘 때마다 전부 수정해야 한다.

// 안티 패턴 - 모든 메서드에 같은 상태 분기가 반복된다
ErrorCode Camera::StartCapture()
{
    switch (m_state)
    {
        case CameraState::Idle:      return ErrorCode::InvalidState;  // 준비 안 됨
        case CameraState::Ready:     m_state = CameraState::Capturing; return ErrorCode::Ok;
        case CameraState::Capturing: return ErrorCode::InvalidState;  // 이미 캡처 중
    }
    return ErrorCode::Unknown;
}
// Connect(), Disconnect(), StopCapture() ... 전부 같은 switch 반복
카메라 상태 전이 — 각 상태는 자신이 받아들이는 동작과 다음 상태만 안다

해법 — 상태를 클래스로

각 상태를 ICameraState 구현 클래스로 만든다. 카메라(context)는 현재 상태 객체에 동작을 위임하고, 상태 객체가 다음 상태를 반환한다. switch는 완전히 사라진다.

class Camera;   // 전방 선언

// 상태 인터페이스 - 각 동작이 다음 상태를 반환한다
class ICameraState
{
public:
    virtual ~ICameraState() = default;
    virtual ErrorCode Connect(Camera& camera) = 0;
    virtual ErrorCode StartCapture(Camera& camera) = 0;
};

// Idle 상태 - Connect만 받아들인다
class IdleState : public ICameraState
{
public:
    ErrorCode Connect(Camera& camera) override;        // Ready로 전이
    ErrorCode StartCapture(Camera& camera) override
    {
        return ErrorCode::InvalidState;                // Idle에서는 불가
    }
};

// Ready 상태 - StartCapture만 받아들인다
class ReadyState : public ICameraState
{
public:
    ErrorCode Connect(Camera& camera) override
    {
        return ErrorCode::InvalidState;                // 이미 연결됨
    }
    ErrorCode StartCapture(Camera& camera) override;   // Capturing으로 전이
};

// Context - 현재 상태에 위임만 한다. 분기가 없다
class Camera
{
public:
    Camera() : m_state(std::make_unique<IdleState>()) {}

    ErrorCode Connect()      { return m_state->Connect(*this); }
    ErrorCode StartCapture() { return m_state->StartCapture(*this); }

    void ChangeState(std::unique_ptr<ICameraState> next)
    {
        m_state = std::move(next);
    }

private:
    std::unique_ptr<ICameraState> m_state;
};

// 상태 전이 - IdleState가 직접 다음 상태를 지정한다
ErrorCode IdleState::Connect(Camera& camera)
{
    camera.ChangeState(std::make_unique<ReadyState>());
    return ErrorCode::Ok;
}

각 상태 클래스는 자기가 받아들이는 동작과 전이할 다음 상태만 안다. 새 상태가 필요하면 ICameraState 구현을 추가하면 되고, 전이 규칙이 한곳에 흩어지지 않는다. 다만 상태가 지나치게 많으면 클래스 수가 폭발하므로, 상태 가짓수가 적고 안정적일 때 가장 잘 맞는다.

Template Method — 알고리즘 골격

Template Method 패턴은 알고리즘의 골격을 기반 클래스에 정의하고, 변하는 일부 단계만 파생 클래스가 채우게 한다. 전체 흐름은 고정하되 세부 구현만 위임하는 구조다.

// 검사 파이프라인의 골격을 정의한다
class InspectionPipeline
{
public:
    // Template Method - 전체 흐름은 고정. public, non-virtual
    ErrorCode Run(const Image& input, InspectionResult& result)
    {
        Image preprocessed;
        ErrorCode ec = preprocess(input, preprocessed);   // 단계 1 (가변)
        if (ec != ErrorCode::Ok)
        {
            return ec;
        }
        ec = analyze(preprocessed, result);               // 단계 2 (가변)
        if (ec != ErrorCode::Ok)
        {
            return ec;
        }
        return finalize(result);                          // 단계 3 (공통)
    }

    virtual ~InspectionPipeline() = default;

private:
    // 파생 클래스가 채우는 단계 - private virtual (NVI)
    virtual ErrorCode preprocess(const Image& in, Image& out) = 0;
    virtual ErrorCode analyze(const Image& in, InspectionResult& result) = 0;

    // 공통 단계 - 모든 파이프라인이 동일
    ErrorCode finalize(InspectionResult& result)
    {
        // 결과 후처리
        return ErrorCode::Ok;
    }
};
NVI 패턴과의 연결 위 예제처럼 public 인터페이스(Run)는 non-virtual로 두고, 커스터마이즈 지점만 private virtual로 빼는 것을 NVI(Non-Virtual Interface) 관용구라 한다. 골격(불변식·전후 처리)은 기반 클래스가 통제하고, 파생 클래스는 정해진 구멍만 메운다. Template Method의 안전한 C++ 구현 형태다.

Iterator — 컬렉션 순회

Iterator 패턴은 컬렉션의 내부 구조(배열인지 연결 리스트인지 트리인지)를 노출하지 않고 원소를 순차적으로 순회하는 방법을 제공한다. 순회 방식이 컬렉션 구현과 분리된다.

C++에서는 이 패턴이 STL 이터레이터로 언어 차원에 녹아 있다. begin() / end()가 이터레이터를 반환하고, 모든 표준 컨테이너가 동일한 인터페이스를 따르므로 알고리즘이 컨테이너 종류와 무관하게 동작한다.

// STL 이터레이터 - 컨테이너 내부 구조를 몰라도 순회한다
std::vector<InspectionResult> results = RunBatch();

// range-based for - 내부적으로 begin()/end() 이터레이터를 사용
for (const InspectionResult& r : results)
{
    // vector든 list든 set이든 같은 코드로 순회된다
}

// 알고리즘도 이터레이터만 받으므로 컨테이너에 독립적이다
auto failCount = std::count_if(results.begin(), results.end(),
    [](const InspectionResult& r) { return r.IsFail(); });

커스텀 컨테이너를 만들 때도 begin() / end()와 이터레이터 타입을 제공하면 range-based for와 STL 알고리즘을 그대로 쓸 수 있다 — Iterator 패턴을 직접 구현하는 셈이다.

Chain of Responsibility — 처리 체인

Chain of Responsibility 패턴은 요청을 처리할 수 있는 객체들을 체인으로 연결하고, 요청을 체인을 따라 흘려보낸다. 각 핸들러는 요청을 처리하거나, 처리할 수 없으면 다음 핸들러로 넘긴다. 요청을 보내는 쪽은 누가 처리할지 알 필요가 없다.

// 핸들러 - 처리하거나 다음으로 넘긴다
class ImageValidator
{
public:
    virtual ~ImageValidator() = default;

    void SetNext(std::shared_ptr<ImageValidator> next)
    {
        m_next = std::move(next);
    }

    // 자신이 처리하지 못하면 다음 핸들러로 위임한다
    ErrorCode Validate(const Image& image)
    {
        ErrorCode ec = checkSelf(image);
        if (ec != ErrorCode::Ok)
        {
            return ec;                       // 이 핸들러에서 거부
        }
        if (m_next != nullptr)
        {
            return m_next->Validate(image);   // 다음 핸들러로 전달
        }
        return ErrorCode::Ok;                // 체인 끝까지 통과
    }

private:
    virtual ErrorCode checkSelf(const Image& image) = 0;
    std::shared_ptr<ImageValidator> m_next;
};

// 구체 핸들러들 - 크기 검사, 포맷 검사, 빈 이미지 검사 등
class SizeValidator : public ImageValidator
{
private:
    ErrorCode checkSelf(const Image& image) override
    {
        // 이미지 크기가 허용 범위인지 검사
        return ErrorCode::Ok;
    }
};

검사 단계를 추가·제거·재배열하기가 쉽고, 호출하는 쪽은 체인의 시작점만 알면 된다. 다만 체인이 길어지면 요청이 어디서 처리됐는지 추적하기 어려워질 수 있다.

행위 패턴들의 공통점

지금까지 본 패턴들은 표면적으로 달라 보이지만, 한 가지 목표를 공유한다 — 결합도를 낮추고 책임을 분산한다.

모두 "변하는 부분"을 인터페이스 뒤로 빼낸다. Strategy는 알고리즘을, State는 상태별 행동을, Command는 요청을, Observer는 반응을 각각 별도 객체로 분리한다. 그 결과 변경이 한 클래스 안에 격리되고, 새 기능은 새 클래스 추가만으로 끝난다. 호출하는 쪽 코드는 닫혀 있다 — 개방·폐쇄 원칙이 관통하는 셈이다.

패턴무엇을 캡슐화하나주로 쓰는 상황
Strategy교체 가능한 알고리즘같은 작업의 방식이 여럿일 때, if-else 분기 제거
Observer상태 변화에 대한 반응한 변화에 여러 객체가 반응해야 할 때, 이벤트
Command요청 그 자체실행 취소, 작업 큐, 로깅, 매크로
State상태별 행동과 전이상태에 따라 동작이 갈리고 전이가 복잡할 때
Template Method알고리즘의 가변 단계전체 흐름은 같고 일부 단계만 다를 때
Iterator순회 방법컬렉션 내부 구조를 감추고 순회할 때
Chain of Responsibility요청 처리자의 선택처리 단계를 유연하게 조합할 때

산업 SW 관점

산업용 이미징 시스템에서는 행위 패턴이 곳곳에 자연스럽게 들어맞는다. 추상 이론이 아니라 실제 구조 결정으로 직결된다.

검사 알고리즘 — Strategy

같은 "결함 검출"이라도 블롭 기반·엣지 기반·템플릿 매칭 기반 등 방식이 여럿이다. 각 방식을 IDefectDetectionStrategy로 캡슐화하면, 검사 블록은 알고리즘을 런타임에 갈아끼울 수 있고 새 방식 추가가 기존 코드를 건드리지 않는다.

검사 완료 이벤트 — Observer

한 번의 검사가 끝나면 여러 주체가 반응해야 한다 — UI는 결과를 표시하고, 로거는 기록하고, 통계 모듈은 수율을 갱신하고, PLC 인터페이스는 양품·불량 신호를 내보낸다. 검사 엔진을 Subject로 두면 각 반응을 observer로 독립적으로 붙였다 뗄 수 있다.

작업 큐 — Command

플로우 에디터에서 사용자의 편집 동작(블록 추가·연결·파라미터 변경)을 Command로 만들면 실행 취소·재실행이 자연스럽게 따라온다. 배치 처리에서는 작업을 Command 큐에 쌓아 워커 스레드가 순서대로 처리하게 한다.

카메라·검사 상태 머신 — State

카메라(연결·준비·캡처·오류)나 검사 시퀀스(대기·트리거·획득·처리·완료)는 명확한 상태 머신이다. State 패턴으로 각 상태를 클래스화하면 잘못된 전이를 컴파일 구조 차원에서 막고, 거대한 switch가 흩어지는 것을 방지한다.

흔한 함정

함정 1 — Strategy 과용

분기 두세 개를 없애겠다고 인터페이스·구현 클래스 여러 개를 만드는 것은 과한 설계다. Strategy는 알고리즘이 실제로 여럿이고, 런타임 교체가 필요하며, 앞으로 늘어날 가능성이 있을 때 가치가 있다.

단순 분기에 Strategy를 끼우지 말 것 값에 따라 한두 줄이 갈리는 정도라면 if-else나 switch가 더 읽기 쉽다. "변형이 늘어날 것"이라는 막연한 추측만으로 클래스 계층을 미리 만들면, 정작 변형은 안 늘고 간접 호출과 파일 개수만 늘어난다. 패턴은 통증이 실제로 나타난 뒤에 도입해도 늦지 않다.

함정 2 — Observer의 메모리 누수와 순환 참조

앞서 본 대로 구독 해제를 빠뜨리면 댕글링 포인터나 누수가 생긴다. 더 까다로운 경우는 순환 참조다. A가 B를 구독하고 B도 A를 구독하면서 서로 shared_ptr로 붙들면, 둘 다 영원히 해제되지 않는다.

Observer는 수명 관리가 핵심이다 Subject가 observer를 shared_ptr로 소유하면 안 된다 — 소유는 다른 곳이 하고, Subject는 weak_ptr로 "참조만" 해야 한다. 통보 시점에 lock()으로 생존을 확인하고, 죽은 observer는 목록에서 정리한다. 양방향 구독이 불가피하면 한쪽은 반드시 weak_ptr로 끊어 순환을 방지한다.

함정 3 — Command 남용

모든 함수 호출을 Command 객체로 감싸면 코드가 간접 호출의 미로가 된다. Command는 실행 취소·큐잉·로깅·매크로 중 하나라도 실제로 필요할 때 쓴다. 그냥 함수를 한 번 부르면 되는 일을 명령 객체로 만드는 것은 보일러플레이트만 늘린다.

함정 4 — State 클래스 폭발

State 패턴은 상태마다 클래스를 만든다. 상태가 3~5개로 적고 안정적이면 깔끔하지만, 상태가 수십 개거나 상태 × 이벤트 조합이 많으면 클래스와 전이 코드가 폭발한다. 이런 경우엔 오히려 상태 전이 테이블(table-driven)이나 전용 상태 머신 라이브러리가 더 관리하기 쉽다. 패턴을 적용할지는 상태의 개수와 변동성을 보고 판단한다.

패턴은 목적이 아니라 도구다 행위 패턴의 가치는 "결합도를 낮추고 책임을 분산한다"는 효과에 있지, 패턴 이름을 코드에 박는 데 있지 않다. 먼저 해결하려는 통증(분기 누적, 변경 전파, undo 요구 등)을 분명히 하고, 그 통증에 맞는 패턴을 고른다. 통증이 없는데 패턴부터 꺼내면 복잡도만 늘어난다.
