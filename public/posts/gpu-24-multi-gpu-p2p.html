멀티 GPU가 필요한 경우

GPU 한 장으로 처리가 끝나지 않을 때 GPU를 더 꽂는다. 다만 GPU를 두 장 꽂는다고 프로그램이 저절로 두 배 빨라지지는 않는다. CUDA는 GPU를 하나씩 따로 다루므로, 일을 어떻게 나눌지는 프로그래머가 정해야 한다.

상황멀티 GPU 효과
카메라 여러 대, 각자 독립된 검사큼. 카메라마다 GPU를 나눠 주면 거의 대수만큼 빨라짐
영상 하나가 너무 커서 한 GPU 메모리에 안 들어감필요. 영상을 나눠 처리 (경계 처리 필요)
단계가 긴 파이프라인 (전처리, 추론, 후처리)단계별로 GPU를 나누면 처리량 증가 (지연 시간은 그대로)
작은 영상 하나를 빨리 처리해야 함작음. 나누고 합치는 비용이 이득보다 큼

장치 선택의 기본 규칙

CUDA에는 "현재 장치"라는 개념이 있다. cudaSetDevice로 고른 장치에 이후의 메모리 할당, 스트림 생성, 커널 실행이 모두 걸린다.

int count = 0;
cudaGetDeviceCount(&count);
for (int d = 0; d < count; ++d)
{
    cudaDeviceProp p;
    cudaGetDeviceProperties(&p, d);
    printf("GPU %d: %s, %d SMs, %.1f GB, PCI bus %d\n",
           d, p.name, p.multiProcessorCount, p.totalGlobalMem / 1e9, p.pciBusID);
}

cudaSetDevice(1);                    // everything below goes to GPU 1
float* d_buf;
cudaMalloc(&d_buf, bytes);           // allocated on GPU 1
cudaStream_t s;
cudaStreamCreate(&s);                // stream belongs to GPU 1
MyKernel<<<grid, block, 0, s>>>(d_buf);   // runs on GPU 1
규칙설명
현재 장치는 CPU 스레드마다 따로임스레드 A에서 cudaSetDevice(1)을 해도 스레드 B의 현재 장치는 바뀌지 않음. 새 스레드는 0번에서 시작
메모리, 스트림, 이벤트는 만들 때의 장치에 속함GPU 1의 스트림에 GPU 0 커널을 넣을 수 없음 (오류)
장치 번호 순서는 바뀔 수 있음기본은 성능 순. PCI 순서로 고정하려면 환경 변수 CUDA_DEVICE_ORDER=PCI_BUS_ID
보일 장치 제한CUDA_VISIBLE_DEVICES=1이면 프로그램에는 GPU 1만 0번으로 보임
스레드 풀에서 현재 장치를 잊음 작업 스레드 풀에서 GPU 작업을 실행할 때, 작업마다 어느 스레드에서 실행될지 모른다. 작업 시작마다 cudaSetDevice를 다시 부르지 않으면 엉뚱한 GPU에 할당하거나 "invalid resource handle" 오류가 난다. 가장 단순한 설계는 GPU마다 전용 스레드를 하나씩 두는 것이다.

일을 나누는 세 가지 방식

멀티 GPU 작업 분할. 가능하면 ①처럼 GPU 사이 데이터 이동이 없는 방식부터 검토한다

GPU마다 전용 스레드 두기

카메라별 나누기를 구현하는 가장 깔끔한 방법은 GPU 하나에 CPU 스레드 하나를 붙이는 것이다. 각 스레드는 시작할 때 한 번 cudaSetDevice를 하고, 자기 GPU의 메모리, 스트림, 그래프(17편)를 소유한다.

struct GpuWorker
{
    int device;
    CameraQueue* input;          // frames from one camera
    ResultQueue* output;

    void Run()
    {
        cudaSetDevice(device);                    // once per thread
        Pipeline pipe;                            // allocates buffers, streams, graphs on THIS device
        pipe.Init(1920, 1200);

        Frame f;
        while (input->Pop(f))
        {
            pipe.Process(f);                      // H2D, kernels, D2H on this GPU only
            output->Push(pipe.Result());
        }
        pipe.Release();                           // free on the same device that allocated
    }
};

std::vector<std::thread> threads;
for (int d = 0; d < numGpus; ++d)
    threads.emplace_back(&GpuWorker::Run, &workers[d]);
for (auto& t : threads) t.join();
설계 원칙이유
자원은 한 GPU 안에서 만들고 그 GPU에서 해제다른 장치의 포인터를 해제하거나 다른 장치 스트림을 쓰는 실수를 원천 차단
핀드 메모리는 공유 가능cudaHostAlloc(..., cudaHostAllocPortable)로 잡으면 모든 GPU가 핀드 메모리로 인식
오류 복구도 GPU별로한 GPU에서 sticky 오류(19편)가 나도 다른 GPU 스레드는 계속 동작하게 분리

GPU 사이 데이터 이동 - P2P

단계별 나누기나 영상 나누기에서는 GPU끼리 데이터를 주고받아야 한다. 방법은 두 가지다.

방식경로속도
CPU 메모리를 거쳐 복사GPU 0 → CPU 메모리 → GPU 1 (PCIe를 두 번 지남)느림
P2P (peer-to-peer)GPU 0 → GPU 1 직접 (PCIe 스위치 또는 NVLink)빠름. NVLink면 PCIe보다 훨씬 빠름
// 1) can GPU 0 access GPU 1 directly?
int can01 = 0, can10 = 0;
cudaDeviceCanAccessPeer(&can01, 0, 1);
cudaDeviceCanAccessPeer(&can10, 1, 0);

if (can01 && can10)
{
    // 2) enable once per direction (called with the ACCESSING device current)
    cudaSetDevice(0); cudaDeviceEnablePeerAccess(1, 0);
    cudaSetDevice(1); cudaDeviceEnablePeerAccess(0, 0);
}

// 3) copy GPU0 -> GPU1 on a stream (falls back to staging through the host if P2P is off)
cudaMemcpyPeerAsync(d_dst_on1, 1, d_src_on0, 0, bytes, streamOnGpu1);

// 4) with P2P enabled, a kernel on GPU 1 may even read GPU 0 memory directly
cudaSetDevice(1);
ReadRemote<<<grid, block, 0, streamOnGpu1>>>(d_src_on0 /* lives on GPU 0 */, d_out_on1, n);
P2P는 항상 되는 것이 아님 P2P 지원 여부는 GPU 종류, 메인보드의 PCIe 구성, 운영체제, 드라이버 모드에 따라 다르다. 게이밍용 GPU는 P2P를 지원하지 않는 경우가 많고, Windows의 화면 출력용 드라이버 모드(WDDM)에서도 제한이 있다. 설계 전에 반드시 cudaDeviceCanAccessPeer로 확인하고, 안 되는 환경에서도 동작하도록(CPU 메모리 경유) 코드를 둔다. cudaMemcpyPeerAsync는 P2P가 꺼져 있어도 내부적으로 CPU 메모리를 거쳐 동작한다.

장치 사이 순서 맞추기

단계별 나누기에서 GPU 1의 추론은 GPU 0의 전처리가 끝난 뒤에 시작해야 한다. CPU에서 cudaStreamSynchronize로 기다리면 CPU가 멈춘다. 이벤트는 장치를 넘어서도 쓸 수 있으므로, GPU 1 스트림이 GPU 0의 이벤트를 기다리게 하면 CPU는 멈추지 않는다.

// GPU 0: preprocess, then record an event
cudaSetDevice(0);
Preprocess<<<g, b, 0, s0>>>(d_raw0, d_pre0, w, h);
cudaEventRecord(preDone, s0);                      // preDone was created on GPU 0

// GPU 1: wait for GPU 0's event, copy, infer - the CPU does not block
cudaSetDevice(1);
cudaStreamWaitEvent(s1, preDone, 0);               // cross-device wait is allowed
cudaMemcpyPeerAsync(d_pre1, 1, d_pre0, 0, bytes, s1);
Infer<<<g, b, 0, s1>>>(d_pre1, d_out1);

두 GPU가 각자 다른 프레임을 처리하도록 버퍼를 2~3개 두고 돌려 쓰면(12편의 링 버퍼), GPU 0이 프레임 N+1을 전처리하는 동안 GPU 1이 프레임 N을 추론해 두 GPU가 동시에 바쁘게 일한다.

영상 하나를 나눠 처리할 때

영상을 위아래로 나눠 GPU 두 장에 맡기면, 필터처럼 이웃 픽셀을 쓰는 처리는 경계 근처에서 상대 GPU 쪽 픽셀이 필요하다. 22편의 타일 halo와 같은 문제다.

단계할 일
1. 나누기각 GPU에 자기 영역 + 필터 반경만큼의 경계 줄(halo)을 같이 복사
2. 처리각 GPU가 자기 영역만 계산 (halo는 읽기만)
3. 여러 단계 필터단계마다 halo를 상대 GPU와 다시 교환(P2P) 하거나, 처음부터 halo를 단계 수만큼 넓게 잡음
4. 합치기결과를 한 GPU나 CPU 메모리로 모음. 영상 전체 통계가 필요하면 부분 결과를 합침(13편)

나누고 합치는 비용이 있으므로, 영상이 GPU 메모리에 들어가는 크기라면 영상 나누기보다 프레임을 GPU별로 번갈아 맡기는 편(짝수 프레임은 GPU 0, 홀수 프레임은 GPU 1)이 대부분 단순하고 빠르다. 다만 이 방식은 처리 순서가 섞이므로 결과를 프레임 번호로 다시 정렬해야 한다.

흔한 함정

다른 장치의 포인터를 그냥 넘김 P2P를 켜지 않은 상태에서 GPU 1 커널에 GPU 0 포인터를 넘기면 illegal address 오류가 난다. 장치 포인터를 담는 구조체에 장치 번호를 같이 들고 다니면 이런 실수를 찾기 쉽다. cudaPointerGetAttributes로 포인터가 어느 장치 것인지 확인할 수 있다.
GPU 성능이 서로 다름 종류가 다른 GPU를 섞으면, 일을 반씩 나눴을 때 느린 GPU가 전체 속도를 정한다. 카메라별 나누기라면 무거운 검사를 빠른 GPU에 배정하고, 프레임 나누기라면 고정 배분 대신 먼저 끝난 GPU가 다음 프레임을 가져가는 작업 큐를 쓴다.
PCIe 대역폭 공유 GPU를 여러 장 꽂으면 메인보드에 따라 슬롯당 PCIe 레인 수가 줄어든다(x16 → x8). 카메라 영상을 GPU로 올리는 속도가 GPU 한 장일 때보다 느려질 수 있으므로, 실제 장비에서 복사 시간을 측정한다(4편).
