2026-06-25 약 8분 분량 Rust 시리즈

클로저 기초 — 문법과 추론

클로저는 주변 환경을 캡처할 수 있는 익명 함수다. 파라미터를 세로 막대 | |로 감싸고 그 뒤에 본문을 둔다. 한 줄이면 중괄호를 생략하고, 여러 줄이면 블록으로 감싼다.

// 한 줄 클로저 — 파라미터와 반환 타입을 컴파일러가 추론한다
let add_one = |x| x + 1;
let result = add_one(5); // 6

// 타입을 명시할 수도 있다
let multiply = |a: i32, b: i32| -> i32 { a * b };
let product = multiply(3, 4); // 12

// 여러 줄 본문은 블록으로
let describe = |n: i32| {
    let parity = if n % 2 == 0 { "even" } else { "odd" };
    format!("{n} is {parity}")
};
println!("{}", describe(7)); // "7 is odd"

함수와 달리 클로저의 파라미터·반환 타입은 보통 추론에 맡긴다. 단, 추론은 첫 호출에서 한 번 고정된다. 같은 클로저를 서로 다른 타입으로 두 번 호출하면 컴파일 오류가 난다 — 처음 쓰인 타입으로 시그니처가 못 박히기 때문이다.

C++과 이렇게 다르다 — 캡처 목록 C++ 람다는 [&]·[=]·[x]처럼 캡처 목록을 직접 적어 무엇을 어떻게 가져올지 지정한다. Rust 클로저에는 캡처 목록이 없다. 본문에서 변수를 어떻게 쓰는지(읽기만 / 변경 / 소비)를 보고 컴파일러가 캡처 방식을 자동으로 고른다. 소유권을 강제로 넘기고 싶을 때만 move 키워드를 앞에 붙인다.

캡처와 Fn 트레이트 삼형제

클로저가 주변 변수를 어떻게 사용하느냐에 따라 캡처 방식이 셋으로 갈린다. 그리고 그 방식에 따라 클로저가 자동으로 구현하는 트레이트가 정해진다.

불변 빌림 → Fn

변수를 읽기만 하면 불변 참조로 캡처하고, 클로저는 Fn을 구현한다. 여러 번 호출해도 안전하다.

let greeting = String::from("Hello");

// greeting을 읽기만 하므로 불변 빌림으로 캡처된다 (Fn)
let say_hello = || println!("{greeting}, world!");
say_hello();
say_hello(); // 여러 번 호출 가능

// 클로저가 빌리기만 했으므로 원본도 그대로 쓸 수 있다
println!("original still usable: {greeting}");

가변 빌림 → FnMut

변수를 변경하면 가변 참조로 캡처하고, 클로저는 FnMut을 구현한다. 호출이 상태를 바꾸므로 클로저 변수 자체를 mut으로 선언해야 한다.

let mut count = 0;

// count를 변경하므로 가변 빌림으로 캡처된다 (FnMut)
let mut increment = || {
    count += 1;
    println!("count = {count}");
};
increment(); // count = 1
increment(); // count = 2

// 클로저 사용이 끝난 뒤에는 원본을 다시 쓸 수 있다
println!("final: {count}"); // final: 2

소유권 이동 → FnOnce

캡처한 값을 본문에서 소비(이동)하면 그 클로저는 한 번만 호출할 수 있고 FnOnce만 구현한다. 스레드로 값을 넘길 때처럼 소유권 이동이 필요하면 move를 붙인다.

let data = vec![1, 2, 3];

// move로 data의 소유권을 클로저로 옮긴다
let consume = move || {
    let total: i32 = data.iter().sum();
    println!("sum = {total}");
    data // 캡처한 값을 반환하며 소비 → FnOnce
};
let returned = consume(); // 단 한 번만 호출 가능
println!("got back {} items", returned.len());
세 트레이트는 포함 관계다 모든 Fn은 FnMut이고, 모든 FnMut은 FnOnce다. 그래서 함수 파라미터를 받을 때는 필요한 가장 약한 제약을 고른다. 클로저를 한 번만 호출한다면 FnOnce로 받는 게 가장 많은 클로저를 허용한다. 반복 호출이 필요하면 Fn이나 FnMut으로 받는다. 
// 클로저를 인자로 받는 함수 — Fn 바운드
fn apply_twice<F: Fn(i32) -> i32>(f: F, x: i32) -> i32 {
    f(f(x)) // 두 번 호출하므로 Fn이 필요하다
}

let squared = apply_twice(|n| n * n, 2); // (2^2)^2 = 16
println!("{squared}");

Iterator 트레이트의 정체

Iterator는 "다음 값을 하나 달라"는 한 가지 동작으로 정의된다. 핵심은 연관 타입 Item과 메서드 next다. next는 값이 있으면 Some(item), 끝났으면 None을 돌려준다.

// 직접 만든 카운터 이터레이터
struct Counter {
    current: u32,
    max: u32,
}

impl Iterator for Counter {
    type Item = u32; // 내보낼 값의 타입

    fn next(&mut self) -> Option<Self::Item> {
        if self.current < self.max {
            self.current += 1;
            Some(self.current)
        } else {
            None // 끝에 도달하면 None
        }
    }
}

let counter = Counter { current: 0, max: 3 };
for n in counter {
    println!("{n}"); // 1, 2, 3
}

next 하나만 구현하면 map·filter·sum·collect 등 수십 개의 메서드를 공짜로 얻는다. 이들은 모두 next 위에 기본 구현으로 얹혀 있기 때문이다. for 루프 역시 내부적으로 next를 반복 호출하는 문법 설탕이다.

iter · iter_mut · into_iter

컬렉션에서 이터레이터를 얻는 방법은 셋이며, 각각 빌림 방식이 다르다. 소유권 규칙이 여기서도 그대로 적용된다.

메서드Item 타입원본
iter()&T불변 빌림, 이후에도 사용 가능
iter_mut()&mut T가변 빌림, 원소 수정 가능
into_iter()T소유권 이동, 이후 사용 불가

어댑터 체인과 지연 평가

map·filter처럼 이터레이터를 받아 새 이터레이터를 돌려주는 메서드를 어댑터라 한다. 어댑터는 지연(lazy)이다 — 호출만으로는 아무 일도 일어나지 않고, 새 이터레이터 구조를 만들어 둘 뿐이다. collect·sum·for 같은 소비자(consumer)가 next를 당겨야 비로소 계산이 흐른다.

let numbers = vec![1, 2, 3, 4, 5, 6];

// 짝수만 골라 제곱한 뒤 Vec으로 모은다
let result: Vec<i32> = numbers
    .iter()                  // &i32를 내보내는 이터레이터
    .filter(|&&n| n % 2 == 0) // 짝수만 통과 (아직 실행 안 됨)
    .map(|&n| n * n)         // 제곱 (아직 실행 안 됨)
    .collect();              // 여기서 비로소 전체가 흐른다

println!("{:?}", result); // [4, 16, 36]

지연 평가의 실질적 이점은 중간 컬렉션이 생기지 않는다는 점이다. 위 코드는 짝수만 담은 임시 Vec을 만들고 다시 제곱한 Vec을 만드는 식이 아니다. 원소 하나가 filter를 통과하면 곧바로 map으로 흘러가고, 한 번의 패스로 끝난다.

// 무한 이터레이터도 지연 평가 덕분에 안전하다
let first_five_squares: Vec<u64> = (1u64..)   // 1, 2, 3, ... 무한 범위
    .map(|n| n * n)
    .take(5)        // 앞에서 5개만 당긴다
    .collect();

println!("{:?}", first_five_squares); // [1, 4, 9, 16, 25]

(1u64..)는 끝이 없는 범위지만, take(5)가 다섯 번만 next를 당기므로 무한 루프에 빠지지 않는다. 소비자가 요구하는 만큼만 생산되는 pull 모델이기 때문이다.

C++과 이렇게 다르다 — std::ranges와의 대응 C++20의 std::ranges 뷰는 Rust 이터레이터 어댑터와 발상이 거의 같다. 둘 다 지연 평가되고 체이닝된다. 대응을 보면 한눈에 익힌다 — Rust의 .filter(...)는 C++ std::views::filter(...), .map(...)은 std::views::transform(...), .take(n)은 std::views::take(n)에 대응한다. 다만 C++은 파이프 연산자 |로 뷰를 잇고(rng | views::filter(f) | views::transform(g)), Rust는 메서드 체인 .으로 잇는다. 또 Rust 이터레이터는 빌림 검사기가 캡처와 수명을 강제하므로, 댕글링 뷰 같은 함정을 컴파일 단계에서 막는다.

zero-cost 추상화

위 어댑터 체인은 읽기 좋지만, 성능을 손해 보지는 않을까? Rust의 답은 "그렇지 않다"이다. 이터레이터 어댑터는 zero-cost 추상화를 지향한다 — 고수준으로 쓴 코드가 손으로 쓴 루프와 거의 같은 기계어로 컴파일된다는 뜻이다.

비결은 두 가지다. 첫째, 어댑터는 제네릭이라 호출 지점마다 구체 타입으로 단형화(monomorphization)된다. 둘째, 클로저 호출과 어댑터의 얇은 래퍼는 인라이닝으로 사라진다. 그 결과 아래 두 코드는 사실상 같은 수준으로 최적화된다.

let values = vec![1, 3, 5, 7, 9];

// 1) 고수준 이터레이터 체인
let sum_a: i32 = values.iter().map(|&x| x * 2).sum();

// 2) 손으로 쓴 루프
let mut sum_b = 0;
for &x in &values {
    sum_b += x * 2;
}

assert_eq!(sum_a, sum_b); // 결과 동일, 최적화 후 코드도 사실상 동일

즉 "추상화를 쓰면 느려진다"는 통념이 여기서는 깨진다. 가독성을 위해 map·filter를 마음껏 체이닝해도, 컴파일러가 그 층을 걷어 내고 단단한 루프로 바꿔 준다. 가독성과 성능 사이에서 타협할 필요가 줄어드는 것이다.

"항상 공짜"는 아니다 zero-cost는 목표이자 일반적 경향이지, 모든 경우의 절대 보장은 아니다. 트레이트 객체(dyn Fn)로 동적 디스패치를 쓰거나 인라이닝이 막히면 호출 오버헤드가 남을 수 있다. 의심스러우면 추측하지 말고 --release 빌드로 벤치마크하고 생성된 어셈블리를 확인하는 게 맞다.
