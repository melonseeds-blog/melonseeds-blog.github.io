1편에서 고객사로부터 덤프를 받아오는 방법까지 정리했다. 이제 그 .dmp 파일을 열어 볼 차례다. 도구는 WinDbg다. 그런데 막상 설치하려고 하면 "WinDbg"와 "WinDbg Preview" 두 이름이 나와 헷갈리고, 정작 덤프를 열면 콜스택이 의미 없는 주소 나열로만 보인다. 그 두 함정을 먼저 정리하고 넘어간다.

이 글의 절반은 도구 설치이고, 나머지 절반은 심볼(symbol)이다. 심볼 설정을 제대로 하지 않으면 WinDbg는 켜져도 아무것도 알려주지 않는다. 분석의 성패가 여기서 갈린다.

WinDbg vs WinDbg(Preview)

WinDbg는 두 갈래로 존재해 왔다. 이름이 비슷해 혼란스럽지만 정리하면 간단하다.

클래식 WinDbg

오래된 회색 UI의 windbg.exe다. Windows SDK 안의 "Debugging Tools for Windows" 컴포넌트로 배포된다. 같은 패키지에 콘솔 디버거인 cdb.exe, 커널 디버거 kd.exe도 함께 들어 있다. 기능은 완전하지만 UI가 투박하다.

WinDbg(과거의 WinDbg Preview)

리본 UI에 시계열 디버깅(TTD) 같은 현대적 기능을 더한 새 버전이다. Microsoft Store에서 MSIX 패키지로 배포되며, 처음에는 "WinDbg Preview"라는 이름이었다. 지금은 Preview 딱지를 떼고 사실상 기본 WinDbg로 자리 잡는 추세라, 최근 문서나 메뉴에서는 그냥 "WinDbg"로 부른다.

지금 새로 시작한다면 특별한 이유가 없다면 Microsoft Store의 WinDbg(구 Preview)를 권장한다. UI가 직관적이고 업데이트가 자동이다. 다만 어느 쪽을 쓰든 디버거 명령어(k, !analyze, lm 등)는 완전히 동일하다. 이 시리즈의 명령은 두 버전에서 그대로 통한다. 보안 정책상 Store를 못 쓰는 폐쇄망 환경이라면 SDK 버전을 설치한다.

설치 방법

경로 A — Microsoft Store (간편)

Store 설치
  1. Microsoft Store를 열고 "WinDbg"를 검색한다.
  2. Microsoft 게시자의 WinDbg를 설치한다.
  3. 시작 메뉴에서 바로 실행된다. 별도 환경 설정이 거의 필요 없다.

경로 B — Windows SDK (폐쇄망·오프라인)

SDK 설치
  1. Windows SDK 설치 관리자를 실행한다.
  2. 구성 요소 선택 화면에서 "Debugging Tools for Windows" 하나만 체크해도 된다(다른 항목은 해제 가능).
  3. 설치 후 windbg.exe는 보통 C:\Program Files (x86)\Windows Kits\10\Debuggers\x64\에 들어간다.
비트(아키텍처)를 맞춘다 SDK 버전에는 x64와 x86 디버거가 따로 들어 있다. 분석 대상 프로세스가 64비트면 x64 디버거를, 32비트면 x86 디버거를 쓰는 것이 가장 깔끔하다. Store 버전은 덤프의 비트를 자동 인식하므로 이 고민이 줄어든다.

심볼이란 무엇인가

WinDbg를 설치하고 덤프를 열었는데 콜스택이 이렇게 나온다면, 심볼이 없는 것이다.

0:000> k
 # Child-SP          RetAddr               Call Site
00 000000ab`12dff8a0 00007 ff8`9c2e1234     0x00007ff89c2e5678
01 000000ab`12dff8e0 00007ff8`9c2e0abc     0x00007ff89c2e1234
02 000000ab`12dff920 00007ff8`9c2dffff     0x00007ff89c2e0abc

주소만 잔뜩 나오고 함수 이름이 하나도 없다. 이래서는 어디서 죽었는지 알 수 없다. 여기서 심볼(symbol)이 필요하다.

심볼은 메모리 주소를 사람이 읽을 수 있는 함수 이름·소스 줄번호로 매핑하는 정보다. C++ 컴파일러는 빌드 시 이 매핑을 .pdb(Program Database) 파일에 따로 저장한다. 디버거가 이 pdb를 찾으면 위의 주소 나열이 다음처럼 의미 있는 콜스택으로 바뀐다.

0:000> k
 # Call Site
00 VisionCore!ImageBuffer::At+0x2a
01 VisionCore!GaussianFilter::Apply+0x1f4
02 VisionCore!ProcessBlock::Execute+0x88
03 HostApp!Pipeline::Run+0x143
심볼이 분석의 90%다 심볼이 없거나 버전이 안 맞으면, WinDbg는 잘못된 함수 이름을 가져다 붙이거나 주소만 보여 준다. 그 상태로 추측하면 엉뚱한 결론에 도달한다. 분석을 시작하기 전, 심볼이 제대로 로드됐는지부터 확인하는 습관이 필요하다. 심볼은 운영체제(Windows)용과 우리 제품용, 두 종류 모두 맞춰야 한다.

심볼 경로 설정

심볼은 두 출처에서 가져온다. Windows 시스템 모듈(ntdll, kernel32 등)의 심볼은 Microsoft 공개 심볼 서버에서, 우리 제품 모듈의 심볼은 우리가 보관한 pdb에서 가져온다.

Microsoft 공개 심볼 서버

Microsoft는 OS 모듈의 심볼을 공개 서버로 제공한다. 심볼 경로는 다음 형식으로 지정한다.

srv*C:\symbols*https://msdl.microsoft.com/download/symbols

이 문자열의 의미를 분해하면 이렇다.

  • srv* — 심볼 서버를 사용한다는 표시다.
  • C:\symbols — 내려받은 심볼을 캐싱할 로컬 폴더다. 한 번 받으면 다음부터는 여기서 바로 읽는다.
  • https://msdl.microsoft.com/download/symbols — Microsoft 공개 심볼 서버 주소다.

즉 "서버에서 받아서 C:\symbols에 캐싱하라"는 뜻이다. 로컬 캐시 폴더 덕분에 같은 모듈을 매번 다시 받지 않는다.

_NT_SYMBOL_PATH 환경변수

매번 심볼 경로를 입력하기 번거로우면, _NT_SYMBOL_PATH 환경변수에 한 번 등록해 둔다. WinDbg는 시작할 때 이 변수를 자동으로 읽어 심볼 경로로 삼는다.

시스템 환경변수로 등록 (한 번만)
:: setx 로 사용자 환경변수에 영구 등록 — 새 창부터 적용됨
setx _NT_SYMBOL_PATH "srv*C:\symbols*https://msdl.microsoft.com/download/symbols"

:: 우리 제품 pdb 폴더를 함께 넣고 싶다면 세미콜론으로 연결
setx _NT_SYMBOL_PATH "srv*C:\symbols*https://msdl.microsoft.com/download/symbols;C:\ProductSymbols"

.sympath / .reload 명령

WinDbg 안에서 심볼 경로를 직접 다룰 때 쓰는 명령이다. 분석 중 가장 자주 입력하게 된다.

:: 현재 설정된 심볼 경로 확인
.sympath

:: 심볼 경로를 새로 지정
.sympath srv*C:\symbols*https://msdl.microsoft.com/download/symbols

:: 기존 경로에 우리 제품 pdb 폴더를 추가
.sympath+ C:\ProductSymbols

:: 심볼을 다시 로드 (경로를 바꾼 뒤 반드시 실행)
.reload

:: 모든 모듈의 심볼을 즉시 강제로 다시 로드
.reload /f

.reload는 기본적으로 "필요할 때 로드(deferred)" 방식이라, 심볼 상태가 이상하면 .reload /f로 즉시 강제 로드해 확인한다. /f는 force의 약자다.

심볼 로딩 과정을 보고 싶다면 !sym noisy를 먼저 입력하고 .reload /f 모듈명을 실행하면, WinDbg가 어느 경로에서 어떤 pdb를 찾으려 시도하는지 한 줄씩 출력한다. "왜 우리 모듈 심볼이 안 잡히지?"를 추적할 때 가장 확실한 방법이다. 다시 끄려면 !sym quiet를 입력한다.

내 프로그램 심볼 관리

Windows 시스템 심볼은 Microsoft 서버에서 알아서 받아온다. 문제는 우리 제품의 심볼이다. 이건 우리가 직접 만들고 보관해야 한다. 여기서 실수하면, 정작 가장 중요한 우리 모듈의 콜스택이 주소로만 남는다.

릴리스 빌드도 pdb를 만든다

흔한 오해가 "릴리스 빌드는 pdb가 없다"는 것이다. 사실 릴리스 빌드도 pdb를 생성할 수 있고, 반드시 생성해야 한다. 최적화는 그대로 두고 디버그 정보만 함께 출력하면 된다. Visual Studio의 C++ 프로젝트 기준 설정은 다음과 같다.

  • 컴파일러 — C/C++ > 일반 > 디버그 정보 형식을 /Zi(프로그램 데이터베이스)로 설정한다.
  • 링커 — 링커 > 디버깅 > 디버그 정보 생성을 /DEBUG(또는 /DEBUG:FULL)로 설정한다.
  • 최적화(/O2 등)는 릴리스 그대로 둔다. pdb 생성과 최적화는 양립한다.

이렇게 하면 최적화된 릴리스 바이너리(.dll/.exe)와 짝이 맞는 .pdb가 함께 나온다. 단, 최적화로 인해 일부 함수가 인라인되거나 변수가 레지스터로 사라져, 디버그 빌드만큼 모든 지역 변수가 보이지는 않는다는 점은 감안한다.

바이너리와 pdb는 한 쌍이다 pdb는 빌드할 때마다 고유한 서명(GUID + age)을 갖고, 정확히 그 빌드의 바이너리하고만 매칭된다. 소스를 한 줄만 고쳐 다시 빌드해도 새 pdb는 옛 바이너리와 맞지 않는다. 그래서 릴리스 산출물을 낼 때 바이너리와 pdb를 같은 묶음으로 보관해야 한다. pdb를 버리면, 나중에 그 버전의 덤프를 받아도 심볼을 맞출 길이 사라진다.

버전별로 pdb를 보관한다

고객사마다 설치된 제품 버전이 다르다. 그래서 받은 덤프의 모듈 버전에 맞는 pdb를 꺼내 쓸 수 있어야 한다. 두 가지 방식이 있다.

  • 버전별 폴더 보관 — 릴리스마다 \\fileserver\symbols\Product\1.4.2\처럼 버전 폴더에 바이너리와 pdb를 함께 보관한다. 소규모 팀에 충분하다.
  • 심볼 서버 구축 — symstore.exe로 사내 심볼 서버에 적재하면, WinDbg가 모듈 서명으로 정확한 pdb를 자동으로 찾아온다. 버전이 많아지면 이쪽이 훨씬 편하다. 심볼 경로에 srv*C:\symbols*\\symsrv\product처럼 사내 서버를 추가하면 된다.
1편의 "버전을 함께 받으라"가 여기서 빛난다 덤프를 받을 때 제품 버전을 같이 물어 둔 이유가 이것이다. 버전을 알면 보관해 둔 pdb 중 정확히 맞는 것을 꺼내 심볼 경로에 넣을 수 있다. 버전 기록 없이 덤프만 있으면, 어떤 pdb를 맞춰야 할지부터 추적해야 해서 시간이 두 배로 든다.

덤프 열기와 첫 명령

이제 준비가 끝났다. 받아온 .dmp를 연다.

덤프 파일 열기

  • GUI — WinDbg에서 File > Open Dump File을 선택하고 .dmp를 연다.
  • 명령줄 — -z 옵션으로 바로 연다.
:: 덤프 파일을 지정해 WinDbg 실행
windbg -z C:\CrashDumps\MyVisionApp.dmp

:: 심볼 경로(-y)와 함께 한 번에 지정
windbg -y "srv*C:\symbols*https://msdl.microsoft.com/download/symbols;C:\ProductSymbols" -z C:\CrashDumps\MyVisionApp.dmp

첫 명령 — !analyze -v

덤프가 열리면, 가장 먼저 돌려 보는 명령은 거의 정해져 있다.

0:000> !analyze -v

!analyze -v는 WinDbg의 자동 분석 엔진이다. 예외 코드, 크래시가 발생한 명령 위치(FAULTING_IP), 콜스택, 의심 모듈을 한 번에 요약해 준다. -v는 verbose(자세히)다. 이 한 줄이 1차 진단의 출발점이며, 출력을 읽는 법은 3편에서 본격적으로 다룬다.

분석 전 의례 — 심볼 상태 확인 !analyze -v를 돌리기 전에 lm(loaded modules)으로 우리 모듈의 심볼이 잡혔는지 먼저 본다. 모듈 옆에 (private pdb symbols)나 파일 경로가 보이면 정상이고, (no symbols) 또는 (deferred)로만 남아 있으면 심볼 경로부터 손봐야 한다.

심볼이 안 맞을 때

실무에서 가장 자주 부딪히는 벽이다. 심볼이 없거나 버전이 어긋나면 콜스택이 거짓말을 한다. 증상과 대처를 정리한다.

증상

  • 콜스택에 함수 이름 대신 주소(0x00007ff8...)만 나온다.
  • 출력에 *** WARNING: Unable to verify checksum 또는 *** ERROR: Module load completed but symbols could not be loaded가 보인다.
  • 함수 이름은 나오는데 줄번호가 엉뚱하거나, 호출 관계가 코드와 맞지 않는다(버전 불일치의 전형적 증상).

대처

:: 1) 심볼 로딩 과정을 자세히 출력하도록 켠다
0:000> !sym noisy

:: 2) 문제 모듈만 강제로 다시 로드해 본다
0:000> .reload /f VisionCore.dll

:: 3) 그 모듈의 상세 정보로 pdb 매칭 상태를 확인한다
0:000> lmvm VisionCore

lmvm VisionCore 출력에서 모듈의 타임스탬프·버전과, 디버거가 찾고 있는 pdb의 서명을 비교할 수 있다. 여기서 버전이 어긋나 있으면, 보관해 둔 pdb 중 그 빌드의 것을 찾아 심볼 경로에 넣고 다시 .reload /f 한다.

심볼이 안 맞은 콜스택을 믿지 마라 가장 위험한 상황은 "그럴듯해 보이지만 틀린" 콜스택이다. 버전이 어긋난 pdb를 억지로 물리면, 존재하지도 않는 함수 호출 경로가 만들어져 완전히 잘못된 결론으로 이어진다. 콜스택을 해석하기 전에 우리 모듈 심볼이 정확히 그 버전으로 매칭됐는지부터 확정하는 것이 철칙이다.
2편 정리 WinDbg는 Store 버전이든 SDK 버전이든 명령어가 같다. 심볼 경로는 srv*C:\symbols*https://msdl.microsoft.com/download/symbols로 OS 심볼을 받고, 우리 제품은 릴리스 pdb를 버전별로 보관해 맞춘다. 덤프를 열면 !analyze -v 전에 lm으로 심볼 상태부터 확인한다. 환경이 갖춰졌으니, 이제 콜스택을 읽고 원인을 짚는 단계로 간다.
