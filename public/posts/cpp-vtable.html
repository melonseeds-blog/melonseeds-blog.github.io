가상 함수가 푸는 문제

부모 포인터로 함수를 불렀는데 실제 객체(자식)의 함수가 실행되게 하는 것이 가상 함수다. 컴파일러는 s->Draw()를 컴파일하는 시점에 s가 실제로 원인지 사각형인지 모른다. 그래서 "어느 함수를 부를지"를 실행 중에 정하는 장치가 필요하고, 대부분의 C++ 컴파일러는 이것을 가상 함수 테이블(vtable)로 구현한다.

struct Shape
{
    virtual ~Shape() = default;
    virtual void Draw() const = 0;
    virtual double Area() const { return 0.0; }
    int id = 0;
};

struct Circle : Shape
{
    void Draw() const override { /* draw circle */ }
    double Area() const override { return 3.14159 * r * r; }
    double r = 1.0;
};

struct Rect : Shape
{
    void Draw() const override { /* draw rect */ }   // Area() not overridden
    double w = 1.0, h = 1.0;
};

void Render(const std::vector<Shape*>& shapes)
{
    for (const Shape* s : shapes)
        s->Draw();          // which Draw? decided at run time
}
표준이 정한 것은 동작뿐 C++ 표준은 "가상 함수는 실제 객체의 함수가 불린다"는 동작만 정하고, vtable이라는 구현 방법은 정하지 않는다. 다만 MSVC, GCC, Clang 모두 vtable 방식을 쓰고 세부 배치만 조금씩 다르다. 이 글의 배치 설명은 그 공통 구조를 기준으로 한다.

vtable과 vptr의 구조

두 가지가 짝을 이룬다.

이름어디에, 몇 개내용
vtable가상 함수가 있는 클래스마다 하나. 프로그램의 읽기 전용 데이터 영역그 클래스가 실제로 부를 가상 함수들의 주소를 순서대로 담은 배열
vptr객체마다 하나. 보통 객체의 맨 앞자기 클래스의 vtable을 가리키는 숨은 포인터
같은 클래스의 객체는 모두 같은 vtable을 가리킨다. Rect는 Area를 고치지 않았으므로 그 칸에 Shape::Area가 그대로 들어 있다

vptr이 생기므로 가상 함수가 있는 클래스의 객체는 포인터 크기만큼(64비트에서 8바이트) 커진다.

struct Plain   { int x; };                       // sizeof == 4
struct Virtual { virtual ~Virtual() {} int x; };  // sizeof == 16 on 64-bit (8 vptr + 4 x + 4 padding)

가상 함수 호출이 실제로 하는 일

s->Draw()는 컴파일되면 대략 다음 세 단계가 된다. Draw가 vtable의 1번 칸이라고 하자.

// what s->Draw() compiles to (conceptually)
void** vptr = *reinterpret_cast<void***>(s);       // 1) read the hidden pointer at the start of *s
auto   fn   = reinterpret_cast<void(*)(const Shape*)>(vptr[1]);   // 2) read slot 1 of the table
fn(s);                                              // 3) indirect call, passing s as 'this'
단계하는 일비용
1객체에서 vptr 읽기메모리 읽기 1번 (객체가 캐시에 있으면 빠름)
2vtable에서 함수 주소 읽기메모리 읽기 1번 (vtable은 보통 캐시에 있음)
3그 주소로 간접 호출CPU 분기 예측이 맞으면 빠름, 틀리면 수십 사이클 손해

일반 함수 호출보다 메모리 읽기 두 번과 간접 호출이 더 붙는다. 한 번만 보면 매우 작은 비용이다. 진짜 비용은 다른 곳에 있다(아래 "비용" 절).

위 코드는 설명용 vptr을 직접 읽는 코드는 구현에 의존하고, 표준으로는 정의되지 않은 동작이다. 구조를 이해하는 실험에만 쓰고 제품 코드에는 넣지 않는다.

상속과 override가 vtable에 남기는 것

자식 클래스의 vtable은 부모 vtable을 복사한 뒤 고친 칸만 바꾸고, 새 가상 함수는 뒤에 붙인 것과 같다.

struct Base
{
    virtual ~Base();
    virtual void A();
    virtual void B();
};
struct Derived : Base
{
    void B() override;      // replaces slot of B
    virtual void C();       // new slot appended
};
칸Base vtableDerived vtable
0Base::~BaseDerived::~Derived (소멸자는 항상 자기 것)
1Base::ABase::A (물려받음)
2Base::BDerived::B (override로 교체)
3-Derived::C (새로 추가)

칸 번호는 부모와 자식이 같으므로, 부모 포인터로 2번 칸을 부르면 실제 객체가 Base든 Derived든 맞는 B가 불린다. 이것이 가상 함수 동작의 전부다.

override를 꼭 붙이기 자식에서 void B() const처럼 시그니처를 조금만 달리 써도 새 가상 함수가 생길 뿐, 부모의 B 칸은 바뀌지 않는다. 컴파일 오류도 없다. override를 붙이면 부모에 같은 함수가 없을 때 컴파일 오류가 나서 이 실수를 막는다.

생성자와 소멸자 안의 가상 호출

vptr은 생성자가 실행되는 동안 단계별로 바뀐다. 자식 객체를 만들면 부모 생성자가 먼저 돌고, 그동안 vptr은 부모의 vtable을 가리킨다. 그래서 부모 생성자 안에서 가상 함수를 부르면 자식 것이 아니라 부모 것이 불린다.

struct Camera
{
    Camera()          { Init(); }               // vptr -> Camera's vtable here
    virtual ~Camera() { Close(); }              // vptr -> Camera's vtable again here
    virtual void Init()  { puts("Camera::Init"); }
    virtual void Close() { puts("Camera::Close"); }
};

struct GigECamera : Camera
{
    GigECamera()  { /* vptr -> GigECamera's vtable from here */ }
    void Init()  override { puts("GigECamera::Init"); }
    void Close() override { puts("GigECamera::Close"); }
};

GigECamera cam;     // prints "Camera::Init", NOT "GigECamera::Init"
// at destruction:  prints "Camera::Close"
시점vptr이 가리키는 것가상 호출 결과
Camera 생성자 실행 중Camera vtableCamera 함수
GigECamera 생성자 실행 중, 이후GigECamera vtableGigECamera 함수
GigECamera 소멸자 실행 중GigECamera vtableGigECamera 함수
Camera 소멸자 실행 중Camera vtableCamera 함수

이렇게 동작하는 이유는 안전 때문이다. 부모 생성자가 도는 동안 자식 멤버는 아직 초기화되지 않았으므로, 자식 함수가 불리면 초기화 안 된 값을 쓰게 된다.

"pure virtual function call" 오류 부모의 Init이 순수 가상 함수(= 0)라면, 부모 생성자에서 부를 때 구현이 없는 칸을 부르게 되어 프로그램이 "pure virtual function call" 오류로 죽는다. 생성자, 소멸자에서는 가상 함수를 부르지 않는다. 초기화가 자식마다 다르면 생성 후 따로 Open() 같은 함수를 부르는 2단계 초기화를 쓴다.

가상 소멸자

부모 포인터로 자식 객체를 delete할 때, 부모 소멸자가 가상이 아니면 vtable을 거치지 않고 부모 소멸자만 불린다. 자식 소멸자가 실행되지 않아 자식이 가진 자원(버퍼, 파일, 장치 핸들)이 해제되지 않는다. 표준으로는 정의되지 않은 동작이다.

struct IFilter            { /* no virtual destructor */ virtual void Apply(Image&) = 0; };
struct GpuFilter : IFilter { ~GpuFilter() { cudaFree(buf); } void Apply(Image&) override; float* buf; };

IFilter* f = new GpuFilter();
delete f;          // only IFilter's destructor runs -> GPU buffer leaks (undefined behavior)

// fix: polymorphic base classes get a virtual destructor
struct IFilterOk { virtual ~IFilterOk() = default; virtual void Apply(Image&) = 0; };
규칙설명
가상 함수가 하나라도 있으면 소멸자도 가상부모 포인터로 지울 가능성이 있기 때문
부모 포인터로 지우지 않게 막고 싶으면소멸자를 protected로, 가상 아니게
std::unique_ptr<Base>로 소유내부에서 delete를 부르므로 같은 규칙 적용

다중 상속과 vptr 여러 개

가상 함수가 있는 부모를 둘 이상 상속하면, 객체 안에 부모 부분마다 vptr이 하나씩 생긴다. 27편에서 본 것처럼 두 번째 부모 포인터는 객체 시작 위치가 아니라 두 번째 부모 부분을 가리킨다.

struct ICamera   { virtual ~ICamera() = default;   virtual Frame Grab() = 0; };
struct IDevice   { virtual ~IDevice() = default;   virtual void Reset() = 0; };
struct UsbCamera : ICamera, IDevice
{
    Frame Grab() override;
    void  Reset() override;
};
// sizeof(UsbCamera) includes TWO vptrs on 64-bit: 16 bytes of hidden pointers
객체 안의 위치내용
오프셋 0ICamera 부분의 vptr → UsbCamera용 ICamera vtable
오프셋 8IDevice 부분의 vptr → UsbCamera용 IDevice vtable
그 뒤UsbCamera 자기 멤버

IDevice* d로 d->Reset()을 부르면, d는 객체의 오프셋 8을 가리킨다. 그런데 UsbCamera::Reset은 객체 시작 주소를 this로 받아야 한다. 그래서 IDevice vtable의 Reset 칸에는 실제 함수 대신 "this를 8만큼 빼고 UsbCamera::Reset으로 가는" 작은 코드(thunk)의 주소가 들어 있다. 디버거 콜스택에서 가끔 보이는 [thunk], adjustor{8} 같은 이름이 이것이다.

RTTI와 dynamic_cast의 위치

vtable에는 함수 주소만 있는 것이 아니다. 대부분의 구현은 vtable 바로 앞 칸에 그 클래스의 타입 정보(type_info, 상속 관계)를 가리키는 포인터를 둔다. GCC, Clang(Itanium 규약)은 type_info를 직접, MSVC는 "Complete Object Locator"라는 구조체를 거쳐 가리킨다.

기능vtable을 쓰는 방식
typeid(*p)p의 vptr → vtable 앞 칸 → type_info
dynamic_cast<T*>(p)같은 경로로 실제 타입 정보를 얻고, 상속 관계를 따라가며 T가 있는지 찾음. 있으면 다중 상속 오프셋만큼 주소를 고쳐 돌려줌
MFC IsKindOf (26편)같은 일을 매크로로 만든 클래스별 정보 구조체와 가상 함수 GetRuntimeClass()로 함

그래서 dynamic_cast와 typeid는 가상 함수가 있는 클래스에서만 동작한다. vptr이 없으면 실행 중에 실제 타입을 알아낼 방법이 없기 때문이다. MSVC에서 /GR-로 RTTI를 끄면 타입 정보가 빠지고 dynamic_cast를 쓸 수 없다.

가상 함수의 실제 비용

비용크기신경 쓸 때
객체마다 vptr8바이트 (64비트)작은 객체(예: 점, 픽셀)를 수백만 개 만들 때
클래스마다 vtable칸 수 × 8바이트거의 없음
간접 호출메모리 읽기 2번 + 간접 분기아주 작은 함수를 수백만 번 부를 때
인라인 불가컴파일러가 함수 본문을 호출 자리에 펼치지 못함이것이 가장 큰 비용. 반복문 최적화, SIMD 자동 벡터화가 막힘

영상 처리에서 흔한 실수는 픽셀 하나마다 가상 함수를 부르는 설계다.

// slow: one virtual call per pixel, no inlining, no vectorization
struct IPixelOp { virtual ~IPixelOp() = default; virtual uint8_t Apply(uint8_t v) const = 0; };
for (size_t i = 0; i < n; ++i) dst[i] = op->Apply(src[i]);

// fast option 1: virtual call per IMAGE, tight loop inside
struct IImageOp { virtual ~IImageOp() = default; virtual void Apply(const uint8_t* src, uint8_t* dst, size_t n) const = 0; };
struct Invert : IImageOp
{
    void Apply(const uint8_t* src, uint8_t* dst, size_t n) const override
    { for (size_t i = 0; i < n; ++i) dst[i] = 255 - src[i]; }   // inlined, vectorized
};

// fast option 2: compile-time polymorphism with templates
template <typename Op>
void ApplyAll(const uint8_t* src, uint8_t* dst, size_t n, Op op)
{ for (size_t i = 0; i < n; ++i) dst[i] = op(src[i]); }

가상 함수 호출 횟수를 "픽셀 수"에서 "영상 수"로 줄이면 비용은 사실상 사라지고, 반복문 안은 컴파일러가 마음껏 최적화할 수 있다. C++ 시리즈의 인터페이스 설계 패턴 글과 플러그인 아키텍처 글의 구조도 이 원칙을 따른다.

컴파일러가 가상 호출을 없애는 경우

컴파일러가 실제 타입을 확실히 알면 vtable을 거치지 않고 직접 호출하고, 인라인까지 한다(devirtualization).

상황예
객체를 값으로 직접 사용Circle c; c.Draw(); (포인터, 참조가 아님)
클래스나 함수에 finalstruct Circle final : Shape이면 Circle*로 부른 Draw는 다른 것일 수 없음
링크 시간 최적화(LTO)로 자식 클래스가 하나뿐임을 앎MSVC /GL, GCC/Clang -flto

직접 확인하는 방법

도구방법
Visual Studio 디버거조사식 창에서 객체를 펼치면 __vfptr이 보이고, 그 아래에 vtable 칸과 함수 이름이 나옴
MSVC 컴파일러비공식 옵션 /d1reportSingleClassLayoutCircle을 주면 Circle의 메모리 배치와 vtable을 빌드 출력에 찍음
GCC-fdump-lang-class로 클래스 배치와 vtable 내용을 파일로 출력
Clang-Xclang -fdump-record-layouts, -Xclang -fdump-vtable-layouts
# MSVC: print the layout of class Circle while compiling
cl /c /d1reportSingleClassLayoutCircle shapes.cpp

# GCC: writes shapes.cpp.*.class with every class layout and vtable
g++ -c -fdump-lang-class shapes.cpp

흔한 함정

memset, memcpy로 다형적 객체 초기화 memset(this, 0, sizeof(*this))는 vptr까지 0으로 지운다. 이후 가상 함수를 부르면 주소 0으로 점프해 죽는다. 옛 C 스타일 코드를 클래스로 옮길 때 자주 생긴다. 멤버별로 초기화하거나 멤버 초기화 목록을 쓴다.
DLL 경계에서 클래스 정의 불일치 DLL과 실행 파일이 같은 인터페이스 헤더의 다른 버전으로 빌드되면, 가상 함수 순서가 달라 vtable 칸 번호가 어긋난다. Grab을 불렀는데 Reset이 실행되는 식의 이상한 동작이 생긴다. 인터페이스에 가상 함수를 추가할 때는 맨 뒤에만 추가하고, 양쪽을 함께 다시 빌드한다.
해제된 객체의 가상 호출 이미 delete된 객체로 가상 함수를 부르면, 소멸자가 vptr을 부모 vtable로 바꿔 둔 상태이거나 메모리가 다른 용도로 쓰인 상태라 엉뚱한 함수가 불리거나 "pure virtual function call"로 죽는다. 콜스택에 이 오류가 보이면 해제 후 사용(use-after-free)을 먼저 의심한다.

정리
