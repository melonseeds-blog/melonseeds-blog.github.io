WPF란 무엇인가

WPF (Windows Presentation Foundation)는 Microsoft가 .NET 3.0과 함께 2006년에 발표한 데스크톱 UI 프레임워크다. 이전 세대의 GDI/GDI+ 기반 WinForms와 달리 DirectX 위에서 동작하므로 화면 그리기가 전부 벡터 기반·하드웨어 가속으로 처리된다.

핵심 특징을 한 문단으로 정리하면 이렇다. UI를 XAML이라는 XML 계열 마크업 언어로 선언하고, 비즈니스 로직은 C#(코드 비하인드)에 작성한다. 화면 요소는 Logical Tree와 Visual Tree로 구조화되고, 모든 속성은 의존성 속성(Dependency Property) 시스템 위에서 동작하여 바인딩·애니메이션·스타일·테마를 일관되게 지원한다.

항목WPF
출시2006 (.NET 3.0)
플랫폼Windows 전용
렌더링DirectX (벡터·하드웨어 가속)
UI 정의XAML (마크업) + C# (코드 비하인드)
아키텍처 친화MVVM, 데이터 바인딩, 명령
주 사용 분야산업용·엔지니어링·금융 등 윈도우 데스크톱

WPF vs WinForms

WinForms는 1.0 시절부터 이어진 전통적 데스크톱 UI다. 픽셀 기반 GDI로 그리며, 컨트롤은 Win32 핸들(HWND)에 1:1 매핑된다. WPF는 이를 거의 전면 재설계한 결과다.

항목WinFormsWPF
렌더링GDI/GDI+ (래스터)DirectX (벡터)
해상도/DPIDPI 변경에 취약벡터라 해상도 독립
UI 정의디자이너 코드 자동 생성 (.Designer.cs)XAML 마크업
데이터 바인딩기본 제공이나 제한적강력한 양방향 바인딩
스타일·테마없음 (직접 그려야 함)Style·Template·ResourceDictionary
애니메이션없음 (수동 타이머)Storyboard 내장
커스텀 컨트롤OnPaint 오버라이드ControlTemplate 변경만으로 가능
러닝 커브낮음높음 (개념 다수)
WinForms는 죽었는가 아직 .NET 8/9에서 정식 지원된다. 단순 도구·내부용 유틸은 여전히 WinForms가 빠르고 가볍다. 하지만 데이터 시각화, MVVM, 테마가 필요한 본격 데스크톱은 WPF가 압도적이다.

산업용 데스크톱 SW를 만들 때 WPF가 여전히 표준인 이유는 다음과 같다.

  • 성숙도 — 약 20년간 누적된 라이브러리·예제·StackOverflow 답변
  • 강력한 컨트롤 생태계 — DevExpress, Telerik, Syncfusion 등 상용 컴포넌트
  • .NET 전체와의 호환 — C++/CLI·P/Invoke로 네이티브 통합 용이
  • 안정성 — Microsoft가 계속 메인테넌스, 기능 추가는 적지만 잘 동작

프로젝트 구조

Visual Studio 2022에서 "WPF Application (.NET)" 템플릿으로 만들면 다음 파일이 생긴다.

MyApp/
├── App.xaml             # 애플리케이션 진입점·전역 리소스
├── App.xaml.cs          # App 클래스 코드 비하인드
├── MainWindow.xaml      # 메인 창 UI
├── MainWindow.xaml.cs   # 메인 창 코드 비하인드
├── AssemblyInfo.cs
└── MyApp.csproj         # SDK 스타일 프로젝트 파일

App.xaml — 애플리케이션 정의

<Application x:Class="MyApp.App"
             xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
             xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
             StartupUri="MainWindow.xaml">
    <Application.Resources>
        <!-- 전역 스타일·리소스를 여기에 정의 -->
        <SolidColorBrush x:Key="AccentBrush" Color="#FF3DA9FC" />
    </Application.Resources>
</Application>
// App.xaml.cs — partial class로 XAML과 결합
using System.Windows;

namespace MyApp
{
    public partial class App : Application
    {
        protected override void OnStartup(StartupEventArgs e)
        {
            base.OnStartup(e);
            // 전역 예외 처리·DI 컨테이너 초기화 등
        }
    }
}

MainWindow.xaml — 메인 창

<Window x:Class="MyApp.MainWindow"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        Title="MainWindow" Height="450" Width="800">
    <Grid>
        <Button x:Name="OkButton"
                Content="OK"
                Width="120" Height="32"

    </Grid>
</Window>
// MainWindow.xaml.cs
using System.Windows;

namespace MyApp
{
    public partial class MainWindow : Window
    {
        public MainWindow()
        {
            InitializeComponent();   // XAML을 메모리로 로드
        }

        private void OkButton_Click(object sender, RoutedEventArgs e)
        {
            MessageBox.Show("Hello WPF");
        }
    }
}

XAML — Extensible Application Markup Language

XAML은 XML 형식의 선언적 UI 언어다. 각 태그는 .NET 클래스에 매핑되고, 속성은 클래스의 프로퍼티에 매핑된다. <Button Content="OK"/>은 코드로 new Button { Content = "OK" }과 동등하다.

네임스페이스

<Window
    xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
    xmlns:local="clr-namespace:MyApp"
    xmlns:vm="clr-namespace:MyApp.ViewModels">
    ...
</Window>
  • 기본 xmlns — WPF 표준 컨트롤 (Button, Grid 등)
  • xmlns:x — XAML 자체 언어 키워드 (x:Name, x:Class, x:Key)
  • xmlns:local — 내 프로젝트의 C# 네임스페이스 매핑

속성 표기 — Attribute vs Property Element

<!-- Attribute 문법: 단순 값 -->
<Button Content="OK" Background="#3DA9FC" />

<!-- Property Element 문법: 복잡한 값을 자식 요소로 -->
<Button>
    <Button.Background>
        <LinearGradientBrush StartPoint="0,0" EndPoint="0,1">
            <GradientStop Offset="0" Color="#3DA9FC" />
            <GradientStop Offset="1" Color="#094A82" />
        </LinearGradientBrush>
    </Button.Background>
    <Button.Content>OK</Button.Content>
</Button>

마크업 확장 (Markup Extension)

중괄호 { } 안에 쓰면 런타임 평가 표현식이 된다.

<!-- 정적 리소스 참조 -->
<Button Background="{StaticResource AccentBrush}" />

<!-- 데이터 바인딩 -->
<TextBlock Text="{Binding UserName}" />

<!-- 다른 요소 참조 -->
<TextBlock Text="{Binding ElementName=Slider1, Path=Value}" />

<!-- 정적 값 -->
<TextBlock Foreground="{x:Static SystemColors.WindowTextBrush}" />

XAML과 코드 비하인드

XAML 파일과 C# 파일은 partial class로 하나의 클래스를 이룬다. x:Class가 클래스 이름을, x:Name이 멤버 필드 이름을 결정한다.

// XAML에서 x:Name="OkButton"으로 선언된 요소는
// 코드 비하인드에서 같은 이름의 필드로 접근 가능
private void Window_Loaded(object sender, RoutedEventArgs e)
{
    OkButton.Content = "Confirm";   // XAML 요소를 코드에서 조작
    OkButton.IsEnabled = false;
}
x:Name 남발 주의 x:Name은 코드 비하인드에서 직접 조작할 때만 붙인다. 바인딩이나 스타일로 충분히 해결되는 경우에 x:Name을 무분별하게 붙이면 MVVM이 깨지고 단위 테스트도 어려워진다.

요소 트리 — Logical / Visual Tree

WPF의 모든 UI 요소는 UIElement를 상속하고 부모-자식 트리로 구성된다. 트리는 두 종류가 있다.

  • Logical Tree — XAML에 적은 그대로의 논리적 구조. Window → Grid → Button
  • Visual Tree — 실제 렌더링되는 모든 시각 요소. Button 하나가 내부적으로 Border + ContentPresenter + TextBlock으로 확장된다
using System.Windows.Media;
using System.Windows;

// Logical Tree 탐색
DependencyObject parent = LogicalTreeHelper.GetParent(myButton);

// Visual Tree 탐색 (템플릿 내부 접근 가능)
DependencyObject child = VisualTreeHelper.GetChild(myButton, 0);
int count = VisualTreeHelper.GetChildrenCount(myButton);

의존성 속성 (Dependency Property)

WPF의 가장 중요한 개념이다. 일반 CLR 속성은 단순히 필드를 감싸지만, Dependency Property는 DependencyObject의 내부 저장소를 사용하며 바인딩·애니메이션·스타일·상속 등 WPF 기능을 가능하게 한다.

항목CLR 속성의존성 속성
저장객체 내 필드DependencyObject 사전
기본값생성자에서 초기화메타데이터로 지정
변경 통지INotifyPropertyChanged 직접 구현자동 (PropertyChangedCallback)
값 상속불가부모로부터 상속 (예: FontSize)
바인딩 대상소스만 가능소스·타깃 모두 가능
애니메이션불가가능
스타일 적용불가가능

DependencyProperty.Register

using System.Windows;
using System.Windows.Controls;

public class GaugeControl : Control
{
    // 1) static readonly DependencyProperty 필드 (관례: 이름 + Property)
    public static readonly DependencyProperty ValueProperty =
        DependencyProperty.Register(
            name:          nameof(Value),
            propertyType:  typeof(double),
            ownerType:     typeof(GaugeControl),
            typeMetadata:  new FrameworkPropertyMetadata(
                defaultValue:                0.0,
                flags:                       FrameworkPropertyMetadataOptions.AffectsRender,
                propertyChangedCallback:     OnValueChanged));

    // 2) CLR 래퍼 (GetValue/SetValue만 호출, 다른 코드 금지!)
    public double Value
    {
        get => (double)GetValue(ValueProperty);
        set => SetValue(ValueProperty, value);
    }

    // 3) 변경 콜백
    private static void OnValueChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
    {
        var gauge = (GaugeControl)d;
        double newValue = (double)e.NewValue;
        // 추가 처리...
    }
}
CLR 래퍼에 로직을 넣지 말 것 XAML 로더와 애니메이션은 GetValue/SetValue를 직접 호출하지, 래퍼를 거치지 않는다. 래퍼에 검증·로깅을 넣으면 그 경로로만 동작한다. 추가 로직은 PropertyChangedCallback에 넣어야 한다.

읽기 전용 의존성 속성

private static readonly DependencyPropertyKey IsLoadedKey =
    DependencyProperty.RegisterReadOnly(
        nameof(IsLoaded), typeof(bool), typeof(MyControl),
        new PropertyMetadata(false));

public static readonly DependencyProperty IsLoadedProperty = IsLoadedKey.DependencyProperty;

public bool IsLoaded
{
    get => (bool)GetValue(IsLoadedProperty);
    private set => SetValue(IsLoadedKey, value);   // Key로만 쓰기 가능
}

라우티드 이벤트 (Routed Event)

일반 .NET 이벤트와 달리 트리를 따라 전파된다. 세 가지 라우팅 전략이 있다.

  • Bubbling — 자식 → 부모로 올라간다 (대부분 이벤트, 예: Click, MouseUp)
  • Tunneling — 부모 → 자식으로 내려간다 (이름이 Preview로 시작, 예: PreviewMouseDown)
  • Direct — 발생한 요소에서만 (예: MouseEnter)
// 라우티드 이벤트 등록
public static readonly RoutedEvent ValueChangedEvent =
    EventManager.RegisterRoutedEvent(
        name:        "ValueChanged",
        routingStrategy: RoutingStrategy.Bubble,
        handlerType:     typeof(RoutedPropertyChangedEventHandler<double>),
        ownerType:       typeof(GaugeControl));

public event RoutedPropertyChangedEventHandler<double> ValueChanged
{
    add    => AddHandler(ValueChangedEvent, value);
    remove => RemoveHandler(ValueChangedEvent, value);
}

// 발생 시키기
private void RaiseValueChanged(double oldV, double newV)
{
    var args = new RoutedPropertyChangedEventArgs<double>(oldV, newV, ValueChangedEvent);
    RaiseEvent(args);
}
// 핸들러에서 트리 정보 활용
private void Grid_PreviewMouseDown(object sender, MouseButtonEventArgs e)
{
    // sender: 핸들러가 붙은 요소 (Grid)
    // e.Source: 실제 이벤트가 발생한 요소 (예: 내부 Button)
    // e.OriginalSource: 가장 안쪽 Visual (예: TextBlock)
    if (e.OriginalSource is Button)
    {
        e.Handled = true;   // 더 이상 전파 안 함
    }
}

Attached Property

부모가 정의하지만 자식에게 적용되는 의존성 속성이다. 가장 유명한 예가 Grid.Row, Grid.Column이다. Button 자체에는 Row 속성이 없지만, Grid가 자식에게 "몇 번 행에 배치되는지"를 부착하는 형태다.

<Grid>
    <Grid.RowDefinitions>
        <RowDefinition Height="Auto"/>
        <RowDefinition Height="*"/>
    </Grid.RowDefinitions>

    <!-- Grid.Row, Grid.Column이 Attached Property -->
    <TextBlock Grid.Row="0" Text="Header"/>
    <Button   Grid.Row="1" Content="Body"/>
</Grid>

직접 정의하기

public static class FormHelper
{
    // RegisterAttached 사용
    public static readonly DependencyProperty LabelProperty =
        DependencyProperty.RegisterAttached(
            "Label",
            typeof(string),
            typeof(FormHelper),
            new PropertyMetadata(string.Empty));

    // static Get/Set 메서드 (이름 규칙: Get{이름}, Set{이름})
    public static string GetLabel(DependencyObject obj) => (string)obj.GetValue(LabelProperty);
    public static void   SetLabel(DependencyObject obj, string value) => obj.SetValue(LabelProperty, value);
}
<TextBox local:FormHelper.Label="사용자 이름" />

Resource와 Style

Resource는 재사용 가능한 객체(브러시, 색상, 스타일, 템플릿)를 키로 저장하는 사전이다. Style은 특정 타입의 요소에 속성 집합을 일괄 적용한다.

Resource — 기본 사용

<Window.Resources>
    <SolidColorBrush x:Key="AccentBrush" Color="#FF3DA9FC"/>
    <sys:Double x:Key="DefaultRadius" xmlns:sys="clr-namespace:System;assembly=mscorlib">8</sys:Double>
</Window.Resources>

<Button Background="{StaticResource AccentBrush}" />

Style — 일괄 적용

<Window.Resources>
    <!-- TargetType만 지정하면 해당 타입 전체에 자동 적용 -->
    <Style TargetType="Button">
        <Setter Property="FontSize" Value="14"/>
        <Setter Property="Padding"  Value="12,6"/>
        <Setter Property="Background" Value="{StaticResource AccentBrush}"/>
        <Setter Property="Foreground" Value="White"/>

        <!-- Trigger로 상태별 변화 -->
        <Style.Triggers>
            <Trigger Property="IsMouseOver" Value="True">
                <Setter Property="Opacity" Value="0.8"/>
            </Trigger>
        </Style.Triggers>
    </Style>

    <!-- x:Key 지정 시 명시 적용만 -->
    <Style x:Key="PrimaryButton" TargetType="Button" BasedOn="{StaticResource {x:Type Button}}">
        <Setter Property="FontWeight" Value="Bold"/>
    </Style>
</Window.Resources>

<Button Content="자동 스타일"/>
<Button Content="명시 스타일" Style="{StaticResource PrimaryButton}"/>

ResourceDictionary 분리

<!-- Themes/Light.xaml -->
<ResourceDictionary xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
                    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml">

<Application.Resources>
    <ResourceDictionary>
        <ResourceDictionary.MergedDictionaries>

흔한 함정

XAML과 코드 비하인드 혼합 남용 UI 로직을 전부 xaml.cs에 몰면 WinForms 시절과 다를 게 없다. WPF는 MVVM으로 갈수록 강력해진다. 코드 비하인드는 윈도우 라이프사이클·뷰 전용 트릭에만 쓰고, 나머지는 ViewModel·바인딩으로 옮기자.
x:Name 남발 x:Name을 붙이면 자동으로 NameScope 등록·필드 생성·강한 참조가 생긴다. 수백 개 요소에 다 붙이면 메모리·테스트 모두 곤란해진다. 꼭 필요한 곳에만.
의존성 속성을 인스턴스 필드처럼 등록 DependencyProperty.Register는 반드시 public static readonly 필드여야 한다. 인스턴스 멤버로 두면 객체마다 새로 등록되어 메모리 누수·중복 등록 예외가 발생한다. 또한 DependencyObject는 본질적으로 스레드 친화(thread-affinity) 객체다 — 만든 스레드에서만 접근 가능하다. 백그라운드 스레드에서 SetValue를 호출하면 즉시 예외가 난다. Dispatcher.Invoke로 UI 스레드로 마샬링해야 한다. 
// 잘못된 예 — 백그라운드 스레드에서 직접 접근
Task.Run(() =>
{
    myControl.Value = 42;   // InvalidOperationException
});

// 올바른 예 — Dispatcher 마샬링
Task.Run(() =>
{
    Application.Current.Dispatcher.Invoke(() =>
    {
        myControl.Value = 42;
    });
});
라우티드 이벤트 e.Handled 처리 누락 Tunneling 단계(Preview*)에서 e.Handled = true를 설정하면 뒤이은 Bubbling 단계가 막힌다. 반대로 ScrollViewer 안의 마우스 휠 같은 이벤트가 부모로 올라가지 않게 막고 싶을 때는 의도적으로 e.Handled를 켜야 한다. 라우팅 모델을 모르고 짜면 "왜 핸들러가 두 번 실행되지" 류의 버그가 끝없이 생긴다.
실무 팁 — Snoop·Live Visual Tree 활용 Visual Studio의 Live Visual Tree와 외부 도구 Snoop으로 실행 중인 앱의 Visual Tree·속성을 직접 검사할 수 있다. 바인딩이 안 먹는 원인을 찾을 때 필수 도구다.
