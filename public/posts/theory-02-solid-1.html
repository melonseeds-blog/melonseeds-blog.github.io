SOLID란?

SOLID는 로버트 마틴(Robert C. Martin, 통칭 "Uncle Bob")이 2000년대 초에 정리한 객체지향 설계의 5가지 원칙이다. 다섯 원칙의 앞 글자를 모은 약어이며, 유연하고 유지보수가 쉬운 코드를 만들기 위한 지침이다.

SOLID는 새로운 문법이나 도구가 아니라 설계 판단의 기준이다. 코드가 점점 고치기 어려워질 때, 어디를 어떻게 나눠야 할지 알려주는 나침반 역할을 한다. 객체지향 4대 특성(캡슐화·상속·다형성·추상화)이 "도구"라면, SOLID는 그 도구를 "언제 어떻게 쓰는가"에 대한 원칙이다.

약자원칙핵심 한 줄
SSRP — 단일 책임 원칙클래스는 변경 이유가 하나여야 한다
OOCP — 개방-폐쇄 원칙확장에는 열려 있고 수정에는 닫혀 있어야 한다
LLSP — 리스코프 치환 원칙자식은 부모를 대체할 수 있어야 한다
IISP — 인터페이스 분리 원칙쓰지 않는 인터페이스에 의존하지 않아야 한다
DDIP — 의존 역전 원칙구체가 아니라 추상에 의존해야 한다

이 글은 앞 3개(SRP·OCP·LSP)를 다룬다. 나머지 두 개(ISP·DIP)는 다음 글에서 이어간다. 5원칙은 서로 독립적이지 않고 맞물려 있으므로, 앞 3개를 먼저 탄탄히 이해해 두면 뒤 2개가 자연스럽게 따라온다.

SOLID는 "지켜야 하는 법"이 아니다 SOLID는 트레이드오프를 가진 가이드다. 모든 코드에 100% 적용하면 오히려 과한 추상화로 복잡해진다. "이 코드가 자주 바뀌는가, 바뀐다면 어디가 바뀌는가"를 먼저 묻고, 그 답에 따라 원칙을 적용하는 것이 핵심이다.

SRP — 단일 책임 원칙

Single Responsibility Principle. 하나의 클래스는 하나의 책임만 가져야 한다. 마틴은 이를 더 정밀하게 "클래스를 변경할 이유는 하나뿐이어야 한다"라고 표현한다.

"책임"이란 무엇인가

여기서 "책임"은 메서드 하나, 기능 하나가 아니다. 변경을 요구하는 주체(actor)로 보는 것이 정확하다. 어떤 클래스를 수정하라고 요구하는 사람이나 부서가 둘 이상이라면, 그 클래스는 책임이 둘 이상인 것이다.

예를 들어 영상 검사 결과를 담는 클래스가 (1) 검사 로직 담당자의 요구로도 바뀌고, (2) 보고서 양식 담당자의 요구로도 바뀌고, (3) DB 스키마 담당자의 요구로도 바뀐다면 책임이 셋이다. 한쪽 요구로 코드를 고치다가 다른 쪽 기능을 깨뜨릴 위험이 항상 따라다닌다.

위반 예시 — 책임이 뭉친 클래스

아래 InspectionReport는 검사 데이터 보관, 통계 계산, 파일 저장, 로그 출력을 모두 떠안고 있다.

// 책임이 4개 뭉친 클래스 — 변경 이유가 너무 많다
class InspectionReport
{
public:
    void AddResult(const Defect& defect) { m_defects.push_back(defect); }

    // 책임 1: 통계 계산
    double CalculatePassRate() const
    {
        // ... 합격률 계산 로직
    }

    // 책임 2: 파일 포맷 직렬화
    void SaveAsCsv(const std::string& path) const
    {
        // ... CSV 포맷으로 변환 + 파일 쓰기
    }

    // 책임 3: 화면 출력 포맷
    void PrintToConsole() const
    {
        // ... 콘솔 표 형태로 출력
    }

    // 책임 4: 로그 전송
    void SendToLogServer() const
    {
        // ... 네트워크로 로그 서버에 전송
    }

private:
    std::vector<Defect> m_defects;
};

CSV 포맷이 바뀌어도, 로그 서버 주소가 바뀌어도, 합격률 정의가 바뀌어도 전부 이 한 파일을 건드려야 한다. 테스트도 어렵다. 통계 로직만 검증하고 싶은데 파일 시스템과 네트워크가 딸려 온다.

개선 예시 — 책임 단위로 분리

데이터, 통계, 직렬화, 전송을 각각 별도 클래스로 나눈다. 각 클래스는 변경 이유가 하나씩이다.

// 책임 1: 검사 데이터 보관만 담당
class InspectionResult
{
public:
    void AddDefect(const Defect& defect) { m_defects.push_back(defect); }
    const std::vector<Defect>& GetDefects() const { return m_defects; }

private:
    std::vector<Defect> m_defects;
};

// 책임 2: 통계 계산만 담당
class InspectionStatistics
{
public:
    // Compute the pass rate from an inspection result.
    double ComputePassRate(const InspectionResult& result) const
    {
        // ... 합격률 계산 로직
    }
};

// 책임 3: CSV 직렬화만 담당
class CsvReportWriter
{
public:
    // Write the inspection result to a CSV file.
    ErrorCode Write(const InspectionResult& result, const std::string& path) const
    {
        // ... CSV 변환 + 파일 쓰기
        return ErrorCode::Ok;
    }
};

// 책임 4: 로그 전송만 담당
class LogServerClient
{
public:
    // Send the inspection result to the remote log server.
    ErrorCode Send(const InspectionResult& result) const
    {
        // ... 네트워크 전송
        return ErrorCode::Ok;
    }
};

이제 CSV 포맷이 바뀌면 CsvReportWriter만, 로그 서버가 바뀌면 LogServerClient만 손대면 된다. InspectionStatistics는 파일 시스템 없이 단독으로 테스트할 수 있다. 클래스 수는 늘었지만 각각이 작고 이해하기 쉬워졌다.

"책임"을 "함수 하나"로 오해하지 않는다 SRP를 "메서드는 한 가지 일만"으로 받아들이면 클래스를 잘게 쪼개다 못해 메서드 하나짜리 클래스를 양산하게 된다. SRP의 단위는 함수가 아니라 변경을 요구하는 주체다. 같은 주체가 함께 바꾸는 코드는 한곳에 모여 있는 편이 오히려 응집도가 높다.

OCP — 개방-폐쇄 원칙

Open-Closed Principle. 소프트웨어 요소는 확장에는 열려 있어야 하고(open for extension), 수정에는 닫혀 있어야 한다(closed for modification). 새 기능을 추가할 때 기존에 동작하던 코드를 고치지 않고, 새 코드를 더하는 방식으로 끝내는 것이 목표다.

"기존 코드를 고치지 않는다"가 중요한 이유는 단순하다. 이미 검증된 코드를 건드리면 회귀 버그(regression)가 생길 위험이 있다. 새 코드만 추가하면 기존 동작은 그대로 보존된다. OCP는 추상화와 다형성으로 달성한다.

위반 예시 — 늘어나는 분기문

필터 종류가 추가될 때마다 switch 문에 case를 덧붙이는 구조다.

enum class FilterType { GaussianBlur, Median, Sobel };

// 필터가 추가될 때마다 이 함수를 수정해야 한다 — OCP 위반
class ImageProcessor
{
public:
    ErrorCode ApplyFilter(Image& image, FilterType type)
    {
        switch (type)
        {
        case FilterType::GaussianBlur:
            // ... 가우시안 블러 처리
            break;
        case FilterType::Median:
            // ... 미디언 필터 처리
            break;
        case FilterType::Sobel:
            // ... 소벨 엣지 처리
            break;
        // 새 필터 추가 시 여기에 case 추가 → 기존 코드 수정
        }
        return ErrorCode::Ok;
    }
};

새 필터 하나를 추가하려면 검증이 끝난 ApplyFilter를 다시 열어야 한다. 분기가 늘어날수록 함수는 비대해지고, 한 필터를 고치다 다른 필터의 case를 건드릴 위험도 생긴다.

개선 예시 — 추상화로 확장 지점 만들기

필터를 인터페이스로 추상화하면, 새 필터는 인터페이스를 구현하는 새 클래스 추가만으로 끝난다. ImageProcessor는 다시 열 필요가 없다.

// 확장 지점이 되는 추상 인터페이스
class IFilter
{
public:
    virtual ~IFilter() = default;
    // Apply the filter to the given image in place.
    virtual ErrorCode Apply(Image& image) = 0;
};

// 기존 필터 구현
class GaussianBlurFilter : public IFilter
{
public:
    ErrorCode Apply(Image& image) override
    {
        // ... 가우시안 블러 처리
        return ErrorCode::Ok;
    }
};

class MedianFilter : public IFilter
{
public:
    ErrorCode Apply(Image& image) override
    {
        // ... 미디언 필터 처리
        return ErrorCode::Ok;
    }
};

// ImageProcessor는 구체 필터를 모른다 — 수정에 닫혀 있다
class ImageProcessor
{
public:
    ErrorCode ApplyFilter(Image& image, IFilter& filter)
    {
        return filter.Apply(image);
    }
};

// === 새 필터 추가: 기존 코드를 전혀 건드리지 않는다 ===
class SharpenFilter : public IFilter
{
public:
    ErrorCode Apply(Image& image) override
    {
        // ... 샤프닝 처리
        return ErrorCode::Ok;
    }
};

SharpenFilter를 추가했지만 IFilter, ImageProcessor, 기존 필터 클래스는 한 줄도 바뀌지 않았다. 확장에는 열려 있고(새 클래스 추가 가능), 수정에는 닫혀 있다(기존 클래스 불변). 이 구조가 곧 전략 패턴(Strategy Pattern)이다.

OCP 확장 구조 — 새 필터는 IFilter를 구현하는 클래스를 더할 뿐, 위쪽 클래스들은 그대로다.
"변할 부분"을 미리 찾아 추상화한다 OCP의 핵심은 "어디가 자주 바뀔지" 예측하는 것이다. 필터 종류처럼 계속 늘어날 게 뻔한 지점은 인터페이스로 뽑아 둔다. 반대로 거의 안 바뀌는 부분까지 추상화하면 비용만 든다.

LSP — 리스코프 치환 원칙

Liskov Substitution Principle. 바버라 리스코프(Barbara Liskov)의 이름을 딴 원칙으로, 자식 타입은 부모 타입을 대체할 수 있어야 한다는 내용이다. 부모 타입을 사용하는 코드에 자식 객체를 넣어도 프로그램의 동작이 깨지면 안 된다.

상속 관계가 문법적으로 성립한다고 해서 LSP를 만족하는 것은 아니다. 컴파일이 되더라도, 자식이 부모가 약속한 동작을 어기면 LSP 위반이다.

위반 예시 — 정사각형-직사각형 문제

"정사각형은 직사각형의 일종"이라는 수학적 직관 때문에 Square를 Rectangle의 자식으로 만드는 고전적 함정이다.

class Rectangle
{
public:
    virtual ~Rectangle() = default;
    virtual void SetWidth(int w)  { m_width = w; }
    virtual void SetHeight(int h) { m_height = h; }
    int GetArea() const { return m_width * m_height; }

protected:
    int m_width = 0;
    int m_height = 0;
};

// "정사각형은 직사각형이다" — 문법은 되지만 LSP를 깬다
class Square : public Rectangle
{
public:
    void SetWidth(int w) override  { m_width = w; m_height = w; }
    void SetHeight(int h) override { m_width = h; m_height = h; }
};

// Rectangle을 기대하고 쓰는 코드
void ResizeAndCheck(Rectangle& rect)
{
    rect.SetWidth(5);
    rect.SetHeight(4);
    // Rectangle이라면 면적은 반드시 20이어야 한다
    assert(rect.GetArea() == 20);  // Square를 넣으면 16 → 실패
}

ResizeAndCheck는 "너비와 높이를 따로 설정할 수 있다"는 Rectangle의 약속에 의존한다. 그런데 Square를 넣으면 SetHeight가 너비까지 바꿔 버려 면적이 16이 된다. 부모를 쓰던 코드가 자식 때문에 깨졌으니 LSP 위반이다.

LSP 위반 — 부모(Rectangle)를 기대하는 코드에 자식(Square)을 넣으면 면적 계약이 깨진다.

사전조건 강화·사후조건 약화 금지

LSP를 어기지 않으려면 자식은 부모와의 "계약(contract)"을 지켜야 한다. 두 가지 규칙으로 요약된다.

  • 사전조건을 강화하지 않는다 — 부모가 받아 주던 입력을 자식이 거부하면 안 된다. 부모가 0 이상의 너비를 받았다면 자식도 받아야 한다.
  • 사후조건을 약화하지 않는다 — 부모가 보장하던 결과를 자식이 보장하지 못하면 안 된다. Square는 "너비와 높이를 독립적으로 설정 후 면적은 W×H"라는 사후조건을 약화시켰다.

개선 예시 — 잘못된 상속을 끊는다

해법은 Square를 Rectangle의 자식으로 두지 않는 것이다. 둘 다 "도형"이라는 공통 추상에서 갈라지게 하고, 가변 크기 행동을 강요하지 않는다.

// 공통 추상 — "면적을 구할 수 있다"만 약속한다
class IShape
{
public:
    virtual ~IShape() = default;
    // Return the area of this shape.
    virtual int GetArea() const = 0;
};

// 직사각형 — 너비와 높이가 독립적이다
class Rectangle : public IShape
{
public:
    Rectangle(int width, int height)
        : m_width(width), m_height(height) {}

    void SetWidth(int w)  { m_width = w; }
    void SetHeight(int h) { m_height = h; }
    int GetArea() const override { return m_width * m_height; }

private:
    int m_width;
    int m_height;
};

// 정사각형 — 변이 하나뿐이다. Rectangle을 상속하지 않는다
class Square : public IShape
{
public:
    explicit Square(int side) : m_side(side) {}

    void SetSide(int side) { m_side = side; }
    int GetArea() const override { return m_side * m_side; }

private:
    int m_side;
};

이제 Rectangle의 "너비·높이 독립 설정" 계약을 Square가 상속하지 않으므로 깨질 일이 없다. IShape를 쓰는 코드는 GetArea()만 호출하므로, 어느 도형을 넣어도 안전하게 동작한다. "is-a 관계가 성립하는가"를 묻기 전에 "자식이 부모의 모든 계약을 지킬 수 있는가"를 먼저 물어야 한다.

세 원칙은 어떻게 연결되는가

SRP·OCP·LSP는 따로 노는 규칙이 아니라 하나의 흐름으로 이어진다.

  • SRP로 책임을 나눈다 — 먼저 클래스를 변경 이유 단위로 쪼개면, 무엇이 자주 바뀌는 부분인지 드러난다.
  • OCP로 확장 지점을 만든다 — 자주 바뀌는 책임을 인터페이스로 추상화하면, 그 부분이 확장 가능한 지점이 된다.
  • LSP로 다형성을 안전하게 만든다 — OCP가 만든 인터페이스 뒤의 구현체들이 계약을 지켜야, 다형성으로 갈아끼우는 동작이 깨지지 않는다.

즉 SRP가 "어디를 나눌지"를 알려주고, OCP가 "나눈 곳에 확장 구멍을 어떻게 뚫을지"를 알려주고, LSP가 "그 구멍에 끼우는 부품들이 지켜야 할 규격"을 알려준다. OCP 없이 LSP만 지키면 확장이 어렵고, LSP 없이 OCP만 추구하면 다형성이 언제든 깨질 수 있다. 세 원칙은 함께 쓰일 때 의미가 산다.

산업 SW 관점에서 보기

산업용 영상 처리 SDK에서 SOLID는 추상적인 이론이 아니라 실제 구조 결정이다.

OCP — IProcessBlock과 필터 확장

데이터 플로우 기반 블록 에디터에서 모든 처리 블록은 IProcessBlock 인터페이스를 구현한다. 새 필터나 검사 알고리즘을 추가할 때, 코어 라이브러리의 실행 엔진은 한 줄도 고치지 않는다. 인터페이스를 구현하는 새 블록 클래스를 더하면 끝이다. 이것이 플러그인 구조가 가능한 이유이며, 정확히 OCP의 적용이다.

// 코어가 정의한 확장 지점 — 블록 에디터의 모든 블록이 구현한다
class IProcessBlock
{
public:
    virtual ~IProcessBlock() = default;
    // Process the input image and produce the output.
    virtual ErrorCode Process(const Image& input, Image& output) = 0;
};

// 측정 솔루션이 추가하는 블록 — 코어 수정 없이 확장된다
class EdgeDistanceBlock : public IProcessBlock
{
public:
    ErrorCode Process(const Image& input, Image& output) override
    {
        // ... 엣지 기반 거리 측정
        return ErrorCode::Ok;
    }
};

SRP — 검사 블록의 책임 분리

검사 블록 하나가 영상 전처리, 특징 추출, 판정, 결과 시각화를 전부 떠안으면 SRP 위반이다. 판정 기준이 바뀔 때마다 전처리 코드까지 위험에 노출된다. 전처리·추출·판정을 각각의 클래스로 분리하면, 판정 임계값이 바뀌어도 판정 클래스만 손대면 된다. 각 단계를 GoogleTest로 독립 검증하기도 쉬워진다.

LSP는 블록 교체의 안전망이다 블록 에디터에서 사용자가 한 필터 블록을 다른 필터 블록으로 갈아끼울 수 있는 이유는, 모든 블록이 IProcessBlock의 계약(같은 입출력 규약, null 이미지 처리 규칙 등)을 지키기 때문이다. 어떤 블록이 이 계약을 어기면 플로우 전체가 예측 불가능해진다.

흔한 오해

"SRP = 함수 하나만"이라는 오해

앞서 다뤘듯 SRP의 "책임"은 함수 단위가 아니다. 메서드 하나짜리 클래스를 잔뜩 만드는 것은 SRP를 지키는 게 아니라 응집도를 깨는 것이다. 같은 이유로 함께 바뀌는 코드는 한곳에 있는 편이 낫다.

OCP를 위한 과한 추상화 "언젠가 확장될지 모르니까" 모든 클래스에 인터페이스를 붙이는 것은 OCP가 아니라 과잉 설계(over-engineering)다. 추상화 계층마다 코드를 읽고 따라가는 비용이 생긴다. 확장 가능성이 실제로 보이는 지점에만 추상화를 둔다. 한 번도 두 번째 구현체가 생기지 않을 인터페이스는 비용만 남긴다.

LSP를 "단순 상속 문제"로만 보는 오해

LSP 위반은 extends/: public 키워드만의 문제가 아니다. 인터페이스 구현(implements)에서도, 심지어 덕 타이핑에서도 발생한다. 핵심은 "어떤 타입을 기대하는 코드에 그 하위 타입을 넣었을 때 약속이 지켜지는가"다. 상속 문법 여부가 아니라 계약 준수 여부가 판단 기준이다. NotImplementedException을 던지는 오버라이드, 부모보다 좁은 입력만 받는 오버라이드는 모두 LSP 위반 신호다.

원칙위반 신호개선 방향
SRP한 클래스를 서로 다른 이유로 자꾸 수정한다 / 클래스 이름에 "And", "Manager"가 들어간다변경을 요구하는 주체별로 클래스를 분리한다
OCP기능 추가 때마다 switch/if-else 분기가 늘어난다 / 검증된 코드를 자꾸 다시 연다변하는 부분을 인터페이스로 추상화하고 구현을 추가한다
LSP오버라이드에서 예외를 던지거나 빈 구현을 둔다 / 타입 검사(dynamic_cast) 후 분기한다잘못된 상속을 끊고, 공통 추상은 지킬 수 있는 계약만 담는다
다음 글 예고 SOLID의 나머지 두 원칙 ISP(인터페이스 분리)와 DIP(의존 역전)는 "SOLID 원칙 (하)"에서 이어진다. ISP·DIP는 이 글에서 다룬 OCP의 추상화를 "어떻게 잘게 나누고, 어느 방향으로 의존시킬지"로 확장하는 원칙이다.
