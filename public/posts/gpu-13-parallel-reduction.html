리덕션이란

리덕션(reduction)은 배열 전체를 값 하나로 줄이는 연산이다. 합계, 최댓값, 최솟값, 평균, 내적(dot product)이 모두 리덕션이다. 비전 쪽에서는 영상 평균 밝기, ROI 픽셀 합, 두 영상 차이의 제곱합(SSD) 같은 계산이 여기에 해당한다.

CPU에서는 반복문 하나로 끝난다. 앞에서부터 하나씩 더하니 n번 순서대로 계산한다.

float SumCpu(const float* a, int n)
{
    float sum = 0.0f;
    for (int i = 0; i < n; ++i)
        sum += a[i];       // each step depends on the previous one
    return sum;
}

문제는 매 단계가 바로 앞 단계의 결과를 기다린다는 점이다. 이대로는 스레드 수천 개를 둘 자리가 없다. GPU에서는 덧셈의 결합 법칙을 사용해 계산 순서를 트리 모양으로 바꾼다. 짝을 지어 동시에 더하고, 그 결과끼리 다시 짝을 지어 더한다. 원소가 n개면 log2n 단계로 끝난다.

원소 8개를 3단계(log28)로 더하는 트리 리덕션. 같은 단계의 덧셈은 서로 기다리지 않으므로 동시에 실행할 수 있다

이 글은 NVIDIA의 Mark Harris가 정리한 유명한 자료 "Optimizing Parallel Reduction in CUDA"의 흐름을 따라간다. 가장 단순한 커널에서 시작해 한 단계씩 고치면서, 각 단계가 6편(shared memory, 뱅크 충돌)과 7편(워프, 메모리 결합)에서 다룬 원리 중 무엇을 적용한 것인지 짚는다. 리덕션 하나를 끝까지 최적화해 보면 CUDA 최적화의 주요 기법을 거의 다 한 번씩 써 보게 된다.

블록 단위 리덕션의 기본 구조

스레드 수백만 개가 한 번에 트리 하나를 만들 수는 없다. 블록끼리는 동기화 수단이 없기 때문이다(__syncthreads()는 블록 안에서만 동작한다). 그래서 리덕션은 두 층으로 나눈다.

층하는 일결과
1. 블록 안각 블록이 맡은 구간을 shared memory에 올리고 트리로 더함블록마다 부분합 1개
2. 블록 사이부분합 배열을 다시 리덕션 (커널을 한 번 더 실행하거나 atomicAdd)최종 값 1개

입력이 1,600만 개(224)이고 블록당 256개를 맡으면, 1층이 끝났을 때 부분합이 65,536개 남는다. 이것을 같은 커널로 한 번 더 줄이면 256개, 한 번 더 줄이면 1개가 된다. 아래에서 고치는 것은 모두 1층, 즉 블록 안 리덕션이다.

버전 1 - 인터리브 주소와 나머지 연산

가장 먼저 떠오르는 구현이다. stride를 1, 2, 4, ...로 키우면서, 인덱스가 2×stride의 배수인 스레드만 옆 원소를 더한다.

__global__ void Reduce1(const float* in, float* out, int n)
{
    extern __shared__ float s[];
    unsigned int tid = threadIdx.x;
    unsigned int i   = blockIdx.x * blockDim.x + threadIdx.x;

    s[tid] = (i < n) ? in[i] : 0.0f;   // pad with 0 outside the array
    __syncthreads();

    for (unsigned int stride = 1; stride < blockDim.x; stride *= 2)
    {
        if (tid % (2 * stride) == 0)   // only every (2*stride)-th thread works
            s[tid] += s[tid + stride];
        __syncthreads();
    }

    if (tid == 0)
        out[blockIdx.x] = s[0];        // one partial sum per block
}

// launch: shared memory = blockDim.x floats
Reduce1<<<numBlocks, 256, 256 * sizeof(float)>>>(d_in, d_partial, n);

결과는 맞지만 느리다. 원인은 두 가지다.

문제설명
워프 분기 (divergence)첫 단계에서 짝수 스레드만 일한다. 한 워프 32개 중 16개가 놀고, 단계가 지날수록 노는 스레드가 섞인 채로 워프 전체가 계속 실행된다 (7편)
나머지 연산 %GPU에서 정수 나눗셈과 나머지는 덧셈보다 훨씬 비싸다. 반복문 안에서 매번 실행된다

버전 2 - 분기 없애기와 뱅크 충돌

일하는 스레드를 앞쪽에 몰아 주면 분기가 줄어든다. 스레드 번호를 그대로 쓰지 않고, 스레드 번호로 일할 위치(index)를 계산한다.

for (unsigned int stride = 1; stride < blockDim.x; stride *= 2)
{
    unsigned int index = 2 * stride * tid;   // contiguous threads do the work
    if (index < blockDim.x)
        s[index] += s[index + stride];
    __syncthreads();
}

이제 첫 단계에서는 스레드 0~127이 일하고 128~255가 쉰다. 워프 단위로 보면 앞쪽 워프 4개는 전부 일하고 뒤쪽 워프 4개는 전부 쉬므로, 한 워프 안에서 갈라지는 일이 크게 줄어든다. %도 사라졌다.

대신 새 문제가 생긴다. stride가 커질수록 스레드들이 접근하는 주소 간격이 2, 4, 8, ...로 벌어진다. shared memory는 32개 뱅크로 나뉘어 있는데(6편), 간격이 2의 거듭제곱이면 여러 스레드가 같은 뱅크에 몰린다. 이것이 뱅크 충돌이다.

뱅크 충돌 계산 예 stride = 16이면 index = 32 × tid. 스레드 0, 1, 2, ...가 s[0], s[32], s[64], ...에 접근한다. 뱅크 번호는 (주소 / 4바이트) % 32이므로 모두 뱅크 0이다. 같은 뱅크 접근은 한 번에 하나씩 처리되므로 이 명령은 여러 번에 나뉘어 실행된다.

버전 3 - 순차 주소로 뱅크 충돌 없애기

방향을 뒤집는다. stride를 블록 크기의 절반에서 시작해 반씩 줄이고, 앞쪽 절반의 스레드가 뒤쪽 절반의 값을 더한다.

for (unsigned int stride = blockDim.x / 2; stride > 0; stride >>= 1)
{
    if (tid < stride)
        s[tid] += s[tid + stride];   // thread k reads s[k] and s[k + stride]
    __syncthreads();
}
순차 주소 방식. 일하는 스레드도, 읽는 주소도 항상 앞쪽에 연속으로 모인다

연속한 스레드가 연속한 주소를 읽으므로 32개 스레드가 32개 뱅크에 하나씩 접근한다. 분기 문제도 버전 2처럼 앞쪽 워프에 몰려 있다. 이 버전에서 남은 낭비는 첫 단계부터 스레드 절반이 논다는 점이다. 256개 스레드를 띄웠는데 첫 덧셈은 128개만 한다.

버전 4 - 불러오면서 한 번 더하기

스레드 절반이 노는 첫 단계를 없앤다. 블록 하나가 원소 2×blockDim개를 맡고, 각 스레드가 global memory에서 값 두 개를 읽어 더한 결과를 shared memory에 넣는다.

__global__ void Reduce4(const float* in, float* out, int n)
{
    extern __shared__ float s[];
    unsigned int tid = threadIdx.x;
    unsigned int i   = blockIdx.x * (blockDim.x * 2) + threadIdx.x;

    float v = 0.0f;
    if (i < n)              v  = in[i];
    if (i + blockDim.x < n) v += in[i + blockDim.x];   // first add happens during load
    s[tid] = v;
    __syncthreads();

    for (unsigned int stride = blockDim.x / 2; stride > 0; stride >>= 1)
    {
        if (tid < stride)
            s[tid] += s[tid + stride];
        __syncthreads();
    }
    if (tid == 0) out[blockIdx.x] = s[0];
}

// half as many blocks as before
int numBlocks = (n + 256 * 2 - 1) / (256 * 2);
Reduce4<<<numBlocks, 256, 256 * sizeof(float)>>>(d_in, d_partial, n);

블록 수가 절반으로 줄고, 모든 스레드가 처음부터 일한다. 두 번의 global 읽기는 각각 연속 주소라서 메모리 결합(coalescing, 7편)도 그대로 유지된다.

버전 5 - 마지막 워프 펼치기

stride가 32 이하로 내려가면 일하는 스레드가 워프 하나 안에 모두 들어간다. 이때부터는 블록 전체를 세우는 __syncthreads()가 낭비다. 반복문도 단계가 5개로 정해져 있으니 펼쳐 쓰면 된다.

예전 자료에서는 shared memory를 volatile로 선언하고 동기화 없이 6줄을 이어 쓰는 방식을 소개한다. 그런데 Volta(compute capability 7.0) 이후 GPU는 워프 안의 스레드도 각자 따로 스케줄될 수 있어서, 이 방식은 더 이상 안전하지 않다. 지금은 warp shuffle로 레지스터끼리 값을 주고받는 방식을 사용한다. shuffle은 15편에서 자세히 다루고, 여기서는 사용법만 본다.

// sum of v across the 32 lanes of a warp; lane 0 ends up with the total
__device__ __forceinline__ float WarpReduceSum(float v)
{
    for (int offset = 16; offset > 0; offset >>= 1)
        v += __shfl_down_sync(0xffffffff, v, offset);   // read v from lane (laneId + offset)
    return v;
}

__global__ void Reduce5(const float* in, float* out, int n)
{
    extern __shared__ float s[];
    unsigned int tid = threadIdx.x;
    unsigned int i   = blockIdx.x * (blockDim.x * 2) + threadIdx.x;

    float v = 0.0f;
    if (i < n)              v  = in[i];
    if (i + blockDim.x < n) v += in[i + blockDim.x];
    s[tid] = v;
    __syncthreads();

    // shared-memory tree only down to 64 elements
    for (unsigned int stride = blockDim.x / 2; stride > 32; stride >>= 1)
    {
        if (tid < stride)
            s[tid] += s[tid + stride];
        __syncthreads();
    }

    // last 64 -> 1 inside the first warp, no __syncthreads
    if (tid < 32)
    {
        v = s[tid] + s[tid + 32];
        v = WarpReduceSum(v);
        if (tid == 0) out[blockIdx.x] = v;
    }
}
volatile 펼치기 코드를 그대로 가져오지 않기 인터넷에 흔한 volatile float* vs = s; vs[tid] += vs[tid + 32]; vs[tid] += vs[tid + 16]; ... 코드는 Volta 이전 GPU의 워프 동작을 전제로 한다. 지금 GPU에서 쓰려면 줄마다 __syncwarp()를 넣어야 하므로, 처음부터 shuffle을 쓰는 편이 간단하고 빠르다.

버전 6 - 템플릿으로 반복문 모두 펼치기

블록 크기를 컴파일 시점에 알면 남은 반복문도 모두 펼칠 수 있다. 블록 크기를 템플릿 인자로 넘기면, 컴파일러가 조건이 거짓인 if를 통째로 지운다.

template <unsigned int BLOCK>
__global__ void Reduce6(const float* in, float* out, int n)
{
    extern __shared__ float s[];
    unsigned int tid = threadIdx.x;
    unsigned int i   = blockIdx.x * (BLOCK * 2) + threadIdx.x;

    float v = 0.0f;
    if (i < n)         v  = in[i];
    if (i + BLOCK < n) v += in[i + BLOCK];
    s[tid] = v;
    __syncthreads();

    if (BLOCK >= 1024) { if (tid < 512) s[tid] += s[tid + 512]; __syncthreads(); }
    if (BLOCK >= 512)  { if (tid < 256) s[tid] += s[tid + 256]; __syncthreads(); }
    if (BLOCK >= 256)  { if (tid < 128) s[tid] += s[tid + 128]; __syncthreads(); }
    if (BLOCK >= 128)  { if (tid <  64) s[tid] += s[tid +  64]; __syncthreads(); }

    if (tid < 32)
    {
        v = s[tid] + s[tid + 32];
        v = WarpReduceSum(v);
        if (tid == 0) out[blockIdx.x] = v;
    }
}

// the host picks the instantiation that matches the launch
switch (threads)
{
    case 1024: Reduce6<1024><<<blocks, 1024, 1024 * sizeof(float)>>>(d_in, d_out, n); break;
    case 512:  Reduce6<512> <<<blocks, 512,  512  * sizeof(float)>>>(d_in, d_out, n); break;
    case 256:  Reduce6<256> <<<blocks, 256,  256  * sizeof(float)>>>(d_in, d_out, n); break;
    case 128:  Reduce6<128> <<<blocks, 128,  128  * sizeof(float)>>>(d_in, d_out, n); break;
}

반복문의 비교, 증가, 분기 명령이 사라진다. 이런 명령은 한 번에 보면 작지만, 리덕션처럼 실제 계산(덧셈 1번)이 적은 커널에서는 반복문 관리 비용이 차지하는 비율이 크다.

버전 7 - 스레드 하나가 여러 원소 맡기

마지막 단계는 발상이 다르다. 지금까지는 스레드 하나가 원소 2개를 맡았다. 이번에는 블록 수를 GPU를 채울 만큼만 띄우고, 각 스레드가 grid-stride loop로 배열 전체를 훑으며 레지스터에 합계를 모은다. 트리 리덕션은 그 다음에 한 번만 한다.

__device__ __forceinline__ float BlockReduceSum(float v)
{
    __shared__ float warpSums[32];               // one slot per warp (max 1024/32)
    int lane   = threadIdx.x & 31;
    int warpId = threadIdx.x >> 5;

    v = WarpReduceSum(v);                        // 1) reduce inside each warp
    if (lane == 0) warpSums[warpId] = v;         // 2) lane 0 writes the warp total
    __syncthreads();

    int numWarps = (blockDim.x + 31) / 32;
    v = (threadIdx.x < numWarps) ? warpSums[lane] : 0.0f;
    if (warpId == 0) v = WarpReduceSum(v);       // 3) first warp reduces warp totals
    return v;                                    // valid in thread 0
}

__global__ void Reduce7(const float* __restrict__ in, float* out, size_t n)
{
    float sum = 0.0f;
    // grid-stride loop: each thread accumulates many elements in a register
    for (size_t i = blockIdx.x * blockDim.x + threadIdx.x;
         i < n;
         i += (size_t)blockDim.x * gridDim.x)
    {
        sum += in[i];
    }

    sum = BlockReduceSum(sum);
    if (threadIdx.x == 0)
        out[blockIdx.x] = sum;
}

// enough blocks to fill the GPU, not one per 512 elements
int numSMs;
cudaDeviceGetAttribute(&numSMs, cudaDevAttrMultiProcessorCount, 0);
Reduce7<<<numSMs * 4, 256>>>(d_in, d_partial, n);
Reduce7<<<1, 1024>>>(d_partial, d_out, numSMs * 4);   // second pass: partials -> 1

이 방식이 빠른 이유는 세 가지다.

이유설명
트리 단계가 한 번뿐shared memory 트리와 __syncthreads()가 블록당 한 번만 일어남. 나머지 덧셈은 모두 레지스터에서 처리
블록 수가 적음부분합이 수천 개가 아니라 SM 수의 몇 배 정도. 두 번째 패스가 아주 작아짐
메모리 대역폭에 집중반복문 안은 읽기와 덧셈뿐이라, GPU가 global memory 대역폭 한계에 가깝게 읽음

리덕션은 원소 하나당 덧셈 1번이 전부이므로 계산이 아니라 메모리 읽기 속도가 한계를 정한다(memory-bound). 그래서 최적화의 목표는 "GPU 메모리 대역폭에 얼마나 가깝게 읽느냐"다. 8편의 Nsight Compute에서 dram__throughput이 장치 최대치의 80~90%에 가까워지면 더 손댈 곳이 거의 없다고 보면 된다.

단계별 비교

Mark Harris의 원래 자료는 2007년 G80 GPU에서 원소 400만 개(222)를 더한 결과를 싣고 있다. 지금 GPU와 숫자는 다르지만, 단계마다 얼마나 좋아지는지 감을 잡기에는 충분하다.

블록 결과 합치기 - 두 번 실행과 atomicAdd

블록마다 나온 부분합을 합치는 방법은 두 가지다.

커널을 두 번 실행

버전 7 코드의 마지막 두 줄처럼 같은 커널을 블록 1개로 한 번 더 실행한다. 순서가 항상 같으므로 매번 같은 결과가 나온다. 실행 비용이 커널 한 번만큼 늘지만, 부분합이 수백 개라 두 번째 커널은 아주 짧다.

atomicAdd로 한 번에

__global__ void ReduceAtomic(const float* in, float* out, size_t n)
{
    float sum = 0.0f;
    for (size_t i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += (size_t)blockDim.x * gridDim.x)
        sum += in[i];

    sum = BlockReduceSum(sum);
    if (threadIdx.x == 0)
        atomicAdd(out, sum);     // one atomic per block, not per element
}

cudaMemsetAsync(d_out, 0, sizeof(float), stream);   // must reset before every run
ReduceAtomic<<<numSMs * 4, 256, 0, stream>>>(d_in, d_out, n);

커널 한 번으로 끝나고 코드도 짧다. atomic은 블록당 한 번이라 경합도 거의 없다. 다만 블록이 끝나는 순서는 매번 다르고, float 덧셈은 순서에 따라 마지막 자리가 달라지므로 실행할 때마다 결과가 아주 조금씩 달라질 수 있다. 회귀 테스트에서 결과를 비트 단위로 비교한다면 두 번 실행 방식을 쓴다. atomic 연산은 14편에서 더 자세히 다룬다.

합계 말고 다른 리덕션

트리 구조는 그대로 두고 연산만 바꾸면 된다. 조건은 결합 법칙이 성립하는 연산이어야 한다는 것이다. (a ⊕ b) ⊕ c = a ⊕ (b ⊕ c)가 성립해야 순서를 바꿔 묶어도 같은 결과가 나온다.

합계a + b0
곱a * b1

최댓값 위치 (argmax)(값, 인덱스) 쌍 중 값이 큰 쪽(-INFINITY, -1)

버전 1의 (i < n) ? in[i] : 0.0f에서 0이 바로 이 항등원이다. 최댓값 리덕션에서 0을 넣으면, 값이 모두 음수인 배열의 결과가 0으로 나오는 버그가 생긴다.

// argmax: carry the index along with the value
__device__ __forceinline__ void WarpArgMax(float& v, int& idx)
{
    for (int offset = 16; offset > 0; offset >>= 1)
    {
        float ov = __shfl_down_sync(0xffffffff, v,   offset);
        int   oi = __shfl_down_sync(0xffffffff, idx, offset);
        if (ov > v || (ov == v && oi < idx)) { v = ov; idx = oi; }   // tie -> smaller index
    }
}

실무에서는 CUB와 Thrust

원리를 알았다면, 실제 제품 코드에서는 직접 짠 커널보다 NVIDIA가 관리하는 라이브러리를 먼저 검토한다. CUDA Toolkit에 기본으로 들어 있고, GPU 세대마다 튜닝되어 있다.

#include <cub/cub.cuh>

// CUB: two calls - first asks how much temp memory, second does the work
void*  dTemp = nullptr;
size_t tempBytes = 0;
cub::DeviceReduce::Sum(dTemp, tempBytes, d_in, d_out, n, stream);   // query size
cudaMallocAsync(&dTemp, tempBytes, stream);
cub::DeviceReduce::Sum(dTemp, tempBytes, d_in, d_out, n, stream);   // run
cudaFreeAsync(dTemp, stream);

// Thrust: one line, but synchronous and returns the value to the host
#include <thrust/reduce.h>
#include <thrust/execution_policy.h>
float total = thrust::reduce(thrust::device, d_in, d_in + n, 0.0f);

CUB는 블록 안 리덕션(cub::BlockReduce)이나 워프 리덕션(cub::WarpReduce) 같은 부품도 제공하므로, 직접 짠 커널 안에서 BlockReduceSum 대신 끼워 쓸 수도 있다. 영상 처리 파이프라인에서는 임시 버퍼를 매 프레임 할당하지 말고, 처음 한 번 크기를 물어서 미리 잡아 둔다(12편의 버퍼 풀).

흔한 함정

분기 안의 __syncthreads() if (tid < stride) { s[tid] += ...; __syncthreads(); }처럼 동기화를 if 안에 넣으면, 일부 스레드만 배리어에 도착해서 커널이 멈추거나 결과가 깨진다. 동기화는 항상 블록의 모든 스레드가 지나가는 자리에 둔다.
블록 크기가 2의 거듭제곱이 아님 stride = blockDim.x / 2로 반씩 줄이는 코드는 블록 크기가 2의 거듭제곱이라고 가정한다. 블록 크기를 192 같은 값으로 바꾸면 일부 원소가 빠진다. 버전 7의 워프 단위 방식은 32의 배수면 동작한다.
float 합계의 정밀도 float는 유효 숫자가 약 7자리다. 값 수백만 개를 더하면 작은 값이 큰 합계에 묻혀 사라진다. 트리 리덕션은 CPU의 순차 합보다 오히려 오차가 작은 편이지만, 정확도가 중요하면 합계 변수만 double로 두거나 Kahan 보정 합을 쓴다. 8비트 영상 픽셀 합처럼 정수인 경우에는 unsigned long long으로 더하면 오차가 없다.
CPU 결과와 비트 단위로 비교 더하는 순서가 다르므로 GPU 합계와 CPU 합계는 마지막 몇 자리가 다를 수 있다. 테스트에서는 상대 오차(예: 1e-5)로 비교한다.
atomicAdd 결과 변수 초기화 atomicAdd 방식은 결과 변수를 0으로 만든 뒤 실행해야 한다. 프레임마다 반복 실행하는 파이프라인에서 cudaMemsetAsync를 빠뜨리면 합계가 계속 누적된다.
