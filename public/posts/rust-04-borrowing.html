참조와 빌림(Borrowing) — borrow checker

2026-06-25 약 8분 분량 Rust 시리즈
이 편에서 배우는 것 값을 옮기지(move) 않고도 빌려 쓰는 방법, 즉 참조를 다룬다. 읽기 전용 공유 참조 &T와 쓰기 가능한 가변 참조 &mut T의 차이를 본다. borrow checker가 컴파일 타임에 강제하는 핵심 규칙 — "가변 참조 1개 또는 공유 참조 여럿, 둘은 동시에 불가" — 이 어떻게 데이터 경쟁을 원천 차단하는지 이해한다. 마지막으로 같은 규칙 위에 서는 슬라이스를 다룬다.

왜 옮기지 않고 빌리나

앞 편에서 소유권을 봤다. String 같은 힙 데이터를 함수에 넘기면 소유권이 그쪽으로 이동(move)하고, 호출한 쪽에서는 더 이상 그 값을 쓸 수 없다. 그런데 함수에 "잠깐 읽기만" 시키고 싶을 때마다 소유권을 넘겼다 돌려받는 건 번거롭다.

그래서 Rust는 값을 옮기지 않고 빌려 쓰는 길을 둔다. 참조(&)를 넘기면 소유권은 그대로 둔 채 접근 권한만 빌려준다. 아래는 소유권을 넘기지 않고 길이만 읽는 예다.

fn main() {
    let s = String::from("hello");
    let len = calculate_length(&s); // 참조를 넘긴다. s의 소유권은 그대로다
    println!("'{}' 의 길이는 {}", s, len); // s를 계속 쓸 수 있다
}

fn calculate_length(s: &String) -> usize {
    s.len() // 빌린 값을 읽기만 한다
} // s는 참조일 뿐이라, 여기서 값이 버려지지 않는다

&s가 만드는 참조를 두고 "s를 빌렸다(borrow)"고 한다. 참조는 빌린 값을 가리킬 뿐 소유하지 않으므로, 참조가 스코프를 벗어나도 가리키던 값은 해제되지 않는다.

C++과 이렇게 다르다 — dangling 참조를 컴파일이 막는다 C++에서 지역 변수의 참조나 포인터를 반환하면 댕글링이 되지만, 컴파일러는 대개 경고에 그치고 런타임에 미정의 동작으로 터진다. Rust에서는 빌린 값보다 참조가 더 오래 살아남으려 하면 borrow checker가 컴파일 자체를 거부한다. "참조는 가리키는 값보다 오래 살 수 없다"가 타입 시스템 규칙이라, 댕글링 참조를 만들 방법이 없다.

공유 참조 &T

&T는 공유 참조(불변 참조)다. 빌린 값을 읽을 수만 있고 바꿀 수는 없다. 핵심 성질은 "여럿이 동시에 가능"이다 — 같은 값을 가리키는 공유 참조는 몇 개든 함께 존재할 수 있다. 아무도 쓰지 않으니 서로 방해하지 않기 때문이다.

fn main() {
    let v = vec![10, 20, 30];

    let a = &v; // 공유 참조 1
    let b = &v; // 공유 참조 2 — 동시에 여럿 OK

    println!("{}", a[0]); // 10
    println!("{}", b[2]); // 30
    println!("합계 = {}", sum(&v)); // 또 빌려서 읽어도 된다
}

fn sum(nums: &Vec<i32>) -> i32 {
    let mut total = 0;
    for n in nums { // &Vec를 순회하면 각 원소는 &i32로 빌려진다
        total += n;
    }
    total
}

공유 참조를 통해서는 값을 수정할 수 없다. 예컨대 nums.push(40) 같은 변경 메서드는 &Vec<i32>로는 호출되지 않는다. 읽기 전용이라는 점이 타입에 박혀 있어서, 실수로 변경하는 코드는 컴파일되지 않는다.

가변 참조 &mut T

값을 빌려서 바꾸고 싶으면 가변 참조 &mut T를 쓴다. 단, 원본이 mut로 선언돼 있어야 가변으로 빌릴 수 있다.

fn main() {
    let mut s = String::from("hello"); // 원본이 mut여야 한다
    append_world(&mut s); // 가변으로 빌려준다
    println!("{}", s); // hello world
}

fn append_world(s: &mut String) {
    s.push_str(" world"); // 빌린 값을 직접 수정한다
}

가변 참조에는 강한 제약이 하나 붙는다. 어떤 값에 대한 가변 참조는 한 시점에 단 하나만 존재할 수 있고, 그 동안에는 공유 참조도 함께 둘 수 없다. 즉 "쓰는 사람이 있으면 그 사람만 접근"이다. 아래는 컴파일되는 올바른 패턴 — 가변 참조의 사용이 끝난 뒤에 다시 빌린다.

fn main() {
    let mut n = 1;

    {
        let r = &mut n; // 가변 참조 — 이 블록 안에서만 산다
        *r += 10; // 역참조로 값을 바꾼다
    } // 여기서 r의 빌림이 끝난다

    let s = &n; // 가변 빌림이 끝났으니 이제 공유 참조 OK
    println!("{}", s); // 11
}

*r처럼 *로 참조를 따라가 값에 접근하는 것을 역참조(dereference)라 한다. 가변 참조의 빌림 범위가 블록으로 끝나기 때문에, 그 뒤의 공유 참조는 규칙을 어기지 않는다.

빌림 규칙과 borrow checker

지금까지 본 것을 한 문장으로 모으면 빌림 규칙이 된다. 컴파일러의 borrow checker가 이 규칙을 강제한다.

  1. 한 값에 대해 가변 참조 1개를 두거나, 공유 참조 여럿을 둘 수 있다 — 그러나 둘을 동시에는 안 된다.
  2. 모든 참조는 가리키는 값보다 오래 살 수 없다 (댕글링 금지).

이 규칙의 효과가 데이터 경쟁(data race)의 원천 차단이다. 데이터 경쟁은 (1) 둘 이상이 같은 데이터에 접근하고, (2) 그중 적어도 하나가 쓰기이며, (3) 동기화가 없을 때 생긴다. "쓰기가 있으면 단독 접근"이라는 빌림 규칙은 이 조건을 구조적으로 불가능하게 만든다. 아래는 규칙 위반이라 컴파일되지 않는 예다.

fn main() {
    let mut v = vec![1, 2, 3];

    let r = &v;        // 공유 참조
    v.push(4);          // 컴파일 에러: 공유 빌림이 살아 있는데 가변 접근(push)
    println!("{:?}", r);
}

push는 내부적으로 &mut v를 필요로 하는데, 그 시점에 r이라는 공유 빌림이 아직 살아 있어 규칙 1을 어긴다. 컴파일러는 이를 거부한다. 순서를 바꿔, 공유 참조를 다 쓴 뒤에 변경하면 통과한다.

fn main() {
    let mut v = vec![1, 2, 3];

    let r = &v;
    println!("{:?}", r); // 여기서 r의 마지막 사용 — 빌림이 끝난다

    v.push(4); // 이제 가변 접근 OK
    println!("{:?}", v); // [1, 2, 3, 4]
}

참조의 빌림은 선언 지점부터 마지막 사용 지점까지만 살아 있다(non-lexical lifetimes). 그래서 r을 마지막으로 쓴 줄 이후에는 가변 접근이 자유롭다.

C++과 이렇게 다르다 — aliasing과 const correctness를 컴파일이 강제 C++의 const T&는 "이 참조로는 못 바꾼다"는 약속이지만, 같은 객체를 다른 비-const 경로가 동시에 바꾸는 것(aliasing)을 막지 못한다. 그래서 한 스레드가 읽는 도중 다른 스레드가 쓰는 데이터 경쟁이 컴파일을 통과해 버린다. Rust의 &T/&mut T는 단순한 약속이 아니라 borrow checker가 강제하는 배타성 규칙이다. 가변 접근이 있으면 그 경로만 유일하므로, 같은 데이터에 대한 읽기-쓰기 동시 접근 자체가 컴파일되지 않는다. const correctness가 "지키면 좋은 관례"가 아니라 타입 시스템의 일부인 셈이다.

슬라이스

슬라이스(slice)는 컬렉션 전체가 아닌 연속된 일부를 빌리는 참조다. 소유하지 않고 "어디부터 어디까지"를 가리키므로, 앞서 본 빌림 규칙을 그대로 따른다. 문자열 슬라이스의 타입은 &str, 배열·벡터 슬라이스의 타입은 &[T]다.

fn main() {
    let s = String::from("hello world");

    let hello = &s[0..5];  // "hello" — 0번부터 5번 직전까지
    let world = &s[6..11]; // "world"

    println!("{} / {}", hello, world);
    println!("첫 단어: {}", first_word(&s)); // hello
}

// &str을 받으면 String과 문자열 리터럴 둘 다 받을 수 있다
fn first_word(s: &str) -> &str {
    let bytes = s.as_bytes();
    for (i, &b) in bytes.iter().enumerate() {
        if b == b' ' {
            return &s[0..i]; // 공백 직전까지를 빌려서 반환
        }
    }
    &s[..] // 공백이 없으면 전체
}

슬라이스가 빌림이라는 점은 안전성으로 이어진다. 슬라이스가 원본을 공유 참조로 빌리고 있는 동안에는, 원본을 가변으로 바꾸려는 시도가 빌림 규칙에 걸려 컴파일되지 않는다.

fn main() {
    let mut s = String::from("hello world");
    let word = first_word(&s); // s를 공유 참조로 빌리는 슬라이스
    // s.clear(); // 만약 여기서 s를 비우려 하면 컴파일 에러: word가 아직 s를 빌리는 중
    println!("{}", word); // word의 마지막 사용
    s.clear(); // word를 다 썼으니 이제 변경 OK
    println!("len = {}", s.len()); // 0
}

fn first_word(s: &str) -> &str {
    match s.find(' ') {
        Some(i) => &s[..i],
        None => s,
    }
}

배열·벡터도 같다. &v[1..3]은 &[T] 타입의 슬라이스이고, 함수 인자를 &[i32]로 받으면 배열이든 벡터든 그 일부든 모두 받아들일 수 있어 더 일반적인 API가 된다.

fn sum_slice(nums: &[i32]) -> i32 {
    let mut total = 0;
    for &n in nums { // &n으로 패턴 매칭해 i32 값을 꺼낸다
        total += n;
    }
    total
}

fn main() {
    let arr = [1, 2, 3, 4, 5];
    let v = vec![10, 20, 30];

    println!("{}", sum_slice(&arr));      // 15 — 배열 전체
    println!("{}", sum_slice(&arr[1..4])); // 9 — 부분 슬라이스
    println!("{}", sum_slice(&v));        // 60 — 벡터도 같은 함수로
}

정리와 주의

  • 빌림은 소유권을 옮기지 않는다 — &로 접근만 빌려주고 원본은 호출한 쪽에 남는다.
  • 두 종류의 참조 — &T는 읽기 전용·여럿 동시 가능, &mut T는 쓰기 가능·단독으로만.
  • 핵심 규칙 — 한 값에 가변 참조 1개 또는 공유 참조 여럿, 둘은 동시에 불가. 이 배타성이 데이터 경쟁을 컴파일 타임에 차단한다.
  • 슬라이스는 컬렉션의 일부를 빌리는 참조(&str, &[T])이고, 같은 빌림 규칙을 따른다.
  • 주의 — 빌림은 마지막 사용 지점까지만 산다. 에러 메시지가 가리키는 "빌림이 살아 있는 지점"을 보면 원인이 보인다. C++ 경험으로 생긴 aliasing 습관은 Rust에서 컴파일러가 먼저 잡아 준다.
