SOLID의 나머지 두 글자

앞 글에서 SRP·OCP·LSP를 다뤘다. 단일 책임으로 변경 이유를 하나로 묶고(SRP), 확장에는 열고 변경에는 닫으며(OCP), 자식이 부모를 안전하게 대체하도록(LSP) 만드는 원칙들이었다. 이번 글은 마지막 두 글자 ISP와 DIP를 다룬다.

이 두 원칙은 모두 의존성을 다룬다. ISP는 "무엇에 의존하는가"의 크기를 줄이고, DIP는 "어느 방향으로 의존하는가"를 뒤집는다. 둘은 따로 노는 규칙이 아니라 함께 맞물려 동작한다. 작게 쪼갠 인터페이스(ISP)에 의존(DIP)할 때 설계가 가장 유연해진다.

SOLID는 목적이 아니라 수단이다 다섯 원칙 모두 "변경에 강한 코드"라는 하나의 목표를 향한다. 원칙을 외우는 것보다, 각 원칙이 어떤 변경을 쉽게 만드는지 이해하는 것이 중요하다.

ISP — 인터페이스 분리 원칙

Interface Segregation Principle. 클라이언트는 자신이 사용하지 않는 메서드에 의존하면 안 된다. 하나의 거대한 인터페이스보다, 역할별로 잘게 나뉜 여러 개의 작은 인터페이스가 낫다.

뚱뚱한 인터페이스의 문제

이미징 라이브러리의 처리 블록을 예로 든다. "블록이라면 당연히 이 정도는 해야지" 하는 마음으로 메서드를 한 인터페이스에 다 몰아넣으면 fat interface가 된다.

// 위반 — 모든 책임을 한 인터페이스에 몰아넣음
class IImageBlock
{
public:
    virtual ~IImageBlock() = default;
    virtual ErrorCode Process(const Image& in, Image& out) = 0;
    virtual ErrorCode StartLiveView() = 0;     // 카메라 블록만 필요
    virtual ErrorCode StopLiveView() = 0;      // 카메라 블록만 필요
    virtual ErrorCode SaveToFile(const std::string& path) = 0;  // 저장 블록만 필요
    virtual nlohmann::json Serialize() const = 0;
};

// GaussianBlur는 라이브뷰도, 파일 저장도 하지 않는데
// 인터페이스가 강제하니 빈 메서드로 채울 수밖에 없다.
class GaussianBlur : public IImageBlock
{
public:
    ErrorCode Process(const Image& in, Image& out) override;
    ErrorCode StartLiveView() override { return ErrorCode::NotSupported; } // 의미 없음
    ErrorCode StopLiveView()  override { return ErrorCode::NotSupported; } // 의미 없음
    ErrorCode SaveToFile(const std::string&) override { return ErrorCode::NotSupported; } // 의미 없음
    nlohmann::json Serialize() const override;
};

문제는 빈 메서드만이 아니다. IImageBlock에 카메라 관련 메서드가 추가되면, 카메라와 무관한 GaussianBlur까지 다시 컴파일된다. 클라이언트가 쓰지도 않는 메서드 때문에 결합이 생기는 것이다.

역할별로 작게 분리

인터페이스를 "이 역할을 쓰는 클라이언트는 누구인가" 기준으로 쪼갠다. 각 구현체는 자신이 실제로 수행하는 역할만 골라서 구현한다.

// 개선 — 역할별로 작은 인터페이스로 분리
class IProcessBlock
{
public:
    virtual ~IProcessBlock() = default;
    virtual ErrorCode Process(const Image& in, Image& out) = 0;
};

class ILiveSource
{
public:
    virtual ~ILiveSource() = default;
    virtual ErrorCode StartLiveView() = 0;
    virtual ErrorCode StopLiveView() = 0;
};

class ISerializable
{
public:
    virtual ~ISerializable() = default;
    virtual nlohmann::json Serialize() const = 0;
};

// 블러는 처리와 직렬화만 한다. 라이브뷰 메서드에 의존하지 않는다.
class GaussianBlur : public IProcessBlock, public ISerializable
{
public:
    ErrorCode Process(const Image& in, Image& out) override;
    nlohmann::json Serialize() const override;
};

// 카메라 블록만 라이브 소스 역할을 더 가진다.
class CameraBlock : public IProcessBlock, public ILiveSource, public ISerializable
{
public:
    ErrorCode Process(const Image& in, Image& out) override;
    ErrorCode StartLiveView() override;
    ErrorCode StopLiveView() override;
    nlohmann::json Serialize() const override;
};

이제 라이브뷰만 다루는 코드는 ILiveSource*만 받으면 된다. GaussianBlur는 라이브뷰 인터페이스를 아예 모르므로, 거기에 메서드가 추가돼도 영향이 없다.

분리 기준은 "구현체"가 아니라 "클라이언트"다 인터페이스를 나눌 때는 누가 그 메서드를 호출하는지를 본다. 같은 클라이언트가 항상 함께 쓰는 메서드는 한 인터페이스로 묶고, 서로 다른 클라이언트가 쓰는 메서드는 떼어낸다.

DIP — 의존성 역전 원칙

Dependency Inversion Principle. 두 가지를 말한다. 첫째, 고수준 모듈은 저수준 모듈에 의존하면 안 된다. 둘 다 추상화에 의존해야 한다. 둘째, 추상화는 세부사항에 의존하면 안 된다. 세부사항이 추상화에 의존해야 한다.

구체 클래스에 직접 의존하면

검사 파이프라인(고수준)이 특정 카메라 구현(저수준)을 직접 안다고 하자.

// 위반 — 고수준 모듈이 저수준 구체 클래스를 직접 안다
#include "VieworksCamera.h"   // 구체 클래스에 #include 의존

class InspectionPipeline
{
public:
    ErrorCode Run()
    {
        VieworksCamera cam;          // 구체 타입에 직접 의존
        Image frame;
        cam.Grab(frame);
        return Inspect(frame);
    }
private:
    ErrorCode Inspect(const Image& frame);
};

이 코드는 VieworksCamera 없이는 컴파일조차 안 된다. 다른 카메라로 바꾸려면 InspectionPipeline을 고쳐야 하고, 테스트에서 가짜 카메라를 끼울 수도 없다. 고수준 정책이 저수준 세부사항에 묶여 있다.

추상화에 의존하도록 뒤집기

ICamera 인터페이스를 두고, 고수준과 저수준이 모두 그것에 의존하게 한다. 의존성의 화살표가 저수준 구현 쪽이 아니라 추상화 쪽을 향하도록 "역전"시키는 것이다.

// 개선 — 고수준과 저수준이 모두 ICamera 추상화에 의존
class ICamera
{
public:
    virtual ~ICamera() = default;
    virtual ErrorCode Grab(Image& outFrame) = 0;
};

// 저수준 — 추상화를 구현한다 (세부사항이 추상화에 의존)
class VieworksCamera : public ICamera
{
public:
    ErrorCode Grab(Image& outFrame) override;
};

// 고수준 — 추상화에만 의존한다. 구체 카메라를 모른다.
class InspectionPipeline
{
public:
    explicit InspectionPipeline(ICamera& camera) : m_camera(camera) {}

    ErrorCode Run()
    {
        Image frame;
        const auto rc = m_camera.Grab(frame);   // 인터페이스로 호출
        if (rc != ErrorCode::Ok) return rc;
        return Inspect(frame);
    }
private:
    ErrorCode Inspect(const Image& frame);
    ICamera& m_camera;                            // 추상화에 의존
};

"역전"이라는 이름이 붙은 이유는 다이어그램으로 보면 분명해진다. 원래는 고수준이 저수준을 향해 의존하지만, 추상화를 사이에 두면 저수준의 의존 방향이 위로 뒤집힌다.

고수준 → 추상화 ← 저수준. 저수준 모듈의 의존 화살표가 위로 뒤집힌다.
"역전"의 진짜 의미 제어 흐름은 여전히 고수준 → 저수준으로 흐른다. 뒤집히는 것은 소스 코드의 의존 방향이다. 인터페이스를 누가 소유하느냐도 핵심인데, ICamera는 고수준 모듈 쪽에 두는 것이 정석이다. 그래야 저수준이 고수준의 요구에 맞춰 따라온다.

의존성 주입(Dependency Injection)

DIP는 "추상화에 의존하라"는 원칙이다. 그렇다면 그 추상화의 실제 구현체는 누가, 언제 넣어주는가? 객체가 자기 의존성을 스스로 new 하지 않고, 외부에서 받아오게 만드는 기법이 의존성 주입(DI)이다.

생성자 주입

가장 권장되는 방식. 객체가 생성되는 시점에 필요한 의존성을 모두 받는다. 생성만 되면 항상 유효한 상태가 보장된다.

class InspectionPipeline
{
public:
    // 생성자에서 의존성을 받는다. 이후 항상 유효하다.
    explicit InspectionPipeline(ICamera& camera)
        : m_camera(camera) {}
private:
    ICamera& m_camera;
};

VieworksCamera realCamera;
InspectionPipeline pipeline(realCamera);   // 외부에서 주입

세터 주입

생성 후 세터로 의존성을 넣거나 교체한다. 선택적 의존성이거나 런타임에 바꿔야 할 때 쓴다. 단점은 세터 호출 전까지 객체가 불완전하다는 것이다.

class InspectionPipeline
{
public:
    void SetCamera(ICamera& camera) { m_camera = &camera; }
private:
    ICamera* m_camera = nullptr;   // 세터 호출 전에는 비어 있음
};

인터페이스 주입

주입받는 메서드 자체를 인터페이스로 규정한다. "이 객체는 카메라를 받을 수 있다"는 능력을 인터페이스로 표현하는 방식이다. C++에서는 잘 쓰지 않고, 보통 생성자 주입으로 충분하다.

주입 방식주입 시점장점단점 / 적합한 곳
생성자 주입객체 생성 시생성 후 항상 유효, 불변 가능의존성 많으면 생성자 비대 / 필수 의존성
세터 주입생성 후 임의 시점런타임 교체, 선택적 의존성주입 전 불완전 상태 / 옵션 의존성
인터페이스 주입주입용 메서드 호출 시주입 능력을 명시적으로 표현보일러플레이트 많음 / C++에선 드묾

DI 컨테이너

의존성이 많아지면 "무엇을 무엇에 주입할지"를 손으로 엮는 코드가 길어진다. DI 컨테이너는 이 조립을 자동화하는 도구다. 어떤 인터페이스에 어떤 구현을 쓸지 등록해두면, 컨테이너가 객체 그래프를 알아서 만들어준다. C#의 Microsoft.Extensions.DependencyInjection이 대표적이다.

DIP와 DI는 다르다 DIP는 "추상화에 의존하라"는 설계 원칙이고, DI는 그 의존성을 외부에서 넣어주는 구현 기법이다. DI 컨테이너는 DI를 편하게 해주는 도구일 뿐이다. 컨테이너 없이 생성자 인자만으로도 DI는 완벽히 성립하고, DIP도 지킬 수 있다. 셋을 같은 말로 쓰면 안 된다.

ISP와 DIP의 연결

두 원칙은 한 쌍으로 움직인다. ISP로 인터페이스를 작게 정의하고, DIP로 그 작은 인터페이스에 의존한다.

만약 인터페이스가 뚱뚱하면(ISP 위반), 그 인터페이스에 의존하는 고수준 모듈은 자기가 쓰지도 않는 메서드까지 끌고 들어온다. DIP를 지켜 추상화에 의존했더라도, 그 추상화 자체가 비대하면 의존성을 줄인 효과가 반감된다.

// ISP — 검사에 필요한 최소 역할만 인터페이스로 정의
class IFrameSource
{
public:
    virtual ~IFrameSource() = default;
    virtual ErrorCode Grab(Image& outFrame) = 0;   // 딱 이것만 필요
};

// DIP — 고수준 모듈은 그 작은 인터페이스에만 의존
class InspectionPipeline
{
public:
    explicit InspectionPipeline(IFrameSource& source)
        : m_source(source) {}
private:
    IFrameSource& m_source;   // 작은 추상화에 의존
};

// 카메라든 파일 리더든 IFrameSource만 구현하면 주입할 수 있다.
class VieworksCamera : public ICamera, public IFrameSource { /* ... */ };
class ImageFileReader : public IFrameSource { /* ... */ };

InspectionPipeline은 카메라의 라이브뷰·노출 설정 같은 메서드를 전혀 모른다. 오직 Grab 한 줄짜리 인터페이스에만 의존한다. 작게 쪼갠 덕분에(ISP) 의존이 가벼워지고, 추상화에 의존한 덕분에(DIP) 구현체를 자유롭게 갈아끼울 수 있다.

SOLID 5원칙 전체 정리

두 글에 걸쳐 다룬 다섯 원칙을 한 표로 모은다.

약자원칙한 줄 요약주로 막는 문제
SRP단일 책임 원칙클래스의 변경 이유는 하나여야 한다한 변경이 여러 곳을 건드림
OCP개방-폐쇄 원칙확장에는 열고 변경에는 닫는다기능 추가 때마다 기존 코드 수정
LSP리스코프 치환 원칙자식은 부모를 안전하게 대체해야 한다상속이 다형성을 깨뜨림
ISP인터페이스 분리 원칙안 쓰는 메서드에 의존하지 않게 한다뚱뚱한 인터페이스가 불필요한 결합 유발
DIP의존성 역전 원칙고수준·저수준 모두 추상화에 의존한다고수준 정책이 저수준 세부사항에 묶임

다섯 원칙은 따로 쓰는 도구가 아니라 함께 작동한다. SRP로 책임을 나누면 자연스럽게 작은 인터페이스(ISP)가 나온다. 그 인터페이스에 의존(DIP)하면 새 구현을 끼우는 확장(OCP)이 가능해진다. 그 구현이 부모를 제대로 대체(LSP)해야 확장이 안전하다. 결국 SOLID 전체가 만드는 것은 "한 곳을 고쳐도 다른 곳이 무너지지 않는 설계" 하나다.

원칙은 트리거가 있을 때 적용한다 처음부터 다섯 원칙을 모두 적용하려 들면 과설계가 된다. 같은 코드를 두 번째 고치게 됐을 때, 그 변경을 어렵게 만든 원인을 SOLID로 짚어 리팩토링하는 것이 현실적이다.

산업 SW 관점

머신비전 라이브러리에서 ISP·DIP가 어떻게 쓰이는지 본다.

카메라 SDK 추상화 (DIP)

코어 라이브러리는 특정 카메라 SDK를 직접 알면 안 된다. ICamera 인터페이스를 두고, 코어는 거기에만 의존한다. Vieworks·GigE·CoaXPress 카메라는 각각 ICamera를 구현하는 저수준 어댑터가 된다. 새 카메라를 지원할 때 코어 코드는 한 줄도 바뀌지 않는다.

// 코어는 ICamera만 안다. 어떤 SDK가 뒤에 있는지 모른다.
class CameraGrabBlock : public IProcessBlock
{
public:
    explicit CameraGrabBlock(std::shared_ptr<ICamera> camera)
        : m_camera(std::move(camera)) {}

    ErrorCode Process(const Image&, Image& out) override
    {
        return m_camera->Grab(out);
    }
private:
    std::shared_ptr<ICamera> m_camera;
};

검사 블록 인터페이스 분리 (ISP)

모든 처리 블록이 직렬화·파라미터 튜닝·미리보기를 다 해야 하는 것은 아니다. 역할별로 IProcessBlock, IConfigurable, IPreviewable, ISerializable로 쪼개면, 블록 에디터의 파라미터 패널은 IConfigurable만, 그래프 저장 코드는 ISerializable만 다루면 된다. 각 클라이언트가 자기 역할에만 의존한다.

테스트 시 mock 주입

DIP의 가장 실용적인 이득은 테스트다. ICamera를 구현하는 MockCamera를 만들어, 미리 준비한 이미지를 Grab이 반환하게 한다. 실제 카메라 하드웨어 없이 검사 파이프라인 전체를 단위 테스트할 수 있다.

// 테스트용 가짜 카메라 — 정해진 프레임을 그대로 돌려준다
class MockCamera : public ICamera
{
public:
    explicit MockCamera(Image fixture) : m_fixture(std::move(fixture)) {}

    ErrorCode Grab(Image& outFrame) override
    {
        outFrame = m_fixture;
        return ErrorCode::Ok;
    }
private:
    Image m_fixture;
};

// GoogleTest — 하드웨어 없이 파이프라인 검증
TEST(InspectionPipelineTest, DetectsDefectOnFixture)
{
    MockCamera cam(LoadTestImage("defect_sample.png"));
    InspectionPipeline pipeline(cam);

    EXPECT_EQ(pipeline.Run(), ErrorCode::DefectFound);
}
추상화가 곧 테스트 가능성이다 구체 클래스에 직접 의존한 코드는 그 클래스를 떼어낼 수 없어 테스트가 어렵다. DIP를 지킨 코드는 같은 인터페이스에 mock을 끼우는 것만으로 격리 테스트가 된다. "테스트하기 어렵다"는 신호는 대개 DIP 위반의 신호다.

흔한 오해

"DIP = DI 프레임워크 쓰기"라는 오해 DIP는 의존 방향에 관한 원칙이다. DI 컨테이너를 도입했다고 DIP가 지켜지는 것도 아니고, 컨테이너 없이 생성자 인자만 써도 DIP는 완벽히 성립한다. 프레임워크는 수단이지 원칙 그 자체가 아니다.
인터페이스를 무조건 잘게 쪼개기 ISP는 "최대한 작게"가 아니라 "클라이언트 기준으로 적절하게"다. 항상 함께 쓰이는 메서드를 메서드 하나당 인터페이스 하나로 쪼개면, 구현체가 인터페이스 십여 개를 상속하는 기형이 된다. 응집된 역할 단위로 묶는 것이 핵심이다.
추상화를 위한 추상화 구현체가 영원히 하나뿐일 게 분명한데도 "혹시 모르니" 인터페이스를 만드는 것은 비용만 늘린다. 간접 호출 한 단계, 파일 한 개, 읽을 때 점프 한 번이 공짜가 아니다. 추상화는 실제로 교체·확장·테스트 가능성이라는 이득이 보일 때 도입한다.
인터페이스만 만들면 DIP가 끝났다는 착각 ICamera를 만들어놓고도 고수준 모듈 안에서 new VieworksCamera()를 호출하면 의존은 그대로 남는다. 추상화를 정의하는 것과, 구체 타입을 생성 책임에서 떼어내 외부 주입으로 옮기는 것은 별개의 작업이다. 둘 다 해야 DIP가 완성된다.
