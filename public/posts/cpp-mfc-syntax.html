MFC(Microsoft Foundation Classes)는 Win32 API를 C++ 클래스로 감싼 라이브러리다. 1992년에 나왔고, 그때 C++에는 템플릿도 RTTI(dynamic_cast, typeid)도 제대로 없었다. 그래서 MFC는 지금 C++에서 언어가 해 주는 일을 매크로로 직접 만들어 둔 부분이 많다. MFC 코드가 낯설게 보이는 이유는 대부분 여기에 있다. 매크로가 무엇을 만들어 주는지만 알면 나머지는 평범한 C++이다.

이름 규칙

이름 앞부분만 보고도 무엇인지 알 수 있게 되어 있다.

모양뜻예
C로 시작클래스CWnd, CString, CMyDlg
m_로 시작멤버 변수m_hWnd, m_strName
Afx로 시작MFC 전역 함수AfxMessageBox, AfxBeginThread, AfxGetApp
On으로 시작메시지를 받는 함수(핸들러)OnPaint, OnBnClickedOk
대문자 매크로코드를 만들어 주는 매크로DECLARE_DYNAMIC, BEGIN_MESSAGE_MAP
afx_msg"메시지 핸들러"라는 표시. 빈 매크로라 컴파일에는 영향 없음afx_msg void OnPaint();

변수 이름 앞에는 헝가리안 표기가 붙는 경우가 많다. n(정수), b(BOOL), str(CString), p(포인터), h(핸들), lpsz(문자열 포인터), dw(DWORD) 정도만 알아 두면 읽는 데 지장이 없다.

Win32에서 온 타입 이름도 함께 나온다.

타입실제
BOOL, TRUE, FALSEint, 1, 0. C++ bool과 다른 타입
TCHAR, _T("...")유니코드 빌드면 wchar_t, L"...". 아니면 char
LPCTSTRconst TCHAR*
HWND, HDC, HBITMAPWin32 핸들. MFC 객체는 이 핸들을 안에 들고 있음
WPARAM, LPARAM, LRESULT메시지에 딸려 오는 값과 돌려주는 값. 64비트에서는 포인터 크기
UINT_PTR포인터 크기의 부호 없는 정수. 타이머 ID 등에 사용

클래스 계층

거의 모든 MFC 클래스는 CObject에서 시작한다. 내가 만드는 클래스(주황색)는 대개 아래 중 하나를 상속한다.

  • CObject런타임 클래스 정보, 직렬화, 디버그 덤프의 바탕
    • CCmdTarget메시지 맵을 가질 수 있음
      • CWinApp프로그램 하나에 객체 하나
        • CMyApp
      • CWnd창 하나. 안에 HWND를 들고 있음
        • CDialog / CDialogEx
          • CMyDlg
        • CFrameWnd메인 창 틀
        • CView문서 내용을 그리는 창
        • CButton, CEdit, CListCtrl ...컨트롤
      • CDocument데이터 보관
    • CDC그리기 도구 (HDC)
    • CGdiObjectCPen, CBrush, CFont, CBitmap

CString, CRect, CPoint 같은 값 타입은 CObject를 상속하지 않는다. 가볍게 복사해서 사용하는 타입이라 런타임 정보가 필요 없기 때문이다.

런타임 클래스 정보 - DYNAMIC, DYNCREATE, SERIAL

MFC 코드에서 가장 낯선 부분이다. 목적은 하나다. 프로그램이 돌아가는 중에 "이 객체가 실제로 어떤 클래스인가"를 알아내는 것. 지금 C++라면 dynamic_cast와 typeid로 하는 일을, MFC는 클래스마다 정보 구조체를 하나씩 만들어 두는 방식으로 해결했다. 그 구조체가 CRuntimeClass다.

CRuntimeClass 구조체

클래스 하나당 이 구조체가 static 변수로 딱 하나 생긴다. 주요 멤버는 이렇다.

struct CRuntimeClass
{
    LPCSTR   m_lpszClassName;    // "CMyView" 같은 클래스 이름 문자열
    int      m_nObjectSize;      // sizeof(CMyView)
    UINT     m_wSchema;          // 직렬화 버전 번호 (SERIAL일 때)
    CObject* (PASCAL* m_pfnCreateObject)();  // 객체를 만드는 함수 (DYNCREATE일 때)
    CRuntimeClass* m_pBaseClass; // 부모 클래스의 CRuntimeClass  ← 상속 관계

    CObject* CreateObject();
    BOOL IsDerivedFrom(const CRuntimeClass* pBaseClass) const;
};

핵심은 m_pBaseClass다. 부모의 정보를 가리키고, 부모는 또 그 부모를 가리킨다. 그래서 정보 구조체들이 CMyView → CView → CWnd → CCmdTarget → CObject로 줄줄이 이어진다. "이 객체가 CWnd의 자식인가?"는 이 줄을 따라 올라가며 찾으면 된다.

네 가지 도구

사용하는 것넣는 곳하는 일
DECLARE_DYNAMIC(클래스)헤더, 클래스 선언 안런타임 정보(CRuntimeClass)가 들어갈 static 변수와 GetRuntimeClass() 선언을 만듦
IMPLEMENT_DYNAMIC(클래스, 부모)cpp, 함수 밖그 static 변수에 실제 값을 채움. 부모 이름을 같이 적어서 상속 관계를 담음
RUNTIME_CLASS(클래스)어디서든그 클래스의 런타임 정보를 가리키는 포인터(CRuntimeClass*)를 얻음. 객체 없이 클래스 이름만으로 얻는 것
객체->GetRuntimeClass()어디서든그 객체가 실제로 어떤 클래스인지 런타임 정보로 돌려줌. 가상 함수라 부모 포인터로 불러도 실제 클래스 정보가 나옴

RUNTIME_CLASS는 "클래스 쪽에서" 정보를 꺼내고, GetRuntimeClass()는 "객체 쪽에서" 정보를 꺼낸다. 둘을 비교하는 것이 기본 사용법이다.

매크로를 펼친 모습

매크로가 낯설면 펼쳐 보면 된다. 실제 정의는 조건부 컴파일 때문에 더 길지만, 줄이면 이 정도다.

// ── MyWnd.h ──
class CMyWnd : public CWnd
{
    DECLARE_DYNAMIC(CMyWnd)
    // 펼치면 대략:
    // public:
    //     static const CRuntimeClass classCMyWnd;
    //     virtual CRuntimeClass* GetRuntimeClass() const;
};

// ── MyWnd.cpp ──
IMPLEMENT_DYNAMIC(CMyWnd, CWnd)
// 펼치면 대략:
// const CRuntimeClass CMyWnd::classCMyWnd = {
//     "CMyWnd", sizeof(CMyWnd), 0xFFFF,
//     NULL,                    // 객체 생성 함수 없음 (DYNAMIC이라서)
//     RUNTIME_CLASS(CWnd),     // 부모 정보 ← 여기서 상속 관계가 연결됨
//     ...
// };
// CRuntimeClass* CMyWnd::GetRuntimeClass() const
// {   return RUNTIME_CLASS(CMyWnd);   }

// RUNTIME_CLASS(CMyWnd) 는 그냥 이것:
// ((CRuntimeClass*)(&CMyWnd::classCMyWnd))

펼쳐 보면 특별한 것이 없다. static 변수 하나, 그 주소를 돌려주는 가상 함수 하나다. 매크로는 이 반복 코드를 클래스마다 직접 쓰지 않게 해 줄 뿐이다.

실제 사용 - IsKindOf와 형 변환

void Handle(CWnd* pWnd)
{
    // 1) 이 객체가 CMyWnd이거나 그 자식인가?
    if (pWnd->IsKindOf(RUNTIME_CLASS(CMyWnd)))
    {
        CMyWnd* pMy = (CMyWnd*)pWnd;   // 안전한 형 변환
        pMy->DoSomething();
    }

    // 2) 위 두 줄을 한 번에: 아니면 NULL
    CMyWnd* p2 = DYNAMIC_DOWNCAST(CMyWnd, pWnd);
    if (p2) p2->DoSomething();

    // 3) 클래스 이름 출력 (디버깅용)
    TRACE(_T("실제 클래스: %S\n"), pWnd->GetRuntimeClass()->m_lpszClassName);

    // 4) 정확히 이 클래스인가? (자식 클래스는 제외)
    if (pWnd->GetRuntimeClass() == RUNTIME_CLASS(CMyWnd)) { /* ... */ }
}
MFC표준 C++ 대응
p->IsKindOf(RUNTIME_CLASS(C))dynamic_cast<C*>(p) != nullptr
DYNAMIC_DOWNCAST(C, p)dynamic_cast<C*>(p)
STATIC_DOWNCAST(C, p)static_cast<C*>(p) + 디버그 빌드에서 ASSERT로 검사
p->GetRuntimeClass()->m_lpszClassNametypeid(*p).name()

DYNAMIC, DYNCREATE, SERIAL의 차이

같은 계열 매크로가 세 단계로 있다. 아래 단계는 위 단계 기능을 모두 포함한다.

매크로 쌍추가되는 기능주로 쓰는 곳
DECLARE_DYNAMIC / IMPLEMENT_DYNAMIC클래스 판별 (IsKindOf)판별만 필요한 클래스
DECLARE_DYNCREATE / IMPLEMENT_DYNCREATE+ 이름만으로 객체 생성 (CreateObject()). 기본 생성자가 필요함문서, 뷰, 프레임 클래스
DECLARE_SERIAL / IMPLEMENT_SERIAL(클래스, 부모, 버전)+ 파일 저장, 읽기 (Serialize, CArchive)파일에 저장하는 데이터 클래스

DYNCREATE가 왜 필요한지는 문서/뷰 구조를 보면 바로 보인다. 프레임워크는 내 클래스 이름을 모르는데도 내 문서, 프레임, 뷰 객체를 직접 만들어야 한다. 그래서 클래스 대신 런타임 정보를 넘긴다.

// CMyApp::InitInstance() 안 - 마법사가 만들어 주는 코드
CSingleDocTemplate* pDocTemplate = new CSingleDocTemplate(
    IDR_MAINFRAME,
    RUNTIME_CLASS(CMyDoc),      // 프레임워크가 나중에 CreateObject()로 new 해 줌
    RUNTIME_CLASS(CMainFrame),
    RUNTIME_CLASS(CMyView));
AddDocTemplate(pDocTemplate);
자식 클래스에서 DECLARE_DYNAMIC을 빼먹으면 GetRuntimeClass()는 가상 함수라서, 자식에서 다시 만들지 않으면 부모의 것이 그대로 불린다. 그러면 CMyWnd 객체가 자기를 CWnd라고 대답한다. 컴파일 에러도 나지 않으므로, IsKindOf가 이상하게 동작하면 그 클래스에 매크로 쌍이 있는지부터 본다. 헤더에 DECLARE를 넣고 cpp에 IMPLEMENT를 빠뜨리면 이번에는 링크 에러(LNK2001)가 난다.

메시지 맵

Windows는 버튼 클릭, 그리기 요청, 타이머 같은 일을 전부 메시지(WM_PAINT, WM_TIMER, WM_COMMAND ...)로 창에 보낸다. 메시지 맵은 "이 메시지가 오면 이 함수를 불러라"를 적어 두는 표다. 가상 함수 수백 개를 두는 대신 클래스마다 필요한 것만 표에 적는 방식이다.

// ── MyDlg.h ──
#define WM_MY_DONE  (WM_APP + 1)       // 직접 만든 메시지 번호

class CMyDlg : public CDialogEx
{
protected:
    afx_msg void OnBnClickedStart();                     // 버튼 클릭
    afx_msg void OnTimer(UINT_PTR nIDEvent);             // WM_TIMER
    afx_msg LRESULT OnMyDone(WPARAM wParam, LPARAM lParam); // 직접 만든 메시지
    DECLARE_MESSAGE_MAP()
};

// ── MyDlg.cpp ──
BEGIN_MESSAGE_MAP(CMyDlg, CDialogEx)        // (내 클래스, 부모 클래스)
    ON_BN_CLICKED(IDC_BTN_START, &CMyDlg::OnBnClickedStart)
    ON_WM_TIMER()                           // 함수 이름이 OnTimer로 정해져 있음
    ON_MESSAGE(WM_MY_DONE, &CMyDlg::OnMyDone)
END_MESSAGE_MAP()                           // 항목 사이에 세미콜론 없음
항목 매크로받는 것함수 모양
ON_WM_PAINT(), ON_WM_TIMER(), ON_WM_SIZE() ...Windows 표준 메시지이름과 인자가 정해져 있음 (OnPaint(), OnSize(UINT, int, int))
ON_BN_CLICKED(ID, 함수)버튼 클릭void f()
ON_EN_CHANGE(ID, 함수)에디트 박스 내용 변경void f()
ON_COMMAND(ID, 함수)메뉴, 툴바 명령void f()
ON_NOTIFY(코드, ID, 함수)리스트 컨트롤 등의 알림void f(NMHDR*, LRESULT*)
ON_MESSAGE(번호, 함수)직접 만든 메시지LRESULT f(WPARAM, LPARAM)

표에 없는 메시지는 BEGIN_MESSAGE_MAP에 적은 부모 클래스의 표로 넘어간다. 그래서 두 번째 인자의 부모 이름이 실제 상속과 다르면 메시지가 엉뚱한 곳으로 간다.

직접 만드는 메시지 번호 WM_APP + n을 사용한다. WM_USER + n도 많이 보이지만, 이 범위는 일부 표준 컨트롤이 자기 메시지로 이미 사용하고 있어서 겹칠 수 있다.

대화상자와 DDX

대화상자 클래스에서는 화면의 컨트롤과 멤버 변수를 잇는 DDX(Dialog Data Exchange)가 핵심이다.

class CMyDlg : public CDialogEx
{
    enum { IDD = IDD_MYDLG };   // 리소스의 대화상자 ID
    CString   m_strName;        // 값 연결: 에디트 박스 글자
    int       m_nCount = 0;     // 값 연결: 숫자
    CListCtrl m_list;           // 컨트롤 연결: 리스트 컨트롤 객체 자체
protected:
    virtual void DoDataExchange(CDataExchange* pDX) override;
    virtual BOOL OnInitDialog() override;
};

void CMyDlg::DoDataExchange(CDataExchange* pDX)
{
    CDialogEx::DoDataExchange(pDX);
    DDX_Text(pDX, IDC_EDIT_NAME, m_strName);
    DDX_Text(pDX, IDC_EDIT_COUNT, m_nCount);
    DDV_MinMaxInt(pDX, m_nCount, 0, 100);       // 범위 검사 (DDV)
    DDX_Control(pDX, IDC_LIST, m_list);
}

BOOL CMyDlg::OnInitDialog()
{
    CDialogEx::OnInitDialog();      // 부모 호출 필수 - 여기서 DDX가 처음 돈다
    m_list.InsertColumn(0, _T("이름"), LVCFMT_LEFT, 120);
    return TRUE;                    // TRUE: 기본 컨트롤에 포커스를 줌
}
호출방향
UpdateData(TRUE)화면 → 멤버 변수 (사용자가 입력한 값을 읽음)
UpdateData(FALSE)멤버 변수 → 화면 (값을 바꾼 뒤 보여 줌)

방향이 헷갈리면 "TRUE = 저장(save and validate)"으로 기억한다. 대화상자를 띄우는 쪽은 DoModal()을 부르고, 돌아온 값이 IDOK인지 확인한다. OK 버튼을 누르면 OnOK()가 UpdateData(TRUE)를 부르고 닫히므로, 닫힌 뒤에도 dlg.m_strName으로 값을 읽을 수 있다.

CMyDlg dlg;
dlg.m_strName = _T("기본값");
if (dlg.DoModal() == IDOK)
    AfxMessageBox(dlg.m_strName);

자주 쓰는 타입 - CString, CRect, 컬렉션

CString

CString s = _T("Hello");
s.Format(_T("값=%d, 이름=%s"), 42, (LPCTSTR)name);   // printf 형식
int len = s.GetLength();
CString left = s.Left(3), mid = s.Mid(2, 4);
int pos = s.Find(_T("lo"));                           // 없으면 -1
s.Trim(); s.MakeUpper();
LPCTSTR p = s;                                        // 읽기용 포인터로 바로 변환

// Win32 함수가 버퍼에 직접 써야 할 때
LPTSTR buf = s.GetBuffer(MAX_PATH);
::GetModuleFileName(NULL, buf, MAX_PATH);
s.ReleaseBuffer();                                    // 길이를 다시 계산함. 빼먹으면 길이가 틀림

// 문자셋 변환
CStringA a = CT2A(s, CP_UTF8);                        // 유니코드 → UTF-8
CString  w = CA2T(a, CP_UTF8);                        // UTF-8 → 유니코드
Format에 CString을 그대로 넘기지 않기 %s 자리에 CString을 그대로 넣어도 대부분 동작하지만, 가변 인자라서 타입 검사가 없다. (LPCTSTR)str이나 str.GetString()으로 넘기는 습관을 들이면 안전하다.

CPoint, CSize, CRect

Win32의 POINT, SIZE, RECT를 상속해서 연산자와 편의 함수를 붙인 것이다. Win32 함수에 그대로 넘길 수 있다.

CRect rc;
GetClientRect(&rc);              // 창 안쪽 영역 (left, top은 항상 0)
int w = rc.Width(), h = rc.Height();
rc.DeflateRect(10, 10);          // 사방 10픽셀 줄이기
if (rc.PtInRect(point)) { /* 점이 안에 있음 */ }
CPoint c = rc.CenterPoint();

그리기 - CDC와 GDI 객체

그리기는 CDC(장치 컨텍스트) 객체를 통해 한다. 상황에 따라 만드는 종류가 다르다.

클래스쓰는 때
CPaintDC dc(this);OnPaint() 안에서만. 생성자와 소멸자가 BeginPaint/EndPaint를 대신 불러 줌
CClientDC dc(this);OnPaint() 밖에서 바로 그릴 때
CDC memDC; memDC.CreateCompatibleDC(&dc);메모리에 먼저 그린 뒤 한 번에 옮길 때(더블 버퍼링, 깜빡임 방지)
void CMyView::OnPaint()
{
    CPaintDC dc(this);

    CPen pen(PS_SOLID, 2, RGB(255, 0, 0));
    CPen* pOldPen = dc.SelectObject(&pen);   // 새 펜을 끼우고 원래 펜을 받아 둠

    dc.MoveTo(10, 10);
    dc.LineTo(200, 100);
    dc.TextOut(10, 120, _T("Hello MFC"));

    dc.SelectObject(pOldPen);                // 원래 펜으로 되돌림 - 빼먹으면 GDI 리소스가 샘
}

다시 그리라고 요청할 때는 OnPaint()를 직접 부르지 않고 Invalidate()를 부른다. 그러면 Windows가 적당한 때에 WM_PAINT를 보내 준다.

작업 스레드와 화면 갱신

MFC 창 객체(CWnd)는 자기를 만든 스레드에서만 다루는 것이 원칙이다. 작업 스레드는 결과를 메시지로 UI 스레드에 보내고, 화면은 UI 스레드가 갱신한다.

struct WorkParam { HWND hWnd; int nInput; };

UINT WorkThread(LPVOID pParam)            // 스레드 함수 모양: UINT f(LPVOID)
{
    WorkParam* p = (WorkParam*)pParam;
    int result = HeavyJob(p->nInput);
    ::PostMessage(p->hWnd, WM_MY_DONE, (WPARAM)result, 0);  // UI에 결과만 알림
    delete p;
    return 0;
}

void CMyDlg::OnBnClickedStart()
{
    auto* p = new WorkParam{ GetSafeHwnd(), 10 };   // CWnd* 말고 HWND를 넘김
    AfxBeginThread(WorkThread, p);
}

LRESULT CMyDlg::OnMyDone(WPARAM wParam, LPARAM)
{
    m_nCount = (int)wParam;
    UpdateData(FALSE);                    // 여기는 UI 스레드
    return 0;
}
CWnd* 대신 HWND를 넘기는 이유 MFC는 HWND와 CWnd 객체의 짝을 스레드마다 따로 관리한다. 다른 스레드에서 CWnd*로 함수를 부르면 디버그 빌드에서 ASSERT가 뜨거나 엉뚱한 임시 객체를 만지게 된다. 핸들(HWND)과 ::PostMessage는 어느 스레드에서 사용해도 안전하다. SendMessage는 UI 스레드가 받을 때까지 기다리므로, UI 스레드가 그 작업 스레드를 기다리고 있으면 서로 멈춘다.

증상원인
IsKindOf가 부모 클래스라고 대답함자식 클래스에 DECLARE_DYNAMIC/IMPLEMENT_DYNAMIC 쌍이 없음
LNK2001 classCMyXxx 관련 링크 에러헤더의 DECLARE만 있고 cpp의 IMPLEMENT가 없음
버튼을 눌러도 함수가 안 불림메시지 맵에 항목이 없거나 컨트롤 ID가 다름, 또는 BEGIN_MESSAGE_MAP의 부모 이름이 틀림
ON_WM_xxx 항목에서 컴파일 에러핸들러 함수 이름이나 인자가 정해진 모양과 다름 (예: OnTimer(UINT) → UINT_PTR)
입력한 값이 멤버 변수에 안 들어옴UpdateData(TRUE)를 안 부름, 또는 TRUE/FALSE 방향을 반대로 씀
OnInitDialog에서 컨트롤 접근 시 ASSERT부모 OnInitDialog()를 먼저 부르지 않아서 DDX_Control 연결 전
문자열 길이가 이상함GetBuffer 뒤에 ReleaseBuffer를 안 부름
오래 돌리면 그림이 깨지거나 멈춤SelectObject로 원래 GDI 객체를 되돌리지 않아 리소스가 샘
작업 스레드에서 화면 갱신 시 ASSERT, 멈춤다른 스레드에서 CWnd* 사용. HWND + PostMessage로 바꿈
릴리스에서만 동작이 빠짐ASSERT 안에 꼭 실행돼야 할 코드를 넣음. VERIFY로 바꿈
MFC 코드를 읽는 순서 헤더에서 상속한 부모 클래스와 DECLARE 매크로를 보고, cpp에서 메시지 맵을 먼저 본다. 메시지 맵이 그 창이 반응하는 일의 목록이고, 나머지 함수는 거기서 불리는 것들이다.
