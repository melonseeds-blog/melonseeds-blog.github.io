머신비전 SDK를 납품하면 언젠가는 반드시 이 연락을 받는다. "프로그램이 갑자기 죽습니다." 현장은 멀리 있고, 카메라·그래버·조명·PLC가 얽힌 장비를 우리가 직접 들여다볼 수도 없다. 재현은 안 되고, 로그는 크래시 직전에 끊긴다. 이때 원격에서 원인을 짚어낼 수 있는 거의 유일한 단서가 크래시 덤프(crash dump)다.

이 글은 "Windows 크래시 덤프 분석" 시리즈의 1편이다. 분석 도구(WinDbg)를 켜기 전에, 먼저 어떤 덤프를 어떻게 받아와야 분석이 가능한지를 정리한다. 잘못된 덤프를 받으면 아무리 좋은 도구가 있어도 분석이 막히기 때문에, 수집 단계의 설계가 절반이다.

크래시 덤프란 무엇인가

크래시 덤프는 프로세스가 비정상 종료되는 순간의 메모리 스냅샷이다. 그 시점의 스레드 목록, 각 스레드의 콜스택, 레지스터, 로드된 모듈(DLL) 목록, 그리고 설정에 따라 힙과 전역 데이터까지 파일 하나(.dmp)에 담는다. 디버거로 이 파일을 열면, 마치 그 순간으로 시간을 되감아 멈춰 둔 것처럼 프로세스 내부를 들여다볼 수 있다.

덤프가 중요한 이유는 단순하다. 현장 장애는 대부분 재현되지 않는다. 특정 카메라 모델, 특정 해상도, 특정 타이밍에서만 터지는 문제를 개발 PC에서 똑같이 만들어내는 것은 거의 불가능하다. 덤프는 "그 순간"을 통째로 박제해 두므로, 재현 없이도 크래시가 일어난 코드 위치와 직전 호출 경로를 복원할 수 있다.

로그와 덤프는 역할이 다르다 로그는 "무슨 일이 있었는지"를 시간 순으로 기록하지만, 정작 크래시가 나면 마지막 로그를 남기기 전에 프로세스가 죽어 단서가 끊긴다. 덤프는 "죽는 순간의 상태"를 통째로 보존한다. 둘은 경쟁 관계가 아니라 보완 관계이므로, 실무에서는 로그와 덤프를 함께 받아오는 것이 좋다.

사용자 모드 vs 커널 모드 덤프

덤프를 이해하려면 먼저 Windows의 두 실행 모드를 구분해야 한다. 덤프의 종류가 갈리는 가장 큰 분기점이 바로 여기다.

사용자 모드 덤프 (User-mode Dump)

특정 프로세스 하나의 메모리를 담은 덤프다. 우리 비전 SDK가 올라간 호스트 애플리케이션(예: 고객사의 검사 프로그램)이 죽으면, 그 프로세스만의 스냅샷을 뜬다. 머신비전 SDK 기술지원에서 마주치는 덤프는 99% 이 사용자 모드 덤프다. 응용 프로그램 크래시, 라이브러리 내부의 Access Violation, 핸들링되지 않은 예외 등이 모두 여기에 해당한다.

커널 모드 덤프 (Kernel-mode Dump)

운영체제 커널과 드라이버 영역의 메모리를 담은 덤프다. 흔히 말하는 블루스크린(BSOD)이 떴을 때 시스템이 자동으로 생성한다. 그래버 드라이버, 네트워크 드라이버, GPU 드라이버처럼 커널에서 동작하는 컴포넌트가 시스템 전체를 멈추게 한 경우에만 들여다본다. 사용자 애플리케이션 크래시는 커널 덤프로 분석하지 않는다.

덤프 종류 — 미니 vs 풀

사용자 모드 덤프 안에서도 "얼마나 많은 메모리를 담느냐"에 따라 종류가 갈린다. 이 선택이 파일 크기와 분석 가능 범위를 결정한다.

미니덤프 (Minidump)

"미니덤프"는 사실 파일 포맷의 이름이다. Windows의 MiniDumpWriteDump API가 생성하는 .dmp 파일을 통칭하며, 어떤 플래그를 주느냐에 따라 담기는 정보량이 크게 달라진다. 기본형 미니덤프는 스레드 목록, 각 스레드의 콜스택, 로드된 모듈 목록, 예외 정보 정도만 담아 크기가 수백 KB~수 MB로 작다.

이 정도만 있어도 "어디서 죽었는지(콜스택)"와 "어떤 예외인지(예외 코드)"는 대부분 알 수 있다. 그래서 1차 분류용으로는 기본 미니덤프로도 충분한 경우가 많다. 다만 힙·전역 변수·객체 내부 값은 담기지 않으므로, "왜 그 값이 들어왔는지"까지 파고들 수는 없다.

풀(Full / Complete) 사용자 덤프

프로세스가 커밋한 전체 메모리를 담은 덤프다. 정확히는 미니덤프 포맷에 MiniDumpWithFullMemory 플래그를 더한 것으로, 힙 전체와 지역·전역 변수, 객체 내부 데이터까지 들어 있다. 그래서 "버퍼 포인터가 가리키던 메모리의 실제 내용", "이미지 폭·높이 멤버 값" 같은 것을 직접 확인할 수 있다.

대신 크기가 프로세스 메모리 사용량만큼 커진다. 비전 프로그램은 대용량 이미지 버퍼를 잡고 있는 경우가 많아, 풀 덤프가 수백 MB~수 GB가 되기도 한다. 전송과 보관 비용이 그만큼 든다.

"미니덤프 = 작다"는 항상 참이 아니다 미니덤프는 포맷 이름일 뿐이라, MiniDumpWithFullMemory 플래그를 주면 전체 메모리를 담은 사실상의 풀 덤프가 된다. 작업 관리자의 "덤프 파일 만들기"와 ProcDump의 -ma 옵션이 바로 이 전체 메모리 덤프를 만든다. 파일 확장자가 .dmp라고 해서 다 작은 것은 아니라는 점을 기억해야 한다.

참고 — 커널 덤프의 하위 종류

커널 모드 덤프는 직접 다루는 일이 드물지만, 용어는 알아 두면 좋다. Windows는 다음 종류를 지원한다.

  • Active Memory Dump — 실제 활성 메모리만 담아, 가상화 호스트의 불필요한 게스트 메모리를 제외한다. 비교적 최신 방식이다.
  • Complete Memory Dump — 물리 메모리 전체를 담는다. 가장 크다.
  • Kernel Memory Dump — 커널 모드 메모리만 담는다.
  • Small Memory Dump (미니덤프) — %SystemRoot%\Minidump에 쌓이는 작은 커널 덤프다.
  • Automatic Memory Dump — Windows 8 이후 기본값으로, 커널 덤프를 뜨되 페이지 파일 크기를 OS가 알아서 관리한다.

덤프 생성 방법

이제 실제로 덤프를 만드는 방법이다. 상황에 따라 세 가지를 골라 쓴다. 가장 쉬운 것부터 가장 자동화된 것 순으로 정리한다.

방법 1 — 작업 관리자 (가장 쉬움)

프로세스가 죽지 않고 멈춰 있거나(행, hang), 아직 살아 있는 상태에서 덤프가 필요할 때 가장 빠른 방법이다. 추가 설치가 전혀 필요 없다.

  1. Ctrl + Shift + Esc로 작업 관리자를 연다.
  2. "세부 정보(Details)" 탭으로 이동한다.
  3. 대상 프로세스(예: 고객사 검사 프로그램의 .exe)를 우클릭한다.
  4. "덤프 파일 만들기(Create dump file)"를 선택한다.
  5. 완료되면 저장 경로가 표시된다. 보통 %LOCALAPPDATA%\Temp 아래에 <프로세스명>.DMP로 저장된다.

이 방법은 전체 메모리 덤프를 만든다. 즉 파일이 클 수 있다. 그리고 이미 크래시가 끝나 프로세스가 사라진 뒤에는 쓸 수 없다. "지금 멈춰 있어요" 상황에 적합하다.

32비트 / 64비트 작업 관리자 주의 64비트 Windows에서 32비트 프로세스를 기본 작업 관리자(64비트)로 덤프하면, 콜스택이 WOW64 계층으로 뒤섞여 분석이 까다로워질 수 있다. 32비트 애플리케이션이라면 C:\Windows\SysWOW64\taskmgr.exe(32비트 작업 관리자)로 덤프하거나, 비트 수를 맞춘 ProcDump를 쓰는 편이 깔끔하다.

방법 2 — ProcDump (Sysinternals)

ProcDump는 Microsoft Sysinternals의 단일 실행 파일 도구다. 설치가 필요 없고, "어떤 조건에서 덤프를 뜰지"를 명령줄로 지정할 수 있어 현장 자동 수집에 가장 유용하다. 핵심 옵션은 다음과 같다.

  • -ma — 전체 메모리(풀) 덤프를 생성한다. 사실상 거의 항상 붙인다.
  • -e — 처리되지 않은 예외(unhandled exception)가 발생하는 순간 덤프를 뜬다.
  • -t — 프로세스가 종료될 때 덤프를 뜬다.
  • -h — 창이 응답 없음(hung) 상태가 될 때 덤프를 뜬다.
  • -n — 덤프를 몇 개까지 뜰지 횟수를 지정한다(예: -n 3).
  • -accepteula — 최초 실행 시 뜨는 라이선스 동의를 자동 처리한다. 무인 수집에 필수다.
이미 실행 중인 프로세스를 PID로 지정해 즉시 풀 덤프
:: 작업 관리자의 PID 열에서 확인한 프로세스 ID가 4812라고 가정
procdump -accepteula -ma 4812 C:\dumps\
크래시(미처리 예외)가 나는 순간을 노려서 잡기
:: 프로세스 이름으로 감시하다가, 예외가 터지는 순간 덤프 생성
procdump -accepteula -ma -e MyVisionApp.exe C:\dumps\

:: 프로세스를 새로 띄우면서 감시 시작 (런처처럼 사용)
procdump -accepteula -ma -e -x C:\dumps\ MyVisionApp.exe
프로세스가 비정상 종료될 때 잡기
:: 종료 시점(-t)에 덤프 — "그냥 꺼져버린다"는 제보에 유용
procdump -accepteula -ma -t MyVisionApp.exe C:\dumps\

조건을 더 세밀하게 줄 수도 있다. 자원 사용량이 튀거나 응답이 멈추는 순간을 노릴 때 쓰는 옵션들이다.

조건부 수집 — CPU·메모리·예외 차수 기준
:: CPU 사용률이 80% 이상으로 10초간 지속되면 덤프 (성능 행 추적)
procdump -accepteula -ma -c 80 -s 10 MyVisionApp.exe C:\dumps\

:: 커밋 메모리가 2000MB를 넘으면 덤프 (메모리 누수 의심 시)
procdump -accepteula -ma -m 2000 MyVisionApp.exe C:\dumps\

:: 첫 번째 예외(first-chance)까지 잡으려면 -e 1
procdump -accepteula -ma -e 1 MyVisionApp.exe C:\dumps\

-e만 주면 처리되지 않은 예외(2차 예외)에서만 덤프를 뜨고, -e 1을 주면 첫 번째 예외(1차 예외)에서도 뜬다. 1차 예외에는 코드가 try/catch로 정상 처리하는 예외까지 포함되므로 덤프가 과하게 쏟아질 수 있다. 평소에는 -e(2차)로 두는 편이 안전하다. 1차·2차 예외의 차이는 분석 단계에서도 중요한데, 자세한 내용은 3편에서 다시 짚는다.

현장에는 -e 감시를 걸어 둔다 "언제 죽을지 모른다"가 가장 흔한 상황이다. 이때는 procdump -accepteula -ma -e로 프로세스를 감시하도록 걸어 두고, 크래시가 재현될 때까지 그대로 둔다. 예외가 터지는 바로 그 순간의 덤프가 자동으로 떨어지므로, 사람이 작업 관리자 앞을 지킬 필요가 없다.

방법 3 — WER LocalDumps 레지스트리 (무인 자동 수집)

가장 강력하고 손이 덜 가는 방법이다. Windows Error Reporting(WER)의 LocalDumps 기능을 레지스트리로 켜 두면, 그 PC에서 어떤 프로세스든 크래시가 날 때마다 OS가 알아서 덤프를 지정 폴더에 저장한다. 도구를 미리 띄워 둘 필요도, 사람이 지켜볼 필요도 없다. 고객사 PC에 한 번 심어 두면 그만이라 SDK 지원에서 특히 가치가 높다.

설정 위치는 다음 레지스트리 키다.

HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps

주요 값은 세 가지다.

값 이름형식의미
DumpFolderREG_EXPAND_SZ덤프를 저장할 폴더 경로
DumpTypeREG_DWORD0=커스텀, 1=미니덤프, 2=풀 덤프
DumpCountREG_DWORD폴더에 보관할 최대 덤프 개수(기본 10)
모든 프로세스 공통 설정 — 관리자 권한 명령 프롬프트에서
:: 저장 폴더 지정 (없으면 OS가 자동 생성)
reg add "HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps" /v DumpFolder /t REG_EXPAND_SZ /d "C:\CrashDumps" /f

:: 풀 덤프(2)로 설정
reg add "HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps" /v DumpType /t REG_DWORD /d 2 /f

:: 최대 20개까지 보관
reg add "HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps" /v DumpCount /t REG_DWORD /d 20 /f

프로세스별 설정 — 우리 앱만 콕 집어서

공통 설정은 PC의 모든 프로세스에 적용되어 엉뚱한 덤프까지 쌓일 수 있다. 우리 제품이 올라간 호스트 실행 파일만 대상으로 하고 싶다면, LocalDumps 아래에 실행 파일 이름으로 하위 키를 만들어 그쪽에만 값을 넣는다. 실행 파일 이름별 설정이 공통 설정보다 우선한다.

MyVisionApp.exe 에만 풀 덤프 설정 적용
:: 키 이름에 실행 파일 이름을 그대로 사용
reg add "HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\MyVisionApp.exe" /v DumpFolder /t REG_EXPAND_SZ /d "C:\CrashDumps" /f
reg add "HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\MyVisionApp.exe" /v DumpType /t REG_DWORD /d 2 /f
reg add "HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\MyVisionApp.exe" /v DumpCount /t REG_DWORD /d 10 /f
LocalDumps의 동작 조건 WER LocalDumps는 애플리케이션이 처리하지 못한 예외로 크래시할 때 동작한다. 만약 호스트 앱이 자체적으로 최상위 예외 핸들러를 두고 예외를 삼켜 버리면(또는 자체 덤프를 뜬 뒤 조용히 종료하면) LocalDumps가 동작하지 않을 수 있다. 이 경우에는 ProcDump의 -e 감시를 병행한다.

세 방법, 언제 무엇을 쓰나

세 가지 생성 방법은 경쟁 관계가 아니라 상황별 선택지다. 현장 조건에 맞춰 고른다.

상황권장 방법이유
지금 멈춰(행) 있다작업 관리자즉시, 설치 불필요
언제 죽을지 모른다ProcDump -e 감시예외 순간 자동 포착
장기간 무인 운영WER LocalDumpsOS가 항상 대기, 설정 1회
성능 저하·행이 반복ProcDump -c/-h임계 조건으로 포착
여러 PC에 일괄 적용WER LocalDumps레지스트리 스크립트 배포

덤프와 함께 받아야 할 정보

덤프 파일 하나만으로 분석이 끝나는 경우는 드물다. 같은 봉투에 몇 가지를 더 넣어 받으면 분석 시간이 절반으로 준다. SDK 지원에서 특히 가치가 큰 항목들이다.

항목왜 필요한가
제품·모듈 버전그 빌드의 pdb를 정확히 맞추기 위해. 가장 중요하다.
크래시 발생 시각같은 시간대의 로그와 대조하기 위해
로그 파일크래시 직전의 동작 흐름 파악
카메라·그래버 모델 / 드라이버 버전하드웨어 의존 문제와 코드 버그 구분
OS 버전·비트(32/64)시스템 심볼 매칭, WOW64 여부 판단
재현 절차"항상 / 가끔 / 특정 조건" 구분
덤프와 로그의 시각을 맞춘다 덤프는 "죽는 순간"만, 로그는 "그전까지의 흐름"만 보여 준다. 둘의 타임스탬프를 맞춰 놓으면 "어떤 프레임을 처리하다가, 어떤 파라미터로, 어디서 죽었는지"가 한 줄로 이어진다. 그래서 덤프를 받을 때 로그도 같은 시간대로 함께 요청하는 것이 기본이다.

고객사 덤프 수집 SOP

실무의 핵심은 "고객이 따라 할 수 있는 절차"를 만드는 것이다. 전화로 설명하면 반드시 어긋난다. 아래처럼 복사해서 그대로 보낼 수 있는 가이드를 준비해 두면, 한 번의 왕복으로 덤프를 받아낼 수 있다.

고객사 전달용 — 크래시 덤프 수집 안내
  1. 아래 명령을 관리자 권한 명령 프롬프트에 그대로 붙여넣어 한 번만 실행해 주세요. (덤프 자동 저장 설정)
  2. 설정 후 프로그램을 평소처럼 사용하시다가, 크래시가 재현되면 별도 조작 없이 자동으로 덤프가 저장됩니다.
  3. C:\CrashDumps 폴더의 .dmp 파일을, 같은 시간대의 로그 파일과 함께 압축해 보내 주세요.
  4. 덤프와 함께 제품 버전, 카메라 모델, 발생 시각, 직전 동작을 한 줄로 적어 주시면 분석이 빨라집니다.
reg add "HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps" /v DumpFolder /t REG_EXPAND_SZ /d "C:\CrashDumps" /f
reg add "HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps" /v DumpType /t REG_DWORD /d 2 /f
reg add "HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps" /v DumpCount /t REG_DWORD /d 10 /f

이 SOP가 강력한 이유는 고객이 타이밍을 맞출 필요가 없다는 점이다. "죽는 순간에 작업 관리자를 여세요" 같은 요구는 현장에서 거의 실패한다. 설정만 미리 심어 두면, 다음 크래시가 알아서 증거를 남긴다.

덤프만 받지 말고 짝을 맞춘다 덤프 분석은 우리 모듈의 정확한 버전에 맞는 심볼(.pdb)이 있어야 제대로 된다. 그래서 덤프를 받을 때 반드시 제품 버전을 함께 묻는다. 버전을 알아야 그 빌드의 pdb를 꺼내 맞춰 볼 수 있다. 심볼 관리는 2편(WinDbg 세팅)에서 자세히 다룬다.

미니로 충분한 경우 vs 풀이 필요한 경우

마지막으로 실무 판단 기준이다. 무조건 풀 덤프가 좋은 것은 아니다. 전송·보관 비용과 분석 깊이를 저울질해 고른다.

미니덤프로 충분한 경우 크래시 위치(콜스택)와 예외 종류만 알면 원인이 명확한 문제들이다. 널 포인터 역참조, 명백한 무한 재귀로 인한 스택 오버플로, "특정 함수 진입 직후 항상 죽음" 같은 패턴이 여기 속한다. 1차 분류 단계에서는 작은 미니덤프로 빠르게 거르는 것이 효율적이다.
풀 덤프가 필요한 경우 "왜 그 값이 거기 들어왔나"까지 봐야 하는 문제들이다. 이미지 버퍼의 실제 내용, 객체 멤버 변수 값, 힙 손상(heap corruption) 여부, 컨테이너에 쌓인 데이터 상태를 확인해야 한다면 풀 덤프가 필수다. 손상된 메모리를 직접 들여다봐야 원인이 드러나는 경우가 많다.

실무 전략은 보통 2단계로 간다. 먼저 미니덤프(또는 LocalDumps의 기본 설정)로 빠르게 1차 분류를 하고, 콜스택만으로 원인이 명확하면 거기서 끝낸다. 콜스택만으로 부족하다고 판단되면, 그때 "다음 재현 시 풀 덤프로 받아 주세요"라고 요청해 깊이 들어간다. 처음부터 모든 고객에게 수 GB 풀 덤프를 요구하면 전송 단계에서 막히기 쉽다.

수집 시 자주 겪는 실수

덤프를 "받긴 받았는데 분석이 안 되는" 상황은 대부분 수집 단계의 실수에서 비롯된다. 현장에서 반복적으로 마주치는 함정을 정리한다.

실수 1 — 비트(32/64)를 섞어 뜬다 64비트 작업 관리자로 32비트 프로세스를 덤프하면 WOW64 계층이 끼어 콜스택이 지저분해진다. 대상 프로세스의 비트에 맞춰 도구를 고르거나, ProcDump를 사용한다. 분석 단계에서 콜스택이 이상하면 가장 먼저 이걸 의심한다.
실수 2 — 버전을 기록하지 않는다 덤프만 있고 제품 버전이 없으면, 맞는 pdb를 찾는 데만 한참이 걸린다. 같은 제품이라도 빌드가 다르면 심볼이 어긋난다. 덤프와 버전은 항상 한 쌍으로 받는다.
실수 3 — 크래시 직후가 아니라 한참 뒤에 뜬다 이미 죽어 사라진 프로세스는 작업 관리자로 덤프할 수 없다. 또 사용자가 확인 창을 닫아 버리면 프로세스가 정리되어 늦는다. "죽는 순간"을 자동 포착하는 ProcDump -e나 WER LocalDumps를 미리 걸어 두는 이유가 이것이다.
실수 4 — 풀 덤프에 민감 정보가 담길 수 있다 풀 덤프는 프로세스 메모리 전체를 담으므로, 검사 이미지나 설정값 같은 데이터가 포함될 수 있다. 외부로 전송할 때는 압축·암호화하고, 사내 보안 정책에 맞춰 보관·폐기 절차를 정해 둔다.
1편 정리 덤프는 재현되지 않는 현장 크래시의 거의 유일한 단서다. SDK 지원에서는 사용자 모드 덤프를 다루며, 1차 분류는 미니덤프, 심층 분석은 풀 덤프를 쓴다. 수집은 작업 관리자(즉석) · ProcDump(조건 감시) · WER LocalDumps(무인 자동)로 하고, 고객사에는 복사·붙여넣기 SOP로 전달한다. 이제 받아온 덤프를 열어 볼 차례다.
