이 시리즈는 덤프 종류와 생성 설정, 분석 환경과 심볼, 콜스택과 !analyze까지 다뤘다. 3편까지의 방법으로 풀리는 크래시는 사실 운이 좋은 편이다. 콜스택이 범인을 그대로 가리키기 때문이다. 그런데 현장에서 가장 골치 아픈 부류는 따로 있다. 힙 손상(heap corruption)이다. 이번 편은 콜스택을 믿을 수 없는 상황을 다룬다.

왜 힙 손상은 어려운가

일반적인 크래시는 "잘못한 코드"가 곧바로 죽는다. 널 포인터를 역참조하면 그 줄에서 즉시 access violation이 난다. 콜스택 맨 위가 범인이다. 힙 손상은 다르다. 메모리를 망가뜨린 코드와 그 망가진 메모리 때문에 죽는 코드가 시간적으로도 공간적으로도 떨어져 있다.

힙 할당자는 각 블록 앞뒤에 크기·상태 같은 메타데이터(헤더)를 함께 저장한다. 어떤 코드가 자기 버퍼의 경계를 1바이트 넘겨 쓰면, 바로 옆 블록의 헤더가 조용히 망가진다. 이 시점에는 아무 일도 일어나지 않는다. 한참 뒤 그 옆 블록을 free하거나 할당자가 인접 블록을 병합하려고 헤더를 읽는 순간, 그제야 할당자 내부에서 크래시가 난다.

핵심 비유 힙 손상은 "범행 현장"과 "시체가 발견된 장소"가 다른 사건이다. 콜스택은 시체가 발견된 장소(할당자 내부)만 알려준다. 우리가 찾아야 하는 건 범행 현장(경계를 넘겨 쓴 그 코드)이다. 그래서 수동적으로 덤프만 보는 게 아니라, 능동적으로 "범행 즉시 현장을 덮치는" 도구가 필요하다.

여기에 두 가지 악조건이 더해진다. 첫째, 재현이 불규칙하다. 손상이 드러나느냐는 힙 레이아웃과 할당·해제 타이밍에 달려 있어서, 같은 입력이라도 어떤 날은 터지고 어떤 날은 멀쩡하다. 둘째, 콜스택이 거짓말을 한다. 망가진 헤더를 따라 할당자가 잘못된 주소를 역참조하면, 콜스택 자체가 엉뚱한 곳을 가리키거나 깨진 채로 나온다. 3편의 !analyze -v를 그대로 믿으면 안 되는 상황이다.

손상의 증상 읽기

덤프를 열었을 때 "이건 힙 손상이다"라고 의심할 신호들이 있다. 이 패턴을 빨리 알아채는 것이 분석 시간을 크게 줄인다.

의심해야 할 신호

  • 예외 코드 0xC0000374 — STATUS_HEAP_CORRUPTION. 힙 무결성 검사가 손상을 잡았다는 가장 명확한 신호다.
  • 콜스택 최상단이 할당자 내부 함수 — ntdll!RtlpAllocateHeap, ntdll!RtlFreeHeap, ntdll!RtlpCoalesceFreeBlocks, ntdll!RtlpLogHeapFailure 등 Rtlp로 시작하는 이름들이 보인다.
  • 엉뚱한 곳에서의 access violation — 내 코드와 무관해 보이는 위치에서, 그것도 매번 다른 위치에서 죽는다.
  • 재현 불규칙 — 빌드를 바꾸거나 로그 한 줄을 추가하면 증상이 사라지거나 옮겨 다닌다(힙 레이아웃이 바뀌기 때문).

아래는 손상이 드러난 덤프에서 !analyze -v를 돌렸을 때 흔히 보는 형태다.

0:000> !analyze -v
*******************************************************************************
EXCEPTION_CODE: (NTSTATUS) 0xc0000374 - A heap has been corrupted.

FAULTING_IP:
ntdll!RtlpLogHeapFailure+45

STACK_TEXT:
ntdll!RtlpLogHeapFailure
ntdll!RtlpAnalyzeHeapFailure
ntdll!RtlpFreeHeapInternal
ntdll!RtlFreeHeap
MyVision!ImageBuffer::~ImageBuffer        // 여기서 죽었지만, 범인은 여기가 아니다
MyVision!Pipeline::releaseFrame
...
콜스택을 액면 그대로 믿지 마라 위 스택에서 ImageBuffer 소멸자가 보인다고 해서 그 소멸자가 범인인 건 아니다. 이 소멸자는 단지 "이미 누군가 망가뜨려 둔 블록"을 free하다가 손상을 발견했을 뿐이다. 진짜 범인은 그 블록과 인접한 메모리를 넘겨 쓴, 전혀 다른 코드다. 이 단계에서 콜스택만 보고 결론 내리면 시간을 통째로 날린다.

이 신호들이 보이면 방향을 바꿔야 한다. 정적인 덤프 분석으로는 범인을 잡을 수 없으니, 손상이 일어나는 바로 그 순간을 크래시로 바꿔주는 도구를 켜고 재현을 시도한다. 그 도구가 PageHeap이다.

gflags와 Full PageHeap

PageHeap은 힙 할당 방식을 검증용으로 바꾸는 운영체제 기능이다. Full PageHeap을 켜면 모든 할당이 다음과 같이 배치된다.

  • 각 할당을 자체 페이지(들)에 배치하고, 할당이 끝나는 지점 바로 뒤에 접근 금지(PAGE_NOACCESS) 가드 페이지를 둔다.
  • 할당의 끝을 페이지 경계에 딱 맞춘다. 그래서 버퍼 끝을 1바이트라도 넘겨 쓰면 곧장 가드 페이지를 건드리고, 그 즉시 access violation이 난다.
  • 해제된 블록의 페이지를 곧바로 재사용하지 않고 PAGE_NOACCESS로 막아둔다. 그래서 use-after-free도 접근 즉시 터진다.

핵심은 "나중에 옆 블록을 free할 때"가 아니라 "경계를 넘겨 쓰는 그 순간" 크래시가 난다는 점이다. 범행 현장에서 바로 잡힌다. 콜스택 맨 위가 진짜 범인이 된다.

gflags 명령

gflags.exe는 Debugging Tools for Windows(Windows SDK에 포함, 2편 참고)에 들어 있다. 특정 실행 파일에 대해 PageHeap을 켜고 끄는 방법은 다음과 같다.

:: Full PageHeap 활성화 (가장 강력, 메모리 많이 씀)
gflags /p /enable MyVision.exe /full

:: Normal PageHeap 활성화 (가벼움, 즉시성은 낮음)
gflags /p /enable MyVision.exe

:: 현재 PageHeap 설정 확인
gflags /p

:: 해제 (분석이 끝나면 반드시)
gflags /p /disable MyVision.exe

설정은 레지스트리의 Image File Execution Options에 기록되므로, 명령을 실행한 뒤 대상 프로세스를 새로 띄워야 적용된다. 이미 떠 있는 프로세스에는 소급 적용되지 않는다.

Normal vs Full PageHeap

구분Full PageHeapNormal PageHeap
검출 시점오버런하는 순간 즉시 크래시해제 시점에 채움 패턴(fill pattern) 훼손 검사
메모리 비용매우 큼(할당마다 페이지 단위)작음
정확도범인 코드를 직접 포착"언젠가 망가졌다"까지만

오버런이 "버퍼 앞쪽"으로 일어나는 언더런(underrun)이 의심되면 가드 페이지를 할당 앞에 두는 옵션(/full에 /backwards 병행)도 있다. 다만 기본 동작은 뒤쪽 오버런 검출이라는 점을 기억한다.

큰 이미지 버퍼를 쓰는 앱이라면 범위를 좁혀라 Full PageHeap은 할당마다 최소 한 페이지를 더 쓰기 때문에, 수십 MB짜리 프레임 버퍼를 초당 수십 장 다루는 비전 애플리케이션에서는 메모리가 금방 바닥난다. gflags /p /enable MyVision.exe /full /size 16 64처럼 특정 크기 범위만 PageHeap 대상으로 지정하면 부담을 줄이면서 의심 구간만 집중 검사할 수 있다.

Application Verifier

Application Verifier(appverif.exe)는 PageHeap을 포함한 런타임 검증 도구 모음이다. gflags가 PageHeap 한 가지를 켜는 단일 스위치라면, Application Verifier는 힙 검증에 더해 핸들 오용, 락 사용 오류, 위험한 API 호출까지 한꺼번에 감시한다.

GUI에서 대상 exe를 추가하고 Basics > Heaps를 체크하면 내부적으로 Full PageHeap에 준하는 힙 검증이 켜진다. 명령줄로도 설정할 수 있다.

:: Heaps 검사만 켜기
appverif -enable Heaps -for MyVision.exe

:: 여러 검사 켜기 (힙 + 핸들 + 락)
appverif -enable Heaps Handles Locks -for MyVision.exe

:: 전부 해제
appverif -disable * -for MyVision.exe

Application Verifier가 위반을 잡으면, 프로세스를 디버거에 물려 두었을 때 멈추면서 어떤 규칙을 어겼는지 알려준다. 덤프로 남았다면 콜스택에 verifier!로 시작하는 프레임이나 verifier stop 코드가 보인다. gflags PageHeap과 Application Verifier 중 하나만 켜면 된다. 힙만 빠르게 보려면 gflags, 핸들·락까지 종합적으로 보려면 Application Verifier를 택한다.

락 검증은 5편과 이어진다 Application Verifier의 Locks 검사는 크리티컬 섹션을 초기화 없이 쓰거나 잘못된 순서로 잡는 패턴을 잡아준다. 멀티스레드 비전 파이프라인의 데드락을 사전에 거르는 데 유용하다. 락과 데드락 분석은 5편에서 본격적으로 다룬다.

!heap로 범인 추적

PageHeap을 켠 채로 재현에 성공하면, 손상이 일어나는 순간 크래시가 나면서 덤프가 떨어진다. 이제 WinDbg의 !heap 확장으로 그 메모리가 어떤 블록이었고 누가 할당했는지 역추적한다.

자주 쓰는 !heap 명령

명령용도
!heap -s모든 힙의 요약 정보
!heap -p -a <address>그 주소가 속한 힙 블록 + 할당 당시 스택 트레이스
!heap -p -h <heap>특정 PageHeap 힙의 블록 목록
!address <address>그 주소의 메모리 영역 속성(상태·보호)

분석의 출발점은 "어느 주소에서 죽었는가"다. !analyze -v나 .exr -1로 fault address를 확보한 다음, 그 주소를 !heap -p -a에 넣는다.

!heap -p -a 출력 읽기

PageHeap이 켜져 있으면 각 블록에 할당 당시의 콜스택이 함께 저장된다. 그래서 !heap -p -a가 "이 메모리를 누가 할당했나"를 그대로 보여준다. use-after-free에서 특히 강력하다. 이미 해제된 블록의 원래 주인을 찾을 수 있기 때문이다.

0:000> !heap -p -a 0x0a3f0040
    address 0a3f0040 found in
    _DPH_HEAP_ROOT @ 4fd1000
    in free-ed allocation (  DPH_HEAP_BLOCK:   VirtAddr   VirtSize)
                                    a3e0f9c:    a3f0000      2000
    7ff... ntdll!RtlDebugFreeHeap
    7ff... ntdll!RtlpFreeHeap
    ...
    Stack trace of the allocation:
       MyVision!ImageBuffer::allocate+0x3a
       MyVision!FrameGrabber::onFrame+0x118
       MyVision!GrabThread::run+0x too

여기서 읽어야 할 것은 두 가지다. 첫째, in free-ed allocation은 이 주소가 이미 해제된 블록임을 뜻한다. 해제된 메모리에 접근했으니 use-after-free다. 둘째, Stack trace of the allocation은 그 블록을 처음 할당한 코드다. 여기서는 FrameGrabber::onFrame이 만든 이미지 버퍼였음을 알 수 있다. 누가 너무 일찍 해제했는지, 누가 해제 뒤에 건드렸는지를 좁혀 들어가면 된다.

반대로 오버런이면 출력이 다르다. fault address가 busy allocation의 끝 직후(가드 페이지)로 잡히고, 크래시 콜스택 맨 위가 경계를 넘겨 쓴 바로 그 코드가 된다. 이 경우엔 할당 스택이 아니라 크래시 콜스택이 범인이다.

손상 유형 구분

힙 손상은 크게 세 가지다. PageHeap 환경에서 각각이 어떻게 드러나는지 알면 진단이 빨라진다.

유형정의PageHeap에서의 증상
Buffer overrun할당 경계 너머로 쓰기쓰는 순간 가드 페이지에서 AV. 크래시 콜스택 = 범인
Use-after-free해제 후 접근해제된 페이지 접근 즉시 AV. !heap -p -a가 free-ed 표시
Double free같은 블록을 두 번 해제RtlFreeHeap에서 0xC0000374 또는 verifier stop

Buffer overrun

가장 고전적인 손상이다. 크기 계산 실수, off-by-one, 잘못된 stride로 이미지 한 줄을 넘겨 쓰는 경우 등이 모두 여기에 든다. Full PageHeap에서는 오버런이 곧 가드 페이지 쓰기라서 즉시 잡힌다. 콜스택 맨 위를 그대로 믿어도 된다.

Use-after-free

멀티스레드에서 객체 수명 관리가 어긋날 때 흔하다. 한 스레드가 버퍼를 해제했는데 다른 스레드가 아직 그 포인터를 들고 있는 식이다. PageHeap이 해제된 페이지를 막아두므로 접근 즉시 AV가 나고, !heap -p -a의 할당 스택으로 어떤 버퍼였는지 식별한다.

Double free

같은 포인터를 두 곳에서 해제하거나, 소유권 이전을 잘못 설계했을 때 난다. std::unique_ptr로 소유권을 명확히 하면 상당수가 사라진다. CLAUDE.md의 스마트 포인터 정책(직접 new/delete 금지)이 이런 부류를 구조적으로 막는 안전장치다.

예방이 분석보다 싸다 RAII와 스마트 포인터로 수명을 코드 구조에 묶어 두면 double free와 use-after-free의 큰 줄기가 사라진다. PageHeap은 이미 새어 나간 버그를 잡는 도구이고, 처음부터 새지 않게 하는 건 설계의 몫이다.

머신비전 실전 시나리오

이론을 비전 SDK 맥락으로 옮겨 본다. 고객사에서 "장시간 검사를 돌리면 가끔 죽는다"는 제보가 들어왔다고 하자.

시나리오 1 — ROI 복사 오버런

증상

특정 해상도에서만, 그것도 며칠에 한 번씩 검사 프로세스가 할당자 내부에서 죽는다. 덤프의 예외 코드는 0xC0000374, 콜스택 맨 위는 매번 다른 위치다.

원인

ROI를 잘라 별도 버퍼로 복사하는 코드에서 대상 버퍼의 stride를 소스 기준으로 계산했다. 폭이 4의 배수가 아닌 해상도에서 행마다 몇 바이트씩 경계를 넘겨 썼고, 인접 힙 블록의 헤더가 조금씩 망가졌다.

추적

가상의 입력으로 Full PageHeap을 켠 진단 빌드를 재현 장비에 올렸다. 잘못 넘겨 쓰는 첫 행에서 즉시 AV가 났고, 크래시 콜스택 맨 위가 복사 루프를 정확히 가리켰다. 정적 덤프로는 며칠을 헤맬 버그가 PageHeap에서는 한 번에 잡혔다.

시나리오 2 — grab 버퍼 use-after-free

두 번째는 멀티스레드 수명 문제다. grab 스레드가 카메라(또는 GenICam 버퍼)에서 프레임을 받아 큐에 올리고, process 스레드가 꺼내 검사한다. 의사코드로 단순화하면 다음과 같다.

// grab 스레드
auto frame = bufferPool.acquire();   // 풀에서 버퍼 획득
fillFromCamera(frame);
queue.push(frame);
// ... 잘못된 지점: 큐가 가득 차면 오래된 프레임을 풀로 반납
if (queue.full())
    bufferPool.release(queue.popOldest());   // 아직 process가 보고 있을 수 있다

// process 스레드
auto frame = queue.pop();
runInspection(frame);                // release된 버퍼를 참조 → use-after-free
증상

고부하(고속 grab)에서만 간헐적으로 access violation. 부하가 낮으면 재현이 안 된다. 타이밍 의존이라 로그를 추가하면 증상이 옮겨 다닌다.

원인

큐가 가득 찼을 때 오래된 프레임을 풀로 반납하는데, 그 프레임을 process 스레드가 아직 검사 중일 수 있다. grab이 release한 버퍼를 process가 계속 읽어 use-after-free가 된다.

추적

Full PageHeap을 켜자 release된 페이지를 process가 건드리는 순간 즉시 AV. !heap -p -a <faultAddr>가 free-ed allocation으로 표시하고, 할당 스택이 grab 스레드의 bufferPool.acquire를 가리켰다. 버퍼 수명이 grab과 process 사이에서 어긋났음을 확정했다. 근본 해결은 참조 카운트(std::shared_ptr)로 검사가 끝나야만 반납되게 하는 것이다.

이 시나리오는 5편과 짝을 이룬다 같은 grab↔process 파이프라인에서, 수명 문제는 use-after-free(이번 편)로, 락 순서 문제는 데드락(5편)으로 드러난다. 멀티스레드 버그는 한 가지 도구로 끝나지 않는다. PageHeap과 스레드 분석을 함께 들고 있어야 한다.

PageHeap 운영 주의

PageHeap은 강력하지만 공짜가 아니다. 운영 환경에 함부로 켜면 새로운 문제를 만든다.

  • 메모리 폭증 — Full PageHeap은 할당마다 페이지를 더 쓴다. 큰 프레임 버퍼를 대량으로 다루는 비전 앱은 메모리가 빠르게 고갈될 수 있다. 크기 범위 한정(/size)이나 Normal PageHeap으로 완화한다.
  • 성능 저하 — 페이지 단위 할당과 보호 전환으로 처리량이 떨어진다. 실시간 검사 타이밍에 영향을 줄 수 있으니 성능 측정용으로는 쓰지 않는다.
  • 상시 적용 금지 — 고객 운영 환경에 PageHeap을 켜둔 채 두면 안 된다. 재현 시도용으로 한정하고, 끝나면 반드시 gflags /p /disable로 해제한다.
  • 해제 확인 — 설정이 레지스트리에 남기 때문에, 해제했는지 gflags /p로 확인하는 습관을 들인다. 켜둔 걸 잊으면 "왜 이 PC만 느리지"의 원인이 된다.
고객사에 적용할 때의 원칙 고객 장비에 PageHeap을 켜야 할 때는 별도 진단 빌드/세션으로 한정하고, 메모리 여유를 먼저 확인한다. /size로 의심 구간만 좁히고, 재현 후 즉시 해제한다. "잠깐 켜고 잊은" PageHeap이 또 다른 장애 신고로 돌아오는 일을 막아야 한다.

이번 편 요약

힙 손상은 콜스택이 거짓말을 한다. Full PageHeap으로 손상을 발생 즉시 크래시로 바꾸고, !heap -p -a의 할당 스택으로 범인을 추적한다.

다음 5편에서는 프로세스가 죽지 않고 멈추는 또 다른 난제, 데드락과 행(hang)을 다룬다. 크래시가 없으니 덤프부터 직접 떠야 하고, 모든 스레드의 콜스택을 한꺼번에 읽어 서로를 기다리는 사이클을 찾아내는 분석이다.
