Option과 Result — null 없는 설계

2026-06-25 약 8분 분량 Rust 시리즈
이 편에서 배우는 것 Rust에는 null이 없다. "값이 없을 수도 있음"은 Option<T>로, "실패할 수도 있음"은 Result<T, E>로 타입에 드러낸다. 컴파일러가 두 경우를 모두 처리하도록 강제하므로, C++의 null 포인터 역참조나 무시된 에러 코드 같은 실수가 컴파일 단계에서 막힌다. 이 글은 두 타입을 match로 다루는 법, unwrap/expect의 함정, 그리고 에러 전파를 한 글자로 줄이는 ? 연산자까지 본다.

왜 null이 문제인가

C++을 써 본 사람이라면 null 포인터 역참조로 프로그램이 죽어 본 경험이 있을 것이다. 문제의 본질은 "값이 있다"와 "값이 없다"가 같은 타입으로 표현된다는 데 있다. Widget* w는 유효한 객체를 가리킬 수도, nullptr일 수도 있는데 타입만 봐서는 구분되지 않는다. 그래서 검사를 깜빡하면 런타임에 터진다.

Rust는 이 문제를 언어 차원에서 없앴다. Rust에는 null이 아예 없고, 대신 "없을 수도 있는 값"을 표현하는 별도의 타입 Option<T>가 있다. 핵심은 Option은 일반 T와 다른 타입이라는 점이다. 값을 실제로 쓰려면 반드시 "있는 경우"와 "없는 경우"를 모두 처리해야 하고, 빠뜨리면 컴파일이 안 된다. 검사 누락이 런타임 사고가 아니라 컴파일 에러로 바뀐다.

C++과 이렇게 다르다 C++17의 std::optional<T>는 Rust의 Option<T>와 발상이 같다. 다만 C++에서는 빈 optional을 검사 없이 *opt로 역참조해도 컴파일러가 막지 않는다(미정의 동작). Rust는 Option 안의 값을 꺼내려면 분기 처리를 문법적으로 강제한다. "있을 수 있는 실수"를 "할 수 없는 실수"로 바꾼 것이 차이다.

Option<T> — 값이 없을 수도 있음

Option<T>는 표준 라이브러리의 열거형(enum)이고 변형(variant)이 둘뿐이다. 값이 있으면 Some(value), 없으면 None이다. 정의를 단순화하면 다음과 같다.

// 표준 라이브러리에 이미 정의돼 있다 (직접 쓸 필요는 없다)
enum Option<T> {
    Some(T),
    None,
}

"이름으로 사용자를 찾는" 함수를 생각해 보자. 찾으면 나이를, 못 찾으면 아무것도 돌려주지 않는다. 반환 타입을 Option<u32>로 두면 "없을 수 있음"이 시그니처에 그대로 드러난다.

fn find_age(name: &str) -> Option<u32> {
    match name {
        "Alice" => Some(30),
        "Bob" => Some(25),
        _ => None,
    }
}

fn main() {
    // match로 두 경우를 모두 처리해야 한다
    match find_age("Alice") {
        Some(age) => println!("나이: {}", age),
        None => println!("찾을 수 없음"),
    }
}

호출하는 쪽은 find_age가 None을 줄 수 있다는 사실을 무시할 수 없다. Some(age)와 None 두 갈래를 모두 적지 않으면 match가 모든 경우를 덮지 않았다며 컴파일 에러가 난다. 표준 라이브러리의 HashMap::get, slice::first, 문자열 검색 등 "없을 수 있는" 모든 API가 이 타입을 돌려준다.

Result<T, E> — 실패할 수도 있음

"값이 없음"과 "작업이 실패함"은 다른 개념이다. 후자에는 실패의 이유가 따라온다. Rust는 이를 Result<T, E>로 표현한다. 성공이면 결과를 담은 Ok(value), 실패면 에러를 담은 Err(error)다.

// 이것도 표준 라이브러리 정의다
enum Result<T, E> {
    Ok(T),
    Err(E),
}

문자열을 정수로 바꾸는 작업은 실패할 수 있다("12"는 되지만 "abc"는 안 된다). 직접 만든 예로, 0으로 나누는 경우를 에러로 돌려주는 나눗셈 함수를 보자.

fn divide(a: f64, b: f64) -> Result<f64, String> {
    if b == 0.0 {
        Err(String::from("0으로 나눌 수 없음"))
    } else {
        Ok(a / b)
    }
}

fn main() {
    match divide(10.0, 2.0) {
        Ok(value) => println!("결과: {}", value),   // 결과: 5
        Err(msg) => println!("에러: {}", msg),
    }

    match divide(1.0, 0.0) {
        Ok(value) => println!("결과: {}", value),
        Err(msg) => println!("에러: {}", msg),       // 에러: 0으로 나눌 수 없음
    }
}

여기서도 핵심은 같다. Result를 받은 쪽은 성공과 실패를 모두 다루도록 강제된다. C++의 정수 반환 에러 코드는 검사하지 않고 무시해도 경고조차 없을 수 있지만, Rust에서 Result를 받고 아무것도 하지 않으면 #[must_use] 속성 덕분에 컴파일러가 "이 값을 쓰지 않았다"고 경고한다.

Option과 Result, 언제 무엇을 값이 단순히 없을 수 있을 뿐이고 이유가 필요 없으면 Option. 작업이 실패할 수 있고 그 원인을 호출자에게 전하고 싶으면 Result. 둘은 서로 변환할 수도 있다 — Option을 Result로 바꾸는 ok_or, 반대로 Result를 Option으로 만드는 ok 메서드가 있다.

값을 꺼내고 다루는 법

match는 가장 명시적이지만, 매번 두 갈래를 적기 번거로울 때가 있다. 표준 라이브러리는 더 짧은 도구를 제공한다.

unwrap과 expect — 편하지만 위험하다

unwrap()은 Some/Ok면 안의 값을 꺼내고, None/Err이면 그 자리에서 패닉(panic)을 일으켜 프로그램을 멈춘다. expect("메시지")는 패닉 시 지정한 메시지를 함께 출력한다.

fn main() {
    let some_value: Option<i32> = Some(7);
    let n = some_value.unwrap();        // 7 — Some이므로 안전
    println!("{}", n);

    let nothing: Option<i32> = None;
    // 아래 줄은 패닉한다. 실제 코드에서는 피한다.
    // let bad = nothing.expect("값이 있어야 함");
    let _ = nothing;
}

unwrap은 "여기서 None/Err이면 버그이므로 차라리 멈추는 게 낫다"가 확실할 때만 쓴다. 예제 코드나 프로토타입에서는 흔하지만, 사용자 입력이나 파일·네트워크처럼 실패가 정상 범위인 곳에서 남발하면 사소한 입력 하나로 프로그램이 죽는다.

패닉 없이 다루는 메서드들

패닉을 피하면서 간결하게 쓰는 방법이 많다. unwrap_or는 없을 때 쓸 기본값을 주고, map은 안에 값이 있을 때만 변환을 적용하며, if let은 한 변형만 관심 있을 때 쓴다.

fn find_age(name: &str) -> Option<u32> {
    if name == "Alice" { Some(30) } else { None }
}

fn main() {
    // 1) 기본값: None이면 0을 쓴다
    let age = find_age("Charlie").unwrap_or(0);
    println!("나이: {}", age);                  // 나이: 0

    // 2) map: Some일 때만 변환 (None은 그대로 None)
    let next: Option<u32> = find_age("Alice").map(|a| a + 1);
    println!("{:?}", next);                     // Some(31)

    // 3) if let: Some인 경우에만 본문 실행
    if let Some(a) = find_age("Alice") {
        println!("찾음: {}", a);                // 찾음: 30
    }
}

{:?}는 디버그 출력 형식으로, Option이나 Result 같은 타입을 그대로 찍어 볼 때 쓴다. 위 코드는 소유권 규칙을 위반하지 않는다 — u32는 복사(Copy)되는 타입이고, 클로저 |a| a + 1은 값을 받아 새 값을 돌려줄 뿐 빌림 충돌이 없다.

? 연산자로 에러 전파

여러 단계가 줄줄이 실패할 수 있을 때, 매 단계마다 match로 Err을 검사해 되돌려 주는 코드는 금방 장황해진다. ? 연산자는 이 패턴을 한 글자로 줄인다. Result 뒤에 ?를 붙이면, Ok면 값을 꺼내고 Err면 그 에러를 즉시 함수의 반환값으로 되돌린다.

fn divide(a: f64, b: f64) -> Result<f64, String> {
    if b == 0.0 {
        Err(String::from("0으로 나눌 수 없음"))
    } else {
        Ok(a / b)
    }
}

// 두 번 연속 나눈다. 어느 단계든 실패하면 그 에러가 그대로 전파된다.
fn divide_twice(a: f64, b: f64, c: f64) -> Result<f64, String> {
    let first = divide(a, b)?;   // Err이면 여기서 바로 return
    let second = divide(first, c)?;
    Ok(second)
}

fn main() {
    match divide_twice(100.0, 5.0, 2.0) {
        Ok(v) => println!("결과: {}", v),   // 결과: 10
        Err(e) => println!("에러: {}", e),
    }

    match divide_twice(100.0, 0.0, 2.0) {
        Ok(v) => println!("결과: {}", v),
        Err(e) => println!("에러: {}", e),  // 에러: 0으로 나눌 수 없음
    }
}

? 없이 같은 함수를 쓰면 divide 호출마다 match로 Err을 받아 return하는 코드가 반복돼 길이가 몇 배로 늘어난다. ?는 "성공이면 계속, 실패면 즉시 위로"라는 흐름을 그대로 표현한다. 단, ?는 반환 타입이 Result(또는 Option)인 함수 안에서만 쓸 수 있다 — 전파할 대상이 있어야 하기 때문이다. Option에 ?를 쓰면 같은 방식으로 None이 전파된다.

C++의 std::optional / std::expected와 비교 C++23의 std::expected<T, E>는 Rust의 Result<T, E>와 거의 같은 모양이다. 차이는 두 가지다. 첫째, Rust는 ? 한 글자로 에러를 전파하지만 C++에는 동등한 언어 차원 연산자가 없어 if (!exp) return exp.error(); 식으로 직접 풀어 써야 한다. 둘째, Rust의 Result는 #[must_use]라 무시하면 경고가 뜨지만, C++에서는 반환값을 버려도 기본적으로 조용하다. 결과적으로 Rust 쪽이 "에러 처리를 빠뜨리기 더 어렵게" 설계돼 있다.

정리와 주의

  • null이 없다 — "없을 수 있는 값"은 Option<T>(Some/None), "실패할 수 있는 작업"은 Result<T, E>(Ok/Err)로 타입에 드러낸다.
  • 처리가 강제된다 — match는 모든 변형을 덮어야 컴파일되고, Result는 #[must_use]라 무시하면 경고가 난다. 검사 누락이 컴파일 단계에서 막힌다.
  • unwrap/expect는 신중히 — None/Err일 때 패닉한다. "여기서 실패면 버그"가 확실할 때만 쓰고, 정상적으로 실패할 수 있는 곳에서는 unwrap_or·map·match 등으로 다룬다.
  • ? 로 깔끔하게 전파 — 반환 타입이 Result/Option인 함수 안에서 ?를 쓰면 에러/None을 즉시 위로 되돌려 보일러플레이트를 없앤다.
