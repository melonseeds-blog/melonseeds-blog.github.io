특징점이란?

특징점(feature, keypoint)은 이미지에서 식별 가능한 두드러진 지점이다. 대표적으로 코너가 있다. 같은 장면을 다른 각도, 다른 거리, 다른 조명에서 다시 찍어도 그 지점을 또 찾을 수 있다면 좋은 특징점이다.

왜 코너인가? 평평한 영역은 주변과 구별되지 않는다 — 어디가 어디인지 알 수 없다. 엣지(경계선) 위의 점은 선을 따라 미끄러질 수 있어 한 방향으로는 위치가 모호하다. 반면 코너는 두 방향 모두 밝기 변화가 크므로 위치가 한 점으로 고정된다. 이 "딱 하나로 집어낼 수 있다"는 성질이 매칭의 출발점이다.

이미지 위치밝기 변화특징점으로서
평평한 영역 (flat)모든 방향으로 변화 없음나쁨 — 구별 불가
엣지 (edge)한 방향만 변화모호함 — 선 따라 미끄러짐
코너 (corner)두 방향 모두 변화 큼좋음 — 위치 고정

좋은 특징점이 갖춰야 할 성질은 반복성(repeatability)으로 요약된다. 같은 물리적 지점이 변환된 이미지에서도 다시 검출되어야 한다. 그래서 검출기를 평가할 때는 회전 불변성, 스케일 불변성, 조명 변화에 대한 강건성을 본다.

특징점은 "다시 찾을 수 있는 점"이다 검출 자체보다 중요한 건 재현성이다. 한 장에서만 잘 찾히고 다른 장에서 안 찾히는 점은 매칭에 쓸 수 없다. 회전·스케일·조명이 바뀌어도 같은 점이 또 잡혀야 비로소 두 이미지를 연결할 수 있다.

특징점 처리 3단계

특징점을 이용한 작업은 항상 세 단계를 거친다. 검출 → 기술 → 매칭이다. 단계마다 다루는 대상과 출력이 다르다.

특징점 처리 파이프라인 — 검출로 위치를 찾고, 기술로 지문을 만들고, 매칭으로 두 이미지를 연결한다.

검출은 "어디가 특징점인가"를 답한다. 출력은 좌표·크기·방향을 담은 cv::KeyPoint 목록이다. 기술은 "그 점이 어떻게 생겼나"를 답한다. 각 키포인트 주변 패치를 고정 길이 벡터(기술자)로 요약한다. 매칭은 "이쪽 점과 저쪽 점이 같은가"를 답한다. 두 이미지의 기술자를 비교해 가장 닮은 쌍을 찾는다.

Harris 코너 검출

Harris 코너 검출은 가장 고전적인 검출기다. 원리는 직관적이다 — 작은 윈도우를 이미지 위에서 조금씩 움직였을 때, 어느 방향으로 옮겨도 윈도우 안의 밝기가 크게 변하는 지점이 코너다. 평평한 곳은 어디로 옮겨도 안 변하고, 엣지는 한 방향(엣지를 따라가는 방향)으로는 안 변한다. 코너만 두 방향 모두 변한다.

OpenCV는 cv::cornerHarris로 이 코너 응답값을 계산한다. 응답값이 큰 픽셀이 코너다.

#include <opencv2/opencv.hpp>

cv::Mat src = cv::imread("part.jpg", cv::IMREAD_GRAYSCALE);
if (src.empty())
{
    std::cerr << "이미지를 열 수 없습니다." << std::endl;
    return -1;
}

// 코너 응답값 계산 (CV_32FC1 결과)
cv::Mat response;
int blockSize = 2;     // 코너 판정에 쓰는 이웃 윈도우 크기
int ksize = 3;         // Sobel 미분 커널 크기
double k = 0.04;       // Harris 검출기 자유 파라미터 (보통 0.04~0.06)
cv::cornerHarris(src, response, blockSize, ksize, k);

// 응답값을 0~255로 정규화해서 시각화하기 좋게
cv::Mat normResponse;
cv::normalize(response, normResponse, 0, 255, cv::NORM_MINMAX, CV_8UC1);

// 임계값을 넘는 픽셀을 코너로 표시
cv::Mat display;
cv::cvtColor(src, display, cv::COLOR_GRAY2BGR);
for (int y = 0; y < normResponse.rows; ++y)
{
    for (int x = 0; x < normResponse.cols; ++x)
    {
        if (normResponse.at<uchar>(y, x) > 120)  // 임계값
        {
            cv::circle(display, cv::Point(x, y), 4, cv::Scalar(0, 0, 255), 1);
        }
    }
}

goodFeaturesToTrack — 더 쓰기 쉬운 코너 검출

cornerHarris는 응답 맵을 그대로 돌려주므로 임계값과 비최대 억제를 직접 처리해야 한다. cv::goodFeaturesToTrack은 그 과정을 알아서 해주고 코너 좌표 목록을 바로 돌려준다. 내부적으로 Harris 또는 Shi-Tomasi 방식을 쓴다.

cv::Mat gray = cv::imread("part.jpg", cv::IMREAD_GRAYSCALE);

std::vector<cv::Point2f> corners;
int maxCorners = 200;          // 최대 코너 개수
double qualityLevel = 0.01;    // 최강 코너 대비 품질 비율 하한
double minDistance = 10.0;     // 코너 사이 최소 거리 (픽셀)

cv::goodFeaturesToTrack(gray, corners, maxCorners,
                        qualityLevel, minDistance);

std::cout << "검출된 코너 수: " << corners.size() << std::endl;

cv::Mat display;
cv::cvtColor(gray, display, cv::COLOR_GRAY2BGR);
for (const cv::Point2f& pt : corners)
{
    cv::circle(display, pt, 4, cv::Scalar(0, 255, 0), -1);
}
실행 결과 (콘솔)
검출된 코너 수: 187
Harris는 스케일 불변이 아니다 Harris 코너는 회전에는 강하지만 스케일이 바뀌면 약하다. 이미지를 키우면 작은 코너가 완만한 곡선처럼 보여 더 이상 코너로 잡히지 않는다. 또한 Harris는 검출만 한다 — 기술자가 없어 그 자체로는 매칭에 못 쓴다. 매칭까지 하려면 ORB·SIFT 같은 검출·기술 통합 검출기가 필요하다.

ORB — 빠르고 무료인 이진 검출기

ORB(Oriented FAST and Rotated BRIEF)는 이름 그대로 두 알고리즘을 결합한다. 코너 검출은 FAST에 방향 정보를 더해 쓰고(Oriented FAST), 기술자는 BRIEF에 회전 보정을 더해 쓴다(Rotated BRIEF). 결과는 이진 기술자다 — 각 차원이 0/1 비트다.

ORB는 빠르고, 메모리를 적게 쓰고, 특허가 없어 상업적으로 자유롭게 쓸 수 있다. 산업 검사나 실시간 처리에 가장 먼저 검토할 검출기다.

#include <opencv2/opencv.hpp>

cv::Mat gray = cv::imread("part.jpg", cv::IMREAD_GRAYSCALE);

// ORB 검출기 생성 — 최대 특징점 수를 지정
cv::Ptr<cv::ORB> orb = cv::ORB::create(1000);

std::vector<cv::KeyPoint> keypoints;
cv::Mat descriptors;

// 검출과 기술을 한 번에 수행
orb->detectAndCompute(gray, cv::noArray(), keypoints, descriptors);

std::cout << "키포인트 수: " << keypoints.size() << std::endl;
std::cout << "기술자 행렬: " << descriptors.rows << " x "
          << descriptors.cols << ", 타입="
          << descriptors.type() << std::endl;  // CV_8U = 0

// 키포인트를 이미지에 그린다 (크기·방향 포함)
cv::Mat display;
cv::drawKeypoints(gray, keypoints, display, cv::Scalar::all(-1),
                  cv::DrawMatchesFlags::DRAW_RICH_KEYPOINTS);
실행 결과 (콘솔)
키포인트 수: 1000 기술자 행렬: 1000 x 32, 타입=0

주목할 점은 기술자 행렬의 형태다. 키포인트 1000개에 대해 1000 x 32 행렬이고 타입은 CV_8U다. ORB 기술자 한 개는 32바이트 = 256비트다. 각 비트가 점 주변 픽셀쌍의 밝기 비교 결과다. 이 이진 구조 때문에 매칭이 빠르다 — 두 기술자의 거리는 단순히 다른 비트 수(해밍 거리)다.

ORB의 nfeatures는 넉넉히 잡는다 cv::ORB::create(nfeatures)의 기본값은 500이다. 매칭 정확도를 높이려면 1000~2000으로 올리는 게 보통이다. 다만 키포인트가 많을수록 매칭 비용도 늘어나니, 실시간이라면 처리 시간을 측정하며 균형을 잡는다.

SIFT — 스케일 불변 특징

SIFT(Scale-Invariant Feature Transform)는 강건성의 기준점 같은 검출기다. 이미지를 여러 스케일로 만든 피라미드에서 특징점을 찾기 때문에 스케일이 바뀌어도, 회전해도, 조명이 달라져도 같은 점을 다시 찾는다. Harris가 스케일에 약했던 문제를 정면으로 해결한다.

대가가 있다. SIFT는 느리다. 그리고 기술자가 128차원 실수 벡터라 메모리도 더 쓴다. 한때는 특허로 묶여 있었지만 특허가 만료되어 지금은 OpenCV 메인 모듈(features2d)에 포함되어 별도 contrib 없이 쓸 수 있다.

#include <opencv2/opencv.hpp>
#include <opencv2/features2d.hpp>

cv::Mat gray = cv::imread("part.jpg", cv::IMREAD_GRAYSCALE);

// SIFT 검출기 생성 (인자 없이 기본값)
cv::Ptr<cv::SIFT> sift = cv::SIFT::create();

std::vector<cv::KeyPoint> keypoints;
cv::Mat descriptors;
sift->detectAndCompute(gray, cv::noArray(), keypoints, descriptors);

std::cout << "키포인트 수: " << keypoints.size() << std::endl;
std::cout << "기술자 행렬: " << descriptors.rows << " x "
          << descriptors.cols << ", 타입="
          << descriptors.type() << std::endl;  // CV_32F = 5
실행 결과 (콘솔)
키포인트 수: 642 기술자 행렬: 642 x 128, 타입=5

ORB와 비교하면 차이가 명확하다. ORB는 x 32 / CV_8U(이진), SIFT는 x 128 / CV_32F(실수)다. 이 타입 차이가 매칭 단계에서 어떤 거리 측정을 써야 하는지를 결정한다 — 뒤에서 다시 다룬다.

API가 통일되어 있다 ORB든 SIFT든 모두 cv::Feature2D 인터페이스를 따른다. create()로 만들고 detectAndCompute()로 검출·기술을 한 번에 한다. 그래서 검출기를 바꿔 끼우기 쉽다 — cv::Ptr<cv::Feature2D> 타입으로 받아두면 같은 코드로 ORB와 SIFT를 모두 돌릴 수 있다.

기술자(descriptor) — 이진 vs 실수

기술자는 키포인트 주변을 고정 길이 벡터로 표현한 것이다. 사람으로 치면 지문이다. 두 키포인트가 같은 물리적 지점이라면 기술자도 서로 비슷할 것이고, 이 "비슷함"을 숫자로 잴 수 있어야 매칭이 가능하다.

기술자는 크게 두 종류다 — 이진 기술자와 실수 기술자. 둘은 저장 형태도, 거리를 재는 방법도 다르다.

구분이진 기술자실수 기술자
대표 검출기ORB, BRISK, AKAZESIFT, SURF, KAZE
저장 형태비트열 (CV_8U)실수 벡터 (CV_32F)
ORB / SIFT 예32바이트 = 256비트128차원 float = 512바이트
거리 측정해밍 거리 (다른 비트 수)L2 거리 (유클리드)
매칭 normNORM_HAMMINGNORM_L2
속도매우 빠름상대적으로 느림
강건성좋음매우 좋음

핵심은 거리 측정 방법이 기술자 종류에 묶여 있다는 점이다. 이진 기술자는 비트 단위라 두 비트열에서 다른 비트가 몇 개인지(해밍 거리)를 센다. 실수 기술자는 벡터 공간의 점이라 두 점 사이 유클리드 거리(L2)를 잰다. 이걸 잘못 짝지으면 매칭이 통째로 망가진다 — 이 글의 마지막 함정 절에서 다시 강조한다.

매칭 — BFMatcher와 FLANN

두 이미지에서 각각 기술자를 뽑았다면, 이제 한쪽 기술자마다 다른 쪽에서 가장 가까운 기술자를 찾는다. 이게 매칭이다. OpenCV는 두 가지 매처를 제공한다.

BFMatcher — 무차별 대입 매칭

BFMatcher(Brute-Force Matcher)는 가장 단순하다. 한쪽의 기술자 하나를 다른 쪽 전부와 비교해 가장 가까운 것을 고른다. 정확하지만 기술자가 많으면 느리다. 매처를 만들 때 norm 종류를 반드시 기술자에 맞춰 지정한다.

norm 타입거리 측정맞는 기술자
NORM_HAMMING해밍 거리ORB, BRISK, AKAZE (이진)
NORM_HAMMING2해밍 거리 (2비트 묶음)WTA_K=3,4로 만든 ORB
NORM_L2유클리드 거리SIFT, SURF, KAZE (실수)
NORM_L1맨해튼 거리SIFT, SURF (대안)
#include <opencv2/opencv.hpp>

cv::Mat img1 = cv::imread("scene1.jpg", cv::IMREAD_GRAYSCALE);
cv::Mat img2 = cv::imread("scene2.jpg", cv::IMREAD_GRAYSCALE);

// 1) ORB로 양쪽 검출 + 기술
cv::Ptr<cv::ORB> orb = cv::ORB::create(1000);
std::vector<cv::KeyPoint> kp1, kp2;
cv::Mat desc1, desc2;
orb->detectAndCompute(img1, cv::noArray(), kp1, desc1);
orb->detectAndCompute(img2, cv::noArray(), kp2, desc2);

// 2) ORB는 이진 기술자 → NORM_HAMMING 필수
cv::BFMatcher matcher(cv::NORM_HAMMING);

// 3) 단순 매칭 — 각 기술자의 최근접 1개
std::vector<cv::DMatch> matches;
matcher.match(desc1, desc2, matches);

std::cout << "전체 매칭 수: " << matches.size() << std::endl;

// 매칭 결과 그리기
cv::Mat matchImg;
cv::drawMatches(img1, kp1, img2, kp2, matches, matchImg);
cv::imwrite("matches.jpg", matchImg);

cv::DMatch 하나는 매칭 쌍 하나를 나타낸다. queryIdx(첫 이미지 키포인트 인덱스), trainIdx(둘째 이미지 키포인트 인덱스), distance(두 기술자 거리)를 담는다. distance가 작을수록 닮은 쌍이다.

FLANN — 빠른 근사 매칭

기술자가 수천 개를 넘어가면 BFMatcher의 전수 비교는 부담스럽다. FLANN(Fast Library for Approximate Nearest Neighbors)은 인덱스 트리를 만들어 근사 최근접을 빠르게 찾는다. 정확도를 조금 양보하는 대신 훨씬 빠르다 — 대규모 매칭이나 실시간에 쓴다.

#include <opencv2/opencv.hpp>

// SIFT 실수 기술자라고 가정 (desc1, desc2는 CV_32F)
cv::Ptr<cv::SIFT> sift = cv::SIFT::create();
std::vector<cv::KeyPoint> kp1, kp2;
cv::Mat desc1, desc2;
sift->detectAndCompute(img1, cv::noArray(), kp1, desc1);
sift->detectAndCompute(img2, cv::noArray(), kp2, desc2);

// FLANN 기반 매처 — 기본 인덱스는 실수 기술자(L2)에 맞다
cv::FlannBasedMatcher flann;

// knnMatch — 각 기술자에 대해 가장 가까운 k개를 찾는다
std::vector<std::vector<cv::DMatch>> knnMatches;
flann.knnMatch(desc1, desc2, knnMatches, 2);  // k=2

std::cout << "knn 매칭 그룹 수: " << knnMatches.size() << std::endl;
기본 FLANN은 이진 기술자에 그대로 못 쓴다 cv::FlannBasedMatcher의 기본 인덱스는 실수 기술자(L2) 전용이다. ORB 같은 이진 기술자를 그냥 넣으면 오류가 나거나 결과가 엉망이 된다. 이진 기술자에 FLANN을 쓰려면 LshIndexParams로 LSH(지역 민감 해싱) 인덱스를 따로 구성해야 한다. 그래서 ORB에는 보통 BFMatcher(NORM_HAMMING)를 쓴다.

knnMatch가 단순 match와 다른 점은 최근접 1개가 아니라 k개를 돌려준다는 것이다. 위에서 k=2로 둔 이유는 다음 절의 ratio test 때문이다 — 1등과 2등 거리를 비교해야 좋은 매칭을 거를 수 있다.

좋은 매칭 거르기

매처는 "가장 가까운" 쌍을 무조건 돌려준다 — 그게 실제로 같은 점인지 아닌지는 신경 쓰지 않는다. 그래서 매칭 결과에는 항상 오매칭(false match)이 섞여 있다. 거르지 않고 그대로 쓰면 뒤 단계(호모그래피 추정 등)가 통째로 망가진다. 거르는 방법은 세 가지다.

Lowe's ratio test

SIFT를 만든 David Lowe가 제안한 방법이다. 각 기술자에 대해 1등과 2등의 거리 비율을 본다. 진짜 매칭이면 1등이 압도적으로 가깝다(비율이 작다). 1등과 2등이 비슷하게 가깝다면(비율이 크다) 그 점은 애매하니 버린다. 보통 임계값은 0.7~0.8이다.

// knnMatch로 k=2를 받아둔 상태 (knnMatches)
std::vector<cv::DMatch> goodMatches;
const float ratioThresh = 0.75f;  // Lowe 권장 0.7~0.8

for (const std::vector<cv::DMatch>& pair : knnMatches)
{
    if (pair.size() < 2)
    {
        continue;  // 2등이 없으면 비교 불가
    }

    // 1등 거리가 2등 거리의 75%보다 작아야 신뢰
    if (pair[0].distance < ratioThresh * pair[1].distance)
    {
        goodMatches.push_back(pair[0]);
    }
}

std::cout << "ratio test 통과: " << goodMatches.size()
          << " / " << knnMatches.size() << std::endl;
실행 결과 (콘솔)
ratio test 통과: 214 / 983

교차 검사 (crossCheck)

교차 검사는 발상이 단순하다. A의 점 a가 B의 점 b를 1등으로 골랐다면, b도 a를 1등으로 골라야 진짜 매칭이라고 본다. 한쪽만 짝사랑하는 매칭은 버린다. BFMatcher 생성자에서 crossCheck=true로 켠다.

// crossCheck=true — 양방향 1등이 일치하는 매칭만 반환
cv::BFMatcher matcher(cv::NORM_HAMMING, true);

std::vector<cv::DMatch> matches;
matcher.match(desc1, desc2, matches);  // 이미 교차 검증된 결과

std::cout << "교차 검사 통과 매칭: " << matches.size() << std::endl;
crossCheck와 knnMatch는 같이 못 쓴다 crossCheck=true로 만든 BFMatcher에 knnMatch를 호출하면 동작하지 않는다. 교차 검사는 단순 match와 함께 쓰고, ratio test는 knnMatch(k=2)와 함께 쓴다. 둘 중 하나를 택하거나, ratio test로 거른 뒤 직접 교차 검증 로직을 추가한다.

RANSAC으로 기하 검증

ratio test와 교차 검사는 기술자의 닮음만 본다. 하지만 닮은 패치가 우연히 엉뚱한 곳에 있을 수 있다. 마지막 관문은 기하학적 일관성 검증이다 — 진짜 매칭들은 하나의 변환(호모그래피 등)으로 설명되어야 한다. RANSAC은 매칭 다수가 동의하는 변환을 찾고, 그 변환에서 벗어나는 매칭(outlier)을 버린다.

// goodMatches: ratio test를 통과한 매칭들
std::vector<cv::Point2f> pts1, pts2;
for (const cv::DMatch& m : goodMatches)
{
    pts1.push_back(kp1[m.queryIdx].pt);
    pts2.push_back(kp2[m.trainIdx].pt);
}

// RANSAC으로 호모그래피 추정 + inlier 마스크 획득
std::vector<uchar> inlierMask;
cv::Mat H = cv::findHomography(pts1, pts2, cv::RANSAC,
                              3.0, inlierMask);  // 3.0px 허용 오차

// 마스크가 1인 매칭만 최종 inlier
std::vector<cv::DMatch> inlierMatches;
for (size_t i = 0; i < goodMatches.size(); ++i)
{
    if (inlierMask[i])
    {
        inlierMatches.push_back(goodMatches[i]);
    }
}

std::cout << "RANSAC inlier: " << inlierMatches.size()
          << " / " << goodMatches.size() << std::endl;
호모그래피는 다음 글에서 자세히 다룬다 여기서는 RANSAC이 "기하적으로 말이 안 되는 매칭을 걸러준다"는 역할만 짚는다. findHomography가 돌려주는 변환 행렬 H 자체와 그 의미 — 두 평면 사이의 사상 — 는 다음 글 「기하 변환과 호모그래피」에서 이어 다룬다.

정리하면 거르기는 단계적이다. ratio test로 애매한 매칭을 떨어내고 → (필요하면) 교차 검사로 한 번 더 → RANSAC으로 기하적으로 어긋난 것을 최종 제거한다. 각 단계가 다른 기준으로 거르므로 함께 쓸수록 결과가 깨끗해진다.

템플릿 매칭의 한계를 어떻게 보완하는가

앞 글에서 본 템플릿 매칭(matchTemplate)은 작은 패치를 픽셀 단위로 슬라이딩하며 비교한다. 빠르고 단순하지만 약점이 뚜렷하다 — 회전과 스케일 변화에 거의 무력하다. 대상이 조금만 돌아가거나 크기가 달라지면 점수가 급락한다. 조명이 바뀌어도 흔들린다.

특징점 매칭은 이 약점을 정면으로 메운다. 검출기 자체가 회전·스케일 불변으로 설계되었고, 기술자가 조명 변화를 어느 정도 흡수한다. 게다가 특징점은 대상의 일부만 보여도 — 가려지거나 화면 밖으로 일부 나가도 — 보이는 특징점만으로 매칭이 된다. 템플릿 매칭은 패치 전체가 보여야 하지만, 특징점은 부분 가림(occlusion)에 강하다.

둘은 경쟁이 아니라 도구함의 다른 칸이다 검사 대상이 항상 같은 자세·같은 크기로 들어온다면 템플릿 매칭이 더 빠르고 충분하다. 대상이 회전하거나 거리가 변하거나 일부가 가려질 수 있다면 특징점 매칭으로 올라간다. 현장에서는 두 기법을 상황에 따라 골라 쓴다.

흔한 함정

특징점 매칭에서 거의 모두가 한 번씩 밟는 함정들이다.

이진 기술자에 L2 norm 사용

ORB에는 NORM_HAMMING, SIFT에는 NORM_L2 ORB 같은 이진 기술자에 BFMatcher(NORM_L2)를 쓰면 비트열을 실수 벡터처럼 다루게 되어 거리가 의미를 잃는다 — 매칭이 통째로 엉망이 된다. 반대로 SIFT 실수 기술자에 NORM_HAMMING을 쓰는 것도 똑같이 틀렸다. 기술자 종류와 norm은 한 세트다. 검출기를 바꾸면 norm도 같이 바꾼다. 
// 나쁨 — ORB(이진)에 L2를 쓰면 거리가 무의미해진다
// cv::BFMatcher wrong(cv::NORM_L2);
// wrong.match(orbDesc1, orbDesc2, matches);  // 결과 엉망

// 좋음 — ORB는 해밍 거리
cv::BFMatcher orbMatcher(cv::NORM_HAMMING);

// 좋음 — SIFT는 L2 거리
cv::BFMatcher siftMatcher(cv::NORM_L2);

ratio test 생략으로 오매칭 폭증

match() 결과를 거르지 않고 그대로 쓰면 안 된다 matcher.match()는 모든 기술자에 대해 최근접 쌍을 무조건 하나씩 만든다 — 실제로 대응점이 없는 키포인트도 억지로 짝이 지어진다. 거르지 않으면 매칭 절반이 오매칭일 수 있고, 이걸 RANSAC에 넣으면 변환 추정이 실패한다. ratio test나 교차 검사 중 최소 하나는 반드시 거친다. 
// 나쁨 — 거르지 않은 raw 매칭을 그대로 사용
// matcher.match(desc1, desc2, matches);
// cv::findHomography(...);  // 오매칭 때문에 추정 실패 가능

// 좋음 — knnMatch + ratio test로 거른 뒤 사용
std::vector<std::vector<cv::DMatch>> knn;
matcher.knnMatch(desc1, desc2, knn, 2);

std::vector<cv::DMatch> good;
for (const auto& p : knn)
{
    if (p.size() == 2 && p[0].distance < 0.75f * p[1].distance)
    {
        good.push_back(p[0]);
    }
}
// 이제 good을 findHomography에 넘긴다

텍스처 없는 표면은 특징점이 부족하다

특징점은 밝기 변화가 있는 곳에서만 잡힌다. 균일한 금속판, 매끈한 플라스틱, 흰 벽처럼 텍스처가 없는 표면에서는 키포인트가 거의 안 나온다. 검출 수가 한 자릿수면 매칭이 불가능하다.

cv::Ptr<cv::ORB> orb = cv::ORB::create(1000);
std::vector<cv::KeyPoint> kp;
cv::Mat desc;
orb->detectAndCompute(plainSurface, cv::noArray(), kp, desc);

// 텍스처 없는 표면은 검출 수가 극히 적다
if (kp.size() < 20)
{
    std::cerr << "특징점 부족 (" << kp.size()
              << "개) — 조명·패턴 추가 검토 필요" << std::endl;
}
대안 — 조명을 바꾸거나 검사 방식을 바꾼다 텍스처가 없으면 특징점 매칭은 적합하지 않다. 측면 조명(grazing light)으로 표면의 미세한 굴곡을 드러내거나, 대상에 마커·패턴이 있는 부분을 기준으로 삼거나, 아예 엣지·윤곽 기반 검사(앞 글들에서 다룬 contour·blob)로 접근을 바꾸는 편이 낫다.

SIFT는 느리다 — 실시간에 무턱대고 쓰지 않는다

SIFT는 강력하지만 ORB보다 수 배에서 수십 배 느리다. 고해상도 이미지를 30fps로 처리해야 하는 인라인 검사에 SIFT를 그냥 넣으면 프레임이 밀린다.

실시간이면 ORB부터, 정밀도가 부족할 때만 SIFT로 먼저 ORB로 충분한지 측정한다. 스케일·시점 변화가 커서 ORB 매칭률이 낮을 때만 SIFT를 검토하되, 처리 영역을 ROI로 좁히거나, 이미지를 다운스케일하거나, 검출 주기를 낮추는(매 프레임 대신 N프레임마다) 식으로 비용을 관리한다. 처리 시간은 항상 실측한다 — 추측하지 않는다.
정리하면 특징점은 검출 → 기술 → 매칭의 3단계를 거친다. 검출기는 ORB(빠름·이진)와 SIFT(강건·실수)를 상황에 맞게 고르고, 기술자 종류에 맞는 norm(NORM_HAMMING / NORM_L2)을 짝지어 쓴다. 매칭 결과는 반드시 ratio test·교차 검사·RANSAC으로 거른다. 텍스처가 없는 표면에는 애초에 적합하지 않다는 점도 기억한다.
