Python 패키지 생태계

Python 코드를 다른 사람에게 전달하는 방법은 세 가지다. 소스 파일을 그대로 주거나, PyPI에 올려 pip install로 받게 하거나, 사내 인덱스·Git URL로 배포한다. 어느 쪽이든 패키징 표준을 따라야 재현 가능하고 의존성을 안전하게 묶을 수 있다.

코드 → pyproject → 빌드 → wheel/sdist → PyPI 업로드. 모든 단계가 표준화돼 있다.

세 가지 기둥

  • PyPI — pypi.org. 전 세계 Python 패키지가 모인 공식 저장소.
  • pip — PyPI에서 패키지를 받아 설치하는 표준 클라이언트.
  • venv — 프로젝트마다 독립된 인터프리터·패키지 디렉터리를 두는 가상환경.

모듈 vs 패키지

패키징을 이해하려면 먼저 모듈과 패키지의 차이를 분명히 한다.

구분실체임포트 예
모듈 (module)하나의 .py 파일import math
패키지 (package)__init__.py를 포함한 디렉터리import numpy
서브패키지패키지 안의 또 다른 패키지from numpy import linalg
네임스페이스 패키지__init__.py 없는 디렉터리 (PEP 420)여러 위치에 분산 가능

표준 디렉터리 구조 (src-layout)

my-vision-tool/
├── pyproject.toml          # 메타데이터·빌드 설정
├── README.md
├── LICENSE
├── src/
│   └── vision_tool/        # 실제 패키지 (배포 단위)
│       ├── __init__.py     # 패키지 표식 + 공개 API
│       ├── core.py         # 모듈
│       ├── filters.py
│       └── io/             # 서브패키지
│           ├── __init__.py
│           ├── reader.py
│           └── writer.py
├── tests/
│   ├── test_core.py
│   └── test_filters.py
└── .venv/                  # 가상환경 (gitignore)
왜 src-layout인가 src/ 안에 패키지를 두면 테스트가 설치된 패키지를 임포트하도록 강제된다. 작업 디렉터리에 우연히 같은 이름 폴더가 있어 "내 컴에선 되네" 식의 거짓 성공을 막아준다.

__init__.py의 역할

# src/vision_tool/__init__.py

# 1. 패키지의 공개 API를 정의한다.
from .core import ImageProcessor
from .filters import gaussian_blur, canny_edge

# 2. 버전을 노출한다.
__version__ = "0.1.0"

# 3. wildcard import 대상 제한
__all__ = ["ImageProcessor", "gaussian_blur", "canny_edge"]
# 사용자는 짧은 경로로 접근한다
from vision_tool import ImageProcessor, gaussian_blur
# 내부 모듈 경로(vision_tool.core)를 노출하지 않는다.

가상환경 복습

1편에서 다룬 venv를 패키징 관점에서 다시 본다. 패키지 개발자는 가상환경 없이는 단 한 줄도 시작하지 않는다.

# 프로젝트 루트에서
python -m venv .venv

# 활성화
source .venv/bin/activate           # Linux / macOS
.venv\Scripts\Activate.ps1          # Windows PowerShell

# 개발 모드로 자기 자신을 설치 (editable install)
pip install -e .

# 또는 개발용 의존성까지
pip install -e ".[dev]"

editable install (-e)

pip install -e .은 소스 파일을 심볼릭 링크처럼 가상환경에 연결한다. 코드를 수정하면 재설치 없이 즉시 반영된다. 패키지 개발 중에는 반드시 이 방식으로 설치한다.

requirements.txt의 한계

# 흔히 쓰는 방식
pip freeze > requirements.txt

이 파일은 현재 설치된 모든 패키지의 평면 목록일 뿐이다. 직접 의존성과 간접(전이) 의존성을 구분하지 못하고, 다른 플랫폼·Python 버전에서 동일한 해결을 보장하지 않는다. 진짜 재현성이 필요하면 lockfile을 쓰는 도구로 넘어가야 한다.

현대 도구 — uv·poetry·hatch·pdm

pip + venv는 표준이지만 의존성 해결이 느리고 lockfile이 없다. 최근에는 uv가 사실상 새 표준 자리를 차지하고 있다.

도구구현특징추천 용도
uvRustpip의 10~100배. venv·pip·pyenv 통합. lockfile 내장2026년 기준 새 프로젝트의 기본
poetryPython의존성 해결·lockfile·빌드·게시 일체화. 오래된 안정성중대형 라이브러리, 팀 표준이 잡힌 곳
hatchPythonPyPA 공식. 멀티 환경·매트릭스 테스트. hatchling 백엔드 제공여러 Python 버전·환경 매트릭스가 필요한 라이브러리
pdmPythonPEP 표준 충실. PEP 582(가상환경 없이 __pypackages__) 지원PEP 표준만 쓰고 싶을 때
pip + venvPython표준 기본기. lockfile 없음학습·간단 스크립트
이 시리즈에서는 uv를 권장한다 Rust로 작성돼 압도적으로 빠르고, pyproject.toml 표준을 그대로 따른다. pip·venv·pip-tools·pyenv가 했던 일을 한 바이너리에서 처리한다. 산업 환경에서 의존성 설치 시간을 분 단위에서 초 단위로 줄여 준다.

uv 사용 흐름

# 설치 — Windows
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"
# 또는 pipx / brew
pipx install uv
brew install uv

# 프로젝트 초기화
uv init my-vision-tool
cd my-vision-tool

# 의존성 추가 (자동으로 .venv 생성 + 설치 + lockfile 갱신)
uv add numpy opencv-python
uv add --dev pytest ruff mypy        # 개발 의존성

# 실행 (자동으로 .venv 사용)
uv run python -m vision_tool
uv run pytest

# lockfile 기반 동기화 (협업자가 클론 후)
uv sync

poetry 흐름 (비교)

pipx install poetry
poetry new my-vision-tool --src
cd my-vision-tool

poetry add numpy opencv-python
poetry add --group dev pytest

poetry install                       # lockfile 기반 설치
poetry run pytest
poetry build                         # sdist + wheel 생성
poetry publish                       # PyPI 업로드

pyproject.toml 표준

PEP 518(2016)이 pyproject.toml을 빌드 설정 파일로 도입했고, PEP 621(2020)이 프로젝트 메타데이터의 표준 위치로 확장했다. 이제 setup.py·setup.cfg는 레거시고, 모든 새 프로젝트는 pyproject.toml 하나로 통일한다.

기본 골격

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "vision-tool"
version = "0.1.0"
description = "Industrial vision utilities"
readme = "README.md"
requires-python = ">=3.10"
license = { text = "MIT" }
authors = [
    { name = "Your Name", email = "you@example.com" },
]
keywords = ["vision", "image-processing", "opencv"]
classifiers = [
    "Programming Language :: Python :: 3",
    "License :: OSI Approved :: MIT License",
    "Operating System :: OS Independent",
    "Topic :: Scientific/Engineering :: Image Processing",
]
dependencies = [
    "numpy>=1.24",
    "opencv-python>=4.10",
    "pillow>=10.0",
]

[project.optional-dependencies]
dev = ["pytest>=8.0", "ruff", "mypy"]
gpu = ["cupy-cuda12x"]

[project.urls]
Homepage = "https://github.com/you/vision-tool"
Issues = "https://github.com/you/vision-tool/issues"

[project.scripts]
vision-cli = "vision_tool.cli:main"     # 콘솔 명령으로 노출

주요 필드

필드의미
[build-system]이 프로젝트를 빌드할 때 필요한 도구. pip이 격리 환경에서 먼저 설치한다
[project]PEP 621 표준 메타데이터. 이름·버전·설명·의존성
dependencies런타임 필수 의존성. pip install 시 함께 설치
optional-dependenciesextra. pip install vision-tool[dev,gpu]로 선택 설치
[project.scripts]설치 시 PATH에 노출될 콘솔 명령
[tool.*]도구별 설정 (ruff·pytest·mypy 등)

버전 지정자 (PEP 440)

dependencies = [
    "numpy>=1.24,<2.0",       # 범위
    "opencv-python==4.10.*",   # 와일드카드
    "torch~=2.3.0",            # compatible release (2.3.* 허용)
    "pillow!=10.1.0",          # 특정 버전 제외
]

빌드 백엔드 선택

빌드 백엔드는 소스 트리를 sdist·wheel로 만드는 도구다. [build-system]의 build-backend로 지정한다. 백엔드는 바꿔도 결과물의 형식은 동일하다.

백엔드장점단점
setuptools가장 오래되고 호환성 최고. C 확장 빌드의 사실상 표준설정이 복잡. 레거시 코드와 섞임
hatchling가볍고 빠름. PyPA 공식 권장. 순수 Python에 최적네이티브 확장은 어색
poetry-corepoetry와 자연스럽게 통합poetry 생태계에 묶임
pdm-backendpdm과 통합. PEP 표준 충실점유율 낮음
scikit-build-core / meson-pythonCMake·Meson 기반. C++ 확장에 최적설정 비용
# setuptools 예시
[build-system]
requires = ["setuptools>=68", "wheel"]
build-backend = "setuptools.build_meta"

[tool.setuptools.packages.find]
where = ["src"]
# hatchling 예시 (권장 — 순수 Python)
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]
packages = ["src/vision_tool"]

빌드 — sdist와 wheel

표준 빌드 명령은 단 한 줄이다.

pip install build       # 한 번만
python -m build         # dist/ 폴더에 sdist + wheel 생성
실행 결과
* Creating isolated environment: venv+pip... * Installing packages in isolated environment: - hatchling * Building sdist... * Building wheel from sdist Successfully built vision_tool-0.1.0.tar.gz and vision_tool-0.1.0-py3-none-any.whl

sdist vs wheel

산출물확장자형식설치 속도네이티브 확장
sdist (source distribution).tar.gz소스 코드 압축느림 (설치 시 빌드)설치 시 컴파일러 필요
wheel.whl빌드된 ZIP 아카이브빠름 (압축만 해제)플랫폼별 prebuilt 가능

wheel 파일명은 호환성 태그를 포함한다.

# 순수 Python 패키지 — 모든 환경에서 동작
vision_tool-0.1.0-py3-none-any.whl

# 플랫폼·Python 버전별 — numpy, opencv 같은 네이티브 확장
numpy-1.26.4-cp312-cp312-win_amd64.whl
numpy-1.26.4-cp312-cp312-manylinux_2_17_x86_64.whl
numpy-1.26.4-cp312-cp312-macosx_11_0_arm64.whl
# {name}-{version}-{python}-{abi}-{platform}.whl
wheel을 반드시 함께 배포한다 sdist만 올리면 사용자는 설치 시점에 컴파일러·헤더가 필요해진다. 순수 Python이면 py3-none-any.whl 하나로 충분하고, 네이티브 확장이면 cibuildwheel·CI 매트릭스로 플랫폼별 wheel을 모두 만든다.

PyPI 배포 — twine

빌드한 산출물을 PyPI에 올릴 때는 twine을 쓴다. python setup.py upload는 절대 쓰지 않는다(보안·인증 문제).

TestPyPI 먼저

실제 PyPI는 이름을 한 번 쓰면 회수 불가다. 잘못 올린 버전은 다시 같은 번호로 올릴 수 없다. 먼저 TestPyPI에서 리허설한다.

pip install twine

# TestPyPI 업로드 (https://test.pypi.org 계정·토큰 필요)
twine upload --repository testpypi dist/*

# TestPyPI에서 설치 검증
pip install --index-url https://test.pypi.org/simple/ \
            --extra-index-url https://pypi.org/simple/ \
            vision-tool

# 문제 없으면 진짜 PyPI로
twine upload dist/*

API 토큰

2024년부터 PyPI는 비밀번호 대신 API 토큰을 요구한다. ~/.pypirc에 저장하거나 환경 변수로 전달한다.

# ~/.pypirc
[pypi]
username = __token__
password = pypi-AgEIcHlwaS5vcmcC...

# 또는 환경 변수
export TWINE_USERNAME=__token__
export TWINE_PASSWORD=pypi-AgEIcHlwaS5vcmcC...
Trusted Publishing (OIDC) 권장 GitHub Actions에서 PyPI로 배포할 때는 토큰조차 저장하지 않는 Trusted Publishing을 쓸 수 있다. PyPI 프로젝트 설정에서 GitHub 저장소·워크플로명을 등록하면 OIDC로 자동 인증된다.

버전 관리

패키지 버전은 Semantic Versioning(MAJOR.MINOR.PATCH)을 따른다.

  • MAJOR — 하위 호환을 깨는 변경.
  • MINOR — 하위 호환되는 기능 추가.
  • PATCH — 하위 호환되는 버그 수정.

사전 릴리스는 PEP 440이 정의한 접미사를 쓴다.

0.1.0a1     # alpha
0.1.0b2     # beta
0.1.0rc1    # release candidate
0.1.0       # final
0.1.0.post1 # post release (메타데이터 수정 등)
0.1.0.dev3  # development

버전 단일 출처

버전을 pyproject.toml·__init__.py·Git 태그 세 군데에 적으면 반드시 어긋난다. 단일 출처에서 읽는다.

# src/vision_tool/__init__.py
from importlib.metadata import version, PackageNotFoundError

try:
    __version__ = version("vision-tool")     # 설치된 메타데이터에서 읽음
except PackageNotFoundError:
    __version__ = "0.0.0+unknown"
# hatch는 동적 버전을 지원한다 — 코드의 __version__ 읽어 옴
[project]
name = "vision-tool"
dynamic = ["version"]

[tool.hatch.version]
path = "src/vision_tool/__about__.py"

C++ 확장 — pybind11·Cython

OpenCV·NumPy·PyTorch가 빠른 이유는 C/C++ 코드를 Python에 바인딩하기 때문이다. 직접 C++ 확장을 만들 때는 pybind11이 사실상 표준이다.

# pyproject.toml — scikit-build-core + pybind11
[build-system]
requires = ["scikit-build-core>=0.8", "pybind11>=2.12"]
build-backend = "scikit_build_core.build"

[project]
name = "fast-blur"
version = "0.1.0"
requires-python = ">=3.10"
# src/fast_blur/__init__.py
from ._core import gaussian_blur     # C++로 작성된 함수
__all__ = ["gaussian_blur"]
# C++ 쪽 (src/_core.cpp) — pybind11
#include <pybind11/pybind11.h>
#include <pybind11/numpy.h>
namespace py = pybind11;

py::array_t<uint8_t> gaussian_blur(py::array_t<uint8_t> input, int ksize)
{
    // ... OpenCV 호출 ...
    return input;
}

PYBIND11_MODULE(_core, m)
{
    m.def("gaussian_blur", &gaussian_blur, "Apply Gaussian blur");
}

Cython은 Python과 비슷한 문법으로 C 확장을 작성하는 도구다. NumPy 내부의 많은 부분이 Cython으로 작성됐다. 새 프로젝트라면 pybind11이 더 자연스럽다.

cibuildwheel로 모든 플랫폼 빌드 네이티브 확장을 배포할 때는 GitHub Actions에서 cibuildwheel을 돌려 Linux·macOS·Windows × Python 3.10~3.13 매트릭스 wheel을 자동 생성한다. 그렇지 않으면 사용자가 컴파일러를 직접 갖춰야 한다.

lockfile과 재현성

pyproject.toml은 "무엇을 원하는가"를 적는다. lockfile은 "실제로 무엇이 어디서 설치됐는가"를 한 줄도 빠짐없이 기록한다.

도구lockfile커밋 대상
uvuv.lock예
poetrypoetry.lock예
pdmpdm.lock예
pip-toolsrequirements.txt (해시 포함 컴파일된)예
# pip-tools — pip + venv 표준에서 lockfile 흉내
pip install pip-tools

# requirements.in (사람이 작성)
# ----------
# numpy
# opencv-python
# ----------

pip-compile requirements.in --generate-hashes
# requirements.txt가 해시 포함으로 만들어짐
pip-sync requirements.txt
lockfile 없는 협업은 사실상 비결정적 직접 의존성만 적어 두면 전이 의존성은 설치 시점마다 달라진다. 어제는 잘 돌던 코드가 오늘 빌드에서 새로 올라온 마이너 버전 때문에 깨진다. 라이브러리는 lockfile을 안 올리고 애플리케이션·서비스는 반드시 올린다.

산업·연구 — 사내 패키지 배포

회사 코드를 공개 PyPI에 올릴 수는 없다. 대신 사내 인덱스나 Git URL을 쓴다.

사내 인덱스 (Nexus·Artifactory·devpi)

# 사내 인덱스 + 공개 PyPI를 함께 사용
pip install vision-tool \
    --index-url https://pypi.company.local/simple/ \
    --extra-index-url https://pypi.org/simple/

# 영구 설정 — pip.conf
# Linux/macOS: ~/.config/pip/pip.conf
# Windows:     %APPDATA%\pip\pip.ini
[global]
index-url = https://pypi.company.local/simple/
extra-index-url = https://pypi.org/simple/

Git URL 직접 설치

# 인덱스를 안 두고 GitLab/GitHub에서 바로 설치
pip install git+https://code.vieworks.com/vision/vision-tool.git@v0.1.0

# pyproject.toml에서도 가능
# dependencies = [
#   "vision-tool @ git+https://code.vieworks.com/vision/vision-tool.git@v0.1.0",
# ]

# 특정 브랜치·커밋·서브디렉터리
pip install "git+https://.../mono-repo.git@main#subdirectory=packages/vision-tool"

로컬 wheel 배포

# 빌드한 wheel을 사내 공유 폴더에 두고 직접 설치
pip install \\fileserver\packages\vision_tool-0.1.0-py3-none-any.whl

# 또는 폴더를 인덱스처럼 사용
pip install --find-links \\fileserver\packages vision-tool
실무 권장 구조 사내 GitLab의 CI에서 태그를 푸시할 때마다 python -m build로 wheel을 만들고, Nexus 사내 인덱스에 자동 업로드한다. 사용자는 pip install company-vision-tool만 치면 된다. 공개 PyPI와 분리돼 보안 검토도 단순해진다.

흔한 함정

1. 시스템 pip을 그대로 쓴다 sudo pip install ...이나 venv 밖 글로벌 설치는 OS·다른 프로젝트와 충돌을 부른다. PEP 668 이후 최신 pip은 이를 거부한다. 무조건 venv 안에서만 설치한다.
2. requirements.txt만으로는 lock이 안 된다 pip freeze는 평면 목록이고 해시·플랫폼 정보가 없다. 진짜 재현성이 필요하면 uv·poetry·pip-tools의 lockfile을 쓴다.
3. 가상환경 없이 글로벌에 설치 프로젝트 A는 numpy 1.21, B는 numpy 1.26이 필요하면 글로벌은 한쪽을 깬다. 프로젝트 = 가상환경 = lockfile이 1:1이 되도록 한다.
4. 빌드 메타데이터 누락 setup.py·setup.cfg만 있고 pyproject.toml이 없으면 최신 pip이 격리 빌드를 만들지 못해 실패하기도 한다. 새 프로젝트는 pyproject.toml 단일 파일로 시작한다.
5. 버전을 여러 곳에 중복 기록 pyproject.toml·__init__.py·Git 태그·CHANGELOG가 제각각이 된다. importlib.metadata.version() 한 곳에서 읽거나, hatch의 dynamic = ["version"]으로 단일 출처를 보장한다.
6. sdist만 배포 wheel을 함께 올리지 않으면 네이티브 확장은 설치자 머신에서 컴파일된다. 컴파일러·헤더가 없는 사용자는 그냥 실패한다. cibuildwheel로 플랫폼 매트릭스를 빌드해서 wheel을 함께 올린다.
7. PyPI 이름 선점 한 번 올린 버전 번호는 같은 번호로 재업로드할 수 없다. 잘못 올리면 0.1.1로 새 버전을 올려야 한다. 진짜 PyPI 전에 TestPyPI에서 반드시 리허설한다.
8. editable install 없이 개발 pip install -e . 없이 자기 패키지를 임포트하려고 sys.path를 만지작거리는 코드는 자라면 반드시 부패한다. 항상 editable install로 자기 자신을 가상환경에 등록한다.
