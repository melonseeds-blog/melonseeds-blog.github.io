Python의 예외 — EAFP 철학

Python에서 예외(exception)는 단순한 오류 신호가 아니라 정상 흐름을 통제하는 메커니즘의 하나다. 파일이 없을 때, 키가 사전에 없을 때, 반복자가 끝났을 때 모두 예외로 처리한다. 그래서 Python 프로그래머는 다음 원칙을 따른다.

EAFP — Easier to Ask Forgiveness than Permission "쉽게 허락받기보다 용서 구하기". 미리 조건을 검사하기보다 일단 시도하고 실패하면 그때 처리한다는 Pythonic한 사고방식이다.

C++이나 Java처럼 예외가 "비정상 상황"만을 의미하지 않는다. for 루프 종료도 내부적으로는 StopIteration 예외다. 그러니 예외 처리는 "에러 잡기"가 아니라 "흐름 분기"로 받아들이는 것이 자연스럽다.

try / except / else / finally

Python의 예외 처리 블록은 최대 4개 절로 구성된다. 각 절의 역할과 실행 시점은 다음과 같다.

절실행 시점주 용도
try항상 진입, 본문 실행예외가 발생할 수 있는 코드
except매칭되는 예외 발생 시예외 처리 / 복구
else예외가 없었을 때만예외 없을 때만 실행할 후속 작업
finally예외 유무와 무관하게 항상리소스 정리 (close, unlock)
def read_int(path):
    try:
        f = open(path, "r", encoding="utf-8")
        value = int(f.read())
    except FileNotFoundError:
        print("파일이 없다.")
        return None
    except ValueError:
        print("정수 형식이 아니다.")
        return None
    else:
        # 예외가 없었을 때만 실행
        print(f"성공적으로 읽었다: {value}")
        return value
    finally:
        # 예외 유무와 관계없이 반드시 실행
        try:
            f.close()
        except NameError:
            pass
else의 진짜 가치 try 안에 너무 많은 코드를 넣으면 어느 줄에서 예외가 나는지 흐려진다. "예외가 날 가능성이 있는 줄"만 try에 두고, 정상 흐름은 else로 분리하면 의도가 명확해진다.

except 절 사용법

특정 예외 잡기

예외 타입은 가능한 구체적으로 지정한다. 막연한 except:는 KeyboardInterrupt까지 잡아 Ctrl+C도 무력화시킨다.

try:
    x = int(input("숫자 입력: "))
except ValueError:
    print("정수가 아니다.")

여러 예외를 하나로 묶기

처리 방식이 같다면 튜플로 묶는다.

try:
    do_something()
except (ValueError, TypeError, KeyError) as e:
    print(f"입력 오류: {e}")

as 키워드로 예외 객체 받기

예외 객체에는 메시지·인자·트레이스백 정보가 담겨 있다.

try:
    int("hello")
except ValueError as e:
    print(type(e).__name__)  # ValueError
    print(e.args)            # ("invalid literal for int() with base 10: 'hello'",)
    print(str(e))            # invalid literal for int() with base 10: 'hello'

여러 except 절 — 위에서 아래로 매칭

예외 매칭은 위에서 아래로 순서대로 시도된다. 구체적인 예외를 위에, 일반적인 예외를 아래에 둔다.

try:
    risky()
except FileNotFoundError:        # 구체적
    print("파일 없음")
except OSError:                  # FileNotFoundError의 부모
    print("OS 오류")
except Exception as e:           # 가장 일반적 — 마지막
    print(f"기타 오류: {e}")
순서가 뒤바뀌면 안 잡힌다 except OSError가 위에 있으면 FileNotFoundError도 거기서 잡혀버려서, 그 아래 except FileNotFoundError는 영원히 실행되지 않는다.

예외 계층 구조

모든 내장 예외는 BaseException에서 출발하는 트리를 이룬다. 사용자 코드에서는 보통 Exception을 기준으로 다룬다.

BaseException
 ├── SystemExit              # sys.exit() — 잡지 말 것
 ├── KeyboardInterrupt       # Ctrl+C — 잡지 말 것
 ├── GeneratorExit
 └── Exception               # ★ 사용자 예외는 여기 아래
      ├── ArithmeticError
      │    ├── ZeroDivisionError
      │    └── OverflowError
      ├── LookupError
      │    ├── IndexError
      │    └── KeyError
      ├── ValueError
      ├── TypeError
      ├── AttributeError
      ├── NameError
      ├── OSError
      │    ├── FileNotFoundError
      │    ├── PermissionError
      │    └── TimeoutError
      ├── RuntimeError
      │    └── RecursionError
      └── StopIteration
예외발생 상황
ValueError타입은 맞지만 값이 부적절 — int("abc")
TypeError타입 자체가 부적절 — "a" + 1
KeyError딕셔너리에 키가 없음
IndexError시퀀스 인덱스 범위 초과
AttributeError객체에 속성 없음
OSError파일·네트워크 등 OS 관련 오류
StopIteration반복자 종료 (내부적 사용)
BaseException은 잡지 말 것 except BaseException:이나 맨 except:는 KeyboardInterrupt, SystemExit까지 삼킨다. 사용자가 Ctrl+C로도 못 끄는 프로그램을 만들지 말자. 항상 except Exception:까지만 잡는다.

raise — 예외 발생과 체이닝

기본 raise

def set_age(age):
    if not isinstance(age, int):
        raise TypeError(f"age는 int여야 한다: {type(age).__name__}")
    if age < 0:
        raise ValueError(f"age는 0 이상이어야 한다: {age}")
    return age

재발생 (re-raise)

로깅만 하고 예외는 그대로 위로 넘기고 싶을 때 인자 없이 raise만 쓴다.

try:
    do_work()
except ValueError:
    log.exception("처리 실패, 상위로 위임")
    raise   # 동일 예외를 그대로 다시 던진다

원인 체이닝 — raise X from Y

저수준 예외를 의미 있는 도메인 예외로 변환하면서, 원인을 보존한다.

class ConfigError(Exception):
    pass

def load_config(path):
    try:
        with open(path) as f:
            return parse(f.read())
    except FileNotFoundError as e:
        raise ConfigError(f"설정 파일을 찾을 수 없다: {path}") from e
트레이스백 출력
FileNotFoundError: [Errno 2] No such file or directory: 'config.ini' The above exception was the direct cause of the following exception: ConfigError: 설정 파일을 찾을 수 없다: config.ini

from None을 쓰면 원인을 의도적으로 숨길 수 있다. from을 생략해도 암묵적 체이닝(__context__)은 남는다.

커스텀 예외 만들기

도메인에 의미 있는 이름을 가진 예외는 가독성을 크게 높인다. Exception을 상속하는 것으로 충분하다.

class ImageError(Exception):
    """이미지 처리 관련 예외의 베이스."""

class ImageLoadError(ImageError):
    """이미지를 디스크에서 읽지 못했다."""

class ImageFormatError(ImageError):
    """지원하지 않는 이미지 포맷이다."""
    def __init__(self, path, fmt):
        super().__init__(f"지원하지 않는 포맷: {fmt} ({path})")
        self.path = path
        self.fmt = fmt

# 사용 측
try:
    img = load_image("frame.xyz")
except ImageFormatError as e:
    print(f"포맷 오류: {e.fmt}, 경로: {e.path}")
except ImageError:
    print("이미지 처리 중 오류")
패키지마다 베이스 예외를 둔다 라이브러리를 만든다면 모든 커스텀 예외가 한 베이스(예: ImageError)를 상속하게 하자. 사용자가 except ImageError 한 줄로 라이브러리 예외만 깔끔히 잡을 수 있다.

EAFP vs LBYL

LBYL(Look Before You Leap, 뛰기 전에 살펴라)은 사전 검사를 우선하는 방식이고, EAFP는 일단 시도하고 실패하면 처리하는 방식이다.

# LBYL — C 스타일
if "key" in d and isinstance(d["key"], int):
    use(d["key"])

# EAFP — Pythonic
try:
    use(d["key"])
except (KeyError, TypeError):
    pass
관점EAFPLBYL
철학시도 후 처리사전 확인
경쟁 조건없음 (원자적)존재 (체크 사이에 변경 가능)
성공 빈도 높을 때 성능유리 (예외 없음)불리 (매번 체크)
실패 빈도 높을 때 성능불리 (예외 비용)유리
스타일Pythonic전통적 / 명시적
파일 검사 — EAFP가 안전 if os.path.exists(p): open(p) 사이에 파일이 사라지면 LBYL은 실패한다. try: open(p) except FileNotFoundError가 원자적이라 안전하다.

assert — 디버깅용 단언

assert는 "이 조건이 참이어야만 하는 불변식"을 표현한다. 거짓이면 AssertionError가 발생한다.

def average(values):
    assert len(values) > 0, "values가 비어 있다"
    return sum(values) / len(values)
assert를 입력 검증에 쓰지 말 것 Python을 -O(최적화) 옵션으로 실행하면 모든 assert가 통째로 제거된다. 사용자 입력·외부 데이터 검증은 반드시 if ... raise로 작성한다. assert는 "개발자의 가정"을 표현하는 용도다. 
# 나쁜 예 — -O 옵션에서 통째로 사라진다
def set_age(age):
    assert age >= 0   # ❌ 사용자 입력 검증

# 좋은 예
def set_age(age):
    if age < 0:
        raise ValueError("age는 0 이상이어야 한다")   # ✅

logging과 결합

예외를 잡으면 정보가 사라지기 쉽다. 트레이스백은 logging.exception()이나 logger.error(..., exc_info=True)로 보존한다.

import logging
log = logging.getLogger(__name__)

def process(item):
    try:
        do_work(item)
    except ValueError:
        # 트레이스백까지 자동으로 포함된다 (level=ERROR)
        log.exception("item 처리 실패: %r", item)
    except Exception:
        log.exception("예기치 못한 오류")
        raise   # 위로 다시 던진다
메서드레벨트레이스백 포함
log.exception(msg)ERROR자동 포함 (except 블록 안에서만)
log.error(msg, exc_info=True)ERROR포함
log.error(msg)ERROR미포함 (메시지만)

Exception Groups (3.11+)

Python 3.11에서 도입된 ExceptionGroup은 여러 예외를 동시에 묶어 던지는 기능이다. 비동기 작업이나 병렬 처리에서 여러 작업이 동시에 실패한 경우를 자연스럽게 표현한다.

# 여러 예외를 묶어 던지기
def run_all():
    errors = []
    for task in tasks:
        try:
            task.run()
        except Exception as e:
            errors.append(e)
    if errors:
        raise ExceptionGroup("작업 일부가 실패했다", errors)

# except* 로 그룹 안의 특정 타입만 골라 잡기
try:
    run_all()
except* ValueError as eg:
    print(f"ValueError {len(eg.exceptions)}건")
except* OSError as eg:
    print(f"OSError {len(eg.exceptions)}건")
except* 의 특이점 일반 except는 첫 번째로 매칭된 절만 실행되지만, except*는 그룹 안의 예외들을 타입별로 여러 절이 동시에 처리할 수 있다. asyncio.TaskGroup이 이 방식으로 자식 예외를 모은다.

흔한 함정

침묵 처리 — except: pass

# ❌ 매우 나쁜 코드
try:
    important_work()
except:
    pass   # 모든 예외를 조용히 삼킨다. 버그가 영원히 숨는다.
가장 흔하고 가장 위험한 안티패턴 예외를 무시해야 한다면 최소한 구체 타입을 지정하고, 의도를 주석으로 남기거나 log.debug로 흔적을 남긴다. contextlib.suppress(ValueError)도 의도를 명확히 드러내는 좋은 선택지다. 
# ✅ 의도를 명확히 — 특정 예외만 의도적으로 무시
from contextlib import suppress
with suppress(FileNotFoundError):
    os.remove(tmp_path)

너무 광범위한 catch

# ❌ 정확히 무엇을 처리하는지 알 수 없다
try:
    user = db.get_user(user_id)
    send_email(user.email, render(template))
    audit.log(user_id)
except Exception:
    return "error"

세 줄 모두 예외 가능성이 있지만 원인이 무엇인지 알 수 없다. DB 오류와 이메일 오류는 처리도 달라야 한다. 가능하면 좁은 범위 + 구체 예외로 분리한다.

finally에서 return — 예외 삼킴

# ❌ finally의 return이 예외를 삼킨다
def risky():
    try:
        raise ValueError("문제 발생")
    finally:
        return "ok"   # ValueError가 사라지고 "ok"가 반환된다

print(risky())   # "ok" — 예외가 어디로 갔는지 모른다
finally에서는 return·break·continue 금지 이 흐름 제어문들은 예외를 조용히 삼킨다. finally는 정리(close, unlock, 자원 반환)만 하고, 흐름 제어는 try나 except에서 처리한다.

assert로 입력 검증

앞서 다뤘듯, -O 옵션에서 assert가 모두 사라진다. 외부 입력 검증은 반드시 if ... raise로 작성한다.

잘못된 예외 타입

관습을 따르지 않으면 호출자가 잡기 어렵다.

# ❌ 모든 오류에 Exception
raise Exception("나이가 음수")

# ✅ 의미에 맞는 구체 타입
raise ValueError("나이는 0 이상이어야 한다")
