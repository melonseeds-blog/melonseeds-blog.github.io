좋은 모듈 설계의 두 축

소프트웨어를 여러 모듈로 나누는 이유는 단순하다. 한 번에 머릿속에 담을 수 있는 크기로 문제를 쪼개기 위해서다. 그런데 잘못 쪼개면 오히려 더 복잡해진다. 모듈을 어떻게 나눠야 잘 나눈 것인지 판단하는 기준이 바로 결합도(coupling)와 응집도(cohesion)다.

결론부터 말하면 원칙은 하나다. 결합도는 낮게, 응집도는 높게. 이 두 개념은 1970년대 구조적 설계(structured design)에서 나왔지만, 객체지향이든 함수형이든 마이크로서비스든 설계의 좋고 나쁨을 가르는 기준은 지금도 동일하다.

개념보는 대상목표한 줄 정의
결합도모듈 사이의 관계낮을수록 좋음한 모듈이 다른 모듈을 얼마나 알아야 하는가
응집도모듈 내부의 관계높을수록 좋음한 모듈 안의 요소들이 얼마나 한 가지 일에 집중하는가

왜 이 두 가지가 핵심인가. 소프트웨어 비용의 대부분은 작성이 아니라 변경에서 나온다. 결합도가 낮으면 한 모듈을 고칠 때 다른 모듈을 건드릴 일이 적다. 응집도가 높으면 어떤 기능을 고쳐야 할 때 어디를 봐야 하는지 명확하다. 둘 다 결국 "변경의 파급을 좁게 가둔다"는 같은 목표를 향한다.

두 개념은 짝으로 본다 결합도만 낮추거나 응집도만 높이는 경우는 드물다. 보통 모듈을 잘 나누면 둘 다 좋아지고, 잘못 나누면 둘 다 나빠진다. 그래서 항상 함께 평가한다.

결합도란 무엇인가

결합도는 한 모듈이 다른 모듈에 의존하는 정도다. A가 B를 호출하고, B의 내부 구조를 알고, B가 바뀌면 A도 바뀌어야 한다면 A와 B는 강하게 결합돼 있다.

결합도가 높으면 무슨 일이 벌어지는가. 한 곳을 수정했을 때 연쇄적으로 다른 곳도 수정해야 한다. 이를 변경의 파급(ripple effect)이라 부른다. 다음 예를 보면 감이 온다.

// 강한 결합 — Report가 Database의 내부 구현을 직접 안다
class Database
{
public:
    MYSQL* GetRawConnection();   // 내부 구현(MySQL)이 그대로 노출됨
};

class Report
{
public:
    void Generate(Database& db)
    {
        MYSQL* conn = db.GetRawConnection();   // MySQL API에 직접 의존
        mysql_query(conn, "SELECT ...");       // DB를 PostgreSQL로 바꾸면 Report도 수정
    }
};

위 코드에서 Report는 Database가 MySQL을 쓴다는 사실까지 알고 있다. DB 엔진을 바꾸면 Report도 같이 깨진다. 의존이 "있다 / 없다"의 문제가 아니라 "얼마나 깊이 의존하느냐"의 문제라는 점이 핵심이다. 의존 자체는 피할 수 없다. 다만 그 의존을 얕고 명확하게 만드는 것이 목표다.

결합도의 7가지 수준

결합도는 한 덩어리가 아니라 단계가 있다. 아래는 나쁨에서 좋음 순으로 정리한 스펙트럼이다.

결합도 스펙트럼 — 왼쪽이 피해야 할 강한 결합, 오른쪽이 지향할 약한 결합
수준이름설명평가
1내용 결합
(Content)		한 모듈이 다른 모듈의 내부 데이터나 코드를 직접 건드린다. 다른 클래스의 private 멤버를 친구(friend)로 직접 수정하는 경우.최악
2공통 결합
(Common)		여러 모듈이 같은 전역 변수를 공유한다. 누가 언제 그 값을 바꾸는지 추적이 안 된다.매우 나쁨
3외부 결합
(External)		모듈들이 외부에서 정해진 데이터 포맷·프로토콜·디바이스 인터페이스에 함께 묶인다.나쁨
4제어 결합
(Control)		한 모듈이 다른 모듈에 "무엇을 할지" 지시하는 제어 플래그를 넘긴다. 호출하는 쪽이 받는 쪽의 내부 로직을 알아야 한다.보통
5스탬프 결합
(Stamp)		필요한 값 하나만 쓰면 되는데 구조체·객체 전체를 통째로 넘긴다. 받는 쪽이 안 쓰는 필드까지 알게 된다.괜찮음
6자료 결합
(Data)		꼭 필요한 기본형 데이터만 매개변수로 주고받는다. 의존이 가장 얕고 명확하다.가장 좋음

전통적으로는 위 6단계로 정리하지만, 가장 이상적인 7번째 상태로 결합 없음(no coupling)을 두기도 한다. 두 모듈이 서로 전혀 모르는 상태다. 다만 협력 없이는 프로그램이 동작하지 않으므로, 현실의 목표는 "자료 결합"까지 내려오는 것이다.

아래는 제어 결합을 자료 결합 쪽으로 개선한 예다.

// 제어 결합 — 호출하는 쪽이 플래그로 내부 동작을 지시
void ProcessImage(Image& img, int mode)
{
    if (mode == 1)      ApplyBlur(img);
    else if (mode == 2) ApplySharpen(img);   // 호출자가 mode 의미를 다 알아야 함
}

// 자료 결합 — 각 동작을 별도 함수로, 필요한 데이터만 전달
void BlurImage(Image& img, int kernelSize);
void SharpenImage(Image& img, double amount);
// 호출자는 원하는 함수를 직접 고른다. 플래그 해석이 사라진다.

응집도란 무엇인가

응집도는 한 모듈 내부의 요소들이 얼마나 한 가지 목적에 집중하는가다. 클래스 안의 메서드와 멤버 변수가 모두 하나의 책임을 위해 존재하면 응집도가 높다.

응집도가 낮으면 모듈이 잡탕이 된다. 서로 관련 없는 기능이 한 클래스에 모여 있으면, 그 클래스를 이해하려면 여러 맥락을 동시에 머릿속에 올려야 한다. 또 한 기능을 고치다가 무관한 기능을 깨뜨릴 위험도 커진다.

// 낮은 응집 — 이름부터 "Manager", 하는 일이 제각각
class ImageManager
{
public:
    void LoadFromFile(const std::string& path);   // 파일 입출력
    void ApplyGaussianBlur(int kernelSize);        // 영상 처리
    void SendToNetwork(const std::string& url);    // 네트워크 전송
    void WriteLog(const std::string& msg);         // 로깅
};
// 이 클래스가 바뀌는 이유가 4개다. 파일 포맷, 필터 알고리즘, 통신 규약, 로그 정책.

위 ImageManager는 영상 로딩, 처리, 전송, 로깅을 한꺼번에 들고 있다. 이것은 다음 절에서 볼 응집도 수준 중 가장 낮은 축에 속한다.

응집도의 7가지 수준

응집도 역시 단계가 있다. 아래는 나쁨에서 좋음 순이다.

응집도 스펙트럼 — 왼쪽이 피해야 할 낮은 응집, 오른쪽이 지향할 높은 응집
수준이름설명평가
1우연적
(Coincidental)		아무 관련 없는 기능들이 그냥 한 곳에 모여 있다. 대표적으로 잡다한 함수를 모은 "Util" 클래스.최악
2논리적
(Logical)		"비슷한 종류"라는 이유로 묶였지만 실제 동작은 다르다. 모든 입력 처리 함수를 한 모듈에 몰아넣고 플래그로 분기하는 식.매우 나쁨
3시간적
(Temporal)		"같은 시점에 실행된다"는 이유로 묶였다. 프로그램 시작 시 호출되는 초기화 코드 모음 등.나쁨
4절차적
(Procedural)		정해진 실행 순서를 따라 묶였다. 순서는 맞지만 다루는 데이터는 제각각이다.보통
5통신적
(Communicational)		같은 데이터를 사용하거나 같은 데이터에 작업하는 요소들이 모였다.괜찮음
6순차적
(Sequential)		한 요소의 출력이 다음 요소의 입력이 된다. 데이터가 흐름을 따라 이어진다.좋음
7기능적
(Functional)		모듈 안의 모든 요소가 단 하나의 잘 정의된 작업에 기여한다.가장 좋음
응집도를 빠르게 판단하는 질문 "이 모듈을 한 문장으로, 'and' 없이 설명할 수 있는가?" 설명에 "그리고"가 끼면 그만큼 응집도가 떨어진 것이다. 기능적 응집은 항상 한 문장으로 끝난다.

결합도와 응집도의 관계

두 지표는 보통 같은 방향으로 움직인다. 응집도를 높이면 결합도가 낮아지는 경향이 있다. 이유는 간단하다.

응집도가 낮은 모듈은 여러 책임을 갖는다. 책임이 많으니 그만큼 많은 다른 모듈과 얽힌다. 앞에서 본 ImageManager는 파일 시스템, 영상 처리 라이브러리, 네트워크 스택, 로깅 시스템 네 곳 모두에 의존했다. 반대로 책임을 하나로 좁혀 ImageLoader, ImageFilter, ImageSender로 쪼개면 각 클래스의 의존 대상도 하나씩으로 줄어든다.

그래서 설계를 개선할 때는 보통 응집도부터 손본다. 책임 단위로 모듈을 다시 자르면, 결합도는 따라서 정리되는 경우가 많다.

상태응집도결합도증상
이상적높음낮음변경이 한 모듈에 갇힌다
흔한 나쁜 설계낮음높음한 곳 고치면 여러 곳이 깨진다
드문 경우높음높음책임은 명확하나 의존 정리가 덜 됨

결합도를 낮추는 방법

인터페이스에 의존한다 (DIP)

구체 클래스 대신 추상 인터페이스에 의존하면, 구현이 바뀌어도 의존하는 쪽은 그대로다. 이것이 SOLID의 의존성 역전 원칙(DIP)이다.

// 인터페이스에 의존 — 구현이 무엇이든 Report는 모른다
class IDataSource
{
public:
    virtual ~IDataSource() = default;
    virtual std::vector<Row> Query(const std::string& sql) = 0;
};

class Report
{
public:
    explicit Report(IDataSource& source) : m_source(source) {}
    void Generate()
    {
        auto rows = m_source.Query("SELECT ...");   // MySQL인지 PostgreSQL인지 모름
    }
private:
    IDataSource& m_source;
};

의존성을 주입한다 (DI)

모듈이 필요한 것을 스스로 new로 만들지 않고, 외부에서 받는다. 위 Report가 생성자로 IDataSource를 받는 것이 의존성 주입이다. 모듈은 "무엇을 쓸지"를 직접 결정하지 않으므로 결합이 끊긴다.

이벤트와 콜백으로 방향을 뒤집는다

A가 B를 직접 호출하는 대신, B가 A에게 콜백을 등록해두고 A는 "사건이 일어났다"고 알리기만 한다. A는 누가 듣는지 모른다. 산업 SW에서 에러 통지나 처리 완료 알림에 자주 쓰는 구조다.

// 콜백 — 처리 모듈은 결과를 누가 받는지 모른다
class ImageProcessor
{
public:
    using DoneCallback = std::function<void(const Image&)>;
    void SetOnDone(DoneCallback cb) { m_onDone = std::move(cb); }
    void Process(Image& img)
    {
        // ... 처리 ...
        if (m_onDone) m_onDone(img);   // 호출 대상을 컴파일 타임에 모름
    }
private:
    DoneCallback m_onDone;
};

모듈 경계를 명확히 한다

공개 API는 좁게, 내부 구현은 숨긴다. 헤더에 노출되는 것이 적을수록 다른 모듈이 의존할 수 있는 표면이 줄어든다. 앞서 본 GetRawConnection()처럼 내부 구현을 그대로 흘리는 API는 결합도를 끌어올린다.

응집도를 높이는 방법

단일 책임 원칙을 따른다 (SRP)

한 클래스는 변경 이유가 하나여야 한다. 변경 이유가 둘 이상이면 책임이 섞인 것이고, 그만큼 응집도가 낮다. ImageManager를 책임별로 쪼개면 각 클래스가 기능적 응집에 가까워진다.

// 책임별로 분리 — 각 클래스는 변경 이유가 하나뿐
class ImageLoader
{
public:
    Image LoadFromFile(const std::string& path);   // 파일 포맷이 바뀔 때만 수정
};

class ImageFilter
{
public:
    void ApplyGaussianBlur(Image& img, int kernelSize);   // 필터 로직이 바뀔 때만
};

class ImageSender
{
public:
    void Send(const Image& img, const std::string& url);  // 통신 규약이 바뀔 때만
};

관련된 것끼리 묶는다

같은 데이터를 다루거나, 한 요소의 출력이 다음 요소의 입력이 되는 것들은 한 모듈에 둔다. 이것이 통신적·순차적 응집이다. 흩어진 관련 코드를 한곳에 모으는 것만으로 응집도가 올라간다.

관련 없는 것은 분리한다

반대로, 한 모듈 안에 목적이 다른 코드가 섞여 있으면 빼낸다. "이 함수가 이 클래스에 왜 있지?"라는 질문이 나오면 그 함수는 다른 곳으로 가야 한다.

SRP와 응집도는 같은 이야기다 단일 책임 원칙은 "응집도를 높여라"를 객체지향 언어로 다시 쓴 것이다. 책임이 하나면 그 모듈의 모든 요소가 한 가지 일에 기여하게 되고, 그것이 곧 기능적 응집이다.

측정과 위험 신호

결합도와 응집도를 정밀하게 수치화하기는 어렵지만, 코드를 보면 드러나는 신호들이 있다.

결합도가 높다는 신호

  • 파일 하나를 고쳤더니 관련 없어 보이는 여러 파일이 같이 깨진다
  • 한 클래스를 테스트하려는데 다른 클래스 대여섯 개를 같이 만들어야 한다
  • #include 목록이 길고, 그중 상당수가 구체 구현 헤더다
  • 한 모듈이 다른 모듈의 내부 필드나 private 멤버를 직접 참조한다

응집도가 낮다는 신호

  • 클래스 이름에 And가 들어간다 — LoadAndValidate는 책임이 둘이다
  • 클래스 이름이 Manager, Util, Helper, Common으로 끝난다 — 무엇이든 담을 수 있다는 뜻
  • 클래스가 하는 일을 한 문장으로 설명할 수 없다
  • 메서드들이 서로 다른 멤버 변수 집합을 쓴다 — 한 클래스에 두 클래스가 숨어 있다
"Manager"라는 이름을 경계한다 Manager나 Util은 이름 자체가 책임의 부재를 드러낸다. 무엇이든 관리할 수 있고 무엇이든 도울 수 있다는 말은, 명확한 책임이 없다는 말과 같다. 그런 이름이 떠오르면 잠시 멈추고 "이 클래스의 진짜 책임은 무엇인가"를 다시 묻는다.

산업 SW 관점

산업용 이미징 SDK처럼 오래 유지되는 소프트웨어에서 결합도와 응집도는 더 중요하다. 제품 수명이 길고, 카메라·그래버·알고리즘이 계속 추가되기 때문이다.

코어와 솔루션 라이브러리의 결합 최소화

코어 라이브러리(영상 처리 기본기)와 솔루션 라이브러리(측정, OCR, 딥러닝)는 약하게 결합돼야 한다. 솔루션이 코어의 공개 인터페이스에만 의존하면, 코어 내부를 최적화하거나 GPU 경로를 추가해도 솔루션은 영향을 받지 않는다. 반대로 솔루션이 코어의 내부 구조에 의존하면 코어를 손볼 때마다 모든 솔루션이 흔들린다.

검사 블록의 기능적 응집

데이터 플로우 편집기의 각 처리 블록은 기능적 응집을 목표로 한다. "블러 블록"은 블러만, "엣지 검출 블록"은 엣지 검출만 한다. 블록 하나가 한 가지 일만 하면, 블록을 자유롭게 조합해도 동작을 예측할 수 있다. 블록이 잡탕이 되면 플로우 편집기의 조합 가능성 자체가 무너진다.

플러그인 구조의 전제 나중에 블록을 플러그인으로 확장하려면 공통 인터페이스(예: IProcessBlock)에만 의존하는 약한 결합이 전제다. 처음부터 인터페이스 경계를 명확히 두면 확장 시점에 구조를 갈아엎지 않아도 된다.

흔한 오해

"결합도를 0으로 만들어야 한다"

결합을 완전히 없애려다 과한 추상화에 빠지는 경우가 많다. 인터페이스를 위한 인터페이스, 한 번만 쓰이는 팩토리, 의미 없는 래퍼 계층이 쌓이면 코드를 읽는 사람은 실제 동작을 찾으려고 파일 열 개를 헤맨다. 모듈은 어차피 협력해야 한다. 목표는 결합을 없애는 것이 아니라 얕고 명확하게 만드는 것이다.

과한 추상화도 비용이다 추상화 계층은 공짜가 아니다. 추가될 가능성이 실제로 보이지 않는데도 "혹시 몰라서" 인터페이스를 만들면, 낮은 결합이 아니라 불필요한 복잡도를 얻는다. 두 번째 구현이 나타날 때 추상화해도 늦지 않다.

"Util 클래스는 편하니까 괜찮다"

Util 클래스는 당장은 편하지만 응집도가 가장 낮은 우연적 응집의 표본이다. 처음엔 함수 두세 개로 시작했다가, 갈 곳 없는 함수의 종착지가 되어 수백 줄로 불어난다. 관련 기능은 그 기능을 쓰는 도메인 클래스 가까이에 두는 것이 맞다.

"Util"은 미루기의 다른 이름 함수를 Util에 넣는다는 것은 "이게 어디 속하는지 지금 정하지 않겠다"는 결정이다. 그 결정이 쌓이면 아무도 책임지지 않는 거대한 잡탕 클래스가 남는다. 새 함수를 만들 때 "이건 어느 도메인의 것인가"를 먼저 정한다.

"전역 변수 하나쯤은 문제없다"

전역 변수는 그 자체로 공통 결합을 만든다. 여러 모듈이 같은 전역 상태를 읽고 쓰면, 누가 언제 그 값을 바꿨는지 추적할 수 없다. 버그가 나면 전역 변수를 건드리는 모든 코드가 용의자가 된다. 멀티스레드 환경에서는 데이터 경쟁까지 더해진다.

전역 변수는 숨은 결합이다 함수 시그니처에는 드러나지 않지만 모든 모듈이 같은 값에 묶인다. 싱글톤도 본질은 전역 변수이므로 같은 문제를 갖는다. 상태는 가능한 한 명시적으로 매개변수나 멤버로 넘기고, 공유 범위를 최대한 좁힌다.

정리하면, 결합도와 응집도는 "변경의 파급을 좁게 가둔다"는 하나의 목표를 두 방향에서 바라본 것이다. 응집도를 책임 단위로 끌어올리고, 결합도를 인터페이스 의존으로 끌어내리면, 코드는 고치기 쉬워지고 오래 살아남는다. 다만 어느 쪽도 극단으로 밀어붙이지 않는 균형 감각이 함께 필요하다.
