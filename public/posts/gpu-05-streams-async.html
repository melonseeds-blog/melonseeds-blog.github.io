비동기 실행이란

CUDA 커널 호출은 기본적으로 비동기다. 호스트(CPU)는 kernel<<<...>>>(...) 호출 직후 즉시 다음 줄로 넘어가고, GPU는 백그라운드에서 작업을 수행한다. 이 비동기성을 잘 활용하면 CPU와 GPU가 동시에 일하게 만들 수 있다.

// 커널은 비동기 — 호스트는 바로 다음 줄로
myKernel<<<grid, block>>>(d_data, n);

doCpuWork();   // GPU가 일하는 동안 CPU도 일함

// 결과가 필요한 시점에서만 명시적으로 동기화
cudaDeviceSynchronize();

반면 메모리 전송 API는 두 종류로 나뉜다. cudaMemcpy는 동기이고, cudaMemcpyAsync는 비동기다.

// 동기 — 복사가 끝날 때까지 호스트는 블록됨
cudaMemcpy(d_a, h_a, size, cudaMemcpyHostToDevice);

// 비동기 — 즉시 반환, 스트림에 큐잉됨
cudaMemcpyAsync(d_a, h_a, size, cudaMemcpyHostToDevice, stream);
API동작핀드 메모리 필요
cudaMemcpy동기 (호스트 블록)불필요
cudaMemcpyAsync비동기 (스트림 큐잉)필수
커널 호출 <<<...>>>비동기—
cudaDeviceSynchronize모든 스트림 종료 대기—
cudaStreamSynchronize(s)스트림 s의 작업 종료 대기—
cudaMemcpyAsync는 핀드 메모리가 아니면 사실상 동기 페이지가능(pageable) 호스트 메모리는 DMA로 직접 전송할 수 없어 드라이버가 내부적으로 핀드 버퍼를 거쳐 동기 복사로 처리한다. cudaMallocHost 또는 cudaHostAlloc으로 핀드 메모리를 할당해야 진짜 비동기로 동작한다.

Stream — 작업 큐

Stream은 GPU에서 순서대로 실행되는 작업 큐다. 한 스트림 안의 작업은 큐잉된 순서대로 실행되지만, 서로 다른 스트림은 동시 실행 가능하다.

3개 스트림의 작업이 시간 축에서 중첩 실행되는 모습. 각 스트림은 H→D, Kernel, D→H를 순서대로 수행하지만, 스트림 간에는 전송·계산·역전송이 동시 진행된다.

위 그림에서 핵심은 한 스트림이 커널을 실행하는 동안 다른 스트림은 메모리 전송을 동시에 진행한다는 점이다. 단일 스트림으로 직렬화하면 전송 구간 동안 GPU 연산기가 놀게 되지만, 여러 스트림을 쓰면 전송·계산·역전송 엔진을 동시에 활용할 수 있다.

스트림 API 사용법

스트림은 cudaStream_t 핸들로 표현된다. 생성, 사용, 파괴의 3단계를 거친다.

#include <cuda_runtime.h>

cudaStream_t stream;
cudaStreamCreate(&stream);                // 생성

// 비동기 전송에 스트림 지정
cudaMemcpyAsync(d_a, h_a, size, cudaMemcpyHostToDevice, stream);

// 커널 실행에 스트림 지정 — 4번째 launch config 인자
myKernel<<<grid, block, 0, stream>>>(d_a, n);

// 결과 회수도 같은 스트림에
cudaMemcpyAsync(h_out, d_a, size, cudaMemcpyDeviceToHost, stream);

// 이 스트림의 모든 작업이 끝날 때까지 대기
cudaStreamSynchronize(stream);

cudaStreamDestroy(stream);                  // 파괴

커널 런치 구문의 세 번째 인자는 동적 shared memory 크기(바이트)이고, 네 번째가 스트림이다. shared memory를 안 쓰면 0을 넣으면 된다.

// kernel<<< gridDim, blockDim, sharedMemBytes, stream >>>(args...)
processKernel<<<blocks, threads, 0, stream>>>(d_image, width, height);

스트림 생성 플래그

cudaStreamCreateWithFlags로 default stream과의 동기화 동작을 제어할 수 있다.

cudaStream_t stream;
// 기본 동작 — default stream과 암시적 동기화
cudaStreamCreate(&stream);

// non-blocking — default stream과 동기화하지 않음 (대부분의 경우 추천)
cudaStreamCreateWithFlags(&stream, cudaStreamNonBlocking);

호스트-디바이스 전송과 커널 실행 중첩

처리량을 극대화하는 핵심 기법이다. 핀드 메모리 + 여러 스트림을 조합하면 PCIe 전송과 GPU 연산을 시간상으로 겹칠 수 있다.

위: 단일 스트림은 H→D, Kernel, D→H를 순차 처리. 아래: 3개 스트림으로 청크를 나누면 전송과 계산이 시간상 겹쳐 총 처리 시간이 단축된다.

아래는 큰 배열을 N개 청크로 나눠 nStreams 개의 스트림에 라운드로빈으로 큐잉하는 기본 패턴이다.

constexpr int kNumStreams = 4;
constexpr int kChunkSize  = 1024 * 1024;  // 청크당 요소 수

float* h_data = nullptr;
float* d_data = nullptr;
cudaMallocHost(&h_data, totalSize * sizeof(float));  // 핀드 메모리!
cudaMalloc(&d_data, totalSize * sizeof(float));

cudaStream_t streams[kNumStreams];
for (int i = 0; i < kNumStreams; ++i)
{
    cudaStreamCreate(&streams[i]);
}

const int nChunks = totalSize / kChunkSize;
for (int i = 0; i < nChunks; ++i)
{
    const int offset = i * kChunkSize;
    cudaStream_t s = streams[i % kNumStreams];

    // 1) H→D
    cudaMemcpyAsync(d_data + offset, h_data + offset,
                    kChunkSize * sizeof(float),
                    cudaMemcpyHostToDevice, s);

    // 2) Kernel
    dim3 block(256);
    dim3 grid((kChunkSize + 255) / 256);
    processKernel<<<grid, block, 0, s>>>(d_data + offset, kChunkSize);

    // 3) D→H
    cudaMemcpyAsync(h_data + offset, d_data + offset,
                    kChunkSize * sizeof(float),
                    cudaMemcpyDeviceToHost, s);
}

cudaDeviceSynchronize();   // 모든 스트림 완료 대기

for (int i = 0; i < kNumStreams; ++i)
{
    cudaStreamDestroy(streams[i]);
}
cudaFreeHost(h_data);
cudaFree(d_data);
중첩이 가능하려면 하드웨어 조건도 충족해야 한다 대부분의 현대 NVIDIA GPU는 복사 엔진(copy engine)을 2개 가져서 H→D와 D→H를 동시에 진행할 수 있다. cudaDeviceProp::asyncEngineCount로 확인 가능하다. 1이면 양방향 중첩이 어렵고, 2 이상이면 양방향 + 커널까지 3중 중첩이 된다.

Default Stream의 함정

스트림을 지정하지 않은 모든 작업은 default stream(=stream 0, null stream)에서 실행된다. 문제는 이것이 다른 스트림과 암시적으로 동기화된다는 점이다.

// 의도: 두 스트림이 동시 실행되길
kernelA<<<g, b, 0, stream1>>>(...);
kernelB<<<g, b>>>(...);              // ← default stream!
kernelC<<<g, b, 0, stream2>>>(...);

// 실제: kernelB가 default stream에 들어가는 순간
//       stream1과 stream2의 모든 큐 작업이 끝나길 기다린 뒤 B 실행,
//       이후 stream2의 후속 작업은 B가 끝나야 시작됨.
//       결국 직렬화된다.
실수로 default stream을 끼우면 모든 중첩이 망가진다 멀티 스트림 코드에서는 모든 커널 호출과 메모리 API에 명시적으로 스트림을 지정하자. 라이브러리(cuBLAS, cuDNN, OpenCV cv::cuda 등)도 기본은 default stream이므로 setStream() 류 API로 사용 스트림을 명시해야 한다.

혹은 컴파일 옵션으로 per-thread default stream을 켜면 호스트 스레드마다 별도의 default stream을 갖게 되어 위 문제가 완화된다.

nvcc --default-stream per-thread main.cu -o app

Events — 동기화와 시간 측정

cudaEvent_t는 스트림의 특정 지점에 표지(marker)를 꽂는 객체다. 두 가지 용도로 쓴다.

  • 시간 측정 — 두 이벤트 사이의 경과 시간(ms) 계산
  • 스트림 간 동기화 — 한 스트림이 다른 스트림의 특정 지점까지 끝나길 기다리게 함

시간 측정

cudaEvent_t start, stop;
cudaEventCreate(&start);
cudaEventCreate(&stop);

cudaEventRecord(start, stream);
myKernel<<<g, b, 0, stream>>>(...);
cudaEventRecord(stop, stream);

cudaEventSynchronize(stop);                // stop 시점까지 대기

float ms = 0.0f;
cudaEventElapsedTime(&ms, start, stop);
spdlog::info("Kernel elapsed: {:.3f} ms", ms);

cudaEventDestroy(start);
cudaEventDestroy(stop);
왜 CPU 타이머 대신 Event를 쓰나 커널 호출은 비동기라 std::chrono로 감싸면 큐잉 시간만 잰다. 정확한 GPU 측 경과 시간을 알려면 GPU 클럭 기반의 event timer가 필요하다. 8편(프로파일링)에서 다시 다룬다.

스트림 간 동기화

cudaStreamWaitEvent는 호스트를 블록하지 않고, 해당 스트림의 큐에 "이 이벤트까지 대기"라는 의존성을 삽입한다.

cudaEvent_t eventA;
cudaEventCreate(&eventA);

// stream1에서 전처리
preprocessKernel<<<g, b, 0, stream1>>>(d_image);
cudaEventRecord(eventA, stream1);

// stream2는 stream1의 eventA 시점이 끝나야 진행
cudaStreamWaitEvent(stream2, eventA, 0);
inferenceKernel<<<g, b, 0, stream2>>>(d_image, d_result);

시간 측정이 목적이 아니면 cudaEventCreateWithFlags(&e, cudaEventDisableTiming)으로 만드는 편이 약간 더 가볍다.

CUDA Graphs

매 프레임 똑같은 커널·메모리 작업 순서를 반복한다면, 그 순서를 그래프로 캡처한 뒤 한 번의 launch로 재생할 수 있다. 커널 launch 오버헤드와 호스트 측 호출 비용을 크게 줄인다.

cudaGraph_t graph;
cudaGraphExec_t graphExec;

// 1) 스트림에서 일련의 작업을 캡처
cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);

cudaMemcpyAsync(d_in, h_in, size, cudaMemcpyHostToDevice, stream);
stage1Kernel<<<g, b, 0, stream>>>(d_in, d_tmp);
stage2Kernel<<<g, b, 0, stream>>>(d_tmp, d_out);
cudaMemcpyAsync(h_out, d_out, size, cudaMemcpyDeviceToHost, stream);

cudaStreamEndCapture(stream, &graph);

// 2) 실행 가능 형태로 인스턴스화
cudaGraphInstantiate(&graphExec, graph, nullptr, nullptr, 0);

// 3) 반복 launch — 매번의 호출 오버헤드가 매우 작다
for (int frame = 0; frame < nFrames; ++frame)
{
    cudaGraphLaunch(graphExec, stream);
}
cudaStreamSynchronize(stream);

cudaGraphExecDestroy(graphExec);
cudaGraphDestroy(graph);
CUDA Graphs는 짧은 커널이 많을수록 효과가 크다 커널 하나당 launch 오버헤드는 수 μs 수준인데, 한 프레임에 수십~수백 개의 짧은 커널이 도는 추론 파이프라인에서는 이 오버헤드가 누적된다. 그래프 캡처로 호스트 호출을 1회로 줄이면 처리량이 눈에 띄게 올라간다.

실전 파이프라이닝 패턴

대용량 데이터(예: 큰 이미지, 영상 배치)는 여러 청크로 나눠 N 스트림에 분산하는 것이 정석이다. 전체 처리량은 "가장 느린 스테이지 + 마지막 청크의 wrap-up"으로 결정된다.

// 큰 이미지 1장을 stripe(가로줄)로 나눠 파이프라이닝
ErrorCode ProcessImagePipelined(const uint8_t* h_src, uint8_t* h_dst,
                                int width, int height)
{
    if (!h_src || !h_dst) return ErrorCode::InvalidArgument;

    constexpr int kStreams = 4;
    const int stripeRows = height / kStreams;
    const size_t stripeBytes = stripeRows * width;

    uint8_t* d_src = nullptr;
    uint8_t* d_dst = nullptr;
    cudaMalloc(&d_src, width * height);
    cudaMalloc(&d_dst, width * height);

    cudaStream_t streams[kStreams];
    for (int i = 0; i < kStreams; ++i)
    {
        cudaStreamCreateWithFlags(&streams[i], cudaStreamNonBlocking);
    }

    for (int i = 0; i < kStreams; ++i)
    {
        const size_t offset = i * stripeBytes;

        cudaMemcpyAsync(d_src + offset, h_src + offset, stripeBytes,
                        cudaMemcpyHostToDevice, streams[i]);

        dim3 block(16, 16);
        dim3 grid((width + 15) / 16, (stripeRows + 15) / 16);
        filterKernel<<<grid, block, 0, streams[i]>>>(
            d_src + offset, d_dst + offset, width, stripeRows);

        cudaMemcpyAsync(h_dst + offset, d_dst + offset, stripeBytes,
                        cudaMemcpyDeviceToHost, streams[i]);
    }

    for (int i = 0; i < kStreams; ++i)
    {
        cudaStreamSynchronize(streams[i]);
        cudaStreamDestroy(streams[i]);
    }
    cudaFree(d_src);
    cudaFree(d_dst);
    return ErrorCode::Ok;
}
스트림 동기화 방법대상호스트 블록 여부
cudaDeviceSynchronize()모든 스트림블록
cudaStreamSynchronize(s)특정 스트림 s블록
cudaEventSynchronize(e)이벤트 e가 기록된 시점블록
cudaStreamWaitEvent(s, e)스트림 s에 의존성 삽입비블록
cudaStreamQuery(s)완료 여부만 즉시 확인비블록 (polling)

산업 비전 적용 — Grab → 전처리 → 추론

검사 시스템의 일반적인 파이프라인은 다음과 같다.

  1. 카메라 grab — 호스트 메모리에 새 프레임 도착
  2. H→D 전송 — 프레임을 GPU로 업로드
  3. 전처리 — DSNU/PRNU 보정, 디모자이킹, ROI 추출
  4. 추론 — 결함 분류 또는 검출 모델
  5. D→H 전송 — 결과를 호스트로
  6. 판정·결과 송출

프레임 N의 추론이 도는 동안 프레임 N+1의 H→D 전송이 동시에 진행되도록 스트림을 두 개 이상 운영하는 것이 핵심이다.

// 더블 버퍼링 + 2 스트림 — 가장 단순한 산업 비전 파이프라인
class InspectionPipeline
{
public:
    ErrorCode Initialize(int width, int height)
    {
        m_width  = width;
        m_height = height;
        const size_t bytes = width * height;

        for (int i = 0; i < 2; ++i)
        {
            cudaMallocHost(&m_hostBuf[i], bytes);    // 핀드
            cudaMalloc(&m_devBuf[i], bytes);
            cudaMalloc(&m_resultBuf[i], kResultBytes);
            cudaStreamCreateWithFlags(&m_stream[i], cudaStreamNonBlocking);
        }
        return ErrorCode::Ok;
    }

    // 프레임 큐잉 — 호스트 블록 없이 즉시 반환
    ErrorCode SubmitFrame(const uint8_t* grabbedFrame, int slot)
    {
        if (!grabbedFrame) return ErrorCode::InvalidArgument;

        memcpy(m_hostBuf[slot], grabbedFrame, m_width * m_height);

        cudaMemcpyAsync(m_devBuf[slot], m_hostBuf[slot],
                        m_width * m_height,
                        cudaMemcpyHostToDevice, m_stream[slot]);

        preprocessKernel<<<m_grid, m_block, 0, m_stream[slot]>>>(
            m_devBuf[slot], m_width, m_height);

        inferenceKernel<<<m_grid, m_block, 0, m_stream[slot]>>>(
            m_devBuf[slot], m_resultBuf[slot]);

        cudaMemcpyAsync(m_hostResult[slot], m_resultBuf[slot],
                        kResultBytes, cudaMemcpyDeviceToHost,
                        m_stream[slot]);
        return ErrorCode::Ok;
    }

    // 특정 슬롯의 결과 대기 — 다른 슬롯은 계속 진행 중
    ErrorCode WaitResult(int slot, InspectionResult& outResult)
    {
        cudaStreamSynchronize(m_stream[slot]);
        outResult = ParseResult(m_hostResult[slot]);
        return ErrorCode::Ok;
    }

private:
    int m_width  = 0;
    int m_height = 0;
    uint8_t*     m_hostBuf[2]    = { nullptr, nullptr };
    uint8_t*     m_devBuf[2]     = { nullptr, nullptr };
    float*       m_resultBuf[2]  = { nullptr, nullptr };
    float        m_hostResult[2][kResultFloats]{};
    cudaStream_t m_stream[2]{};
    dim3         m_grid;
    dim3         m_block{ 16, 16 };
};

실제 운용에서는 호출자가 짝/홀수 프레임을 슬롯 0/1에 번갈아 큐잉하고, N-1 프레임의 결과를 N 프레임 큐잉 직후에 회수한다. 한 프레임의 GPU 시간보다 grab 주기가 길기만 하면 어떤 프레임도 놓치지 않는다.

흔한 함정

async API인데 핀드 메모리를 안 씀

가장 흔한 실수다. cudaMemcpyAsync를 썼지만 호스트 버퍼가 malloc/new로 할당된 페이지가능 메모리라면 드라이버가 내부 핀드 버퍼를 거쳐 동기 복사로 처리한다. 프로파일러로 봤을 때 "분명 async로 짰는데 중첩이 안 일어남" 증상의 대부분이 이것이다.

Default stream으로 인한 의도치 않은 동기화

OpenCV의 cv::cuda::GaussianBlur(src, dst)처럼 스트림 인자를 생략하면 default stream으로 들어가, 멀티 스트림 코드 전체를 직렬화시킨다. 라이브러리 호출에는 반드시 스트림을 명시한다.

// 나쁜 예 — default stream 사용
cv::cuda::GaussianBlur(src, dst, cv::Size(5, 5), 1.0);

// 좋은 예 — Stream 명시
cv::cuda::Stream cvStream;
cv::cuda::GaussianBlur(src, dst, cv::Size(5, 5), 1.0, 0,
                       cv::BORDER_DEFAULT, cvStream);

이벤트 동기화 누락

스트림 A에서 만든 결과를 스트림 B에서 읽으면서 cudaStreamWaitEvent를 빼먹으면 race condition이 발생한다. 데이터 의존성이 스트림 경계를 넘는 모든 지점에 이벤트 동기화를 추가해야 한다.

스트림을 너무 많이 만들기

"많을수록 좋다"가 아니다. 하드웨어 큐 수(보통 32개)와 작업 단위 크기로 결정되는 최적 스트림 수는 보통 2~8개다. 그보다 많이 만들면 각 스트림의 작업이 너무 작아져 launch 오버헤드만 늘어난다. 청크 크기와 함께 튜닝해야 한다.

비동기 에러를 놓침

커널이 비동기라 launch 직후의 cudaGetLastError()는 launch 설정 오류만 잡는다. 런타임 오류(잘못된 메모리 접근 등)는 다음 동기화 시점에서야 보고된다. CI/디버깅 환경에서는 매 launch 후 cudaDeviceSynchronize() + 에러 체크를 강제하면 원인 위치를 빨리 찾을 수 있다.
