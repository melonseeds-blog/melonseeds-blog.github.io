LINQ란?

LINQ는 Language Integrated Query의 약자다. 컬렉션·XML·데이터베이스·JSON 등 다양한 데이터 소스에 대해 SQL과 유사한 질의를 C# 언어 차원에서 작성할 수 있게 해 준다. 별도 문자열 쿼리가 아니라 컴파일러가 검증하는 코드라서 타입 안정성과 IntelliSense 지원을 모두 받는다.

핵심 가치는 두 가지다. 첫째, 선언적 표현 — "무엇을 원하는지"를 쓰고 "어떻게 순회할지"는 LINQ에 맡긴다. 둘째, 균일성 — 메모리 리스트든, 데이터베이스든, XML이든 같은 문법을 쓴다.

using System;
using System.Collections.Generic;
using System.Linq;

int[] numbers = { 5, 2, 8, 1, 9, 3, 7 };

// "5보다 큰 수만 골라 정렬해서 리스트로 만든다"
var result = numbers
    .Where(n => n > 5)
    .OrderBy(n => n)
    .ToList();

// result: { 7, 8, 9 }
Console.WriteLine(string.Join(", ", result));
실행 결과
7, 8, 9
LINQ를 쓰려면 using System.Linq;가 필요하다 LINQ는 확장 메서드 묶음이라 네임스페이스를 import해야 IntelliSense에 노출된다. 누락 시 Where·Select가 "정의되지 않음" 오류로 보인다.

쿼리 문법 (Query Syntax)

SQL과 비슷한 형태로 쓰는 표현식이다. from ... where ... orderby ... select ... 구조를 따른다. SQL 경험자에게 친숙하다.

int[] numbers = { 5, 2, 8, 1, 9, 3, 7 };

var result =
    from n in numbers
    where n > 5
    orderby n
    select n;

foreach (var n in result)
{
    Console.WriteLine(n);
}

객체 컬렉션도 동일하게 다룬다.

public class Product
{
    public string Name { get; set; }
    public string Category { get; set; }
    public decimal Price { get; set; }
}

List<Product> products = GetProducts();

var cheapElectronics =
    from p in products
    where p.Category == "Electronics" && p.Price < 100m
    orderby p.Price descending
    select p.Name;

쿼리 문법은 join·group by·let 같은 키워드를 자연스럽게 표현한다. 다만 모든 연산자를 지원하지는 않아서, 일부는 메서드 문법과 섞어 써야 한다.

메서드 문법 (Method Syntax)

확장 메서드를 점(.)으로 이어 호출하는 방식이다. 실무에서 더 자주 본다. 모든 LINQ 연산자를 지원하며 람다와 잘 어울린다.

int[] numbers = { 5, 2, 8, 1, 9, 3, 7 };

var result = numbers
    .Where(n => n > 5)
    .OrderBy(n => n)
    .Select(n => n);

// 객체 예시
var cheapElectronics = products
    .Where(p => p.Category == "Electronics" && p.Price < 100m)
    .OrderByDescending(p => p.Price)
    .Select(p => p.Name);

두 문법은 같은 것

컴파일러는 쿼리 문법을 메서드 문법으로 변환해서 실행한다. 즉 IL 수준에서는 차이가 없다.

// 쿼리 문법
var a = from n in numbers where n > 5 select n * 2;

// ↓ 컴파일러가 다음과 동일하게 변환
var b = numbers.Where(n => n > 5).Select(n => n * 2);
실무에서는 메서드 문법이 더 흔하다 체이닝이 자연스럽고, 람다 표현이 강력하며, 모든 연산자를 지원한다. 다만 다중 join이나 복잡한 group by는 쿼리 문법이 더 읽기 쉽다.

// 성인만 골라 이름만 추출

var sorted = people

GroupBy

키별로 묶어 IGrouping<TKey, TElement>를 반환한다.

var byCategory = products.GroupBy(p => p.Category);

foreach (var group in byCategory)
{
    Console.WriteLine($"[{group.Key}] count={group.Count()}");
    foreach (var p in group)
    {
        Console.WriteLine($"  - {p.Name}: {p.Price}");
    }
}

// 그룹별 집계 한 줄
var summary = products
    .GroupBy(p => p.Category)
    .Select(g => new
    {
        Category = g.Key,
        Count    = g.Count(),
        Total    = g.Sum(p => p.Price)
    })
    .ToList();

Join

var orders     = GetOrders();      // OrderId, CustomerId, Amount
var customers  = GetCustomers();   // CustomerId, Name

var joined = orders.Join(
    customers,
    o => o.CustomerId,    // 외부 키
    c => c.CustomerId,    // 내부 키
    (o, c) => new { o.OrderId, c.Name, o.Amount });

foreach (var row in joined)
{
    Console.WriteLine($"{row.OrderId} / {row.Name} / {row.Amount}");
}

집계 — Sum, Max, Aggregate

int[] nums = { 3, 1, 4, 1, 5, 9, 2, 6 };

int sum  = nums.Sum();
int max  = nums.Max();
double avg = nums.Average();

int product = nums.Aggregate(1, (acc, n) => acc * n);

Any / All / Contains

bool hasMinor    = people.Any(p => p.Age < 18);   // true
bool allAdult    = people.All(p => p.Age >= 18);  // false
bool hasAlice    = people.Select(p => p.Name).Contains("Alice");

지연 평가 (Deferred Execution)

LINQ의 핵심 특성이다. Where·Select·OrderBy 같은 연산자는 호출 즉시 실행되지 않는다. 대신 "어떻게 계산할지"를 담은 IEnumerable<T>를 반환한다. 실제 계산은 열거하는 순간 일어난다.

var numbers = new List<int> { 1, 2, 3 };

// 이 시점에 아무 일도 일어나지 않는다
var query = numbers.Where(n =>
{
    Console.WriteLine($"checking {n}");
    return n > 1;
});

Console.WriteLine("--- before foreach ---");
foreach (var n in query)   // ← 여기서 실행
{
    Console.WriteLine($"got {n}");
}
실행 결과
--- before foreach --- checking 1 checking 2 got 2 checking 3 got 3

즉시 평가하기 — ToList / ToArray

지연을 끝내고 지금 계산을 끝마치고 싶으면 ToList()·ToArray()·ToDictionary()·Count()·First() 등을 호출한다.

var snapshot = numbers.Where(n => n > 1).ToList();  // 지금 평가

numbers.Add(99);  // 원본을 바꿔도 snapshot은 영향 없음
지연 평가 함정 — 같은 쿼리를 두 번 열거하면 두 번 계산된다 foreach를 두 번 돌리거나 .Count() + .First()를 같은 쿼리 변수에 호출하면 소스를 두 번 순회한다. DB·파일·네트워크 소스라면 비용이 두 배다. 결과를 재사용하려면 ToList()로 구체화해서 보관한다.

IEnumerable<T> vs IQueryable<T>

LINQ는 두 종류 인터페이스 위에서 동작한다. 둘 다 LINQ 연산자를 지원하지만 실행 방식이 다르다.

항목IEnumerable<T>IQueryable<T>
실행 위치로컬 메모리 (LINQ to Objects)원격 (LINQ to SQL / EF Core 등)
람다 표현Func<T, bool> — 컴파일된 코드Expression<Func<T, bool>> — 표현식 트리
변환 대상없음 — CLR이 직접 실행SQL·CosmosDB 쿼리 등으로 번역
전체 로드전체를 메모리에서 순회서버 측에서 필터·정렬 후 결과만 가져옴
대표 사용처List·Array·DictionaryEF Core DbSet, IQueryable<T> 리포지토리
// IEnumerable — 메모리 컬렉션
IEnumerable<Product> local = products;
var cheap1 = local.Where(p => p.Price < 100m).ToList();
// → 전체 컬렉션을 순회, CLR에서 람다 실행

// IQueryable — EF Core 등 (가상 예시)
IQueryable<Product> remote = db.Products;
var cheap2 = remote.Where(p => p.Price < 100m).ToList();
// → 표현식 트리를 SQL로 번역
// → "SELECT * FROM Products WHERE Price < 100" 만 서버 실행
경계를 의식하자 IQueryable에 .ToList()·.AsEnumerable()이 호출되는 순간 이후 연산은 모두 메모리에서 일어난다. 의도치 않게 일찍 메모리로 끌어오면 서버 필터링 기회를 잃는다.

람다와 Func 델리게이트

LINQ 연산자의 인자는 대부분 델리게이트다. C#은 람다 표현식으로 짧게 표현한다.

// 람다 — 매개변수 => 식
Func<int, bool> isPositive = n => n > 0;
Func<int, int, int> add    = (a, b) => a + b;

// 블록 본문 람다
Func<int, string> describe = n =>
{
    if (n > 0) return "positive";
    if (n < 0) return "negative";
    return "zero";
};

// LINQ는 이런 델리게이트를 받는다
var positives = numbers.Where(isPositive).ToList();
var positives2 = numbers.Where(n => n > 0).ToList();  // 동일

Func, Action, Predicate

타입시그니처반환
Func<T, TResult>입력 T → 결과 TResult있음
Action<T>입력 T → 동작void
Predicate<T>입력 T → boolbool
Func<int, int, int> mul = (a, b) => a * b;       // (int, int) => int
Action<string>       log = msg => Console.WriteLine(msg);
Predicate<int>       even = n => n % 2 == 0;

확장 메서드

LINQ 연산자는 모두 IEnumerable<T>의 확장 메서드다. static class의 static 메서드에 첫 인자로 this 키워드를 붙여 정의한다. 컴파일러가 메서드 호출처럼 보이게 해 준다.

public static class EnumerableExtensions
{
    // 짝수만 골라내는 우리만의 LINQ 연산자
    public static IEnumerable<int> WhereEven(this IEnumerable<int> source)
    {
        foreach (var n in source)
        {
            if (n % 2 == 0) yield return n;
        }
    }
}

// 사용 — 마치 원래 메서드인 것처럼
var evens = numbers.WhereEven().ToList();

실제 System.Linq.Enumerable 클래스가 이런 확장 메서드를 수십 개 정의해 두었기 때문에 using System.Linq; 한 줄로 모두 사용할 수 있다.

익명 타입

Select에서 그 자리에서 임시 타입을 만들 때 쓴다. 컴파일러가 자동으로 클래스를 생성한다.

var summary = people
    .Where(p => p.Age >= 18)
    .Select(p => new { p.Name, p.Age, IsAdult = true })
    .ToList();

foreach (var item in summary)
{
    Console.WriteLine($"{item.Name} ({item.Age}) - {item.IsAdult}");
}
익명 타입은 메서드 안에서만 쓸모 있다 타입 이름을 적을 수 없어서 메서드 반환 타입으로는 불가. 외부로 노출해야 한다면 record나 일반 클래스를 정의하자. 메서드 내부에서 foreach·즉시 집계용으로 쓰기 좋다.

record (C# 9+) — 익명 타입의 더 강한 사촌

public record CategorySummary(string Category, int Count, decimal Total);

var report = products
    .GroupBy(p => p.Category)
    .Select(g => new CategorySummary(g.Key, g.Count(), g.Sum(p => p.Price)))
    .ToList();

산업·이미지 관점에서의 LINQ

비전 시스템 코드에서도 LINQ는 매우 자주 등장한다. C++ 코어가 만들어 낸 검사 결과를 C# 뷰어에서 다룰 때, 컬렉션 처리가 깔끔해진다.

검사 결과 필터링·집계

public record DefectInfo(int Id, string Type, double Area, double Score);

List<DefectInfo> defects = inspector.RunAll();

// NG 후보만 추출
var ngCandidates = defects
    .Where(d => d.Score >= 0.8 && d.Area > 30.0)
    .OrderByDescending(d => d.Score)
    .ToList();

// 결함 종류별 카운트
var byType = defects
    .GroupBy(d => d.Type)
    .Select(g => new { Type = g.Key, Count = g.Count(), AvgArea = g.Average(d => d.Area) })
    .OrderByDescending(x => x.Count)
    .ToList();

// 최악의 결함 한 개
var worst = defects
    .OrderByDescending(d => d.Score)
    .FirstOrDefault();

ROI 겹침 검사

public record Roi(int Id, int X, int Y, int W, int H);

// 검사 영역끼리 겹치는 쌍을 찾는다
var overlaps =
    from a in rois
    from b in rois
    where a.Id < b.Id && Intersects(a, b)
    select new { A = a.Id, B = b.Id };

로그 분석

var lines = File.ReadAllLines("inspection.log");

// 시간대별 NG 건수 — 1시간 버킷
var ngPerHour = lines
    .Select(ParseLogEntry)
    .Where(e => e != null && e.Result == "NG")
    .GroupBy(e => new DateTime(e.Time.Year, e.Time.Month, e.Time.Day, e.Time.Hour, 0, 0))
    .Select(g => new { Hour = g.Key, Count = g.Count() })
    .OrderBy(x => x.Hour)
    .ToList();

흔한 함정

1. 지연 평가 두 번 열거

// 나쁜 예 — Where가 두 번 실행된다
var slow = bigCollection.Where(IsExpensiveCheck);
int count = slow.Count();          // 첫 번째 순회
var first = slow.FirstOrDefault(); // 두 번째 순회

// 좋은 예 — 한 번만 평가
var snapshot = bigCollection.Where(IsExpensiveCheck).ToList();
int count2 = snapshot.Count;
var first2 = snapshot.FirstOrDefault();
같은 IEnumerable 변수에 LINQ를 여러 번 부르지 말자 파일·DB·네트워크 소스라면 매번 다시 읽는다. 큰 컬렉션이라면 ToList()로 한 번 구체화하는 비용이 훨씬 싸다.

2. First() vs FirstOrDefault()

// First — 비어있으면 InvalidOperationException
var item = collection.First(x => x.Id == 999);

// FirstOrDefault — 비어있으면 default(T) (참조 타입은 null)
var item2 = collection.FirstOrDefault(x => x.Id == 999);

// Single — 정확히 1개. 0개나 2개 이상이면 예외
var unique = collection.Single(x => x.IsPrimary);
"없을 수도 있다"면 무조건 OrDefault 계열 First()를 쓰면 빈 결과가 곧장 런타임 예외가 된다. UI 코드에서 깨지면 사용자에게 그대로 노출되기 십상이다. 반대로 정확히 하나만 있어야 한다는 비즈니스 규칙이라면 Single()로 명시해서 위반 시 빨리 실패하게 만든다.

3. GroupBy 후 Count로 인한 N+1 (EF Core)

// 나쁜 예 — 각 그룹의 Count를 따로따로 쿼리
foreach (var category in db.Products.Select(p => p.Category).Distinct().ToList())
{
    int count = db.Products.Count(p => p.Category == category);  // 매번 DB 호출
    Console.WriteLine($"{category}: {count}");
}

// 좋은 예 — 한 번에 그룹 집계
var summary = db.Products
    .GroupBy(p => p.Category)
    .Select(g => new { Category = g.Key, Count = g.Count() })
    .ToList();  // SQL 한 방

4. 람다 클로저 변수 캡처

람다 안에서 외부 변수를 참조하면 참조로 캡처된다. 반복문 변수를 그대로 캡처하면 모든 람다가 마지막 값을 가리킨다.

var actions = new List<Action>();

// 나쁜 예 (C# 5 이전 스타일 — 지금은 for 변수만 이런 버그가 남음)
for (int i = 0; i < 3; i++)
{
    actions.Add(() => Console.WriteLine(i));
}
foreach (var a in actions) a();   // 3, 3, 3 (!)

// 좋은 예 — 지역 변수로 복사
for (int i = 0; i < 3; i++)
{
    int captured = i;
    actions.Add(() => Console.WriteLine(captured));
}
// 0, 1, 2

// foreach는 C# 5부터 매 반복마다 새 변수 — 안전
foreach (var x in items)
{
    actions.Add(() => Console.WriteLine(x));  // 각자 다른 x
}
for 루프 변수는 람다 안에서 위험하다 for (int i = ...)의 i는 모든 반복이 공유하는 한 변수다. 람다가 그대로 캡처하면 모든 람다가 같은 값을 본다. 캡처 직전에 지역 변수로 복사하거나 foreach를 쓰자.
