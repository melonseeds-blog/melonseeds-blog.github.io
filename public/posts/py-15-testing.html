왜 테스트가 필요한가

코드는 한 번 짜고 끝이 아니다. 기능이 추가되고, 버그가 고쳐지고, 리팩터링이 일어난다. 그 모든 변경마다 "기존 동작이 깨지지 않았는가"를 확인할 방법이 필요하다. 자동화된 테스트는 그 확인을 사람의 기억이 아니라 코드로 옮긴다.

  • 변경 안전망 — 리팩터링을 두려움 없이 한다. 망가뜨리면 즉시 빨간 줄이 뜬다.
  • 회귀 방지 — 한 번 고친 버그가 다시 등장하지 않도록 잠근다.
  • 살아있는 문서 — "이 함수를 이렇게 쓰면 이런 결과가 나온다"가 코드로 박혀 있다. 주석과 달리 거짓말을 못 한다.
  • 설계 압력 — 테스트하기 어려운 코드는 대개 설계가 나쁘다. 테스트는 결합도를 낮추는 압력으로 작동한다.

이 시리즈와 별개로 프로그래밍 이론 시리즈 #16에서 테스트 전략(피라미드·TDD·테스트 더블)을 더 깊게 다룬다. 여기서는 Python에서 그것을 어떻게 실천하는지에 집중한다.

테스트 피라미드 — 단위 테스트를 두텁게, 상위 테스트는 얇게.

unittest vs pytest

Python 표준 라이브러리에는 unittest가 있다. JUnit 계열을 본떠 만든 xUnit 스타일이라 클래스 상속과 self.assertEqual 같은 메서드 호출이 강제된다. pytest는 외부 라이브러리지만 훨씬 간결하고 표현력이 좋아 사실상 표준이 되었다.

항목unittest (표준)pytest (사실상 표준)
설치표준 라이브러리pip install pytest
테스트 정의TestCase 상속 + test_* 메서드최상위 def test_* 함수면 충분
단언self.assertEqual(a, b) 같은 전용 메서드그냥 assert a == b
실패 메시지기본적이다좌·우 값과 차이까지 풍부하게 출력
fixturesetUp / tearDown@pytest.fixture 의존성 주입
파라미터화외부 라이브러리 필요@pytest.mark.parametrize 내장
플러그인제한적1000개 이상 (pytest-cov, pytest-mock, ...)
호환성—unittest.TestCase도 그대로 실행한다

같은 테스트를 두 스타일로 비교해 보면 차이가 분명하다.

# unittest 스타일
import unittest

class TestMath(unittest.TestCase):
    def setUp(self):
        self.values = [1, 2, 3]

    def test_sum(self):
        self.assertEqual(sum(self.values), 6)

    def test_max(self):
        self.assertEqual(max(self.values), 3)

if __name__ == "__main__":
    unittest.main()
# pytest 스타일 — 같은 동작을 절반 분량으로
import pytest

@pytest.fixture
def values():
    return [1, 2, 3]

def test_sum(values):
    assert sum(values) == 6

def test_max(values):
    assert max(values) == 3

pytest 기본

pytest는 규약에 따라 테스트를 자동으로 찾아낸다.

  • 파일명은 test_*.py 또는 *_test.py.
  • 함수명은 test_*.
  • 클래스로 묶을 때는 Test로 시작하고 __init__이 없어야 한다.
# calculator.py — 테스트 대상
def add(a, b):
    return a + b

def divide(a, b):
    if b == 0:
        raise ZeroDivisionError("0으로 나눌 수 없다")
    return a / b
# test_calculator.py
import pytest
from calculator import add, divide

def test_add_positive():
    assert add(2, 3) == 5

def test_add_negative():
    assert add(-1, -1) == -2

def test_divide():
    assert divide(10, 2) == 5.0

def test_divide_by_zero():
    with pytest.raises(ZeroDivisionError):
        divide(1, 0)

def test_divide_by_zero_message():
    with pytest.raises(ZeroDivisionError, match="0으로 나눌 수 없다"):
        divide(1, 0)
# 현재 디렉터리 하위 모든 테스트 실행
pytest

# 특정 파일만
pytest test_calculator.py

# 특정 테스트 하나만
pytest test_calculator.py::test_divide_by_zero

# 자세한 출력
pytest -v

# 첫 실패에서 멈춤
pytest -x

# 출력(print) 표시 — 통과한 테스트에서도 보고 싶을 때
pytest -s

pytest의 가장 빛나는 부분은 assert 실패 메시지다. unittest의 단조로운 메시지와 달리, 좌·우 값과 차이를 풍부하게 풀어 보여준다.

def test_dict_equal():
    result = {"name": "Alice", "age": 30, "city": "Seoul"}
    expected = {"name": "Alice", "age": 31, "city": "Seoul"}
    assert result == expected
실행 결과
FAILED test_x.py::test_dict_equal E AssertionError: assert {'age': 30, 'city': 'Seoul', 'name': 'Alice'} == {'age': 31, ...} E Common items: E {'city': 'Seoul', 'name': 'Alice'} E Differing items: E {'age': 30} != {'age': 31'}

부동소수점 비교

==로 실수를 비교하면 0.1 + 0.2 != 0.3 같은 함정에 빠진다. pytest.approx를 쓴다.

def test_float():
    assert 0.1 + 0.2 == pytest.approx(0.3)
    assert 0.1 + 0.2 == pytest.approx(0.3, abs=1e-9)
    # 컬렉션도 가능
    assert [0.1 + 0.2, 1.0 / 3] == pytest.approx([0.3, 0.3333], rel=1e-3)

fixture — 의존성 주입

테스트마다 동일한 준비 작업이 필요할 때, fixture를 정의하면 pytest가 그 이름의 인자를 자동으로 주입한다.

import pytest
import tempfile, pathlib

@pytest.fixture
def sample_text():
    return "hello world"

@pytest.fixture
def tmp_file(tmp_path):
    # tmp_path는 pytest 내장 fixture
    p = tmp_path / "data.txt"
    p.write_text("line1\nline2\n")
    return p

def test_count_words(sample_text):
    assert len(sample_text.split()) == 2

def test_read_lines(tmp_file):
    lines = tmp_file.read_text().splitlines()
    assert lines == ["line1", "line2"]

fixture는 fixture를 받을 수 있다. 의존성 그래프를 pytest가 자동으로 해결한다.

@pytest.fixture
def db_connection():
    conn = open_connection()
    yield conn          # 테스트에 전달
    conn.close()        # 테스트 끝난 뒤 정리

@pytest.fixture
def user_repo(db_connection):
    return UserRepository(db_connection)

def test_find_user(user_repo):
    user = user_repo.find(1)
    assert user.name == "Alice"

scope — 생애 주기

비싼 셋업을 매 테스트마다 반복하면 느리다. scope로 fixture의 수명을 조정한다.

scope생애전형적 용도
function (기본)테스트 함수마다 새로 생성임시 파일, 가벼운 데이터
class클래스당 한 번같은 클래스 안에서 공유할 객체
module파일당 한 번파일 단위 공유 자원
session전체 실행 동안 한 번DB 컨테이너 기동, 무거운 모델 로딩
@pytest.fixture(scope="session")
def heavy_model():
    print("모델 로딩...")
    model = load_dnn_model("resnet50.onnx")
    yield model
    model.release()

def test_inference_a(heavy_model):
    out = heavy_model.predict(...)
    assert out.shape == (1, 1000)

def test_inference_b(heavy_model):
    out = heavy_model.predict(...)
    assert out.dtype == "float32"
scope가 넓을수록 격리는 약해진다 session fixture에서 상태를 변경하면 모든 테스트가 영향을 받는다. 공유 객체는 가능하면 읽기 전용으로 두자.

parametrize — 한 테스트, 여러 입력

같은 검증 로직을 여러 입력에 대해 반복해야 할 때, 복사 붙여넣기 대신 @pytest.mark.parametrize를 쓴다.

import pytest

def is_palindrome(s: str) -> bool:
    s = s.lower()
    return s == s[::-1]

@pytest.mark.parametrize("text, expected", [
    ("level", True),
    ("racecar", True),
    ("hello", False),
    ("", True),
    ("A", True),
])
def test_palindrome(text, expected):
    assert is_palindrome(text) == expected

각 입력이 별개 테스트로 보고된다. 하나가 실패해도 나머지는 계속 실행되고, 출력에는 어떤 입력에서 실패했는지 명확히 표시된다.

실행 결과
test_x.py::test_palindrome[level-True] PASSED test_x.py::test_palindrome[racecar-True] PASSED test_x.py::test_palindrome[hello-False] PASSED test_x.py::test_palindrome[-True] PASSED test_x.py::test_palindrome[A-True] PASSED

여러 parametrize를 쌓으면 조합이 만들어진다.

@pytest.mark.parametrize("dtype", ["uint8", "uint16", "float32"])
@pytest.mark.parametrize("size", [(64, 64), (1024, 1024)])
def test_blur_supports_all_combinations(dtype, size):
    img = make_test_image(size, dtype)
    out = apply_blur(img, ksize=3)
    assert out.shape == img.shape
    assert out.dtype == img.dtype
# 3 * 2 = 6개의 테스트가 생성된다

mock — 외부 의존성 격리

네트워크·DB·카메라·파일 시스템처럼 느리거나 불확실한 의존성은 테스트에서 가짜로 대체한다. 표준 라이브러리에 unittest.mock이 있고, pytest와 자연스럽게 어울리는 pytest-mock이 있다.

pip install pytest-mock
# weather.py
import requests

def get_temperature(city: str) -> float:
    resp = requests.get(f"https://api.example.com/weather/{city}")
    resp.raise_for_status()
    return resp.json()["temperature"]
# test_weather.py — 실제 네트워크를 타지 않는다
from weather import get_temperature

def test_get_temperature(mocker):
    fake = mocker.Mock()
    fake.json.return_value = {"temperature": 18.5}
    fake.raise_for_status.return_value = None

    mocker.patch("weather.requests.get", return_value=fake)

    assert get_temperature("seoul") == 18.5

patch로 어디를 가로채는가가 중요하다. "정의된 위치가 아니라 사용되는 위치를 patch한다"가 원칙이다. 위 예에서 requests.get이 아니라 weather.requests.get을 patch한 이유다.

# 호출 검증
def test_get_temperature_calls_correct_url(mocker):
    fake = mocker.Mock()
    fake.json.return_value = {"temperature": 0.0}
    mock_get = mocker.patch("weather.requests.get", return_value=fake)

    get_temperature("seoul")

    mock_get.assert_called_once_with("https://api.example.com/weather/seoul")
mock은 양날의 검 과한 mock은 "내 mock이 내가 짠 대로 동작한다"를 검증하는 동어반복으로 전락한다. 진짜 외부 시스템(네트워크, 시계, 무작위)만 격리하고, 내 코드 안에서는 가능하면 실물을 쓰자.

마커 — 선택 실행

모든 테스트를 매번 다 돌릴 필요는 없다. 느린 테스트, 통합 테스트, GPU 필요 테스트 등은 마커로 분류해 두고 필요할 때만 실행한다.

import pytest

@pytest.mark.slow
def test_train_full_model():
    train(epochs=100)
    ...

@pytest.mark.integration
def test_database_round_trip(db):
    ...

@pytest.mark.gpu
def test_cuda_kernel():
    ...

@pytest.mark.skip(reason="아직 구현 전")
def test_future_feature():
    ...

@pytest.mark.skipif(sys.platform == "win32", reason="POSIX 전용")
def test_unix_signal():
    ...

@pytest.mark.xfail(reason="알려진 버그 #42, 조만간 수정")
def test_known_bug():
    assert buggy_function() == 0
# 빠른 테스트만
pytest -m "not slow"

# 통합 테스트만
pytest -m integration

# 여러 조건 조합
pytest -m "slow and gpu"

사용자 정의 마커는 pyproject.toml에 등록해 두는 게 좋다. 그렇지 않으면 오타가 나도 조용히 통과한다.

# pyproject.toml
[tool.pytest.ini_options]
markers = [
    "slow: 느린 테스트 (수 초 이상)",
    "integration: 외부 시스템 사용",
    "gpu: CUDA 필요",
]

테스트 디렉터리 구조와 conftest.py

작은 프로젝트는 테스트를 소스와 같이 둬도 되지만, 보통은 분리한다.

myproject/
├── src/
│   └── myproject/
│       ├── __init__.py
│       ├── image.py
│       └── filter.py
├── tests/
│   ├── conftest.py            # 공용 fixture
│   ├── unit/
│   │   ├── test_image.py
│   │   └── test_filter.py
│   └── integration/
│       └── test_pipeline.py
├── pyproject.toml
└── requirements.txt

conftest.py는 마법 파일이다. 그 디렉터리(와 하위)에서 자동으로 인식되는 fixture와 훅을 정의한다. import 없이 쓸 수 있다.

# tests/conftest.py
import pytest
import numpy as np

@pytest.fixture
def gray_image():
    """64x64 회색 이미지."""
    return np.full((64, 64), 128, dtype=np.uint8)

@pytest.fixture
def random_rgb():
    rng = np.random.default_rng(seed=42)
    return rng.integers(0, 256, size=(128, 128, 3), dtype=np.uint8)
# tests/unit/test_filter.py — import 없이 fixture 사용
def test_blur_preserves_shape(gray_image):
    out = apply_blur(gray_image, ksize=5)
    assert out.shape == gray_image.shape

coverage — 커버리지와 그 함정

coverage.py는 어떤 줄이 테스트로 실행되었는지 추적한다. pytest와 묶은 pytest-cov를 가장 많이 쓴다.

pip install pytest-cov

# 커버리지 측정
pytest --cov=myproject

# 줄별 상세 — 어느 줄이 안 돌았는지
pytest --cov=myproject --cov-report=term-missing

# HTML 리포트
pytest --cov=myproject --cov-report=html
# htmlcov/index.html 열어보기

# 기준선 미달 시 실패
pytest --cov=myproject --cov-fail-under=80
실행 결과
---------- coverage: platform win32, python 3.12.3 ---------- Name Stmts Miss Cover Missing -------------------------------------------------------- myproject/image.py 42 2 95% 58, 73 myproject/filter.py 28 0 100% -------------------------------------------------------- TOTAL 70 2 97%
커버리지의 함정 — 높은 숫자가 좋은 테스트를 뜻하지 않는다 100% 커버리지여도 assert가 부실하면 버그를 못 잡는다. 줄을 "지나갔다"와 "그 줄이 옳다고 검증했다"는 다른 이야기다. 커버리지는 안 짠 영역을 찾는 지표로 쓰자. 목표 자체로 삼으면, 무의미한 assert로 숫자만 채우는 코드가 늘어난다.

doctest — 문서 안 예제 테스트

docstring에 적힌 예제도 테스트가 될 수 있다. 문서와 동작이 어긋나는 것을 막는 가벼운 도구다.

def add(a, b):
    """두 수를 더한다.

    >>> add(2, 3)
    5
    >>> add(-1, 1)
    0
    >>> add(0.1, 0.2)
    0.30000000000000004
    """
    return a + b
# 표준 도구
python -m doctest -v mymodule.py

# pytest로 함께 실행
pytest --doctest-modules

doctest는 가볍지만 표현력이 약하다. 진지한 검증은 pytest로 하고, doctest는 "문서 예제가 실제로 돈다"는 보증 정도로 두자.

CI 통합 — GitHub Actions

로컬에서만 도는 테스트는 결국 누락된다. CI(Continuous Integration)에 묶어 push마다 자동 실행하게 한다.

# .github/workflows/test.yml
name: Tests

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.10", "3.11", "3.12"]

    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:

산업·이미지 관점

이미지 처리는 출력이 거대한 배열이라 일반 단위 테스트 방식이 어색하다. 흔히 쓰는 패턴 몇 가지를 정리한다.

속성 기반 검증

출력 값 자체를 못 박기보다 가져야 할 성질을 검증한다.

def test_blur_shape_dtype_preserved(gray_image):

def test_blur_reduces_variance(gray_image):
    noisy = gray_image + np.random.normal(0, 10, gray_image.shape).astype(np.int16)
    noisy = np.clip(noisy, 0, 255).astype(np.uint8)
    out = apply_blur(noisy, ksize=9)
    assert out.var() < noisy.var()

골든 이미지 비교

알고리즘의 결과를 "기준 이미지"와 비교한다. 픽셀 단위 동일이 어려우면 허용 오차를 둔다.

import cv2, numpy as np
from pathlib import Path

GOLDEN_DIR = Path(__file__).parent / "golden"

def test_canny_matches_golden():
    src = cv2.imread(str(GOLDEN_DIR / "input_lena.png"), cv2.IMREAD_GRAYSCALE)
    out = my_canny(src, low=50, high=150)

    expected = cv2.imread(str(GOLDEN_DIR / "expected_canny.png"), cv2.IMREAD_GRAYSCALE)

    # 픽셀 단위 비교 — 완전 일치 요구
    assert np.array_equal(out, expected)

def test_blur_matches_golden_with_tolerance():
    src = cv2.imread(str(GOLDEN_DIR / "input_lena.png"))
    out = my_blur(src, ksize=5)
    expected = cv2.imread(str(GOLDEN_DIR / "expected_blur.png"))

    # 평균 절대 오차로 비교 — 부동소수점 차이 허용
    mae = np.mean(np.abs(out.astype(int) - expected.astype(int)))
    assert mae < 1.0
골든 이미지 갱신은 의식적으로 알고리즘이 의도적으로 바뀌면 골든도 새로 만들어야 한다. 갱신할 때 사람이 눈으로 확인하고 커밋 메시지에 이유를 남기는 절차를 두자. "왜 깨졌는지 모르겠어서 그냥 새로 찍었다"는 가장 위험한 신호다.

흔한 함정

1. 구현 결합이 과한 테스트 내부 메서드 호출 순서까지 mock으로 잠그면 리팩터링하는 순간 전부 깨진다. 테스트는 관찰 가능한 동작을 검증해야지, 구현 디테일을 검증하면 안 된다.
2. 깨진 테스트 방치(skip 남용) "지금은 안 도니까 일단 skip" 한 줄이 1년 뒤 100개로 늘어난다. 깨진 테스트는 곧 죽은 안전망이다. 고치든, 지우든, 둘 중 하나로 결판낸다.
3. 커버리지만 추구 앞서 강조한 부분의 반복이다. --cov-fail-under=80은 유용하지만, "줄을 밟았다"가 "검증했다"는 아니다. 단언이 약한 테스트는 숫자만 키운다.
4. 너무 느린 테스트 모음 전체 실행에 10분 걸리면 아무도 push 전에 안 돌린다. 빠른 단위 테스트와 느린 통합 테스트를 마커로 분리하고, 평소엔 -m "not slow"로 돌린다.
5. 테스트 간 상태 공유 전역 변수, 파일, DB에 흘러간 부수효과가 다음 테스트에 영향을 준다. 실행 순서를 바꾸면 깨지는 테스트는 일단 의심하자. pytest -p no:randomly 대신 pytest-randomly 플러그인으로 순서를 일부러 섞어 보면 숨은 결합을 찾을 수 있다.
6. 시간·난수·네트워크에 의존 datetime.now(), random, 외부 API는 비결정적이다. 시드를 고정하거나, 시계를 주입하거나, mock으로 격리하자. "어제는 됐는데 오늘 깨진" 테스트가 가장 신뢰를 갉아먹는다.

시리즈 마무리

Python 시리즈 15편을 여기서 닫는다. 1편 입문에서는 설치와 가상환경으로 출발했다. 중반에는 자료형, 함수, 클래스, 예외, 모듈, 이터레이터·제너레이터, 데코레이터 같은 "파이썬다움"을 짚었다. 후반에는 타입 힌트, 비동기, NumPy·Pandas, 그리고 마지막으로 이번 글 테스팅까지, 실무에서 코드를 굴리는 데 필요한 도구들로 이어졌다. 입문 → 파이썬다움 → 실무라는 흐름이었다.

이 시리즈는 그 자체로 끝이 아니라 다른 시리즈와 짝을 이룬다. C++ 시리즈는 양산 장비의 저지연·메모리 제어를 책임지고, OpenCV·머신비전 시리즈는 두 언어 모두에서 같은 알고리즘을 다루며, AI 시리즈는 Python으로 학습해 ONNX·TensorRT로 C++ 추론에 얹는 흐름을 그린다. Python으로 빠르게 만들고 검증한 다음, 양산할 때는 C++로 옮기는 패턴이 현실의 머신비전 개발이다. 이 시리즈가 그 패턴의 Python 쪽 절반을 채워줬다면 충분하다. 다음은 코드를 쓰는 차례다.
