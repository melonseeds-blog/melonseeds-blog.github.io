자료구조란 무엇인가

자료구조(data structure)는 데이터를 메모리에 어떻게 담고 조직하는가에 대한 약속이다. 같은 데이터라도 연속된 칸에 줄지어 담느냐, 흩어 놓고 포인터로 잇느냐, 계층으로 쌓느냐에 따라 "특정 연산이 얼마나 빠른가"가 달라진다.

핵심은 공짜 점심은 없다는 것이다. 모든 연산을 동시에 빠르게 하는 자료구조는 없다. 임의 접근이 빠르면 중간 삽입이 느리고, 삽입이 빠르면 탐색이 느리다. 자료구조를 고른다는 것은 어떤 연산을 자주 하는가에 맞춰 트레이드오프를 선택하는 일이다.

복잡도와의 연결

이전 글에서 다룬 시간 복잡도는 자료구조를 평가하는 잣대다. 같은 "원소 찾기"라도 정렬되지 않은 배열은 O(n), 이진 탐색 트리는 O(log n), 해시 테이블은 평균 O(1)이다. 데이터가 100개일 때는 차이가 미미하지만, 100만 개를 초당 수천 번 조회하는 산업용 코드에서는 자료구조 선택 하나가 곧 제품의 응답성을 결정한다.

복잡도 편과 함께 읽기 이 글의 모든 복잡도 표기(O(1), O(n), O(log n))는 복잡도 편의 정의를 따른다. 복잡도가 "연산 비용을 어떻게 측정하는가"라면, 자료구조는 "그 비용을 어떻게 설계하는가"다. 두 글은 한 쌍이다.

배열 (Array)

배열은 같은 타입의 원소를 연속된 메모리에 줄지어 담는 자료구조다. 가장 단순하지만 가장 중요하다. 시작 주소와 인덱스만 알면 원하는 원소의 주소를 한 번의 곱셈과 덧셈으로 계산할 수 있다.

원소가 메모리에 빈틈없이 줄지어 있어, 인덱스로 주소를 직접 계산한다

성능 특성

배열의 강점과 약점은 모두 "연속 메모리"에서 나온다.

  • 임의 접근 O(1) — arr[i]는 인덱스로 주소를 즉시 계산한다. 원소가 1개든 100만 개든 같은 비용이다.
  • 중간 삽입·삭제 O(n) — 빈틈을 만들거나 메우려면 뒤따르는 원소를 전부 한 칸씩 밀어야 한다.
  • 캐시 친화적 — 인접한 원소가 메모리에서도 인접하므로, CPU가 한 번에 끌어오는 캐시 라인에 다음 원소들이 함께 담긴다. 순차 순회가 매우 빠르다.
// 정적 배열 — 크기가 컴파일 타임에 고정된다
int staticArr[6] = { 12, 37, 5, 88, 21, 9 };
int third = staticArr[2];   // O(1) 임의 접근

// 동적 배열(std::vector) — 런타임에 크기가 늘어난다
std::vector<int> dynamicArr = { 12, 37, 5, 88 };
dynamicArr.push_back(21);   // 끝에 추가, 분할 상환 O(1)
dynamicArr.push_back(9);
int value = dynamicArr[4];  // O(1) 임의 접근

정적 배열 vs 동적 배열

정적 배열은 크기가 고정이라 늘릴 수 없다. std::vector 같은 동적 배열은 내부에 더 큰 연속 메모리를 잡고, 가득 차면 보통 두 배 크기의 새 메모리를 할당해 기존 원소를 복사한다. 이 재할당 때문에 개별 push_back은 가끔 O(n)이지만, 여러 번에 걸쳐 평균을 내면 분할 상환 O(1)이 된다. 재할당이 잦을 것을 안다면 reserve()로 미리 용량을 확보해 복사를 줄인다.

기본 선택은 거의 항상 동적 배열이다 "어떤 자료구조를 쓸지 모르겠다"면 std::vector로 시작한다. 캐시 친화성과 O(1) 접근 덕분에, 이론적으로 더 나아 보이는 자료구조보다 실측이 빠른 경우가 많다. 다른 자료구조는 vector로는 부족하다는 근거가 생겼을 때 선택한다.

연결 리스트 (Linked List)

연결 리스트는 원소를 노드(node)에 담고, 각 노드가 다음 노드의 주소를 포인터로 가리켜 사슬처럼 잇는 자료구조다. 노드들은 메모리 여기저기 흩어져 있어도 된다 — 포인터만 따라가면 순서가 유지된다.

노드는 데이터와 next 포인터를 가진다 — 메모리상 위치는 제각각이다

성능 특성

  • 삽입·삭제 O(1) — 삽입/삭제할 위치의 노드를 이미 가리키고 있다면, 포인터 몇 개만 고쳐 끼우거나 빼면 된다. 원소를 미는 일이 없다.
  • 임의 접근 O(n) — n번째 노드를 찾으려면 head부터 포인터를 n번 따라가야 한다. 인덱스로 주소를 계산할 수 없다.
  • 캐시 비친화 — 노드가 메모리 여기저기 흩어져 있어, 순회할 때마다 캐시 미스가 난다. 같은 O(n) 순회라도 배열보다 훨씬 느린 경우가 많다.
// 단일 연결 리스트 노드
struct Node
{
    int m_value;
    Node* m_next;
};

// head 바로 뒤에 새 노드 삽입 — O(1), 원소를 밀지 않는다
void InsertAfterHead(Node* head, int value)
{
    Node* node = new Node{ value, nullptr };
    node->m_next = head->m_next;
    head->m_next = node;
}

// n번째 노드 탐색 — O(n), 포인터를 하나씩 따라가야 한다
Node* GetNodeAt(Node* head, int index)
{
    Node* current = head;
    for (int i = 0; i < index && current != nullptr; ++i)
    {
        current = current->m_next;
    }
    return current;
}

단일 · 이중 · 원형

  • 단일 연결 리스트 — 각 노드가 next만 가진다. 앞으로만 이동할 수 있다.
  • 이중 연결 리스트 — next와 prev를 모두 가진다. 양방향 이동이 가능하고, 어떤 노드든 그 자체만으로 O(1) 삭제가 된다. std::list가 이 구조다.
  • 원형 연결 리스트 — 마지막 노드의 next가 다시 head를 가리킨다. 라운드 로빈 순회처럼 "끝없이 도는" 구조에 쓴다.
"연결 리스트가 삽입이 빠르다"는 절반만 맞다 삽입 자체는 O(1)이지만, 삽입할 위치를 먼저 찾는 비용이 O(n)이다. 게다가 노드가 메모리에 흩어져 캐시 미스가 끊임없이 발생한다. 실제 측정에서는 "중간에 자주 삽입/삭제"하는 경우조차 std::vector가 std::list보다 빠른 일이 흔하다. 연결 리스트는 이미 노드를 손에 쥐고 있고, 원소 이동 비용이 클 때만 진짜 유리하다.

스택 (Stack)

스택은 LIFO(Last In, First Out) 규칙을 따르는 자료구조다. 마지막에 넣은 것이 가장 먼저 나온다. 접시를 쌓았다가 위에서부터 꺼내는 모습과 같다. 한쪽 끝(top)에서만 넣고 빼므로 push와 pop 모두 O(1)이다.

쓰임 — 함수 호출, undo, 괄호 검사

스택은 "가장 최근의 것으로 되돌아간다"는 성질이 필요한 곳에 나타난다.

  • 함수 호출 스택 — 함수가 호출되면 호출 프레임이 쌓이고, 반환되면 가장 위 프레임이 빠진다. 재귀가 동작하는 원리다.
  • undo 기능 — 작업을 스택에 쌓고, 실행 취소는 가장 최근 작업을 pop한다.
  • 괄호 검사 — 여는 괄호를 push하고, 닫는 괄호를 만나면 pop해서 짝이 맞는지 확인한다.
// 스택으로 괄호 짝 검사 — push/pop 모두 O(1)
bool IsBalanced(const std::string& expr)
{
    std::stack<char> openStack;
    for (char ch : expr)
    {
        if (ch == '(' || ch == '{' || ch == '[')
        {
            openStack.push(ch);
        }
        else if (ch == ')' || ch == '}' || ch == ']')
        {
            if (openStack.empty())
            {
                return false;   // 닫는 괄호가 더 많다
            }
            openStack.pop();    // 가장 최근에 연 괄호와 짝지음
        }
    }
    return openStack.empty();   // 남은 여는 괄호가 없어야 균형
}
IsBalanced 실행 결과
IsBalanced("(a[b]{c})") -> true IsBalanced("(a[b)c]") -> false IsBalanced("((x)") -> false

큐 (Queue)

큐는 FIFO(First In, First Out) 규칙을 따른다. 먼저 넣은 것이 먼저 나온다. 줄을 서는 모습과 같다 — 앞쪽(front)에서 빼내고(dequeue), 뒤쪽(back)에서 넣는다(enqueue). 양 끝 연산 모두 O(1)이다.

쓰임 — 작업 큐, BFS

큐는 "도착한 순서대로 처리한다"는 공정함이 필요한 곳에 쓴다. 카메라가 캡처한 프레임을 처리 순서대로 담는 작업 큐, 그래프를 가까운 곳부터 훑는 너비 우선 탐색(BFS)이 대표적이다.

// 작업 큐 — 도착 순서대로 프레임을 처리한다
std::queue<Frame> jobQueue;

jobQueue.push(frameA);      // enqueue — 뒤에 넣음, O(1)
jobQueue.push(frameB);
jobQueue.push(frameC);

while (!jobQueue.empty())
{
    Frame next = jobQueue.front();   // 가장 먼저 들어온 것
    jobQueue.pop();                  // dequeue — 앞에서 뺌, O(1)
    ProcessFrame(next);              // A -> B -> C 순서로 처리됨
}

덱과 우선순위 큐

큐에는 변종이 있다.

  • 덱(deque, double-ended queue) — 양쪽 끝 모두에서 넣고 뺄 수 있다. 스택으로도 큐로도 쓸 수 있다. std::deque가 이것이다.
  • 우선순위 큐(priority queue) — 들어온 순서가 아니라 우선순위가 가장 높은 원소가 먼저 나온다. 보통 힙(heap)으로 구현하며, 삽입과 최댓값 추출이 O(log n)이다. std::priority_queue가 이에 해당한다.
스택·큐는 "인터페이스"이지 "구현"이 아니다 스택과 큐는 LIFO/FIFO라는 동작 규칙을 정의할 뿐, 내부는 배열로도 연결 리스트로도 만들 수 있다. 실제로 std::stack과 std::queue는 다른 컨테이너(std::deque 등)를 감싼 어댑터다. "무엇을 할 수 있는가"와 "어떻게 만들었는가"를 구분하는 것이 자료구조 사고의 핵심이다.

트리 (Tree)

트리는 원소가 계층(hierarchy)을 이루는 비선형 자료구조다. 하나의 루트(root)에서 시작해 각 노드가 여러 자식(child)을 가지며, 사이클이 없다. 파일 시스템, 조직도, 파싱 트리처럼 "포함 관계"가 있는 데이터에 자연스럽다.

BST는 정렬된 계층 구조 — 값을 비교하며 한쪽 가지로만 내려가면 O(log n)에 찾는다

이진 트리와 이진 탐색 트리

이진 트리(binary tree)는 각 노드가 자식을 최대 둘(왼쪽·오른쪽)만 가지는 트리다. 여기에 정렬 규칙을 더한 것이 이진 탐색 트리(Binary Search Tree, BST)다 — 모든 노드에 대해 "왼쪽 서브트리의 값 < 노드 값 < 오른쪽 서브트리의 값"이 성립한다. 이 규칙 덕분에 탐색할 때 한 번 비교할 때마다 절반을 버릴 수 있어, 균형 잡힌 BST의 탐색·삽입·삭제는 O(log n)이다.

// 이진 탐색 트리 노드
struct TreeNode
{
    int m_value;
    TreeNode* m_left;
    TreeNode* m_right;
};

// BST 탐색 — 비교할 때마다 절반을 버린다, 균형 시 O(log n)
TreeNode* Search(TreeNode* root, int target)
{
    TreeNode* current = root;
    while (current != nullptr)
    {
        if (target == current->m_value)
        {
            return current;             // 찾음
        }
        else if (target < current->m_value)
        {
            current = current->m_left;  // 왼쪽 가지로만 내려감
        }
        else
        {
            current = current->m_right; // 오른쪽 가지로만 내려감
        }
    }
    return nullptr;                     // 없음
}

균형 트리 — AVL, Red-Black

BST의 O(log n)은 트리가 균형 잡혀 있을 때만 보장된다. 정렬된 데이터를 순서대로 삽입하면 한쪽으로만 자라 사실상 연결 리스트가 되고, 탐색이 O(n)으로 퇴화한다. 이를 막는 것이 균형 트리(balanced tree)다.

  • AVL 트리 — 모든 노드에서 좌우 서브트리 높이 차가 1 이하가 되도록 삽입·삭제 때마다 회전(rotation)으로 재조정한다. 균형이 엄격해 탐색이 빠르다.
  • Red-Black 트리 — 노드에 빨강/검정 색을 부여하고 색 규칙으로 높이 균형을 느슨하게 유지한다. AVL보다 회전이 적어 삽입·삭제가 잦을 때 유리하다. std::map과 std::set이 보통 이 구조다.

힙 (Heap)

힙은 "부모가 자식보다 항상 크다(최대 힙) 또는 작다(최소 힙)"는 규칙만 지키는 완전 이진 트리다. BST와 달리 전체가 정렬되어 있지는 않지만, 최댓값(또는 최솟값)이 항상 루트에 있다. 그래서 우선순위 큐 구현에 쓰인다 — 최댓값 추출 O(log n), 삽입 O(log n). 완전 이진 트리라 보통 배열 하나로 구현한다.

해시 테이블 (Hash Table)

해시 테이블은 키(key)를 해시 함수에 통과시켜 얻은 숫자로 저장 위치(버킷)를 직접 계산하는 자료구조다. 트리처럼 비교하며 내려가지 않고, 키 하나로 위치를 단번에 계산하므로 평균 조회·삽입·삭제가 모두 O(1)이다.

해시 함수가 키를 버킷 인덱스로 변환한다 — 비교 없이 위치를 계산하므로 평균 O(1)

해시 함수와 부하율

해시 함수는 임의의 키를 고정 범위의 정수로 매핑한다. 좋은 해시 함수는 키를 버킷에 고르게 흩뿌려야 한다 — 한곳에 몰리면 O(1)이 깨진다. 부하율(load factor)은 "원소 수 / 버킷 수"로, 이 값이 일정 임계(보통 0.75 정도)를 넘으면 버킷을 늘리고 전체를 다시 해싱(rehash)한다. 부하율이 낮을수록 충돌이 줄지만 메모리를 더 쓴다.

충돌 해결 — 체이닝과 개방 주소법

서로 다른 키가 같은 버킷으로 매핑되는 것을 충돌(collision)이라 한다. 버킷 수는 유한하므로 충돌은 반드시 일어난다. 해결 방법은 둘이다.

  • 체이닝(chaining) — 각 버킷을 연결 리스트로 만들어, 충돌한 원소를 그 리스트에 잇는다. 구현이 단순하고 부하율이 높아도 견딘다. std::unordered_map이 이 방식이다.
  • 개방 주소법(open addressing) — 충돌하면 정해진 규칙(선형 탐사 등)으로 다른 빈 버킷을 찾아 거기 넣는다. 모든 원소가 버킷 배열 안에 있어 캐시 친화적이지만, 부하율이 높아지면 급격히 느려진다.
해시 테이블의 O(1)은 "평균"이다 — 충돌을 무시하지 말 것 해시 함수가 나쁘거나 키가 악의적으로 골라지면 모든 키가 한 버킷에 몰릴 수 있고, 그러면 조회가 O(n)으로 퇴화한다. "해시 = 항상 O(1)"이라고 믿고 최악 케이스를 고려하지 않으면, 데이터가 늘었을 때 원인을 알 수 없는 성능 저하를 만난다. 키 분포와 부하율을 항상 의식해야 한다.

그래프 (Graph)

그래프는 정점(vertex)들과 그 사이를 잇는 간선(edge)으로 이루어진 자료구조다. 트리도 그래프의 한 종류지만, 그래프는 사이클을 가질 수 있고 계층이라는 제약이 없다. 도로망, SNS 친구 관계, 작업 의존성, 데이터 플로우 등 "무엇이 무엇과 연결되어 있는가"를 표현한다.

방향·무방향·가중치

  • 무방향 그래프 — 간선에 방향이 없다. "A와 B는 친구"처럼 대칭 관계를 나타낸다.
  • 방향 그래프(directed graph) — 간선에 방향이 있다. "A 작업이 끝나야 B 작업 시작"처럼 비대칭 관계를 나타낸다.
  • 가중치 그래프 — 간선에 비용·거리 같은 값이 붙는다. 최단 경로 계산의 기반이다.

인접 행렬 vs 인접 리스트

그래프를 메모리에 담는 방법은 크게 둘이다.

  • 인접 행렬(adjacency matrix) — V×V 크기의 2차원 배열. matrix[i][j]가 정점 i→j 간선의 유무(또는 가중치)다. 간선 존재 확인이 O(1)이지만, 간선이 적어도 O(V²) 메모리를 쓴다.
  • 인접 리스트(adjacency list) — 각 정점마다 "연결된 정점들의 리스트"를 둔다. 메모리가 O(V+E)로 효율적이라, 간선이 희소한 대부분의 실제 그래프에 적합하다.
// 인접 리스트로 표현한 방향 그래프
class Graph
{
public:
    // 정점 from -> to 방향 간선을 추가한다
    void AddEdge(int from, int to)
    {
        m_adjacency[from].push_back(to);
    }

    // 한 정점에서 나가는 간선들을 돌려준다
    const std::vector<int>& GetNeighbors(int vertex) const
    {
        return m_adjacency.at(vertex);
    }

private:
    // 정점 번호 -> 인접 정점 목록
    std::unordered_map<int, std::vector<int>> m_adjacency;
};

인접 리스트O(V+E)O(degree)간선이 적은 희소 그래프 (대부분)

상황별 선택

  • 인덱스로 빠르게 접근하고 순차 순회가 잦다 → 동적 배열(vector)
  • 키로 빠르게 찾되 순서는 필요 없다 → 해시 테이블(unordered_map)
  • 키로 찾으면서 정렬 순서도 유지해야 한다 → 균형 트리(map)
  • 가장 최근/먼저 들어온 것만 꺼낸다 → 스택 / 큐
  • 항상 우선순위가 가장 높은 것을 꺼낸다 → 힙(priority_queue)
  • 개체 간 연결 관계를 표현한다 → 그래프(인접 리스트)

산업 SW 관점

산업용 이미징 SDK에서 자료구조는 추상적 이론이 아니라 코드 곳곳에 박혀 있다.

  • 이미지 픽셀은 배열이다 — 한 장의 이미지는 결국 픽셀 값의 연속 메모리 블록이다. 행 단위 순차 접근이 압도적으로 많으므로, 배열의 캐시 친화성이 곧 처리 속도다. 픽셀을 연결 리스트에 담는다는 발상은 성능상 재앙이다.
  • 작업 큐 — 카메라가 초당 수십~수백 프레임을 쏟아낼 때, 도착한 프레임을 큐에 담아 처리 스레드가 FIFO로 꺼내 처리한다. 긴급 프레임이 섞이면 우선순위 큐로 바꾼다.
  • 블록 그래프(데이터 플로우 에디터) — 비주얼 블록 에디터의 처리 블록들은 정점, 블록 간 연결은 간선인 방향 그래프다. 어떤 순서로 블록을 실행할지는 이 그래프의 위상 정렬로 결정한다.
  • 이름 조회 테이블 — 블록 종류를 이름 문자열로 찾을 때는 해시 테이블(unordered_map)이 자연스럽다.
자료구조가 아키텍처를 만든다 "데이터 플로우 기반 블록 에디터"라는 제품 컨셉 자체가 그래프 자료구조의 직접적 표현이다. 자료구조를 제대로 고르면 아키텍처가 데이터의 자연스러운 형태를 따라간다. 잘못 고르면 데이터와 코드가 끊임없이 싸운다.

흔한 함정

함정 1 — 연결 리스트가 항상 빠르다는 오해

"중간 삽입·삭제가 많으면 연결 리스트"라는 교과서 규칙은 캐시를 고려하지 않은 이론값이다. 현대 CPU에서는 메모리 접근 패턴이 곧 성능이다. 연결 리스트는 노드가 흩어져 매 순회마다 캐시 미스가 나는 반면, 배열은 연속 메모리라 순회가 수십 배 빠를 수 있다. 실제로는 "삽입 위치를 찾아 이동하는" 시나리오에서도 std::vector가 std::list를 이기는 일이 흔하다. 추측하지 말고 측정해야 한다.

함정 2 — 해시 충돌을 무시한다

해시 테이블의 O(1)은 평균값이지 보장값이 아니다. 나쁜 해시 함수나 치우친 키 분포는 모든 원소를 한 버킷에 몰아넣어 O(n)을 만든다. 커스텀 타입을 키로 쓸 때 해시 함수를 대충 작성하면, 데이터가 적을 때는 멀쩡하다가 규모가 커지면 갑자기 느려진다. 부하율과 키 분포를 의식하고, 커스텀 키에는 제대로 된 해시 함수를 제공해야 한다.

함정 3 — map과 unordered_map을 혼동한다

이름이 비슷해 무심코 섞어 쓰지만 둘은 전혀 다른 자료구조다. std::map은 균형 트리로 O(log n)이며 키가 정렬되어 있다. std::unordered_map은 해시 테이블로 평균 O(1)이지만 순서가 없다. 정렬 순회나 범위 조회가 필요하면 map, 단순 조회 속도만 필요하면 unordered_map이다. "더 빠를 것 같아서" unordered_map을 골랐는데 정렬된 순회가 필요해지면 설계를 다시 해야 한다.

함정 4 — 자료구조 없이 배열로 다 해결하려 한다

배열만으로도 어떻게든 동작은 한다 — 이름으로 찾기 위해 전체를 순회하고(O(n)), 정렬 유지를 위해 매번 다시 정렬하고, 계층 관계를 인덱스 계산으로 흉내 낸다. 작은 데이터에서는 문제가 드러나지 않지만, 규모가 커지면 곳곳에서 O(n)·O(n log n)이 누적되어 제품이 느려진다. "이 데이터에 자주 하는 연산이 무엇인가"를 묻고 그에 맞는 자료구조를 고르는 것은, 나중에 갈아엎는 것보다 처음에 하는 편이 훨씬 싸다.

자료구조 선택은 되돌리기 비싼 결정이다 한번 자료구조를 정하면 그것을 다루는 코드가 그 위에 쌓인다. 나중에 바꾸려면 그 코드를 전부 손봐야 한다. 그래서 자료구조 선택은 "일단 되게 만들고 나중에 고치자"가 가장 잘 안 통하는 영역이다. 데이터의 형태와 주요 연산을 먼저 분석하고 시작해야 한다.
