소유권(Ownership) — Rust의 핵심

2026-06-25 약 8분 분량 Rust 시리즈
이 편에서 배우는 것 Rust가 가비지 컬렉터 없이 메모리 안전을 보장하는 핵심 장치, 소유권(ownership)을 다룬다. 소유권 3대 규칙, 값을 옮기는 move 시맨틱, 스코프가 끝날 때 일어나는 자동 정리(drop), 스택 값에 적용되는 Copy와 힙 값에 적용되는 Move의 차이, 그리고 함수 인자로 값을 넘길 때 소유권이 어떻게 이동하는지를 컴파일 가능한 예제로 익힌다. C++의 move 시맨틱·RAII를 알면 절반은 이미 아는 셈이지만, 결정적 차이는 "컴파일러가 강제한다"는 점이다.

소유권이란 무엇인가

프로그램은 메모리를 빌려 쓴다. 문제는 "언제 돌려주느냐"다. C/C++는 사람이 직접 free/delete를 부르고, 그 결과 누수·이중 해제·해제 후 사용(use-after-free) 같은 버그가 생긴다. Java나 Go는 가비지 컬렉터(GC)가 대신 회수하지만, 런타임에 비용과 멈춤(pause)을 떠안는다.

Rust는 제3의 길을 택한다. 소유권(ownership)은 "이 값을 누가 책임지고 해제할 것인가"를 컴파일 시점에 추적하는 규칙 체계다. 모든 값에는 단 하나의 소유자가 있고, 소유자가 스코프를 벗어나면 값은 자동으로 정리된다. GC도, 수동 해제도 없다. 메모리 관리 비용을 런타임에서 컴파일 타임으로 옮긴 것이 소유권의 본질이다.

C++ 경험자를 위한 한 줄 다리 소유권은 새로운 개념이라기보다, C++에서 권장되는 좋은 습관(RAII, std::unique_ptr로 단일 소유, move로 자원 이전)을 언어가 문법으로 못 박은 것에 가깝다. C++에서는 규율로 지키던 것을, Rust에서는 컴파일러가 어기면 빌드를 막는다.

소유권 3대 규칙

Rust 공식 The Book이 정리한 소유권의 규칙은 단 세 줄이다.

  1. Rust의 모든 값에는 소유자(owner)라 불리는 변수가 있다.
  2. 한 시점에 소유자는 오직 하나다.
  3. 소유자가 스코프를 벗어나면 값은 버려진다(dropped).

이 세 규칙이 전부다. 나머지 동작은 모두 여기서 파생된다. 먼저 세 번째 규칙, 스코프 종료와 정리를 보자.

fn main() {
    // s는 아직 선언되지 않았다 — 여기서는 유효하지 않다
    {
        let s = String::from("hello"); // 이 지점부터 s가 유효하다
        println!("{s}");               // s를 사용한다
    } // 이 중괄호에서 스코프가 끝난다 → s.drop()이 자동 호출되어 힙 메모리 해제

    // 여기서 s를 쓰면 컴파일 에러: s가 스코프 밖이다
}

String은 힙에 문자열 데이터를 들고 있다. 스코프가 끝나는 } 지점에서 Rust는 자동으로 drop을 호출해 그 힙 메모리를 돌려준다. 개발자가 해제 코드를 한 줄도 쓰지 않았다는 점이 핵심이다. 이것은 C++의 소멸자(destructor)와 정확히 같은 RAII 패턴이다.

move 시맨틱과 drop

규칙 2번 "소유자는 오직 하나"가 흥미로워지는 지점은 값을 다른 변수에 대입할 때다. 힙을 가진 값을 대입하면 Rust는 복사하지 않고 소유권을 옮긴다(move).

fn main() {
    let s1 = String::from("hello");
    let s2 = s1; // 소유권이 s1 → s2로 이동(move)한다. 힙 데이터는 복사되지 않는다

    // 이제 s1은 더 이상 유효하지 않다 (moved-from 상태)
    println!("{s2}"); // OK: 새 소유자 s2를 통해 접근
} // s2만 drop된다. s1은 이미 무효라 이중 해제가 일어나지 않는다

let s2 = s1; 한 줄에서 무슨 일이 일어났는지가 전부다. 힙에 있는 실제 문자열 바이트는 그대로 두고, 그것을 가리키는 포인터·길이·용량(스택에 있는 작은 메타데이터)만 s2로 넘어간다. 동시에 s1은 무효화된다. 그래서 두 변수가 같은 힙을 가리켜 둘 다 해제하려 드는 이중 해제(double free) 위험이 원천 차단된다.

무효화된 s1을 다시 쓰려 하면 어떻게 될까. C++이라면 moved-from 객체에 접근하는 코드가 런타임까지 살아남을 수 있지만, Rust는 그렇지 않다.

fn main() {
    let s1 = String::from("hello");
    let s2 = s1;          // 여기서 s1의 소유권이 옮겨졌다
    println!("{s1}");     // ❌ 컴파일 에러: borrow of moved value: `s1`
}
// 위 코드는 빌드되지 않는다. use-after-move를 컴파일러가 거부한다.
C++과 이렇게 다르다 — use-after-move C++에서 auto s2 = std::move(s1); 이후 s1을 쓰는 것은 합법이다. moved-from 상태는 "유효하지만 미지정 값"이라, 컴파일러는 막지 않고 잘해야 정적 분석 도구가 경고할 뿐이다. Rust는 같은 상황을 컴파일 에러로 거부한다. move 이후 원래 변수는 타입 시스템 수준에서 접근 불가가 되므로, "옮긴 뒤 실수로 다시 쓰는" 버그 자체가 존재할 수 없다.

Copy 타입 vs Move 타입

그렇다면 모든 대입이 move일까? 아니다. 다음 코드는 멀쩡히 동작한다.

fn main() {
    let x = 5;
    let y = x;        // i32는 Copy 타입 — x가 y로 복사된다
    println!("{x} {y}"); // OK: x도 여전히 유효하다. 둘 다 5
}

i32 같은 정수는 크기가 고정돼 있고 전부 스택에 들어간다. 이런 타입은 Copy 트레이트를 구현하며, 대입 시 값을 그대로 복제한다. 복제 비용이 작고 힙 자원이 없어 이중 해제 걱정이 없으니, 원본을 무효화할 이유가 없다. 그래서 x는 대입 후에도 살아 있다.

반대로 String처럼 힙 자원을 가진 타입은 Copy가 아니고, 대입은 move가 된다. 갈림길은 단순하다.

구분Copy 타입Move 타입(비-Copy)
대표 예i32, f64, bool, char, 이들로만 된 튜플String, Vec<T>, Box<T>
저장 위치전적으로 스택힙 자원 보유
대입 동작비트 단위 복사소유권 이동(move)
대입 후 원본그대로 유효무효화됨

Move 타입의 데이터를 진짜로 복제하고 싶다면 명시적으로 .clone()을 부른다. 그러면 힙 데이터까지 깊은 복사가 되어 두 변수가 독립적으로 유효해진다.

fn main() {
    let s1 = String::from("hello");
    let s2 = s1.clone(); // 힙 데이터를 깊은 복사한다 — 둘은 독립적

    println!("{s1} {s2}"); // OK: s1, s2 모두 유효하다
} // s1, s2 각각의 힙 메모리가 따로 drop된다

C++에 대응시키면, move 타입의 기본 대입은 std::move에, .clone()은 깊은 복사 생성자에 해당한다. 다만 Rust에서는 비용이 큰 복사를 clone()이라는 명시적 호출로만 일어나게 해, "어디서 깊은 복사가 발생하는지"가 코드에 드러난다.

함수와 소유권 이동

함수에 값을 넘기는 것은 변수에 대입하는 것과 똑같이 동작한다. Move 타입을 인자로 넘기면 소유권이 함수 안으로 이동하고, 호출한 쪽에서는 그 변수를 더 못 쓴다.

fn takes_ownership(s: String) {
    println!("받음: {s}");
} // s가 여기서 drop된다

fn makes_copy(n: i32) {
    println!("받음: {n}");
} // n은 Copy라 특별한 정리 없음

fn main() {
    let s = String::from("hello");
    takes_ownership(s); // s의 소유권이 함수로 이동한다
    // 여기서 s를 쓰면 컴파일 에러 — 소유권이 이미 넘어갔다

    let n = 5;
    makes_copy(n);      // i32는 복사되어 넘어간다
    println!("{n}");    // OK: n은 여전히 유효하다
}

그렇다면 함수에 값을 줬다가 계속 쓰고 싶을 때는 어떻게 할까. 한 방법은 함수가 소유권을 돌려주는 것이다. 값을 반환하면 소유권도 함께 호출자에게 이동한다.

fn append_world(mut s: String) -> String {
    s.push_str(", world"); // 받은 값을 수정한다
    s                      // 소유권을 호출자에게 되돌려준다
}

fn main() {
    let s1 = String::from("hello");
    let s2 = append_world(s1); // s1의 소유권을 넘기고, 결과의 소유권을 s2로 받는다

    println!("{s2}"); // 출력: hello, world
} // s2가 drop된다
매번 돌려주는 건 번거롭다 — 그래서 빌림(borrowing)이 있다 값을 쓸 때마다 소유권을 넘겼다 돌려받는 것은 분명 불편하다. 실무에서는 소유권을 옮기지 않고 잠시 빌려 쓰는 참조(reference)와 빌림(borrowing)을 쓴다(&s). 이 글은 소유권의 이동 자체에 집중했고, 빌림 규칙은 시리즈 다음 편에서 다룬다.

정리

  • 소유권은 메모리 관리를 컴파일 타임으로 옮긴다 — GC도, 수동 해제도 없이 메모리 안전을 얻는다.
  • 3대 규칙 — 모든 값엔 소유자가 있고, 소유자는 하나뿐이며, 소유자가 스코프를 벗어나면 값은 drop된다.
  • move 시맨틱 — 힙 자원을 가진 값의 대입·인자 전달은 소유권을 옮기고 원본을 무효화한다. 이중 해제가 원천 차단된다.
  • Copy vs Move — 스택만 쓰는 작은 값은 복사되고 원본도 살아 있다. 힙 자원을 가진 값은 이동되며, 깊은 복사는 명시적 .clone()으로만 일어난다.
  • C++과의 결정적 차이 — RAII·move라는 개념은 닮았지만, Rust는 use-after-move를 컴파일 에러로 막는다. 규율이 아니라 타입 시스템이 안전을 보장한다.
