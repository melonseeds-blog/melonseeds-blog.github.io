모듈 시스템과 크레이트

2026-06-25 약 8분 분량 Rust 시리즈
이 편에서 배우는 것 Rust 코드를 어떻게 여러 조각으로 나누고 다시 이어 붙이는지 본다. mod로 모듈 트리를 만들고, pub으로 공개 범위를 정하고, use로 긴 경로를 줄인다. 한 파일이 어떻게 여러 파일·디렉터리로 자라는지, crate·super·self 경로가 무엇을 가리키는지 익힌다. 끝으로 Cargo.toml로 외부 크레이트를 끌어오고, 워크스페이스로 여러 크레이트를 한 묶음으로 다루는 법을 맛본다.

왜 모듈 시스템인가

프로그램이 커지면 코드를 나눠야 한다. C++에서는 코드를 .h 헤더와 .cpp 구현으로 가르고, 이름 충돌을 막으려고 namespace로 묶고, 누가 무엇을 보게 할지는 #include와 빌드 시스템이 결정한다. 선언과 정의가 따로 놀고, 텍스트 단위의 #include가 컴파일 순서에 끼어든다.

Rust는 이 일을 하나의 메커니즘 모듈 트리로 푼다. 크레이트(crate)는 컴파일의 한 단위다. 실행 파일을 만드는 바이너리 크레이트는 main.rs가, 라이브러리 크레이트는 lib.rs가 뿌리(루트)다. 그 뿌리에서 mod 선언으로 가지를 뻗어 모듈 트리가 자란다. 모든 항목은 기본이 비공개라, 공개하고 싶은 것만 pub으로 골라 내보낸다.

C++과 이렇게 다르다 — 헤더가 없다 Rust에는 선언을 따로 적는 헤더가 없다. 한 곳에 정의를 쓰면 그게 곧 선언이다. 또 #include 같은 텍스트 복사가 없어, 어떤 모듈을 두 곳에서 써도 코드가 두 번 들어가지 않는다. 가시성도 파일 분할과 분리돼 있다 — 파일을 나눴다고 자동으로 공개되지 않고, pub을 붙여야만 밖에서 보인다.

mod · pub · use

세 키워드의 역할은 분명하다. mod는 모듈을 선언하고, pub은 항목을 공개하고, use는 긴 경로를 짧은 이름으로 끌어온다. 한 파일 안에서 인라인 모듈로 셋을 모두 보면 이렇다.

// src/main.rs — 한 파일 안에서 모듈 트리 만들기
mod network {
    // 모듈 안의 항목은 기본이 비공개다.
    pub mod client {
        // pub을 붙여야 바깥 모듈에서 호출할 수 있다.
        pub fn connect(host: &str) -> String {
            format!("connected to {host}")
        }

        // pub이 없으니 client 모듈 밖에서는 보이지 않는다.
        fn handshake() -> u32 {
            42
        }
    }
}

// 긴 경로를 use로 한 번 끌어오면 짧은 이름으로 쓴다.
use network::client;

fn main() {
    let msg = client::connect("example.com");
    println!("{msg}");
}

handshake는 pub이 없어서 client 모듈 안에서만 쓸 수 있다. 밖에서 호출하면 컴파일 오류가 난다. 가시성은 항상 한 단계씩 열린다 — client를 공개해도 그 안의 항목까지 자동으로 공개되지는 않는다.

pub의 갈래와 구조체 필드

구조체는 타입을 공개해도 필드는 따로 공개해야 한다. 이 점이 캡슐화를 자연스럽게 만든다.

mod geometry {
    pub struct Point {
        pub x: f64,      // 공개 필드
        y: f64,          // 비공개 필드 — 모듈 밖에서 직접 못 읽는다
    }

    impl Point {
        // 비공개 필드가 있으니 생성은 이런 연관 함수로만 가능하다.
        pub fn new(x: f64, y: f64) -> Point {
            Point { x, y }
        }

        // &self는 값을 빌려 읽기만 한다 — 소유권을 가져가지 않는다.
        pub fn distance_from_origin(&self) -> f64 {
            (self.x * self.x + self.y * self.y).sqrt()
        }
    }
}

fn main() {
    let p = geometry::Point::new(3.0, 4.0);
    println!("x = {}", p.x);                    // OK: x는 pub
    println!("dist = {}", p.distance_from_origin()); // 5.0
    // println!("{}", p.y);  // 컴파일 오류: y는 비공개
}

distance_from_origin은 &self로 자기 자신을 빌려 읽기만 한다. 값을 옮기지 않으니 호출 뒤에도 p를 계속 쓸 수 있다. use로 이름을 끌어올 때 충돌이 나면 as로 별명을 준다.

use std::fmt::Result;
use std::io::Result as IoResult;   // 같은 이름 Result 충돌을 별명으로 해소

fn render() -> Result { Ok(()) }
fn read() -> IoResult<()> { Ok(()) }

파일과 디렉터리로 쪼개기

인라인 모듈이 커지면 파일로 옮긴다. 규칙은 단순하다. mod 이름;처럼 본문 대신 세미콜론으로 선언하면, 컴파일러가 같은 이름의 파일에서 본문을 찾는다.

예를 들어 루트에서 mod network;라고 쓰면 컴파일러는 src/network.rs를 읽는다. 그 모듈이 다시 하위 모듈을 가지면 두 가지 배치가 가능하다.

// 디렉터리 모듈 배치 (현대 Rust 권장 형태)
// src/
//  ├─ main.rs        ← 크레이트 루트
//  ├─ network.rs     ← network 모듈 본문, 하위 모듈을 선언
//  └─ network/
//       └─ client.rs ← network::client 모듈 본문
// src/main.rs
mod network;   // src/network.rs 를 읽어 온다

fn main() {
    let s = network::client::connect("example.com");
    println!("{s}");
}
// src/network.rs
pub mod client;   // src/network/client.rs 를 읽어 온다
// src/network/client.rs
pub fn connect(host: &str) -> String {
    format!("connected to {host}")
}

파일을 어떻게 나눠도 모듈 트리의 경로는 그대로다. 위 코드에서 함수는 한 파일에 있든 세 파일에 흩어져 있든 똑같이 network::client::connect로 부른다. 파일 위치는 구현 세부일 뿐, 호출하는 쪽의 경로를 바꾸지 않는다.

파일을 만들었다고 모듈이 되지 않는다 src/network/client.rs 파일을 만들어도, 부모에 mod client; 선언이 없으면 컴파일에 포함되지 않는다. C++의 빌드 시스템이 소스 목록을 관리하던 자리를, Rust에서는 mod 선언이 대신한다. 트리에 연결돼야 비로소 코드가 산다.

crate · super · self 경로

모듈 안에서 다른 항목을 가리킬 때 경로를 쓴다. 절대 경로는 크레이트 루트를 뜻하는 crate에서 시작하고, 상대 경로는 현재 위치를 뜻하는 self나 부모를 뜻하는 super에서 시작한다. super는 파일 시스템의 ..과 같은 감각이다.

mod store {
    pub fn open() -> &'static str {
        "store open"
    }

    pub mod front {
        pub fn greet() -> String {
            // super = 부모 모듈(store). 형제 함수 open을 부른다.
            let status = super::open();
            // crate = 크레이트 루트에서 내려오는 절대 경로.
            let banner = crate::config::BANNER;
            format!("{banner}: {status}")
        }
    }
}

mod config {
    pub const BANNER: &str = "MyShop";
}

fn main() {
    // 루트에서는 절대 경로로 자연스럽게 접근한다.
    println!("{}", store::front::greet());  // MyShop: store open
}

고르는 기준은 단순하다. 항목이 모듈 트리에서 함께 움직일 것 같으면 super 같은 상대 경로가 리팩터링에 강하고, 멀리 떨어진 안정된 위치를 가리키면 crate 절대 경로가 읽기 쉽다. self는 현재 모듈을 명시할 때나 use에서 여러 항목을 묶을 때 쓴다.

// self는 현재 모듈을 가리킨다. 묶음 import에서 자주 보인다.
use std::io::{self, Write};   // std::io 모듈 자체 + io::Write 트레잇

fn log(line: &str) -> io::Result<()> {
    let mut out = io::stdout();
    out.write_all(line.as_bytes())   // Write 트레잇 메서드
}
C++과 이렇게 다르다 — 경로가 곧 의존성이다 C++의 :: 네임스페이스 경로는 이름을 한정할 뿐, 그 심볼이 어디서 컴파일되는지는 헤더와 링커가 따로 정한다. Rust에서는 crate:: · super:: 경로가 모듈 트리의 실제 위치를 가리키고, 그 트리가 곧 컴파일 단위 구성이다. 경로와 빌드 구성이 분리돼 있지 않다.

Cargo.toml과 워크스페이스

외부 크레이트를 쓰려면 Cargo.toml의 [dependencies]에 한 줄 적으면 된다. Cargo가 crates.io에서 받아 빌드까지 엮는다. C++처럼 헤더 경로·라이브러리 경로·링크 플래그를 손으로 맞출 필요가 없다.

# Cargo.toml — 의존성을 선언하면 Cargo가 받아서 빌드까지 연결한다
[package]
name = "myshop"
version = "0.1.0"
edition = "2021"

[dependencies]
serde = { version = "1", features = ["derive"] }
rand = "0.8"

선언한 외부 크레이트는 코드에서 그 이름을 루트로 하는 경로로 쓴다. std를 쓰던 방식과 똑같다.

use rand::Rng;   // 외부 크레이트 rand에서 Rng 트레잇을 끌어온다

fn roll_dice() -> u32 {
    let mut rng = rand::thread_rng();
    rng.gen_range(1..=6)   // 1 이상 6 이하 난수
}
관심사C++ 전형Rust + Cargo
이름 한정namespace + ::모듈 트리 + 경로(::)
선언/정의 분리헤더(.h) + 구현(.cpp)분리 없음 — 정의가 곧 선언
다른 파일 포함#include 텍스트 복사mod 선언으로 트리에 연결
외부 라이브러리경로·링크 플래그 수동 설정Cargo.toml 한 줄
여러 패키지 묶음상위 빌드 스크립트로 조립워크스페이스

워크스페이스 맛보기

프로젝트가 여러 크레이트로 커지면 워크스페이스로 묶는다. 여러 크레이트가 하나의 Cargo.lock과 공통 target/ 출력 폴더를 공유해, 의존성 버전이 한 묶음 안에서 일관되게 맞춰진다.

# 최상위 Cargo.toml — 멤버 크레이트를 묶는 워크스페이스
[workspace]
members = ["core", "cli"]
resolver = "2"
# cli/Cargo.toml — 같은 워크스페이스 안의 core를 경로로 의존한다
[package]
name = "cli"
version = "0.1.0"
edition = "2021"

[dependencies]
core = { path = "../core" }

이렇게 두면 cli 크레이트의 코드에서 core를 외부 크레이트처럼 부른다 — use core::geometry::Point; 식이다. 모듈이 한 크레이트 안의 구획이라면, 워크스페이스는 여러 크레이트를 한 저장소에서 함께 빌드·테스트하는 상위 묶음이다.

정리

  • 크레이트는 컴파일 단위 — main.rs(바이너리)나 lib.rs(라이브러리)가 모듈 트리의 뿌리다.
  • mod · pub · use — mod로 선언하고, 기본 비공개를 pub으로 한 단계씩 열고, use로 긴 경로를 줄인다.
  • 파일 분할은 트리와 무관 — 한 파일이든 디렉터리든 호출 경로는 그대로다. mod 선언이 없으면 파일은 빌드에 포함되지 않는다.
  • 경로 키워드 — crate(루트 절대 경로), super(부모), self(현재 모듈).
  • Cargo가 의존성을 일원화 — Cargo.toml 한 줄로 외부 크레이트를 엮고, 워크스페이스로 여러 크레이트를 한 묶음으로 다룬다.
