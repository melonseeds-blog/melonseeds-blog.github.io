TensorRT란?

TensorRT는 NVIDIA가 만든 고성능 딥러닝 추론(inference) SDK다. PyTorch나 TensorFlow로 학습한 모델을 그대로 추론에 사용하면 일반적으로 느리다. TensorRT는 학습된 모델을 받아 다음과 같은 최적화를 수행한 뒤, NVIDIA GPU에서 매우 빠르게 실행되는 엔진(engine)으로 변환한다.

  • Layer fusion — Conv + BN + ReLU 같은 연속된 연산을 하나의 커널로 합친다.
  • Kernel auto-tuning — 대상 GPU에 가장 빠른 커널을 자동 선택한다.
  • Precision calibration — FP32를 FP16/INT8로 낮춰 메모리·연산을 줄인다.
  • Dynamic tensor memory — 텐서 메모리를 재사용해 풋프린트를 줄인다.
  • Multi-stream execution — 여러 입력을 병렬로 처리한다.
학습용이 아니라 추론용이다 TensorRT는 학습(training) 도구가 아니다. 학습은 PyTorch·TensorFlow에서 하고, 양산 단계의 추론만 TensorRT로 옮긴다. 이전 글 AI #10 모델 최적화에서 다룬 양자화·프루닝의 실전 런타임이 TensorRT다.

ONNX Runtime / OpenCV DNN과의 차이

산업 비전 현장에서 추론 런타임 선택지는 보통 세 가지다. AI #11 ONNX 배포와 AI #12 OpenCV DNN에서 다룬 두 런타임에 비해 TensorRT는 속도가 가장 빠르지만, 환경 제약이 가장 크다.

항목OpenCV DNNONNX RuntimeTensorRT
플랫폼CPU/GPU/모두CPU/GPU/모두NVIDIA GPU 전용
속도(NVIDIA GPU)중상최상
모델 호환성제한적매우 넓음넓음(일부 미지원 op 존재)
빌드 단계없음(즉시 로드)없음/짧음필수(수초~수십분)
엔진 이식성높음높음낮음(GPU/버전 종속)
INT8 양자화제한적지원강력하게 지원
통합 난이도쉬움쉬움중간
선택 기준 택트 타임이 빠듯하고 GPU가 고정된 양산 라인이면 TensorRT가 정답이다. 다양한 PC·GPU·CPU 환경에 모델을 배포해야 한다면 ONNX Runtime이 무난하다. 검사 로직과 추론이 한 OpenCV 파이프라인에 묶여 있고 모델이 작다면 OpenCV DNN으로도 충분하다.

TensorRT 워크플로우

TensorRT 사용 흐름은 항상 동일하다. 학습된 모델을 ONNX로 내보내기 → Builder로 엔진 빌드 → 엔진 파일 저장 → 런타임에서 deserialize 후 추론의 4단계다.

그림 1. TensorRT 표준 워크플로우 (ONNX → Builder → Engine → Runtime)

1단계 — PyTorch에서 ONNX 내보내기

import torch
import torchvision.models as models

model = models.resnet50(weights="DEFAULT").eval().cuda()
dummy = torch.randn(1, 3, 224, 224, device="cuda")

torch.onnx.export(
    model, dummy, "resnet50.onnx",
    input_names=["input"], output_names=["output"],
    opset_version=17,
    dynamic_axes={"input": {0: "batch"}, "output": {0: "batch"}},
)

2단계 — C++ API로 엔진 빌드

// Build a TensorRT engine from an ONNX model.
#include <NvInfer.h>
#include <NvOnnxParser.h>
#include <fstream>
#include <memory>

using namespace nvinfer1;

class Logger : public ILogger
{
public:
    void log(Severity severity, const char* msg) noexcept override
    {
        if (severity <= Severity::kWARNING)
        {
            std::cout << "[TRT] " << msg << std::endl;
        }
    }
};

bool BuildEngine(const std::string& onnxPath, const std::string& enginePath)
{
    Logger logger;
    auto builder = std::unique_ptr<IBuilder>(createInferBuilder(logger));
    const auto flag = 1U << static_cast<uint32_t>(NetworkDefinitionCreationFlag::kEXPLICIT_BATCH);
    auto network = std::unique_ptr<INetworkDefinition>(builder->createNetworkV2(flag));

    // Parse ONNX into the TensorRT network graph.
    auto parser = std::unique_ptr<nvonnxparser::IParser>(
        nvonnxparser::createParser(*network, logger));
    if (!parser->parseFromFile(onnxPath.c_str(),
            static_cast<int>(ILogger::Severity::kWARNING)))
    {
        return false;
    }

    // Builder config — workspace, precision, optimization profile.
    auto config = std::unique_ptr<IBuilderConfig>(builder->createBuilderConfig());
    config->setMemoryPoolLimit(MemoryPoolType::kWORKSPACE, 1ULL << 30);  // 1 GiB
    if (builder->platformHasFastFp16())
    {
        config->setFlag(BuilderFlag::kFP16);  // FP16 mixed precision
    }

    // Dynamic shape profile for batch size 1..8.
    auto profile = builder->createOptimizationProfile();
    profile->setDimensions("input", OptProfileSelector::kMIN,  Dims4{1, 3, 224, 224});
    profile->setDimensions("input", OptProfileSelector::kOPT,  Dims4{4, 3, 224, 224});
    profile->setDimensions("input", OptProfileSelector::kMAX,  Dims4{8, 3, 224, 224});
    config->addOptimizationProfile(profile);

    // Build and serialize.
    auto serialized = std::unique_ptr<IHostMemory>(
        builder->buildSerializedNetwork(*network, *config));
    if (!serialized) return false;

    std::ofstream out(enginePath, std::ios::binary);
    out.write(static_cast<const char*>(serialized->data()), serialized->size());
    return true;
}

3단계 — 런타임에서 추론

// Load a serialized engine and run inference.
#include <NvInfer.h>
#include <cuda_runtime_api.h>
#include <fstream>
#include <vector>

class TrtInferer
{
public:
    bool Load(const std::string& enginePath)
    {
        std::ifstream in(enginePath, std::ios::binary | std::ios::ate);
        const std::streamsize size = in.tellg();
        in.seekg(0);
        std::vector<char> blob(size);
        in.read(blob.data(), size);

        m_runtime.reset(createInferRuntime(m_logger));
        m_engine.reset(m_runtime->deserializeCudaEngine(blob.data(), size));
        m_context.reset(m_engine->createExecutionContext());
        cudaStreamCreate(&m_stream);
        return m_context != nullptr;
    }

    // Run a single inference. Caller provides device pointers.
    bool Infer(float* dInput, float* dOutput, int batch)
    {
        m_context->setInputShape("input", Dims4{batch, 3, 224, 224});
        m_context->setTensorAddress("input", dInput);
        m_context->setTensorAddress("output", dOutput);
        if (!m_context->enqueueV3(m_stream)) return false;
        cudaStreamSynchronize(m_stream);
        return true;
    }

private:
    Logger m_logger;
    std::unique_ptr<IRuntime> m_runtime;
    std::unique_ptr<ICudaEngine> m_engine;
    std::unique_ptr<IExecutionContext> m_context;
    cudaStream_t m_stream{};
};
입력은 GPU 메모리에 미리 올려둔다 카메라에서 받은 이미지는 보통 호스트에 있다. cudaMemcpyAsync로 디바이스에 올린 뒤 추론하면 PCIe 복사가 추론 시간에 포함된다. 시리즈 2편 메모리 계층에서 본 핀드 메모리(pinned memory)를 함께 쓰면 복사 자체가 빨라진다.

정밀도 (FP32 / FP16 / INT8)

TensorRT가 가장 큰 속도 이득을 주는 부분은 저정밀도 추론이다. FP32 그대로 두는 것은 사실상 GPU 텐서 코어(Tensor Core)를 놀리는 셈이다.

정밀도비트상대 속도 (Tensor Core 기준)정확도 손실추가 작업
FP32321.0×없음없음
FP16162~3×거의 없음플래그 설정만
BF16162~3×거의 없음플래그 설정만(Ampere+)
INT883~5×0.1~1% 수준캘리브레이션 필요
FP883~5×모델 의존적Hopper+ 한정
FP16부터 켜라 FP16은 거의 무료로 얻는 가속이다. 검사 정확도 검증만 통과하면 그냥 켠다. INT8은 캘리브레이션과 정확도 재검증이 필요하므로 택트 타임이 부족할 때만 단계적으로 적용한다. 
// Enable mixed precision.
config->setFlag(BuilderFlag::kFP16);   // half precision
config->setFlag(BuilderFlag::kINT8);   // INT8 (requires calibrator)
// kSTRICT_TYPES is deprecated; use kPREFER_PRECISION_CONSTRAINTS if needed.

INT8 캘리브레이션

INT8은 [-128, 127] 범위로 활성값을 양자화한다. 어느 실수 범위를 8비트 정수에 매핑할지 스케일(scale)을 결정해야 하며, 이 과정이 캘리브레이션(calibration)이다. 학습 후 양자화(PTQ — Post Training Quantization)는 다음과 같이 진행된다.

  1. 대표 입력 이미지를 수백~수천 장 준비 (양산 라인의 실제 분포와 닮을 것)
  2. FP32로 추론하면서 각 레이어 활성값의 분포(히스토그램)를 수집
  3. KL divergence 등을 최소화하는 클리핑 임계값으로 스케일 결정
  4. 이 스케일을 엔진에 굽기
// Minimal INT8 calibrator. Feeds batches from a dataset folder.
class Int8Calibrator : public IInt8EntropyCalibrator2
{
public:
    Int8Calibrator(int batchSize, const std::string& cacheFile,
                   const std::vector<std::string>& files)
        : m_batchSize(batchSize), m_cacheFile(cacheFile), m_files(files)
    {
        cudaMalloc(&m_deviceInput, batchSize * 3 * 224 * 224 * sizeof(float));
    }

    int getBatchSize() const noexcept override { return m_batchSize; }

    bool getBatch(void* bindings[], const char* names[], int n) noexcept override
    {
        if (m_index + m_batchSize > m_files.size()) return false;
        std::vector<float> host = LoadAndPreprocess(m_files, m_index, m_batchSize);
        cudaMemcpy(m_deviceInput, host.data(), host.size() * sizeof(float),
                   cudaMemcpyHostToDevice);
        bindings[0] = m_deviceInput;
        m_index += m_batchSize;
        return true;
    }

    // Cache to skip recalibration on rebuild.
    const void* readCalibrationCache(std::size_t& length) noexcept override
    {
        m_cache = ReadFile(m_cacheFile);
        length = m_cache.size();
        return length ? m_cache.data() : nullptr;
    }

    void writeCalibrationCache(const void* data, std::size_t length) noexcept override
    {
        WriteFile(m_cacheFile, data, length);
    }

private:
    int m_batchSize;
    std::string m_cacheFile;
    std::vector<std::string> m_files;
    std::vector<char> m_cache;
    void* m_deviceInput = nullptr;
    std::size_t m_index = 0;
};

// Use it in builder config.
Int8Calibrator calib(8, "resnet50_int8.cache", calibrationImages);
config->setFlag(BuilderFlag::kINT8);
config->setInt8Calibrator(&calib);
캘리브레이션 데이터가 분포를 대표해야 한다 검사 라인의 실제 이미지(양품·불량 비율 포함)를 써야 한다. 합성 데이터나 학습 데이터만 사용하면 양산에서 정확도가 떨어진다. 통상 500~1000장이면 충분하지만, 클래스 불균형이 심하면 더 늘린다.
PTQ로 부족하면 QAT 분류는 PTQ로 보통 0.5% 이내 손실에 그치지만, 검출·세그멘테이션은 손실이 크게 보이기도 한다. 이때는 학습 단계에서 양자화를 시뮬레이션하는 QAT (Quantization Aware Training)로 넘어간다.

엔진 빌드 시간 vs 런타임 속도

TensorRT 빌더는 가능한 모든 커널 후보를 실측해 가장 빠른 것을 고른다. 그래서 빌드는 오래 걸리고, 그 대가로 런타임은 빠르다. ResNet-50 기준 빌드는 수 분, INT8까지 켜면 수십 분까지 간다.

// Trade build time for runtime quality.
config->setBuilderOptimizationLevel(5);   // 0=fast build, 5=best perf (default 3)

// Profile cache speeds up rebuild on the same GPU.
auto cache = std::unique_ptr<ITimingCache>(
    config->createTimingCache(cacheBlob.data(), cacheBlob.size()));
config->setTimingCache(*cache, false);
빌드는 한 번, 추론은 매 프레임 빌드는 CI나 셋업 단계에서 1회만 돌리고, 양산 PC에는 결과 엔진(.plan)만 배포한다. 빌드 시간은 양산 성능에 영향을 주지 않는다.

Plugin — 미지원 연산 처리

대부분의 표준 연산은 TensorRT가 직접 지원하지만, 최신 논문의 커스텀 연산이나 비표준 후처리(예: 특정 NMS 변형)는 미지원일 수 있다. 이때 두 가지 선택지가 있다.

  1. 모델 수정 — 가능하면 동등한 표준 연산 조합으로 그래프를 다시 짠다.
  2. TensorRT Plugin — IPluginV3를 구현해 커스텀 CUDA 커널을 끼워 넣는다.
// Skeleton of a TensorRT plugin (V3 interface, simplified).
class MyOpPlugin : public IPluginV3, public IPluginV3OneCore,
                   public IPluginV3OneBuild, public IPluginV3OneRuntime
{
public:
    // Run the custom CUDA kernel.
    int32_t enqueue(const PluginTensorDesc* inDesc, const PluginTensorDesc* outDesc,
                    const void* const* inputs, void* const* outputs,
                    void* workspace, cudaStream_t stream) noexcept override
    {
        MyCustomKernelLaunch(
            static_cast<const float*>(inputs[0]),
            static_cast<float*>(outputs[0]),
            inDesc[0].dims.d[0], stream);
        return 0;
    }
    // ... configure / clone / serialize methods omitted for brevity
};
가능하면 plugin은 피한다 plugin은 유지 관리 비용이 크다. TensorRT 메이저 버전이 올라가면 인터페이스가 바뀌어 다시 빌드해야 할 때도 있다. 모델 수정이나 ONNX opset 업그레이드로 해결되는 경우가 더 많다.

trtexec CLI vs C++ API

TensorRT는 빠른 실험과 성능 측정을 위해 trtexec라는 CLI 도구를 함께 제공한다. 모델을 빠르게 평가할 때는 trtexec, 양산 통합에는 C++ API를 쓴다.

# 가장 단순한 빌드 + 벤치마크
trtexec --onnx=resnet50.onnx --saveEngine=resnet50.plan

# FP16 + 동적 shape + 워크스페이스 2GB
trtexec --onnx=resnet50.onnx \
        --saveEngine=resnet50_fp16.plan \
        --fp16 \
        --minShapes=input:1x3x224x224 \
        --optShapes=input:4x3x224x224 \
        --maxShapes=input:8x3x224x224 \
        --memPoolSize=workspace:2048

# INT8 + 캘리브레이션 캐시
trtexec --onnx=resnet50.onnx \
        --int8 --calib=resnet50_int8.cache \
        --saveEngine=resnet50_int8.plan

# 기존 엔진의 추론 속도만 측정
trtexec --loadEngine=resnet50_fp16.plan --iterations=1000 --warmUp=200

DLA (Deep Learning Accelerator)

Jetson AGX Orin, Xavier 등 일부 NVIDIA 임베디드 SoC에는 GPU 외에 DLA라는 고정 기능 추론 가속기가 함께 들어 있다. DLA는 GPU보다 느리지만 전력 효율이 좋고, GPU를 다른 작업에 비워둘 수 있다.

// Route the engine to DLA core 0, fall back to GPU when an op is unsupported.
config->setFlag(BuilderFlag::kFP16);    // DLA requires FP16 or INT8
config->setDefaultDeviceType(DeviceType::kDLA);
config->setDLACore(0);
config->setFlag(BuilderFlag::kGPU_FALLBACK);
DLA는 임베디드 한정 데스크톱·서버 GPU(RTX, A100, H100)에는 DLA가 없다. Jetson 같은 엣지 디바이스에 검사 시스템을 올릴 때 의미가 있다.

산업 비전 적용

검사 시스템에서 TensorRT가 해결하는 문제는 결국 두 가지다. 택트 타임 안에 들어가기와 한 PC에서 여러 모델 동시 추론이다.

택트 타임에 맞추기

예를 들어 200 ms 택트 라인에서 카메라 노출 30 ms, 전처리 10 ms, 후처리 10 ms를 빼면 추론에 쓸 수 있는 시간은 150 ms 정도다. ResNet-50을 PyTorch CPU로 돌리면 150 ms를 훌쩍 넘기지만, TensorRT FP16 + RTX 4070에서는 0.5 ms 미만으로 떨어진다. 즉 모델을 더 키울 여유가 생긴다.

다중 모델 동시 추론

한 검사 셀에서 분류 + 결함 검출 + 세그멘테이션을 동시에 돌려야 할 때, 모델마다 독립 CUDA 스트림으로 묶으면 GPU 자원을 겹쳐 쓸 수 있다.

// Run three engines concurrently on three CUDA streams.
struct Pipeline
{
    TrtInferer classifier;
    TrtInferer detector;
    TrtInferer segmenter;
    cudaStream_t s1, s2, s3;
};

ErrorCode RunFrame(Pipeline& pipe, const Image& image)
{
    if (image.IsEmpty()) return ErrorCode::InvalidArgument;

    UploadToDeviceAsync(image, pipe.s1);
    pipe.classifier.InferAsync(pipe.s1);   // class label
    pipe.detector.InferAsync(pipe.s2);     // defect boxes
    pipe.segmenter.InferAsync(pipe.s3);    // mask

    cudaStreamSynchronize(pipe.s1);
    cudaStreamSynchronize(pipe.s2);
    cudaStreamSynchronize(pipe.s3);
    return ErrorCode::Success;
}
CUDA Graph로 한 단계 더 같은 입력 shape, 같은 시퀀스로 매 프레임 반복된다면 cudaGraph로 묶어 런치 오버헤드를 줄일 수 있다. 짧은 추론(< 1 ms)에서 효과가 크다.

흔한 함정

다른 GPU·다른 TensorRT 버전으로 빌드한 엔진은 호환되지 않는다 엔진(.plan)은 GPU 컴퓨트 capability + TensorRT 버전 + cuDNN/cuBLAS 버전에 묶인다. RTX 3060에서 빌드한 엔진은 RTX 4070에서 로드되지 않거나, 되더라도 최적화가 어긋난다. 양산 PC에서 직접 빌드하거나, 동일한 SKU별로 따로 빌드한다.
INT8 캘리브레이션 데이터가 너무 적으면 정확도가 무너진다 50장으로 캘리브레이션 하고 양산에서 검출 정확도가 떨어지는 사례가 흔하다. 최소 수백 장, 가능하면 라인의 하루치 샘플을 쓴다.
벤치마크에 빌드 시간을 포함하지 않는다 "TensorRT 추론에 30초 걸린다"고 보고하는 측정의 대부분은 엔진 빌드/로드를 포함한 것이다. 양산 추론 측정은 반드시 워밍업 후 enqueueV3만 잰다.
지원되지 않는 ONNX opset / 연산자 최신 PyTorch가 내보낸 opset이 설치된 TensorRT보다 높으면 파싱이 실패한다. torch.onnx.export(..., opset_version=17)처럼 명시적으로 낮추거나 TensorRT를 업그레이드한다. 파서 로그에 "Unsupported operator"가 찍히면 해당 op만 따로 처리해야 한다.
PCIe 복사가 추론보다 오래 걸리는 경우 4K 이미지를 매 프레임 호스트→디바이스로 복사하면 추론보다 복사가 더 걸린다. 카메라 SDK가 GPUDirect나 핀드 메모리를 지원하는지 확인하고, 가능하면 GPU에 직접 DMA로 받는 경로를 만든다.
