멈춘 것처럼 보이는 프로그램의 원인 찾기 - cdb 콜스택

2026-10-21 약 10분 분량 트러블슈팅
이 글에서 다루는 내용
  • 화면 문구 대신 지금 실행 중인 코드를 보는 순서: 바쁜 프로세스, 바쁜 스레드, 콜스택, 숫자 확인

5편에서는 멈춘 프로그램의 덤프를 떠서 나중에 분석하는 방법을 다룸. 이번 편은 덤프 없이, 지금 돌고 있는 프로그램에 cdb를 잠깐 붙여 콜스택만 읽고 떨어지는 방법을 다룸. 프로그램을 끄지 않아도 되므로 "멈춘 건지 느린 건지" 확인할 때 부담이 적음.

문제 상황 - 같은 문구에서 멈춘 제거 창

증상
  • 사내 프로그램의 설치 패키지(InstallShield + MSI)를 제거함
  • 제거 창이 Removing shortcuts 문구에서 몇 분째 움직이지 않음
  • 어떤 PC에서는 금방 끝나고, 어떤 PC에서는 오래 걸림

바로가기 몇 개 지우는 데 몇 분이 걸릴 리는 없음. 그래서 "바로가기 삭제가 막혔다"고 생각하기 쉬움. 하지만 화면 문구는 원인이 아님. 화면은 마지막으로 갱신된 상태만 보여 줌. 원인을 알려면 프로그램이 지금 실제로 실행 중인 코드를 봐야 함.

전체 순서 한눈에 보기

순서는 항상 같음. 누가 바쁜지 찾고, 그중 바쁜 스레드를 찾고, 그 스레드의 콜스택을 보고, 스택에서 나온 가설을 숫자로 확인함. 이번 사례에서 각 단계의 결과는 아래와 같음.

단계한 일본 결과
1관련 프로세스 목록setup.exe 2개, ISBEW64.exe, msiexec.exe /V
25초 간격으로 CPU 두 번 측정setup, ISBEW64는 CPU 증가 0. msiexec /V만 5초에 CPU 4.7초 증가
3msiexec 스레드별 CPU스레드 하나(36736)가 CPU 366초, 나머지는 거의 0
4cdb로 그 스레드 콜스택Msi!RemoveShortcut → Shell 고정 해제 → 환경 변수 확장 → 파일 속성 조회
5가설 확인시스템 환경 변수 88개, PATH 59항목, 작업 표시줄 고정 17개
6진행 여부 확인시작 메뉴 바로가기 4개 → 3개로 줄어듦. 멈춘 게 아니라 느린 것

단계별 명령과 뜻

1단계 - 관련 프로세스 찾기

Get-CimInstance Win32_Process |
  Where-Object { $_.Name -match 'msiexec|setup|ISBEW' } |
  Select-Object ProcessId, ParentProcessId, Name, CreationDate, CommandLine
  • ParentProcessId로 부모와 자식 관계를 이어 봄. 누가 누구를 실행했는지 보임
  • CreationDate로 이번 작업 때 생긴 프로세스인지 구분함
  • 설치 프로그램은 화면을 띄우는 프로세스(setup.exe)와 실제 일을 하는 프로세스가 다른 경우가 많음. MSI는 실제 작업을 Windows Installer 서비스(msiexec.exe /V, SYSTEM 계정)가 함

2단계 - 바쁜 프로세스 찾기

CPU 값은 누적 값이라 한 번만 보면 알 수 없음. 간격을 두고 두 번 보고 차이를 봄.

$ids = 35280,19904,24088,28604
$a = Get-Process -Id $ids | Select-Object Id, Name, CPU
Start-Sleep 5
$b = Get-Process -Id $ids | Select-Object Id, Name, CPU
$a; $b
차이뜻
CPU가 계속 늘어남무언가를 계산하거나 반복 중. 콜스택을 보면 그 반복이 보임
CPU가 그대로무언가를 기다리는 중. 콜스택 맨 위가 WaitFor...로 나옴. 무엇을 기다리는지가 원인
파일 수나 크기가 변함실제로 진행 중. 느릴 뿐 멈춘 것은 아님

3단계 - 바쁜 스레드 찾기

프로세스 하나에 스레드가 여러 개이므로, 바쁜 스레드 하나를 골라야 스택이 의미 있음.

(Get-Process -Id 28604).Threads |
  Sort-Object TotalProcessorTime -Descending |
  Select-Object -First 3 Id, ThreadState, WaitReason,
    @{n='CPU'; e={$_.TotalProcessorTime.TotalSeconds}}
  • 여기서 나온 Id(스레드 ID, 10진수)를 4단계에서 사용함
  • ThreadState = Running이고 CPU가 혼자 큰 스레드가 범인 후보

4단계 - cdb로 콜스택 보기

cdb는 WinDbg의 콘솔판임. Windows SDK의 Debugging Tools에 들어 있음.

  • 위치: C:\Program Files (x86)\Windows Kits\10\Debuggers\x64\cdb.exe
  • 관리자 권한 PowerShell 필요. 서비스 프로세스(msiexec, SYSTEM 계정)에 붙으려면 꼭 필요함
  • 관리자 확인: ([Security.Principal.WindowsPrincipal][Security.Principal.WindowsIdentity]::GetCurrent()).IsInRole('Administrators')
$cdb = "C:\Program Files (x86)\Windows Kits\10\Debuggers\x64\cdb.exe"
$env:_NT_SYMBOL_PATH = "srv*C:\Symbols*https://msdl.microsoft.com/download/symbols"
& $cdb -pv -p 28604 -c ".symfix+;.reload;~~[0n36736]s;kn 40;qd" > stack.txt
부분뜻
-pv비침입(noninvasive) 연결. 디버거로 등록하지 않고 메모리만 읽음. 떨어질 때 대상 프로세스가 그대로 계속 실행됨
-p 28604붙을 프로세스 ID
-c "..."붙자마자 실행할 명령들. ;로 이어 적음
.symfix+, _NT_SYMBOL_PATH마이크로소프트 심볼 서버를 사용함. 심볼이 있어야 주소 대신 Msi!RemoveShortcut 같은 함수 이름이 나옴. 처음에는 내려받느라 시간이 걸림
.reload심볼을 다시 불러옴
~~[0n36736]s스레드 ID 36736으로 전환. 0n은 10진수라는 표시 (cdb 기본은 16진수)
kn 40콜스택을 번호를 붙여 40줄까지 출력
qd떨어지고(detach) 끝냄. 침입 모드에서 q로 끝내면 대상 프로세스도 같이 종료되므로 습관적으로 qd 사용

다른 경우의 명령

  • 모든 스레드 스택: ~*kn 30
  • 내 프로그램이라 PDB가 있으면 심볼 경로 앞에 PDB 폴더를 추가함: C:\Build\MyApp\x64\Release;srv*C:\Symbols*https://msdl.microsoft.com/download/symbols

콜스택 읽는 법

콜스택은 아래에서 위로 읽음. 맨 아래가 스레드의 시작점이고, 위로 갈수록 더 안쪽에서 불린 함수임. 맨 위가 지금 실행 중인 곳. 이번 스택을 줄여서 보면 아래와 같음 (앞의 번호는 kn 출력의 줄 번호).

30 ntdll!RtlUserThreadStart                       스레드 시작
2e Msi!MsiUIMessageContext::MainEngineThread      Windows Installer 엔진
26 Msi!InstallFinalize                            예약된 작업 실행 구간
21 Msi!CMsiOpExecute::ProcessShortcut             바로가기 처리
20 Msi!CMsiServices::RemoveShortcut               바로가기 하나 제거
1f SHELL32!CStartMenuPin::RemoveFromList          시작 메뉴 고정 목록에서 빼기
1e SHELL32!CStartMenuPin::_RemoveFromTaskbarList  작업 표시줄 고정 목록에서 빼기
1b SHELL32!CPinList::Load                         고정 목록 전체를 다시 읽음
18 SHELL32!CPinList::FindPidl                     고정 항목 하나의 경로 해석
0d windows_storage!SHGetKnownFolderPath_Internal  "문서", "프로그램 파일" 같은 폴더 경로 구하기
06 USERENV!ExpandEnvironmentStringsForUserW       %변수% 확장
04 profapi!_SetMachineEnvironment                 시스템 환경 변수를 레지스트리에서 다시 읽음
02 KERNELBASE!GetShortPathNameW                   경로를 8.3 짧은 이름으로 변환
00 ntdll!NtQueryAttributesFile                    파일 속성 조회 (지금 여기)

모듈!함수 형식

  • 각 줄은 모듈!함수 형식. 모듈 이름만 봐도 어느 영역인지 알 수 있음
  • Msi: Windows Installer, SHELL32 및 windows_storage: 탐색기 셸, ntdll 및 KERNELBASE: OS 기본 함수
  • 내 코드라면 MyApp!..., MyLib!...처럼 내 exe와 dll 이름으로 나옴

내 코드와 OS 코드의 경계

  • 콜스택을 읽을 때 핵심은 경계를 찾는 것임. "어떤 작업 중인지"와 "누구에게 맡겼는지"가 만나는 줄
  • 이번에는 Msi!RemoveShortcut(바로가기 제거 중)과 SHELL32!CStartMenuPin(셸에 고정 해제를 맡김)이 경계였음
  • 맨 위의 OS 함수(NtQueryAttributesFile)는 증상일 뿐임. "왜 이렇게 많이 부르나"는 그 아래쪽 호출 구조에서 나옴

원인 - 바로가기마다 반복되는 경로 조회

원인
  • Windows Installer는 바로가기를 하나 지울 때마다 Shell에 "시작 메뉴와 작업 표시줄 고정 해제"를 요청함
  • Shell은 고정 목록 전체를 다시 읽고, 고정 항목마다 경로를 다시 해석함
  • 경로를 해석할 때마다 시스템 환경 변수를 레지스트리에서 다시 읽고, 경로를 하나씩 조회함
바로가기 1개 제거
  × 고정 목록 다시 읽기 (작업 표시줄 고정 17개)
    × 환경 변수 다시 읽기 (시스템 변수 88개)
      × 경로마다 파일 조회 (PATH 59항목)
→ 곱으로 늘어난 조회 횟수가 몇 분이 됨

SDK와 개발 도구가 많이 깔려 환경 변수 경로가 많은 개발 PC일수록 느림. 같은 패키지라도 PC마다 걸리는 시간이 다르므로 "가끔" 느린 것처럼 보임.

가설을 숫자로 확인

스택에서 "환경 변수 경로를 반복해서 조회한다"는 가설이 나오면, 실제로 그 양이 많은지 셈.

$k = Get-Item 'HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\Environment'
$path = $k.GetValue('Path', '', 'DoNotExpandEnvironmentNames')
"변수 수: $($k.ValueCount), PATH 항목: $(($path -split ';' | ? { $_ }).Count)"
(Get-ChildItem "$env:APPDATA\Microsoft\Internet Explorer\Quick Launch\User Pinned\TaskBar" -Filter *.lnk).Count
  • 항목 하나씩 조회 시간도 측정해 봄 (Measure-Command { Test-Path ... }). 네트워크 경로가 있으면 하나에 몇 초씩 걸려서 그것이 곧 원인이 됨
  • 이번에는 전부 빠른 로컬 경로였고, 원인은 개수와 반복 횟수였음
  • 마지막으로 진행되는지 확인함: 대상 파일 수가 줄어드는지, 스레드 CPU가 계속 느는지. 이번에는 시작 메뉴 바로가기가 4개에서 3개로 줄어듦. 멈춘 것이 아니라 느린 것

상황별 판단 표

스택 맨 위 쪽 모습뜻다음에 볼 것
여러 번 찍어도 같은 함수가 계속 나옴, CPU 증가반복 작업 또는 무한 루프그 아래 호출 구조에서 반복 횟수를 정하는 것
WaitForSingleObject, WaitForMultipleObjects다른 스레드나 프로세스를 기다림기다리는 대상. 자식 프로세스, 다른 스레드의 스택(~*kn)
EnterCriticalSection, RtlpWaitOnCriticalSection잠금 대기. 교착(deadlock) 후보그 잠금을 쥔 스레드: !cs -l, !locks (5편)
recv, WSARecv, NtDeviceIoControlFile네트워크나 드라이버 응답 대기장비 연결 상태, 드라이버
NtQueryAttributesFile, NtCreateFile 반복파일 조회가 많음조회 대상 개수, 네트워크 경로, 백신 및 문서 보안 프로그램

주의점

비침입 모드도 붙어 있는 동안은 잠깐 멈춤 -pv로 붙어도 붙어 있는 짧은 동안은 대상의 스레드가 멈춤. 네트워크로 장비와 통신하는 프로그램은 오래 붙어 있으면 연결 유지 신호가 끊겨 장비 연결이 끊길 수 있음. 스택만 읽고 바로 qd로 떨어짐.
침입 모드에서 q는 대상 종료 -pv 없이 붙는 침입 모드는 브레이크포인트를 걸 수 있지만, 대상이 멈춘 채로 있고 q로 끝내면 대상이 종료됨. 원인을 찾는 목적이면 -pv로 충분함.
두세 번 찍어서 확인 같은 스택이 우연히 한 번 잡힌 것일 수 있음. 몇 초 간격으로 두세 번 찍어서 같은 자리가 계속 나오는지 봄. 계속 같은 곳이면 그 자리가 시간을 먹는 곳임.

연습 - 메모장 콜스택

  1. 메모장을 열고 PowerShell로 PID 찾기: Get-Process notepad
  2. cdb -pv -p <PID> -c ".symfix+;.reload;~*kn 20;qd" 실행
  3. 메인 스레드 스택에서 user32!GetMessageW나 win32u!NtUserGetMessage 찾기. "입력 메시지를 기다리는 중"이라는 뜻
  4. 메모장이 그대로 살아 있는지 확인 (비침입이라 영향 없음)

이번 편 요약

화면 문구 대신 실행 중인 코드를 봄. CPU 차이로 바쁜 프로세스와 스레드를 고르고, cdb -pv로 콜스택만 읽고 qd로 떨어짐. 스택에서 나온 가설은 개수와 시간을 세어 확인함.
