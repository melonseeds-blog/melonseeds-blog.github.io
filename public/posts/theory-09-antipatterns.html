안티패턴이란 무엇인가

안티패턴(anti-pattern)은 자주 쓰이지만 결과가 나쁜 패턴이다. 디자인 패턴이 "반복되는 문제에 대한 검증된 해법"이라면, 안티패턴은 그 거울상이다 — 반복적으로 등장하고, 처음에는 그럴듯해 보이며, 시간이 지나면 반드시 대가를 치르게 하는 구조다.

이 용어는 Andrew Koenig가 1995년에 처음 썼고, 1998년 책 AntiPatterns(Brown 외)가 개념을 체계화했다. 핵심 정의는 두 조건이다 — 첫째, 흔히 채택되는 해법일 것. 둘째, 그 해법이 이득보다 손해를 더 많이 낼 것. 단순히 나쁜 코드가 아니라, "나쁜 줄 모르고 반복해서 쓰게 되는" 코드라는 점이 핵심이다.

좋은 코드를 알려면 나쁜 코드도 알아야 한다. 패턴만 외우면 "무엇을 해야 하는가"는 알지만 "무엇을 피해야 하는가"는 모른다. 안티패턴을 이름으로 인식할 수 있으면, 코드 리뷰에서 "이건 God Object로 가고 있다"는 한마디로 문제를 짚어낼 수 있다. 안티패턴은 경고 어휘다.

안티패턴 기술서는 "탈출법"을 함께 적는다 제대로 된 안티패턴 정의는 증상과 원인만 적지 않는다. 반드시 리팩토링된 해법(refactored solution) — 즉 거기서 빠져나오는 길을 함께 제시한다. 안티패턴을 안다는 것은 "이게 나쁘다"를 아는 것이 아니라 "여기서 어디로 가야 하는가"를 아는 것이다.

안티패턴의 분류

안티패턴은 크게 두 갈래로 나눌 수 있다. 구조에서 오는 것 — 클래스와 코드의 배치가 잘못된 경우. 그리고 사고방식에서 오는 것 — 판단과 습관이 잘못된 경우. 아래 다이어그램이 이 글에서 다루는 안티패턴의 지도다.

안티패턴은 코드의 배치가 잘못된 경우와, 그 배치를 만든 판단이 잘못된 경우로 나뉜다

God Object — 모든 것을 떠안은 클래스

God Object(또는 God Class)는 너무 많은 책임을 가진 거대 클래스다. 이름에 Manager, Handler, System, Controller가 붙어 있고, 메서드가 수십 개에 멤버 변수가 수십 개이며, 프로젝트의 거의 모든 코드가 이 클래스를 거쳐 간다. "이 클래스가 모든 걸 한다"가 God Object의 증상이다.

God Object는 단일 책임 원칙(SRP)의 정면 위반이다. 클래스가 바뀔 이유가 하나여야 하는데, God Object는 바뀔 이유가 수십 가지다. 카메라 설정이 바뀌어도, 파일 포맷이 바뀌어도, UI 로직이 바뀌어도 같은 클래스를 건드리게 된다. 그 결과 누가 무엇을 고치든 충돌하고, 한 곳을 고치면 무관한 다른 기능이 깨진다.

안티패턴 — 모든 책임을 떠안은 InspectionManager

// 안티패턴 — 검사, 카메라, 파일, 로깅, 통계를 한 클래스가 모두 한다
class InspectionManager
{
public:
    // 카메라 책임
    ErrorCode ConnectCamera(const std::string& ip);
    ErrorCode SetExposure(double microseconds);
    ErrorCode GrabImage(Image& outImage);

    // 이미지 처리 책임
    ErrorCode ApplyBlur(Image& image, int kernelSize);
    ErrorCode DetectEdges(Image& image);
    ErrorCode FindDefects(const Image& image, std::vector<Defect>& outDefects);

    // 파일 입출력 책임
    ErrorCode SaveImageToFile(const Image& image, const std::string& path);
    ErrorCode LoadConfig(const std::string& path);
    ErrorCode ExportReport(const std::string& path);

    // 통계 책임
    double GetPassRate() const;
    void ResetStatistics();

    // 로깅 책임
    void WriteLog(const std::string& message);

private:
    // 멤버가 30개 넘게 이어진다...
    CameraHandle m_camera;
    double m_exposureUs;
    std::vector<Defect> m_lastDefects;
    int m_totalCount;
    int m_passCount;
    std::ofstream m_logFile;
    Config m_config;
    // ...
};
God Object는 변경을 마비시킨다 위 InspectionManager는 노출 시간 단위를 바꾸려 해도, 리포트 포맷을 바꾸려 해도 같은 파일을 연다. 두 사람이 동시에 작업하면 거의 매번 충돌한다. 단위 테스트도 불가능에 가깝다 — 통계 로직 하나를 테스트하려면 카메라까지 전부 초기화해야 한다.

탈출 — 책임을 분리한다

탈출법은 단순하다. 책임을 기준으로 클래스를 쪼갠다. 각 클래스는 바뀔 이유가 하나가 되도록 한다. 그리고 상위 클래스는 그 부품들을 조율만 하고, 직접 일하지 않는다.

God Object를 책임 단위로 쪼개고, 상위 클래스는 부품을 조율(orchestrate)하는 역할만 맡는다
// 탈출 — 책임별로 분리된 클래스들. 각자 바뀔 이유가 하나뿐이다
class CameraController   // 카메라만 담당
{
public:
    ErrorCode Connect(const std::string& ip);
    ErrorCode SetExposure(double microseconds);
    ErrorCode Grab(Image& outImage);
private:
    CameraHandle m_camera;
    double m_exposureUs;
};

class DefectDetector     // 결함 검출만 담당
{
public:
    ErrorCode Detect(const Image& image, std::vector<Defect>& outDefects);
};

class InspectionStats    // 통계만 담당
{
public:
    void Record(bool passed);
    double GetPassRate() const;
private:
    int m_totalCount = 0;
    int m_passCount = 0;
};

// 상위 클래스는 부품을 조율만 한다 — 직접 일하지 않는다
class InspectionRunner
{
public:
    ErrorCode RunOnce()
    {
        Image frame;
        ErrorCode ec = m_camera.Grab(frame);
        if (ec != ErrorCode::Ok)
        {
            return ec;
        }

        std::vector<Defect> defects;
        ec = m_detector.Detect(frame, defects);
        if (ec != ErrorCode::Ok)
        {
            return ec;
        }

        m_stats.Record(defects.empty());
        return ErrorCode::Ok;
    }

private:
    CameraController m_camera;
    DefectDetector m_detector;
    InspectionStats m_stats;
};

이제 노출 시간 단위를 바꾸면 CameraController만 열면 된다. 통계 로직은 InspectionStats만 따로 테스트할 수 있다. 각 클래스는 작고, 이름이 곧 책임이며, 변경의 영향이 그 클래스 안에 갇힌다.

Spaghetti Code — 추적 불가능한 제어 흐름

Spaghetti Code는 제어 흐름이 국수 가닥처럼 얽혀 추적이 불가능한 코드다. 깊은 중첩, 여기저기 흩어진 goto나 조기 분기, 전역 상태에 대한 산발적인 읽기·쓰기가 특징이다. 코드를 위에서 아래로 읽어서는 무슨 일이 일어나는지 알 수 없고, 한 줄을 고치려면 머릿속에 흐름 전체를 담아야 한다.

안티패턴 — 깊은 중첩과 얽힌 흐름

// 안티패턴 — 6단 중첩. 정상 경로가 어디인지 보이지 않는다
ErrorCode ProcessFrame(Image& image)
{
    if (!image.IsEmpty())
    {
        if (image.GetWidth() > 0)
        {
            if (image.GetHeight() > 0)
            {
                if (g_isCalibrated)   // 전역 상태에 의존
                {
                    if (PreparePipeline() == ErrorCode::Ok)
                    {
                        if (RunDetection(image) == ErrorCode::Ok)
                        {
                            g_lastResultValid = true;   // 전역 상태를 또 건드림
                            return ErrorCode::Ok;
                        }
                        else
                        {
                            return ErrorCode::DetectionFailed;
                        }
                    }
                    else
                    {
                        return ErrorCode::PipelineError;
                    }
                }
                else
                {
                    return ErrorCode::NotCalibrated;
                }
            }
        }
    }
    return ErrorCode::InvalidImage;
}

탈출 — early return·함수 추출·구조화

탈출법은 세 가지다. early return으로 실패 조건을 먼저 걸러내 중첩을 평탄화한다. 함수 추출(extract function)로 의미 있는 단계에 이름을 붙인다. 전역 상태 대신 인자와 반환값으로 데이터를 명시적으로 흘려보낸다.

// 탈출 — early return으로 평탄화. 정상 경로가 한눈에 보인다
ErrorCode ProcessFrame(Image& image, const CalibrationData& calibration)
{
    // 실패 조건을 먼저 걸러낸다 (guard clause)
    if (image.IsEmpty() || image.GetWidth() <= 0 || image.GetHeight() <= 0)
    {
        return ErrorCode::InvalidImage;
    }
    if (!calibration.IsValid())
    {
        return ErrorCode::NotCalibrated;
    }

    // 여기서부터는 정상 경로만 남는다
    ErrorCode ec = PreparePipeline();
    if (ec != ErrorCode::Ok)
    {
        return ErrorCode::PipelineError;
    }

    ec = RunDetection(image);
    if (ec != ErrorCode::Ok)
    {
        return ErrorCode::DetectionFailed;
    }

    return ErrorCode::Ok;
}

중첩이 6단에서 0단으로 줄었다. 전역 변수 g_isCalibrated는 calibration 인자로 바뀌어, 함수가 무엇에 의존하는지 시그니처만 봐도 드러난다. g_lastResultValid 같은 숨은 부수효과도 사라졌다 — 결과는 반환값으로만 전달된다.

전역 상태는 스파게티의 주재료다 전역 변수는 "누가 언제 이 값을 바꾸는가"를 코드 어디에서도 보장할 수 없게 만든다. 함수 시그니처에 드러나지 않는 입력·출력은 전부 숨은 의존성이며, 스파게티 코드의 가닥이 된다. 데이터는 인자로 받고 반환값으로 내보낸다 — 이 원칙 하나가 추적 가능성을 크게 끌어올린다.

Copy-Paste Programming — 복붙이 만드는 중복

Copy-Paste Programming은 비슷한 코드가 필요할 때 기존 코드를 복사해 조금 고쳐 쓰는 습관이다. 당장은 빠르다. 문제는 나중이다. 복사된 코드 중 한 곳에서 버그를 발견하고 고쳤을 때, 나머지 복사본들을 모두 고쳤는지 아무도 보장할 수 없다. 하나를 깜빡하면 같은 버그가 코드베이스에 계속 살아남는다.

이것은 DRY 원칙(Don't Repeat Yourself)의 위반이다. DRY의 핵심은 "지식은 코드베이스에 단 한 번만 표현되어야 한다"는 것이다. 같은 로직이 다섯 군데에 복사되어 있다면, 그 지식은 다섯 번 표현된 것이고, 변경은 다섯 배로 위험해진다.

안티패턴 — 복사된 검증 로직

// 안티패턴 — 같은 ROI 검증 로직이 함수마다 복사되어 있다
ErrorCode MeasureWidth(const Image& image, const Rect& roi, double& outWidth)
{
    if (roi.x < 0 || roi.y < 0)                           { return ErrorCode::InvalidRoi; }
    if (roi.x + roi.width > image.GetWidth())             { return ErrorCode::InvalidRoi; }
    if (roi.y + roi.height > image.GetHeight())           { return ErrorCode::InvalidRoi; }
    // 측정 로직...
    return ErrorCode::Ok;
}

ErrorCode MeasureHeight(const Image& image, const Rect& roi, double& outHeight)
{
    if (roi.x < 0 || roi.y < 0)                           { return ErrorCode::InvalidRoi; }
    if (roi.x + roi.width > image.GetWidth())             { return ErrorCode::InvalidRoi; }
    if (roi.y + roi.height > image.GetHeight())           { return ErrorCode::InvalidRoi; }
    // 측정 로직...
    return ErrorCode::Ok;
}
// MeasureAngle, MeasureArea... 검증 코드가 계속 복사된다
// roi.width < 0 검사가 빠진 버그를 발견해도, 네 군데를 다 고쳐야 한다

탈출 — 공통을 추출한다

// 탈출 — 검증 지식을 한 곳에 모은다. 고칠 곳도 한 곳뿐이다
ErrorCode ValidateRoi(const Image& image, const Rect& roi)
{
    if (roi.x < 0 || roi.y < 0 || roi.width < 0 || roi.height < 0)
    {
        return ErrorCode::InvalidRoi;
    }
    if (roi.x + roi.width > image.GetWidth() ||
        roi.y + roi.height > image.GetHeight())
    {
        return ErrorCode::InvalidRoi;
    }
    return ErrorCode::Ok;
}

ErrorCode MeasureWidth(const Image& image, const Rect& roi, double& outWidth)
{
    ErrorCode ec = ValidateRoi(image, roi);   // 공통 로직에 위임
    if (ec != ErrorCode::Ok)
    {
        return ec;
    }
    // 측정 로직...
    return ErrorCode::Ok;
}
"세 번째 복사" 규칙 한 번 쓴 코드를 두 번째로 복사할 때는 "정말 같은 지식인가, 우연히 비슷할 뿐인가"를 판단하기 어렵다. 흔히 쓰는 경험칙은 세 번째로 같은 코드를 복사하려는 순간 추출하라는 것이다. 세 번 반복되면 그것은 우연이 아니라 패턴이며, 추출할 가치가 분명하다. 단, 겉모습만 비슷하고 변경 이유가 다른 코드를 억지로 합치는 것은 또 다른 함정이라는 점도 기억한다.

Magic Number / Magic String

Magic Number는 의미를 알 수 없는 숫자 리터럴이 코드 곳곳에 직접 박혀 있는 것이다. 문자열이면 Magic String이다. if (mode == 3)에서 3이 무엇을 뜻하는지, buffer[1024]의 1024가 왜 그 값인지, 코드만 봐서는 알 수 없다. 같은 값이 여러 곳에 흩뿌려져 있으면, 그 값을 바꿔야 할 때 어디를 고쳐야 하는지조차 알기 어렵다.

안티패턴 — 흩뿌려진 리터럴

// 안티패턴 — 3, 255, 0.85가 무엇을 뜻하는지 알 수 없다
ErrorCode InspectSurface(const Image& image, InspectionResult& outResult)
{
    if (image.GetChannels() == 3)            // 3 = ? (RGB라는 뜻)
    {
        ConvertToGray(image);
    }

    Image binary = Threshold(image, 255 * 0.6);   // 255? 0.6? 왜?

    double defectRatio = CountDefectPixels(binary) / (double)image.GetPixelCount();
    if (defectRatio > 0.85)                  // 0.85 = ? (불량 판정 임계값)
    {
        outResult.status = 2;                // 2 = ? (FAIL이라는 뜻)
        return ErrorCode::Ok;
    }
    outResult.status = 1;                    // 1 = ? (PASS)
    return ErrorCode::Ok;
}

탈출 — 명명된 상수와 enum

탈출법은 모든 의미 있는 리터럴에 이름을 주는 것이다. 단순 값은 k 접두사 상수로, 한정된 선택지는 enum으로 표현한다. 이름이 곧 설명이 되어, 주석 없이도 코드가 읽힌다.

// 탈출 — 이름이 의미를 설명한다. 값 변경도 한 곳에서 끝난다
namespace
{
    constexpr int kRgbChannelCount = 3;
    constexpr int kMaxPixelValue = 255;
    constexpr double kThresholdRatio = 0.6;
    constexpr double kDefectRejectRatio = 0.85;
}

// 한정된 상태는 enum으로 — 잘못된 값 자체가 불가능해진다
enum class InspectionStatus
{
    Pass,
    Fail
};

ErrorCode InspectSurface(const Image& image, InspectionResult& outResult)
{
    if (image.GetChannels() == kRgbChannelCount)
    {
        ConvertToGray(image);
    }

    Image binary = Threshold(image, kMaxPixelValue * kThresholdRatio);

    double defectRatio = CountDefectPixels(binary) / (double)image.GetPixelCount();
    outResult.status = (defectRatio > kDefectRejectRatio)
                       ? InspectionStatus::Fail
                       : InspectionStatus::Pass;
    return ErrorCode::Ok;
}

Premature Optimization — 조급한 최적화

Premature Optimization은 측정 없이, 추측만으로 성능 최적화를 하는 것이다. Donald Knuth의 유명한 말 — "조급한 최적화는 모든 악의 근원이다(premature optimization is the root of all evil)" — 이 가리키는 바가 이것이다. 정작 느린 곳은 따로 있는데, "여기가 느릴 것 같다"는 직감만으로 코드를 비틀어 가독성을 희생한다.

안티패턴 — 측정 없이 비튼 코드

// 안티패턴 — "함수 호출이 느릴 것 같아서" 직접 인라인하고 비트 연산으로 비틈
double ComputeAverageBrightness(const Image& image)
{
    unsigned char* p = image.RawData();
    int n = image.GetWidth() * image.GetHeight();
    long long sum = 0;
    int i = 0;
    // 루프 언롤링을 손으로... 정작 병목은 여기가 아니다
    for (; i + 4 <= n; i += 4)
    {
        sum += p[i] + p[i + 1] + p[i + 2] + p[i + 3];
    }
    for (; i < n; ++i)
    {
        sum += p[i];
    }
    return (sum >> 0) / (double)n;   // 가독성만 잃고 이득은 측정된 적 없다
}

탈출 — 먼저 명확하게, 측정 후 최적화

// 탈출 — 먼저 명확하게 쓴다. 컴파일러 최적화가 대부분 알아서 처리한다
double ComputeAverageBrightness(const Image& image)
{
    const auto& pixels = image.Pixels();
    if (pixels.empty())
    {
        return 0.0;
    }
    long long sum = std::accumulate(pixels.begin(), pixels.end(), 0LL);
    return static_cast<double>(sum) / pixels.size();
}

// 최적화는 측정이 "여기가 병목"이라고 말한 다음에 한다.
// 프로파일러를 돌리고, 핫스팟을 찾고, 그 지점만 고치고, 다시 측정한다.
"측정 없는 최적화"와 "최적화 전면 금지"는 다르다 Knuth의 말은 최적화를 하지 말라는 뜻이 아니다. 같은 문장의 뒷부분에서 그는 "결정적인 3%는 놓치지 말아야 한다"고 덧붙인다. 핵심은 순서다 — 먼저 명확하게 작성하고, 프로파일러로 병목을 찾고, 그 3%에 노력을 집중한다. 추측으로 비튼 나머지 97%는 가독성만 잃을 뿐이다.

Golden Hammer — 황금 망치

Golden Hammer는 "망치를 든 사람에게는 모든 것이 못으로 보인다"는 속담에서 온 이름이다. 익숙한 도구·언어·패턴·라이브러리를 모든 문제에 무리하게 적용하는 안티패턴이다. 정규표현식에 익숙한 사람이 모든 파싱을 정규식으로, 상속에 익숙한 사람이 모든 재사용을 상속으로, 특정 프레임워크에 익숙한 팀이 단순한 스크립트성 작업까지 그 프레임워크로 해결하려 한다.

안티패턴 — 모든 것을 상속으로

// 안티패턴 — "상속이 익숙하니까" 단순 설정값 묶음까지 상속으로 만든다
class BaseConfig
{
protected:
    int m_timeout = 1000;
};

class CameraConfig : public BaseConfig { public: std::string m_ip; };
// CameraConfig is-a BaseConfig? 어색하다. 그냥 timeout을 "가지고 싶었을" 뿐이다

// 더 나아가, 다형성이 전혀 필요 없는데도 깊은 계층을 쌓는다
class HighSpeedCameraConfig : public CameraConfig { public: int m_fps; };
class CooledHighSpeedCameraConfig : public HighSpeedCameraConfig { /* ... */ };
// 4단 상속 계층. 정작 가상 함수는 하나도 없다

탈출 — 문제에 맞는 도구를 고른다

// 탈출 — 단순한 값 묶음은 단순한 구조체로. 필요하면 합성한다
struct TimeoutPolicy
{
    int timeoutMs = 1000;
};

struct CameraConfig
{
    std::string ip;
    int fps = 30;
    TimeoutPolicy timeout;   // 상속이 아니라 합성 — "가진다"가 맞으니까
};

탈출법은 도구를 늘리는 것이 아니라, "이 문제에 이 도구가 정말 맞는가"를 의식적으로 묻는 습관이다. 익숙함은 도구 선택의 근거가 될 수 없다. 상속이 필요한 곳은 진짜 is-a 관계와 다형성이 있는 곳이지, 단지 값을 공유하고 싶은 곳이 아니다.

Boat Anchor · Dead Code · Lava Flow

마지막 세 안티패턴은 공통적으로 "치우지 않은 것"에서 온다.

Boat Anchor / Dead Code — 안 쓰는 코드

Boat Anchor는 "혹시 나중에 쓸지도 모른다"며 남겨둔, 현재는 아무 쓸모 없는 코드·라이브러리·설정이다. Dead Code는 어디서도 호출되지 않는 함수, 도달 불가능한 분기, 항상 거짓인 조건문이다. 둘 다 코드를 읽는 사람에게 "이건 중요한가? 건드려도 되나?"라는 불필요한 질문을 강요한다.

// 안티패턴 — 주석 처리된 옛 구현, 호출되지 않는 함수가 남아 있다
ErrorCode DetectEdges(Image& image)
{
    // 2024년에 쓰던 옛날 방식 - 혹시 몰라서 남겨둠
    // for (int y = 0; y < image.GetHeight(); ++y) {
    //     for (int x = 0; x < image.GetWidth(); ++x) { ... 50줄 ... }
    // }
    return ApplySobel(image);
}

// 아무 데서도 호출되지 않는 함수 - 언제부터 죽었는지 아무도 모른다
ErrorCode LegacyDetectEdges_DoNotUse(Image& image) { /* ... */ }

탈출법은 단순하다 — 삭제한다. 버전 관리 시스템이 있기 때문에 "혹시 나중에"는 핑계가 안 된다. 삭제한 코드는 git 히스토리에 영원히 남아 있고, 정말 필요하면 언제든 되살릴 수 있다. 주석 처리된 코드 블록과 _DoNotUse, _old, _v2 같은 이름은 보이는 즉시 지운다.

Lava Flow — 굳어버린 정체불명의 코드

Lava Flow는 한 단계 더 나쁘다. 누가 왜 작성했는지 아무도 모르고, 무슨 일을 하는지도 불확실하지만, 지우면 무언가 깨질 것 같아 아무도 못 건드리는 코드다. 흘러내린 용암이 식어 굳듯이, 임시방편으로 작성된 코드가 검토되지 않은 채 시스템의 일부로 굳어버린 것이다.

Lava Flow는 "지워라"로 해결되지 않는다 Dead Code는 죽었다는 것이 확실하니 지우면 된다. 하지만 Lava Flow는 살았는지 죽었는지조차 모르는 것이 본질이다. 탈출법은 점진적 이해다 — 테스트로 현재 동작을 고정하고(characterization test), 로그를 붙여 실제로 실행되는지 관찰하고, 작은 부분부터 의미를 파악해 떼어낸다. 한 번에 들어내려다 진짜로 시스템을 망가뜨린다.

안티패턴은 왜 생기는가

안티패턴을 만드는 사람은 대부분 게으르거나 무능한 사람이 아니다. 안티패턴은 합리적으로 보이는 결정들이 쌓여서 생긴다. 원인을 알아야 예방할 수 있다.

원인어떻게 안티패턴이 되는가
시간 압박마감에 쫓기면 "일단 돌아가게" 만든다. 복붙이 가장 빠르고, 새 클래스를 만드는 것보다 기존 클래스에 메서드 하나 더 붙이는 게 빠르다. God Object와 Copy-Paste의 가장 흔한 출발점이다.
경험 부족SRP·DRY 같은 원칙을 모르거나, 알아도 "이 정도는 괜찮겠지"라고 판단한다. 좋은 구조를 본 적이 없으면 나쁜 구조를 나쁘다고 인식하지 못한다.
요구사항 변화처음엔 깔끔했던 클래스에 "이것도 해달라"가 반복적으로 붙는다. 매 변경은 작지만, 누적되면 God Object가 된다. 아무도 의도하지 않았는데 결과적으로 그렇게 된다.
"나중에 고치자"임시방편을 넣으면서 "나중에 정리하겠다"고 다짐하지만, 그 나중은 거의 오지 않는다. TODO 주석은 쌓이고, 임시 코드는 Lava Flow로 굳는다.
측정 대신 추측"이게 느릴 것 같다", "이 도구가 좋을 것 같다"는 추측으로 결정하면 Premature Optimization과 Golden Hammer가 나온다. 데이터 없이 내린 판단은 자주 틀린다.
기술 부채(technical debt)라는 렌즈 많은 안티패턴은 "기술 부채"로 이해할 수 있다. 시간 압박 속에서 의도적으로 빠른 길을 택하는 것 자체가 항상 잘못은 아니다 — 부채를 지는 것처럼. 문제는 부채를 인식하고 갚을 계획이 있는가다. 인식되지 않고 방치된 부채가 안티패턴으로 굳는다.

안티패턴 발견과 대응

안티패턴은 인식되지 않으면 고쳐지지 않는다. 발견하는 세 가지 경로가 있다.

코드 리뷰 — 사람이 본다

코드 리뷰는 안티패턴 발견의 가장 강력한 도구다. 작성자는 자기 코드의 문제를 보지 못하지만, 제3자는 "이 클래스가 너무 많은 일을 한다", "이 숫자가 뭔지 모르겠다"를 금방 짚어낸다. 안티패턴을 이름으로 부를 수 있으면 리뷰가 훨씬 효율적이다 — "여기 God Object 조짐이 있다"는 한마디가 긴 설명을 대신한다.

정적 분석 — 도구가 본다

정적 분석 도구는 사람이 놓치는 것을 기계적으로 잡는다. cppcheck, clang-tidy 같은 도구는 도달 불가능한 코드, 사용되지 않는 변수, 과도하게 긴 함수, 높은 순환 복잡도(cyclomatic complexity)를 자동으로 경고한다. CI 파이프라인에 정적 분석을 넣으면 안티패턴이 커지기 전에 걸린다.

리팩토링 — 발견한 것을 고친다

발견했으면 고쳐야 한다. 고치는 체계적인 기법이 리팩토링이다 — 동작을 바꾸지 않으면서 구조를 개선하는 작업. Extract Function, Extract Class, Replace Magic Number with Constant 같은 기법은 이 글에서 본 탈출법들에 그대로 대응한다. 리팩토링은 별도의 글(15편)에서 본격적으로 다룬다.

한 번에 다 고치려 하지 말 것 안티패턴투성이 코드를 보면 전부 갈아엎고 싶어진다. 하지만 대규모 재작성(big rewrite)은 그 자체가 또 하나의 안티패턴이다 — 동작하던 것을 멈추고, 새 버그를 잔뜩 만들고, 일정이 무한정 늘어진다. 안전한 길은 점진적 개선이다. 테스트로 현재 동작을 고정한 뒤, 한 번에 안티패턴 하나씩, 작은 단위로 고친다. 매 단계마다 코드는 여전히 동작해야 한다.

산업 SW 관점

산업용 이미징·검사 소프트웨어는 특정 안티패턴에 특히 취약하다. 도메인의 성격 때문이다.

검사 로직은 God Class가 되기 쉽다

검사 소프트웨어는 현장 요구가 끊임없이 추가된다 — "이 제품엔 이 검사도", "이 라인엔 이 예외도", "이 고객은 리포트 포맷이 달라야". 이 요구들이 모두 하나의 InspectionEngine이나 VisionController에 메서드로 쌓이면, 앞에서 본 God Object가 된다. 산업 현장은 변경 요구가 잦은 만큼 God Class로 미끄러질 압력도 크다. 검사 단계(획득·전처리·검출·판정·리포트)를 처음부터 별도 책임으로 나눠두는 것이 거의 필수다.

임계값 하드코딩 — Magic Number의 온상

검사 알고리즘은 본질적으로 수많은 임계값으로 가득하다 — 이진화 threshold, 결함 크기 하한, 밝기 허용 범위, 매칭 점수 컷오프. 이 값들을 코드에 직접 박으면 전형적인 Magic Number 안티패턴이 된다. 게다가 산업 현장에서 이 값들은 제품·라인·조명 조건마다 달라져야 한다. 하드코딩된 임계값은 새 제품이 들어올 때마다 코드를 고치고 재컴파일하게 만든다.

// 안티패턴 — 임계값이 코드에 박혀 있다. 제품이 바뀌면 재컴파일해야 한다
bool IsDefective(const Image& image)
{
    return CountDefectPixels(image) > 150;   // 이 150은 이 제품 전용...
}

// 탈출 — 임계값을 외부 설정으로 빼낸다. 코드 변경 없이 제품별로 조정 가능
struct InspectionRecipe
{
    int defectPixelLimit = 150;
    double brightnessMin = 40.0;
    double brightnessMax = 220.0;
    double matchScoreCutoff = 0.8;
};

bool IsDefective(const Image& image, const InspectionRecipe& recipe)
{
    return CountDefectPixels(image) > recipe.defectPixelLimit;
}

임계값을 InspectionRecipe 같은 설정 객체로 묶어 외부 파일에서 읽어 들이면, Magic Number를 없애는 동시에 현장에서 코드 수정 없이 제품별 튜닝이 가능해진다. 안티패턴 제거가 곧 제품 유연성으로 이어지는 사례다.

안티패턴증상원인탈출법
God Object한 클래스가 모든 책임을 떠안음, 멤버·메서드 수십 개요구사항 누적, 시간 압박책임 단위로 클래스 분리, 상위는 조율만
Spaghetti Code깊은 중첩, 전역 상태, 추적 불가능한 흐름경험 부족, 임시방편 누적early return, 함수 추출, 데이터를 인자/반환값으로
Copy-Paste같은 로직이 여러 곳에 복제됨시간 압박, "복붙이 빠르다"공통 로직 추출, DRY 적용
Magic Number의미 없는 리터럴이 코드에 흩뿌려짐"일단 동작하게", 이름 짓기 귀찮음명명된 상수(k 접두사), enum
Premature Optimization측정 없이 비튼 코드, 가독성 희생추측 기반 판단먼저 명확하게, 프로파일링 후 핫스팟만
Golden Hammer익숙한 도구를 모든 문제에 무리하게 적용익숙함을 근거로 삼음문제에 맞는 도구 선택, 의식적으로 질문
Boat Anchor / Dead Code호출되지 않는 코드, 주석 처리된 옛 구현"혹시 나중에", 삭제 불안삭제 — 버전 관리가 보존한다
Lava Flow정체불명의 코드가 굳어 못 건드림임시 코드가 검토 없이 굳음점진적 이해 — 테스트로 고정 후 떼어냄
안티패턴을 안다는 것 안티패턴 학습의 목적은 남의 코드를 비판하는 어휘를 얻는 것이 아니다. 자기 코드가 어느 방향으로 미끄러지고 있는지 일찍 알아채는 것이다. God Object는 어느 날 갑자기 생기지 않는다 — 메서드 하나씩 붙으며 자란다. 그 신호를 이름으로 인식할 수 있으면, 작을 때 멈출 수 있다.
