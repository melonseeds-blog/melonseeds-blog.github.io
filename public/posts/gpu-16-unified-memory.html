Unified Memory란

4편에서는 CPU 메모리와 GPU 메모리를 따로 할당하고 cudaMemcpy로 직접 옮겼다. 포인터가 두 개(h_data, d_data)이고, 어느 쪽이 최신인지 프로그래머가 관리해야 했다. Unified Memory(관리 메모리, managed memory)는 포인터 하나를 CPU와 GPU가 같이 쓰게 해 준다. 데이터를 언제 어느 쪽으로 옮길지는 CUDA 드라이버가 정한다.

항목명시적 복사 (4편)Unified Memory
할당malloc + cudaMalloccudaMallocManaged 한 번
포인터CPU용, GPU용 따로하나를 양쪽에서 사용
데이터 이동cudaMemcpy를 직접 호출드라이버가 필요할 때 자동으로 옮김
성능 예측쉬움 (복사 시점이 코드에 보임)어려움 (언제 옮기는지 안 보임)
코드 양많음적음
물리 메모리가 하나가 되는 것은 아님 일반 PC의 독립 GPU는 CPU 메모리(DDR)와 GPU 메모리(GDDR)가 물리적으로 따로 있고 PCIe로 연결되어 있다. Unified Memory는 이 구조를 바꾸지 않는다. 주소 공간을 하나로 보여 주고, 실제 데이터는 뒤에서 PCIe로 옮긴다. 옮기는 비용은 그대로 있다. 다만 누가 언제 옮기느냐가 바뀔 뿐이다.

기본 사용법

__global__ void Scale(float* data, int n, float k)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) data[i] *= k;
}

int main()
{
    const int n = 1 << 24;
    float* data = nullptr;
    cudaMallocManaged(&data, n * sizeof(float));   // one pointer for CPU and GPU

    for (int i = 0; i < n; ++i)                     // CPU writes directly
        data[i] = 1.0f;

    Scale<<<(n + 255) / 256, 256>>>(data, n, 2.0f); // GPU uses the same pointer

    cudaDeviceSynchronize();                        // REQUIRED before the CPU reads
    printf("%f\n", data[0]);                        // 2.0

    cudaFree(data);                                 // same free function as cudaMalloc
}

복사 코드가 사라졌다. 반드시 지켜야 할 규칙은 하나다. 커널이 끝나기 전에 CPU가 그 메모리를 만지면 안 된다. 커널 실행은 비동기이므로(5편), CPU에서 읽기 전에 cudaDeviceSynchronize()나 해당 스트림 동기화가 필요하다. 이 동기화를 빠뜨렸을 때 어떤 일이 생기는지는 아래 "동작 방식 두 가지"에 따라 다르다.

동작 방식 두 가지 - Windows에서 특히 중요

Unified Memory는 GPU 세대와 운영체제에 따라 동작이 크게 다르다. 같은 코드가 리눅스에서는 잘 돌고 Windows에서는 접근 위반으로 죽는 일이 생기므로, 먼저 내 환경이 어느 쪽인지 알아야 한다.

항목기본 방식완전 지원 방식
해당 환경Windows (WDDM), Pascal 이전 GPU (Kepler, Maxwell)리눅스 + Pascal(GTX 10xx) 이후 GPU
데이터 이동 시점커널을 실행할 때 관리 메모리를 GPU로 한꺼번에 옮김GPU가 실제로 접근한 페이지만 그때그때 옮김 (page fault)
커널 실행 중 CPU 접근불가. GPU가 일하는 동안 CPU가 관리 메모리를 만지면 접근 위반가능 (성능은 나빠짐)
GPU 메모리보다 큰 할당불가가능 (oversubscription)
cudaMemPrefetchAsyncGPU 쪽으로는 사용 불가사용 가능
cudaDevAttrConcurrentManagedAccess01
int dev = 0, concurrent = 0, pageable = 0;
cudaDeviceGetAttribute(&concurrent, cudaDevAttrConcurrentManagedAccess, dev);
cudaDeviceGetAttribute(&pageable,   cudaDevAttrPageableMemoryAccess,   dev);
printf("concurrentManagedAccess = %d\n", concurrent);   // 0 on Windows (WDDM)
printf("pageableMemoryAccess    = %d\n", pageable);     // 1 only with HMM or hardware coherence
Windows에서 흔한 사고 Windows에서는 "커널 실행 중 CPU 접근 불가"가 그 장치에서 실행 중인 어떤 커널이든 해당된다. 스트림 A에서 커널을 돌리는 동안 CPU가 스트림 B용 관리 메모리를 읽어도 접근 위반이 날 수 있다. 여러 스트림을 쓰는 영상 파이프라인(12편)에서는 cudaStreamAttachMemAsync로 메모리를 특정 스트림에 묶어, 그 스트림만 끝나면 CPU가 접근할 수 있게 해야 한다. 
// attach a managed buffer to one stream (basic mode / Windows)
cudaStreamAttachMemAsync(streamA, bufA, 0, cudaMemAttachSingle);
cudaStreamSynchronize(streamA);     // after this, CPU may touch bufA
                                    // even if kernels are running in other streams

완전 지원 방식의 페이지 이동 원리

리눅스 + Pascal 이후 환경에서는 운영체제의 가상 메모리와 같은 방식으로 동작한다. 관리 메모리는 페이지 단위로 나뉘고, 각 페이지는 어느 순간 CPU 쪽이나 GPU 쪽 중 한 곳에 있다.

요청 시 페이지 이동 (on-demand page migration). 접근하는 쪽에 페이지가 없으면 그때 옮긴다

세부 동작은 대략 다음과 같다.

항목동작
처음 할당cudaMallocManaged 직후에는 물리 메모리가 아직 없다. 처음 접근하는 쪽(CPU 또는 GPU)에 그때 페이지가 생긴다 (first touch)
이동 단위오류는 작은 페이지 단위로 나지만, 드라이버가 근처 페이지를 묶어 더 큰 덩어리로 옮긴다. 순차 접근이면 묶음이 커져서 효율이 좋아진다
오류 처리 비용GPU는 page fault가 나면 해당 워프를 멈추고 드라이버에 처리를 맡긴다. 수많은 워프가 동시에 오류를 내므로 드라이버가 묶어서 처리하지만, 그래도 명시적 복사보다 대역폭이 낮다
양쪽이 번갈아 접근CPU와 GPU가 같은 페이지를 번갈아 쓰면 페이지가 계속 왔다 갔다 한다 (thrashing). 가장 나쁜 경우

그래서 Unified Memory 코드를 처음 짜고 프로파일러로 보면, 첫 커널이 비정상적으로 오래 걸리는 경우가 많다. 커널 계산 시간이 아니라 페이지를 옮기는 시간이다.

prefetch - 미리 옮겨 두기

page fault를 피하는 가장 효과적인 방법은 커널 실행 전에 미리 옮겨 두는 것이다. cudaMemPrefetchAsync는 지정한 범위를 지정한 장치로 한꺼번에 옮긴다. 오류를 하나씩 처리하는 대신 큰 덩어리로 복사하므로 명시적 cudaMemcpyAsync에 가까운 속도가 나온다.

int dev = 0;
size_t bytes = n * sizeof(float);
cudaMallocManaged(&data, bytes);
FillOnCpu(data, n);

cudaMemPrefetchAsync(data, bytes, dev, stream);              // CPU -> GPU, before the kernel
Scale<<<grid, block, 0, stream>>>(data, n, 2.0f);
cudaMemPrefetchAsync(data, bytes, cudaCpuDeviceId, stream);  // GPU -> CPU, before CPU reads
cudaStreamSynchronize(stream);
UseOnCpu(data, n);

prefetch도 스트림에 들어가는 비동기 작업이라, 5편에서 본 것처럼 다른 스트림의 커널과 겹쳐서 실행할 수 있다. 결국 "언제 옮길지"를 다시 프로그래머가 정하는 셈이지만, 포인터가 하나라는 장점은 그대로 남는다.

새 버전 API CUDA 12.2부터는 장치 번호 대신 cudaMemLocation 구조체로 위치를 지정하는 새 버전 함수가 추가되었다. 장치 번호를 받는 위 형태는 많은 자료와 예제가 쓰는 기본형이다. 사용하는 CUDA 버전의 헤더에서 어떤 형태를 제공하는지 확인한다.

cudaMemAdvise - 드라이버에 힌트 주기

prefetch가 "지금 옮겨라"라면, advise는 "이 메모리는 이렇게 쓸 것이다"라고 미리 알려 주는 힌트다. 드라이버는 이 힌트에 맞춰 페이지를 어디에 둘지, 복사본을 만들지 정한다.

힌트의미어울리는 데이터
cudaMemAdviseSetReadMostly대부분 읽기만 한다. 접근하는 장치마다 읽기 전용 복사본을 둠. 누가 쓰면 다른 복사본은 무효가 됨보정 테이블, LUT, 신경망 가중치
cudaMemAdviseSetPreferredLocation이 장치에 두는 것을 우선한다. 다른 쪽이 접근해도 가능하면 옮기지 않고 원격으로 읽게 함GPU가 주로 쓰고 CPU가 가끔 들여다보는 버퍼
cudaMemAdviseSetAccessedBy이 장치가 접근할 것이다. 미리 매핑해 두어 접근할 때 page fault 없이 원격으로 읽게 함여러 GPU가 나눠 읽는 데이터
// lookup table: written once on the CPU, read by many kernels
cudaMallocManaged(&lut, 256 * sizeof(float));
BuildLutOnCpu(lut);
cudaMemAdvise(lut, 256 * sizeof(float), cudaMemAdviseSetReadMostly, dev);
cudaMemPrefetchAsync(lut, 256 * sizeof(float), dev, stream);   // GPU gets a read-only copy
// CPU can still read lut without pulling it back from the GPU

GPU 메모리보다 큰 데이터 다루기

완전 지원 방식에서는 GPU 메모리보다 큰 관리 메모리를 할당할 수 있다(oversubscription). 8GB GPU에서 12GB 배열을 할당하고 커널을 돌리면, 드라이버가 필요한 페이지를 GPU로 올리고 오래 안 쓴 페이지를 CPU로 내보내며 처리한다.

편리하지만 속도는 접근 방식에 크게 좌우된다. 앞에서부터 순서대로 한 번 훑는 처리는 그럭저럭 동작하지만, 무작위 접근이나 같은 데이터를 여러 번 반복해서 읽는 처리는 페이지가 계속 들락날락해서 매우 느려진다. 큰 데이터를 다뤄야 한다면 처음부터 데이터를 GPU에 맞는 크기의 덩어리로 나눠서 스트림 파이프라인(5편)으로 흘리는 설계가 대부분 더 빠르고 예측 가능하다.

언제 쓰고 언제 피하나

상황판단이유
알고리즘 시험, 빠른 시제품쓴다복사 코드 없이 커널 정확성부터 확인. 나중에 명시적 복사로 바꾸기 쉬움
포인터로 얽힌 자료구조 (트리, 그래프, 연결 리스트)쓴다명시적 복사로는 포인터마다 깊은 복사(deep copy)가 필요. 관리 메모리는 포인터를 그대로 사용 가능
설정값, LUT처럼 작고 자주 안 바뀌는 데이터쓸 만함ReadMostly 힌트와 함께 쓰면 관리가 편함
GPU 메모리보다 큰 데이터 (리눅스)상황에 따라순차 접근이면 동작. 성능이 중요하면 직접 나누는 편이 나음
실시간 영상 파이프라인 (택트 타임 보장)피한다page fault 시점과 비용을 예측할 수 없어서 최악 처리 시간이 흔들림. 핀드 메모리 + 명시적 비동기 복사(4편, 12편)가 맞음
여러 스트림이 동시에 도는 Windows 프로그램피한다기본 방식이라 실행 중 CPU 접근 제약이 많음
Jetson 같은 통합 GPU는 사정이 다름 Jetson처럼 CPU와 GPU가 같은 물리 DRAM을 쓰는 장치에서는 관리 메모리가 데이터를 실제로 옮기지 않는다. 대신 캐시 일관성을 맞추는 비용이 생긴다. 이런 장치에서는 관리 메모리나 mapped pinned memory(cudaHostAlloc + cudaHostAllocMapped)로 복사 없이 쓰는 방식이 흔하다. 독립 GPU 기준으로 배운 "복사 비용" 감각이 그대로 맞지 않으므로 장치별로 측정한다.

페이지 이동 확인하기

Unified Memory 성능 문제는 대부분 "보이지 않는 이동"이다. Nsight Systems로 이동을 눈으로 확인한다(8편).

nsys profile --trace=cuda,nvtx \
     --cuda-um-cpu-page-faults=true \
     --cuda-um-gpu-page-faults=true \
     -o um_report ./my_app

타임라인에 "Unified Memory" 줄이 생기고, CPU에서 GPU로(HtoD), GPU에서 CPU로(DtoH) 옮긴 양과 page fault 위치가 표시된다. 확인할 점은 다음과 같다.

보이는 것뜻조치
커널 시작 직후 GPU page fault가 몰림데이터를 미리 안 옮김커널 전에 cudaMemPrefetchAsync
같은 구간에서 HtoD, DtoH가 반복CPU와 GPU가 같은 페이지를 번갈아 사용 (thrashing)CPU 접근을 모아서 한 번에 처리하거나 SetPreferredLocation

흔한 함정

동기화 없이 CPU에서 읽기 Windows에서는 접근 위반으로 프로그램이 죽고, 리눅스에서는 죽지 않는 대신 커널이 아직 덜 쓴 값을 읽는다. 둘 다 버그다. 커널 뒤 CPU 접근 전에는 항상 동기화한다.
리눅스에서 개발하고 Windows에 배포 리눅스에서는 커널 실행 중 CPU 접근이 허용되므로 버그가 드러나지 않는다. 같은 코드를 Windows에 올리면 그때서야 접근 위반이 난다. 대상 환경에서 반드시 테스트한다.
구조체 안의 일반 포인터 관리 메모리에 구조체를 두어도, 그 안의 멤버 포인터가 new나 malloc으로 할당한 CPU 메모리를 가리키면 GPU에서 접근할 수 없다(HMM이 없는 환경). 구조체가 가리키는 메모리도 모두 관리 메모리로 할당한다. std::vector를 쓰려면 cudaMallocManaged를 사용하는 사용자 정의 할당자가 필요하다.
첫 실행 시간을 성능으로 착각 관리 메모리 코드의 첫 커널 시간에는 페이지 이동이 포함된다. 성능을 비교할 때는 prefetch를 한 상태에서, 몇 번 돌린 뒤의 시간을 잰다.
