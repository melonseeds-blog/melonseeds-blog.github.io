왜 비동기가 필요한가

WPF UI는 단일 스레드로 동작한다. 이 스레드가 파일 읽기·네트워크 요청·이미지 처리 같은 긴 작업에 막히면 창이 얼어붙고 사용자 입력에 반응하지 않는다. 비동기는 이런 블로킹을 피하기 위해 존재한다.

블로킹의 문제

// 나쁜 예 — UI 스레드에서 동기 호출
private void OnLoadClick(object sender, RoutedEventArgs e)
{
    // 큰 파일 읽기 — 수 초 동안 UI가 얼어붙는다.
    byte[] data = File.ReadAllBytes(@"D:\large_image.tif");
    ImageView.Source = Decode(data);
}

UI 스레드가 디스크 I/O를 기다리는 동안에는 다른 일을 못 한다. 비동기로 바꾸면 OS가 I/O를 처리하는 동안 UI 스레드는 자유로워진다.

// 좋은 예 — 비동기 호출
private async void OnLoadClick(object sender, RoutedEventArgs e)
{
    // 파일 I/O가 끝날 때까지 UI는 계속 반응한다.
    byte[] data = await File.ReadAllBytesAsync(@"D:\large_image.tif");
    ImageView.Source = Decode(data);
}

I/O 바운드와 CPU 바운드

구분특징처리 방식
I/O 바운드디스크·네트워크 대기await로 OS 완료 통지를 기다린다. 스레드 점유 안 함.
CPU 바운드계산·이미지 처리Task.Run으로 스레드풀에 던진다.

Task와 Task<T>

Task는 "언젠가 끝날 작업"을 표현하는 객체다. 결과 없이 끝나는 작업은 Task, 값을 돌려주는 작업은 Task<T>를 쓴다. C++의 std::future와 비슷하지만 훨씬 통합된 도구다.

// 결과 없는 작업
Task t1 = Task.Delay(1000);

// 결과 있는 작업
Task<int> t2 = Task.FromResult(42);

// 완료 대기 (비동기적으로)
await t1;
int value = await t2;

async/await 키워드

async 함수 안에서만 await를 쓸 수 있다. await는 Task가 끝날 때까지 함수를 "일시 정지"한 뒤, 끝나면 이어서 실행한다. 스레드를 막지 않는다는 점이 핵심이다.

public async Task<string> DownloadHtmlAsync(string url)
{
    using HttpClient client = new();
    string html = await client.GetStringAsync(url);  // 여기서 일시 정지
    return html.ToLower();                            // 완료되면 이어서 실행
}

컴파일러는 state machine으로 변환한다

겉보기에는 순차 코드지만, 컴파일러는 await 지점마다 분할되는 상태 머신을 만든다. 각 await 직전 상태를 저장하고, 콜백으로 이어 실행한다.

async 함수의 상태 머신 변환과 UI 스레드 점유

async 반환 타입

반환 타입용도
Task결과 없는 비동기 메서드. 가장 기본.
Task<T>결과를 돌려주는 비동기 메서드.
ValueTask<T>핫 패스 최적화. 동기 완료가 잦을 때.

Task.Run과 스레드풀

I/O는 OS가 비동기로 처리해 주지만, CPU 작업은 누군가는 실제로 계산해야 한다. Task.Run이 작업을 스레드풀로 옮겨 UI 스레드를 비워 준다.

// CPU 바운드 — 이미지 처리, 무거운 계산
private async void OnFilterClick(object sender, RoutedEventArgs e)
{
    // 스레드풀에서 처리, UI는 그대로 응답
    Bitmap result = await Task.Run(() => ApplyGaussianBlur(_source, 5));
    ImageView.Source = ToBitmapSource(result);
}

// I/O 바운드는 Task.Run으로 감싸지 말 것
// 잘못된 예: await Task.Run(() => File.ReadAllBytesAsync(path));
// 올바른 예: await File.ReadAllBytesAsync(path);

Task.Run vs Task.Factory.StartNew

오래된 코드에서는 Task.Factory.StartNew를 보게 된다. 옵션이 풍부하지만 기본값이 위험하다. 일반 코드는 Task.Run을 쓴다.

StartNew의 함정 async 람다를 StartNew에 넘기면 Task<Task>가 반환된다. Unwrap()이 필요하다. 그냥 Task.Run을 쓰면 자동으로 풀어 준다.

WhenAll / WhenAny

여러 비동기 작업을 동시에 돌리고 합칠 때 쓴다. 순차 await와 결과가 크게 다르다.

// 순차 — 9초 (각 3초씩)
string a = await DownloadAsync(url1);
string b = await DownloadAsync(url2);
string c = await DownloadAsync(url3);

// 병렬 — 3초 (동시에 시작)
Task<string> ta = DownloadAsync(url1);
Task<string> tb = DownloadAsync(url2);
Task<string> tc = DownloadAsync(url3);
string[] results = await Task.WhenAll(ta, tb, tc);

WhenAny — 가장 빠른 결과 / 타임아웃

// 타임아웃 패턴
Task<string> download = DownloadAsync(url);
Task timeout = Task.Delay(TimeSpan.FromSeconds(5));

Task winner = await Task.WhenAny(download, timeout);
if (winner == timeout)
{
    throw new TimeoutException("다운로드 5초 초과");
}
string html = await download;
WhenAll의 예외 동작 여러 Task가 예외를 던지면 WhenAll의 결과 Task는 모든 예외를 모은 AggregateException을 보관한다. 하지만 await는 첫 번째 예외만 throw한다. 모든 예외를 보려면 task.Exception.InnerExceptions를 확인한다.

CancellationToken

비동기 작업의 취소는 강제 종료가 아니라 협력적 취소다. 작업 측이 토큰을 주기적으로 확인하고 스스로 중단한다.

public async Task<int> CountAsync(CancellationToken ct)
{
    int count = 0;
    for (int i = 0; i < 1_000_000; i++)
    {
        ct.ThrowIfCancellationRequested();  // 협력 지점
        count += Compute(i);
        if (i % 1000 == 0)
        {
            await Task.Delay(1, ct);  // Delay 자체도 토큰을 받는다
        }
    }
    return count;
}

// 호출 측
var cts = new CancellationTokenSource();
cts.CancelAfter(TimeSpan.FromSeconds(3));  // 3초 후 자동 취소

try
{
    int result = await CountAsync(cts.Token);
}
catch (OperationCanceledException)
{
    // 취소는 정상 흐름으로 처리
    Log("사용자 취소");
}
표준 라이브러리 API는 대부분 CancellationToken을 받는다 HttpClient.GetAsync, Stream.ReadAsync, Task.Delay 모두 토큰 오버로드가 있다. 자신이 만든 비동기 API에도 마지막 파라미터로 토큰을 받자.

ConfigureAwait(false)

await는 기본적으로 호출 직전의 SynchronizationContext(WPF에선 UI 스레드)로 돌아온다. 라이브러리 코드처럼 UI 컨텍스트가 필요 없는 곳에서는 이 복귀가 오버헤드이자 데드락 원인이 된다.

// 라이브러리 — UI 스레드로 돌아갈 필요 없음
public async Task<byte[]> LoadImageAsync(string path)
{
    using var fs = File.OpenRead(path);
    var buf = new byte[fs.Length];
    await fs.ReadAsync(buf).ConfigureAwait(false);  // 컨텍스트 복귀 회피
    return Process(buf).ConfigureAwait(false) is var x ? x : buf;
}

// UI 코드 — 그대로 두기 (UI 업데이트 필요)
private async void OnClick(...)
{
    byte[] data = await LoadImageAsync(path);  // ConfigureAwait 없이
    ImageView.Source = Decode(data);           // UI 스레드에서 실행됨
}
코드 종류권장
라이브러리/Core 코드ConfigureAwait(false) 일관 적용
WPF UI 코드붙이지 않음 (UI 컨텍스트로 복귀해야 함)
ASP.NET Core / 콘솔SynchronizationContext가 없어 차이 없음

동기 컨텍스트 (SynchronizationContext)

"await 후 어디로 돌아갈까?"를 결정하는 객체다. 런타임 환경마다 다르다.

환경SynchronizationContextawait 복귀 위치

WinFormsWindowsFormsSynchronizationContextUI 스레드
ASP.NET (Classic)AspNetSynchronizationContext요청 컨텍스트
ASP.NET Core없음 (null)임의의 스레드풀 스레드
콘솔 앱없음 (null)임의의 스레드풀 스레드

WPF에서 await 후 자연스럽게 ImageView.Source = ...를 할 수 있는 이유는 컨텍스트가 자동으로 UI 스레드로 끌어와 주기 때문이다.

예외 처리

비동기 함수의 예외는 Task 안에 보관됐다가 await 시점에 다시 throw된다. 따라서 일반 try/catch로 처리된다.

try
{
    string html = await DownloadHtmlAsync(url);
}
catch (HttpRequestException ex)
{
    Log($"네트워크 오류: {ex.Message}");
}
catch (OperationCanceledException)
{
    Log("취소됨");
}

AggregateException

여러 Task가 예외를 던지는 경우 WhenAll의 Task에는 AggregateException이 담긴다. await는 첫 예외만 풀어 throw하므로 모든 예외를 잡으려면 직접 본다.

Task all = Task.WhenAll(t1, t2, t3);
try
{
    await all;
}
catch
{
    // all.Exception에 모든 예외가 들어 있다.
    foreach (var inner in all.Exception!.InnerExceptions)
    {
        Log(inner.Message);
    }
}

UI 스레드와 Dispatcher

WPF의 UI 요소는 자신이 만들어진 스레드(UI 스레드)에서만 접근할 수 있다. 다른 스레드에서 ImageView.Source = ...를 하면 InvalidOperationException이 난다. 이때 Dispatcher로 마샬링한다.

// 백그라운드 스레드에서 직접 UI 업데이트
await Task.Run(() =>
{
    for (int i = 0; i < 100; i++)
    {
        int progress = i;
        Application.Current.Dispatcher.Invoke(() =>
        {
            ProgressBar.Value = progress;  // UI 스레드에서 실행
        });
    }
});

// await 패턴이라면 Dispatcher가 거의 필요 없다
private async void OnProcessClick(...)
{
    var progress = new Progress<int>(p => ProgressBar.Value = p);
    await Task.Run(() => HeavyWork(progress));
    // 여기서는 자동으로 UI 스레드 복귀
}
IProgress<T>는 마샬링까지 처리한다 UI 스레드에서 만든 Progress<T>는 Report 호출을 자동으로 UI 스레드로 옮긴다. Dispatcher.Invoke를 직접 부르지 않아도 된다. 자세한 내용은 WPF 편에서 다룬다.

비동기 함정

async void는 이벤트 핸들러에서만

async void는 호출자가 완료를 알 수 없고, 예외가 SynchronizationContext로 직접 던져져 보통 앱이 죽는다. 이벤트 핸들러 시그니처 때문에 어쩔 수 없는 경우 외에는 반드시 async Task로 한다.

// 금지
public async void DoWork()
{
    throw new InvalidOperationException();  // 앱 크래시
}

// OK — 이벤트 핸들러는 예외
private async void OnButtonClick(object sender, RoutedEventArgs e)
{
    try
    {
        await DoWorkAsync();
    }
    catch (Exception ex)
    {
        ShowError(ex);  // 반드시 자체에서 try/catch
    }
}
위험: async void 예외가 잡히지 않고, 단위 테스트도 불가능하다. 이벤트 핸들러가 아니면 절대 쓰지 말 것.

.Result / .Wait() 데드락

동기 코드에서 비동기 함수를 .Result로 받으면 WPF에서는 데드락이 발생한다. UI 스레드가 Task 완료를 기다리는데, Task 안의 await는 같은 UI 스레드로 돌아오려 하기 때문이다.

// 데드락
private void OnSyncClick(object sender, RoutedEventArgs e)
{
    string html = DownloadHtmlAsync(url).Result;  // 멈춤
}

// 올바른 해법 — async로 전염시키기
private async void OnAsyncClick(object sender, RoutedEventArgs e)
{
    string html = await DownloadHtmlAsync(url);
}
위험: .Result, .Wait(), GetAwaiter().GetResult() WPF·WinForms·ASP.NET Classic에서 UI/요청 컨텍스트가 있는 동안 호출하면 데드락. 라이브러리 안 어디서든 합쳐서 한 번이라도 호출하면 위험하다. "비동기는 끝까지 비동기"가 규칙이다.

fire-and-forget의 예외 손실

// 나쁜 예 — 예외가 묻힌다
_ = SaveLogAsync(message);

// 좋은 예 — 최소한 로깅
_ = SaveLogAsync(message).ContinueWith(
    t => Log(t.Exception),
    TaskContinuationOptions.OnlyOnFaulted);

기타 흔한 실수

  • CancellationToken 무시 — 비동기 API를 만들면서 토큰을 받지 않으면 호출자가 취소할 방법이 없다.
  • foreach 안에서 순차 await — 동시 가능한 작업을 순차 처리해 느려진다. Task.WhenAll(items.Select(asyncFn))을 고려한다.
  • I/O를 Task.Run으로 감싸기 — 이미 비동기인 I/O를 스레드풀로 옮기는 건 스레드 낭비다.
  • 람다 캡처에 의한 누수 — Task가 오래 살아 있으면 캡처한 객체도 살아 있다.

C++ std::async / 코루틴과 비교

C++ 시리즈에서 다룬 std::async·std::future·코루틴과 개념적으로 대응된다.
