[Ch7] 왜 AI 시스템 테스팅이 다른가

AI 기반 시스템에도 요구사항 명세와 설계 명세는 여전히 중요하다. 테스터가 "실제 동작이 명시된 요구사항과 일치하는가"를 판단하려면 그 근거가 필요하기 때문이다. 그러나 AI 시스템의 명세는 본질적으로 불완전해지기 쉽고, 그 불완전함이 곧 테스트 오라클 문제로 직결된다.

AI 시스템 명세가 어려운 6가지 이유

실러버스 7.1절은 명세를 어렵게 만드는 요소를 다음과 같이 열거한다.

  1. 탐색적 개발의 본질 — AI 프로젝트는 "데이터에서 출발해 무엇을 예측할 수 있는지 찾아가는" 흐름이라 시작 시점에 요구사항을 단정하기 어렵다. 비즈니스 목표와 필요 예측 정도만 상위 수준으로 명시되는 경우가 흔하다.
  2. 정확도는 사후에야 안다 — 독립 테스팅 결과가 나와야 정확도가 드러나기 때문에 인수 기준 자체를 구현이 진행된 뒤에 다듬게 된다.
  3. 확률적 특성 — 예측 정확도 같은 품질 요구사항에 허용 오차를 명시해야 한다. "정답인지 아닌지"가 아니라 "최적 해답의 N% 이내인가"라는 표현이 필요하다.
  4. 인간 모방 시스템 — "사람만큼 잘하면 된다"는 식의 미흡한 요구사항이 자주 나온다. 사람들 사이 편차가 크면 오라클 정의는 더 흐릿해진다.
  5. 유연한 UI — 자연어, 컴퓨터 비전, 물리적 상호작용을 다루는 시스템은 상호작용 패턴을 모두 식별·문서화하기가 어렵다.
  6. 새로운 품질 특성 — 적응성, 유연성, 진화, 자율성은 정의 자체가 새로워서 테스트 방법도 같이 개발해야 한다.
출제 포인트 "AI 시스템 명세가 어려운 이유"는 K2 학습 목표(AI-7.1.1)다. 위 6가지 중 두 개를 골라야 하는 시나리오 문항이 출제될 수 있다. "탐색적 개발 성격"과 "허용 오차 명세 필요"는 단골 보기다.

[Ch7] AI 시스템 테스팅 vs 기존 테스팅

전통적 V 모델은 컴포넌트, 통합, 시스템, 인수 4단계가 친숙하다. AI 시스템에서는 여기에 두 개의 새로운 레벨이 추가된다.

입력 데이터 테스팅 (Input Data Testing)

훈련과 예측을 위해 시스템이 사용하는 데이터의 품질을 확인하는 새로운 레벨이다. 활동은 네 갈래다.

  • 리뷰 — 데이터 수집 정책, 라벨링 규칙을 인간이 직접 검토한다.
  • 통계 기법 — 데이터 편향성 테스팅 등.
  • 훈련 데이터 EDA — 탐색적 데이터 분석으로 분포·이상값·결측을 본다.
  • 데이터 파이프라인의 정적·동적 테스팅 — 데이터 준비 컴포넌트별 테스팅 + 통합 테스팅.

훈련용 파이프라인은 일종의 프로토타입이고, 운영용 파이프라인은 완전 엔지니어링된 자동화 버전이다. 둘이 상당히 다를 수 있어서 두 버전의 기능적 동등성 자체를 별도로 테스트하기도 한다.

ML 모델 테스팅 (ML Model Testing)

선택한 모델이 지정한 성능 기준을 충족하는지 확인한다. 두 갈래가 있다.

  • ML 기능적 성능 기준 — 정확도, 정밀도, 재현율, F1, AUC 등 (Ch5 참조).
  • ML 비기능적 기준 — 훈련 속도, 예측 속도, 자원 사용량, 적응성, 투명성.

여기에 ML 프레임워크·알고리즘·모델·설정·초매개변수 선택이 "가능한 최적에 가까운가"를 판단한다. 필요하다면 신경망 화이트박스 커버리지도 이 단계에서 본다.

그 외 레벨

레벨AI 시스템에서의 초점
컴포넌트 테스팅UI·통신 등 모델이 아닌 컴포넌트를 일반적 방식으로 테스트한다.
컴포넌트 통합 테스팅데이터 파이프라인 → 모델 → 후속 컴포넌트로 이어지는 흐름이 정상인지 확인한다. AI as a Service인 경우 API 테스팅이 포함된다.
시스템 테스팅운영 환경 또는 시뮬레이터에서 전체 동작을 본다. ML 기능적 성능 기준을 다시 한번 측정하는 것이 핵심이다(DNN 압축 등으로 성능이 떨어졌을 수 있다). 강건성을 위한 적대적 테스팅, 설명 가능성 테스팅, 센서 인터페이스 테스팅도 포함된다.
인수 테스팅AI 시스템은 인수 기준 정의가 까다롭다(8.8절). AI as a Service라면 서비스 적합성·기능적 성능 충족 여부를 인수 테스팅으로 판단한다.
암기 팁 — "AI 시스템은 V 모델 + 2" 기존 4레벨(컴포넌트/통합/시스템/인수) 위에 입력 데이터 테스팅과 ML 모델 테스팅이 얹힌다. 모든 레벨에서 데이터 엔지니어/과학자와 도메인 전문가의 협업이 강조된다.

[Ch7] AI 시스템에 대한 데이터 소싱

AI 시스템 테스트 데이터 확보는 일반 시스템보다 훨씬 까다롭다. 실러버스가 짚는 잠재 문제는 네 가지다.

  1. 빅 데이터의 어려움 — 대량·고속·다양성을 모두 갖춘 데이터를 생성·관리하는 것 자체가 어렵다. 예: 초당 수많은 이미지를 처리하는 시스템의 대표성 있는 테스트 데이터 만들기.
  2. 시간 흐름에 따른 변경 — 실제 이벤트를 반영하는 데이터는 시간이 지나며 변한다. 얼굴 인식 시스템 테스트용 사진을 몇 년에 걸친 노화 과정으로 "에이징"해야 할 수도 있다.
  3. 개인정보·기밀 — 삭제, 암호화, 익명화 같은 기술이 필요하고 법적 승인까지 받아야 한다.
  4. 테스터가 데이터 과학자처럼 행동할 때 — 동일한 전처리를 반복하면 그 단계의 결함을 놓치기 쉽다. 다른 시각·다른 도구가 필요하다.

자동화 편향성 테스팅

인간 의사결정을 보조하는 AI 시스템은 흔히 자동화 편향성(automation bias), 다른 말로 안심 편향성(complacency bias)을 유발한다. 두 가지 형태가 있다.

  • 형태 1: 권고를 그대로 수용 — 양식 자동 완성, 휴대전화 자동 수정 등. 의사결정 품질이 보통 5% 정도, 상황에 따라 더 많이 떨어진다고 보고된다.
  • 형태 2: 모니터링 소홀 — 반자율주행 차량 운전자가 시스템을 지나치게 신뢰해 주의를 기울이지 않는 경우. 사고 직전 인간이 개입해야 할 때 대응 불가 상태에 빠진다.

테스터는 두 시나리오 모두에서 시스템이 주는 권고의 품질과 대표 사용자가 입력하는 품질을 함께 테스트해야 한다. 자동화에 기댄 인간의 의사결정이 어떻게 손상되는지를 모델링하는 것이 핵심이다.

[Ch7] AI 컴포넌트 문서화의 중요성

명확한 문서는 AI 시스템의 투명성을 높여 테스팅을 개선한다. 실러버스는 AI 컴포넌트가 갖춰야 할 문서 항목을 다음 6개 영역으로 정리한다.

영역포함 내용
일반식별자, 설명, 개발자, 하드웨어 요구사항, 라이선스, 버전, 날짜, 담당자
설계가정, 기술적 결정
운용1·2차 유스케이스, 사용자, 자가학습 접근법, 알려진 편향성, 윤리·안전 문제, 투명성, 의사결정 임계값, 플랫폼, 컨셉 드리프트
데이터 세트특성, 수집, 가용성, 전처리, 사용, 내용, 라벨링, 크기, 개인정보, 보안, 편향/공정성, 제약
테스팅테스트 데이터 세트, 독립성, 결과, 강건성 접근법, 설명 가능성, 컨셉 드리프트, 이식성
훈련·성능ML 알고리즘, 가중치, 검증 데이터 세트, 측정지표 선택, 임계값, 실측값

테스터 관점에서 특히 중요한 문서 내용은 다음과 같다.

  • 시스템 목적·기능·비기능 요구사항 명세 — 테스트 베이시스가 된다.
  • 아키텍처·설계 정보 — 통합 테스팅 목표 식별과 화이트박스 테스팅 베이시스가 된다.
  • 운영 환경 명세 — 자율성·유연성·적응성 테스팅에 필요하다.
  • 입력 데이터 출처와 메타데이터 — 기능적 정확성, 표본 편향성, 자가학습 시 저품질 데이터로 인한 잘못된 학습을 검증할 때 쓴다.
  • 환경 변화에 시스템이 적응하는 방식 — 적응성 테스팅 베이시스.
  • 예상 사용자 정보 — 테스트가 대표성을 갖도록 한다.
왜 6개 영역인가 AI 시스템은 코드만 있는 게 아니라 데이터·모델·학습 절차·운영 컨텍스트가 모두 결합돼 있다. 어느 하나만 빠져도 테스트 결과의 의미를 해석할 수 없다. 그래서 문서가 6개 영역으로 갈리는 것이다.

[Ch7] 컨셉 드리프트와 테스트 접근법 선택

컨셉 드리프트 테스팅

운영 환경은 시간이 지나며 변하는데 훈련된 모델은 같이 변하지 않을 수 있다. 이 현상이 컨셉 드리프트(concept drift)다. 모델 결과의 정확도와 유용성이 점점 떨어지는 결과로 나타난다.

원인은 외부의 문화·도덕·사회 변화이거나 시기적·갑작스러운 변화다. 실러버스가 드는 대표 예가 COVID-19 대유행이 판매 예측·주식 시장 모델에 미친 영향이다. 평소 분포에서 벗어난 입력이 갑자기 들어오면 기존 모델은 무력해진다.

대응 방법은 다음과 같다.

  • 정기 재테스트 — 합의된 ML 기능적 성능 기준으로 운영 모델을 주기적으로 측정한다.
  • 완화 — 시스템 중단 — 회복 불능 시 일단 사용을 멈춘다.
  • 완화 — 재훈련 — 최신 데이터로 다시 훈련한 뒤 확인 테스팅, 회귀 테스팅, 그리고 A/B 테스팅으로 갱신된 B 시스템이 원래 A 시스템보다 나은지 비교한다.

ML 시스템을 위한 테스트 접근법 선택

AI 시스템 테스트 접근법은 리스크 분석으로부터 도출된다. 실러버스는 대표적인 리스크와 완화 방법을 표로 정리한다. 시험 K4 학습 목표(AI-7.7.1)에 해당하는 부분이다.

리스크완화 방법
데이터 품질이 예상보다 낮다리뷰, EDA, 동적 테스팅

AI 특유 품질 특성 테스팅

Ch7이 "AI 시스템 테스팅의 큰 그림"이었다면 Ch8은 AI 시스템에만 나타나는 7가지 품질 특성을 어떻게 테스트할지를 다룬다. Ch2 품질 특성에서 정의했던 자가학습·자율성·적응성·유연성·진화·편향성·투명성을 실제 테스트 활동으로 옮기는 단계다.

[Ch8] 자가학습 시스템 테스팅의 어려움

자가학습 시스템은 자기가 자기를 바꾼다. 이 점이 모든 어려움의 출발점이다. 실러버스 8.1절은 6가지 문제와 그 대응을 정리한다.

어려움대응
예기치 않은 변경 — 시스템이 새로운 해결책을 스스로 만들어낼 수 있다. 이전에 합격한 테스트가 다시 합격한다는 보장이 없다.시스템 동작이 변해도 의미가 유지되는 테스트를 설계하고, 관찰된 새 동작에 맞춰 새 테스트를 추가한다.
복잡한 인수 기준 — "개선되어야 한다"만으로는 부족하다. 환경 요인과 연결한 조건부 기준이 필요해진다(예: 환경 요인 F가 Y 이상으로 바뀌면 기능 X가 10% 이상 개선되어야 함).복잡한 인수 기준 명세 + 기준 기능적 성능 기록 지속 유지.
테스팅 시간 부족 — 적응이 빠른 시스템은 변경 후 수동 테스트할 시간이 없다.변경 시 자동으로 실행되는 테스트를 작성한다.
자원 요구사항 — 자가학습에 쓸 수 있는 시간·메모리 한계가 인수 기준에 포함되어야 한다."자원 사용량 ↔ 기능 개선" 연결 여부를 명시한다.
운영 환경의 불충분한 명세 — 훈련 데이터에 없던 입력이 들어오면 예측 불가 동작을 보인다. 데이터 오염 공격과 구분하기 어려울 수 있다(9.1.2절 참조).가능한 운영 환경 변화의 범위를 인수 기준으로 정의한다.
복잡한 테스트 환경 — 잠재적 고위험 환경 변화를 모방하기가 어렵다.결함 주입 도구, 다양한 물리 환경 확보, 가상 테스트 환경 활용.

마지막으로 빼놓을 수 없는 함정이 "테스트가 시스템에 영향을 준다"는 점이다. 자가학습 시스템에 같은 테스트를 반복하면 그 테스트에 적응한 동작이 학습돼 장기 동작이 왜곡될 수 있다. 테스트 케이스 설계와 테스트 관리 모두에서 이 부분을 의식해야 한다.

[Ch8] 자율 AI 시스템 테스팅

자율 시스템은 "사람이 개입해야 할 시점"과 "개입하지 않아도 될 시점"을 스스로 결정해야 한다. 따라서 자율성 테스팅의 핵심은 그 결정을 강제로 유도할 조건을 만드는 것이다.

  • 제어 포기 테스트 — 운영 환경 변화가 자율성 범위를 넘어섰을 때 시스템이 사람의 개입을 제대로 요청하는가.
  • 시간 기반 제어 포기 — 지정된 시간이 지나도 결정을 내리지 못하면 사람에게 권한을 넘기는가.
  • 불필요한 개입 요청 — 자율적으로 처리해야 할 상황에서 오히려 사람에게 떠넘기지는 않는가.

이런 조건을 만들 때 운영 환경에 적용되는 경계값 분석이 도움이 된다. 자율성을 좌우하는 변수가 운영 환경에서 어떻게 분포하는지 정의한 뒤, 그 변수의 경계 부근에서 시나리오를 생성한다.

실무 관점 자율주행차의 ODD(Operational Design Domain) 경계가 정확히 이 개념이다. ODD를 벗어나는 입력을 의도적으로 만들어 시스템이 정상적으로 통제권을 넘기는지를 본다.

[Ch8] 알고리즘·샘플·부적절한 편향성 테스팅

Ch2에서 정의한 세 가지 편향성(알고리즘·샘플·부적절한)을 어떻게 검증하는가가 이 절의 핵심이다. 부적절한 편향성을 제거하기 위해 의도적인 긍정적 편향성을 주입하는 조치까지 포함될 수 있다.

독립적인 데이터 세트로 테스트하면 편향성을 식별할 수 있는 경우가 많다. 하지만 ML 알고리즘은 관련 없어 보이는 특성들의 조합으로도 편향을 만들 수 있어 모든 원인을 찾기는 어렵다.

편향성 테스팅 활동

  • 알고리즘 편향성 식별 — 훈련·검증·튜닝 활동 중에 분석한다.
  • 샘플 편향성 식별 — 훈련 데이터 출처와 획득 프로세스를 리뷰한다.
  • 전처리 단계 리뷰 — 전처리 과정에서 샘플 편향성이 새로 들어왔는지 확인한다.
  • 입력 변화의 출력 영향 측정 — 시스템 입력 변화가 출력에 미치는 영향을 측정하고, 특정 사람/객체 집단을 기준으로 결과를 조사한다. LIME 방법(8.6절)과 유사한 접근이며, 출시 전 테스트뿐 아니라 생산 환경에서도 수행할 수 있다.
  • 숨겨진 변수 분석 — 입력으로 명시되지 않은 인구통계학 정보 같은 속성을 결과와 연관시켜 본다. 알고리즘이 "숨겨진" 변수를 추론하고 있을 수 있다.
주의 — "입력에 없으면 안전하다"는 환상 성별·인종 같은 민감 변수를 모델 입력에서 빼도 편향이 사라지지 않는 경우가 많다. 이름·우편번호·구매 패턴 같은 다른 특성에서 그 정보가 새어 나오기 때문이다.

[Ch8] 확률적·비결정적 시스템 테스팅의 어려움

대부분의 확률적 시스템은 비결정적이기도 하다. 이런 속성을 가진 AI 시스템 테스팅의 어려움은 셋이다.

  1. 여러 유효한 결과 — 사전 조건과 입력이 같아도 다양한 결과가 나올 수 있다. 기대 결과 정의가 어려워지고, 다음 활동들이 모두 영향을 받는다.
    • 확인 테스팅 재사용
    • 회귀 테스팅 재사용
    • 재현성이 중요한 경우
    • 테스트 자동화
  2. 합리적 판단이 필요 — 특정값으로 기대 결과를 정하기 어렵기 때문에 테스터가 더 깊은 도메인 지식을 가져야 한다. "실제 결과가 최적 해답의 3% 이내인가?" 같은 허용 오차 기반 기대 결과가 필요하다.
  3. 다중 실행 필요 — 통계적으로 유효한 결과를 얻으려면 같은 테스트를 여러 번 돌려야 한다.

[Ch8] 복잡한 AI 시스템 테스팅의 어려움

AI 시스템은 사람이 수행하기 너무 복잡한 작업을 구현하는 데 자주 쓰인다. 이때 테스터는 평소처럼 기대 결과를 정할 수 없고, 곧장 테스트 오라클 문제로 이어진다.

예를 들어 대용량 데이터에서 사람이 찾을 수 없는 패턴을 발견하는 시스템을 생각해 보자. 이런 시스템은 본질적으로 사람이 "원하는 동작"을 정확히 정의하기 어렵다. 또 AI 시스템의 내부 구조가 소프트웨어로 생성된 결과여서 사람이 이해하기 너무 복잡할 때도 같은 문제가 나타난다. 블랙박스로만 테스트할 수 있는 상황으로 귀결되는 것이다.

복잡성은 시스템이 확률적·비결정적일 때 더 커진다. 또한 안면 인식처럼 여러 AI 컴포넌트가 결합된 시스템에서는 컴포넌트 간 상호작용이 복잡해서 모든 리스크를 파악하기가 거의 불가능해진다. (예: "얼굴 위치 찾기" 모델 + "누구인지 식별" 모델)

[Ch8] 투명성·해석 가능성·설명 가능성 테스팅

세 용어의 구분

용어의미누구를 위한 것인가
투명성(Transparency)훈련 데이터 출처·라벨링·컴포넌트 설계 등 시스템 구현 정보가 공개되는가주로 개발자·테스터
해석 가능성(Interpretability)근간 기술이 어떻게 동작하는지를 얼마나 이해할 수 있는가이해관계자별로 다름
설명 가능성(Explainability)특정 입력에 대해 왜 그런 출력이 나왔는가를 설명할 수 있는가최종 사용자·규제기관

투명성은 "데이터·알고리즘에 대한 문서화된 정보를 실제 구현과 비교"해 테스트할 수 있다. 둘이 얼마나 일치하는지를 보는 것이다.

ML은 전통 시스템보다 특정 입력과 출력 사이 연결을 설명하기가 어렵다. 모델 자체가 코드로 생성되고 사람이 같은 문제를 푸는 방식과 다르기 때문이다. 모델 종류에 따라 설명 가능성 수준이 다르므로 요구사항에 맞춰 모델을 선택해야 한다.

섭동 기법과 LIME

설명 가능성을 정량화하는 한 가지 방법이 테스트 데이터에 섭동(perturbations)을 적용하고 모델의 반응을 동적으로 측정하는 것이다. 대표적인 도구가 LIME (Local Interpretable Model-Agnostic Explanations)이다.

  • 모델 독립적 — 특정 알고리즘에 종속되지 않는다.
  • 섭동 주입 + 출력 분석 — 입력을 살짝 바꿔가며 출력 변화를 추적해 "어떤 입력 특성이 어떤 출력에 영향을 미치는가"를 보여준다.
  • 한계 — "결정적 이유"가 아니라 "출력이 나오게 된 이유"를 제공한다. 모든 알고리즘에 적용되지는 않는다.

탐색적 테스팅도 모델 입출력 관계를 더 잘 이해하는 데 쓸 수 있다.

해석 가능성 측정

이해관계자마다 역량과 요구가 다르기 때문에 해석 가능성·설명 가능성의 이해 수준 측정 자체가 어렵다. 실무에서는 일반적으로 사용자 설문 조사나 설문지 형태로 수행한다.

[Ch8] AI 시스템의 테스트 오라클 문제

AI 시스템 테스팅의 가장 큰 문제는 "기대 결과를 어떻게 정할 것인가"다. 테스트 오라클은 기대 결과를 정하는 데 쓰는 출처이고, 기대 결과 정의가 어려운 상황을 테스트 오라클 문제(test oracle problem)라고 한다.

오라클 ≠ 실제 값(ground truth) 실제 값은 "AI가 예측하려고 하는 진짜 답"이다. 오라클은 반드시 기대값을 제공할 필요는 없고, 시스템이 올바르게 동작하는지를 판단하는 메커니즘만 제공해도 된다. 둘은 다르다.

AI 시스템은 진화하고 자가학습하기 때문에 기능적 기대 결과를 자주 업데이트해야 한다. 또한 시스템 정확성 판단이 본질적으로 주관적인 경우가 많다(예: 시리·알렉사 같은 가상 비서).

오라클 문제 완화 전략

  • 범위·허용 오차로 기대 결과 정의 — 자율주행차 정지 지점을 "특정 지점에서 최대 N 미터 이내" 같은 방식으로 정한다.
  • 전문가 시스템 — 전문가와 논의해 기대 결과를 정한다. 단, 전문가도 틀릴 수 있다.
    • 전문가 역량은 시스템이 대체하려는 인간 전문가 이상이어야 한다.
    • 전문가들 사이 의견이 일치하지 않을 수 있다.
    • 전문가가 자동화에 반감을 가질 수 있다 → 이중 블라인드로 평가한다.
    • 인간은 "잘 모르겠지만…" 같은 머뭇거림이 가능하지만 AI는 그렇지 못한 경우가 많다. 비교 시 이 점을 감안한다.
  • 오라클 문제 완화 기법 — A/B 테스팅(9.4절), 백투백 테스팅(9.3절), 변성 테스팅(9.5절). 자세한 내용은 Ch9에서 다룬다.

[Ch8] 테스트 목적과 인수 기준

AI 시스템 테스트 목적과 인수 기준은 식별된 제품 리스크에 기반한다. 리스크는 보통 필요한 품질 특성 분석에서 나온다. 전통적인 ISO/IEC 25010 품질 특성(기능적 적합성·수행 효율성·호환성·유용성·신뢰도·보안·유지 가능성·이식성) 외에 다음 AI 특유 특성을 추가로 고려한다.

특성인수 기준 예시
적응성환경 변화에 적응하면서 올바른 동작과 비기능 요구사항을 유지하는가. 적응 시간과 자원 사용량은 어떤가. 자동화 회귀 테스팅으로 검증.
유연성초기 명세를 벗어난 상황에 어떻게 대처하는가. 자체 변경 시간·자원은 어떤가.
진화자체 경험을 통해 얼마나 잘 학습하는가. 데이터 프로파일 변화(컨셉 드리프트)에 어떻게 대처하는가.
자율성완전 자율 운영 범위를 강제로 벗어났을 때의 반응. 자율이어야 할 때 인간 개입을 요청하도록 "설득"되는가.
투명성·해석·설명알고리즘과 데이터 세트 접근 용이성 점검. 사용자 또는 유사 배경 인물에게 질문해 해석·설명 가능성 확인.
부적절한 편향으로부터의 자유편향 없는 독립 테스트 스위트 활용, 전문 검토자 활용. 외부 데이터(예: 인구 조사)와 결과 비교로 외부 타당성 테스팅.
윤리"신뢰할 수 있는 AI 윤리 지침" 등의 체크리스트로 점검.
확률적·비결정적정확한 인수 기준 적용 불가. 동일 테스트에 조금씩 다른 결과를 허용한다.
부작용해가 될 수 있는 부작용을 식별하고 그것이 나타날 수 있는 테스트를 만든다.
보상 해킹지능형 에이전트와 다른 방법으로 성공을 측정하는 독립 테스트로 식별.
안전성가상 테스트 환경(10.2절) 활용. 시스템이 스스로에게 해를 입히도록 강제하는 시도 포함.
K4 학습 목표 AI-8.8.1은 K4 수준이라 "주어진 AI 시스템에 적절한 테스트 목적·인수 기준을 선택"하는 능력이 요구된다. 시나리오에서 시스템의 특성(예: "자가학습 + 안전성 중요")을 보고 위 표의 어떤 행을 골라야 할지 판단하는 연습이 필요하다.

연습 문제

Q1. AI 시스템의 명세가 어려운 이유로 가장 적절하지 않은 것은?
  • AI 시스템 개발은 데이터에서 시작해 예측을 도출하는 탐색적 성격이 있다
  • 확률적 특성으로 인해 허용 오차가 필요한 경우가 많다
  • 적응성·자율성 같은 새로운 품질 특성을 정의하기 어렵다
  • AI 시스템은 결정적 시스템이므로 입력별 출력이 명확히 정해진다
정답: D. AI 시스템은 대부분 확률적·비결정적이라 입력별 출력을 미리 못 박기 어렵다. 이게 명세의 어려움 중 하나다.
Q2. AI 시스템 테스트 레벨에서 기존 시스템에 비해 새로 추가되는 두 가지는?
  • 입력 데이터 테스팅, ML 모델 테스팅
  • 컴포넌트 테스팅, 통합 테스팅
  • 시스템 테스팅, 인수 테스팅
  • 리그레션 테스팅, 확인 테스팅
정답: A. 7.2절 핵심 포인트. 입력 데이터와 ML 모델 두 레벨이 추가된다.
Q3. 컨셉 드리프트에 대한 설명으로 옳은 것은?
  • 훈련 시점부터 모델이 가지고 있던 알고리즘적 결함이다
  • 운영 환경 변화로 인해 모델 예측의 정확도와 유용성이 점점 떨어지는 현상이다
  • 적대적 공격의 한 형태로 입력에 노이즈를 주입한다
  • 훈련 데이터에 잘못된 라벨을 의도적으로 섞는 공격이다
정답: B. 시간이 지나면서 환경이 바뀌어 모델이 따라가지 못하는 현상. A/B 테스팅과 재훈련이 일반적 완화책이다.
Q4. 자동화 편향성(automation bias)에 대한 설명으로 옳은 것 두 개를 고르시오.
  • 인간이 AI 시스템의 권고를 다른 출처보다 선호하는 경향이다
  • AI 알고리즘 자체가 편향된 결과를 내는 것을 말한다
  • 훈련 데이터의 표본이 모집단을 대표하지 못해 발생한다
  • 인간이 AI 시스템을 충분히 모니터링하지 않아 오류를 놓치는 경우도 포함된다
정답: A, D. 자동화 편향성은 인간 쪽의 인지 편향이다. B는 알고리즘 편향성, C는 샘플 편향성이다.
Q5. 테스트 오라클 문제를 완화하는 데 적합한 기법으로 묶인 것은?
  • 경계값 분석, 동등 분할, 결정 테이블

  • 상태 전이 테스팅, 사용 사례 테스팅
  • 구문 커버리지, 결정 커버리지, MC/DC
