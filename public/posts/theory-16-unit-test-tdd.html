테스트는 왜 필요한가

코드는 한 번 쓰고 끝나지 않는다. 기능이 추가되고, 버그가 고쳐지고, 구조가 다듬어진다. 문제는 그 모든 변경이 이미 잘 돌아가던 코드를 망가뜨릴 수 있다는 점이다. 한 곳을 고쳤더니 전혀 상관없어 보이던 다른 곳이 깨지는 일 — 이것이 회귀(regression)다.

자동화된 테스트는 이 회귀를 막는 안전망이다. 테스트가 있으면 코드를 바꾼 뒤 테스트를 돌려 "내가 무언가 깨뜨렸는가?"를 몇 초 만에 확인할 수 있다. 테스트가 없으면 그 확인을 사람이 손으로, 매번, 전체에 대해 해야 한다. 현실적으로 불가능하므로 결국 아무도 확인하지 않게 된다.

리팩토링의 전제

15편에서 리팩토링은 "겉보기 동작을 바꾸지 않으면서 내부 구조를 개선하는 것"이라고 정의했다. 여기서 "겉보기 동작을 바꾸지 않았다"를 무엇으로 보장하는가? 바로 테스트다. 테스트 없는 리팩토링은 리팩토링이 아니라 그냥 코드를 건드리는 것이다. 결과가 같다는 보장이 없기 때문이다.

테스트는 또한 살아있는 문서이기도 하다. 잘 쓰인 테스트는 "이 함수는 이런 입력에 이렇게 동작한다"를 코드로 보여준다. 주석과 달리 테스트는 거짓말을 하지 못한다 — 동작이 바뀌면 테스트가 깨지므로, 항상 현재 코드와 동기화되어 있다.

테스트는 비용이 아니라 속도다 "테스트 짤 시간에 기능을 더 만들겠다"는 흔한 생각이다. 하지만 테스트가 없으면 변경할 때마다 두려움 때문에 느려진다. 테스트는 지금 시간을 쓰고 나중에 매 변경마다 시간을 돌려받는 투자다. 코드 수명이 길수록 회수율이 높다.

테스트 피라미드

테스트에도 종류가 있고, 각 종류는 검증하는 범위와 비용이 다르다. 테스트 피라미드(test pyramid)는 어떤 테스트를 얼마나 가져가야 하는지에 대한 지침이다. Mike Cohn이 제안한 이 모델은 아래쪽일수록 많이, 위쪽일수록 적게 두라고 말한다.

테스트 피라미드 — 단위 테스트가 토대를 이루고, E2E 테스트는 얇게 얹는다
계층검증 범위속도개수역할
E2E 테스트전체 시스템을 사용자 관점에서느림 (초~분)적게핵심 시나리오가 끝까지 동작하는지 확인
통합 테스트여러 모듈이 함께 동작중간중간모듈 간 연결·인터페이스 검증
단위 테스트함수·클래스 하나를 격리빠름 (밀리초)많이로직의 정확성을 촘촘하게 검증

피라미드가 뒤집히면 — 즉 E2E 테스트는 많은데 단위 테스트가 적으면 — 테스트 묶음이 느리고 깨지기 쉬워진다. E2E 테스트는 실패했을 때 "어디가 문제인지" 짚어주지 못한다. 반면 단위 테스트는 실패하는 순간 범인을 정확히 가리킨다. 그래서 토대는 단위 테스트여야 한다.

단위 테스트란

단위 테스트(unit test)는 하나의 "단위" — 보통 함수 하나 또는 클래스 하나 — 를 다른 것들로부터 격리해 검증하는 테스트다. 핵심 단어는 격리다. 테스트하려는 대상만 동작하고, 그것이 의존하는 파일 시스템·네트워크·데이터베이스·카메라 같은 것은 개입하지 않는다.

빠르고 결정적이어야 한다

단위 테스트는 두 가지 성질을 반드시 가져야 한다. 첫째, 빠르다. 수백 수천 개를 몇 초 안에 다 돌릴 수 있어야 개발 중 수시로 실행한다. 한 번 돌리는 데 몇 분씩 걸리면 아무도 돌리지 않는다. 둘째, 결정적(deterministic)이다. 같은 코드에 대해 항상 같은 결과를 낸다. 어제는 통과하고 오늘은 실패하는 테스트는 신뢰를 잃고, 신뢰를 잃은 테스트는 무시당한다.

// 테스트 대상 — 순수한 계산 로직, 외부 의존성이 없다
namespace ImagingLib::Core
{
    // Clamp a value into the inclusive range [low, high].
    int Clamp(int value, int low, int high)
    {
        if (value < low)
        {
            return low;
        }
        if (value > high)
        {
            return high;
        }
        return value;
    }
}

위 Clamp는 단위 테스트하기에 이상적이다. 입력만 주면 출력이 결정되고, 파일도 카메라도 시간도 필요 없다. 이런 함수는 테스트를 짜기 쉬울 뿐 아니라, 테스트하기 쉽다는 사실 자체가 잘 설계되었다는 신호다.

좋은 단위 테스트의 조건

테스트를 짠다고 다 좋은 테스트는 아니다. 좋은 단위 테스트가 갖춰야 할 성질을 머리글자로 모은 것이 FIRST 원칙이다.

머리글자의미설명
Fast빠르다밀리초 단위로 끝난다. 느리면 자주 안 돌린다.
Independent독립적이다테스트끼리 순서·상태를 공유하지 않는다. 하나만 따로 돌려도 통과한다.
Repeatable반복 가능하다어떤 환경에서 몇 번을 돌려도 같은 결과가 나온다.
Self-validating스스로 검증한다통과/실패를 테스트가 자동 판정한다. 사람이 로그를 눈으로 볼 필요가 없다.
Timely적시에 작성한다대상 코드와 함께, 혹은 그 직전(TDD)에 작성한다. "나중에"는 오지 않는다.

AAA 패턴 — Arrange · Act · Assert

테스트 본문은 세 단계로 구성하면 읽기 쉽다. Arrange(준비)에서 입력과 객체를 마련하고, Act(실행)에서 테스트 대상을 한 번 호출하고, Assert(검증)에서 결과를 확인한다. 이 세 구역을 시각적으로 분리하면 테스트가 "무엇을, 어떻게, 어떤 결과로" 검증하는지 한눈에 들어온다.

TEST(ClampTest, ValueAboveRangeIsClampedToHigh)
{
    // Arrange — 입력 준비
    int value = 150;
    int low = 0;
    int high = 100;

    // Act — 테스트 대상 호출 (한 번만)
    int result = ImagingLib::Core::Clamp(value, low, high);

    // Assert — 결과 검증
    EXPECT_EQ(result, 100);
}

한 가지 더 — 좋은 단위 테스트는 한 번에 하나의 동작만 검증한다. 하나의 TEST 안에서 여러 시나리오를 한꺼번에 확인하면, 실패했을 때 무엇이 깨졌는지 모호해진다. 테스트 이름이 곧 "검증하는 동작의 문장"이 되도록 잘게 나눈다.

테스트 더블

단위 테스트의 핵심은 격리인데, 현실의 클래스는 다른 것에 의존한다. 검사 로직 클래스가 카메라에서 이미지를 받아온다면, 단위 테스트를 돌릴 때마다 진짜 카메라가 필요할까? 그러면 빠르지도 결정적이지도 않다. 이때 진짜 의존성을 대신하는 가짜 객체가 테스트 더블(test double)이다. 영화의 스턴트 더블에서 온 이름이다.

Gerard Meszaros가 정리한 다섯 종류는 "얼마나 똑똑하게 행동하느냐"로 구분된다.

종류역할행동쓰는 상황
Dummy자리만 채움아무것도 안 함. 호출되지 않음매개변수 목록을 채워야 하지만 실제로 안 쓰일 때
Stub정해진 답을 반환호출되면 미리 정한 값을 돌려줌대상이 의존성의 반환값을 필요로 할 때
Spy호출을 기록Stub처럼 동작하면서 "몇 번, 어떤 인자로 불렸는지" 기록호출 사실을 나중에 검증하고 싶을 때
Mock기대를 검증"이렇게 불려야 한다"는 기대를 미리 설정하고 자동 검증대상이 의존성과 상호작용하는 방식을 검증할 때
Fake가벼운 실제 구현진짜로 동작하지만 단순화됨 (예: 인메모리 DB)실제 구현이 너무 무겁지만 진짜 동작이 필요할 때

DIP가 테스트를 쉽게 만든다

테스트 더블을 끼워 넣으려면, 대상 코드가 구체 클래스가 아니라 인터페이스에 의존해야 한다. 이것이 바로 3편에서 다룬 의존성 역전 원칙(DIP)이다. 검사 로직이 VieworksCamera를 직접 들고 있으면 가짜로 바꿀 수 없지만, IImageSource 인터페이스에 의존하면 테스트에서 가짜 구현을 주입할 수 있다.

// 인터페이스에 의존 — 덕분에 테스트 더블을 주입할 수 있다
class IImageSource
{
public:
    virtual ~IImageSource() = default;
    virtual ErrorCode Grab(Image& outImage) = 0;
};

// 테스트용 Stub — 항상 정해진 이미지를 돌려준다
class StubImageSource : public IImageSource
{
public:
    explicit StubImageSource(Image fixedImage)
        : m_fixedImage(std::move(fixedImage))
    {
    }

    ErrorCode Grab(Image& outImage) override
    {
        outImage = m_fixedImage;   // 카메라 없이 정해진 결과를 반환
        return ErrorCode::Ok;
    }

private:
    Image m_fixedImage;
};

DIP를 지키지 않은 코드는 테스트하기 어렵고, 테스트하기 어려운 코드는 결합도가 높다는 신호다. 그래서 "테스트하기 쉬운가?"는 설계 품질을 가늠하는 좋은 리트머스 시험지다.

Mock을 남용하면 테스트가 구현에 묶인다 Mock으로 "이 메서드가 정확히 이런 순서로 불려야 한다"까지 검증하면, 내부 구현을 조금만 바꿔도 테스트가 깨진다. 가능하면 상태(결과값)를 검증하고, 꼭 필요할 때만 상호작용(호출 여부)을 검증한다. Stub과 Fake가 Mock보다 덜 깨진다.

GoogleTest로 작성하기

C++ 진영에서 가장 널리 쓰이는 단위 테스트 프레임워크가 GoogleTest다. 매크로 기반으로 테스트를 선언하고, 단언(assertion)으로 결과를 검증한다.

TEST 매크로와 단언

가장 기본은 TEST(테스트묶음이름, 테스트이름) 매크로다. 단언에는 두 계열이 있다 — ASSERT_*는 실패하면 그 테스트를 즉시 중단하고, EXPECT_*는 실패를 기록하되 테스트를 계속 진행한다.

#include <gtest/gtest.h>
#include "ImagingLib/Core/MathUtils.h"

// ASSERT — 실패하면 즉시 중단 (이후 코드가 의미 없을 때)
TEST(ClampTest, ValueWithinRangeIsUnchanged)
{
    int result = ImagingLib::Core::Clamp(50, 0, 100);
    ASSERT_EQ(result, 50);
}

// EXPECT — 실패해도 계속 진행 (여러 단언을 한 번에 보고 싶을 때)
TEST(ClampTest, BoundaryValuesAreHandled)
{
    EXPECT_EQ(ImagingLib::Core::Clamp(0, 0, 100), 0);     // 하한 경계
    EXPECT_EQ(ImagingLib::Core::Clamp(100, 0, 100), 100); // 상한 경계
    EXPECT_EQ(ImagingLib::Core::Clamp(-5, 0, 100), 0);    // 하한 미만
    EXPECT_EQ(ImagingLib::Core::Clamp(150, 0, 100), 100); // 상한 초과
}

픽스처 — TEST_F

여러 테스트가 같은 준비 과정을 공유한다면 픽스처(fixture)를 쓴다. ::testing::Test를 상속한 클래스를 정의하고 SetUp()에 공통 준비를, TearDown()에 정리를 둔다. TEST_F는 그 픽스처를 사용하는 테스트다. 중요한 점은 GoogleTest가 테스트마다 픽스처를 새로 만든다는 것 — FIRST의 Independent가 자동으로 지켜진다.

// 검사 로직을 테스트하기 위한 픽스처
class DefectDetectorTest : public ::testing::Test
{
protected:
    void SetUp() override
    {
        // 매 테스트 전에 새 인스턴스를 준비한다
        m_detector = std::make_unique<DefectDetector>();
    }

    std::unique_ptr<DefectDetector> m_detector;
};

TEST_F(DefectDetectorTest, EmptyImageReturnsInvalidArgument)
{
    Image emptyImage;   // null 이미지

    ErrorCode ec = m_detector->Detect(emptyImage);

    EXPECT_EQ(ec, ErrorCode::InvalidArgument);   // 경계 조건 검증
}

TEST_F(DefectDetectorTest, CleanImageReportsNoDefect)
{
    Image cleanImage = makeUniformImage(640, 480, 128);   // 결함 없는 입력

    ErrorCode ec = m_detector->Detect(cleanImage);

    ASSERT_EQ(ec, ErrorCode::Ok);
    EXPECT_EQ(m_detector->GetDefectCount(), 0);
}
GoogleTest 외의 선택지 C++에는 Catch2, doctest 같은 헤더 온리 프레임워크도 있다. Mock 기능은 GoogleTest와 함께 제공되는 GoogleMock이 담당한다. 이 프로젝트는 CLAUDE.md 기준 GoogleTest를 표준으로 삼는다.

TDD — 테스트 주도 개발

TDD(Test-Driven Development)는 Kent Beck이 정리한 개발 방식으로, 한 문장으로 줄이면 "테스트를 먼저 쓰고, 그 다음에 코드를 쓴다"이다. 구현이 끝난 뒤 테스트를 붙이는 것이 아니라, 테스트가 구현을 이끈다(drive). 이를 위해 Red-Green-Refactor라는 짧은 사이클을 반복한다.

Red → Green → Refactor — TDD의 핵심 사이클

세 단계를 코드로

"이미지의 평균 밝기를 구하는 함수"를 TDD로 만든다고 하자.

① RED — 실패하는 테스트 먼저. 함수는 아직 없다. 원하는 동작을 테스트로 먼저 적는다. 컴파일조차 안 되거나 실패한다 — 그게 정상이다.

// RED — ComputeAverageBrightness는 아직 존재하지 않는다
TEST(BrightnessTest, UniformImageReturnsItsPixelValue)
{
    Image image = makeUniformImage(10, 10, 200);   // 모든 픽셀이 200

    double avg = ComputeAverageBrightness(image);

    EXPECT_DOUBLE_EQ(avg, 200.0);
}

② GREEN — 통과시키는 최소 코드. 우아함은 잠시 잊는다. 테스트를 초록색으로 만드는 가장 단순한 구현이면 충분하다.

// GREEN — 일단 테스트를 통과시킨다
double ComputeAverageBrightness(const Image& image)
{
    long long sum = 0;
    int count = image.GetWidth() * image.GetHeight();
    for (int y = 0; y < image.GetHeight(); ++y)
    {
        for (int x = 0; x < image.GetWidth(); ++x)
        {
            sum += image.GetPixel(x, y);
        }
    }
    return static_cast<double>(sum) / count;
}

③ REFACTOR — 테스트를 초록으로 유지하며 정리. 이제 안전망이 있으니 구조를 다듬는다. 예를 들어 빈 이미지에서 0으로 나누는 문제를 발견하면 — 먼저 그 경우를 검증하는 RED 테스트를 추가하고, 다시 GREEN으로 만든다. 사이클이 계속 돈다.

// REFACTOR — 경계 조건을 추가하고(새 RED 테스트와 함께) 정리한다
double ComputeAverageBrightness(const Image& image)
{
    if (image.IsEmpty())
    {
        return 0.0;   // 0으로 나누기 방지
    }

    long long sum = 0;
    const int pixelCount = image.GetWidth() * image.GetHeight();
    for (int y = 0; y < image.GetHeight(); ++y)
    {
        for (int x = 0; x < image.GetWidth(); ++x)
        {
            sum += image.GetPixel(x, y);
        }
    }
    return static_cast<double>(sum) / pixelCount;
}

TDD의 효과와 오해

TDD의 진짜 효과는 "테스트가 생긴다"는 부산물에 있지 않다. 더 중요한 것은 설계가 개선된다는 점이다. 테스트를 먼저 쓰려면 "이 함수를 어떻게 호출하지?"를 먼저 고민하게 된다. 즉 구현자가 아니라 사용자 관점에서 인터페이스를 설계하게 된다. 또한 테스트하기 어려운 코드는 RED 단계에서 바로 드러나므로, 강한 결합이 자연스럽게 억제된다.

또 하나의 효과는 과한 구현의 방지다. "통과하는 최소 코드"라는 규칙은, 지금 필요하지도 않은 기능을 미리 만드는 습관(9편의 YAGNI 위반)을 막는다. 테스트가 요구하지 않으면 코드를 쓰지 않는다.

흔한 오해

"테스트를 먼저 쓰면 느리다" — 코드 작성 시점만 보면 그렇다. 하지만 디버깅 시간, 회귀 추적 시간, 변경할 때의 두려움까지 합치면 전체 개발 속도는 대체로 빨라진다. 느려 보이는 것은 비용이 앞당겨졌기 때문이지 늘어났기 때문이 아니다.

"TDD는 만능이다" — 아니다. 탐색적인 프로토타이핑, UI 레이아웃 조정, 어떤 알고리즘이 맞는지 아직 모르는 연구성 코드에서는 TDD가 어색하다. 또 TDD를 한다고 통합 테스트나 E2E 테스트가 필요 없어지지도 않는다. TDD는 강력한 도구이지 종교가 아니다 — 적합한 곳에 쓴다.

코드 커버리지

코드 커버리지(code coverage)는 테스트가 실행한 코드의 비율을 수치로 보여주는 지표다. 대표적으로 두 가지가 있다.

  • 라인 커버리지(line coverage) — 전체 코드 라인 중 테스트 중 실행된 라인의 비율
  • 브랜치 커버리지(branch coverage) — 모든 분기(if의 true/false 양쪽)가 실행되었는지의 비율. 라인 커버리지보다 엄격하다

커버리지는 테스트되지 않은 영역을 찾는 데 유용하다. 커버리지 0%인 함수는 확실히 검증되지 않았다. 하지만 반대 방향으로는 함정이 있다.

높은 커버리지가 좋은 테스트를 뜻하지는 않는다 커버리지는 "이 라인이 실행되었다"만 말할 뿐, "이 라인이 옳게 동작하는지 검증되었다"는 말하지 않는다. 단언(EXPECT/ASSERT)이 하나도 없는 테스트도 커버리지 100%를 찍을 수 있다. 커버리지는 목표가 아니라 참고 지표다. 숫자를 채우려고 의미 없는 테스트를 양산하면, 느리고 깨지기 쉬운 테스트만 늘어난다.

실무에서는 "커버리지 80%"처럼 숫자를 강제하기보다, "핵심 로직과 경계 조건은 반드시 커버한다"는 질적 기준이 더 건강하다. 커버리지 리포트는 빈 곳을 보는 지도로 쓰고, 점수표로 쓰지 않는다.

무엇을 테스트하고 무엇을 안 하나

모든 코드를 똑같이 테스트할 필요는 없다. 테스트도 유지보수 비용이 드는 코드이므로, 가치가 높은 곳에 집중한다.

테스트해야 하는 것

  • 핵심 비즈니스 로직 — 계산, 변환, 판정. 틀리면 제품이 틀린다
  • 경계 조건(boundary) — 0, 빈 입력, 최댓값, 최솟값, 음수. 버그는 경계에 산다
  • 예외·에러 경로 — 잘못된 입력에 ErrorCode를 제대로 반환하는가
  • 과거에 버그가 났던 곳 — 회귀 테스트로 못 박아 둔다 (한 번 깨진 곳은 또 깨진다)

보통 테스트하지 않는 것

  • 자명한 getter/setter — 단순 대입/반환만 하는 코드는 테스트가 동어반복이다
  • 외부 라이브러리 자체 — OpenCV의 cv::GaussianBlur가 맞는지는 OpenCV가 보증한다. 우리는 그것을 쓰는 우리 코드를 테스트한다
  • 컴파일러가 보장하는 것 — 타입 검사로 이미 막히는 것을 테스트할 필요는 없다
  • 너무 사소해서 깨질 일 없는 것 — 테스트 작성·유지 비용이 가치를 넘으면 짐이 된다

기준은 단순하다. "이게 틀렸을 때 누가, 얼마나 다치는가?"와 "이게 깨질 가능성이 있는가?"를 함께 본다. 둘 다 높으면 반드시 테스트하고, 둘 다 낮으면 굳이 하지 않는다.

산업 SW 관점

산업용 이미징 SDK에서 단위 테스트는 특히 가치가 크다. 검사 알고리즘이 미묘하게 바뀌면 — 예를 들어 임계값 계산을 리팩토링했더니 결함 검출률이 떨어지면 — 그 영향이 현장 불량으로 직결되기 때문이다. 사람 눈으로는 잡기 어려운 회귀를, 테스트는 즉시 잡는다.

이미지 처리 함수의 단위 테스트

이미지 처리 함수는 입력을 합성 이미지로 만들어 결정적으로 테스트할 수 있다. 실제 카메라 영상 대신, 알려진 패턴(균일 이미지, 한 점만 밝은 이미지, 명확한 엣지가 있는 이미지)을 코드로 생성하면 결과를 정확히 예측할 수 있다.

// 합성 입력으로 임계화 함수를 결정적으로 테스트한다
class ThresholdTest : public ::testing::Test
{
protected:
    void SetUp() override
    {
        // 왼쪽 절반은 50, 오른쪽 절반은 200인 이미지
        m_image = makeHalfSplitImage(100, 100, 50, 200);
    }

    Image m_image;
};

TEST_F(ThresholdTest, ThresholdAt128SplitsImageInHalf)
{
    Image binary;

    ErrorCode ec = ApplyThreshold(m_image, binary, 128);

    ASSERT_EQ(ec, ErrorCode::Ok);
    EXPECT_EQ(binary.GetPixel(25, 50), 0);     // 왼쪽(50) -> 0
    EXPECT_EQ(binary.GetPixel(75, 50), 255);   // 오른쪽(200) -> 255
}

TEST_F(ThresholdTest, NullImageReturnsInvalidArgument)
{
    Image emptyInput;
    Image binary;

    ErrorCode ec = ApplyThreshold(emptyInput, binary, 128);

    EXPECT_EQ(ec, ErrorCode::InvalidArgument);   // null 입력 방어
}

회귀 테스트와 CI

한 발 더 나아가, 검사 알고리즘에는 골든 이미지(golden image) 회귀 테스트가 유용하다. 결함이 있는/없는 샘플 이미지 묶음과 정답 결과를 미리 저장해 두고, 알고리즘을 바꿀 때마다 전체를 돌려 검출 결과가 흔들리지 않는지 확인한다. 이것은 엄밀히는 단위 테스트보다 통합 테스트에 가깝지만, 같은 GoogleTest 위에서 운영할 수 있다.

그리고 이 모든 테스트는 CI(지속적 통합)에서 자동으로 돌아야 의미가 있다. CLAUDE.md의 GitLab CI/CD 계획에서 Phase 2가 "빌드 + GoogleTest 자동 실행"인 이유다. 누군가 코드를 푸시할 때마다 테스트가 자동 실행되면, 깨진 코드가 main 브랜치에 들어오는 것을 막을 수 있다. 테스트는 로컬에서 가끔 돌리는 것이 아니라 파이프라인에 박혀 항상 돌아야 안전망 역할을 한다.

다른 시리즈와 연결 합성 이미지 생성과 임계화·블롭 분석 같은 알고리즘 자체는 CV 시리즈에서, 검사 파이프라인 전체 구성은 스마트 공장 시리즈에서 다룬다. 이 글은 "그 코드를 어떻게 검증된 상태로 유지하는가"에 초점을 둔다.

흔한 함정

함정 1 — 테스트가 구현에 너무 결합된다

테스트가 "무엇을 하는가(동작)"가 아니라 "어떻게 하는가(구현)"를 검증하면, 동작이 그대로인데도 리팩토링할 때마다 테스트가 깨진다. 내부 메서드 호출 순서·private 헬퍼의 존재에 의존하는 테스트가 대표적이다. 테스트는 공개 인터페이스의 관찰 가능한 동작만 검증해야 리팩토링의 안전망으로 기능한다.

함정 2 — 느린 테스트

단위 테스트인데 실제 파일을 읽고, 네트워크를 타고, sleep이 들어가 있으면 전체 묶음이 느려진다. 느린 테스트는 점점 덜 돌려지다가, 결국 아무도 돌리지 않는다. 외부 의존성은 테스트 더블로 끊고, 시간 의존성은 주입 가능한 시계로 바꾼다.

함정 3 — 깨진 테스트 방치

"저 테스트는 원래 빨간색이야, 무시해"가 시작되는 순간 테스트 묶음 전체가 죽는다. 빨간 테스트 하나를 용인하면 두 번째 빨간 테스트도 묻혀버리고, 결국 진짜 회귀를 알려주는 신호와 노이즈를 구분할 수 없게 된다. 테스트는 항상 초록이거나, 즉시 고쳐지거나, 명시적으로 삭제되어야 한다. 회색 지대는 없다.

함정 4 — 커버리지 숫자만 추구

커버리지 목표를 강제하면, 단언 없는 테스트나 자명한 getter 테스트로 숫자만 채우는 일이 벌어진다. 숫자는 올라가지만 실제 안전망은 한 칸도 늘지 않는다. 커버리지는 빈 곳을 찾는 지도이지 평가 점수가 아니다.

함정 5 — 테스트 없이 "나중에"

"일단 기능부터 만들고 테스트는 나중에" — 그 나중은 거의 오지 않는다. 마감은 늘 다가오고, 이미 동작하는 코드에 테스트를 붙이는 일은 우선순위에서 밀린다. FIRST의 Timely가 말하는 바가 이것이다. 테스트는 대상 코드와 함께 작성될 때 가장 싸고, 시간이 지날수록 비싸진다.

시리즈 마무리

이 글로 16편짜리 프로그래밍 이론 시리즈를 닫는다. 돌아보면 흐름은 하나로 이어진다. 객체지향 설계(1~4편)에서 캡슐화·다형성과 SOLID·결합도/응집도로 "좋은 구조란 무엇인가"를 세웠고, 디자인 패턴(5~9편)에서 그 구조를 만드는 검증된 해법과 피해야 할 안티패턴을 익혔다. 자료구조와 알고리즘(10~13편)에서는 Big-O로 비용을 보는 눈과 문제를 푸는 도구를 갖췄고, 마지막 코드 품질(14~16편)에서 클린 코드·리팩토링·테스트로 "그 코드를 살아있게 유지하는 법"에 도달했다. 설계 → 패턴 → 알고리즘 → 품질 — 코드를 잘 짜는 것에서 잘 짠 상태를 지키는 것으로 옮겨온 셈이다.

이 이론들은 그 자체로 끝이 아니라 다른 시리즈의 토대다. C++ 시리즈는 이 원칙들을 인터페이스 설계·플러그인 아키텍처·RAII 같은 구체적 언어 기법으로 옮기고, OpenCV(CV) 시리즈와 AI 시리즈는 그 위에서 실제 이미지 처리·딥러닝 알고리즘을 다루며, 스마트 공장 시리즈는 그것들을 묶어 현장 검사 시스템으로 완성한다. 좋은 설계와 검증된 코드라는 토대가 없으면, 그 위에 쌓는 모든 것이 흔들린다. 이론 16편이 한 일은 그 토대를 다진 것이다. 여기서 시리즈를 닫는다.
