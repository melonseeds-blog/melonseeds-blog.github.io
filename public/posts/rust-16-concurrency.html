동시성 — thread·Send/Sync·Arc<Mutex>

2026-06-25 약 8분 분량 Rust 시리즈
이 편에서 배우는 것 thread::spawn으로 스레드를 만들고 join으로 기다리는 법, 그리고 클로저가 바깥 값을 가져갈 때 필요한 move를 다룬다. 이어서 어떤 타입이 스레드 사이를 오갈 수 있는지를 컴파일 타임에 가르는 Send/Sync 마커 트레이트를 본다. 상태를 여러 스레드가 공유할 땐 Arc<Mutex<T>>로 안전하게 감싸고, 값을 주고받기만 하면 되는 경우엔 mpsc 채널을 쓴다. 핵심은 데이터 경쟁을 런타임이 아니라 타입 시스템이 막는다는 점이다.

스레드 만들고 기다리기

Rust의 표준 스레드는 OS 스레드 하나에 1:1로 대응한다. std::thread::spawn에 클로저를 넘기면 새 스레드가 그 클로저를 실행하고, 반환값으로 JoinHandle을 준다. 메인 스레드가 자식 스레드의 종료를 기다리려면 이 핸들의 join을 호출한다.

use std::thread;

fn main() {
    // 새 스레드를 띄우고 핸들을 받는다.
    let handle = thread::spawn(|| {
        for i in 1..=3 {
            println!("자식 스레드: {i}");
        }
    });

    for i in 1..=3 {
        println!("메인 스레드: {i}");
    }

    // join은 자식이 끝날 때까지 기다린다. Result를 반환하므로 unwrap.
    handle.join().unwrap();
}

join을 호출하지 않으면 메인 스레드가 먼저 끝나면서 프로세스가 종료돼 자식 스레드의 일부 출력이 누락될 수 있다. join은 자식이 패닉했는지를 Result로 알려 주기 때문에, 위에서는 unwrap으로 그 결과를 확인한다.

C++과 이렇게 다르다 — join을 잊으면? C++에서 std::thread를 만들고 join()이나 detach() 없이 소멸자에 도달하면 std::terminate()로 프로그램이 죽는다. 즉 실수가 런타임 크래시로 드러난다. Rust의 JoinHandle은 드롭돼도 프로그램을 죽이지 않고, 그냥 스레드를 기다리지 않을 뿐(자동 detach)이다. 대신 Rust는 그 스레드가 빌려 간 데이터의 수명을 컴파일 타임에 검사해, "join 안 하고 떠난 스레드가 죽은 데이터를 참조하는" 부류의 버그 자체를 막는다.

move 클로저 — 소유권 넘기기

스레드 클로저가 바깥 변수를 쓰려면, 그 변수가 자식 스레드보다 오래 산다는 보장이 필요하다. 컴파일러는 그 보장을 못 하기 때문에, 클로저가 빌림(&)으로 값을 캡처하면 컴파일을 거부한다. 해법은 move 키워드로 소유권 자체를 스레드로 넘기는 것이다.

use std::thread;

fn main() {
    let data = vec![10, 20, 30];

    // move가 없으면: data를 빌리려 하지만 메인이 먼저 끝날 수 있어 컴파일 에러.
    // move를 붙이면 data의 소유권이 클로저로 이동한다.
    let handle = thread::spawn(move || {
        let sum: i32 = data.iter().sum();
        println!("합계 = {sum}");
    });

    // 여기서 data를 다시 쓰면 컴파일 에러 — 이미 이동했기 때문이다.
    handle.join().unwrap();
}

move로 넘긴 뒤에는 메인 스레드에서 data를 더 이상 쓸 수 없다. 소유권이 한 곳에만 있다는 규칙 덕분에, 두 스레드가 같은 벡터를 동시에 건드리는 상황이 원천적으로 생기지 않는다. 값을 넘기지 않고 여러 스레드가 함께 봐야 한다면 뒤에서 다룰 Arc가 필요하다.

Send/Sync — 타입으로 막는 데이터 경쟁

Rust가 "이 타입은 스레드 사이를 오가도 안전한가"를 판단하는 기준이 두 마커 트레이트다.

  • Send — 값의 소유권을 다른 스레드로 옮겨도 안전한 타입. 대부분의 타입이 자동으로 Send다.
  • Sync — &T(공유 참조)를 여러 스레드가 동시에 가져도 안전한 타입. T가 Sync라는 것은 &T가 Send라는 것과 같다.

이 두 트레이트는 직접 구현하는 게 아니라, 필드가 모두 안전하면 컴파일러가 자동으로 부여하는 마커다. 그리고 thread::spawn의 시그니처가 넘기는 클로저에 Send를 요구하기 때문에, Send가 아닌 값을 스레드로 보내려 하면 컴파일이 실패한다. 대표적으로 스레드 안전하지 않은 참조 카운터 Rc<T>는 Send가 아니다.

use std::rc::Rc;
use std::thread;

fn main() {
    let counter = Rc::new(5);
    let clone = Rc::clone(&counter);

    // 컴파일 에러: `Rc<i32>` cannot be sent between threads safely
    // Rc는 참조 카운트를 원자적으로 갱신하지 않아 Send가 아니다.
    let handle = thread::spawn(move || {
        println!("{}", clone);
    });

    handle.join().unwrap();
}

같은 코드를 스레드 안전한 Arc로 바꾸면 컴파일된다. 즉 "어떤 공유 타입을 써야 하는가"를 사람이 기억하는 대신, 타입 시스템이 잘못된 선택을 거부해 준다. 데이터 경쟁을 실행 전에 잡는다는 Rust 동시성의 핵심이 바로 이 지점이다.

C++과 이렇게 다르다 — 데이터 경쟁의 처리 시점 C++에서 여러 스레드가 동기화 없이 같은 변수를 쓰면 데이터 경쟁이고, 이는 정의되지 않은 동작(UB)이다. 컴파일러는 대개 막아 주지 않으며, 문제는 ThreadSanitizer 같은 런타임 도구나 재현 어려운 버그로 뒤늦게 드러난다. Rust는 Send/Sync를 타입 검사에 엮어, 스레드 안전하지 않은 값을 스레드로 넘기는 코드를 아예 컴파일하지 않는다. 같은 종류의 실수를 런타임이 아니라 컴파일 타임에 차단하는 것이 가장 큰 차이다.

Arc<Mutex>로 상태 공유

여러 스레드가 같은 가변 데이터를 공유하려면 두 가지가 동시에 필요하다.

  • 공유 소유권 — 여러 스레드가 같은 값을 함께 소유한다. → Arc<T>(원자적 참조 카운트)
  • 상호 배제 — 한 번에 한 스레드만 값을 수정한다. → Mutex<T>

그래서 정석 조합이 Arc<Mutex<T>>다. Arc가 "여러 스레드가 같은 객체를 가리킬 수 있게" 하고, 그 안의 Mutex가 "그 객체를 건드릴 땐 한 명씩"을 보장한다.

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // Arc로 감싸 여러 스레드가 공유, Mutex로 가변 접근을 직렬화한다.
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        // 스레드마다 Arc를 복제한다(참조 카운트만 증가).
        let counter = Arc::clone(&counter);
        let handle = thread::spawn(move || {
            // lock()은 MutexGuard를 돌려준다. 스코프를 벗어나면 자동 해제된다.
            let mut num = counter.lock().unwrap();
            *num += 1;
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    // 모든 스레드가 1씩 더했으므로 결과는 10이다.
    println!("결과 = {}", *counter.lock().unwrap());
}

핵심은 lock()이 돌려주는 MutexGuard다. 이 가드가 살아 있는 동안만 잠금이 유지되고, 가드가 스코프를 벗어나 드롭되는 순간 잠금이 자동으로 풀린다. 잠금 해제를 손으로 호출할 필요가 없어 "unlock을 깜빡해서 데드락" 같은 실수가 줄어든다.

Arc만으로는 못 바꾼다 Arc<T>는 공유는 해 주지만 내부 값을 직접 바꾸게 해 주지는 않는다(공유 참조만 제공). 그래서 가변 상태 공유에는 거의 항상 Arc<Mutex<T>>(또는 RwLock) 조합이 필요하다. 또 Arc는 참조 카운트를 원자적으로 갱신하느라 Rc보다 약간의 비용이 있으니, 단일 스레드에서는 Rc를 쓴다.

mpsc 채널로 메시지 전달

상태를 공유하는 대신 값을 주고받기만 하면 되는 경우도 많다. 이때는 잠금보다 채널이 깔끔하다. 표준 라이브러리의 std::sync::mpsc는 "multiple producer, single consumer" 채널을 제공한다 — 보내는 쪽(Sender)은 여럿일 수 있고 받는 쪽(Receiver)은 하나다.

use std::sync::mpsc;
use std::thread;

fn main() {
    // 송신자 tx, 수신자 rx를 만든다.
    let (tx, rx) = mpsc::channel();

    for id in 0..3 {
        // 송신자는 clone으로 여러 스레드에 나눠 줄 수 있다(multiple producer).
        let tx = tx.clone();
        thread::spawn(move || {
            // send는 값의 소유권을 채널로 넘긴다.
            tx.send(format!("스레드 {id} 보고")).unwrap();
        });
    }

    // 원본 tx를 드롭해야, 모든 송신자가 사라졌을 때 rx 순회가 끝난다.
    drop(tx);

    // rx를 순회하면 송신자가 모두 닫힐 때까지 메시지를 받는다.
    for received in rx {
        println!("받음: {received}");
    }
}

여기서도 소유권 규칙이 안전망이 된다. send는 값의 소유권을 채널로 넘기므로, 보낸 뒤 그 값을 송신 측에서 다시 건드릴 수 없다. 따라서 "보낸 데이터를 보낸 쪽이 동시에 수정하는" 경쟁이 생기지 않는다. 받는 쪽에서 for received in rx로 순회하면 모든 송신자가 닫힐 때까지 자동으로 메시지를 하나씩 받는다.

공유냐 전달이냐 같은 데이터를 여러 스레드가 계속 읽고 쓰면 Arc<Mutex<T>>가 맞다. 작업을 던지고 결과만 거둬들이는 파이프라인이면 채널이 더 단순하고 데드락 위험도 낮다. 둘은 배타적이지 않으니, 큰 구조에서는 채널로 일감을 분배하고 꼭 필요한 공유 상태만 Mutex로 감싸는 식으로 섞어 쓴다.

정리

  • 생성·대기 — thread::spawn으로 스레드를 띄우고 JoinHandle::join으로 종료를 기다린다. join은 패닉 여부를 Result로 알려 준다.
  • move — 스레드 클로저가 바깥 값을 쓰려면 move로 소유권을 넘긴다. 소유권이 한 곳에만 있으므로 동시 접근이 원천 차단된다.
  • Send/Sync — 스레드 사이 이동 가능성(Send)과 공유 가능성(Sync)을 컴파일러가 자동 추론한다. 안전하지 않은 타입(Rc 등)은 컴파일 단계에서 거부된다.
  • 공유 상태 — 여러 스레드가 가변 데이터를 공유하면 Arc<Mutex<T>>. MutexGuard가 드롭될 때 잠금이 자동 해제된다.
  • 메시지 전달 — 값만 주고받으면 mpsc 채널이 더 단순하다. send가 소유권을 넘겨 경쟁을 막는다.
  • 한 줄 요약 — Rust 동시성은 데이터 경쟁을 런타임 도구가 아니라 타입 시스템으로 막는다. C++의 std::thread+뮤텍스와 모양은 같지만, 실수가 컴파일 에러로 먼저 드러난다는 점이 다르다.
