엣지 컴퓨팅이란 무엇인가

엣지 컴퓨팅(Edge Computing)은 데이터가 생기는 현장 근처에서 그 데이터를 바로 처리하는 방식을 말한다. "엣지"는 네트워크의 가장자리, 즉 클라우드 데이터센터에서 멀리 떨어진 현장 끝단을 가리킨다. 공장으로 좁히면 카메라·센서·설비가 놓인 라인 바로 옆에서 연산이 일어난다는 뜻이다.

왜 모든 데이터를 클라우드로 보내 처리하지 않는가. 클라우드는 저장 용량도 크고 연산 자원도 거의 무한하지만, 현장과 클라우드 사이에는 네트워크가 있다. 이 네트워크가 만드는 제약이 엣지 컴퓨팅이 필요한 이유다.

클라우드로 다 보내지 않는 다섯 가지 이유

1. 지연(Latency) — 현장에서 클라우드까지 데이터가 오가는 데 수십~수백 ms가 걸린다. 컨베이어 위를 지나가는 제품을 실시간으로 판정해 불량품을 밀어내야 하는데, 왕복 시간이 검사 주기보다 길면 제어 자체가 성립하지 않는다.
2. 대역폭(Bandwidth) — 머신비전 카메라 한 대가 초당 수십~수백 MB의 이미지를 만든다. 카메라가 여러 대면 이걸 전부 클라우드로 올리는 회선 자체가 비현실적이다.
3. 비용(Cost) — 클라우드는 데이터 전송량과 저장량에 따라 과금된다. 원본 이미지를 전부 올리고 보관하면 비용이 감당하기 어렵게 커진다.
4. 보안(Security) — 생산 공정 데이터와 검사 이미지는 기업의 핵심 자산이다. 외부망으로 내보내는 데이터를 최소화하는 것이 보안 관점에서 안전하다.
5. 가용성(Availability) — 인터넷 회선이 끊겨도 공장은 멈출 수 없다. 검사와 제어가 현장에서 자립적으로 돌아가야 라인이 계속 가동된다.

엣지는 클라우드의 반대가 아니라 짝이다 엣지 컴퓨팅을 "클라우드를 안 쓰는 것"으로 오해하기 쉽다. 그러나 엣지와 클라우드는 경쟁 관계가 아니라 역할 분담 관계다. 빠른 판단이 필요한 일은 엣지가 맡고, 대규모 축적과 분석이 필요한 일은 클라우드가 맡는다. 둘을 어떻게 나누느냐가 스마트 공장 데이터 설계의 핵심이다.

클라우드 vs 엣지 vs 온프레미스

스마트 공장에서 데이터를 처리하는 위치는 보통 세 곳으로 나뉜다. 엣지는 현장 라인 옆, 온프레미스는 공장 내 전산실의 자체 서버, 클라우드는 외부 데이터센터다. 셋은 물리적 거리도 다르고 맡는 일도 다르다.

구분 위치 주 역할 지연 대표 처리
엣지 생산 라인 바로 옆 실시간 검사·판정·제어 ms 단위 (매우 낮음) 비전 검사, 결함 판정, PLC 신호 응답
온프레미스 공장 내 전산실 서버 공장 단위 집계·운영 시스템 수~수십 ms (낮음) MES, 라인별 데이터 통합, 단기 이력 저장
클라우드 외부 데이터센터 장기 저장·대규모 분석·학습 수십~수백 ms (높음) 전사 품질 분석, AI 모델 학습, 공장 간 비교

현실의 스마트 공장은 이 셋을 동시에 쓰는 하이브리드 구조다. 검사는 엣지에서, 공장 운영 데이터는 온프레미스 MES에서, 장기 추세 분석과 AI 학습은 클라우드에서 처리한다. 어느 하나만으로는 전체를 감당할 수 없다.

엣지가 강한 것

  • 즉시 응답이 필요한 실시간 제어
  • 대용량 원본 데이터의 1차 처리
  • 네트워크가 끊겨도 자립 동작

클라우드가 강한 것

  • 대규모 데이터의 장기 축적
  • 여러 라인·공장을 묶은 통합 분석
  • 고연산이 필요한 AI 모델 학습

스마트 공장에서 무엇을 엣지에서 처리하나

엣지와 클라우드의 역할을 가르는 기준은 단순하다. "얼마나 빨리 답이 필요한가"와 "얼마나 많은 데이터를 봐야 하는가"다. 즉시 답해야 하는 일은 엣지로, 많이 모아서 봐야 하는 일은 클라우드로 간다.

엣지에서 처리

  • 실시간 비전 검사와 결함 판정
  • 양품/불량 신호의 PLC 전달
  • 설비 인터록과 시퀀스 응답
  • 이상 징후 1차 감지와 즉시 알람
  • 원본 데이터의 필터링·집계

클라우드에서 처리

  • 장기 품질 추세 분석
  • 불량 패턴 통계와 상관관계 도출
  • AI 검사 모델의 학습·재학습
  • 여러 공장의 생산 데이터 비교
  • 경영 대시보드용 데이터 집계

책임 분담의 원칙

핵심은 "판단은 엣지, 학습은 클라우드"로 요약된다. 제품 하나를 양품으로 볼지 불량으로 볼지는 엣지가 그 자리에서 결정한다. 그러나 "어떤 기준으로 판단해야 하는가", 즉 검사 모델 자체를 만들고 개선하는 일은 대량의 데이터가 모인 클라우드에서 한다. 클라우드가 학습한 모델을 엣지로 내려보내면, 엣지는 그 모델로 다시 현장에서 빠르게 판단한다. 이 순환이 잘 돌아가는 것이 스마트 공장 데이터 구조의 목표다.

나누는 기준을 한 문장으로 "라인을 멈추게 하거나 제품을 밀어내는 결정"은 엣지가 맡는다. 그 결정이 1초라도 늦으면 안 되기 때문이다. "여러 날·여러 라인의 데이터를 모아야 보이는 것"은 클라우드가 맡는다. 그 일은 빠를 필요는 없지만 많은 데이터가 필요하기 때문이다.

머신비전과 엣지

머신비전 검사는 그 자체가 가장 대표적인 엣지 처리다. 다른 무엇보다 비전이 엣지여야 하는 이유는 두 가지가 겹친다. 빠른 응답이 필요하고, 데이터가 너무 크다.

비전 검사는 컨베이어 위를 지나가는 제품을 그 자리에서 판정해야 한다. 검사 주기는 보통 수십 ms에서 수백 ms 사이다. 이미지를 클라우드로 보내 판정 결과를 받아오는 왕복 시간으로는 이 주기를 맞출 수 없다. 또 머신비전 카메라가 만드는 데이터의 양은 다른 센서와 비교가 안 된다.

데이터 종류 대략적인 크기 발생 빈도 클라우드 직송 가능 여부
온도·진동 센서값 수~수십 byte 초당 수~수십 회 가능 — 부담 거의 없음
검사 결과 (판정·측정값) 수백 byte ~ 수 KB 제품당 1회 가능 — 가벼움
압축 검사 이미지 수백 KB ~ 수 MB 제품당 1~수 장 선별 전송 — 일부만
원본(비압축) 고해상도 이미지 수 MB ~ 수십 MB 초당 수~수십 장 사실상 불가 — 엣지 보관

그래서 머신비전에서 엣지의 역할은 분명하다. 이미지는 엣지에서 검사하고, 클라우드로는 결과와 일부 이미지만 보낸다. 원본 이미지는 엣지나 온프레미스 스토리지에 일정 기간 보관하고, 클라우드에는 판정 결과·측정값 같은 가벼운 데이터와 불량 이미지처럼 꼭 필요한 이미지만 선별해서 올린다.

"전부 클라우드에 올려두면 나중에 분석하지" 라는 함정 원본 이미지를 일단 다 클라우드에 쌓아두려는 시도는 거의 항상 실패한다. 회선 대역폭이 못 버티고, 저장 비용이 폭증하며, 정작 필요한 이미지를 그 더미에서 찾기도 어렵다. "무엇을 남길지"를 엣지에서 먼저 결정하는 것이 데이터 파이프라인 설계의 출발점이다.

데이터 파이프라인

데이터 파이프라인은 현장에서 생긴 데이터가 클라우드에 저장·분석되기까지 거치는 단계별 흐름을 말한다. 물이 여러 관을 거쳐 흐르듯, 데이터도 수집 → 엣지 처리 → 필터링·집계 → 전송 → 클라우드 저장의 단계를 거친다. 각 단계에서 데이터의 양은 줄고 가치는 압축된다.

그림 1. 데이터 파이프라인 5단계 — 현장에서 클라우드로 갈수록 데이터량은 줄고 가치는 압축되며, 학습된 모델은 다시 엣지로 내려온다

단계별로 보는 파이프라인

① 수집 비전 카메라, IoT 센서, 설비 신호에서 원천 데이터가 만들어진다. 이 단계의 데이터량이 가장 크고 가공되지 않은 상태다.
② 엣지 처리 현장 근처에서 이미지를 검사하고 결함을 판정한다. 실시간 응답이 여기서 끝난다. 라인 제어에 필요한 결정은 클라우드를 거치지 않는다.
③ 필터링·집계 원본을 요약으로 바꾸고, NG 데이터를 선별하고, 정상 데이터는 샘플링한다. 네트워크 장애에 대비한 버퍼링도 이 단계에서 일어난다.
④ 전송 선별·압축된 데이터를 MQTT, OPC UA, REST 같은 프로토콜로 클라우드에 올린다. 가벼워진 데이터만 회선을 탄다.
⑤ 저장·분석 클라우드가 데이터를 장기 보관하고 추세를 분석하며 AI 모델을 학습한다. 학습된 모델은 다시 엣지로 배포되어 순환이 닫힌다.

무엇을 보내고 무엇을 버리나

파이프라인의 ③ 필터링·집계 단계가 사실상 데이터 설계에서 가장 머리를 써야 하는 곳이다. 모든 데이터를 다 남기면 비용과 회선이 못 버티고, 너무 많이 버리면 나중에 필요한 데이터가 없다. 그 사이의 균형을 잡는 것이 데이터 보존 정책이다.

원본이냐 요약이냐

대부분의 데이터는 원본 그대로가 아니라 요약된 형태로 클라우드에 올린다. 진동 센서의 초당 수천 개 샘플은 1초 평균·최대·표준편차로 압축한다. 검사 이미지는 "결함 면적 0.4㎟, 위치 (x, y), 판정 NG" 같은 측정값으로 추출한다. 원본은 엣지에 두고, 클라우드에는 분석에 쓸 수 있는 숫자만 보낸다.

정상은 샘플링, NG는 보존

이미지 보존의 원칙은 비대칭이다. 정상(OK) 이미지는 전부 보관할 필요가 없다. 일정 비율로 샘플링해서 일부만 남긴다. 반면 불량(NG) 이미지는 가능한 한 모두 보존한다. NG 이미지는 클레임 대응의 증거가 되고, AI 검사 모델을 재학습할 때 가장 귀한 데이터다. 정상 이미지는 흔하지만 불량 이미지는 드물기 때문에, 드문 쪽을 더 아껴 모은다.

데이터 클라우드 전송 보존 방식 이유
판정 결과·측정값 전량 전송 장기 보존 가볍고, 추세 분석의 핵심 재료
NG 이미지 전량 전송 장기 보존 클레임 증거이자 모델 재학습 데이터
OK 이미지 샘플링 전송 (일부) 엣지 단기 보관 후 폐기 양이 많고 대부분 분석 가치가 낮음
원본 고해상도 이미지 전송 안 함 엣지/온프레미스 단기 보관 대역폭·비용 부담이 너무 큼
고빈도 센서 원샘플 집계 후 전송 엣지에서 통계로 압축 원샘플은 양이 많고 노이즈가 섞임
보존 정책은 "기간"과 "조건"으로 정의한다 실무에서 데이터 보존 정책은 보통 이런 식으로 적힌다. "원본 이미지는 엣지에 7일 보관 후 삭제, NG 이미지는 클라우드에 3년 보관, OK 이미지는 1% 샘플링해 1년 보관, 판정 결과는 영구 보관." 무엇을 얼마나 남길지 미리 규칙으로 정해두지 않으면, 스토리지는 반드시 한계에 부딪힌다.

엣지 디바이스

엣지 처리를 실제로 수행하는 하드웨어를 엣지 디바이스라고 부른다. 공장 현장에서는 처리 성능, 설치 공간, 환경 내성(온도·진동·먼지)에 따라 여러 형태가 쓰인다.

디바이스 특징 처리 능력 대표 용도
산업용 PC (IPC) 일반 PC를 산업 환경용으로 강화. 팬리스, 광온도 동작 중~높음 (CPU 중심) 비전 검사 SW 구동, 다중 카메라 처리
엣지 게이트웨이 여러 설비·센서의 데이터를 모아 프로토콜 변환·전송 낮~중간 데이터 수집·중계, 프로토콜 브리지
스마트 카메라 카메라 안에 프로세서 내장. 촬영과 검사를 한 몸체에서 낮~중간 (내장 연산) 단순·정형 검사, 공간 제약이 큰 라인
GPU 엣지 박스 GPU를 탑재한 소형 박스. 딥러닝 추론에 특화 높음 (병렬 연산) AI 기반 결함 검사, 실시간 딥러닝 추론

스마트 카메라의 장단

카메라에 처리가 내장되어 배선과 공간이 줄고 구성이 간단하다. 다만 연산 자원이 제한적이라 복잡한 검사나 딥러닝에는 한계가 있다. 정형화된 검사에 적합하다.

GPU 엣지 박스의 장단

딥러닝 추론을 현장에서 실시간으로 돌릴 수 있다. 대신 발열·소비전력·비용이 크고, 모델 관리라는 운영 부담이 따라온다. AI 검사가 필요한 라인의 선택지다.

"카메라에 검사를 넣을까, PC에서 처리할까" 검사가 단순하고 정형적이며 공간이 빠듯하면 스마트 카메라가 낫다. 검사가 복잡하거나 여러 카메라를 묶어야 하거나 딥러닝이 필요하면 산업용 PC나 GPU 엣지 박스가 낫다. 정답은 검사 난이도와 현장 제약이 함께 정한다.

통신과 프로토콜

엣지에서 처리·선별한 데이터를 클라우드(또는 상위 시스템)로 올릴 때는 정해진 통신 프로토콜을 쓴다. 스마트 공장에서 자주 쓰이는 것은 MQTT, OPC UA, REST 세 가지다. 각각 성격이 다르다.

프로토콜 방식 강점 주 용도
MQTT 발행/구독 (Pub/Sub) 가볍고, 불안정한 회선에 강함 다수 엣지 → 클라우드로 센서·결과 데이터 스트리밍
OPC UA 표준 데이터 모델 기반 제조사 독립적, 구조화된 정보 모델 설비·제어 계층과 상위 시스템의 표준 연결
REST 요청/응답 (HTTP) 범용적, 구현·연동이 쉬움 이미지 업로드, 클라우드 API 호출, 모델 배포

어떻게 골라 쓰나

실무에서는 한 가지만 쓰지 않고 섞어 쓴다. 검사 결과나 센서 집계값처럼 끊임없이 흐르는 가벼운 데이터는 MQTT로 스트리밍한다. 설비 데이터를 표준화된 모델로 상위에 올릴 때는 OPC UA를 쓴다. NG 이미지 파일을 클라우드 스토리지에 올리거나 클라우드가 학습한 모델을 엣지로 내려받을 때는 REST가 자연스럽다. OPC UA는 이 시리즈 7편에서 더 자세히 다룬다.

MQTT가 공장에서 인기 있는 이유 MQTT는 메시지 헤더가 매우 작고, 회선이 끊겼다 붙어도 재연결과 메시지 보관(QoS)을 지원한다. 공장 네트워크는 완벽하게 안정적이지 않기 때문에, "끊겨도 데이터를 잃지 않는" 특성이 중요하다. 그래서 다수의 엣지 디바이스가 데이터를 올려보내는 구조에서 MQTT가 사실상 표준처럼 쓰인다.

엣지 컴퓨팅의 장점과 과제

엣지 컴퓨팅은 분명한 이점을 주지만, 공짜는 아니다. 처리를 현장에 분산시킨 만큼 관리해야 할 대상도 분산된다.

장점

  • 지연 감소 — 현장에서 즉시 판단, 실시간 제어 가능
  • 대역폭 절약 — 선별된 데이터만 전송, 회선 부담 감소
  • 오프라인 동작 — 회선이 끊겨도 검사·제어 지속
  • 보안 — 민감 데이터를 현장 안에 머무르게 함

과제

  • 관리 복잡도 — 디바이스가 많아질수록 관리 대상 증가
  • 분산 업데이트 — 수십~수백 대의 SW·모델을 동기화
  • 보안 면적 — 현장 디바이스 하나하나가 공격 지점
  • 장애 대응 — 분산된 고장을 원격으로 진단·복구
엣지가 늘어날수록 "운영"이 문제가 된다 엣지 디바이스 한 대를 설치하는 것은 쉽다. 그러나 그것이 50대, 100대가 되면 이야기가 달라진다. 어느 디바이스가 어떤 버전의 검사 모델을 돌리고 있는지, 누가 펌웨어를 언제 올렸는지, 고장 난 디바이스를 어떻게 원격으로 되살릴지 — 이 분산 디바이스 운영(fleet management)이 엣지 컴퓨팅 도입에서 가장 과소평가되는 과제다.

데이터 파이프라인 설계 시 고려사항

마지막으로, 스마트 공장의 데이터 파이프라인을 설계할 때 반드시 짚어야 하는 네 가지를 정리한다. 이것을 빼먹으면 처음에는 잘 돌아가다가 규모가 커질 때 문제가 터진다.

설계 체크리스트 네 가지

1. 장애 시 버퍼링 — 클라우드로 가는 회선은 반드시 끊긴다고 가정한다. 회선이 끊긴 동안 엣지가 데이터를 로컬에 쌓아두었다가, 복구되면 순서대로 다시 보내는 버퍼링·재전송 구조가 필수다. 이것이 없으면 네트워크 장애 = 데이터 손실이다.
2. 시각 동기화 — 여러 엣지 디바이스의 시계가 어긋나면, 클라우드에서 데이터를 합쳤을 때 사건의 순서가 뒤죽박죽이 된다. NTP 같은 시각 동기화로 모든 디바이스가 같은 시간 기준을 갖게 해야 한다.
3. 스키마 관리 — 데이터의 형식(필드 이름, 단위, 타입)을 미리 정의하고 버전을 관리한다. 엣지가 보내는 데이터 형식과 클라우드가 기대하는 형식이 어긋나면 파이프라인이 조용히 깨진다.
4. 확장성 — 카메라 10대로 시작했어도 100대로 늘어날 것을 가정해 설계한다. 디바이스가 늘어날 때 파이프라인 구조를 갈아엎지 않고 추가만으로 확장되도록 해야 한다.

고려사항 빠뜨리면 생기는 문제 대표 대응
장애 시 버퍼링 회선 장애 때 데이터 영구 손실 엣지 로컬 큐, 재전송, MQTT QoS
시각 동기화 데이터 순서·인과 관계 붕괴 NTP/PTP 시각 동기, 타임스탬프 표준화
스키마 관리 형식 불일치로 파이프라인 무음 장애 스키마 정의·버전 관리, 검증 단계
확장성 디바이스 증가 시 구조 재설계 필요 Pub/Sub 구조, 표준 프로토콜, 모듈화
정리 — 엣지와 파이프라인은 머신비전의 자연스러운 확장이다 머신비전 엔지니어에게 엣지 컴퓨팅은 낯선 분야가 아니다. 현장에서 이미지를 검사하는 일 자체가 이미 엣지 처리다. 거기에서 한 걸음 더 나아가 "검사 결과를 어떻게 위로 올리고, 무엇을 남기고, 어떻게 안정적으로 흐르게 할 것인가"를 설계하는 것이 데이터 파이프라인이다. 다음 13편에서는 이렇게 모인 데이터로 공장을 디지털 공간에 복제하는 디지털 트윈을 다룬다.
