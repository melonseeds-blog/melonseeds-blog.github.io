플러그인 아키텍처가 필요한 이유

플러그인 아키텍처는 코어를 재컴파일하지 않고 기능을 추가할 수 있게 해주는 구조다. 코어는 인터페이스만 알고, 실제 구현은 외부에서 끼워 넣는다.

이미징 라이브러리 같은 산업용 SDK에서 이 구조가 특히 유용한 이유는 세 가지다.

  • 기능 확장 — 새 필터나 분석 알고리즘을 코어 빌드 없이 추가한다.
  • 데이터 플로우 블록 에디터 — 새 처리 블록을 플러그인으로 등록하면 블록 팔레트에 자동으로 나타난다.
  • 서드파티 확장 허용 — 고객사나 파트너가 자체 블록을 만들어 제품에 붙일 수 있다.

핵심은 코어와 확장 모듈 사이의 의존 방향이다. 코어는 플러그인을 모르고, 플러그인이 코어의 인터페이스를 안다. 이 방향을 지켜야 코어가 독립적으로 발전한다.

두 가지 수준의 "플러그인"

"플러그인"이라는 단어는 두 가지 전혀 다른 수준을 가리킨다. 둘을 구분하지 않으면 설계가 꼬인다.

정적 등록 — 같은 바이너리 안에서

DLL을 쓰지 않는다. 같은 실행 파일 안에 있는 여러 처리 블록이 런타임에 자기 자신을 레지스트리에 등록하는 방식이다. 컴파일 타임에 어떤 블록이 있는지 코어가 일일이 알 필요가 없어진다.

동적 로딩 — 별도 DLL을 런타임에

별도로 빌드된 DLL(.so)을 실행 중에 메모리로 불러온다. 진정한 의미의 플러그인이지만, 그만큼 ABI 문제라는 큰 비용을 떠안는다.

비교정적 등록동적 로딩
DLL 사용안 씀 (같은 바이너리)별도 DLL/so
기능 추가 시 코어 재컴파일필요 (전체 재링크)불필요
ABI 문제없음있음 (핵심 난점)
서드파티 확장불가가능
배포 단위단일 실행 파일코어 + 플러그인 파일들
난이도낮음높음

실무에서는 먼저 정적 등록으로 Factory 구조를 잡고, 나중에 동일한 레지스트리 인터페이스 위에 동적 로딩을 얹는 순서가 안전하다.

Factory 패턴 + 런타임 등록

모든 처리 블록은 공통 인터페이스 IProcessBlock을 구현한다. 코어는 이름 문자열로 블록을 생성하고, 어떤 구체 타입인지는 알지 못한다.

// 이름으로 IProcessBlock을 생성하는 중앙 레지스트리.
class BlockRegistry
{
public:
    using Factory = std::function<std::unique_ptr<IProcessBlock>()>;

    // Meyers 싱글톤 — 함수 내 static으로 초기화 순서를 보장한다.
    static BlockRegistry& Instance();

    // 블록 타입을 이름과 factory 함수로 등록한다.
    void Register(const std::string& name, Factory factory);

    // 등록된 이름으로 새 블록 인스턴스를 생성한다.
    std::unique_ptr<IProcessBlock> Create(const std::string& name) const;

    // 등록된 모든 블록 이름을 반환한다.
    std::vector<std::string> ListNames() const;

private:
    std::unordered_map<std::string, Factory> m_factories;
};

자동 등록 트릭

각 블록의 .cpp 파일에 매크로 한 줄만 넣으면, static 객체의 생성자가 main()보다 먼저 실행되면서 자기 자신을 등록한다. 코어 코드를 건드릴 필요가 없다.

// static 변수의 초기화 시점에 Register를 호출하는 매크로.
#define REGISTER_BLOCK(Type) \
    static bool _reg_##Type = [] { \
        BlockRegistry::Instance().Register(#Type, [] { \
            return std::make_unique<Type>(); \
        }); \
        return true; \
    }();

// --- GaussianBlurBlock.cpp ---
REGISTER_BLOCK(GaussianBlurBlock)   // 이 한 줄이면 끝
static initialization order fiasco 주의 서로 다른 번역 단위(.cpp)의 전역 static 객체는 초기화 순서가 정해져 있지 않다. BlockRegistry를 전역 객체로 두면, 블록의 _reg_ 변수가 레지스트리보다 먼저 초기화되어 크래시한다. 반드시 Instance()를 함수 내 static(Meyers 싱글톤)으로 만들어 "처음 호출될 때 생성"되도록 한다. 
// Meyers 싱글톤 — 첫 호출 시점에 생성, 순서 문제 없음.
BlockRegistry& BlockRegistry::Instance()
{
    static BlockRegistry instance;
    return instance;
}

동적 라이브러리 로딩

OS는 라이브러리를 런타임에 메모리로 올리는 API를 제공한다. 플랫폼마다 이름이 다르지만 동작은 같다.

동작WindowsLinux / macOS
라이브러리 로드LoadLibrarydlopen
심볼 주소 얻기GetProcAddressdlsym
라이브러리 해제FreeLibrarydlclose
파일 확장자.dll.so / .dylib

이 차이를 코어 곳곳에 흩뿌리면 안 된다. RAII 래퍼 하나로 감싸서 로드 실패와 해제 누락을 막는다.

// OS별 동적 라이브러리를 RAII로 감싸는 크로스 플랫폼 래퍼.
class SharedLibrary
{
public:
    explicit SharedLibrary(const std::string& path)
    {
#ifdef _WIN32
        m_handle = ::LoadLibraryA(path.c_str());
#else
        m_handle = ::dlopen(path.c_str(), RTLD_NOW | RTLD_LOCAL);
#endif
    }

    ~SharedLibrary()
    {
        if (m_handle)
        {
#ifdef _WIN32
            ::FreeLibrary(static_cast<HMODULE>(m_handle));
#else
            ::dlclose(m_handle);
#endif
        }
    }

    SharedLibrary(const SharedLibrary&) = delete;
    SharedLibrary& operator=(const SharedLibrary&) = delete;

    bool IsValid() const { return m_handle != nullptr; }

    // 심볼 이름으로 함수 포인터를 얻는다.
    template <typename T>
    T GetSymbol(const std::string& name) const
    {
#ifdef _WIN32
        return reinterpret_cast<T>(
            ::GetProcAddress(static_cast<HMODULE>(m_handle), name.c_str()));
#else
        return reinterpret_cast<T>(::dlsym(m_handle, name.c_str()));
#endif
    }

private:
    void* m_handle = nullptr;
};

DLL 경계의 ABI 문제

여기가 동적 플러그인의 진짜 어려운 부분이다. C++에는 표준 ABI(Application Binary Interface)가 없다. 코어와 플러그인이 컴파일러, 컴파일러 버전, 런타임 라이브러리 중 하나라도 다르면 조용히 깨지거나 크래시한다.

무엇이 깨지는가

  • name mangling 차이 — 같은 함수라도 컴파일러마다 심볼 이름을 다르게 만든다. GetProcAddress로 못 찾는다.
  • STL 타입 레이아웃 불일치 — std::string, std::vector의 내부 구조와 allocator는 컴파일러/빌드 설정마다 다르다. DLL 경계로 직접 넘기면 한쪽이 잘못된 메모리를 읽는다.
  • 예외 전파 — 예외를 DLL 경계 너머로 던지면 스택 언와인딩 정보가 호환되지 않아 프로그램이 죽는다.
STL 타입을 DLL 경계로 직접 넘기지 마라 std::string GetName() 같은 시그니처를 DLL이 export하면, 코어가 Release로 빌드되고 플러그인이 Debug로 빌드되었을 때 std::string 레이아웃이 달라 즉시 깨진다. MSVC는 iterator debug level까지 영향을 준다. 경계에서는 const char*, 원시 포인터, 크기처럼 ABI가 고정된 C 타입만 주고받는다.

해결책

  • C 인터페이스로 export — extern "C"로 name mangling을 끄고, C 타입만 주고받는다.
  • 순수 가상 인터페이스만 노출 — vtable 레이아웃은 비교적 안정적이라 인터페이스 포인터는 경계를 넘길 수 있다. 단, 여전히 같은 컴파일러 계열을 강제해야 안전하다.
  • 같은 컴파일러/런타임 강제 — 가장 현실적인 방어선. 코어와 플러그인을 동일한 VS 버전, 동일한 런타임(/MD)으로 빌드하도록 문서화하고 버전 체크로 막는다.

플러그인 진입점 설계 (C ABI)

플러그인 DLL은 코어가 GetProcAddress로 찾을 수 있는 고정된 이름의 C 함수 몇 개를 export한다. 이것이 코어와 플러그인 사이의 계약이다.

// --- 플러그인 측 (MyBlocks.dll) ---
extern "C"
{
    // 플러그인이 빌드된 API 버전을 알린다.
    __declspec(dllexport) const char* PluginApiVersion()
    {
        return "1.0";
    }

    // 이름으로 블록을 생성한다. 실패 시 nullptr.
    __declspec(dllexport) IProcessBlock* CreateBlock(const char* name);

    // 플러그인이 만든 객체를 플러그인이 해제한다.
    __declspec(dllexport) void DestroyBlock(IProcessBlock* p);
}
C ABI export가 안전한 이유 extern "C"는 name mangling을 끄므로 어떤 컴파일러로 빌드해도 심볼 이름이 같다. 인자와 반환값을 const char*와 인터페이스 포인터로만 제한하면, 컴파일러가 달라도 함수 호출 규약 수준에서는 호환된다. 플러그인 경계는 항상 "C 함수 + 추상 인터페이스 포인터" 조합으로 설계한다.

버전 체크

코어는 DLL을 로드한 직후 PluginApiVersion()을 호출해 자신의 API 버전과 비교한다. 불일치하면 로드를 거부한다. 이 체크 한 줄이 "옛날 플러그인을 새 코어에 꽂아 크래시"를 막는다.

Create / Destroy 쌍

플러그인이 new로 만든 객체는 플러그인의 allocator를 쓴다. 이 객체를 코어가 delete하면 코어의 allocator가 호출되어 힙이 깨진다. 그래서 생성한 쪽이 해제한다는 원칙을 CreateBlock / DestroyBlock 쌍으로 강제한다.

// 코어 측 — DestroyBlock을 호출하는 커스텀 deleter로 묶는다.
auto deleter = [destroyFn](IProcessBlock* p) { destroyFn(p); };
std::unique_ptr<IProcessBlock, decltype(deleter)> block(
    createFn("GaussianBlurBlock"), deleter);
// block이 소멸하면 플러그인의 DestroyBlock이 호출된다.

플러그인 매니저

플러그인 매니저는 디렉터리를 스캔해 DLL을 찾고, 검증한 뒤 레지스트리에 등록하는 역할을 한다. 흐름은 단순하다.

  • 스캔 — 플러그인 디렉터리에서 .dll / .so 파일을 찾는다.
  • 로드 — SharedLibrary로 연다. 실패하면 건너뛴다.
  • 검증 — PluginApiVersion()을 호출해 버전을 확인한다. 불일치면 unload하고 경고를 남긴다.
  • 등록 — CreateBlock로 만들 수 있는 블록 이름들을 레지스트리에 등록한다.
살아있는 객체가 있으면 unload 금지 매니저는 각 플러그인이 만든 객체의 수를 세어야 한다. 그 DLL에서 생성된 객체나 함수 포인터가 아직 사용 중인데 FreeLibrary를 호출하면, 객체의 vtable이 가리키던 코드가 메모리에서 사라져 다음 호출에서 즉시 크래시한다. 참조 카운트가 0이 될 때까지 unload를 미룬다.

수명 관리의 함정

동적 플러그인 버그의 대부분은 ABI가 아니라 수명(lifetime)에서 나온다. 코드 자체는 멀쩡한데 "언제 사라지느냐"가 어긋난다.

unload 후 접근 FreeLibrary / dlclose 이후에는 그 DLL의 코드 영역이 통째로 unmap된다. 거기서 만든 객체, 거기를 가리키던 함수 포인터, 그 객체의 vtable 모두 무효다. 접근하는 순간 access violation이다. unload는 반드시 "그 DLL 출처의 모든 것"이 사라진 뒤에 한다.
Create/Destroy allocator 불일치 플러그인이 만든 객체를 코어가 delete하면 안 된다. 플러그인과 코어가 서로 다른 CRT 힙을 쓰면, 한쪽 힙에 할당된 블록을 다른 쪽 힙에 반납하는 꼴이 되어 힙 메타데이터가 손상된다. 항상 DestroyBlock으로 돌려준다.

static 객체 소멸 순서

플러그인 DLL 안의 전역 static 객체는 FreeLibrary 시점에 소멸한다. 이때 그 소멸자가 코어의 레지스트리나 로거에 접근하면, 코어가 먼저 정리되었을 경우 또 다른 순서 문제가 터진다. 플러그인 측 static은 외부 의존을 최소화하고, 코어는 "플러그인을 모두 unload한 뒤"에 자신을 정리한다.

보안 / 안정성 고려

같은 프로세스에 로드된 플러그인은 코어와 주소 공간을 공유한다. 플러그인이 메모리를 밟으면 코어도 같이 죽는다. 신뢰 수준에 따라 격리 전략이 달라진다.

  • 신뢰하는 1st-party 플러그인 — 같은 프로세스에 로드해도 무방하다. 성능 손실이 없다.
  • 신뢰할 수 없는 서드파티 플러그인 — 별도 프로세스(out-of-process)로 띄우고 IPC로 통신한다. 플러그인이 크래시해도 코어 프로세스는 살아남고, 매니저가 해당 플러그인 프로세스만 재시작한다.

out-of-process는 직렬화/IPC 오버헤드가 있지만, "플러그인 하나의 버그가 전체 제품을 죽이지 않는다"는 안정성을 산다. 산업용 장비 소프트웨어에서는 이 트레이드오프가 대개 정당하다.

데이터 플로우 에디터 적용 예

이미징 라이브러리의 블록 에디터에 이 구조를 그대로 적용하면 다음과 같다.

  • 블록 팔레트 — BlockRegistry::ListNames()가 반환하는 이름 목록이 곧 에디터의 블록 팔레트다. 플러그인을 추가하면 팔레트에 자동으로 나타난다.
  • 그래프 직렬화 — 사용자가 만든 플로우 그래프를 JSON으로 저장할 때, 각 노드는 블록 이름 문자열로 기록된다. 불러올 때는 그 이름으로 Create()를 호출해 그래프를 재구성한다. 구체 타입을 직렬화 코드가 알 필요가 없다.
  • 솔루션별 DLL 분리 — 코어, 측정 솔루션, OCR 솔루션을 각각 별도 DLL로 빌드한다. OCR 솔루션을 구매하지 않은 고객에게는 OCR DLL을 빼고 배포하면, 에디터 팔레트에서 OCR 블록이 자연스럽게 사라진다.
// JSON 노드를 이름으로 복원한다.
for (const auto& node : graphJson["nodes"])
{
    std::string typeName = node["type"];      // 예: "GaussianBlurBlock"
    auto block = BlockRegistry::Instance().Create(typeName);
    if (!block)
    {
        // 해당 플러그인이 설치되지 않음 — 경고 후 노드 스킵.
        LogWarn("Unknown block type: " + typeName);
        continue;
    }
    graph.AddNode(std::move(block), node["id"]);
}

대안 — 빌드 타임 플러그인

동적 로딩의 ABI 지옥이 부담스럽다면, 모든 것을 한 바이너리에 정적 링크하고 컴파일 타임에 등록하는 방법이 있다. 앞서 본 REGISTER_BLOCK 매크로가 정확히 이 방식이다.

관점동적 로딩빌드 타임 플러그인
ABI 문제있음없음
기능 추가DLL 교체만전체 재컴파일
서드파티 확장가능불가
배포 안정성버전 조합 검증 필요단일 바이너리, 매우 안정적
디버깅경계 넘는 추적 어려움일반 코드와 동일
많은 산업용 SDK가 빌드 타임 방식을 택한다 의외로 상용 머신비전 SDK 상당수는 동적 플러그인을 쓰지 않고 모든 기능을 정적 링크한다. 이유는 단순하다 — 안정성이 확장성보다 중요하기 때문이다. 현장 장비는 한 번 검증된 바이너리를 오래 쓰며, "플러그인 버전 조합" 같은 변수를 줄이고 싶어한다. 서드파티 확장이 꼭 필요한 게 아니라면 빌드 타임 등록부터 시작하는 것이 합리적이다.
