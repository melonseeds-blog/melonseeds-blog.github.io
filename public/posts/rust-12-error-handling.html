에러 처리 심화 — ?·thiserror·anyhow

2026-06-25 약 8분 분량 Rust 시리즈
이 편에서 배우는 것 Rust는 에러를 예외가 아니라 Result<T, E>라는 값으로 다룬다. 이 글은 회복 불가능한 에러(panic!)와 회복 가능한 에러(Result)를 가르는 기준, ? 연산자로 에러를 위로 전파하는 법, enum 기반 커스텀 에러 타입을 직접 정의하는 법, 그리고 라이브러리에는 thiserror·애플리케이션에는 anyhow를 쓰는 관례까지 다룬다. C++ 예외에 익숙하다면 "전파가 함수 시그니처에 드러나고 비용이 예측 가능하다"는 차이에 주목한다.

에러를 값으로 다룬다

Rust에는 검사 예외도, try/catch도 없다. 실패할 수 있는 함수는 결과를 Result<T, E>라는 열거형으로 돌려준다. 성공이면 Ok(T), 실패면 Err(E)다. 옵션 부재는 Option<T>(Some/None)로 구분한다.

핵심은 에러가 타입 시스템 안의 일반 값이라는 점이다. 함수가 실패할 수 있다는 사실이 반환 타입에 그대로 드러나고, 호출자는 그 값을 반드시 처리해야 한다. 무시하면 컴파일러가 경고하거나, 패턴 매칭을 빠뜨리면 컴파일이 막힌다.

// Result는 표준 라이브러리의 enum이다.
enum Result<T, E> {
    Ok(T),
    Err(E),
}

fn parse_port(text: &str) -> Result<u16, std::num::ParseIntError> {
    // 실패하면 Err가, 성공하면 Ok(숫자)가 그대로 반환된다.
    text.parse::<u16>()
}

fn main() {
    match parse_port("8080") {
        Ok(port) => println!("port = {port}"),
        Err(e)   => println!("parse failed: {e}"),
    }
}
C++과 이렇게 다르다 — 던지는 대신 돌려준다 C++ 예외는 함수 시그니처에 보이지 않는다(noexcept가 없는 한 무엇이든 던질 수 있다). 호출자는 어떤 예외가 날지 추적하기 어렵고, 스택 되감기 비용도 던질 때만 발생한다. Rust는 반대다. 실패 가능성이 -> Result<T, E>로 시그니처에 명시되고, 에러는 일반 값이라 분기 비용이 예측 가능하다. 숨은 제어 흐름이 없어 "이 함수가 실패하면 어디로 가는가"가 코드에 그대로 보인다.

panic! vs Result — 언제 무엇을

Rust도 즉시 중단하는 길은 있다. panic!은 회복 불가능한 상황을 위한 것으로, 기본 설정에서 스택을 되감으며 스레드를 종료한다. 둘을 가르는 기준은 단순하다 — 호출자가 합리적으로 회복할 수 있나다.

상황선택이유
파일 없음, 네트워크 끊김, 입력 파싱 실패Result호출자가 재시도·대체값·사용자 안내로 회복할 수 있다
깨질 수 없는 불변식이 깨짐(프로그램 버그)panic!계속 진행하면 더 위험하다. 빨리 멈추는 게 안전하다
예제·프로토타입·테스트의 빠른 실패unwrap() / expect()회복 처리를 미루고 일단 진행. 단 운영 코드에선 지양
use std::fs;

fn read_config(path: &str) -> Result<String, std::io::Error> {
    // 파일이 없을 수 있다 -- 회복 가능하므로 Result로 돌려준다.
    fs::read_to_string(path)
}

fn divide(a: i32, b: i32) -> i32 {
    if b == 0 {
        // 0으로 나누는 호출은 프로그래밍 오류로 본다 -- 즉시 중단.
        panic!("divide by zero is a bug");
    }
    a / b
}

fn main() {
    // expect는 Err일 때 메시지와 함께 panic 한다. 프로토타입에서만 권장.
    let cfg = read_config("app.toml").expect("config must exist");
    println!("{} bytes", cfg.len());
}
unwrap()은 빚이다 unwrap()과 expect()는 Err/None이면 그 자리에서 panic 한다. 빠른 실험에는 편하지만, 운영 코드에 남으면 예기치 못한 중단의 원인이 된다. 정식 코드에서는 ?나 명시적 매칭으로 바꾼다.

? 연산자로 전파하기

match로 매번 Ok/Err를 풀어 쓰면 코드가 금세 장황해진다. ? 연산자는 이 패턴을 한 글자로 줄인다. Result 뒤에 ?를 붙이면 성공이면 안의 값을 꺼내고, 실패면 그 Err를 즉시 함수에서 반환한다.

use std::fs;
use std::io;

// match로 직접 전파 -- 장황하다.
fn load_verbose(path: &str) -> Result<usize, io::Error> {
    let text = match fs::read_to_string(path) {
        Ok(t) => t,
        Err(e) => return Err(e),
    };
    Ok(text.len())
}

// ? 연산자로 같은 일을 간결하게.
fn load_concise(path: &str) -> Result<usize, io::Error> {
    let text = fs::read_to_string(path)?; // Err면 여기서 바로 반환
    Ok(text.len())
}

?는 호출 체인에도 자연스럽게 이어 붙는다. 여러 단계가 모두 같은 에러 타입을 반환하면, 각 단계 뒤에 ?만 붙여 한 줄로 흐름을 이을 수 있다.

use std::fs;
use std::io;

// 두 파일을 읽어 길이 합을 구한다. 어느 한쪽이라도 실패하면 그 Err가 전파된다.
fn total_len(a: &str, b: &str) -> Result<usize, io::Error> {
    let first = fs::read_to_string(a)?;
    let second = fs::read_to_string(b)?;
    Ok(first.len() + second.len())
}
?는 자동으로 에러를 변환한다 함수의 에러 타입과 ?가 마주친 에러 타입이 다르면, ?는 From 트레잇으로 자동 변환을 시도한다. 즉 SourceErr: Into<TargetErr>(혹은 TargetErr: From<SourceErr>)만 성립하면 변환 코드를 직접 쓰지 않아도 된다. 이 성질이 다음 절의 커스텀 에러 타입을 깔끔하게 만든다.

커스텀 에러 타입 만들기

실무 함수는 보통 여러 종류의 에러를 낸다. 설정을 읽다 보면 입출력 에러도, 파싱 에러도 날 수 있다. 이럴 때 enum으로 에러 종류를 모은 커스텀 타입을 정의하고, 각 원시 에러에서 From 변환을 구현해 두면 ?가 알아서 변환해 준다.

use std::fmt;
use std::fs;

// 이 모듈이 낼 수 있는 에러를 한 enum에 모은다.
#[derive(Debug)]
enum ConfigError {
    Io(std::io::Error),
    Parse(std::num::ParseIntError),
}

// 사람이 읽을 메시지. Error 트레잇은 Display를 요구한다.
impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            ConfigError::Io(e)    => write!(f, "io error: {e}"),
            ConfigError::Parse(e) => write!(f, "parse error: {e}"),
        }
    }
}

// 표준 Error 트레잇 구현(기본 메서드만으로 충분하다).
impl std::error::Error for ConfigError {}

// io::Error -> ConfigError 변환. ?가 이걸 자동으로 쓴다.
impl From<std::io::Error> for ConfigError {
    fn from(e: std::io::Error) -> Self {
        ConfigError::Io(e)
    }
}

// ParseIntError -> ConfigError 변환.
impl From<std::num::ParseIntError> for ConfigError {
    fn from(e: std::num::ParseIntError) -> Self {
        ConfigError::Parse(e)
    }
}

// 두 종류의 에러가 모두 ?로 ConfigError로 변환되어 전파된다.
fn load_port(path: &str) -> Result<u16, ConfigError> {
    let text = fs::read_to_string(path)?;   // io::Error -> ConfigError
    let port = text.trim().parse::<u16>()?; // ParseIntError -> ConfigError
    Ok(port)
}

이 패턴은 정확하지만 보일러플레이트가 많다. Display 구현, From 구현이 에러 종류마다 반복된다. 바로 이 반복을 없애 주는 것이 다음 절의 thiserror다.

thiserror와 anyhow

두 크레이트는 목적이 정반대다. 한 문장으로 가르면 — 라이브러리는 thiserror, 애플리케이션은 anyhow다.

thiserror — 라이브러리의 명시적 에러 타입

라이브러리는 호출자가 에러 종류별로 분기할 수 있도록 구체적인 에러 타입을 노출하는 게 좋다. thiserror는 앞 절의 Display·From·Error 구현을 매크로로 자동 생성해, 같은 결과를 훨씬 짧게 만든다.

// Cargo.toml: thiserror = "2"
use thiserror::Error;

#[derive(Debug, Error)]
enum ConfigError {
    // #[from]이 From 구현을, #[error]가 Display 메시지를 만든다.
    #[error("io error: {0}")]
    Io(#[from] std::io::Error),

    #[error("parse error: {0}")]
    Parse(#[from] std::num::ParseIntError),
}

// 본문은 앞과 동일하다. ?가 #[from] 변환을 그대로 쓴다.
fn load_port(path: &str) -> Result<u16, ConfigError> {
    let text = std::fs::read_to_string(path)?;
    let port = text.trim().parse::<u16>()?;
    Ok(port)
}

앞 절의 수십 줄이 enum 정의 몇 줄로 줄었다. Display·Error·두 개의 From이 모두 매크로로 생성되며, 호출자는 여전히 ConfigError::Io인지 ConfigError::Parse인지 패턴 매칭으로 구분할 수 있다.

anyhow — 애플리케이션의 단일 에러 타입

최종 실행 파일(애플리케이션)은 보통 에러 종류별 분기가 필요 없다. "어디서 왜 실패했는지" 메시지를 남기고 종료하면 충분하다. anyhow는 어떤 에러든 담는 anyhow::Error 하나로 통일하고, 맥락(context)을 덧붙이기 쉽게 해 준다.

// Cargo.toml: anyhow = "1"
use anyhow::{Context, Result};

// 반환 타입이 Result<u16> -- anyhow::Result는 에러 타입이 생략된 별칭이다.
fn load_port(path: &str) -> Result<u16> {
    // 서로 다른 에러들이 ?로 모두 anyhow::Error에 흡수된다.
    let text = std::fs::read_to_string(path)
        .with_context(|| format!("failed to read {path}"))?;
    let port = text.trim().parse::<u16>()
        .context("port must be a valid u16")?;
    Ok(port)
}

fn main() -> Result<()> {
    let port = load_port("app.toml")?;
    println!("port = {port}");
    Ok(())
}

with_context/context로 덧붙인 설명은 에러가 출력될 때 원인 체인과 함께 나와, 어디서 실패가 시작됐는지 추적을 돕는다. 종류별 처리가 필요 없으니 커스텀 enum을 정의할 필요도 없다.

C++과 이렇게 다르다 — 맥락은 자동이 아니라 명시적으로 쌓는다 C++에서 예외에 맥락을 더하려면 잡아서 새 메시지로 다시 던지는 식이 흔하고, 스택 추적은 표준이 아니라 도구·플랫폼에 의존한다. Rust의 anyhow는 ?로 전파하면서 with_context로 그 지점의 의미를 한 줄씩 덧붙이고, 이 맥락이 원인 체인으로 함께 출력된다. 무엇을 남길지는 개발자가 명시적으로 고른다.
고르는 한 줄 기준 호출자가 에러 종류로 분기해야 하면(라이브러리 공개 API) thiserror로 구체 타입을 노출한다. 분기 없이 실패를 보고하고 끝이면(애플리케이션 main 쪽) anyhow로 통일한다. 둘은 한 프로젝트에서 함께 쓰이기도 한다 — 내부 크레이트는 thiserror, 그것을 묶는 바이너리는 anyhow.

정리와 주의

  • 에러는 값이다 — 실패 가능성은 Result<T, E>로 시그니처에 드러나고, 호출자는 반드시 처리한다. 숨은 제어 흐름이 없다.
  • panic!은 버그용 — 회복 가능하면 Result, 깨질 수 없는 불변식이 깨졌으면 panic!. 운영 코드의 unwrap()은 빚으로 남는다.
  • ?는 전파의 기본기 — 성공이면 꺼내고 실패면 반환하며, From 변환까지 자동으로 해 준다.
  • 커스텀 타입은 enum + From — 손으로 짜면 정확하지만 장황하다. thiserror가 그 보일러플레이트를 없앤다.
  • 라이브러리는 thiserror, 애플리케이션은 anyhow — 분기가 필요하면 구체 타입, 보고만 하면 단일 타입.
