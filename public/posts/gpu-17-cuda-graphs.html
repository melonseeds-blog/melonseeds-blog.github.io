커널 실행 비용 문제

커널을 하나 실행할 때마다 CPU 쪽에서 할 일이 있다. 인자를 정리하고, 실행 명령을 만들어 드라이버를 거쳐 GPU의 명령 큐에 넣는다. 이 비용은 커널 하나당 수 µs 정도다. 커널이 수 ms씩 걸리는 일을 한다면 무시해도 되지만, 영상 처리 파이프라인처럼 짧은 커널을 프레임마다 수십 개 실행하면 이야기가 달라진다.

상황커널 시간실행 비용 비율
큰 행렬 곱 1개5 ms실행 비용 수 µs → 0.1% 미만
작은 영상 처리 커널 30개 (각 20 µs)합계 0.6 ms실행 비용 30 × 수 µs → 수십 % 수준까지 커질 수 있음

두 번째 경우에는 GPU가 커널 하나를 금방 끝내고 다음 명령을 기다리며 노는 시간이 생긴다. Nsight Systems 타임라인(8편)에서 GPU 줄의 커널들 사이에 빈틈이 보이고, CPU 줄은 실행 API 호출로 꽉 차 있다면 이 상황이다. 이것을 launch-bound라고 부른다.

CUDA Graph는 이 문제를 이렇게 푼다. 커널 실행, 복사, 메모리 설정 같은 작업 묶음과 그 사이의 의존 관계를 한 번 정의해 두고, 매 프레임에는 그 묶음 전체를 호출 한 번으로 실행한다. 드라이버는 정의 단계에서 미리 검사하고 준비해 두므로, 실행할 때 할 일이 크게 줄어든다.

그래프의 구성 요소

그래프는 노드(node)와 간선(edge)으로 이루어진다. 노드는 작업 하나, 간선은 "A가 끝나야 B를 시작"이라는 의존 관계다. 의존 관계가 없는 노드끼리는 GPU가 동시에 실행할 수 있다.

노드 종류하는 일
kernel커널 실행
memcpy메모리 복사 (CPU↔GPU, GPU↔GPU)
memset메모리를 값으로 채움
hostCPU 함수 호출 (그 안에서 CUDA API는 호출 불가)
event record / wait그래프 밖 스트림과 맞추기
mem alloc / free그래프 안에서 메모리 할당과 해제 (CUDA 11.4+, cudaMallocAsync를 캡처하면 생김)
child graph다른 그래프를 노드 하나로 넣음
conditional조건에 따라 실행 여부나 반복을 GPU에서 결정 (CUDA 12.3+)

그래프를 쓰는 과정은 세 단계로 나뉜다. 이름이 비슷해서 헷갈리기 쉬우므로 타입 이름과 함께 익혀 둔다.

단계타입함수비용
1. 정의cudaGraph_t스트림 캡처 또는 노드 직접 추가작음
2. 인스턴스화cudaGraphExec_tcudaGraphInstantiate큼 (검사, 준비). 한 번만
3. 실행-cudaGraphLaunch(exec, stream)작음. 매 프레임 반복

방법 1 - 스트림 캡처

가장 쉬운 방법이다. 평소처럼 스트림에 작업을 넣되, 앞뒤를 cudaStreamBeginCapture와 cudaStreamEndCapture로 감싼다. 캡처 중에는 작업이 실제로 실행되지 않고 그래프에 기록만 된다. 이미 스트림 기반으로 짠 코드(5편, 12편)를 거의 그대로 그래프로 바꿀 수 있다.

// one frame of a small vision pipeline, written the usual way
void EnqueueFrame(cudaStream_t s, const Buffers& b)
{
    cudaMemcpyAsync(b.dRaw, b.hRaw, b.rawBytes, cudaMemcpyHostToDevice, s);
    Normalize <<<b.grid, b.block, 0, s>>>(b.dRaw, b.dNorm, b.w, b.h);
    Blur3x3   <<<b.grid, b.block, 0, s>>>(b.dNorm, b.dBlur, b.w, b.h);
    Threshold <<<b.grid, b.block, 0, s>>>(b.dBlur, b.dMask, b.w, b.h, b.th);
    cudaMemsetAsync(b.dCount, 0, sizeof(unsigned int), s);
    CountMask <<<b.grid, b.block, 0, s>>>(b.dMask, b.dCount, b.w * b.h);
    cudaMemcpyAsync(b.hCount, b.dCount, sizeof(unsigned int), cudaMemcpyDeviceToHost, s);
}

// --- build the graph once ---
cudaGraph_t     graph;
cudaGraphExec_t graphExec;

cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
EnqueueFrame(stream, buffers);                    // recorded, not executed
cudaStreamEndCapture(stream, &graph);

cudaGraphInstantiate(&graphExec, graph, 0);       // CUDA 12 signature
cudaGraphDestroy(graph);                          // the exec keeps its own copy

// --- every frame ---
while (running)
{
    GrabFrameInto(buffers.hRaw);                  // camera writes into the same pinned buffer
    cudaGraphLaunch(graphExec, stream);           // whole pipeline, one call
    cudaStreamSynchronize(stream);
    Report(*buffers.hCount);
}

cudaGraphExecDestroy(graphExec);
cudaGraphInstantiate 함수 모양은 버전마다 다름 CUDA 11까지는 cudaGraphInstantiate(&exec, graph, nullptr, nullptr, 0)처럼 오류 노드와 로그 버퍼를 받는 5인자 형태였다. CUDA 12부터는 cudaGraphInstantiate(&exec, graph, flags) 3인자 형태다. 예제를 가져올 때 사용하는 Toolkit 버전과 맞는지 확인한다.

캡처된 값은 고정된다

캡처할 때 넘긴 포인터와 인자 값이 그래프 안에 그대로 저장된다. 위 코드가 매 프레임 동작하는 이유는 카메라가 항상 같은 핀드 버퍼(hRaw)에 쓰고, 그래프는 그 고정된 주소에서 읽기 때문이다. 만약 프레임마다 다른 버퍼 주소를 넘기는 구조라면, 그래프는 여전히 캡처 당시 주소를 읽는다. 그래서 그래프를 쓸 때는 다음 원칙으로 설계한다.

원칙방법
버퍼 주소 고정입출력 버퍼를 처음에 한 번 할당하고 계속 재사용 (12편 버퍼 풀)
입력이 매번 다른 곳에 오면고정 버퍼로 복사하는 노드를 그래프 앞에 둠
링 버퍼 N개를 돌려 쓰면버퍼마다 그래프를 하나씩 미리 만들어 두고 번갈아 실행
임계값 같은 작은 인자가 바뀌면값 대신 GPU 메모리의 주소를 넘기고, 그 메모리 값을 바꿈. 또는 노드 인자 갱신 (아래)

여러 스트림을 한 그래프로 캡처

서로 상관없는 작업을 동시에 돌리려면 캡처 중에도 여러 스트림을 쓸 수 있다. 캡처 중인 스트림에서 이벤트를 기록하고, 다른 스트림이 그 이벤트를 기다리게 하면 그 스트림도 같은 캡처에 합류한다. 마지막에는 원래 스트림이 다른 스트림을 기다리게 해서 다시 합친다.

cudaEvent_t forkEv, joinEv;
cudaEventCreateWithFlags(&forkEv, cudaEventDisableTiming);
cudaEventCreateWithFlags(&joinEv, cudaEventDisableTiming);

cudaStreamBeginCapture(s0, cudaStreamCaptureModeGlobal);

Normalize<<<g, b, 0, s0>>>(dRaw, dNorm, w, h);

cudaEventRecord(forkEv, s0);            // fork: s1 joins the capture here
cudaStreamWaitEvent(s1, forkEv, 0);

EdgeDetect<<<g, b, 0, s0>>>(dNorm, dEdge, w, h);      // branch A on s0
Histogram <<<g, b, 0, s1>>>(dNorm, dHist, w * h);     // branch B on s1 (runs in parallel)

cudaEventRecord(joinEv, s1);            // join: s0 waits for s1
cudaStreamWaitEvent(s0, joinEv, 0);

Combine<<<g, b, 0, s0>>>(dEdge, dHist, dOut, w, h);

cudaStreamEndCapture(s0, &graph);       // end on the stream that began the capture
fork와 join으로 캡처한 그래프. 이벤트 대기가 간선이 된다

방법 2 - 노드를 직접 추가

스트림 캡처 대신 노드와 의존 관계를 API로 하나씩 만들 수도 있다. 코드는 길어지지만 그래프 구조를 정확히 통제할 수 있고, 나중에 특정 노드의 인자만 바꾸기 위해 노드 핸들을 들고 있기 좋다.

cudaGraph_t graph;
cudaGraphCreate(&graph, 0);

// kernel node: Normalize(dRaw, dNorm, w, h)
void* normArgs[] = { &dRaw, &dNorm, &w, &h };
cudaKernelNodeParams np = {};
np.func           = (void*)Normalize;
np.gridDim        = grid;
np.blockDim       = block;
np.sharedMemBytes = 0;
np.kernelParams   = normArgs;
cudaGraphNode_t normNode;
cudaGraphAddKernelNode(&normNode, graph, nullptr, 0, &np);        // no dependencies

// kernel node: Threshold(dNorm, dMask, w, h, th) depends on normNode
void* thArgs[] = { &dNorm, &dMask, &w, &h, &th };
cudaKernelNodeParams tp = np;
tp.func         = (void*)Threshold;
tp.kernelParams = thArgs;
cudaGraphNode_t thNode;
cudaGraphAddKernelNode(&thNode, graph, &normNode, 1, &tp);        // edge: norm -> threshold

cudaGraphExec_t exec;
cudaGraphInstantiate(&exec, graph, 0);

kernelParams에는 인자 값 자체가 아니라 인자 변수의 주소 배열을 넘긴다. 드라이버가 노드를 만들 때 그 주소에서 값을 복사해 가므로, 노드를 추가한 뒤에는 원래 변수가 사라져도 된다.

인스턴스화한 그래프 고치기

인스턴스화는 비싸므로, 인자가 조금 바뀔 때마다 다시 하면 그래프를 쓰는 의미가 줄어든다. 구조(노드와 간선)가 그대로이고 인자만 바뀐다면 이미 만든 실행 그래프를 고칠 수 있다.

방법쓰는 때
cudaGraphExecKernelNodeSetParams(exec, node, &params)노드 핸들을 들고 있고, 특정 커널의 인자만 바꿀 때 (명시적 API 방식에 잘 맞음)
cudaGraphExecMemcpyNodeSetParams1D 등복사 노드의 주소, 크기를 바꿀 때
cudaGraphExecUpdate(exec, newGraph, &info)스트림 캡처를 다시 해서 새 그래프를 만들고, 구조가 같으면 기존 실행 그래프에 반영 (재인스턴스화보다 쌈)
// re-capture with new arguments, then try to update in place (CUDA 12 signature)
cudaGraph_t newGraph;
cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);
EnqueueFrame(stream, buffersWithNewThreshold);
cudaStreamEndCapture(stream, &newGraph);

cudaGraphExecUpdateResultInfo info;
if (cudaGraphExecUpdate(graphExec, newGraph, &info) != cudaSuccess)
{
    // topology changed: fall back to a fresh instantiation
    cudaGetLastError();                    // clear the error state
    cudaGraphExecDestroy(graphExec);
    cudaGraphInstantiate(&graphExec, newGraph, 0);
}
cudaGraphDestroy(newGraph);

그래도 가장 좋은 설계는 갱신이 필요 없게 만드는 것이다. 임계값처럼 자주 바뀌는 작은 값은 GPU 메모리(또는 핀드 메모리)에 두고 커널이 포인터로 읽게 하면, 그 값만 바꿔도 그래프는 손댈 필요가 없다.

캡처 중에 하면 안 되는 일

캡처 중인 스트림의 작업은 실제로 실행되지 않으므로, 실행 결과를 기다리거나 확인하는 호출은 의미가 없거나 오류가 난다.

호출결과대신
cudaStreamSynchronize(capturingStream), cudaDeviceSynchronize()오류, 캡처가 무효가 됨동기화는 그래프 실행 뒤에
cudaMemcpy (동기 복사)오류cudaMemcpyAsync
cudaMalloc, cudaFree기본(Global) 모드에서 오류캡처 전에 할당, 또는 cudaMallocAsync/cudaFreeAsync
기본 스트림(0번, legacy)에서 캡처지원 안 함cudaStreamCreate로 만든 스트림 사용
캡처 중인 스트림에 cudaStreamQuery, cudaEventQuery오류그래프 실행 뒤 확인
라이브러리가 내부에서 동기화하는 함수캡처 실패라이브러리 문서에서 "graph capture safe" 여부 확인
캡처 모드 세 가지 cudaStreamCaptureModeGlobal은 캡처 중에 다른 스레드까지 포함해 위험한 호출을 막는다. ThreadLocal은 현재 스레드만, Relaxed는 막지 않는다. 처음에는 Global로 두고, 다른 스레드에서 정상적으로 cudaMalloc을 해야 하는 등의 이유가 있을 때만 완화한다.

효과 측정하기

그래프가 실제로 도움이 되는지는 직접 재 봐야 한다. 아주 짧은 커널을 여러 개 이어 실행하는 경우로 비교해 보자.

__global__ void Tiny(float* d, int n) { int i = blockIdx.x * blockDim.x + threadIdx.x; if (i < n) d[i] += 1.0f; }

const int KERNELS = 20, ITERS = 1000, N = 1 << 14;   // tiny kernels: launch cost dominates

// A) plain launches
cudaEventRecord(t0, s);
for (int it = 0; it < ITERS; ++it)
    for (int k = 0; k < KERNELS; ++k)
        Tiny<<<N / 256, 256, 0, s>>>(d, N);
cudaEventRecord(t1, s);

// B) the same 20 kernels captured once, launched as a graph
cudaStreamBeginCapture(s, cudaStreamCaptureModeGlobal);
for (int k = 0; k < KERNELS; ++k)
    Tiny<<<N / 256, 256, 0, s>>>(d, N);
cudaStreamEndCapture(s, &g);
cudaGraphInstantiate(&ge, g, 0);

cudaEventRecord(t2, s);
for (int it = 0; it < ITERS; ++it)
    cudaGraphLaunch(ge, s);
cudaEventRecord(t3, s);
cudaEventSynchronize(t3);

float msPlain, msGraph;
cudaEventElapsedTime(&msPlain, t0, t1);
cudaEventElapsedTime(&msGraph, t2, t3);
printf("plain %.3f ms, graph %.3f ms, per kernel %.2f us vs %.2f us\n",
       msPlain, msGraph, msPlain * 1000 / (ITERS * KERNELS), msGraph * 1000 / (ITERS * KERNELS));

커널이 짧을수록 그래프 쪽이 확실히 빨라진다. 반대로 커널 하나가 수백 µs 이상 걸리는 큰 일을 한다면 차이가 거의 없다. 결과를 해석할 때는 다음을 같이 본다.

확인할 것이유
인스턴스화 시간은 따로 잰다한 번만 드는 비용이므로 프레임당 시간에 섞으면 안 됨. 대신 프로그램 시작 시간에는 영향
CPU 사용률도 본다그래프의 이득은 GPU 시간보다 CPU 시간에서 더 크게 나타나기도 함. CPU가 다른 일(카메라 수신, UI)을 할 여유가 생김
Nsight Systems 타임라인커널 사이 빈틈이 줄었는지 눈으로 확인

언제 효과가 있나

상황효과설명
프레임마다 같은 순서로 도는 영상 파이프라인큼구조가 매번 같고 커널이 작고 많음. 그래프에 가장 잘 맞는 경우
딥러닝 추론 (고정 입력 크기)큼TensorRT의 enqueueV3를 캡처하거나 PyTorch의 CUDA Graph 기능으로 레이어 수백 개를 한 번에 실행
반복 솔버 (같은 단계 반복)큼CUDA 12.3+ conditional 노드로 반복 조건까지 GPU에서 판단 가능
큰 커널 몇 개작음실행 비용이 원래 작은 비율
프레임마다 영상 크기, 처리 순서가 바뀜작거나 손해매번 다시 캡처하고 인스턴스화하면 오히려 느림. 크기별 그래프를 몇 개 미리 만들어 두는 방법은 가능
14편 히스토그램 평활화를 그래프로 memset(히스토그램 0으로) → 히스토그램 커널 → LUT 커널 → 적용 커널 → 결과 복사, 이 다섯 작업을 한 번 캡처해 두면 프레임마다 cudaGraphLaunch 한 줄로 끝난다. 버퍼 주소만 고정해 두면 된다.

더 나아가기 - 새 기능들

기능버전내용
메모리 노드CUDA 11.4+그래프 안에서 cudaMallocAsync/cudaFreeAsync. 임시 버퍼를 그래프가 직접 관리하고 재사용
장치에서 그래프 실행CUDA 12.0+커널 안에서 다른 그래프를 실행 (device graph launch). CPU를 거치지 않고 다음 작업을 결정
conditional 노드CUDA 12.3+IF, WHILE 노드. GPU가 계산한 값에 따라 하위 그래프를 실행하거나 반복. 이후 버전에서 종류가 늘어남
그래프 디버그 출력CUDA 11.3+cudaGraphDebugDotPrint(graph, "g.dot", flags)로 Graphviz 그림을 만들어 구조 확인

캡처가 의도대로 됐는지 확인할 때는 cudaGraphDebugDotPrint가 유용하다. fork/join이 생각한 대로 병렬 가지를 만들었는지, 빠진 노드는 없는지 그림으로 바로 보인다.

흔한 함정

매 프레임 인스턴스화 루프 안에서 캡처와 cudaGraphInstantiate를 반복하면 일반 실행보다 느려진다. 인스턴스화는 시작할 때 한 번 하고, 루프에서는 cudaGraphLaunch만 호출한다.
프레임마다 바뀌는 포인터 캡처할 때의 포인터가 그래프에 저장된다. 프레임마다 다른 버퍼를 쓰는 코드를 그대로 캡처하면, 그래프는 계속 첫 프레임 버퍼를 처리한다. 오류도 나지 않으므로 찾기 어렵다.
캡처 오류를 확인하지 않음 캡처 중 금지된 호출이 있으면 cudaStreamEndCapture가 오류를 돌려주고 그래프가 만들어지지 않는다. 이후 cudaGraphInstantiate나 cudaGraphLaunch에서 엉뚱한 오류로 보일 수 있으므로, 캡처 단계마다 반환값을 확인한다.
host 노드 안에서 CUDA 호출 cudaLaunchHostFunc로 넣은 CPU 함수(host 노드)는 그래프 실행 흐름 안에서 호출되므로, 그 안에서 CUDA API를 부르면 안 된다. 결과 알림이나 로그 기록처럼 가벼운 일만 넣고, 무거운 후처리는 다른 스레드에 넘긴다.
