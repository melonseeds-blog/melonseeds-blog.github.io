기존 글과의 차이 "C++/CLI 바인딩" 글은 ref class·마샬링·Dispose 패턴 등 C++/CLI 문법 자체를 다룬다. 이 글은 그 위에서 WPF Viewer가 비전 코어를 실제로 어떻게 쓰는지에 집중한다. BitmapSource·Dispatcher·데이터 플로우 에디터와의 결합이 주제다.

WPF는 어떻게 C++ 코어와 통신하는가

WPF Viewer는 C#·.NET 위에서 돌고 ImagingLib 코어는 C++·OpenCV다. 두 세계 사이에 다리가 필요하다. 선택지는 크게 셋이다.

방식장점단점적합한 상황
C++/CLI같은 프로세스, zero-copy 가능, C++ 헤더 그대로 재사용Windows·MSVC 전용, .NET Core 3.1+에서만 가능단일 머신·고성능·이미지 전송 빈번
P/Invoke플랫폼 독립적인 C ABI, 가벼움C 인터페이스로 평탄화 필요, 객체지향 손실C 스타일 함수 몇 개만 노출하면 충분할 때
gRPC / IPC언어·프로세스 독립, 원격 가능직렬화 비용, 대용량 이미지 부담분산·다국어·서비스화

ImagingLib Viewer는 같은 PC에서 카메라 영상을 실시간 처리·표시한다. 이미지가 초당 수십 프레임 흐르므로 직렬화 오버헤드를 감당할 수 없다. C++/CLI가 자연스러운 선택이다.

WPF Viewer ↔ CLI Bridge ↔ Native Core — 같은 프로세스 내 3계층 구조

C++/CLI 핵심 복습

WPF 통합을 이해하려면 최소한 다음 개념은 잡고 가야 한다. 자세한 문법은 별도 글에서 다뤘으니 여기서는 통합에 직접 쓰는 부분만 정리한다.

기호의미예
ref class관리되는(.NET GC 대상) 클래스public ref class ImageNet
^관리 객체 핸들 (포인터 아님)String^ name
gcnew관리 힙에 객체 생성gcnew ImageNet()
pin_ptr<T>GC가 못 옮기게 고정한 포인터pin_ptr<byte> p = &arr[0];
!ClassName()finalizer — GC가 호출네이티브 자원 마지막 방어선
// 같은 .cpp 파일에 네이티브와 관리 코드를 섞을 수 있다.
#include "ImagingLib/Core/Image.h"   // 네이티브 헤더

#pragma managed
using namespace System;

public ref class ImageNet
{
public:
    ImageNet() { m_native = new ImagingLib::Core::Image(); }
    ~ImageNet() { this->!ImageNet(); }      // Dispose 진입점
    !ImageNet() { delete m_native; m_native = nullptr; }   // finalizer

    int Width  { int get() { return m_native->GetWidth(); } }
    int Height { int get() { return m_native->GetHeight(); } }

internal:
    ImagingLib::Core::Image* m_native;   // 같은 어셈블리에서만 접근
};

핵심은 ref class가 .NET 객체이면서 안에 네이티브 포인터를 들고 있다는 점이다. WPF는 C#처럼 이걸 쓰고, 내부에서는 C++ 객체가 동작한다.

브리지 계층 설계

3계층으로 나눈다. 각 계층의 책임을 분명히 한다.

계층프로젝트 형식책임
Native CoreC++ static/dynamic lib이미지 처리, OpenCV 호출. .NET을 모른다.
CLI BridgeC++/CLI DLL (/clr)ref class로 래핑, 마샬링, 콜백 변환
WPF ViewerC# .NET WPF exeUI, MVVM, BitmapSource 표시

브리지는 얇게 유지한다. 비즈니스 로직을 브리지에 넣지 않는다. C++/CLI 코드는 디버깅이 까다롭고 IntelliSense도 약하기 때문이다.

// ImagingBridge.h — CLI 브리지가 공개하는 API
#pragma once
#include "ImagingLib/Core/Image.h"
#include "ImagingLib/Core/Filter.h"

#pragma managed
using namespace System;
using namespace System::Windows::Media::Imaging;   // BitmapSource

namespace ImagingLib::Bridge
{
    public enum class FilterType
    {
        GaussianBlur,
        Median,
        Sobel
    };

    public ref class ImageNet
    {
    public:
        ImageNet();
        ImageNet(int width, int height, int channels);
        ~ImageNet();
        !ImageNet();

        property int Width   { int get(); }
        property int Height  { int get(); }
        property int Stride  { int get(); }

        // 네이티브 픽셀 버퍼를 BitmapSource로 변환
        BitmapSource^ ToBitmapSource();

    internal:
        ImagingLib::Core::Image* GetNative() { return m_native; }

    private:
        ImagingLib::Core::Image* m_native;
    };

    public ref class Processor
    {
    public:
        Processor();
        ~Processor();
        !Processor();

        ImageNet^ Apply(ImageNet^ src, FilterType type, int kernelSize);

    private:
        ImagingLib::Core::Processor* m_native;
    };
}

이미지 데이터 전달

WPF에서 이미지를 표시하려면 ImageSource 계열 객체가 필요하다. 보통 BitmapSource를 쓴다. 네이티브 픽셀 버퍼를 어떻게 거기까지 옮길지가 핵심이다.

픽셀 포맷 매핑

OpenCV와 WPF의 픽셀 순서가 다르다. 이걸 안 맞추면 색이 반전되거나 깨진다.

OpenCV (Mat)WPF (PixelFormat)비고
CV_8UC1 (그레이)PixelFormats.Gray81바이트/픽셀
CV_8UC3 (BGR)PixelFormats.Bgr24OpenCV 기본이 BGR — 그대로 맞음
CV_8UC4 (BGRA)PixelFormats.Bgra32알파 포함
CV_16UC1 (16-bit)PixelFormats.Gray16산업용 카메라에서 흔함
RGB가 아니라 BGR이다 OpenCV는 BGR이 기본인데 무심코 PixelFormats.Rgb24로 넘기면 R과 B가 뒤바뀐다. cv::cvtColor(..., COLOR_BGR2RGB)로 변환하거나, 그냥 Bgr24를 쓰면 된다.

한 번 복사로 BitmapSource 만들기

가장 단순한 방법. BitmapSource.Create는 픽셀을 자체적으로 복사해 보관한다.

// ImageNet::ToBitmapSource — CLI 브리지에서
BitmapSource^ ImageNet::ToBitmapSource()
{
    if (m_native == nullptr || m_native->IsEmpty())
        throw gcnew InvalidOperationException("Image is empty.");

    int w = m_native->GetWidth();
    int h = m_native->GetHeight();
    int stride = m_native->GetStride();
    int channels = m_native->GetChannels();

    System::Windows::Media::PixelFormat fmt =
        (channels == 1) ? System::Windows::Media::PixelFormats::Gray8
        : (channels == 3) ? System::Windows::Media::PixelFormats::Bgr24
        : System::Windows::Media::PixelFormats::Bgra32;

    // 네이티브 픽셀 버퍼 포인터
    IntPtr buffer(m_native->GetData());

    // WPF가 픽셀을 복사해 BitmapSource를 만든다.
    return BitmapSource::Create(
        w, h, 96.0, 96.0, fmt, nullptr,
        buffer, stride * h, stride);
}

장점은 단순하다는 것이다. 단점은 매 프레임마다 새 BitmapSource를 만들고 픽셀을 복사한다는 것. 라이브뷰처럼 빠르게 갱신할 때는 부담이 된다.

WriteableBitmap으로 zero-copy 갱신

한 번만 WriteableBitmap을 만들고 픽셀 버퍼만 갱신한다. WPF Image 컨트롤은 같은 객체를 바라보므로 새 객체 생성·바인딩 비용이 없다.

// ViewModel 측 (C#)
public class LiveViewModel : INotifyPropertyChanged
{
    public WriteableBitmap LiveBitmap { get; private set; }

    public void Initialize(int width, int height)
    {
        LiveBitmap = new WriteableBitmap(
            width, height, 96, 96, PixelFormats.Bgr24, null);
        OnPropertyChanged(nameof(LiveBitmap));
    }

    // CLI 브리지가 호출 (UI 스레드에서 호출되어야 함)
    public void UpdateFrame(IntPtr nativeBuffer, int stride, int height)
    {
        var rect = new Int32Rect(0, 0,
            LiveBitmap.PixelWidth, LiveBitmap.PixelHeight);

        LiveBitmap.WritePixels(rect, nativeBuffer, stride * height, stride);
    }
}

핵심은 WritePixels가 IntPtr을 직접 받는다는 것. 네이티브 픽셀 주소를 그대로 넘기면 WPF 내부에서 한 번만 복사한다(back buffer로). 매번 새 객체를 만드는 것보다 훨씬 가볍다.

관리 배열을 네이티브에 넘길 때 — pin_ptr

반대로 C#이 가진 byte[]를 네이티브에 입력으로 줄 수도 있다. GC가 배열을 움직이지 못하게 고정해야 한다.

void Processor::LoadFromManagedArray(array<Byte>^ pixels, int width, int height)
{
    if (pixels == nullptr) throw gcnew ArgumentNullException("pixels");

    pin_ptr<Byte> pinned = &pixels[0];   // GC가 못 옮기게 고정
    const unsigned char* native = pinned;

    m_native->LoadFrom(native, width, height);
    // 함수 종료 시 pin이 풀린다.
}

콜백 — delegate ↔ 함수 포인터

비전 처리는 비동기로 도는 경우가 많다. 끝났을 때 결과를 WPF에 알리려면 콜백이 필요하다. C# delegate와 네이티브 함수 포인터를 잇는다.

delegate 정의와 변환

// CLI 브리지 헤더
public delegate void ProcessCompletedHandler(ImageNet^ result);

public ref class Processor
{
public:
    event ProcessCompletedHandler^ ProcessCompleted;

    void ApplyAsync(ImageNet^ src, FilterType type, int kernelSize);

private:
    // 네이티브 코어에 등록할 콜백 진입점
    void OnNativeCompleted(ImagingLib::Core::Image* nativeResult);

    // delegate를 GC가 회수하지 못하게 잡아 두는 핸들
    GCHandle m_callbackHandle;
};
// 네이티브 코어가 받는 C 스타일 콜백 타입
// (코어 측 헤더에 typedef로 선언되어 있다고 가정)
typedef void (__stdcall *NativeCallback)(void* userData, ImagingLib::Core::Image* result);

void Processor::ApplyAsync(ImageNet^ src, FilterType type, int kernelSize)
{
    // C# delegate를 네이티브 함수 포인터로 바꿀 thunk delegate
    auto thunk = gcnew Action<IntPtr, IntPtr>(this, &Processor::ThunkCallback);
    m_callbackHandle = GCHandle::Alloc(thunk);    // GC 회수 방지

    IntPtr fp = Marshal::GetFunctionPointerForDelegate(thunk);
    auto nativeCb = static_cast<NativeCallback>(fp.ToPointer());

    m_native->ApplyAsync(
        src->GetNative(),
        static_cast<ImagingLib::Core::FilterType>(type),
        kernelSize,
        nativeCb,
        nullptr);
}
delegate를 GCHandle로 잡지 않으면 크래시한다 GetFunctionPointerForDelegate가 반환한 포인터는 GC가 해당 delegate를 살아 있다고 보지 않는다. 네이티브 코드가 나중에 호출하는 순간 이미 회수돼 액세스 위반이 난다. 반드시 GCHandle::Alloc으로 살려두고, 더 이상 안 쓸 때 Free한다.

스레딩과 Dispatcher

비전 처리는 백그라운드 스레드에서 돈다. WPF UI 객체(WriteableBitmap 포함)는 생성한 스레드에서만 만질 수 있다. 네이티브 콜백이 워커 스레드에서 오면, UI 작업은 Dispatcher로 넘긴다.

// ViewModel — CLI 브리지의 이벤트를 구독
public LiveViewModel()
{
    _processor = new ImagingLib.Bridge.Processor();
    _processor.ProcessCompleted += OnProcessCompleted;
}

private void OnProcessCompleted(ImagingLib.Bridge.ImageNet result)
{
    // 워커 스레드일 가능성이 높다. UI 스레드로 넘긴다.
    Application.Current.Dispatcher.Invoke(() =>
    {
        var rect = new Int32Rect(0, 0, result.Width, result.Height);
        LiveBitmap.WritePixels(rect, result.GetBuffer(),
            result.Stride * result.Height, result.Stride);

        StatusText = $"Processed at {DateTime.Now:HH:mm:ss.fff}";
    });
}
UI 스레드 밖에서 WriteableBitmap을 건드리면 즉시 예외다 InvalidOperationException: The calling thread cannot access this object because a different thread owns it.를 만난다. 무조건 Dispatcher로 넘기는 습관을 들인다. 짧은 작업은 Invoke, 결과가 필요 없으면 BeginInvoke가 빠르다.

Freezable로 크로스 스레드 사용

BitmapSource는 Freezable이다. Freeze()를 호출하면 불변이 되고, 어느 스레드에서든 읽을 수 있다. 작업 스레드에서 만든 BitmapSource를 UI 스레드로 넘길 때 유용하다.

// 워커 스레드
var bmp = nativeImage.ToBitmapSource();
bmp.Freeze();   // 이제 다른 스레드에서도 읽을 수 있다.

Application.Current.Dispatcher.Invoke(() => { CurrentFrame = bmp; });

에러 처리

네이티브는 ErrorCode를, .NET은 예외를 쓴다. 브리지에서 변환한다.

// ImagingException — 네이티브 ErrorCode를 담는 .NET 예외
public ref class ImagingException : Exception
{
public:
    property int Code;
    ImagingException(int code, String^ msg) : Exception(msg) { Code = code; }
};

// 변환 헬퍼
static void ThrowIfFailed(ImagingLib::Core::ErrorCode ec)
{
    using EC = ImagingLib::Core::ErrorCode;
    if (ec == EC::Success) return;

    String^ msg = gcnew String(ImagingLib::Core::ErrorCodeToString(ec));
    throw gcnew ImagingException(static_cast<int>(ec), msg);
}

// 사용
ImageNet^ Processor::Apply(ImageNet^ src, FilterType type, int kernelSize)
{
    auto result = gcnew ImageNet();
    auto ec = m_native->Apply(
        src->GetNative(),
        static_cast<ImagingLib::Core::FilterType>(type),
        kernelSize,
        result->GetNative());

    ThrowIfFailed(ec);
    return result;
}

C# 쪽은 평범하게 try-catch한다. .NET 개발자가 익숙한 모델로 자연스럽게 들어온다.

try
{
    var result = _processor.Apply(src, FilterType.GaussianBlur, 5);
    CurrentImage = result.ToBitmapSource();
}
catch (ImagingException ex)
{
    StatusText = $"Error {ex.Code}: {ex.Message}";
}

메모리 관리

핵심 원칙: ref class가 네이티브 자원을 소유하면 반드시 Dispose 가능해야 한다.

// 표준 패턴 — destructor와 finalizer를 함께 둔다.
ImageNet::ImageNet()
{
    m_native = new ImagingLib::Core::Image();
}

ImageNet::~ImageNet()        // IDisposable.Dispose() → 결정론적 호출
{
    this->!ImageNet();
}

ImageNet::!ImageNet()         // finalizer — GC가 호출 (보험)
{
    if (m_native != nullptr)
    {
        delete m_native;
        m_native = nullptr;
    }
}

C# 쪽은 using으로 결정론적으로 해제한다.

using (var img = new ImagingLib.Bridge.ImageNet(1920, 1080, 3))
using (var processor = new ImagingLib.Bridge.Processor())
{
    var result = processor.Apply(img, FilterType.Median, 3);
    // 스코프 끝나면 Dispose → 네이티브 메모리 즉시 해제
}
Dispose를 놓치면 네이티브 누수가 슬금슬금 쌓인다 finalizer는 보험이지 정답이 아니다. GC가 언제 돌지 모르고, 그동안 거대한 픽셀 버퍼가 계속 살아 있다. 1920×1080×3 = 약 6MB가 한 장이다. 라이브뷰에서 초당 60프레임이면 1초만 누수돼도 360MB다.

빌드 구성

세 프로젝트의 설정이 어긋나면 런타임에 못 만난다. 체크리스트는 다음과 같다.

항목Native CoreCLI BridgeWPF Viewer
플랫폼x64x64x64 (AnyCPU 금지)
CLR—/clr—
런타임MD/MDdMD/MDd (일치)—
.NET 타깃—net6.0-windows 등같은 TFM
출력.lib / .dll.dll (mixed).exe
AnyCPU는 함정이다 WPF 프로젝트의 기본값이 AnyCPU인데, CLI DLL은 보통 x64다. 32비트로 떨어진 프로세스가 x64 DLL을 로드하려다 BadImageFormatException으로 죽는다. 반드시 x64로 고정한다.

WPF 프로젝트의 .csproj는 다음처럼 둔다.

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net6.0-windows</TargetFramework>
    <UseWPF>true</UseWPF>
    <Platforms>x64</Platforms>
    <PlatformTarget>x64</PlatformTarget>
  </PropertyGroup>

  <ItemGroup>
    <ProjectReference Include="..\bridge\ImagingBridge.vcxproj" />
  </ItemGroup>
</Project>

    </Grid>
</Window>
BitmapScalingMode를 NearestNeighbor로 검사 영상은 픽셀 단위 확인이 필요한 경우가 많다. 기본 Linear는 보간으로 디테일을 흐리니, NearestNeighbor가 산업용 viewer에는 더 맞다.

프레임 레이트 조절

카메라가 100 FPS여도 화면이 60 Hz면 그 이상 그릴 이유가 없다. UI 갱신을 제한하면 CPU·GPU를 아낀다.

private DateTime _lastUiUpdate = DateTime.MinValue;
private static readonly TimeSpan _uiInterval = TimeSpan.FromMilliseconds(16);  // 약 60 FPS

private void OnFrameReady(ImageNet frame)
{
    var now = DateTime.UtcNow;
    if (now - _lastUiUpdate < _uiInterval) return;   // drop
    _lastUiUpdate = now;

    Application.Current.Dispatcher.BeginInvoke(() =>
    {
        var rect = new Int32Rect(0, 0, frame.Width, frame.Height);
        LiveBitmap.WritePixels(rect, frame.GetBuffer(),
            frame.Stride * frame.Height, frame.Stride);
    });
}

데이터 플로우 에디터와 통합

11편의 블록 에디터는 노드를 연결해 처리 흐름을 만든다. 그래프 모델은 C#이 들고, 실제 실행은 C++ 코어가 한다. 역할이 분리된다.

UI는 그래프를 편집·시각화, 코어는 IProcessBlock 체인을 실제로 실행
// FlowGraphRunner — C# 그래프를 코어에 넘겨 실행
public class FlowGraphRunner
{
    private readonly ImagingLib.Bridge.GraphExecutor _executor = new();

    public async Task RunAsync(FlowGraphViewModel graph)
    {
        // 1) C# 노드를 코어 블록 명세로 변환
        var spec = new ImagingLib.Bridge.GraphSpec();
        foreach (var node in graph.Nodes)
        {
            spec.AddBlock(node.Id, node.BlockType, node.Parameters.ToDict());
        }
        foreach (var conn in graph.Connections)
        {
            spec.AddEdge(conn.FromNodeId, conn.FromPort,
                         conn.ToNodeId,   conn.ToPort);
        }

        // 2) 코어에 위임. 결과는 노드별 이미지/메트릭
        _executor.NodeCompleted += (nodeId, result) =>
        {
            Application.Current.Dispatcher.BeginInvoke(() =>
            {
                var node = graph.FindNode(nodeId);
                node.PreviewBitmap = result.ToBitmapSource();
            });
        };

        await Task.Run(() => _executor.Execute(spec));
    }
}

UI는 노드를 끌어다 놓고 연결만 한다. 실행은 전부 네이티브에서 돈다. C++가 가진 성능과 OpenCV 자산을 그대로 쓰면서, 편집 경험은 C#·WPF의 풍성한 도구로 만든다. 이것이 C++/CLI 통합의 본래 매력이다.

대안 비교 — gRPC, Pipe, REST

C++/CLI가 항상 정답은 아니다. 상황에 따라 다른 답이 더 좋을 수 있다.

흔한 함정

Dispose 누락 → 네이티브 메모리 누수

이미 다뤘다. using 또는 명시적 Dispose 호출을 빼먹지 않는다. ImageNet, Processor처럼 네이티브를 들고 있는 모든 ref class에 적용된다.

delegate를 잡지 않아 콜백 시 크래시

Marshal.GetFunctionPointerForDelegate의 결과만 들고 delegate를 변수로 안 잡아두면 GC가 회수한다. 인스턴스 필드나 GCHandle에 보관한다.

UI 스레드 밖에서 UI 객체 접근

WriteableBitmap, ObservableCollection, 바인딩 대상 ViewModel 속성은 모두 UI 스레드에서만 만진다. 워커에서 Dispatcher.Invoke로 넘긴다.

픽셀 포맷 mismatch

OpenCV의 BGR을 PixelFormats.Rgb24로 넘기면 색이 뒤집힌다. Bayer 패턴이나 Mono10/Mono12 packed를 그대로 Gray8에 넣어도 망가진다. 카메라 포맷 → OpenCV 변환 → WPF 포맷 매핑 표를 코드에 박아둔다.

stride를 width와 혼동

BitmapSource.Create와 WritePixels는 stride(라인당 바이트 수)를 요구한다. width * channels가 아니라 정렬 패딩이 포함된 값이다. OpenCV Mat::step을 쓰면 된다.

AnyCPU와 비트수 불일치

이미 빌드 섹션에서 언급. WPF 프로젝트를 새로 만들면 잘 잊는다. CI에서 x64를 강제 검증하면 안전하다.

이제 흐름이 보인다. C#·WPF는 편집과 시각화를 담당하고, C++·OpenCV는 실행 엔진을 맡는다. 두 세계는 C++/CLI 브리지로 만난다. WPF 시리즈는 여기서 닫지만 이 viewer는 다른 시리즈와 이어져 있다.

  • C++ 시리즈 — Image 컨테이너, IProcessBlock, OpenCV 래핑은 Native Core의 뼈대다.
  • OpenCV·Vision 시리즈 — Blob, Template Matching, Measurement는 코어 블록의 알맹이다.
  • AI 시리즈 — ONNX 추론 블록을 추가하면 데이터 플로우 안에 딥러닝이 들어온다.

도구는 완성되는 게 아니라 자라난다. ImagingLib Viewer도 마찬가지다. 카메라 통합, 캘리브레이션 마법사, 측정 결과 리포트, CUDA 가속, 플러그인 블록 — 할 일이 줄지어 있다. 시리즈가 다음 단계의 기초가 되기를 바란다.

여기까지 함께 한 분께 머신비전 viewer 하나를 만들겠다고 마음먹는 일은 가볍지 않다. 12편을 끝까지 따라 왔다면 이미 절반은 만든 셈이다. 남은 절반은 손에 달렸다. 작은 블록 하나라도 직접 붙여 보면 그다음 길이 더 또렷해진다.
