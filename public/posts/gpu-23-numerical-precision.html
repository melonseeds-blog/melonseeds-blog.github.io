CPU와 GPU 결과가 다른 이유

CPU로 짠 영상 처리 코드를 CUDA로 옮기고 결과를 비교하면, 대부분 픽셀이 같은데 일부가 소수점 아래에서 다르거나 8비트 출력에서 1씩 차이 나는 일이 흔하다. 버그일 수도 있지만, 대부분은 부동소수점 계산 방식의 차이다. 원인을 알아야 "고쳐야 할 차이"와 "허용해야 할 차이"를 나눌 수 있다.

원인설명
FMA 합치기GPU 컴파일러는 a * b + c를 한 번만 반올림하는 FMA 명령 하나로 합친다. CPU 코드는 곱셈 후 한 번, 덧셈 후 한 번 반올림하는 경우가 많다
더하는 순서리덕션(13편)처럼 병렬 계산은 더하는 순서가 다르다. 부동소수점 덧셈은 순서에 따라 마지막 자리가 달라진다
수학 함수 구현sinf, expf, powf는 CPU 라이브러리와 CUDA 라이브러리의 구현이 달라 마지막 한두 자리가 다를 수 있다
fast math 옵션--use_fast_math를 켜면 나눗셈, 제곱근, 수학 함수가 빠른 근사 버전으로 바뀐다
8비트로 바꾸는 방식float를 정수로 바꿀 때 버림, 반올림, 짝수 반올림 중 무엇을 쓰는지가 코드마다 다르다

FMA - 더 정확하지만 다른 결과

FMA(fused multiply-add)는 a × b + c를 중간 반올림 없이 계산하고 마지막에 한 번만 반올림한다. 정확도는 오히려 더 좋다. 문제는 CPU 결과와 "다르다"는 점이다.

// nvcc contracts this into a single FMA by default (--fmad=true)
float y = gain * x + offset;

// force separate multiply and add (two roundings, like most CPU builds)
float y2 = __fadd_rn(__fmul_rn(gain, x), offset);

// force an explicit FMA (one rounding)
float y3 = __fmaf_rn(gain, x, offset);
방법범위쓰는 때
--fmad=false (nvcc 옵션)파일 전체CPU 결과와 비트 단위로 맞춰야 하는 검증 빌드
__fmul_rn, __fadd_rn그 식만특정 계산만 CPU와 같은 순서로 맞출 때
기본값 (FMA 허용)-일반 제품 코드. 더 빠르고 더 정확함
CPU 쪽도 FMA를 쓸 수 있음 최신 CPU 컴파일러도 최적화 옵션(예: AVX2 대상 빌드, -ffp-contract=fast)에 따라 FMA로 합친다. 같은 CPU 코드라도 빌드 옵션에 따라 결과가 달라질 수 있으므로, "CPU 결과가 정답"이라는 가정 자체를 조심한다.

--use_fast_math가 바꾸는 것

--use_fast_math는 nvcc 옵션 하나로 여러 설정을 한꺼번에 켠다. 속도는 빨라지지만 무엇이 바뀌는지 알고 써야 한다.

함께 켜지는 설정바뀌는 동작영향
-ftz=true아주 작은 수(비정규 수, denormal)를 0으로 바꿈1e-38보다 작은 값이 0이 됨. 영상 처리에서는 거의 문제없음
-prec-div=false나눗셈을 근사 계산마지막 한두 자리 오차
-prec-sqrt=false제곱근을 근사 계산마지막 한두 자리 오차
-fmad=trueFMA 합치기 허용 (기본값과 같음)-
수학 함수 대체sinf → __sinf, expf → __expf 등 하드웨어 근사 함수로 바뀜입력 범위에 따라 오차가 커질 수 있음 (특히 큰 각도의 __sinf)

파일 전체에 켜는 대신, 속도가 필요한 곳에만 빠른 함수(intrinsic)를 직접 쓰는 방법도 있다.

정밀 함수빠른 함수주의
x / y__fdividef(x, y)y가 매우 크면(2126 이상) 결과가 0이 됨
expf(x)__expf(x)상대 오차가 커질 수 있음
logf(x)__logf(x)1 근처 입력에서 오차
powf(x, y)__powf(x, y)내부적으로 exp(y × log(x))라 두 오차가 합쳐짐
sinf(x), cosf(x)__sinf(x), __cosf(x)|x|가 π 범위를 크게 벗어나면 오차 급증
감마 보정 LUT로 바꾸기 8비트 입력의 감마 보정에 powf를 픽셀마다 부르는 대신, 256개 값의 표(LUT)를 미리 정밀하게 계산해 두고 읽으면 빠르고 정확하다(14편의 LUT 적용과 같은 구조). 입력 값의 종류가 적으면 계산보다 표가 낫다.

float에서 8비트로 바꾸기

영상 처리 결과를 8비트 픽셀로 저장할 때 가장 자주 생기는 1 차이의 원인이다. 반올림 방식과 범위 자르기(saturate)를 정확히 정해야 한다.

float v = 254.6f;

unsigned char a = (unsigned char)v;                        // 254: truncation (C cast)
unsigned char b = (unsigned char)__float2int_rn(v);        // 255: round to nearest even
unsigned char c = (unsigned char)(v + 0.5f);               // 255: round half up (positive only)

// out of range: 300.f -> (unsigned char) gives an undefined/wrapped value
float big = 300.f;
unsigned char bad  = (unsigned char)big;                   // NOT 255
unsigned char good = (unsigned char)__float2int_rn(fminf(fmaxf(big, 0.f), 255.f));   // 255

// __saturatef clamps to [0, 1]: handy for normalized pipelines
unsigned char d = (unsigned char)__float2int_rn(__saturatef(v / 255.f) * 255.f);
함수반올림 방식2.5의 결과
(int)x0 쪽으로 버림2
__float2int_rn, rintf가장 가까운 값, 같으면 짝수 (banker's rounding)2
roundf가장 가까운 값, 같으면 0에서 먼 쪽3
(int)(x + 0.5f)절반 올림 (양수에서만 맞음)3

OpenCV의 saturate_cast<uchar>는 가장 가까운 값으로 반올림하고(같으면 짝수) 0~255로 자른다. OpenCV 결과와 맞춰야 한다면 __float2int_rn + 범위 자르기를 쓴다.

정수 넘침

8비트, 16비트 픽셀을 정수로 더하거나 곱할 때는 넘침에 주의한다. GPU에서 넘침은 오류 없이 조용히 값이 돌아간다.

계산위험대책
8비트 픽셀 두 개 더하기를 uint8_t로200 + 100 = 44 (256으로 나눈 나머지)int로 더한 뒤 범위 자르기
영상 전체 픽셀 합을 unsigned int로4K 12비트 영상은 한 장의 합만으로 약 340억이라 32비트 최댓값(약 42.9억)을 넘음unsigned long long
16비트 픽셀 제곱합 (분산 계산)65535² ≈ 42.9억으로 32비트 최댓값에 거의 닿아, 두 픽셀만 더해도 넘음unsigned long long 또는 double
좌표 곱 y * pitch + x를 int로큰 영상이나 3D 볼륨에서 20억을 넘음size_t로 계산
// 16-bit image variance: accumulate in 64-bit integers, no rounding error at all
__global__ void SumAndSumSq(const uint16_t* img, size_t n,
                            unsigned long long* sum, unsigned long long* sumSq)
{
    unsigned long long s = 0, q = 0;
    for (size_t i = blockIdx.x * (size_t)blockDim.x + threadIdx.x; i < n; i += (size_t)blockDim.x * gridDim.x)
    {
        unsigned long long v = img[i];
        s += v;
        q += v * v;
    }
    // block reduction as in part 13, then one atomicAdd per block
    s = BlockReduceSumU64(s);
    q = BlockReduceSumU64(q);
    if (threadIdx.x == 0) { atomicAdd(sum, s); atomicAdd(sumSq, q); }
}

정수 합은 더하는 순서와 상관없이 항상 같은 결과가 나온다. atomicAdd를 써도 결과가 매번 같으므로(14편), 회귀 테스트에 유리하다.

float 누적 오차와 Kahan 합

float는 유효 숫자가 약 7자리다. 큰 합계에 작은 값을 계속 더하면 작은 값이 묻혀 사라진다. 예를 들어 합계가 1,000만(107)일 때 0.5를 더하면, float로는 표현할 수 있는 간격이 1이라 0.5가 반올림되어 없어지거나 1이 된다.

방법정확도비용
트리 리덕션 (13편)순차 합보다 오차가 작음 (비슷한 크기끼리 더하기 때문)추가 비용 없음
double 누적유효 숫자 약 16자리게이밍 GPU는 double 연산이 float보다 수십 배 느림 (아래). 누적 변수 하나만 double이면 영향 작음
Kahan 보정 합float만으로 double에 가까운 정확도덧셈 4번 정도로 늘어남
// Kahan summation: carry the lost low-order bits in c
__device__ void KahanAdd(float& sum, float& c, float x)
{
    float y = x - c;          // corrected input
    float t = sum + y;        // big + small: low bits of y are lost here
    c = (t - sum) - y;        // recover what was lost (algebraically zero)
    sum = t;
}
// NOTE: --use_fast_math or aggressive reassociation may simplify c away.
// Keep this file without fast math, or use __fadd_rn / __fsub_rn for each step.
게이밍 GPU의 double 성능 GeForce 계열 GPU의 FP64(double) 처리량은 FP32의 1/32에서 1/64 정도다. 데이터센터용 일부 GPU만 1/2 수준이다. 커널 전체를 double로 바꾸면 크게 느려지므로, 오차가 쌓이는 누적 변수만 double로 두는 방식이 좋다.

FP16(half) 사용 시 주의

FP16은 메모리 이동량이 float의 절반이라 memory-bound 커널(22편)에서 효과가 크고, half2로 두 값을 한 명령에 계산할 수도 있다. 대신 표현 범위와 정밀도가 매우 좁다.

항목FP32FP16
최댓값약 3.4 × 103865504
유효 숫자약 7자리약 3자리
1 근처 간격약 1.2 × 10-7약 0.001
1024~2048 사이 간격약 0.00011 (정수만 표현)
#include <cuda_fp16.h>

// store as half, compute in float, store back as half
__global__ void ScaleHalf(const __half* in, __half* out, int n, float gain)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n)
    {
        float v = __half2float(in[i]);           // widen
        out[i] = __float2half_rn(v * gain);      // compute in float, round once
    }
}

// two values per instruction with half2 (n even, pointers 4-byte aligned)
__global__ void ScaleHalf2(const __half2* in, __half2* out, int n2, __half2 gain2)
{
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n2) out[i] = __hmul2(in[i], gain2);
}
12비트 이상 원시 영상을 FP16으로 저장 12비트 픽셀(0~4095)을 정규화 없이 FP16으로 저장하면 2048 이상에서는 2 단위로만 표현되어 값이 뭉개진다. 원시 영상은 정수 그대로 두거나, 0~1로 정규화한 뒤 FP16으로 바꾼다. 합계와 분산은 FP16으로 누적하지 않는다.

결과 비교 기준 정하기

CPU 기준 구현과 비교할 때(19편) "완전히 같아야 한다"는 기준은 대부분 맞지 않는다. 데이터 형식과 계산 종류에 따라 허용 기준을 정해 둔다.

출력권장 비교 기준
정수 계산만 하는 커널 (히스토그램, 정수 합, LUT 적용)완전히 같아야 함. 다르면 버그
8비트 출력, 내부 float 계산픽셀 차이 1 이하, 차이 나는 픽셀 비율 상한 (예: 0.1%)
float 출력상대 오차 1e-5 정도 + 0 근처 값을 위한 절대 오차
float 합계, 평균 (리덕션)상대 오차 1e-5~1e-4 (원소 수가 많을수록 넉넉히)
fast math, FP16 사용위 기준보다 넓게. 실제로 잰 최대 오차를 근거로 정함
// tolerance check: |gpu - cpu| <= abs + rel * |cpu|
bool Close(float gpu, float cpu, float absTol = 1e-6f, float relTol = 1e-5f)
{
    return std::fabs(gpu - cpu) <= absTol + relTol * std::fabs(cpu);
}

흔한 함정

fast math를 프로젝트 전체에 켜기 속도가 중요한 파일에만 켜거나, 빠른 함수를 직접 쓴다. 계측, 캘리브레이션처럼 값 자체가 결과인 코드가 같은 빌드 옵션을 공유하면 정확도가 조용히 떨어진다.
double 상수가 섞여 느려짐 v * 0.5처럼 접미사 없는 실수 상수는 double이라, float 커널 안에서 double 연산이 생긴다. 게이밍 GPU에서는 이것만으로 커널이 크게 느려질 수 있다. float 커널에서는 0.5f처럼 항상 f를 붙인다.
NaN 전파 0으로 나누기, 음수의 제곱근, log(0)은 NaN이나 inf를 만들고, 이후 모든 계산으로 퍼진다. NaN은 자기 자신과 비교해도 같지 않으므로(v != v) 결과 비교 코드에서 따로 확인한다. 필터의 정규화 분모, 표준편차 나눗셈에는 작은 값(epsilon)을 더해 둔다.
