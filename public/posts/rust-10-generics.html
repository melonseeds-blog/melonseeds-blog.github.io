제네릭(Generics)

2026-06-25 약 8분 분량 Rust 시리즈
이 편에서 배우는 것 타입을 매개변수로 받는 제네릭 함수와 구조체를 작성한다. T: Trait 트레이트 바운드로 "이 타입이 무엇을 할 수 있어야 하는가"를 명시한다. 여러 바운드가 길어질 때 where 절로 정리한다. 마지막으로 제네릭이 런타임 비용 없이 동작하는 원리인 모노모피제이션(단일화)을 본다. C++ 템플릿과 비교해 어디가 같고 어디가 다른지도 짚는다.

왜 제네릭인가

같은 로직을 타입만 바꿔 가며 여러 번 복사한 경험이 있다면 제네릭이 푸는 문제를 이미 안다. i32 슬라이스에서 최댓값을 찾는 함수를 짰는데, 곧 f64 버전도, char 버전도 필요해진다. 본문은 글자 하나 다르지 않은데 타입 때문에 세 벌이 생긴다.

제네릭은 타입을 매개변수로 받아 이 중복을 없앤다. 함수나 구조체를 "어떤 타입 T에 대해서든"이라는 형태로 한 번만 쓰고, 호출하는 쪽이 구체 타입을 채운다. 핵심은 Rust의 제네릭이 이 일반화를 런타임 비용 없이, 그러면서도 컴파일 시점에 타입 안전성을 완전히 보장하며 해낸다는 점이다.

C++ 경험자를 위한 한 줄 Rust 제네릭은 C++ 템플릿과 같은 자리를 차지한다 — 둘 다 컴파일 시점에 타입별 코드를 찍어 낸다. 결정적 차이는 제약을 거는 방식이다. C++ 템플릿은 (C++20 concept 이전엔) 일단 인스턴스화해 보고 본문에서 안 되는 연산이 나오면 그제서야 에러를 뱉는다. Rust는 트레이트 바운드로 "이 T는 이런 능력이 있어야 한다"를 선언하게 강제한다. 이 점에서 Rust 제네릭은 C++20 concept으로 제약한 템플릿에 가깝다.

제네릭 함수

함수 이름 뒤에 <T>로 타입 매개변수를 선언하면 본문에서 T를 보통 타입처럼 쓸 수 있다. 가장 단순한 예로, 무엇이든 받아 그대로 돌려주는 항등 함수를 보자.

// T는 호출 시점에 결정되는 타입 매개변수다.
fn identity<T>(value: T) -> T {
    value
}

fn main() {
    let a = identity(42);          // T = i32
    let b = identity("hello");     // T = &str
    println!("{a} {b}");           // 42 hello
}

하지만 T에 아무 제약이 없으면 본문에서 할 수 있는 일이 거의 없다. 예를 들어 "두 값 중 큰 쪽을 돌려준다"를 제네릭으로 쓰려면 T끼리 비교할 수 있어야 한다. 비교 능력은 표준 라이브러리의 PartialOrd 트레이트가 제공하므로, 그 능력을 요구해야 한다.

// T는 PartialOrd를 구현한 타입이어야 한다(비교 가능).
fn larger<T: PartialOrd>(a: T, b: T) -> T {
    if a > b { a } else { b }
}

fn main() {
    println!("{}", larger(3, 7));        // 7
    println!("{}", larger(2.5, 1.0));    // 2.5
    println!("{}", larger('a', 'z'));    // z
}

여기서 T: PartialOrd가 바로 트레이트 바운드다. 이 바운드를 빼면 a > b 줄에서 "이 T가 비교 가능한지 보장이 없다"며 컴파일이 거부된다. 본문을 보고 추론하는 게 아니라, 시그니처에 적힌 약속만으로 검사한다는 점이 중요하다.

제네릭 구조체와 메서드

구조체도 타입 매개변수를 가질 수 있다. 좌표쌍을 담는 Point<T>를 보자. 두 필드가 같은 T이므로 둘은 항상 같은 타입이다.

struct Point<T> {
    x: T,
    y: T,
}

// impl 뒤에도 <T>를 선언해야 메서드에서 T를 쓸 수 있다.
impl<T> Point<T> {
    fn new(x: T, y: T) -> Self {
        Point { x, y }
    }

    // 필드를 빌려서 반환하므로 소유권을 옮기지 않는다.
    fn x(&self) -> &T {
        &self.x
    }
}

fn main() {
    let p = Point::new(3, 4);          // Point<i32>
    let q = Point::new(1.5, 2.5);      // Point<f64>
    println!("{}", p.x());             // 3
    println!("{}", q.x());             // 1.5
}

특정 타입에만 존재하는 메서드도 둘 수 있다. 아래는 Point<f64>일 때만 원점까지의 거리를 계산하는 메서드를 더한 것이다. i32로 만든 Point에는 이 메서드가 아예 생기지 않는다.

impl Point<f64> {
    // 이 메서드는 Point<f64>에만 존재한다.
    fn distance_from_origin(&self) -> f64 {
        (self.x * self.x + self.y * self.y).sqrt()
    }
}

fn main() {
    let p = Point::new(3.0, 4.0);
    println!("{}", p.distance_from_origin());   // 5
}

이렇게 impl Point<f64>처럼 구체 타입에 대해 따로 구현을 다는 패턴은, 타입별로 능력을 정밀하게 나눠 주는 Rust의 흔한 방식이다.

트레이트 바운드와 where 절

바운드는 여러 개를 동시에 걸 수 있다. 예를 들어 슬라이스에서 가장 큰 원소를 찾아 돌려주는 함수는 비교(PartialOrd)와 복제(Copy) 두 능력이 필요하다. +로 묶는다.

// T는 비교 가능하고(PartialOrd) 값 복사가 가능해야(Copy) 한다.
fn largest<T: PartialOrd + Copy>(list: &[T]) -> T {
    let mut max = list[0];
    for &item in list {
        if item > max {
            max = item;
        }
    }
    max
}

fn main() {
    let numbers = [34, 50, 25, 100, 65];
    println!("{}", largest(&numbers));     // 100

    let chars = ['y', 'm', 'a', 'q'];
    println!("{}", largest(&chars));       // y
}

Copy를 요구하는 이유는, let mut max = list[0];에서 슬라이스 원소를 값으로 가져오기 때문이다. Copy가 아니면 그 줄은 빌린 데이터에서 소유권을 옮기려다 빌림 규칙에 막힌다. 트레이트 바운드를 정확히 명시하면 이런 제약이 시그니처에 그대로 드러난다.

where 절 — 길어지면 분리한다

매개변수가 여럿이고 각자 바운드가 두세 개씩 붙으면 꺾쇠 안이 금방 빽빽해진다. 이럴 때 where 절로 바운드를 시그니처 본문 밖으로 빼면 한결 읽기 좋다. 아래 두 함수는 의미가 완전히 같다.

use std::fmt::Display;

// 인라인 바운드 — 꺾쇠 안이 빽빽하다.
fn show_pair<T: Display + Clone, U: Display + Clone>(a: T, b: U) {
    println!("{a}, {b}");
}

// where 절 — 시그니처가 한눈에 읽힌다(동작은 위와 동일).
fn show_pair_where<T, U>(a: T, b: U)
where
    T: Display + Clone,
    U: Display + Clone,
{
    println!("{a}, {b}");
}

fn main() {
    show_pair(1, "one");
    show_pair_where(2.0, 'b');
}
C++ concept과 이렇게 다르다 C++20에서 template<std::totally_ordered T>처럼 concept으로 제약하는 것과 Rust의 fn f<T: PartialOrd>는 발상이 같다 — 둘 다 "타입이 만족해야 할 요구사항"을 시그니처에 적는다. 다만 Rust는 이게 선택이 아니라 필수다. 바운드에 없는 능력은 본문에서 쓸 수 없고, 그래서 제네릭 함수 본문은 그 자체로 한 번에 검사된다. 호출처마다 인스턴스화해 보고서야 에러가 터지는 일이 없다. Rust의 where 절은 C++의 requires 절과 위치·역할이 거의 대응한다.

모노모피제이션 — 비용은 0

제네릭이 "타입을 추상화하니 런타임에 분기 비용이 들지 않을까" 걱정될 수 있다. Rust에서는 들지 않는다. 컴파일러가 모노모피제이션(monomorphization, 단일화)을 수행하기 때문이다. 제네릭 코드를 실제로 쓰인 구체 타입마다 한 벌씩 펼쳐, 전용 함수를 찍어 낸다.

앞의 identity를 i32와 &str로 호출하면, 컴파일러는 개념적으로 아래처럼 두 개의 전용 버전을 만들어 호출을 각각 연결한다.

// 우리가 쓴 코드
fn identity<T>(value: T) -> T { value }

// 컴파일러가 만들어 내는 것(개념적 모습)
fn identity_i32(value: i32) -> i32 { value }
fn identity_str(value: &str) -> &str { value }

그래서 실행 시점에는 타입 분기도, 동적 디스패치도 없다. 손으로 타입별 함수를 따로 짠 것과 같은 기계어가 나온다 — 이것이 Rust가 말하는 제로 코스트 추상화(zero-cost abstraction)다. 추상화의 대가는 런타임이 아니라 컴파일 시간과 바이너리 크기로 치른다. 쓰인 타입 조합이 많으면 그만큼 코드가 여러 벌 생기기 때문이다.

모노모피제이션은 C++ 템플릿과 같은 모델 C++ 템플릿도 인스턴스화 시점에 타입별 코드를 생성하므로, "런타임 비용 0, 컴파일 시간·코드 크기로 지불"이라는 트레이드오프가 동일하다. 즉 이 부분은 C++ 경험이 그대로 옮겨 온다. 다른 점은 앞서 본 제약을 거는 방식(트레이트 바운드)과 에러가 드러나는 시점(인스턴스화 전, 정의 시점)뿐이다.

정리

  • 제네릭은 타입 매개변수 — 함수 fn f<T>(...)와 구조체 struct S<T>로 중복 없이 타입을 일반화한다.
  • 트레이트 바운드로 능력을 요구한다 — T: PartialOrd + Copy처럼 적은 능력만 본문에서 쓸 수 있다. 본문 추론이 아니라 시그니처의 약속으로 검사한다.
  • where 절은 가독성용 — 바운드가 길어지면 본문 밖으로 빼되 의미는 그대로다.
  • 모노모피제이션으로 비용은 0 — 타입별 전용 코드를 찍어 내므로 런타임 분기가 없다. 대가는 컴파일 시간·바이너리 크기다.
  • C++ 대조 — 코드 생성 모델은 템플릿과 같고, 제약을 강제로 명시하게 하는 점은 C++20 concept에 가깝다.
