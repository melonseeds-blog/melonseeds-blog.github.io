개요 — Solution Guide II-A의 위치

머신비전 SDK 사용자가 매번 부딪히는 문제는 카메라·프레임 그래버 SDK가 표준화되어 있지 않다는 점이다. 장치를 바꾸면 획득 코드 전체를 다시 써야 하는 경우가 흔하다.

HALCON은 이 문제를 Image Acquisition Interface(IAI)로 풀었다. 50개 이상의 frame grabber와 수백 종 산업 카메라를 동적 로드 라이브러리(DLL/so) 형태로 감싸고, 사용자에게는 15개 operator로 구성된 공통 인터페이스만 노출한다.

Figure 1. Acquisition 경로 — Camera → Grabber → SDK/IAI → HALCON image

장치를 바꾸려 해도 operator 이름은 그대로 유지되고, open_framegrabber의 AcqName과 일부 파라미터 값만 달라진다는 것이 핵심이다.

Acquisition Interface 종류

실무에서 자주 사용하는 인터페이스는 크게 표준 인터페이스, 벤더 전용 인터페이스, 가상(File) 인터페이스로 나뉜다.

분류 대표 인터페이스 특징 파라미터 모델
표준 / Generic GenICamTL, GigEVision 장치 XML에서 파라미터를 동적으로 읽음 임의 파라미터, available_param_names 질의
표준 / 고정 1394IIDC (DCAM), Video4Linux, DirectShow, Twain 표준이 정의한 고정 파라미터 집합 지원 여부만 질의
벤더 전용 각 frame grabber/camera 전용 IAI SDK 고유 기능에 가장 가까움 벤더 문서 + special parameter
가상 File, DirectFile, Image Sequence 디스크의 이미지를 카메라처럼 읽음 경로·시퀀스 인덱스

Generic 인터페이스는 디바이스에 탑재된 XML(GenICam의 경우)을 읽어 파라미터 목록을 만들어낸다. 따라서 같은 인터페이스라도 카메라마다 사용 가능한 파라미터가 다르다. 다음과 같이 질의한다.

get_framegrabber_param(AcqHandle, 'available_param_names', Names)
* 각 파라미터의 메타 정보
get_framegrabber_param(AcqHandle, Name + '_range',       OutRange)
get_framegrabber_param(AcqHandle, Name + '_access',      OutAccess)
get_framegrabber_param(AcqHandle, Name + '_category',    OutCat)
get_framegrabber_param(AcqHandle, Name + '_visibility',  OutVis)

visibility는 beginner / expert / guru로 구분되어 있다. UI를 만들 때 초보자에게는 beginner 파라미터만 보이게 필터링하는 식의 활용이 가능하다.

가상 File 인터페이스의 가치 실제 카메라가 없는 PC에서도 동일한 grab_image 흐름으로 알고리즘을 개발·재현할 수 있다. 회귀 테스트, 현장 이슈 재현, 라인스캔 데이터 검증에 매우 유용하다.

General / Special / Dynamic 파라미터

HALCON은 파라미터를 두 축으로 분리한다.

분리 모델
  • General Parameter — 거의 모든 IAI에 공통. open_framegrabber 호출 시 전달.
  • Special Parameter — 인터페이스/장치 고유. set_framegrabber_param로 설정.
  • Fixed Parameter — 연결 수명 동안 고정. 변경하려면 닫고 다시 열어야 한다.
  • Dynamic Parameter — 연결 도중 변경 가능. 보통 동일 이름의 소문자 special 버전이 제공된다(예: image_width, external_trigger).

대표적인 General Parameter는 다음이다.

파라미터역할
HorizontalResolution, VerticalResolution전송 해상도 비율
ImageWidth, ImageHeight, StartRow, StartColumn전송 영역(ROI)
Field아날로그 카메라 grabbing 모드(interlaced/progressive)
BitsPerChannel, ColorSpace픽셀 데이터 구조
ExternalTrigger외부 트리거 사용 여부
CameraType, Device, Port, LineIn장치 식별
Generic인터페이스별 의미가 다른 일반 슬롯

지원하지 않는 파라미터에도 값을 반드시 채워야 한다. 그래서 string은 'default', 수치는 -1을 넣어 IAI 기본값에 위임하는 패턴이 표준이다. 실제 적용된 기본값은 info_framegrabber로 확인한다.

Special Parameter의 일부는 General Parameter의 동적 버전이다. 예를 들어 set_framegrabber_param(AcqHandle, 'image_width', 1024)처럼 소문자/언더스코어 이름을 쓴다. 일부 인터페이스에서만 동적 변경이 허용되므로 get_framegrabber_param으로 가능 여부를 사전 확인하는 편이 안전하다.

설정 가능 범위 질의 패턴은 다음과 같다.

get_framegrabber_param(AcqHandle, 'gamma_range', GammaRange)
MinGamma := GammaRange[0]
MaxGamma := GammaRange[1]
* 클램프 후 설정
set_framegrabber_param(AcqHandle, 'gamma', NewGamma)

grab 모드와 타이밍

같은 grab_image처럼 보여도 모드에 따라 타이밍과 frame rate가 크게 달라진다. Solution Guide II-A는 모든 모드를 타이밍 다이어그램으로 정리한다.

모드 호출 image delay frame rate 특징
표준 동기 grab_image 가변(최대 1 frame) 처리시간 포함 → 낮음 free-running 카메라 가정
비동기 리셋 grab_image + async-reset cam 거의 0 처리시간 포함 노출 타이밍 보장
Volatile 'volatile' on 표준과 같음 HImage 생성 시간 단축 버퍼 덮어쓰기 위험
비동기 grab grab_image_async 음수(이미 노출됨) camera frame rate 도달 가능 처리·grab 병렬
Continuous 'continuous_grabbing' on 음수 full frame rate grabber가 항상 받음

동기와 비동기 차이

표준 grab_image는 호출 후 카메라가 다음 vsync를 기다리고 → digitize → DMA 전송 → HImage 생성을 순차로 수행한 뒤 반환한다. 그러는 사이 카메라는 다음 프레임을 이미 내보내고 있으므로 free-running + 표준 grab 조합으로는 카메라가 만들어내는 모든 프레임을 처리할 수 없다.

grab_image_async는 이미지를 받자마자 IAI가 자동으로 다음 grab 명령을 grabber에 내려놓는다. 그래서 애플리케이션이 처리하는 동안 다음 이미지가 동시에 채워진다. 단점은 명확하다 — 반환되는 이미지는 호출 시점보다 이전에 노출된 이미지다. 동적으로 파라미터를 바꿔도 다음 호출이 아니라 그 다음다음 호출부터 반영되는 함정이 있다.

Figure 2. grab_image vs. grab_image_async 타이밍 비교

Volatile grabbing

volatile은 IAI가 DMA 버퍼에서 HImage로 복사하지 않고 버퍼 포인터를 그대로 노출하는 모드다. HImage 생성 시간이 줄어들지만 다음 grab이 같은 버퍼를 덮어쓸 수 있다. 일반적으로 grayscale에서만 지원되고, 버퍼 수가 2개 이상이라면 다음 grab 동안 이전 이미지를 처리하는 정도까지는 안전하다. 일부 인터페이스는 'num_buffers'로 버퍼 수를 늘릴 수 있다.

HDevelop 안에서는 진짜 volatile이 아니다 HDevelop 환경에서는 안전을 위해 내부 복사가 일어난다. volatile의 실제 효과를 확인하려면 C++/.NET으로 export하거나 HDevEngine으로 실행해야 한다.

Continuous grabbing

일부 grabber는 grab_image_async로도 frame rate에 도달하지 못한다. 이미지를 받은 직후의 grab 명령이 카메라의 다음 vsync보다 늦게 도착하기 때문이다. 이를 'continuous_grabbing'으로 풀면 grabber가 free-running 카메라의 모든 프레임을 계속 받아 메모리로 전송하므로 full frame rate가 보장된다.

continuous는 모든 프레임을 처리할 때만 모든 프레임을 다 쓸 게 아니라면 PCI 대역폭을 낭비할 뿐이다. 다른 PCI 트래픽까지 블로킹할 수 있다.

MaxDelay의 의미

grab_image_async(Image, AcqHandle, MaxDelay)의 세 번째 인자는 "이미 받아둔 이미지가 너무 오래되었으면 버리고 새로 받아라"라는 임계값이다. 측정의 기준이 노출 시점이 아니라 IAI가 grabber에 마지막으로 내린 grab 명령 시점이라는 점이 함정이다. 대부분 SDK가 노출 타임스탬프를 제공하지 않기 때문이다.

또한 grab_timeout(special parameter)과 혼동하면 안 된다. grab_timeout은 "이 시간 안에 이미지가 안 오면 에러를 반환"하는 타임아웃이고, MaxDelay는 "신선도 임계값"이다.

External Trigger 설계

산업 현장에서 노출 시점은 보통 PLC·encoder·photo-eye 같은 외부 신호가 결정한다. HALCON에서는 다음 한 줄이면 외부 트리거 모드가 켜진다.

open_framegrabber(..., ExternalTrigger := 'true', ...)
* 또는 동적으로
set_framegrabber_param(AcqHandle, 'external_trigger', 'true')

중요한 것은 카메라가 어떤 종류인지다. free-running 카메라 + 외부 트리거 조합은 트리거 신호와 실제 노출 사이에 비결정적 지연이 생긴다. 트리거가 도착해도 카메라는 다음 vsync까지 기다리기 때문이다. 또 표준 grab_image를 쓰면 애플리케이션이 처리하는 동안 들어온 트리거는 그냥 사라진다.

실무 권장 조합은 명확하다.

산업 트리거 권장 조합
  • Asynchronously resettable camera — 트리거 도착 즉시 reset/expose
  • grab_image_async — 처리 도중에도 다음 트리거를 받아둠
  • grab_timeout — 신호 누락 시 무한 대기 방지
  • trigger_signal — rising/falling edge, 디바운스, 입력 라인 선택

몇몇 인터페이스는 트리거 신호로 노출 시간 자체를 제어한다(예: 트리거 펄스 폭 = 노출 시간). 이런 경우 'exposure_time' 파라미터 대신 PLC 측 펄스 폭이 노출을 결정하므로 신호 설계 단계에서 책임 위치를 명확히 해야 한다.

트리거 누락은 침묵한다 grab_timeout을 설정하지 않으면 트리거가 안 들어와도 애플리케이션은 그저 멈춰 있다. 운영자 입장에서는 "프로그램이 죽었다"로 보인다. 반드시 timeout을 설정하고 에러 코드 H_ERR_FGTIMEOUT(5322)을 잡아 외부 트리거를 끄거나 재초기화하는 복구 경로를 만들어야 한다.

멀티 카메라 동기화

여러 카메라를 동시에 다루는 구성은 크게 네 가지다.

구성open 횟수grab 방식동기화
Single board, single cam1handle 1개해당 없음
Multiple boards보드당 1handle 각각SW 또는 HW 트리거
Multiple handles per board카메라당 1handle 각각인터페이스가 처리
Port switching1'port' 변경 후 grab유사 카메라 필요
Simultaneous grabbing1한 번의 grab으로 다채널 이미지grabber HW가 보장

Port switching + 비동기 grab의 함정

같은 보드에 두 대를 연결하고 port를 바꿔가며 grab하는 패턴은 grab_image_async와 함께 쓸 때 위험하다. IAI는 이미지를 받자마자 다음 grab 명령을 자동으로 내리기 때문에, 사용자가 port를 바꾸기 전에 이미 이전 카메라에서 다음 이미지를 받기 시작할 수 있다.

인터페이스가 지원한다면 자동 grab을 꺼야 한다.

set_framegrabber_param(AcqHandle, 'start_async_after_grab_async', 'disable')
* 이제 모든 grab은 명시적으로
set_framegrabber_param(AcqHandle, 'port', Port1)
grab_image_start(AcqHandle, -1)
grab_image_async(Image1, AcqHandle, -1)

Simultaneous grabbing

일부 인터페이스는 한 번의 grab_image 호출로 여러 카메라의 이미지를 multi-channel HImage로 반환한다. 단, 하드웨어가 받쳐줘야 한다. 아날로그라면 A/D 컨버터가 카메라 수만큼 있어야 하고, 디지털이라면 별도의 grabbing unit이 필요하다. 인터페이스가 지원해도 보드가 지원하지 않을 수 있으니 보드 문서 확인이 필수다.

인터페이스가 지원하지 않는 환경이라면 다음과 같이 수동으로 동기화한다.

  • asynchronously resettable 카메라들을 각자 grabber에 연결
  • 공통 hardware trigger 신호를 모든 카메라에 분배
  • 각 핸들에 대해 grab_image_async 호출

메모리·컬러·라인스캔·콜백

표준 인터페이스의 컬러/Bayer 처리

GenICam 계열에서는 픽셀 포맷이 카메라 측에 정의되어 있다(Mono8/Mono12 Packed/Bayer RG8/RGB8 등). HALCON IAI는 이를 받아서 BitsPerChannel과 ColorSpace(General Parameter)로 사용자에게 노출한다. Bayer 입력은 IAI 또는 SDK가 디모자이킹하거나, 원본 그대로 받아 cfa_to_rgb 계열 operator로 후처리한다. 후자가 알고리즘적으로 더 유연하지만 CPU 비용이 든다.

Line scan

HALCON 관점에서 line scan은 그저 높이가 작거나 1인 area scan이다. grabber가 여러 라인을 묶어 "page"로 만들어 올려주는 경우가 많고, ImageHeight로 페이지 크기를 지정한다.

문제는 검사 대상이 페이지 경계를 가로질러 걸쳐 있을 때다. HALCON은 이 경우를 위한 전용 operator를 제공한다.

  • tile_images — 여러 페이지를 하나의 큰 이미지로 이어 붙임
  • merge_regions_line_scan — 인접 페이지의 region을 잇기
  • merge_cont_line_scan_xld — XLD 윤곽을 페이지 경계 너머로 잇기

Callback 함수

일부 인터페이스는 노출 완료, 전송 완료 같은 이벤트를 콜백으로 알려준다. set_framegrabber_callback으로 등록하고, 함수 시그니처에는 acquisition handle, 인터페이스 컨텍스트 포인터, 사용자 컨텍스트 포인터가 들어간다. 사용 가능한 콜백 타입은 'available_callback_types'로 질의한다.

콜백 함수는 짧아야 한다 내부적으로 callback 기반 동기화를 쓰는 인터페이스라면 사용자 콜백이 끝날 때까지 다음 콜백 처리가 막혀 frame rate가 떨어진다. event 기반 동기화를 쓰는 인터페이스라면 일정 대기 시간 후 자동으로 진행되어, 그 사이 다음 이벤트가 사라질 수 있다. 어느 쪽이든 사용자 콜백은 짧게 — 큐에 enqueue만 하고 처리는 워커 쓰레드로 미루는 것이 안전하다.

메모리 관리와 미지원 장치

HALCON IAI가 지원하지 않는 카메라라도 외부 SDK가 메모리 버퍼를 제공한다면 HALCON image로 감쌀 수 있다. 이때 다음 세 가지를 명확히 해야 한다.

  • 버퍼 수명 — HALCON이 참조하는 동안 SDK가 회수하면 안 된다
  • copy 여부 — copy하면 안전하지만 비용이 든다. zero-copy를 쓰려면 buffer pool 관리가 필요하다
  • stride/pitch — 라인 padding이 있는 버퍼라면 그대로 흘려보내면 깨진다

핵심 정리

  • IAI는 벤더 SDK 차이를 흡수하는 얇은 어댑터다 — operator는 그대로, 파라미터 값만 바뀐다.
  • General Parameter는 open_framegrabber에서, Special Parameter는 set_framegrabber_param에서. 동일 이름의 소문자 special 버전은 동적 변경용이다.
  • 실제 frame rate에 도달하려면 grab_image_async가 기본, 그래도 부족하면 'continuous_grabbing'.
  • 외부 트리거 시스템에서는 asynchronously resettable 카메라 + grab_image_async + grab_timeout 조합이 표준이다.
  • 멀티 카메라는 port switching보다 보드 분리 + HW 트리거 분배가 안정적이다. port switching을 쓴다면 start_async_after_grab_async를 반드시 점검한다.
  • MaxDelay는 노출 기준이 아니라 grab 명령 기준이다. 신선도가 정말 중요하면 SDK 타임스탬프를 직접 확인한다.
  • 콜백은 짧게, volatile은 신중히, 미지원 장치는 buffer ownership을 명시한다.
