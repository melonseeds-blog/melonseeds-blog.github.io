비동기 — async/await와 tokio

2026-06-25 약 8분 분량 Rust 시리즈
이 편에서 배우는 것 Rust의 비동기는 async fn이 곧바로 실행되는 함수가 아니라 Future라는 값을 만들어 낸다는 점에서 출발한다. 이 Future는 .await로 진행시키고, 실제로 돌리려면 런타임이 필요한데 표준 라이브러리에는 런타임이 없어 tokio 같은 외부 크레이트를 쓴다. 여러 작업을 한 스레드에서 겹쳐 돌리는 join!과, 비동기와 스레드를 언제 골라야 하는지까지 정리한다.

async fn과 Future — 게으른 값

동기 함수는 호출하는 순간 몸체가 실행된다. Rust의 async fn은 다르다. 호출해도 몸체가 즉시 돌지 않고, "이 일을 나중에 진행할 수 있다"는 약속을 담은 값 하나를 돌려준다. 이 값의 타입이 Future다. 즉 async fn은 "Future를 만드는 공장"이고, 그 Future는 누군가 진행시켜 주기 전까지는 아무 일도 하지 않는다.

async fn greet() -> String {
    // 이 몸체는 호출 시점에 실행되지 않는다.
    String::from("hello")
}

fn main() {
    // greet()는 String이 아니라 Future를 돌려준다.
    let fut = greet();
    // fut를 만들었을 뿐, 아직 "hello"는 만들어지지 않았다.
    // 진행시키지 않았으므로 이 프로그램은 아무 출력도 내지 않는다.
    let _ = fut;
}

핵심은 게으름(laziness)이다. greet()를 호출했다고 문자열이 생기는 게 아니라, "호출되면 문자열을 만들 준비가 된 Future"가 생긴다. 이 Future를 실제로 끝까지 돌리는 두 가지 방법이 다음 절의 .await와, 그 뒤의 런타임이다.

C++ 코루틴과의 첫 대조 C++20의 코루틴도 비슷하다. co_await를 쓰는 함수는 호출해도 몸체가 끝까지 실행되지 않고, 호출자에게 핸들(promise/awaitable)을 돌려준 뒤 멈춰 있을 수 있다. Rust의 async fn이 Future를 돌려주는 것과 발상이 같다. 다만 C++은 코루틴의 메모리 할당·재개 방식 같은 저수준을 직접 다룰 여지가 크고, Rust는 그 기계 장치를 컴파일러가 상태 기계로 자동 생성한다.

.await가 실제로 하는 일

Future를 진행시키는 가장 직접적인 도구가 .await다. fut.await라고 쓰면 "이 Future가 끝날 때까지 결과를 기다렸다가 그 값을 꺼낸다"는 뜻이다. 그런데 여기서 "기다린다"는 스레드를 잡고 노는 대기가 아니다.

Future가 아직 준비되지 않았다면(예: 네트워크 응답이 안 옴) .await 지점에서 현재 작업이 스스로 실행권을 양보(yield)한다. 그동안 같은 스레드는 다른 Future를 진행시킬 수 있다. 기다리던 일이 준비되면 런타임이 그 작업을 멈췄던 지점부터 재개한다. 이 "양보하고 나중에 재개"가 비동기의 본질이다.

async fn fetch_value() -> i32 {
    // 실제로는 여기서 I/O를 await 하며 양보할 수 있다.
    42
}

async fn run() -> i32 {
    // .await로 Future를 진행시키고 결과 i32를 꺼낸다.
    let value = fetch_value().await;
    value + 1
}

주의할 규칙이 하나 있다. .await는 async 문맥 안에서만 쓸 수 있다. 즉 async fn 몸체나 async 블록 안이어야 한다. 평범한 동기 fn 안에서는 .await를 쓸 수 없는데, 동기 함수에는 "양보하고 재개한다"는 장치가 없기 때문이다. 그러면 가장 바깥의 Future, 즉 main은 누가 돌리는가? 그 답이 런타임이다.

런타임이 필요한 이유와 tokio

Future는 게으른 값이라고 했다. 누군가 반복적으로 "조금 진행해 봐(poll)"라고 찔러 줘야 비로소 일을 한다. 이 일을 하는 주체가 비동기 런타임(executor)이다. 런타임은 준비된 작업을 깨워 진행시키고, 양보한 작업은 잠재워 두며, I/O 이벤트가 오면 해당 작업을 다시 깨운다.

중요한 사실: Rust 표준 라이브러리에는 비동기 런타임이 들어 있지 않다. 언어와 표준 라이브러리는 Future 트레이트와 async/.await 문법만 제공하고, 실제로 Future를 돌리는 엔진은 외부 크레이트에 맡긴다. 가장 널리 쓰이는 것이 tokio다. tokio를 의존성에 추가하고 #[tokio::main]을 붙이면, 평범해 보이는 async fn main이 런타임 위에서 돌아간다.

// Cargo.toml 에 의존성 추가가 필요하다:
// tokio = { version = "1", features = ["full"] }

#[tokio::main]
async fn main() {
    // 이 매크로가 런타임을 만들고 main의 Future를 끝까지 진행시킨다.
    let message = greet().await;
    println!("{message}");
}

async fn greet() -> String {
    String::from("hello")
}

#[tokio::main]은 마법이 아니라 코드 변환이다. 컴파일 시 이 매크로는 런타임을 생성하고, 우리가 쓴 async fn main의 몸체를 그 런타임에 넣어 끝까지 돌리는 일반 fn main으로 바꿔 준다. 그래서 우리는 비동기 코드를 자연스럽게 쓰면서도, 가장 바깥에서 Future를 누가 돌리느냐는 문제를 매크로에 위임할 수 있다.

C++과 이렇게 다르다 — 런타임의 위치 C++의 코루틴은 언어가 기계 장치(co_await/co_return, promise_type)를 제공하지만, "코루틴을 어떤 스케줄러 위에서 어떻게 돌릴지"는 표준 라이브러리가 거의 정해 주지 않아 직접 또는 외부 라이브러리로 채운다. Rust도 비슷하게 런타임을 언어가 아니라 외부 크레이트(tokio 등)가 담당한다. 차이는, Rust는 그 외부 런타임이 tokio로 사실상 표준처럼 수렴해 있어 "tokio를 쓴다"는 선택이 거의 기본값에 가깝다는 점이다.

join!으로 동시에 실행하기

여러 비동기 작업을 차례로 .await하면 앞 작업이 끝나야 다음이 시작된다. 두 작업이 서로 무관하다면 이건 낭비다. 한 작업이 I/O를 기다리며 양보하는 동안 다른 작업을 진행시키면, 같은 스레드에서도 둘을 겹쳐서 돌릴 수 있다. 이를 손쉽게 해 주는 것이 tokio의 join! 매크로다.

use tokio::join;

async fn task_a() -> i32 {
    10
}

async fn task_b() -> i32 {
    20
}

#[tokio::main]
async fn main() {
    // 두 Future를 동시에 진행시키고, 둘 다 끝나면 결과를 함께 받는다.
    let (a, b) = join!(task_a(), task_b());
    // join!은 두 작업이 모두 완료될 때까지 기다린다.
    println!("{}", a + b); // 30
}

여기서 짚을 점이 있다. join!은 기본적으로 한 스레드 안에서의 동시성(concurrency)이지, 여러 코어를 동시에 쓰는 병렬성(parallelism)이 아니다. 두 작업은 번갈아 진행되며, 한쪽이 .await에서 양보할 때 다른 쪽이 진행된다. 그래서 task_a와 task_b가 둘 다 양보 지점 없이 CPU만 태우는 계산이라면 join!은 별 이득이 없다. 진짜 효과는 둘 다 I/O처럼 "기다리는 시간"이 있을 때 나온다.

소유권 관점도 자연스럽다. join!에 넘긴 각 Future는 자기 결과를 소유한 채 진행되고, 완료되면 그 값을 튜플로 돌려준다. 빌림 규칙을 어기지 않으면서 여러 작업을 엮을 수 있다.

동시성과 병렬성을 구분한다 진짜로 여러 코어에 작업을 흩뿌리고 싶다면 tokio에서는 각 작업을 tokio::spawn으로 태스크로 띄운다. 그러면 런타임의 워커 스레드들에 분산되어 병렬로 돌 수 있다. join!은 "이 자리에서 여러 Future를 겹쳐 기다린다"에 가깝고, spawn은 "독립 태스크로 떼어 보낸다"에 가깝다.

비동기 vs 스레드 — 무엇을 고르나

"동시에 여러 일"을 하는 길은 두 갈래다. OS 스레드를 여러 개 띄우는 길과, 비동기로 한 줌의 스레드 위에 많은 작업을 얹는 길. 둘은 경쟁이 아니라 적합한 상황이 다르다.

구분OS 스레드비동기(async)
잘 맞는 일CPU를 오래 태우는 계산대기가 많은 I/O(네트워크·디스크)
작업 단위 비용스레드마다 스택 등 자원 큼작업 하나가 가벼움
동시 작업 수수백~수천 규모에서 부담수만 개도 한 줌의 스레드로 운용
필요한 것표준 라이브러리만으로 가능런타임(tokio 등) 필요

기준을 한 문장으로 줄이면 이렇다.

  1. I/O 대기가 지배적이고 동시 연결이 많다(웹 서버, 다수의 네트워크 호출)면 → 비동기. 기다리는 동안 다른 일을 진행시켜 한 줌의 스레드로 많은 작업을 감당한다.
  2. 무거운 계산으로 CPU를 꽉 채운다(이미지·수치 처리)면 → 스레드. 양보할 지점이 없으니 비동기의 이점이 적고, 코어 수만큼 스레드로 병렬화하는 편이 단순하다.
  3. 둘이 섞여 있다면 → 비동기를 기본 골격으로 두고, CPU를 오래 잡는 부분만 별도 스레드(또는 전용 풀)로 떼어 낸다. 무거운 계산을 비동기 작업 안에서 그냥 돌리면 그 작업이 양보하지 않아 같은 스레드의 다른 작업들이 멈춰 버린다.
async 함수 안에서 오래 막지 않는다 비동기 작업 안에서 양보 없이 오래 계산하거나, 동기 블로킹 호출(예: 표준 라이브러리의 블로킹 슬립)을 쓰면, 그 스레드에 얹힌 다른 작업들까지 함께 멈춘다. 무거운 계산은 전용 스레드로 떼어 내고, 비동기 문맥에서는 비동기용 도구를 쓴다. 이 "막지 않기" 규칙이 비동기 코드의 성능을 좌우한다.

정리하면, Rust의 비동기는 게으른 Future를 .await로 진행시키고, 그것을 실제로 돌리는 런타임(tokio)을 외부에서 끼워 넣는 구조다. join!로 한 스레드에서 여러 작업을 겹치고, 일의 성격(I/O냐 CPU냐)에 따라 비동기와 스레드를 고른다. 이 골격만 잡으면 나머지 비동기 API들은 그 위에 얹히는 응용으로 읽힌다.
